# 에이전트 시스템을 설계할 때 무엇을 고려해야 하는가

> 이 위키 전체를 **한 페이지**로 압축한 것이다. 설계는 **사용 시나리오 → 요구 변수 → 레이어 범위와 계약 → 단계별 선택 → 운영 설계** 순서로 내려간다. 각 항목 끝의 링크가 상세 페이지다. 처음 읽는 사람은 이 페이지 → [레퍼런스 아키텍처](01-reference-architecture.md) → [결정 트리](02-decision-guide.md) → 가장 가까운 [시나리오](../07-appendix-scenarios/00-overview.md) 순으로 읽는다.

## 한 문장 요약

에이전트 시스템은 **모델이 아니라 시나리오에서 시작**하고, **무엇을 근거로(Knowledge) · 어떻게 판단하고 행동하며(Reasoning/Action) · 사람과 어떻게 주고받는가(Interaction)** 를 레이어로 나눠 설계하되, 처음부터 **운영 가능한 상태**(10배가 되어도, 죽어도, 바뀌어도, 감사받아도 견디는 상태)를 목표로 한다.

```
사용 시나리오 ─▶ 요구 변수 7개 ─▶ 레이어 범위 + 계약 3개 ─▶ 단계별 선택 (Part 2·3·4) ─▶ 운영 설계 6축 (Part 1/07, Part 5)
   "누가 무엇을"      규모·데이터·지연·     지울 레이어부터       기본값에서 시작,        확장성·안정성·유지보수·
   "실패하면 누가      근거·규제·행동·        정하고, 경계의        조건이 있을 때만         변화 대응·관측성·거버넌스
    다치나"            조직                   스키마를 먼저          올린다
```

## 1. 시나리오에서 시작한다

기술 선택은 시나리오의 함수다. 같은 "문서 QA"라도 임직원 4천 명이 규정을 묻는 것과 외부 고객이 계약 조건을 묻는 것은 다른 시스템이다. 시나리오를 적을 때 반드시 답할 것:

| 질문 | 왜 중요한가 | 결정되는 것 |
|---|---|---|
| **사용자는 결과를 읽나, 조작하나, 승인하나** | Interaction 레이어의 필요 여부와 통제 수준 | 텍스트 응답으로 끝 / Controlled UI / 승인 카드 |
| **에이전트가 행동(툴 실행·데이터 변경·외부 전송)을 하나** | 행동이 있으면 게이트·승인·감사가 생략 불가 | 위험 등급, 가드레일 위치, HITL 설계 |
| **틀리면 누가 어떻게 다치나** | 가역성 × 영향 범위가 통제 두께를 정한다 | 위험 등급 1~5, 승인 수, 폴백 방향 |
| **답의 근거를 보여줘야 하나, 감사받나** | 근거 단위 스키마와 감사 추적의 필요 | citation 설계, 보존 정책, 설명가능성 |
| **질문이 한 문서 안에서 끝나나, 여러 개체를 건너뛰나** | 멀티홉·동일성 요구가 그래프·온톨로지 도입 여부를 정한다 | 벡터만 / 경량 온톨로지 + 그래프 |
| **지식·규칙·조직은 얼마나 자주 바뀌나** | 변화 빈도가 추상화 경계와 자동화 우선순위를 정한다 | 증분 동기화, 규칙 외부화, 어댑터 |

이 질문들의 답이 [결정 트리](02-decision-guide.md)의 입력 변수가 된다. 시나리오 작성 형식은 [시나리오 템플릿](../_templates/scenario.md), 작성된 예는 [문서 QA](../07-appendix-scenarios/01-enterprise-document-qa.md) · [커머스 상담 + UI](../07-appendix-scenarios/02-commerce-assistant-genui.md) · [운영 인시던트](../07-appendix-scenarios/03-ops-incident-agent.md).

## 2. 요구 변수 7개를 숫자로 적는다

| 변수 | 적을 것 | 가장 크게 바꾸는 선택 |
|---|---|---|
| **규모** | 문서·레코드 수, 갱신 빈도, 동시 사용자, 요청/일, 툴 수, 테넌트 수. 그리고 **"10배가 되면"** | 증분 vs 전체 재색인, 무상태 경로·큐·캐시, 툴 라우팅, 모델 티어 |
| **데이터 특성** | 정형/반정형/비정형/멀티모달 비율, 소스 수, 권한 구조 | 파서·청킹·인덱스 유형, 그래프 필요성, ACL 방식 |
| **지연 요구** | 실시간(<1초) / 대화형(<5초) / 배치. 첫 토큰과 완료 각각 | 결정 모델·소형 모델 라우팅, 캐시, 스트리밍 |
| **근거·정확도 요구** | 참고용 / 업무 지원 / 규제·감사 대상 | citation 강제 수준, 검증기, 골든셋 크기 |
| **규제·감사** | 개인정보, 산업 규제, 보존 기간, 설명 의무 | 감사 추적 분리, 삭제 전파, 온톨로지 기반 설명 |
| **행동과 위험** | 행동 목록 각각의 가역성 × 영향 범위 → 등급 1~5 | 게이트·승인·폴백·킬 스위치 두께 |
| **조직 경계·팀** | 툴·에이전트·프론트의 당사자가 둘 이상인가, 팀 규모·역량 | 프로토콜(MCP·A2A·AG-UI) 채택 여부, 프레임워크, RACI |

규모는 특히 **비용이 어느 변수에 비례하는지**를 함께 적는다. 문서 100만 건을 LLM으로 분류하면 인덱싱 비용이 서빙 비용을 넘고, 툴 50개를 매 턴 노출하면 컨텍스트 비용이 답변 비용을 넘는다. 상세: [1/07 확장성](../01-foundations/07-operations-vocabulary.md), [5/02 비용·라우팅](../05-cross-cutting/02-cost-latency-model-routing.md).

## 3. 레이어 범위를 정하고, 계약을 먼저 쓴다

[레퍼런스 아키텍처](01-reference-architecture.md)의 그림에서 **지울 노드부터** 정한다. 읽기만 하는 QA는 Interaction 레이어 대부분이 필요 없고, 모델 지식만으로 되는 변환 과업은 Knowledge 레이어가 필요 없다. 남은 레이어 사이에는 **계약 3개**를 스키마 파일로 먼저 쓴다.

| 계약 | 방향 | 최소 내용 | 없으면 생기는 일 |
|---|---|---|---|
| ① 근거 단위 | Knowledge → Reasoning | 근거 ID, 본문/트리플, 출처·버전·시점, 권한 태그, 신뢰도 | 답변에 citation을 못 붙이고, 삭제된 문서가 계속 인용된다 |
| ② 렌더 가능한 응답 | Reasoning → Interaction | 텍스트, citations, ui_intent(선택), 확신도, 승인 필요 여부, `degradation[]` | 프론트가 표·카드로 보여줄 수 없고, 저하 상태를 사용자가 모른다 |
| ③ 사용자 이벤트 | Interaction → Reasoning | 이벤트 유형(승인·거절·수정·선택), 대상 ID, 페이로드, 서버 재검증 결과 | "이 항목 수정"을 눌러도 에이전트 상태로 돌아갈 길이 없다 |

계약은 **안정적으로, 구현은 가변적으로**. 임베딩 모델·벡터DB·LLM·렌더러·프로토콜은 계약을 지키는 한 교체 가능해야 한다. 필드 추가는 자유, 삭제·의미 변경은 버전 상승.

## 4. 단계별 핵심 결정 — 기본값에서 시작한다

모든 단계에는 "판단이 어려울 때의 기본값"이 있다([결정 트리](02-decision-guide.md)의 단계별 기본값 34행). 기본값에서 시작해 **시나리오의 조건이 확인될 때만** 올린다.

**Knowledge — 무엇을 근거로** ([Part 2](../02-data-pipeline/00-overview.md))
- 근거 단위를 먼저 정하고 청킹·인덱싱을 거꾸로 설계한다. 하이브리드 검색(BM25 + dense)이 기본값
- 택소노미(분류 체계)만으로 되는지 먼저 본다. 멀티홉·동일성·설명 요구가 **확인된 뒤에** 경량 온톨로지와 그래프를 올린다
- 신선도(증분 동기화, 삭제 전파)와 권한(ACL-aware retrieval)은 나중에 붙일 수 없다. 메타데이터 스키마에 처음부터

**Reasoning / Action — 어떻게 판단하고 행동하나** ([Part 3](../03-agent-workflow-rag/00-overview.md))
- **가장 단순한 형태에서 시작한다.** 워크플로우로 충분한 것을 에이전트로 만들지 않는다. 자율성은 비용·지연·비결정성의 대가가 있다
- **판정과 생성을 분리한다.** "어느 경로인가, 승인이 필요한가, 합격인가"는 생성 과업이 아니다. 규칙 → 결정 모델·분류기 → LLM 순으로 가장 단순한 수단을 쓴다. 보안·권한·한도는 규칙만
- **근거는 입력에서 강제하고 출력에서 검증한다.** 구조화 출력으로 citation을 받고, 검증기(스키마 → 규칙 → 근거 부합)를 거친 뒤에만 사용자에게 간다
- 행동이 있다면 **행동 직전 규칙 게이트**(통과 / 차단 / 승인 / 저하)는 생략 불가. 코드 실행형(CodeAct)이라면 게이트를 샌드박스의 `call_tool` 경계로 옮긴다
- 상태는 명시적으로 모델링하고, 메모리는 no-memory 베이스라인과 비교해서만 채택한다

**Interaction — 사람과 어떻게 주고받나** ([Part 4](../04-dynamic-ui/00-overview.md))
- **기본값은 Controlled**(사전 정의 컴포넌트를 에이전트가 선택). 디자인 시스템·접근성·보안을 지키며 운영 가능한 유일한 패턴. 선언적 생성(Declarative)은 조합이 폭발적으로 필요할 때, 자유 생성(Open-ended)은 샌드박스 안에서만
- "어떤 UI를 띄울지"도 판정 문제다. 카탈로그가 닫혀 있으면 결정 모델·규칙이 LLM보다 싸고 예측 가능하다
- UI에서 돌아온 이벤트도 외부 입력이다. 서버에서 권한·스키마를 **다시** 검증한다. 승인 카드는 텍스트로 폴백하지 않는다
- 이 레이어는 프로토콜(AG-UI·A2UI·MCP Apps)이 수렴 중이라 가장 자주 바뀐다. 어댑터 뒤에 두고 버전을 고정한다

## 5. 운영 가능한 설계 — 여섯 축을 단계마다 답한다

PoC는 "되는가"를 묻지만 운영은 **"안 될 때, 열 배가 될 때, 바뀔 때, 감사받을 때"** 를 묻는다. 모든 단계 페이지의 "운영 설계" 섹션이 아래 여섯 축을 답하고, [종합 매트릭스](../05-cross-cutting/06-operational-design-matrix.md)가 레이어 간 불균형을 찾는다. 용어와 판단 기준은 [1/07](../01-foundations/07-operations-vocabulary.md).

| 축 | 설계 질문 | 판단 기준·도구 |
|---|---|---|
| **확장성** | 데이터·사용자·툴·테넌트가 **10배**가 되면 이 단계에서 무엇이 먼저 깨지나. 비용은 어느 변수에 비례하나 | 무상태 경로 + 외부 상태 저장소, 증분 처리, 큐·캐시, 파티셔닝, 모델 티어 라우팅 |
| **운영 안정성** | 이 단계가 **죽으면** 사용자에게 어떻게 보이나. 장애 모드마다 탐지 신호·자동 대응(폴백·저하)·사람 개입 기준이 있나 | 장애 모드 표, 폴백 방향은 위험 등급으로(읽기 경로는 계속, 행동 경로는 fail-closed), 서킷 브레이커, 킬 스위치, SLI/SLO·오류 예산 |
| **유지보수** | 무엇을 **바꾸면** 무엇을 다시 테스트하나. 함께 배포해야 하는 조합은 | 버전 관리 대상 5종(모델·프롬프트·인덱스·툴/규칙·카탈로그), 호환 매트릭스, 롤백 단위, 골든셋 회귀를 CI 게이트로, 카나리·섀도 |
| **변화 대응** | 지식·도메인 모델·모델·규칙·사용자 환경·프로토콜 중 **가장 자주 바뀌는 것**은 무엇이고, 어느 추상화 경계에서 흡수하나 | 안정 계약 vs 가변 구현, 프롬프트·규칙·카탈로그·임계값은 **코드가 아닌 설정**으로, 외부 의존은 포트·어댑터 뒤에, 시점 재현성(모든 레코드에 버전 키) |
| **관측성** | 장애 모드의 "탐지 신호"가 **실제로 어느 스팬·지표에서 나오나**. 알림마다 런북이 있나 | 한 요청 = 한 트레이스(`session → turn → invoke_agent → 단계 스팬`), 버전 키 5종, 지표 3종(RED·품질·흐름), 증상 기반 알림, 대시보드 3장. **"관측이 없으면 못 보는 장애"** 를 단계마다 하나씩 적는다 — 오류율 0인 실패, 스팬 부재로만 존재하는 누락, 서서히 이동하는 분포 |
| **거버넌스** | 누가 결정·승인·책임지나. 정책이 규칙·가드레일·게이트로 **실제로 이어지나**. 사후에 "왜 그 답이 나왔나"를 재구성할 수 있나 | 위험 등급표(가역성 × 영향 범위 → 1~5), 가드레일 세 지점(입력·출력·행동), 승인 매트릭스(만료 = 거부), RACI(A가 빈 행 없음), 감사 추적은 관측 로그와 저장소·보존 분리 |

세 가지 원칙이 여섯 축을 관통한다. **① 통제는 예방·탐지·교정 세 층**으로 — 가드레일만 있고 탐지가 없으면 뚫려도 모르고, 탐지만 있으면 알아도 못 멈춘다. **② 위험 등급이 통제 두께를 정한다** — 등급 1 행동에 승인을 걸면 승인 피로로 전부 승인하게 되고, 등급 5는 에이전트가 제안만 한다. **③ 변화는 레이어 안에 가둔다** — 임베딩 모델 교체가 UI에 보이면 계약이 잘못된 것이다.

## 6. 최신 기술을 대하는 태도

- 트렌드는 **그 단계의 선택지나 기본값을 실제로 바꿀 때만** 설계에 넣는다. 억지로 연결하지 않는다 ([트렌드 레이더](03-trend-radar-2026.md))
- 벤더 주장(`[벤더]`)과 2차 해설(`[2차]`)만으로는 채택하지 않는다. 독립 검증(`[검증]`) 또는 **우리 데이터로 실측**(`[실측]`)이 있어야 "채택"이다. 특히 한국어 성능은 거의 모든 모델·도구가 영어 중심이라 자체 평가셋이 필수
- 이 위키가 깊게 다루는 관심 주제 — **온톨로지**(멀티홉·설명 요구가 있을 때), **뉴로심볼릭**(LLM 출력이 행동으로 이어질 때 규칙이 최종 결정권), **결정 모델**(선택지가 닫힌 판정을 생성 없이) — 도 같은 기준을 따른다. 어디서 쓰이는지는 [레퍼런스 아키텍처의 표](01-reference-architecture.md)

## 7. 설계가 끝났다는 것의 의미 — 산출물 체크리스트

다음이 있으면 설계가 끝난 것이고, 하나라도 없으면 운영에서 그 비용을 열 배로 낸다.

- [ ] **시나리오 문서** — 1절의 질문 6개에 답하고, 요구 변수 7개가 숫자로 적힘
- [ ] **스코프 맵** — 레퍼런스 아키텍처 위에 쓰는 노드와 지운 노드(이유 포함)
- [ ] **계약 스키마 3개** — 근거 단위, 렌더 가능한 응답, 사용자 이벤트. 저장소에 파일로
- [ ] **결정 기록** — 단계마다 선택 / 대안 / 이유 / 근거 페이지 ([결정 트리](02-decision-guide.md)의 템플릿)
- [ ] **골든셋 20건 이상** — 첫 프롬프트를 쓰기 **전에**. 한국어·혼합 언어·비격식 포함
- [ ] **위험 등급표와 승인 매트릭스** — 모든 행동이 1~5에 놓이고, 등급 3 이상에 승인자·시한·만료 처리
- [ ] **RACI** — 프롬프트·모델·인덱스·툴 권한·카탈로그·온톨로지·규칙 각각의 A가 정해짐
- [ ] **장애 모드 표와 폴백** — 단계마다. 이 단계가 죽으면 사용자에게 어떻게 보이는가
- [ ] **SLO 초안과 알림→런북** — 측정 없이 선언한 숫자가 아니라 베이스라인 후 설정. 런북 없는 알림 없음
- [ ] **변화 대응 표** — 가장 자주 바뀌는 것, 흡수 경계, 코드 밖 설정 목록, 어댑터 뒤 외부 의존
- [ ] **트레이스 스키마** — 버전 키 5종이 모든 스팬에, 감사 레코드로 넘어가는 필드가 분리됨
- [ ] **운영 준비도 리뷰(ORR) 통과** — [종합 매트릭스의 통합 체크리스트](../05-cross-cutting/06-operational-design-matrix.md)

## 8. 흔한 실패와 그 원인

| 증상 | 실제 원인 | 이 페이지의 어느 절 |
|---|---|---|
| 검색 품질은 올랐는데 사용자 만족이 그대로 | 시나리오 없이 레이어 하나만 최적화. 사용자는 읽는 게 아니라 조작·승인하고 싶었다 | 1, 3 |
| 프롬프트를 바꿨는데 좋아졌는지 모른다 | 골든셋이 없다 | 7 |
| 에이전트가 데이터를 지웠는데 "가드레일이 있었다" | 입력 필터만 있고 행동 직전 게이트가 없었다 | 4, 5 거버넌스 |
| 문서가 10배 되자 재색인이 하루 넘게 걸린다 | 전체 재색인 전제, 증분·파티셔닝 없음 | 2, 5 확장성 |
| 삭제된 문서가 계속 인용된다 | 삭제 전파가 인덱스에서 끝나고 캐시·메모리·골든셋까지 가지 않았다 | 3 계약 ①, 5 변화 대응 |
| 모델 API 10분 장애에 빈 응답이 그대로 나갔다 | 폴백·저하 설계 없음 | 5 안정성 |
| 승인률 100%, 응답 2초 — 건강해 보이는데 사고가 났다 | 승인 피로. RED 지표로는 가장 건강해 보이는 실패 | 5 관측성·거버넌스 |
| 감사에서 "그때 왜 그 답이 나왔나"에 답을 못 한다 | 트레이스에 근거 ID·버전 키가 없고 감사 레코드가 관측 로그와 섞여 있었다 | 5 관측성·거버넌스 |
| 프로토콜 버전이 올라가자 프론트와 백엔드를 같이 고쳤다 | 어댑터 없이 SDK를 직접 호출했다 | 3, 5 변화 대응 |
| 결정 모델이 벤더 수치만큼 빠르지도 싸지도 않았다 | `[벤더]`를 `[실측]` 없이 채택했다 | 6 |
