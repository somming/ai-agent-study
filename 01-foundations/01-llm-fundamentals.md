# LLM 기초: 컨텍스트, 구조화 출력, 함수 호출

> **범위**: 에이전트 시스템 **설계자**가 알아야 할 LLM의 동작 특성과 그것이 설계에 주는 제약. 모델 내부 구조나 학습 방법은 다루지 않는다. 특정 벤더 API 문법도 다루지 않는다.

## 요약 (3줄)

1. LLM은 **컨텍스트 윈도우 안의 토큰**만 보고, 그 안에서도 위치에 따라 주의가 고르지 않다. 무엇을 넣을지보다 무엇을 빼고 어디에 둘지가 설계 문제다.
2. LLM의 출력을 프로그램이 소비하려면 **구조화 출력**(structured output)이 필요하다. 그 수단은 프롬프트 지시 → JSON 모드 → 함수 호출 → 제약 디코딩 → 결정 모델 순으로 강제력이 세진다.
3. 모든 판단을 가장 큰 모델에 맡기면 비용·지연이 통제되지 않는다. **모델 라우팅**은 선택이 아니라 기본 설계 요소다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** | 모델 호출의 입출력 계약: 컨텍스트 예산(토큰), 출력 스키마, 툴 인터페이스, 모델 선택 규칙 |
| **언제** | 모든 프로젝트의 설계 초기. 특히 Part 3의 어떤 페이지보다 먼저 |
| **어떻게** | ① 컨텍스트 예산을 정하고 구성 요소별로 배분 → ② 출력이 프로그램에 소비되는지 사람에게 읽히는지 구분해 구조화 수단 선택 → ③ 판단·분류·라우팅 과업과 생성 과업을 분리 → ④ 모델 티어(대/중/소/결정 모델)별 담당 과업 표를 만든다 |
| **왜** | 이 계약이 없으면 뒤의 모든 단계(검색 결과 몇 개를 넣을지, citation을 어떻게 받을지, 어떤 모델이 라우팅할지)가 각자 임의로 결정되어 비용과 품질이 예측 불가능해진다 |

## 문제와 맥락

LLM을 "자연어를 넣으면 자연어가 나오는 함수"로 취급하면 세 가지 문제가 생긴다.

- **컨텍스트 과적**: 검색 결과·히스토리·시스템 프롬프트를 전부 밀어 넣으면 비용이 선형으로 늘고, 품질은 오히려 떨어진다. 긴 컨텍스트에서 중간 위치의 정보를 놓치는 현상("lost in the middle")은 롱컨텍스트 모델에서도 RULER 류 스트레스 테스트에서 재현된다 `[2차]`.
- **출력 파싱 실패**: 자유 텍스트를 정규식으로 파싱하는 코드는 반드시 깨진다. 구조화 출력 수단을 쓰지 않으면 운영 중 조용히 실패한다.
- **비용 폭주**: "이 요청은 어느 경로인가" 같은 단순 판정에 최상위 모델을 쓰면 요청당 비용의 대부분이 판정에 쓰인다.

## 핵심 개념

### 컨텍스트 윈도우와 컨텍스트 예산

컨텍스트 윈도우는 모델이 한 번에 볼 수 있는 토큰 수다. 설계자는 이것을 **예산**으로 다룬다.

| 구성 요소 | 특성 | 설계 지침 |
|---|---|---|
| 시스템 프롬프트·지시 | 고정, 매 호출 반복 | 프롬프트 캐싱 대상. 길이보다 명확성 |
| 툴 정의 | 툴 수에 비례해 증가 | 툴이 20개를 넘으면 라우팅으로 부분 노출 검토 |
| 검색된 근거 | 가변, 품질 좌우 | 상위 k개 + 리랭킹 + 압축. [Part 3/03](../03-agent-workflow-rag/03-retrieval-reranking.md) |
| 대화 히스토리 | 턴마다 누적 | 요약·압축(compaction). [Part 3/08](../03-agent-workflow-rag/08-state-memory-context.md) |
| 메모리 | 세션 간 지속 | 관련도 기반 선별 주입 |
| 출력 여유 | 생성에 필요한 공간 | 구조화 출력일수록 예측 가능 |

롱컨텍스트(수백만 토큰)와 RAG는 대체 관계가 아니다. 롱컨텍스트는 복잡한 논리 추론에 유리하고 RAG는 고가치 근거를 선별해 공급한다는 보완 관계로 보는 것이 2026년 현재의 일반적 견해다 `[2차]`.

### 구조화 출력

LLM 출력을 프로그램이 소비하는 수단. 강제력이 약한 것부터.

1. **프롬프트 지시**: "JSON으로 답하라". 강제력 없음. 프로토타입 외에는 쓰지 않는다.
2. **JSON 모드**: 유효한 JSON임을 보장. 스키마 준수는 보장하지 않는다.
3. **함수 호출 / 툴 호출**: 스키마(JSON Schema)를 주면 그에 맞는 인자를 생성. 대부분의 벤더가 스키마 준수를 보장하는 모드를 제공. 에이전트 툴 실행의 표준 수단.
4. **제약 디코딩(constrained decoding / grammar)**: 디코딩 단계에서 문법에 맞지 않는 토큰을 차단. 오픈 모델 서빙(vLLM, llama.cpp 등)에서 가능. 스키마 준수가 100%.
5. **결정 모델**: 생성 자체를 하지 않고 타입드 질문에 대한 선택·점수·확률만 반환. 스키마 준수가 구조적으로 보장되고 보정 확률이 함께 나온다. [02 System 1 vs System 2](02-system1-vs-system2.md), [Part 3/11](../03-agent-workflow-rag/11-decision-layer.md).

**스키마 준수 ≠ 내용의 정확성**이다. 유효한 JSON으로 틀린 답을 할 수 있다. 구조화 출력은 파싱 실패를 없애는 것이지 환각을 없애는 것이 아니다.

### 함수 호출의 설계 단위

함수 호출은 "모델이 어떤 함수를 어떤 인자로 부르고 싶은지"를 구조화해 돌려주는 것이다. 실제 실행은 호출자의 책임이다. 설계 시 결정할 것:

- **툴 수와 노출 범위**: 모든 툴을 항상 노출하면 컨텍스트와 오선택이 늘어난다. 라우팅 후 관련 툴만 노출하는 2단계 구성이 일반적
- **병렬 호출 허용 여부**: 독립적인 툴은 병렬, 순서 의존은 직렬
- **실패 반환 형식**: 툴 실패도 구조화해 모델에 돌려준다. 자유 텍스트 에러는 모델이 오해한다
- 상세: [Part 3/09 툴과 MCP](../03-agent-workflow-rag/09-tools-and-mcp.md)

### 모델 라우팅

요청 또는 하위 과업의 성격에 따라 다른 모델(또는 결정 모델·규칙)로 보내는 것.

| 티어 | 담당 | 예 |
|---|---|---|
| 규칙 | 결정론적으로 판단 가능한 것 | 권한 검사, 포맷 검증, 금칙어 |
| 결정 모델 | 선택지가 닫힌 판정 | intent 분류, 경로 선택, 승인 필요 여부, 품질 합격 여부 |
| 소형 LLM | 단순 변환·추출 | 요약, 키워드 추출, 쿼리 재작성 |
| 대형 LLM | 복잡 추론·생성 | 근거 종합 답변, 계획 수립, 코드 생성 |

라우팅 자체도 판정이므로 결정 모델이나 소형 분류기가 맡는다. 라우팅을 대형 LLM이 하면 절감 효과가 사라진다. 상세: [Part 5/02](../05-cross-cutting/02-cost-latency-model-routing.md).

## 아키텍처 / 파이프라인

```
요청 ─▶ [규칙 검사] ─▶ [라우터: 결정 모델/분류기] ─┬─▶ 경로 A: 소형 LLM (변환)
                                                  ├─▶ 경로 B: 대형 LLM + 툴 (추론·생성)
                                                  └─▶ 경로 C: 규칙/템플릿 (모델 불필요)
각 LLM 호출 = [컨텍스트 조립: 예산 배분] ─▶ [호출] ─▶ [구조화 출력 검증] ─▶ [실패 시 재시도/폴백]
```

## 기술 비교표 — 구조화 출력 수단

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 프롬프트 지시 | 프로토타입, 사람이 읽는 출력 | 프로그램이 소비하는 모든 경우 | 하 | 표준 | `[검증]` 실패율 높음은 널리 알려짐 |
| JSON 모드 | 스키마가 느슨하고 필드 누락을 코드가 처리 가능 | 필수 필드·enum이 있는 경우 | 하 | 안정 | `[벤더]` |
| 함수 호출(스키마 보장 모드) | 에이전트 툴 실행, citation 구조화, 대부분의 운영 시스템 | 수백 개 툴을 동시에 노출해야 할 때(컨텍스트 비용) | 중 | 안정 | `[벤더]` 주요 벤더 공통 제공 |
| 제약 디코딩 | 오픈 모델 자체 서빙, 100% 스키마 준수 필요, 복잡한 문법(DSL) | 매니지드 API만 쓰는 경우(대개 미지원) | 중~상 (서빙 인프라) | 안정 | `[검증]` 오픈소스 구현 다수 |
| 결정 모델 (Jev, Decisions API) | 선택지가 닫힌 판정, 보정 확률이 필요, 저지연·저비용 대량 판정 | 자유 텍스트 생성이 필요한 과업, 한국어 검증 안 된 도메인 | 하 (호출당) / 중 (평가셋 구축) | 신생 (2026-09~) | `[벤더]` 성능 수치 미검증 |

### 선택 가이드

- **출력을 프로그램이 소비한다면** → 함수 호출(스키마 보장 모드)이 기본값. 이유: 매니지드·오픈 모델 모두 지원, 에이전트 툴과 같은 메커니즘
- **자체 서빙이고 복잡한 문법이 필요하다면** → 제약 디코딩. 이유: 100% 준수, 토큰 낭비 없음
- **출력이 선택·점수·예/아니오라면** → 결정 모델 또는 소형 분류기. 이유: 생성 비용과 지연이 불필요. 단 한국어 평가셋으로 `[실측]` 먼저
- **판단이 어려우면** → 함수 호출. 이유: 가장 넓은 호환성

## 설계 시 고려사항 (체크리스트)

- [ ] 컨텍스트 예산을 구성 요소별로 숫자로 적었는가 (예: 시스템 2k, 툴 3k, 근거 8k, 히스토리 4k, 출력 2k)
- [ ] 고정 부분(시스템 프롬프트, 툴 정의)이 캐싱되도록 호출 구조를 잡았는가
- [ ] 프로그램이 소비하는 모든 출력에 스키마가 있는가
- [ ] 스키마 검증 실패 시 재시도·폴백 경로가 있는가
- [ ] 판정 과업과 생성 과업을 분리했고, 판정은 결정 모델·분류기·규칙 중 하나가 맡는가
- [ ] 모델 티어별 담당 과업 표가 있고, 티어 변경이 설정으로 가능한가
- [ ] 모델 버전 고정(pinning)과 교체 시 회귀 평가 절차가 있는가 ([06 평가](06-evaluation-observability.md))

| 토큰 비용의 비선형성 | 긴 컨텍스트에서 비용·지연 급증 | 예산 상한, 압축, 라우팅 |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [07 운영 용어](07-operations-vocabulary.md). 이 페이지의 운영 단위는 **모델 호출 한 번**이다. 호출 하나를 어떻게 다루는지가 뒤의 모든 단계(검색·판정·생성·툴)의 운영 기준선이 된다. 레이어 간 비교는 [Part 5/06 운영 설계 종합 매트릭스](../05-cross-cutting/06-operational-design-matrix.md), 비용·라우팅 상세는 [Part 5/02](../05-cross-cutting/02-cost-latency-model-routing.md).

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 사용자·요청 | 모델 API의 분당 요청·토큰 한도(RPM/TPM)에 먼저 닿는다. 429가 늘고 재시도가 재시도를 부른다 | 호출 전 토큰 버킷으로 클라이언트 측 레이트 리밋, 우선순위 큐(대화형 > 배치), 멀티 키·멀티 리전 분산, 백프레셔(큐 길이 상한 초과 시 거부 응답) | 요청 수 × 요청당 호출 수 |
| 컨텍스트 크기 | 비용과 지연이 **입력 토큰에 선형**으로 는다. 근거 k·히스토리 길이를 늘리면 요청 수가 그대로여도 비용이 10배가 될 수 있다 | 구성 요소별 예산 상한을 설정값으로 강제(초과 시 압축·절단), 고정 접두사 캐싱, 출력 토큰 상한 | 입력 토큰(캐시 미스분) + 출력 토큰 |
| 과업 종류 | 모든 과업이 대형 모델로 가면 단순 판정 트래픽이 비용의 대부분을 차지 | 티어 라우팅 표(과업 → 규칙/결정 모델/소형/대형)를 설정으로 두고 티어별 호출 비율을 관측 | 티어별 호출 비율 |
| 테넌트 | 한 테넌트의 폭주가 공용 레이트 리밋을 소진해 다른 테넌트가 느려짐 | 테넌트별 한도·큐 분리, 모든 호출 트레이스에 테넌트 키 | 테넌트 수 × 테넌트별 한도 |

요청 경로는 무상태로 둔다. 캐시·레이트 리밋 카운터·큐는 외부 저장소에. 비용 관측의 최소 단위는 "호출당 (모델 ID, 입력·캐시·출력 토큰, 티어, 테넌트)"이고, 이것이 없으면 어느 축이 비용을 키우는지 알 수 없다.

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 모델 API 다운·5xx | 빈 응답 또는 무한 로딩 | 오류율, 서킷 브레이커 열림 | 서킷 열림 → 폴백 모델(다른 벤더 또는 하위 티어) → 캐시된 유사 응답 → 규칙·템플릿 경로. 폴백 상태를 응답에 표시 | 서킷이 일정 시간 이상 열려 있음(예시: 10분) |
| 지연 급증 | 응답이 평소보다 수 배 느림 | p95 지연이 SLO 초과 | 타임아웃 후 하위 티어로 1회 재시도, 스트리밍으로 체감 완화 | 지연 알림이 연속 발생 |
| 레이트 리밋 429 | 피크 시간대에 간헐적 실패 집중 | 429 비율, 큐 대기 시간 | 지수 백오프 + 지터, 우선순위 낮은 요청부터 지연·거부, 멀티 키 전환 | 큐 대기가 상한 초과 → 용량 증설 결정 |
| 구조화 출력 스키마 실패 폭증 | 기능이 "조용히" 틀림(파싱 실패 → 기본값 처리) | 스키마 검증 실패율의 급변(예시: 평소 1% → 10%) | 스키마 오류를 피드백으로 1회 재시도 → 폴백 모델 → 해당 기능 저하(자유 텍스트만 표시) | 실패율이 기준의 2배 이상으로 1시간 지속. 대개 모델 측 변경 신호 |
| 모델 자동 업데이트로 출력 분포 변화 | 같은 입력에 톤·길이·판정이 달라짐. 장애처럼 보이지 않아 늦게 발견 | 운영 judge 샘플링 지표 이동, 골든셋 야간 회귀 실패 | 자동 대응 없음. 고정 버전(pinning)이 유일한 예방 | 회귀 실패 즉시 — 핀 확인·롤백 |
| 폴백 모델도 장애 | 두 벤더가 동시에 느려짐 | 폴백 경로 오류율 | 규칙·템플릿·캐시 경로로 최종 저하("답변 생성이 지연되고 있습니다" + 검색 결과만 표시) | 즉시 |

SLI 후보: 호출 성공률, p95 지연(티어별), 스키마 검증 통과율, 캐시 적중률, 호출당 비용. SLO 초안(예시): 성공률 99.5%, 대형 티어 p95 ≤ 15초, 스키마 통과율 ≥ 98%. 이 단계에 쓰기 행동은 없으나 **재시도는 멱등해야 한다** — 같은 요청 ID의 재시도가 과금·로그에 중복 집계되지 않게.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| 모델 ID·버전(핀) | 모든 출력 분포, 구조화 출력 동작, 토큰화(예산 계산) | 전체 골든셋 + 스키마 테스트 + 지연·비용 베이스라인 | 프롬프트 세트, 파라미터(temperature·max_tokens), 라우팅 표 |
| 프롬프트 세트 | 해당 과업 출력 | 과업별 골든셋 | 모델 버전(호환 매트릭스의 한 셀) |
| 출력 스키마 | 하류 파서·UI | 스키마 호환 테스트(추가는 자유, 삭제·의미 변경은 버전 상승) | 소비자 코드 |
| 라우팅 표·예산 상한·임계값 | 티어별 비율, 비용, 지연 | 라우팅 정확도, 비용 시뮬레이션 | — (설정만 교체) |
| 어댑터(벤더 SDK 버전) | 호출 형식, 에러 매핑 | 어댑터 계약 테스트(모의 응답) | — |

**프롬프트-모델 호환 매트릭스**: 행 = 프롬프트 세트 버전, 열 = 모델 버전, 셀 = 골든셋 통과 여부와 날짜. 검증된 셀만 운영에 배포하고, 롤백 단위는 (모델 핀, 프롬프트 세트, 파라미터) 묶음이다. 벤더가 별칭(alias)만 제공하고 고정 버전을 제공하지 않으면 그 사실을 기술 부채로 기록하고 야간 골든셋 회귀로 드리프트를 감시한다.

기술 부채로 기록할 것: 고정 버전 미제공 모델, 특정 벤더에서만 되는 구조화 출력 옵션, 캐시 키에 프롬프트 버전이 포함되지 않은 경로.

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

이 단계에서 **가장 자주 바뀌는 것은 모델**이다(벤더의 버전 업데이트·별칭 이동·가격 개정·한도 조정). 다음이 프롬프트. 지식·규칙은 다른 레이어의 변화이고 이 단계에서는 "그 변화가 컨텍스트로 들어올 때 예산을 넘지 않는가"만 본다.

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| 모델 — 버전 | 출력 분포, 스키마 동작, 토큰화 | 포트 `generate(prompt, schema, budget)` · `decide(question, context)` · `embed(text)` | 어댑터 안의 모델 ID | 핀 변경 + 섀도·카나리 + 전체 골든셋 | Reasoning 전체(`embed` 교체는 Knowledge 전체 재임베딩) |
| 모델 — 벤더 | API 형식, 구조화 출력 방식(함수 호출 vs JSON 스키마 vs 제약 디코딩), 에러 코드, 토큰 계산 | 같은 포트 + 내부 공통 응답 형식(텍스트·구조화 결과·토큰 사용량·종료 사유) | 벤더 어댑터 | 새 어댑터 추가 → 어댑터 계약 테스트 → 호환 매트릭스 열 추가 | 어댑터 + 프롬프트 재검증 |
| 모델 — 가격·한도 | 티어 경제성, 429 빈도 | 라우팅 표의 스키마(과업 → 티어) | 라우팅 표의 값 | 설정 교체(배포 없음) + 비용 시뮬레이션 | 라우팅만 |
| 프롬프트 | 과업별 지시·예시 | 프롬프트가 받는 변수 이름(템플릿 계약) | 프롬프트 본문 | 코드 밖 저장소에서 버전 교체 + 과업 골든셋 | 해당 과업 |
| 출력 스키마 | 필드 추가·변경 | 소비자가 모르는 필드를 무시(tolerant reader) | 스키마 정의 | 추가는 마이너, 삭제·의미 변경은 메이저 + 소비자 재배포 | 하류 파서·UI |
| 지식·규칙(타 레이어) | 컨텍스트에 들어오는 양 | 예산 배분 스키마 | 예산 값 | 설정 교체 | 이 단계 없음(초과 시 압축만) |

- **코드 밖 설정으로 둘 것**: 프롬프트 세트, 출력 스키마, 라우팅 표, 예산 배분, 모델 핀, 파라미터, 재시도·타임아웃 값, 폴백 순서
- **포트·어댑터 뒤에 둘 외부 의존**: 모델 API(생성·판정·임베딩 각각), 토크나이저(예산 계산이 벤더에 종속되지 않게), 프롬프트 캐시. 벤더별 구조화 출력 차이는 **어댑터가 정규화**해 포트 밖으로 새지 않게 한다 — "한계와 리스크"의 벤더 추상화 계층이 이것이다
- **시점 재현성**: 모든 트레이스에 (모델 ID·버전, 프롬프트 세트 버전, 스키마 버전, 파라미터)를 남겨 "그때 그 답"을 같은 조합으로 재현할 수 있게 한다

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성 표의 탐지 신호(오류율·서킷 상태·p95·429 비율·스키마 실패율·judge 지표 이동)는 전부 **모델 호출 스팬 하나**에서 나온다. 규약은 [07 관측성 설계 요소](07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md)를 따르고, 이 소절은 모델 호출 스팬에 무엇을 더 담아야 하는지만 적는다. 자체 속성은 `agent.*`에 두고 OTel `gen_ai.*`는 매핑 계층을 거쳐 붙인다(컨벤션은 Development 등급 `[2차]`). 쿼리 시점 임베딩 호출은 `retrieval.embed`, 배치 임베딩은 `index.embed`로 같은 속성 집합을 쓴다.

| 기록 대상 | 스팬 / 이벤트 (이름, 부모) | 핵심 속성 (버전 키 포함) | 지표 (→ 어느 SLI) | 샘플링 · 보존 · PII |
|---|---|---|---|---|
| 모델 호출 1건 | `generation.generate` / `routing.decide` / `retrieval.embed` — 부모는 호출한 단계 스팬(`invoke_agent` 아래) | `agent.model_version`(**별칭이 아닌 해석된 실제 버전**), `agent.prompt_version`, `agent.schema_version`, `agent.model_tier`(rule / decision / small / large), `agent.vendor`, 파라미터 해시, `gen_ai.usage.input_tokens / output_tokens`(매핑), `agent.cached_tokens`, `agent.cost_estimate`, `agent.finish_reason`, `agent.queue_wait_ms`, TTFT, `tenant_id` | RED(티어·벤더별 호출 수·오류율·p50/p95), 토큰·비용 분포, **캐시 적중률**(`cached_tokens ÷ input_tokens`) → 호출 성공률·p95·호출당 비용 SLI | 메타데이터 전수. 프롬프트·출력 본문은 opt-in·별도 저장소, 스팬에는 해시만. 보존 예시 30일 |
| 구조화 출력 검증 | `generation.validate` (부모: `generation.generate`) | `agent.schema_version`, `agent.validation_result`(pass / retry / fallback), `agent.validation_error_code`(필수 필드 누락 · enum 위반 · 파싱 실패 — **코드화**, 자유 텍스트 금지), 재시도 횟수 | **스키마 검증 실패율**(모델 버전 × 스키마 버전 차원), 재시도 후 통과율, 폴백 전환율 → 스키마 통과율 SLI | 실패 건은 본문 포함 전수 보존(마스킹) — 골든셋 환류 원천 |
| 레이트 리밋·서킷 | `generation.generate`의 이벤트 `rate_limited`, `circuit.state_changed` | `agent.http_status`(429 / 5xx), `agent.retry_after_ms`, `agent.retry_count`, `agent.circuit_state`, `agent.api_key_pool_id` | **429 비율**(벤더·키·테넌트별), 큐 대기 p95, 서킷 열림 시간 → 가용성 SLI | 전수 |
| 폴백·저하 | `generation.generate`의 `agent.outcome`(success / fallback / degraded), `agent.degradation[]`(model_fallback · cache_hit · template_only) | 폴백 대상 모델 버전, 폴백 사유 코드 | 폴백률(사유별), 저하 응답 비율 → 가용성·품질 SLI | 폴백·저하 건 전수 보존 |
| 벤더 측 변경 감지 | `generation.generate`의 속성 `agent.vendor_model_header`(응답 헤더에 실린 모델·버전 식별자 — 벤더가 제공할 때만) | 요청한 핀 ↔ 응답 헤더 버전 일치 여부 `agent.model_version_match` | **핀 불일치 건수**(0이 정상), 별칭 모델의 헤더 버전 변경 이벤트 | 전수. 불일치는 이벤트로 승격 |
| 티어 라우팅 | `routing.decide {tier}` (라우터 자체의 판정 스팬) | `agent.decision`(선택 티어), `agent.decision_source`, `agent.confidence`, 라우팅 표 버전 | **티어별 호출 비율**, 티어별 비용 분해, 라우팅 정확도(샘플) → 비용 SLI | 전수 |

| 알림 | 조건 (예시) | 심각도 | 런북 (첫 3단계) |
|---|---|---|---|
| 스키마 검증 실패율 급증 | 모델 버전 × 스키마 버전별 실패율이 베이스라인 2배 초과 15분 지속 | P2 (하류 기능이 조용히 틀림) — 전 과업 동시 발생이면 P1 | ① 실패 코드 분포 확인(파싱 실패 집중 = 모델 측 변경 의심) ② `agent.vendor_model_header` 변경 이벤트와 시각 대조 ③ 호환 매트릭스의 직전 (모델 핀, 프롬프트 세트) 셀로 롤백 |
| 429 비율 | 벤더·키별 429 비율 임계 초과 5분 지속, 또는 큐 대기 p95 상한 초과 | P2 — 대화형 경로면 P1 | ① 어느 키·테넌트에 집중인지 분해 ② 우선순위 낮은 배치 경로부터 지연·거부 ③ 멀티 키·리전 전환, 지속 시 용량 증설 결정 |
| 지연 p95 | 티어별 p95가 SLO 초과 10분 지속(TTFT와 총 지연 분리) | P2 | ① `queue_wait_ms`로 적체 vs 처리 분리 ② 벤더 상태·서킷 상태 확인 ③ 하위 티어 1회 재시도 또는 폴백 모델 전환 |
| 예산 소진율 | 일 비용 예산의 소진 속도가 선형 추세 대비 1.5배(루프·컨텍스트 폭증 의심) | P2 — 상한 도달 시 P1 | ① 요청당 비용 분포에서 상위 이상치 추출 ② 티어·테넌트·과업별 분해 ③ 예산 상한 가드 확인, 해당 과업 티어 하향 |
| 핀 불일치 · 서킷 장기 열림 | `agent.model_version_match=false` 1건 이상 / 서킷 열림 10분 지속 | P2 / P1 | ① 벤더 변경 공지 확인 ② 야간 골든셋 회귀 즉시 실행 ③ 폴백 경로 상태와 폴백 모델의 핀 확인 |

대시보드에서 이 단계를 보는 뷰: ③ 비용·판정 분포의 **모델 티어별 비용·토큰 캐시율·라우팅 분포** 패널과 ② 레이어별 SLI의 **벤더·티어별 RED + 스키마 통과율** 패널. 감사 추적으로 넘기는 필드(관측 로그와 분리): 해석된 모델 버전·프롬프트 세트 버전·스키마 버전·파라미터 해시·토큰 사용량·검증 결과·폴백 여부와 사유 — 거버넌스 접점 표와 동일하며, 지연·캐시율·비용은 관측에만 둔다. 이 단계의 관측이 없으면 못 보는 장애: 벤더 별칭 뒤에서 조용히 바뀐 모델, 캐시 키에 프롬프트 버전이 빠져 적중률이 0으로 떨어진 경로, 한 테넌트가 공용 429 한도를 독점하는 상황.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 | 모델 호출 자체는 등급 1(가역, 요청자 본인). 호출 결과가 툴 실행·데이터 변경으로 이어지면 그 행동의 등급을 따르며, 그 판정은 이 단계가 아니라 행동 게이트에서([Part 3/12](../03-agent-workflow-rag/12-guardrails-hitl.md)) |
| 가드레일 위치 | **입력**(예산 초과·인젝션 패턴은 호출 전 규칙으로), **출력**(스키마 검증은 모든 호출에 필수, 내용 검증은 하류 검증기). 행동 가드레일은 이 단계에 없음 |
| 게이트 출력과 판정 수단 | 스키마 실패 → 재시도/폴백(저하). 예산 초과 → 압축 또는 차단. 모두 **규칙**으로 판정하고 모델에 맡기지 않는다 |
| 소유자 (A) | 모델 버전 교체: 아키텍트(R: AI 엔지니어, C: 보안·법무). 프롬프트: 제품 책임자. 라우팅 표·예산: AI 엔지니어 리드. "모델 교체" 행의 A가 비어 있으면 안 된다 |
| 모델 리스크 관리 | 사용하는 모델마다 **모델 카드**(용도·한계·검증된 언어), **검증 기록**(골든셋 결과·호환 매트릭스), **변경 승인**(아키텍트 승인 + 회귀 통과), **재검증 주기**(예시: 분기 1회 또는 벤더 변경 공지 시), **사용 중단 기준**(회귀 실패 지속, 벤더 지원 종료). 외부 API 모델도 "우리가 쓰는 버전"에 대해 같은 기록 |
| 감사 추적에 남길 필드 | 모델 ID·버전(별칭이 아닌 해석된 실제 버전), 프롬프트 세트 버전, 출력 스키마 버전, 파라미터, 토큰 사용량, 스키마 검증 결과, 폴백 사용 여부와 사유, 요청 ID·테넌트 |

### 운영 준비도 체크
- [ ] 모델 API마다 클라이언트 측 레이트 리밋·서킷 브레이커·타임아웃이 있고, 폴백 순서(모델 → 캐시 → 규칙)가 코드가 아닌 설정에 있는가
- [ ] 스키마 검증 실패율·429 비율·p95 지연에 알림과 런북이 있는가
- [ ] 운영 중인 모든 모델이 고정 버전으로 핀되어 있고, 별칭만 가능한 모델은 야간 골든셋 회귀로 감시되는가
- [ ] 프롬프트-모델 호환 매트릭스가 있고 롤백 단위(모델 핀 + 프롬프트 세트 + 파라미터)가 정해져 있는가
- [ ] 생성·판정·임베딩 호출이 포트 뒤에 있어 벤더 교체가 어댑터 추가로 끝나는가
- [ ] 트레이스에 모델 ID·프롬프트 버전·스키마 버전·테넌트 키가 남는가
- [ ] 모델 카드·검증 기록·변경 승인자·재검증 주기가 문서화되어 있는가
- [ ] 모델 호출 스팬에 **해석된** 모델 버전·프롬프트·스키마 버전·티어·캐시 토큰이 있고, 스키마 검증 실패 사유가 코드화되어 모델 버전 × 스키마 버전 차원으로 집계되는가
- [ ] 벤더 응답 헤더의 모델 식별자를 요청 핀과 대조하는 `agent.model_version_match` 검사가 있고, 불일치·429·스키마 실패율·예산 소진율 알림 각각에 런북이 연결되어 있는가
