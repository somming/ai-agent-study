# LLM 기초: 컨텍스트, 구조화 출력, 함수 호출

> **범위**: 에이전트 시스템 **설계자**가 알아야 할 LLM의 동작 특성과 그것이 설계에 주는 제약. 모델 내부 구조나 학습 방법은 다루지 않는다. 특정 벤더 API 문법도 다루지 않는다.

## 요약 (3줄)

1. LLM은 **컨텍스트 윈도우 안의 토큰**만 보고, 그 안에서도 위치에 따라 주의가 고르지 않다. 무엇을 넣을지보다 무엇을 빼고 어디에 둘지가 설계 문제다.
2. LLM의 출력을 프로그램이 소비하려면 **구조화 출력**(structured output)이 필요하다. 그 수단은 프롬프트 지시 → JSON 모드 → 함수 호출 → 제약 디코딩 → 결정 모델 순으로 강제력이 세진다.
3. 모든 판단을 가장 큰 모델에 맡기면 비용·지연이 통제되지 않는다. **모델 라우팅**은 선택이 아니라 기본 설계 요소다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** | 모델 호출의 입출력 계약: 컨텍스트 예산(토큰), 출력 스키마, 툴 인터페이스, 모델 선택 규칙 |
| **언제** | 모든 프로젝트의 설계 초기. 특히 Part 3의 어떤 페이지보다 먼저 |
| **어떻게** | ① 컨텍스트 예산을 정하고 구성 요소별로 배분 → ② 출력이 프로그램에 소비되는지 사람에게 읽히는지 구분해 구조화 수단 선택 → ③ 판단·분류·라우팅 과업과 생성 과업을 분리 → ④ 모델 티어(대/중/소/결정 모델)별 담당 과업 표를 만든다 |
| **왜** | 이 계약이 없으면 뒤의 모든 단계(검색 결과 몇 개를 넣을지, citation을 어떻게 받을지, 어떤 모델이 라우팅할지)가 각자 임의로 결정되어 비용과 품질이 예측 불가능해진다 |

## 문제와 맥락

LLM을 "자연어를 넣으면 자연어가 나오는 함수"로 취급하면 세 가지 문제가 생긴다.

- **컨텍스트 과적**: 검색 결과·히스토리·시스템 프롬프트를 전부 밀어 넣으면 비용이 선형으로 늘고, 품질은 오히려 떨어진다. 긴 컨텍스트에서 중간 위치의 정보를 놓치는 현상("lost in the middle")은 롱컨텍스트 모델에서도 RULER 류 스트레스 테스트에서 재현된다 `[2차]`.
- **출력 파싱 실패**: 자유 텍스트를 정규식으로 파싱하는 코드는 반드시 깨진다. 구조화 출력 수단을 쓰지 않으면 운영 중 조용히 실패한다.
- **비용 폭주**: "이 요청은 어느 경로인가" 같은 단순 판정에 최상위 모델을 쓰면 요청당 비용의 대부분이 판정에 쓰인다.

## 핵심 개념

### 컨텍스트 윈도우와 컨텍스트 예산

컨텍스트 윈도우는 모델이 한 번에 볼 수 있는 토큰 수다. 설계자는 이것을 **예산**으로 다룬다.

| 구성 요소 | 특성 | 설계 지침 |
|---|---|---|
| 시스템 프롬프트·지시 | 고정, 매 호출 반복 | 프롬프트 캐싱 대상. 길이보다 명확성 |
| 툴 정의 | 툴 수에 비례해 증가 | 툴이 20개를 넘으면 라우팅으로 부분 노출 검토 |
| 검색된 근거 | 가변, 품질 좌우 | 상위 k개 + 리랭킹 + 압축. [Part 3/03](../03-agent-workflow-rag/03-retrieval-reranking.md) |
| 대화 히스토리 | 턴마다 누적 | 요약·압축(compaction). [Part 3/08](../03-agent-workflow-rag/08-state-memory-context.md) |
| 메모리 | 세션 간 지속 | 관련도 기반 선별 주입 |
| 출력 여유 | 생성에 필요한 공간 | 구조화 출력일수록 예측 가능 |

롱컨텍스트(수백만 토큰)와 RAG는 대체 관계가 아니다. 롱컨텍스트는 복잡한 논리 추론에 유리하고 RAG는 고가치 근거를 선별해 공급한다는 보완 관계로 보는 것이 2026년 현재의 일반적 견해다 `[2차]`.

### 구조화 출력

LLM 출력을 프로그램이 소비하는 수단. 강제력이 약한 것부터.

1. **프롬프트 지시**: "JSON으로 답하라". 강제력 없음. 프로토타입 외에는 쓰지 않는다.
2. **JSON 모드**: 유효한 JSON임을 보장. 스키마 준수는 보장하지 않는다.
3. **함수 호출 / 툴 호출**: 스키마(JSON Schema)를 주면 그에 맞는 인자를 생성. 대부분의 벤더가 스키마 준수를 보장하는 모드를 제공. 에이전트 툴 실행의 표준 수단.
4. **제약 디코딩(constrained decoding / grammar)**: 디코딩 단계에서 문법에 맞지 않는 토큰을 차단. 오픈 모델 서빙(vLLM, llama.cpp 등)에서 가능. 스키마 준수가 100%.
5. **결정 모델**: 생성 자체를 하지 않고 타입드 질문에 대한 선택·점수·확률만 반환. 스키마 준수가 구조적으로 보장되고 보정 확률이 함께 나온다. [02 System 1 vs System 2](02-system1-vs-system2.md), [Part 3/11](../03-agent-workflow-rag/11-decision-layer.md).

**스키마 준수 ≠ 내용의 정확성**이다. 유효한 JSON으로 틀린 답을 할 수 있다. 구조화 출력은 파싱 실패를 없애는 것이지 환각을 없애는 것이 아니다.

### 함수 호출의 설계 단위

함수 호출은 "모델이 어떤 함수를 어떤 인자로 부르고 싶은지"를 구조화해 돌려주는 것이다. 실제 실행은 호출자의 책임이다. 설계 시 결정할 것:

- **툴 수와 노출 범위**: 모든 툴을 항상 노출하면 컨텍스트와 오선택이 늘어난다. 라우팅 후 관련 툴만 노출하는 2단계 구성이 일반적
- **병렬 호출 허용 여부**: 독립적인 툴은 병렬, 순서 의존은 직렬
- **실패 반환 형식**: 툴 실패도 구조화해 모델에 돌려준다. 자유 텍스트 에러는 모델이 오해한다
- 상세: [Part 3/09 툴과 MCP](../03-agent-workflow-rag/09-tools-and-mcp.md)

### 모델 라우팅

요청 또는 하위 과업의 성격에 따라 다른 모델(또는 결정 모델·규칙)로 보내는 것.

| 티어 | 담당 | 예 |
|---|---|---|
| 규칙 | 결정론적으로 판단 가능한 것 | 권한 검사, 포맷 검증, 금칙어 |
| 결정 모델 | 선택지가 닫힌 판정 | intent 분류, 경로 선택, 승인 필요 여부, 품질 합격 여부 |
| 소형 LLM | 단순 변환·추출 | 요약, 키워드 추출, 쿼리 재작성 |
| 대형 LLM | 복잡 추론·생성 | 근거 종합 답변, 계획 수립, 코드 생성 |

라우팅 자체도 판정이므로 결정 모델이나 소형 분류기가 맡는다. 라우팅을 대형 LLM이 하면 절감 효과가 사라진다. 상세: [Part 5/02](../05-cross-cutting/02-cost-latency-model-routing.md).

## 아키텍처 / 파이프라인

```
요청 ─▶ [규칙 검사] ─▶ [라우터: 결정 모델/분류기] ─┬─▶ 경로 A: 소형 LLM (변환)
                                                  ├─▶ 경로 B: 대형 LLM + 툴 (추론·생성)
                                                  └─▶ 경로 C: 규칙/템플릿 (모델 불필요)
각 LLM 호출 = [컨텍스트 조립: 예산 배분] ─▶ [호출] ─▶ [구조화 출력 검증] ─▶ [실패 시 재시도/폴백]
```

## 기술 비교표 — 구조화 출력 수단

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 프롬프트 지시 | 프로토타입, 사람이 읽는 출력 | 프로그램이 소비하는 모든 경우 | 하 | 표준 | `[검증]` 실패율 높음은 널리 알려짐 |
| JSON 모드 | 스키마가 느슨하고 필드 누락을 코드가 처리 가능 | 필수 필드·enum이 있는 경우 | 하 | 안정 | `[벤더]` |
| 함수 호출(스키마 보장 모드) | 에이전트 툴 실행, citation 구조화, 대부분의 운영 시스템 | 수백 개 툴을 동시에 노출해야 할 때(컨텍스트 비용) | 중 | 안정 | `[벤더]` 주요 벤더 공통 제공 |
| 제약 디코딩 | 오픈 모델 자체 서빙, 100% 스키마 준수 필요, 복잡한 문법(DSL) | 매니지드 API만 쓰는 경우(대개 미지원) | 중~상 (서빙 인프라) | 안정 | `[검증]` 오픈소스 구현 다수 |
| 결정 모델 (Jev, Decisions API) | 선택지가 닫힌 판정, 보정 확률이 필요, 저지연·저비용 대량 판정 | 자유 텍스트 생성이 필요한 과업, 한국어 검증 안 된 도메인 | 하 (호출당) / 중 (평가셋 구축) | 신생 (2026-09~) | `[벤더]` 성능 수치 미검증 |

### 선택 가이드

- **출력을 프로그램이 소비한다면** → 함수 호출(스키마 보장 모드)이 기본값. 이유: 매니지드·오픈 모델 모두 지원, 에이전트 툴과 같은 메커니즘
- **자체 서빙이고 복잡한 문법이 필요하다면** → 제약 디코딩. 이유: 100% 준수, 토큰 낭비 없음
- **출력이 선택·점수·예/아니오라면** → 결정 모델 또는 소형 분류기. 이유: 생성 비용과 지연이 불필요. 단 한국어 평가셋으로 `[실측]` 먼저
- **판단이 어려우면** → 함수 호출. 이유: 가장 넓은 호환성

## 설계 시 고려사항 (체크리스트)

- [ ] 컨텍스트 예산을 구성 요소별로 숫자로 적었는가 (예: 시스템 2k, 툴 3k, 근거 8k, 히스토리 4k, 출력 2k)
- [ ] 고정 부분(시스템 프롬프트, 툴 정의)이 캐싱되도록 호출 구조를 잡았는가
- [ ] 프로그램이 소비하는 모든 출력에 스키마가 있는가
- [ ] 스키마 검증 실패 시 재시도·폴백 경로가 있는가
- [ ] 판정 과업과 생성 과업을 분리했고, 판정은 결정 모델·분류기·규칙 중 하나가 맡는가
- [ ] 모델 티어별 담당 과업 표가 있고, 티어 변경이 설정으로 가능한가
- [ ] 모델 버전 고정(pinning)과 교체 시 회귀 평가 절차가 있는가 ([06 평가](06-evaluation-observability.md))
