# System 1 vs System 2: 결정 모델과 생성 모델의 역할 분담

> **범위**: 에이전트 시스템 안의 "판정"과 "생성"을 왜, 어떻게 다른 수단에 맡기는지. 결정 모델(System One 모델)이 무엇이고 기존 수단(프롬프트 LLM, 파인튜닝 분류기, 규칙)과 어떻게 다른지. 특정 제품의 상세 비교는 [Part 6/decision-models](../06-trends/decision-models.md), 배치 설계는 [Part 3/11](../03-agent-workflow-rag/11-decision-layer.md).

## 요약 (3줄)

1. 에이전트가 하는 일의 상당수는 **생성이 아니라 판정**이다. 어느 경로인가, 승인이 필요한가, 이 문서는 관련 있는가, 다음 행동은 무엇인가.
2. 판정을 생성 모델(System 2)에 맡기면 비싸고 느리고 출력이 흔들린다. 2026년 들어 **판정 전용 수단**(System 1 모델)이 상용화되면서 이 분리가 설계 원칙으로 자리잡는 중이다.
3. 분리의 기준은 "선택지가 닫혀 있는가"다. 닫혀 있으면 System 1(결정 모델·분류기·규칙), 열려 있으면 System 2(LLM).

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** | 시스템 안의 모든 판정 지점 목록과, 각 지점을 맡을 수단(규칙 / 결정 모델 / 분류기 / LLM)의 배정표 |
| **언제** | Part 3 설계 시작 전. 판정 지점은 라우팅, 게이팅, 필터링, 품질 판정, UI 선택, 승인 필요 판정 등 모든 Part에 흩어져 있으므로 한 번에 목록화한다 |
| **어떻게** | ① 요청 1건이 흐르는 경로를 그리고 분기점을 전부 표시 → ② 각 분기의 선택지가 닫혀 있는지 판단 → ③ 닫힌 분기는 규칙 → 결정 모델 → 분류기 순으로 가능한 가장 단순한 수단 배정 → ④ 열린 분기만 LLM → ⑤ 한국어 평가셋으로 `[실측]` |
| **왜** | 판정이 LLM에 섞여 있으면 ① 요청당 비용의 대부분이 판정에 쓰이고 ② 같은 입력에 다른 경로가 선택되어 디버깅이 불가능하며 ③ 확신도를 알 수 없어 승인 임계값을 둘 수 없다 |

## 문제와 맥락

Kahneman의 프레임에서 System 1은 빠르고 직관적이며 자동적인 사고, System 2는 느리고 숙고적인 사고다. LLM은 토큰을 하나씩 생성하며 "생각"하므로 System 2에 가깝다. 그런데 에이전트 루프에서 LLM은 다음과 같은 System 1 성격의 일도 떠맡아 왔다.

- 이 요청은 FAQ인가 복잡 문의인가 (라우팅)
- 검색된 20개 청크 중 관련 있는 것은 무엇인가 (필터링)
- 이 툴 호출은 사람 승인이 필요한가 (게이팅)
- 생성된 답이 근거에 부합하는가 (품질 판정)
- 사용자에게 표·차트·폼 중 무엇을 보여줄까 (UI 선택)

이 일들은 선택지가 닫혀 있고, 설명이 아니라 **답과 확신도**만 필요하다. 생성 모델로 처리하면 (a) 답 하나를 얻기 위해 수십~수백 토큰을 생성하고 (b) 온도가 0이어도 프롬프트 미세 변화에 결과가 흔들리며 (c) "확률 80%"라고 써도 그 숫자가 보정(calibrated)되어 있지 않다.

## 핵심 개념

### 판정 수단의 스펙트럼

| 수단 | 동작 | 확신도 | 설명 가능성 | 변경 비용 |
|---|---|---|---|---|
| **규칙** | 코드·정규식·정책 엔진 | 없음(결정론) | 완전 | 코드 수정 |
| **파인튜닝 분류기** | 라벨 데이터로 학습한 소형 모델 | softmax, 보정은 별도 | 낮음 | 재학습 |
| **결정 모델** | 상태 + 타입드 질문 → 선택/점수/예·아니오 + 보정 확률 | 보정 확률 (벤더 주장) | 낮음 | 질문 정의 수정 |
| **프롬프트 LLM** | 자연어 지시 → 생성 | 없음 또는 비보정 | 설명을 생성할 수 있으나 사후 합리화 위험 | 프롬프트 수정 |

### 결정 모델(System One 모델)이란

2026년 9월부터 상용화된 범주. 공통 특징은 **텍스트를 생성하지 않고** 개발자가 코드로 정의한 질문에 대한 답만 돌려준다는 것이다.

- **TypeSafe AI Jev** (2026-09-15 얼리액세스): 결정 전용 모델. 비자기회귀(non-autoregressive) 단일 패스로 여러 질문에 병렬로 답한다고 설명. 보정 결정을 위한 강화학습(RLCD)을 주장. 입력은 텍스트/JSON 상태, 출력은 선택·점수·예/아니오 + 보정 확률 `[벤더]`
- **OpenAI Decisions API** (2026-09-29 발표, 10월 초 퍼블릭 베타 보도): 범용 모델(gpt-6-luna)의 출력을 제약하는 엔드포인트(`POST /v1/decisions`). 조건 참 확률, 선택지 중 선택, 루브릭 점수를 반환. 텍스트·이미지 입력. **별도 결정 전용 모델은 아니다** `[2차]` — 소스 간 날짜·가격 충돌 있음

두 접근은 "생성 없는 판정 API"라는 인터페이스는 같지만 내부가 다르다. Jev는 아키텍처 자체가 다르고, Decisions API는 생성 모델의 출력 제약이다. 지연·비용·보정 품질이 다를 수 있으므로 같은 범주로 묶되 `[실측]`은 따로 한다.

### 분리 기준: 선택지가 닫혀 있는가

| 질문 유형 | 예 | 배정 |
|---|---|---|
| 결정론적으로 답할 수 있다 | 사용자 권한이 있는가, 금액이 한도 이내인가 | 규칙 |
| 선택지가 닫혀 있고 라벨 데이터가 많다 | 10개 카테고리 분류, 스팸 여부 | 분류기 또는 결정 모델 |
| 선택지가 닫혀 있고 라벨 데이터가 적거나 자주 바뀐다 | 신규 intent 추가, 라우팅 경로 변경 | 결정 모델 (질문 정의만 수정) |
| 선택지가 열려 있다 | 답변 작성, 계획 수립, 코드 생성 | LLM |
| 선택지는 닫혀 있지만 근거 설명이 반드시 필요하다 | 규제 심사의 판정 사유 | LLM + 결정 모델 교차 검증, 또는 뉴로심볼릭([04](04-neuro-symbolic-ai.md)) |

### System 1과 System 2의 조합 패턴

1. **Gate → Generate**: 결정 모델이 경로·필요 여부를 판정하고 LLM은 선택된 경로에서만 생성. 가장 흔한 패턴
2. **Generate → Judge**: LLM이 생성하고 결정 모델이 품질·안전·근거 부합을 판정. 불합격이면 재생성 또는 폴백
3. **Parallel Vote**: 결정 모델과 LLM이 독립 판정하고 불일치 시 사람에게. 고위험 결정
4. **Confidence-Routed HITL**: 결정 모델의 보정 확률이 임계값 미만이면 승인 요청. [Part 3/12](../03-agent-workflow-rag/12-guardrails-hitl.md)

## 아키텍처 / 파이프라인

```
                 ┌────────────── System 1 (판정) ──────────────┐
요청 ─▶ 규칙 ─▶ 결정 모델: intent? 경로? 위험도? ─┬─ 확신 ≥ θ ─▶ System 2 (LLM 생성) ─▶ 결정 모델: 근거 부합? 안전? ─▶ 응답
                                                  └─ 확신 < θ ─▶ 사람 승인 / 명확화 질문
```

## 기술 비교표 — 판정 수단

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 규칙 (코드, 정책 엔진) | 결정론적 조건, 보안·권한·금액 한도, 감사 대상 | 자연어 의미 판단이 필요한 경우 | 하 | 표준 | `[검증]` |
| 파인튜닝 분류기 (BERT류, 소형 LM) | 라벨 데이터 수천 건 이상, 카테고리 고정, 초저지연·온프레미스 | 카테고리가 자주 바뀜, 라벨 데이터 없음 | 중 (학습·MLOps) | 표준 | `[검증]` |
| 결정 모델 — Jev | 선택지 닫힘, 라벨 적음, 보정 확률 필요, 저지연(70~500ms 주장), 대량 판정 | 이미지·음성 입력, 영어 외 언어 미검증, 설명 필요 | 하 (호출) / 중 (평가셋) | 신생 | `[벤더]` 지연·비용 미검증 |
| 결정 모델 — OpenAI Decisions API | 위와 유사 + 이미지 입력, 이미 OpenAI 생태계 | 단일 모델(gpt-6-luna) 종속, 가격·상태 정보 유동적 | 하~중 | 신생(베타) | `[2차]` 소스 충돌 |
| 프롬프트 LLM (소형) | 프로토타입, 선택지가 아직 안 정해짐, 설명이 함께 필요 | 대량·저지연·보정 확률 필요 | 중 (토큰) | 안정 | `[검증]` 비보정 문제 널리 보고 |
| LLM-as-judge (대형) | 품질 평가의 오프라인 배치, 골든셋 구축 | 온라인 요청 경로의 게이팅(비용·지연) | 상 | 안정 | `[검증]` 편향·일관성 한계 보고 |

### 선택 가이드

- **보안·권한·한도라면** → 규칙. 이유: 확률로 판단하면 안 되는 영역
- **라벨 데이터가 충분하고 카테고리가 고정이라면** → 파인튜닝 분류기. 이유: 가장 싸고 빠르며 자체 호스팅 가능
- **라벨이 적고 질문이 자주 바뀌며 확신도가 필요하다면** → 결정 모델. 이유: 질문 정의만 바꾸면 되고 보정 확률로 HITL 임계값 설정 가능. 단 한국어 `[실측]` 선행
- **선택지가 아직 정해지지 않았다면** → 소형 LLM으로 시작해 선택지가 굳으면 위로 이전
- **판단이 어려우면** → 결정 모델과 소형 LLM을 같은 평가셋으로 비교 후 결정

## 설계 시 고려사항 (체크리스트)

- [ ] 요청 흐름의 모든 분기점을 목록화했는가
- [ ] 각 분기의 선택지가 닫혀 있는지 표시했는가
- [ ] 닫힌 분기 중 LLM이 맡고 있는 것이 있다면 그 이유를 적었는가
- [ ] 결정 모델을 쓴다면 한국어·혼합 언어·비격식 입력을 포함한 평가셋이 있는가
- [ ] 보정 확률을 쓴다면 신뢰도 다이어그램(reliability diagram)으로 보정을 확인했는가
- [ ] 확신도 임계값 미만의 처리 경로(사람 승인, 명확화 질문, 보수적 기본값)가 있는가
- [ ] 결정 모델 장애 시 폴백(규칙 또는 보수적 기본 경로)이 있는가
- [ ] 판정 결과와 확신도를 트레이스에 기록하는가 ([06](06-evaluation-observability.md))

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 결정 모델의 성능 수치가 벤더 주장뿐 | 기대한 지연·비용·정확도가 안 나올 수 있음 | PoC에서 `[실측]`, 비교군으로 소형 분류기 유지 |
| 영어 중심 학습 (Jev 명시) | 한국어·혼합 언어 입력에서 품질 저하 | 한국어 평가셋 필수, 불합격 시 분류기 |
| 보정 확률의 보정 여부 미확인 | 임계값이 의미 없을 수 있음 | 보정 곡선 측정, 임계값은 실측으로 |
| 설명 불가 | 규제·감사에서 판정 사유 요구 시 대응 불가 | 규칙·온톨로지 기반 설명 병행 ([04](04-neuro-symbolic-ai.md)) |
| 벤더 종속 (특히 Decisions API 단일 모델) | 가격·정책 변경 위험 | 판정 인터페이스를 추상화해 교체 가능하게 |
| 유효한 출력 ≠ 올바른 결정 | 스키마가 맞아도 틀릴 수 있음 | 행동으로 이어지는 판정은 코드에서 권한·한도 재검증 |
