# 뉴로심볼릭 AI

> **범위**: 신경망(LLM 포함)과 기호 체계(규칙, 온톨로지, 논리, 제약 솔버, 프로그램)를 결합하는 패턴의 분류, 각 패턴이 에이전트 시스템의 어느 자리에 들어가는지, 한계. 구체적 배치 설계는 [Part 3/10](../03-agent-workflow-rag/10-neuro-symbolic-reasoning.md), 가드레일 적용은 [Part 3/12](../03-agent-workflow-rag/12-guardrails-hitl.md).

## 요약 (3줄)

1. 뉴로심볼릭(neuro-symbolic)은 특정 기술이 아니라 **결합 패턴의 집합**이다. 2026년 엔터프라이즈에서 실제로 쓰이는 것은 그중 두세 가지, 특히 **LLM 출력을 기호 검증기가 확인하는 패턴**이다.
2. LLM은 확률적이고 규칙은 결정론적이다. 보안·권한·금액·규제처럼 **틀리면 안 되는 것**은 규칙이 최종 결정권을 가져야 하고, LLM은 규칙이 다루지 못하는 자연어 이해를 맡는다.
3. 뉴로심볼릭의 비용은 **기호 체계를 만들고 유지하는 비용**이다. 온톨로지([03](03-knowledge-representation.md))가 없으면 검증할 기준도 없다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** | 시스템 안에서 "확률적 판단"과 "결정론적 판단"의 경계, 그리고 둘을 잇는 검증·변환 지점의 설계 |
| **언제** | LLM 출력이 **행동**(툴 실행, 데이터 변경, 외부 전송)이나 **규제 대상 판단**으로 이어질 때. 출력이 사람이 읽는 텍스트로 끝나면 가드레일 수준으로 충분 |
| **어떻게** | ① 틀리면 안 되는 제약을 목록화(권한, 한도, 필수 필드, 허용 조합, 도메인 규칙) → ② 기호로 표현 가능한 것을 규칙·SHACL·스키마로 작성 → ③ LLM 출력 뒤에 검증기를 배치, 불합격 시 재생성·폴백·사람 → ④ 반복 실패 패턴을 프롬프트나 추출 스키마에 피드백 |
| **왜** | "LLM에게 규칙을 지키라고 프롬프트에 쓰기"는 확률적 준수다. 1만 건 중 몇 건은 어긴다. 규칙 위반이 금전·법적 결과를 낳는다면 확률적 준수는 준수가 아니다 |

## 문제와 맥락

순수 LLM 기반 에이전트의 실패는 대개 세 가지다. ① 사실이 아닌 것을 말한다(환각). ② 규칙을 안다고 하면서 어긴다(지시 불이행). ③ 왜 그렇게 판단했는지 재구성할 수 없다(불투명). 세 가지 모두 LLM이 **확률적 패턴 완성기**이기 때문에 생긴다.

기호 체계는 정반대 성질을 가진다. 정의된 것만 알고(환각 없음), 규칙을 반드시 지키며(결정론), 추론 경로가 명시적이다(투명). 대신 자연어를 이해하지 못하고 정의 밖의 상황에 취약하다. 뉴로심볼릭은 둘을 붙여 서로의 약점을 가리는 시도다. 개념 자체는 수십 년 됐지만(3rd wave 논의는 2020년), **LLM이 "신경망 쪽"을 맡으면서** 기호 체계와의 인터페이스가 자연어·JSON으로 단순해진 것이 최근 1년의 변화다.

## 핵심 개념

### Kautz 분류 (AAAI 2020)와 에이전트에서의 대응

Kautz의 분류는 소스마다 5~6종으로 세고 표기도 조금씩 다르다 `[2차]`. 여기서는 에이전트 설계에 유용한 형태로 정리한다. 표기법: `A|B`는 A와 B가 별개 모듈로 통신, `A[B]`는 B가 A 안에 내장.

| 유형 | 구조 | 에이전트에서의 예 | 쓰임 |
|---|---|---|---|
| **Symbolic Neuro Symbolic** | 기호 입력 → 신경망 → 기호 출력 | 일반적인 LLM 호출 (텍스트→텍스트) | 기준선. 사실상 모든 LLM 사용 |
| **Symbolic[Neural]** | 기호 솔버가 신경망을 서브루틴으로 호출 | 워크플로우 엔진·규칙 엔진이 특정 단계에서만 LLM 호출 | 결정론적 워크플로우 + LLM 노드. [Part 3/05](../03-agent-workflow-rag/05-workflow-vs-agent.md) |
| **Neural\|Symbolic** | 신경망이 입력을 기호로 변환 → 기호 추론기가 처리 | LLM이 문서에서 트리플 추출 → 그래프 DB·규칙 엔진이 추론. LLM이 쿼리를 SQL/Cypher/SPARQL로 변환 → DB 실행 | **가장 흔한 실용 패턴**. 추출, Text-to-Query, 프로그램 합성(PAL) |
| **Neural[Symbolic]** | 신경망이 기호 추론기를 내부 도구로 호출 | LLM 에이전트가 계산기·솔버·그래프 쿼리·규칙 검증을 툴로 호출 | 툴 사용 에이전트. [Part 3/09](../03-agent-workflow-rag/09-tools-and-mcp.md) |
| **Neural:Symbolic → Neural** | 기호 지식을 학습 데이터·손실로 주입 | 온톨로지 제약을 반영한 파인튜닝, 규칙 위반에 페널티 | 모델 학습 단계. 대부분의 프로젝트 범위 밖 |
| **Neuro_Symbolic (통합)** | 기호 규칙이 신경망 구조에 직접 내장 | 논리 텐서 네트워크 등 연구 단계 | 연구. 실무 적용 드묾 |

Garcez & Lamb(2023)는 다른 표기(symbolic[neural], neural[symbolic], neural:symbolic)를 쓴다. 문헌 인용 시 어느 체계인지 확인한다 `[2차]`.

### 실무에서 쓰는 네 가지 패턴

위 분류를 에이전트 설계 자리로 다시 묶으면 네 가지다.

1. **검증기 패턴 (Generate → Verify)**: LLM이 생성한 구조화 출력(추출 결과, 툴 인자, 답변+citation, UI 트리)을 기호 검증기가 검사. 검증기는 JSON Schema → SHACL → 규칙 엔진 → 제약 솔버 순으로 표현력이 올라간다. 불합격 시 오류를 구조화해 LLM에 되돌려 재생성(self-correction loop)하거나 폴백.
2. **변환기 패턴 (Translate → Execute)**: LLM이 자연어를 형식 언어(SQL, Cypher, SPARQL, 규칙 DSL, 코드)로 변환하고 실행은 결정론적 엔진이. 실행 결과가 근거가 되므로 환각이 구조적으로 억제된다. 변환 오류는 실행 오류로 드러난다.
3. **접지 패턴 (Ground → Generate)**: 생성 전에 온톨로지·그래프에서 허용된 개념·값·관계를 조회해 컨텍스트와 출력 스키마(enum)를 제한. 용어 드리프트와 존재하지 않는 엔티티 언급을 막는다.
4. **게이트 패턴 (Rule ∧ Model)**: 행동 직전에 규칙이 최종 허가. 모델(LLM 또는 결정 모델)이 "실행해도 됨"이라 해도 규칙이 "권한 없음·한도 초과"면 차단. 결정 모델의 보정 확률과 결합하면 "확신 낮음 → 사람"까지 한 자리에서 처리. [02](02-system1-vs-system2.md)

### 기호 체계의 선택지

| 기호 체계 | 표현하는 것 | 적합 | 한계 |
|---|---|---|---|
| JSON Schema | 구조·타입·enum·필수 필드 | 모든 구조화 출력의 1차 검증 | 필드 간 관계·도메인 규칙 표현 불가 |
| SHACL / ShEx | 그래프 데이터의 형상·카디널리티·값 제약 | 온톨로지 기반 추출 검증 | RDF 전제(LPG는 변환 필요) |
| 규칙 엔진 (Drools, OPA/Rego, 자체 DSL) | if-then 비즈니스·정책 규칙 | 권한, 한도, 승인 정책 | 규칙 수 증가 시 충돌 관리 |
| 제약 솔버 (SMT, CP) | 조합 제약 충족 | 일정·배치·구성 검증 | 모델링 난이도 |
| 온톨로지 추론기 (OWL reasoner) | 분류·일관성·함의 | 개념 간 모순 탐지, 상위 클래스 추론 | 성능, 표현력 제한(OWL 프로파일) |
| 프로그램 실행 (PAL, 코드 인터프리터) | 계산·알고리즘 | 수치·날짜·집계 | 샌드박스 필요 |

## 아키텍처 / 파이프라인

```
[접지] 온톨로지·그래프 조회 → 허용 개념·enum
         │
         ▼
[생성] LLM → 구조화 출력 (추출 결과 / 툴 인자 / 답변+citation / 쿼리 / UI 트리)
         │
         ▼
[검증] JSON Schema → SHACL/규칙 → (필요 시) 솔버 ──불합격──▶ 오류 구조화 → 재생성 (최대 N회) → 폴백/사람
         │ 합격
         ▼
[게이트] 규칙 최종 허가 ∧ (결정 모델 확신 ≥ θ) ──▶ 실행
```

## 기술 비교표 — 결합 패턴

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 프롬프트에 규칙 명시만 | 프로토타입, 위반 비용 낮음 | 행동·규제·금전 연결 | 하 | 표준 | `[검증]` 확률적 준수 한계 널리 보고 |
| 검증기 패턴 (Schema + 규칙) | 구조화 출력이 행동으로 이어짐. 대부분의 운영 에이전트 | 출력이 자유 텍스트로 끝남 | 중 | 안정 | `[2차]` 벤더·실무 보고 다수 |
| 변환기 패턴 (Text-to-SQL/Cypher/코드) | 정형·그래프 데이터 질의, 수치 계산 | 변환 대상 형식 언어가 없음 | 중 | 안정 | `[검증]` Text-to-SQL 벤치마크 다수 |
| 접지 패턴 (온톨로지 enum·개념 제한) | 도메인 용어 일관성, 존재하지 않는 엔티티 억제 | 온톨로지 없음 | 중 (온톨로지 비용) | 시험 | `[검증-단일저자]` arXiv 2604.00555 |
| 게이트 패턴 (규칙 ∧ 모델) | 툴 실행·외부 전송 직전 | — (행동이 있다면 항상 권장) | 하~중 | 안정 | `[2차]` |
| 기호 지식 주입 학습 | 자체 모델 학습 역량 보유 | 매니지드 모델만 사용 | 상 | 실험 | `[검증]` 연구 문헌 |
| 통합 아키텍처 (LTN 등) | 연구 | 실무 | 상 | 실험 | `[검증]` 연구 문헌 |

### 선택 가이드

- **LLM 출력이 행동으로 이어진다면** → 검증기 + 게이트 패턴은 필수. 이유: 확률적 준수로는 안 되는 영역
- **데이터가 정형·그래프라면** → 변환기 패턴. 이유: 실행 결과가 곧 근거라 환각이 구조적으로 억제
- **용어·엔티티 일관성이 문제라면** → 접지 패턴. 단 온톨로지 먼저([03](03-knowledge-representation.md))
- **판단이 어려우면** → JSON Schema 검증 + 규칙 게이트부터. 이유: 가장 싸고 즉시 효과

## 설계 시 고려사항 (체크리스트)

- [ ] "틀리면 안 되는 제약"을 목록화하고 각각이 기호로 표현 가능한지 표시했는가
- [ ] 검증기가 LLM 출력의 **모든** 행동 경로 앞에 있는가 (우회 경로 없음)
- [ ] 검증 실패 시 오류 메시지가 구조화되어 LLM 재생성에 쓰이는가
- [ ] 재생성 횟수 상한과 상한 도달 시 폴백이 있는가
- [ ] 규칙과 모델이 충돌할 때 규칙이 우선한다는 것이 코드로 보장되는가
- [ ] 규칙의 소유자·변경 절차·테스트가 있는가 (규칙도 코드다)
- [ ] 검증 실패율을 측정·추적하는가 (프롬프트·스키마 개선 신호)
- [ ] 변환기 패턴이라면 생성된 쿼리·코드의 실행이 샌드박스·읽기 전용인가
