# 에이전트 프로토콜: MCP · A2A · AG-UI · A2UI · MCP Apps

> **범위**: 2026년 현재 에이전트 생태계의 주요 개방 프로토콜이 **각각 어느 경계를 맡는지**, 경쟁인지 보완인지, 선택 기준. 각 프로토콜의 메시지 포맷·SDK 사용법은 다루지 않는다. UI 프로토콜의 상세 비교는 [Part 4/02](../04-dynamic-ui/02-protocols-ag-ui-a2ui-mcp-apps.md), 툴 통합은 [Part 3/09](../03-agent-workflow-rag/09-tools-and-mcp.md).
> **시각화**: `assets/html/protocol-map.html` (예정)

## 요약 (3줄)

1. 다섯 프로토콜은 **서로 다른 경계**를 맡는다. MCP는 에이전트↔툴·데이터, A2A는 에이전트↔에이전트, AG-UI는 에이전트 백엔드↔프론트엔드(이벤트), A2UI는 UI의 **내용**(선언적 트리), MCP Apps는 MCP 서버가 돌려주는 샌드박스 UI다. 경쟁 관계는 UI 쪽(AG-UI/A2UI/MCP Apps)에만 부분적으로 있다.
2. 성숙도가 다르다. MCP는 2026-07-28 대개정(무상태 코어)으로 엔터프라이즈 확장 단계, A2A는 2025-06 Linux Foundation 이관으로 거버넌스 안정, AG-UI·A2UI·MCP Apps는 2026년에 SDK·버전이 빠르게 바뀌는 중이다.
3. 프로토콜 채택은 **벤더 중립성과 생태계 크기**를 사는 것이다. 단일 벤더 스택 안에 머문다면 프로토콜 없이 SDK 직접 호출이 더 단순할 수 있다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** | 시스템의 네 경계(툴, 에이전트 간, 프론트-백, UI 내용)마다 프로토콜을 쓸지, 쓴다면 무엇을 쓸지의 결정 |
| **언제** | 아키텍처 초기. 특히 ① 툴·데이터 소스가 여러 팀·벤더에 걸쳐 있거나 ② 에이전트를 다른 조직의 에이전트와 연동하거나 ③ 프론트엔드와 에이전트 백엔드를 다른 팀이 만들 때 |
| **어떻게** | ① 네 경계 중 실제로 존재하는 것을 표시 → ② 각 경계에서 "양쪽을 같은 팀이 같은 스택으로 만드는가" 확인 → ③ 아니면 프로토콜 채택, 맞으면 SDK 직접 호출도 검토 → ④ UI 경계는 통제 수준([Part 4/01](../04-dynamic-ui/01-generative-ui-spectrum.md))을 먼저 정한 뒤 프로토콜 |
| **왜** | 프로토콜 없이 만들면 툴 N개 × 에이전트 M개 × 프론트 K개의 통합이 각각 커스텀이 된다. 프로토콜은 이것을 N+M+K로 줄인다. 반면 경계가 하나뿐이면 프로토콜의 추상화 비용만 낸다 |

## 문제와 맥락

2024년까지 에이전트 통합은 프레임워크별 커스텀이었다. 툴은 프레임워크마다 다른 데코레이터로 감싸고, 프론트엔드는 각자 SSE 포맷을 정의하고, 에이전트 간 통신은 HTTP API를 직접 설계했다. 2024-11 MCP 공개 이후 2년간 경계마다 개방 프로토콜이 생겼고, 2026년에는 "어느 프로토콜이 이기나"보다 **"어떻게 조합하나"** 가 질문이 됐다 `[2차]`.

## 핵심 개념

### 다섯 프로토콜의 경계와 상태

| 프로토콜 | 경계 | 무엇을 표준화 | 주도 | 거버넌스 | 최근 상태 (2026-10) | 검증 수준 |
|---|---|---|---|---|---|---|
| **MCP** (Model Context Protocol) | 에이전트 ↔ 툴·데이터 소스 | 툴·리소스·프롬프트의 발견과 호출 | Anthropic (2024-11) | 오픈 스펙, 다벤더 SDK | **2026-07-28 개정**: initialize 핸드셰이크·세션 ID 제거로 무상태 코어, Multi Round-Trip Requests, Tasks 확장(장기 실행), MCP Apps 확장(서버 렌더 UI). C# SDK v2.0 등 | `[2차]` 개정 전 작성된 소스 포함, 공식 changelog 재확인 권장 |
| **A2A** (Agent2Agent) | 에이전트 ↔ 에이전트 | Agent Card(능력 공개), 태스크 생명주기, 메시지·아티팩트 교환 | Google (2025-04) | **Linux Foundation** (2025-06 이관), 100+ 기업 참여 | 1.0 도달 정황(A2UI가 "A2A 1.0 통합" 언급)이나 전용 발표 미확인 | `[2차]` |
| **AG-UI** (Agent-User Interaction) | 에이전트 백엔드 ↔ 프론트엔드 | 타입드 이벤트 스트림(텍스트 델타, 툴 호출 시작/종료, 상태 패치), SSE 기반, 양방향 | CopilotKit (2025) | MIT, 스타트업 주도(재단 아님) | Microsoft .NET SDK (2026-09-25), Amazon Bedrock AgentCore 지원(2026-03), ThoughtWorks Radar 등재 | `[2차]` `[벤더]` |
| **A2UI** (Agent-to-UI) | UI의 **내용** | 선언적 UI 트리(JSON), 컴포넌트 세트("Basic"), 멀티플랫폼 렌더(웹·Flutter·Android·iOS) | Google | Apache 2.0 | **v0.9** (2026-04-17), Agent SDK 추가, Android Jetpack 라이브러리 | `[벤더]` |
| **MCP Apps** | MCP 서버 → 호스트 UI | 서버가 HTML UI를 반환, 호스트가 샌드박스 iframe에 렌더 | MCP 커뮤니티 (2026-01 CopilotKit 지원 발표) | MCP 확장 | 2026-07-28 스펙의 확장으로 편입 | `[2차]` |

### 경계별 역할 그림

```
                        ┌─────────────── A2A ───────────────┐
                        │ (에이전트 ↔ 외부/타 조직 에이전트)   │
  사용자 ── 프론트엔드 ══ AG-UI ══ 에이전트 백엔드 ══ MCP ══ 툴·데이터 소스
             │  ▲                       │                     │
             │  └── A2UI (UI 트리 내용) ─┘                     └── MCP Apps (서버가 UI 반환)
             └── 렌더러 (React / Flutter / 네이티브)
```

- **AG-UI와 A2UI는 층이 다르다.** AG-UI는 "이벤트를 어떻게 흘릴까"(전송·동기화), A2UI는 "UI가 무엇인가"(내용). A2UI 트리를 AG-UI 이벤트에 실어 보낼 수 있다 `[2차]`
- **MCP Apps는 UI의 출처가 다르다.** AG-UI/A2UI는 **에이전트**가 UI를 결정하지만, MCP Apps는 **툴 서버**가 자기 UI를 가져온다. 서드파티 툴이 자기 위젯을 가진 채 호스트에 꽂히는 모델
- **A2A와 MCP는 보완.** 에이전트가 다른 에이전트를 "툴처럼" MCP로 부를 수도 있지만, 태스크 생명주기·협상·장기 실행이 필요하면 A2A

### 프로토콜을 쓰지 않을 때

- 툴이 모두 같은 코드베이스 안에 있고 다른 호스트에 노출할 계획이 없다 → 함수 직접 등록
- 프론트와 백을 같은 팀이 같은 프레임워크(예: Vercel AI SDK 풀스택)로 만든다 → 프레임워크 내장 스트리밍
- 에이전트가 하나뿐이다 → A2A 불필요

프로토콜은 **경계를 넘는 당사자가 둘 이상**일 때 가치가 있다.

| 경계 | 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|---|
| 툴 | **MCP** | 툴이 여러 팀·벤더에 걸침, 여러 호스트(IDE·챗·자체 앱)에서 재사용 | 단일 코드베이스 내부 툴만 | 중 | 안정 → 2026-07 개정 전환기 | `[2차]` |
| 툴 | 프레임워크 네이티브 툴 | 단일 스택, 빠른 개발 | 재사용·외부 노출 | 하 | 안정 | — |
| 에이전트 간 | **A2A** | 타 조직·타 벤더 에이전트 연동, 장기 태스크, 능력 발견 | 단일 시스템 내 하위 에이전트 | 중~상 | 안정(LF 거버넌스) | `[2차]` |
| 에이전트 간 | 프레임워크 내부 오케스트레이션 (LangGraph 서브그래프, Handoff) | 같은 프로세스·같은 팀 | 조직 경계 | 하 | 안정 | — |
| 프론트-백 | **AG-UI** | 프론트·백 분리 개발, 멀티 프레임워크 백엔드, 상태 동기화 필요 | 단일 풀스택 | 중 | 신생→확산 (MS·AWS 지원) | `[2차]` `[벤더]` |
| 프론트-백 | 프레임워크 스트리밍 (Vercel AI SDK 등) | 풀스택 단일 팀 | 백엔드 교체 가능성 | 하 | 안정 | — |
| UI 내용 | **A2UI** | 멀티플랫폼(모바일 네이티브 포함) 선언적 UI, Declarative 패턴 | Controlled 패턴(사전 정의 컴포넌트 선택만) | 중 | 신생 (v0.9) | `[벤더]` |
| UI 내용 | 자체 컴포넌트 레지스트리 + 툴 호출 | Controlled 패턴, 웹 중심 | 모바일 네이티브 렌더 | 하~중 | 안정 | — |
| UI 내용 | **MCP Apps** | 서드파티 툴이 자기 UI를 가져와야 함, 호스트가 여럿 | 디자인 시스템 일관성이 중요 | 중 | 신생 | `[2차]` |

### 선택 가이드

- **툴이 여러 팀·호스트에 걸친다면** → MCP. 이유: 사실상 표준, 2026-07 개정으로 무상태 스케일링 가능
- **다른 조직의 에이전트와 연동한다면** → A2A. 이유: 벤더 중립 거버넌스, 능력 발견·태스크 생명주기 내장
- **프론트와 백을 다른 팀이 만든다면** → AG-UI. 이유: 이벤트 스키마 합의 비용 절감, MS·AWS 지원으로 생태계 확대 중
- **모바일 네이티브에 에이전트 UI를 그려야 한다면** → A2UI. 이유: 선언적 데이터라 플랫폼 렌더러 교체 가능. 단 v0.9 변경 위험
- **판단이 어려우면** → 툴은 MCP, 나머지는 프레임워크 내장으로 시작. 이유: MCP만 성숙도가 확실하고, 나머지 경계는 나중에 프로토콜로 바꿔도 비용이 작다

## 설계 시 고려사항 (체크리스트)

- [ ] 네 경계(툴, 에이전트 간, 프론트-백, UI 내용) 중 실제로 당사자가 둘 이상인 것을 표시했는가
- [ ] MCP를 쓴다면 2026-07-28 개정(무상태, Multi Round-Trip, Tasks)을 지원하는 SDK 버전인가, 구버전 서버와의 호환 전략이 있는가
- [ ] MCP 툴 서버의 인증·권한·감사 로그를 설계했는가 (프로토콜은 전송만 정의한다)
- [ ] A2A를 쓴다면 Agent Card에 공개할 능력의 범위와 인증 방식을 정했는가
- [ ] AG-UI/A2UI를 쓴다면 버전 고정과 업그레이드 절차가 있는가 (2026년 내 변경 빈번)
- [ ] MCP Apps를 쓴다면 샌드박스 iframe 정책(CSP, 통신 채널)을 검토했는가 ([Part 4/08](../04-dynamic-ui/08-security-sandboxing.md))
- [ ] 프로토콜 스펙에 없는 것(인증, 레이트 리밋, 멀티테넌시, 비용 계측)을 누가 책임지는지 정했는가
- [ ] 프로토콜을 쓰지 않기로 한 경계는 그 이유를 기록했는가

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| UI 프로토콜의 미성숙·빈번한 변경 | 반년 단위 마이그레이션 | 버전 고정, 어댑터 계층, Controlled 패턴 우선 |
| 프로토콜이 보안을 정의하지 않음 | MCP 서버·A2A 엔드포인트가 새로운 공격면 | 인증·권한·감사를 별도 설계, [Part 5/01](../05-cross-cutting/01-security-prompt-injection.md) |
| MCP 대개정의 전환기 | 구·신 서버 혼재, SDK 간 호환 문제 | 2026-07-28 지원 SDK로 통일, 호환 레이어 |
| AG-UI의 단일 스타트업 거버넌스 | 로드맵·라이선스 변경 위험 | MIT 라이선스 포크 가능성 확인, MS·AWS 채택으로 완화 중 |
| 프로토콜 과잉 | 경계가 하나인 시스템에 다섯 프로토콜 | "당사자 둘 이상" 기준 적용 |
| 상태 관리의 책임 이동 | MCP 무상태화로 세션 상태를 호스트·서버 중 누가 들지 재설계 필요 | Tasks 확장과 애플리케이션 상태 저장소 설계 |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [07 운영 용어](07-operations-vocabulary.md). 이 페이지의 운영 단위는 **경계**다 — 툴, 에이전트 간, 프론트-백, UI 내용 네 경계 각각에 프로토콜 어댑터가 하나씩 놓인다. 프로토콜은 전송과 메시지 형식만 정의하므로 아래 항목의 대부분은 "프로토콜이 정하지 않은 것을 우리가 어디서 정하나"의 답이다. 레이어 간 비교는 [Part 5/06](../05-cross-cutting/06-operational-design-matrix.md), 툴 레이어 상세는 [Part 3/09](../03-agent-workflow-rag/09-tools-and-mcp.md).

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 툴·MCP 서버 수 | 서버가 수십 개가 되면 툴 정의가 컨텍스트를 잠식하고([01](01-llm-fundamentals.md)), 서버마다 다른 인증·버전·소유자를 추적하는 운영 비용이 선형으로 는다 | 툴 라우팅(라운드마다 관련 서버만 노출), 서버 레지스트리(소유자·스펙 버전·인증 방식·위험 등급), 서버 측에 상태를 두지 않기 | 서버 수 × (툴 정의 토큰 + 운영 인력) |
| 요청·동시 세션 | 2026-07-28 이전 MCP 서버는 세션 ID에 상태를 묶어 **같은 인스턴스로 다시 가야** 했다. 10배 트래픽에서 스티키 세션이 병목 | **무상태 코어**의 의미가 여기 있다: 요청마다 어느 인스턴스로 가도 되므로 라운드로빈 수평 확장. 장기 실행 상태는 Tasks 확장 + 외부 저장소로 | 요청 수(인스턴스 수로 나뉨) |
| A2A 엔드포인트 수 | 상대 에이전트가 늘면 Agent Card 발견·인증·태스크 추적이 N개의 외부 의존이 된다. 가장 느린 상대가 전체 태스크 지연을 지배 | 상대별 서킷 브레이커·타임아웃·동시 태스크 상한, 태스크 상태를 자체 저장소에(상대 장애와 분리) | 상대 에이전트 수 × 동시 태스크 |
| AG-UI 동시 스트림 | SSE 연결 수가 곧 열린 소켓 수. 10배 사용자면 연결 상한·메모리·이벤트 팬아웃이 병목 | 연결 상한과 백프레셔(이벤트 큐 상한 초과 시 상태 스냅샷으로 재동기화), 스트림 게이트웨이 분리, 재접속 시 재전송 범위 정의 | 동시 사용자 수 × 이벤트 빈도 |
| 테넌트 | MCP·A2A 모두 멀티테넌시를 정의하지 않는다. 분리를 빠뜨리면 한 테넌트의 툴 호출이 다른 테넌트 데이터에 닿는다 | 테넌트 키를 모든 툴 호출·태스크·이벤트 메타데이터에, 서버 측 ACL은 호스트가 전달한 신원으로 | 테넌트 수 × 정책 분기 |

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| MCP 서버 다운·연결 실패 | 특정 기능만 조용히 사라지거나 에이전트가 "할 수 없다"고 답함 | 서버별 오류율, 툴 목록 조회 실패 | 서버 단위 서킷 브레이커 → 해당 툴을 노출 목록에서 제외하고 에이전트에 "일시 불가"를 구조화 오류로 전달 → 대체 서버가 있으면 전환 | 서킷이 열린 채 일정 시간(예시: 15분) |
| 툴 호출 타임아웃·느린 응답 | 턴 전체가 느려짐 | 툴별 p95, 타임아웃 비율 | 툴별 타임아웃(예시: 읽기 10초, 쓰기 30초) 후 구조화 오류 반환. **쓰기 툴은 멱등 키 없이 재시도 금지** | 타임아웃이 특정 서버에 집중 |
| A2A 상대 에이전트 무응답·태스크 미완료 | 위임한 과업이 영원히 "진행 중" | 태스크 상태 전이가 없는 시간, 상대별 오류율 | 태스크 타임아웃 → 사용자에게 저하 알림("외부 처리 지연 중") → 가능하면 자체 처리 경로 | 같은 상대에서 반복 → 신뢰 등급 하향 검토 |
| 스펙·SDK 버전 불일치 (구·신 MCP 서버 혼재, A2UI 0.x 변경) | 핸드셰이크 실패, 필드 누락으로 UI가 비어 보임 | 어댑터의 버전 협상 실패 로그 | 어댑터가 버전별 분기(구버전 서버는 호환 레이어 경유), 미지원 버전은 등록 단계에서 거부 | 호환 매트릭스 밖의 조합이 운영에 나타남 |
| MCP Apps 샌드박스 로드 실패 (CSP 차단, iframe 오류) | 위젯 자리가 비거나 깨짐 | 렌더 실패율, CSP 위반 리포트 | 서버가 함께 돌려준 텍스트·구조화 결과로 폴백 렌더 | 특정 서버 UI가 반복 실패 → 등록 재심사 |
| 경계를 통한 인젝션 (툴 결과·상대 메시지에 지시문) | 에이전트가 의도치 않은 행동 | 출력·행동 가드레일 차단 건수 | 툴 결과·상대 메시지는 데이터로 격리, 행동 게이트([Part 5/01](../05-cross-cutting/01-security-prompt-injection.md)) | 차단 급증 |

**킬 스위치는 툴 단위**로 둔다. 서버 전체가 아니라 특정 툴 하나를 배포 없이 끌 수 있어야 한다(레지스트리의 `enabled` 플래그). A2A 상대 에이전트와 MCP Apps 서버도 각각 끌 수 있어야 한다.

SLI 후보: 툴 호출 성공률(서버별), 툴 p95 지연, A2A 태스크 완료율·완료 시간, AG-UI 스트림 연결 성공률·재접속률, 렌더 실패율. SLO 초안(예시): 툴 호출 성공률 99%, 읽기 툴 p95 ≤ 5초. 쓰기 툴은 멱등 키 필수, 재시도 상한 1회, 타임아웃은 툴 정의에 명시.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| 프로토콜 스펙 버전 (MCP 날짜 버전, A2A, AG-UI, A2UI 0.x) · 클라이언트 SDK 버전 | 핸드셰이크, 메시지 필드, 상태 소유, 어댑터 내부 | 어댑터 계약 테스트(스펙 버전별 모의 서버) | 스펙 ↔ SDK 호환 매트릭스의 한 셀, 어댑터 |
| MCP 서버 목록·툴 정의 (레지스트리) | 노출되는 툴, 컨텍스트 비용, 툴 선택 정확도 | 툴 계약 테스트(입출력 스키마), 툴 선택 골든셋 | 툴 라우팅 설정 |
| A2A Agent Card (우리 것·상대 것) | 상대가 보는 능력 범위, 인증 방식 | 카드 스키마 검증, 상대와의 통합 테스트 | 인증 설정 |
| AG-UI 이벤트 스키마 · A2UI 컴포넌트 세트 | 프론트 렌더 | 이벤트 재생 테스트(기록된 스트림 → 렌더 스냅샷) | 프론트엔드 렌더러 버전 |

**호환 매트릭스는 두 장**이다. ① 서버 스펙 버전 ↔ 클라이언트 SDK 버전(어느 조합이 테스트됐나), ② 우리 어댑터 버전 ↔ 등록된 서버 목록(어느 서버가 어느 스펙으로 말하나). 업그레이드는 **계획된 창**에서만 한다. UI 프로토콜은 0.x라 반년 단위 변경이 예상되므로 분기마다 업그레이드 창을 미리 잡고, 그 밖의 시점에는 버전을 고정한다.

기술 부채로 기록할 것: 구버전 MCP 서버용 호환 레이어(제거 시점), 스펙 밖에서 우리가 임시로 정한 규약(인증 헤더, 레이트 리밋 방식)이 나중에 스펙에 들어올 때의 마이그레이션, 프로토콜 없이 직접 연결한 경계.

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

이 단계에서 **가장 자주 바뀌는 것은 등록된 서버·툴 목록**이고(팀이 툴을 추가·수정할 때마다), 다음이 UI 프로토콜 스펙(0.x), 가장 드문 것이 MCP·A2A 같은 코어 프로토콜의 대개정이다. 빈도가 다른 만큼 흡수 방식도 다르다 — 서버 목록은 설정화·자동화, 스펙 개정은 어댑터로 격리하고 수동 절차.

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| 프로토콜 — 코어 대개정 (예: MCP 2026-07-28의 상태 모델 변경) | 핸드셰이크·세션·메시지 구조 | 내부 포트 `call_tool(name, args) → result`, `list_tools()`. 에이전트 루프는 MCP를 모른다 | MCP 어댑터 | 새 어댑터 버전 추가 → 호환 레이어로 구·신 서버 동시 지원 → 서버 전환 완료 후 구 어댑터 제거 | 어댑터 + 서버 등록 정보. 에이전트 루프 변경 없음 |
| 프로토콜 — UI 스펙 0.x 변경 (A2UI 컴포넌트 개명, AG-UI 이벤트 필드) | 이벤트명·필드·컴포넌트 이름 | 내부 이벤트 스키마와 내부 UI 트리 스키마. 렌더러는 내부 스키마만 본다 | 프로토콜 ↔ 내부 스키마 변환 어댑터 | 어댑터 매핑 표 갱신 + 이벤트 재생 테스트 | 어댑터만. 렌더러·에이전트 변경 없음 |
| 툴·서버 목록 | 등록된 서버, 툴 정의, 소유자, 위험 등급 | 레지스트리 스키마, 툴 결과의 내부 형식 | 레지스트리 항목 | 등록 승인 절차(아래) + 툴 계약 테스트 + 설정 교체(배포 없음) | 툴 라우팅·툴 선택 골든셋 |
| 상대 에이전트 (A2A) | 상대 Agent Card, 능력, 인증 | 내부 `delegate(task) → task_state` 포트 | 상대별 어댑터·신뢰 등급 설정 | Card 재발견 + 통합 테스트 + 신뢰 등급 재평가 | 위임 경로만 |
| 규칙·정책 (타 레이어) | 어느 툴을 누가 쓸 수 있나 | 행동 게이트 인터페이스 | 규칙 값 | 정책 엔진 규칙 버전 교체 | 해당 게이트 |

- **프로토콜 교체와 "프로토콜을 쓰지 않기로 한 경계"도 같은 방식으로**: AG-UI를 다른 이벤트 프로토콜로 바꾸는 것도, 함수 직접 등록으로 시작한 툴이나 프레임워크 내장 스트리밍으로 시작한 프론트-백에 나중에 프로토콜을 켜는 것도 **같은 내부 포트 뒤**의 어댑터 추가로 끝나야 한다. 처음부터 프로토콜을 쓰는 것이 아니라 처음부터 포트를 두는 것이 싸다
- **코드 밖 설정으로 둘 것**: 서버 레지스트리(주소·스펙 버전·인증·소유자·위험 등급·enabled), 툴별 타임아웃·재시도·멱등 여부, A2A 상대 신뢰 등급, 프로토콜 ↔ 내부 스키마 매핑 표
- **포트·어댑터 뒤에 둘 외부 의존**: MCP 서버(툴 호출·발견), A2A 상대(위임), AG-UI 전송(이벤트), A2UI·MCP Apps(UI 내용), 각 프로토콜의 클라이언트 SDK
- **시점 재현성**: 트레이스에 (어댑터 버전, 서버 스펙 버전, 툴 정의 버전)을 남겨 "그때 어떤 툴 정의로 그 호출이 났나"를 재현

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성 표의 탐지 신호(서버별 오류율·툴 p95·태스크 상태 정체·버전 협상 실패·렌더 실패·가드레일 차단)는 **경계마다 하나씩 놓인 어댑터**가 낸다. 프로토콜은 관측을 정의하지 않으므로 어댑터가 스팬을 만들고 W3C Trace Context 헤더를 경계 너머로 전파한다(전파 규약은 [Part 5/03](../05-cross-cutting/03-observability-tracing.md)). 규약은 [07 관측성 설계 요소](07-operations-vocabulary.md). 공통 버전 키 5종 외에 이 단계는 **프로토콜 계층의 버전 3개**를 모든 경계 스팬에 붙인다 — `agent.protocol_version`(우리 어댑터가 말하는 스펙·SDK 버전), `agent.spec_version`(상대 서버·에이전트가 보고한 스펙 버전), `agent.catalog_version`(툴 정의 버전·해시). 셋이 어긋나는 조합이 호환 매트릭스 밖인지가 "스펙·SDK 버전 불일치" 장애의 탐지 원천이다.

| 기록 대상 | 스팬 / 이벤트 (이름, 부모) | 핵심 속성 (버전 키 포함) | 지표 (→ 어느 SLI) | 샘플링 · 보존 · PII |
|---|---|---|---|---|
| MCP 툴 호출 | `tool.invoke {tool_name}` (부모: 호출한 단계 스팬, 종류 CLIENT) — 서버가 자체 계측하면 자식 SERVER 스팬이 헤더로 이어짐 | `agent.mcp_server`(레지스트리 ID), `agent.protocol_version`, `agent.spec_version`, `agent.catalog_version`, `agent.tool_call_id`, `agent.tool_risk_level`, `agent.idempotency_key`(쓰기 툴), 인자·결과는 해시·크기·요약만, `agent.outcome`, `agent.circuit_state`, `tenant_id` | 서버별·툴별 RED(호출 수·실패율·p95), 타임아웃 비율, 결과 크기 분포 → 툴 호출 성공률·툴 p95 SLI | 메타데이터 전수. 인자·결과 본문은 opt-in(PII 마스킹 후 별도 저장소). 실패·차단·쓰기 툴 호출은 전수 보존 |
| 툴 발견·버전 협상 | `tool.discover {server}` (세션 시작 또는 서버 등록·갱신 시) | `agent.spec_version`(서버 보고값) vs 어댑터 지원 범위, `agent.negotiation_result`(ok / compat_layer / rejected), 툴 정의 해시의 직전 등록값 대비 변경 여부 | **프로토콜 버전 불일치 탐지**: 호환 매트릭스 밖 조합 건수(0이 정상), 호환 레이어 경유 비율, 툴 정의 해시 변경 이벤트 수 | 전수. 불일치·해시 변경은 이벤트로 승격 |
| A2A 위임 | `agent.delegate {remote_agent}` (종류 CLIENT) + 태스크 상태 전이 이벤트 `task.state_changed` | `agent.remote_agent_id`(Agent Card URL 해시), `agent.remote_card_version`, `agent.trust_grade`(internal / partner / public), `agent.task_id`, 위임 범위(등급), 상대 trace 링크, 마지막 상태 전이 이후 경과 시간 | 상대별 태스크 완료율·완료 시간·상태 정체 시간, 신뢰 등급별 검증기 거부율 → A2A 태스크 완료율 SLI | 전수. 상대 메시지 본문은 "외부 텍스트" 태그 + opt-in |
| AG-UI 스트림 | `ui.stream {session}` (연결 단위 스팬) + 이벤트 유형별 카운터 | 이벤트 수(텍스트 델타 · 툴 시작/종료 · 상태 패치 · 커스텀), **순서 번호 갭**(수신 순서 불일치 건수), 재연결 횟수·재전송 범위, 연결 지속 시간, `agent.protocol_version`(AG-UI 이벤트 스키마 버전) | 연결 성공률·재접속률, 이벤트 순서 위반율, 백프레셔(큐 상한 초과 → 스냅샷 재동기화) 발동률 → 스트림 연결 성공률 SLI | 메타데이터만 전수. 이벤트 페이로드는 기록하지 않음 |
| MCP Apps 샌드박스 | `ui.render {mcp_app}` (프론트가 보고, 부모는 `tool.invoke`) | `agent.mcp_server`, UI 번들 해시, `agent.render_result`(ok / csp_blocked / load_failed / fallback_text), CSP 위반 리포트 ID | 서버별 샌드박스 로드 실패율, 폴백 렌더 비율 → 렌더 실패율 SLI | 전수 |
| 서킷·킬 스위치 | 이벤트 `circuit.state_changed`, `killswitch.toggled` (서버·툴·상대 에이전트 단위) | 대상 ID, 이전·이후 상태, 트리거(자동 임계 / 수동), 조작자 역할 | **서버별 서킷 상태**와 열림 누적 시간, 킬 스위치가 켜진 툴 수(대시보드 상시 표시) | 전수, 감사 레코드로도 |

| 알림 | 조건 (예시) | 심각도 | 런북 (첫 3단계) |
|---|---|---|---|
| MCP 서버 다운·타임아웃율 | 특정 서버의 실패율 또는 타임아웃 비율이 임계 초과 5분 지속, 또는 서킷 열림 15분 지속 | P2 — 등급 3 이상 툴을 가진 서버면 P1 | ① 레지스트리에서 소유자·대체 서버 확인 ② 서킷 상태와 툴 노출 목록 제외 여부 확인 ③ 소유 팀 호출, 대체 서버 전환 또는 툴 킬 스위치 |
| 프로토콜 버전 불일치 | `agent.negotiation_result=rejected` 1건 이상, 호환 레이어 경유 비율 급증, 또는 등록된 툴 정의 해시가 승인 절차 없이 변경 | P2 — 툴 정의 해시 무단 변경은 P1(공급망) | ① 어느 서버·어느 스펙 조합인지 확인 ② 호환 매트릭스에 있는 조합인지 대조 ③ 매트릭스 밖이면 서버 등록 일시 해제, 해시 변경이면 보안 검토 후 재등록 |
| 샌드박스 로드 실패 | 특정 MCP Apps 서버의 렌더 실패율 급증 또는 CSP 위반 리포트 급증 | P3(텍스트 폴백이 동작하면) / P2 | ① 폴백 렌더 비율로 사용자 영향 확인 ② UI 번들 해시 변경 여부 ③ 해당 서버 UI 비활성(텍스트·구조화 결과만) + 등록 재심사 |
| A2A 태스크 정체 | 상태 전이 없는 시간이 타임아웃의 50%를 넘는 태스크 비율 급증, 특정 상대에 집중 | P2 | ① 상대별 분해 ② 상대 Agent Card·엔드포인트 상태 확인 ③ 상대 서킷 열기 + 자체 처리 경로 전환, 반복 시 신뢰 등급 하향 |
| AG-UI 순서 위반·재연결 폭증 | 순서 번호 갭 비율 또는 재접속률 임계 초과 | P2 | ① 스트림 게이트웨이 연결 수·메모리 확인 ② 백프레셔 발동 여부 ③ 스냅샷 재동기화 강제, 게이트웨이 스케일 아웃 |

대시보드에서 이 단계를 보는 뷰: ② 레이어별 SLI에서 **네 경계가 네 패널** — 서버별 RED·서킷 상태(툴), 상대 에이전트별 태스크 완료·정체(에이전트 간), 스트림 연결·순서 위반(프론트-백), 샌드박스 로드 결과(UI 내용). ③ 비용·판정 분포에는 툴 정의 토큰 비용(노출 서버 수 × 툴 수)과 툴 라우팅 판정 분포가 나타난다. 감사 추적으로 넘기는 필드: 거버넌스 접점 표의 감사 필드(서버 ID·스펙·어댑터 버전, 툴 호출 ID, 게이트 판정과 규칙 버전, 승인자, A2A 태스크 ID·신뢰 등급, 킬 스위치 상태) — 지연·이벤트 수·결과 크기는 관측에만. 이 단계의 관측이 없으면 못 보는 장애: 구·신 스펙 서버가 혼재해 특정 서버의 기능만 조용히 빠지는 것, 상대 에이전트의 Agent Card가 바뀌어 위임 범위가 늘어난 것, 툴 정의가 등록 승인 없이 바뀐 것.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

프로토콜은 보안·권한·감사를 **정의하지 않는다**("한계와 리스크" 참조). 거버넌스 질문의 핵심은 "스펙이 비워둔 것을 누가 소유하나"다.

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 | 프로토콜 경계 자체는 등급 없음. **툴마다** 등급을 매겨 레지스트리에 기록한다(읽기 툴 1~2, 외부 전송·결제·삭제 툴 3~5). A2A 위임은 상대가 수행할 행동의 등급 + 신뢰 등급으로 판정 |
| 가드레일 위치 | **행동**(툴 호출 직전 규칙 게이트, 등급 3 이상은 승인), **입력**(툴 결과·상대 메시지는 데이터로 격리), **출력**(UI 트리·이벤트에 PII·외부 URL 검사) |
| 게이트 출력과 판정 수단 | 툴 호출: 통과 / 차단 / 승인 요청 / 저하(읽기 전용으로 축소). 권한·한도는 규칙만. 툴 선택의 적절성은 결정 모델이 보조할 수 있으나 최종은 규칙 |
| RACI — 스펙이 비워둔 것 | 인증·권한: R 플랫폼 엔지니어, A 보안 책임자. MCP 서버 등록: R 서버 소유 팀, A 플랫폼 아키텍트, C 보안. A2A 상대 신뢰 등급: R 통합 담당, A 서비스 소유자, C 법무(조직 간 계약). 감사 로그: R 플랫폼, A 운영 책임자. A가 비어 있는 행이 없어야 한다 |
| MCP 서버 등록 승인 절차 | ① 서버 소유자·연락처 ② 스펙 버전·인증 방식 ③ 툴별 위험 등급·쓰기 여부·멱등 여부 ④ 툴 계약 테스트 통과 ⑤ 보안 검토(등급 3 이상 툴 포함 시 필수) ⑥ 레지스트리 등록. 외부(서드파티) 서버는 ⑤ 필수 + 샌드박스 정책 |
| 외부 A2A 에이전트 신뢰 등급 | 예시 3단계: **내부**(같은 조직, 전 등급 위임 가능) / **계약 파트너**(등급 1~3 위임, 결과는 검증기 통과 필수) / **공개**(등급 1 읽기만, 결과는 참고 정보로만 표시). 등급은 설정이며 사고 시 즉시 하향 |
| 감사 추적에 남길 필드 | 서버 ID·스펙 버전·어댑터 버전, 툴 이름·툴 정의 버전·**툴 호출 ID**, 인자 요약(PII 마스킹)·결과 요약, 게이트 판정과 적용 규칙 버전, 승인자, 테넌트·요청자, A2A 태스크 ID·상대 에이전트 ID·신뢰 등급, 킬 스위치 상태 |

### 운영 준비도 체크
- [ ] 모든 MCP 서버가 레지스트리에 소유자·스펙 버전·인증·툴별 위험 등급·enabled 플래그와 함께 등록되어 있고, 서버 단위 서킷 브레이커와 **툴 단위 킬 스위치**가 배포 없이 동작하는가
- [ ] 쓰기 툴에 멱등 키·타임아웃·재시도 상한이 툴 정의에 명시되어 있는가
- [ ] 서버 스펙 ↔ 클라이언트 SDK 호환 매트릭스가 있고, 업그레이드 창이 달력에 있는가
- [ ] 에이전트 루프·렌더러가 프로토콜 타입을 직접 참조하지 않고 내부 포트·스키마만 보는가(프로토콜 없이 연결한 경계 포함)
- [ ] 인증·권한·감사 각각의 A(책임자)가 정해져 있는가
- [ ] 트레이스에 서버 ID·스펙 버전·툴 호출 ID·게이트 판정·승인자가 남는가
- [ ] 네 경계 모두에서 어댑터가 W3C Trace Context 헤더를 전파하고, `tool.invoke`·`agent.delegate`·`ui.stream` 스팬에 `agent.protocol_version`·`agent.spec_version`·`agent.catalog_version`이 남는가
- [ ] 호환 매트릭스 밖 스펙 조합과 툴 정의 해시의 무단 변경이 `tool.discover` 이벤트로 탐지되어 알림이 울리고, 서버별 서킷 상태·킬 스위치 상태가 대시보드에 상시 표시되는가
