# 평가와 관측성 기초

> **범위**: 에이전트 시스템을 "잘 된다"고 판단하는 체계의 기본 구성(골든셋, 평가 방법 4종, 트레이싱)과 갖추는 순서. RAG·에이전트별 세부 지표는 [Part 3/13](../03-agent-workflow-rag/13-evaluation-rag-agents.md), Generative UI 평가는 [Part 4/10](../04-dynamic-ui/10-evaluation-genui.md), 운영 관측성 도구 비교는 [Part 5/03](../05-cross-cutting/03-observability-tracing.md).

## 요약 (3줄)

1. 평가 없는 에이전트 개발은 **느낌으로 하는 개발**이다. 프롬프트를 바꿨는데 좋아졌는지 나빠졌는지 모르면 개선이 아니라 변경이다.
2. 평가 수단은 규칙 기반 → 참조 기반(골든셋) → LLM-as-judge → 사람 순으로 **비용과 신뢰도가 함께** 오른다. 네 가지를 층으로 쌓고, 비싼 것은 샘플링한다.
3. 관측성(트레이싱)은 평가의 전제다. 한 턴이 어떤 검색·판정·툴 호출·생성을 거쳤는지 기록돼야 어디서 틀렸는지 알 수 있다. OpenTelemetry GenAI 컨벤션은 2026-10 현재 **아직 Development 상태**라 속성명이 바뀔 수 있다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** | ① 골든셋(입력-기대출력-근거 쌍) ② 자동 평가 파이프라인(규칙 + 참조 + judge) ③ 트레이스 스키마(턴 → 에이전트 호출 → 모델/툴/검색 스팬) ④ 운영 지표 정의 |
| **언제** | **첫 프롬프트를 쓰기 전에** 골든셋 20~50건부터. 평가는 나중에 붙이는 것이 아니라 개발 루프의 일부 |
| **어떻게** | ① 대표 질의 수집(실 로그 > 전문가 작성 > 합성) → ② 기대 답과 근거를 전문가가 라벨 → ③ 결정론적 체크(스키마, citation 존재, 금칙어)를 CI에 → ④ LLM-as-judge를 샘플링으로 → ⑤ 트레이싱을 모든 환경에 → ⑥ 운영 로그에서 실패 사례를 골든셋으로 환류 |
| **왜** | LLM 시스템은 비결정적이고 구성 요소(모델, 프롬프트, 인덱스, 툴)가 각자 바뀐다. 회귀를 자동으로 잡지 못하면 어떤 변경도 안전하게 배포할 수 없다 |

## 문제와 맥락

전통 소프트웨어 테스트는 "입력 X에 출력 Y"를 단언한다. LLM 시스템은 같은 입력에 다른 출력이 나오고, 출력이 "맞다"의 기준도 모호하다(여러 표현이 다 맞을 수 있다). 게다가 평가 대상이 모델 하나가 아니라 **검색 → 판정 → 생성 → 검증 → UI** 파이프라인 전체다. 어느 단계가 틀렸는지 분리하지 않으면 개선 지점을 못 찾는다. 그래서 (a) 단계별 평가 (b) 확률적 출력을 다루는 평가 방법 (c) 단계를 잇는 트레이스가 필요하다.

## 핵심 개념

### 평가 수단 4층

| 층 | 수단 | 측정하는 것 | 비용 | 신뢰도 | 적용 |
|---|---|---|---|---|---|
| 1 | **규칙 기반** | 스키마 준수, citation 존재·유효, 금칙어, 길이, 지연, 툴 호출 성공 | 하 | 높음(측정 범위 안에서) | 모든 요청, CI 게이트 |
| 2 | **참조 기반 (골든셋)** | 기대 답과의 일치(정확 매치, 포함, 임베딩 유사도), 기대 근거 검색 여부(recall@k) | 중 (라벨링) | 높음 | 배포 전 회귀, 인덱스·모델 교체 시 |
| 3 | **LLM-as-judge** | faithfulness(근거 부합), relevancy, 완결성, 톤 등 참조 없이 판정 가능한 품질 | 중~상 (토큰) | 중 (편향·일관성 한계) | 샘플링, 골든셋 보조, 운영 모니터링 |
| 4 | **사람 평가** | 최종 품질, 유해성, 도메인 정확성 | 상 | 가장 높음 | judge 보정, 고위험 샘플, 정기 감사 |

**LLM-as-judge의 알려진 실패**: 긴 답 선호, 자기 생성물 선호, 위치 편향, 판정 JSON 파싱 실패 시 NaN이 집계에서 조용히 빠지는 문제 `[2차]`. judge 자체를 사람 라벨과 맞춰 보정(alignment)하는 절차가 필요하다. RAGAS 등은 judge 정렬 가이드를 제공한다 `[2차]`.

### 골든셋 설계

- **크기**: 시작 20~50건, 운영 전 200건 이상, 카테고리별 최소 10건
- **구성**: 입력, 기대 출력(또는 허용 범위), 기대 근거(문서 ID·청크), 카테고리, 난이도, 작성자, 날짜
- **출처 우선순위**: 실제 로그(익명화) > 도메인 전문가 작성 > LLM 합성(검수 필수)
- **한국어·혼합 언어·비격식 입력 포함**: 결정 모델·임베딩 모델 대부분이 영어 중심이므로 한국어 성능은 별도로 측정
- **환류**: 운영 중 실패·불만·사람 개입 사례를 주기적으로 골든셋에 추가
- **분리**: 프롬프트 튜닝에 쓰는 개발셋과 최종 판정용 홀드아웃을 분리

### 단계별 평가 분리

| 단계 | 평가 질문 | 지표 예 |
|---|---|---|
| 판정·라우팅 | 올바른 경로·카테고리를 골랐나 | 정확도, 보정 곡선(ECE) |
| 검색 | 기대 근거가 상위 k에 있나 | recall@k, MRR, context precision |
| 생성 | 근거에 부합하나, 질문에 답했나 | faithfulness, answer relevancy, citation 정확도 |
| 툴 실행 | 올바른 툴을 올바른 인자로, 성공했나 | 툴 선택 정확도, 인자 스키마 통과율, 성공률 |
| 검증·게이트 | 틀린 출력을 걸렀나, 맞는 출력을 잘못 거르지 않았나 | 검출률, 오탐률 |
| UI | 올바른 컴포넌트를 띄웠나, 렌더됐나 | 선택 정확도, 렌더 실패율 ([Part 4/10](../04-dynamic-ui/10-evaluation-genui.md)) |
| End-to-End | 사용자 과업이 끝났나 | 과업 완료율, 턴 수, 사람 개입률 |

### 트레이싱

한 사용자 턴을 **세션 → 에이전트 호출 → (모델 호출 | 툴 호출 | 검색 | 판정) 스팬**의 트리로 기록한다.

- **OpenTelemetry GenAI 시맨틱 컨벤션**: `invoke_agent` 스팬 아래 모델·툴 호출 자식 스팬 구조를 정의. 2026-10 현재 모든 `gen_ai.*` 속성이 **Development** 안정성 등급이며, v1.42.0에서 별도 저장소(semantic-conventions-genai)로 분리됐고 태그된 릴리스가 없어 버전 고정이 까다롭다 `[2차]`. 2026-06 "안정화됐다"는 한 소스는 레지스트리로 확인되지 않아 미검증
- **프롬프트·출력 본문 기록은 opt-in**: PII 노출 위험. 본문은 별도 저장소에 두고 스팬에는 참조만 `[2차]`
- **기록할 것**: 모델명·버전, 토큰 수(입력·출력·캐시), 지연, 판정 결과와 확신도, 검색된 근거 ID, 툴 인자·결과 요약, 검증 통과 여부, 비용
- **벤더 SDK vs OTel**: Langfuse·LangSmith·Arize 등 벤더 SDK는 즉시 쓸 수 있는 UI를 주고, OTel은 벤더 중립이나 컨벤션 미성숙. 둘 다 OTel 익스포트를 지원하는 추세

## 아키텍처 / 파이프라인

```
개발 루프:  변경 ─▶ 규칙 체크(CI) ─▶ 골든셋 회귀 ─▶ judge 샘플링 ─▶ 배포 판단
                                                           ▲
운영 루프:  요청 ─▶ 트레이스 기록 ─▶ 규칙 모니터 ─▶ judge 샘플링 ─▶ 실패 사례 ─▶ 골든셋 환류
                                                     └─▶ 사람 리뷰 (고위험·불만)
```

## 기술 비교표 — 평가·관측 수단

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 규칙 기반 체크 (스키마·citation·금칙어) | 모든 시스템의 1층, CI 게이트 | 의미 품질 측정 | 하 | 표준 | `[검증]` |
| 골든셋 참조 평가 | 회귀 탐지, 모델·인덱스 교체 | 정답이 하나가 아닌 개방형 과업 (허용 범위로 보완) | 중 | 표준 | `[검증]` |
| RAGAS / DeepEval / 유사 라이브러리 | RAG 표준 지표(faithfulness, context precision/recall, relevancy) 빠른 도입 | 도메인 특화 품질 기준 | 중 | 안정 | `[2차]` judge 한계 공유 |
| LLM-as-judge 자체 구현 (G-Eval 류) | 도메인 특화 루브릭 | judge 보정 없이 운영 지표로 쓰기 | 중~상 | 안정 | `[검증]` 편향 연구 다수 |
| 결정 모델을 judge로 | 합격/불합격·점수처럼 닫힌 판정, 대량·저비용 온라인 판정 | 서술형 피드백 필요 | 하 (호출) | 신생 | `[2차]` 사례 미확인 |
| 사람 평가 | judge 보정, 고위험, 정기 감사 | 전수 | 상 | 표준 | `[검증]` |
| OTel GenAI 컨벤션 | 벤더 중립, 기존 OTel 인프라 보유 | 속성 안정성 필요(아직 Development) | 중 | 신생 | `[2차]` |
| 벤더 관측 SDK (Langfuse, LangSmith, Arize 등) | 즉시 UI·평가 통합, 소규모 팀 | 벤더 종속 회피 | 하~중 | 안정 | `[벤더]` |

### 선택 가이드

- **아직 아무것도 없다면** → 골든셋 30건 + 규칙 체크 + 벤더 SDK 트레이싱. 이유: 하루면 갖출 수 있고 이후 모든 결정의 기반
- **RAG 품질을 측정한다면** → RAGAS 류 표준 지표 + 자체 골든셋. 이유: 지표 정의를 새로 만들지 않아도 됨. 단 judge 보정 필수
- **판정 지점(라우팅·게이트)의 품질이라면** → 정확도 + 보정 곡선. 결정 모델을 썼다면 특히 보정 확인
- **기존 OTel 인프라가 있다면** → OTel GenAI 컨벤션으로 통일하되 속성명 변경에 대비해 매핑 계층
- **판단이 어려우면** → 벤더 SDK로 시작하고 OTel 익스포트를 켜 둔다. 이유: 전환 비용 최소화

## 설계 시 고려사항 (체크리스트)

- [ ] 첫 프롬프트 작성 전에 골든셋 20건 이상이 있는가
- [ ] 골든셋에 한국어·혼합 언어·비격식·적대적 입력이 포함되는가
- [ ] 개발셋과 홀드아웃이 분리되어 있는가
- [ ] 규칙 체크가 CI에서 돌고 실패 시 배포가 막히는가
- [ ] LLM-as-judge를 사람 라벨과 비교해 보정했는가, judge 모델 버전을 고정했는가
- [ ] judge 파싱 실패가 집계에서 조용히 빠지지 않고 별도 집계되는가
- [ ] 단계별(판정·검색·생성·툴·검증·UI) 지표가 분리되어 있는가
- [ ] 모든 환경에서 트레이스가 기록되고, 한 턴을 끝까지 따라갈 수 있는가
- [ ] 프롬프트·출력 본문의 PII 처리 정책이 있는가
- [ ] 운영 실패 사례가 골든셋으로 환류되는 주기와 담당이 있는가
- [ ] 모델·프롬프트·인덱스·컴포넌트 카탈로그 버전이 트레이스에 기록되는가 ([Part 5/05](../05-cross-cutting/05-llmops-agentops.md))

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| LLM-as-judge 편향 | 긴 답·자기 생성물 선호로 지표 왜곡 | 사람 라벨로 보정, 쌍대 비교 시 순서 무작위화, 여러 judge |
| 골든셋 과적합 | 골든셋 점수는 오르는데 운영 품질은 그대로 | 홀드아웃 분리, 운영 샘플 환류, 골든셋 주기 갱신 |
| OTel GenAI 컨벤션 미안정 | 속성명 변경으로 대시보드·쿼리 깨짐 | 매핑 계층, 버전 고정, 레지스트리 직접 확인 |
| 비용 | judge를 전수 적용하면 서빙 비용을 넘음 | 샘플링, 규칙 체크 우선, 결정 모델 judge 검토 |
| 트레이스의 PII | 프롬프트 본문에 개인정보 | opt-in 기록, 마스킹, 별도 저장소 |
| 단계별 지표가 End-to-End와 어긋남 | 검색 recall은 높은데 과업 완료율은 낮음 | E2E 지표를 최상위로, 단계 지표는 진단용 |
