# 평가와 관측성 기초

> **범위**: 에이전트 시스템을 "잘 된다"고 판단하는 체계의 기본 구성(골든셋, 평가 방법 4종, 트레이싱)과 갖추는 순서. RAG·에이전트별 세부 지표는 [Part 3/13](../03-agent-workflow-rag/13-evaluation-rag-agents.md), Generative UI 평가는 [Part 4/10](../04-dynamic-ui/10-evaluation-genui.md), 운영 관측성 도구 비교는 [Part 5/03](../05-cross-cutting/03-observability-tracing.md).

## 요약 (3줄)

1. 평가 없는 에이전트 개발은 **느낌으로 하는 개발**이다. 프롬프트를 바꿨는데 좋아졌는지 나빠졌는지 모르면 개선이 아니라 변경이다.
2. 평가 수단은 규칙 기반 → 참조 기반(골든셋) → LLM-as-judge → 사람 순으로 **비용과 신뢰도가 함께** 오른다. 네 가지를 층으로 쌓고, 비싼 것은 샘플링한다.
3. 관측성(트레이싱)은 평가의 전제다. 한 턴이 어떤 검색·판정·툴 호출·생성을 거쳤는지 기록돼야 어디서 틀렸는지 알 수 있다. OpenTelemetry GenAI 컨벤션은 2026-10 현재 **아직 Development 상태**라 속성명이 바뀔 수 있다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** | ① 골든셋(입력-기대출력-근거 쌍) ② 자동 평가 파이프라인(규칙 + 참조 + judge) ③ 트레이스 스키마(턴 → 에이전트 호출 → 모델/툴/검색 스팬) ④ 운영 지표 정의 |
| **언제** | **첫 프롬프트를 쓰기 전에** 골든셋 20~50건부터. 평가는 나중에 붙이는 것이 아니라 개발 루프의 일부 |
| **어떻게** | ① 대표 질의 수집(실 로그 > 전문가 작성 > 합성) → ② 기대 답과 근거를 전문가가 라벨 → ③ 결정론적 체크(스키마, citation 존재, 금칙어)를 CI에 → ④ LLM-as-judge를 샘플링으로 → ⑤ 트레이싱을 모든 환경에 → ⑥ 운영 로그에서 실패 사례를 골든셋으로 환류 |
| **왜** | LLM 시스템은 비결정적이고 구성 요소(모델, 프롬프트, 인덱스, 툴)가 각자 바뀐다. 회귀를 자동으로 잡지 못하면 어떤 변경도 안전하게 배포할 수 없다 |

## 문제와 맥락

전통 소프트웨어 테스트는 "입력 X에 출력 Y"를 단언한다. LLM 시스템은 같은 입력에 다른 출력이 나오고, 출력이 "맞다"의 기준도 모호하다(여러 표현이 다 맞을 수 있다). 게다가 평가 대상이 모델 하나가 아니라 **검색 → 판정 → 생성 → 검증 → UI** 파이프라인 전체다. 어느 단계가 틀렸는지 분리하지 않으면 개선 지점을 못 찾는다. 그래서 (a) 단계별 평가 (b) 확률적 출력을 다루는 평가 방법 (c) 단계를 잇는 트레이스가 필요하다.

## 핵심 개념

### 평가 수단 4층

| 층 | 수단 | 측정하는 것 | 비용 | 신뢰도 | 적용 |
|---|---|---|---|---|---|
| 1 | **규칙 기반** | 스키마 준수, citation 존재·유효, 금칙어, 길이, 지연, 툴 호출 성공 | 하 | 높음(측정 범위 안에서) | 모든 요청, CI 게이트 |
| 2 | **참조 기반 (골든셋)** | 기대 답과의 일치(정확 매치, 포함, 임베딩 유사도), 기대 근거 검색 여부(recall@k) | 중 (라벨링) | 높음 | 배포 전 회귀, 인덱스·모델 교체 시 |
| 3 | **LLM-as-judge** | faithfulness(근거 부합), relevancy, 완결성, 톤 등 참조 없이 판정 가능한 품질 | 중~상 (토큰) | 중 (편향·일관성 한계) | 샘플링, 골든셋 보조, 운영 모니터링 |
| 4 | **사람 평가** | 최종 품질, 유해성, 도메인 정확성 | 상 | 가장 높음 | judge 보정, 고위험 샘플, 정기 감사 |

**LLM-as-judge의 알려진 실패**: 긴 답 선호, 자기 생성물 선호, 위치 편향, 판정 JSON 파싱 실패 시 NaN이 집계에서 조용히 빠지는 문제 `[2차]`. judge 자체를 사람 라벨과 맞춰 보정(alignment)하는 절차가 필요하다. RAGAS 등은 judge 정렬 가이드를 제공한다 `[2차]`.

### 골든셋 설계

- **크기**: 시작 20~50건, 운영 전 200건 이상, 카테고리별 최소 10건
- **구성**: 입력, 기대 출력(또는 허용 범위), 기대 근거(문서 ID·청크), 카테고리, 난이도, 작성자, 날짜
- **출처 우선순위**: 실제 로그(익명화) > 도메인 전문가 작성 > LLM 합성(검수 필수)
- **한국어·혼합 언어·비격식 입력 포함**: 결정 모델·임베딩 모델 대부분이 영어 중심이므로 한국어 성능은 별도로 측정
- **환류**: 운영 중 실패·불만·사람 개입 사례를 주기적으로 골든셋에 추가
- **분리**: 프롬프트 튜닝에 쓰는 개발셋과 최종 판정용 홀드아웃을 분리

### 단계별 평가 분리

| 단계 | 평가 질문 | 지표 예 |
|---|---|---|
| 판정·라우팅 | 올바른 경로·카테고리를 골랐나 | 정확도, 보정 곡선(ECE) |
| 검색 | 기대 근거가 상위 k에 있나 | recall@k, MRR, context precision |
| 생성 | 근거에 부합하나, 질문에 답했나 | faithfulness, answer relevancy, citation 정확도 |
| 툴 실행 | 올바른 툴을 올바른 인자로, 성공했나 | 툴 선택 정확도, 인자 스키마 통과율, 성공률 |
| 검증·게이트 | 틀린 출력을 걸렀나, 맞는 출력을 잘못 거르지 않았나 | 검출률, 오탐률 |
| UI | 올바른 컴포넌트를 띄웠나, 렌더됐나 | 선택 정확도, 렌더 실패율 ([Part 4/10](../04-dynamic-ui/10-evaluation-genui.md)) |
| End-to-End | 사용자 과업이 끝났나 | 과업 완료율, 턴 수, 사람 개입률 |

### 트레이싱

한 사용자 턴을 **세션 → 에이전트 호출 → (모델 호출 | 툴 호출 | 검색 | 판정) 스팬**의 트리로 기록한다.

- **OpenTelemetry GenAI 시맨틱 컨벤션**: `invoke_agent` 스팬 아래 모델·툴 호출 자식 스팬 구조를 정의. 2026-10 현재 모든 `gen_ai.*` 속성이 **Development** 안정성 등급이며, v1.42.0에서 별도 저장소(semantic-conventions-genai)로 분리됐고 태그된 릴리스가 없어 버전 고정이 까다롭다 `[2차]`. 2026-06 "안정화됐다"는 한 소스는 레지스트리로 확인되지 않아 미검증
- **프롬프트·출력 본문 기록은 opt-in**: PII 노출 위험. 본문은 별도 저장소에 두고 스팬에는 참조만 `[2차]`
- **기록할 것**: 모델명·버전, 토큰 수(입력·출력·캐시), 지연, 판정 결과와 확신도, 검색된 근거 ID, 툴 인자·결과 요약, 검증 통과 여부, 비용
- **벤더 SDK vs OTel**: Langfuse·LangSmith·Arize 등 벤더 SDK는 즉시 쓸 수 있는 UI를 주고, OTel은 벤더 중립이나 컨벤션 미성숙. 둘 다 OTel 익스포트를 지원하는 추세

## 아키텍처 / 파이프라인

```
개발 루프:  변경 ─▶ 규칙 체크(CI) ─▶ 골든셋 회귀 ─▶ judge 샘플링 ─▶ 배포 판단
                                                           ▲
운영 루프:  요청 ─▶ 트레이스 기록 ─▶ 규칙 모니터 ─▶ judge 샘플링 ─▶ 실패 사례 ─▶ 골든셋 환류
                                                     └─▶ 사람 리뷰 (고위험·불만)
```

## 기술 비교표 — 평가·관측 수단

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 규칙 기반 체크 (스키마·citation·금칙어) | 모든 시스템의 1층, CI 게이트 | 의미 품질 측정 | 하 | 표준 | `[검증]` |
| 골든셋 참조 평가 | 회귀 탐지, 모델·인덱스 교체 | 정답이 하나가 아닌 개방형 과업 (허용 범위로 보완) | 중 | 표준 | `[검증]` |
| RAGAS / DeepEval / 유사 라이브러리 | RAG 표준 지표(faithfulness, context precision/recall, relevancy) 빠른 도입 | 도메인 특화 품질 기준 | 중 | 안정 | `[2차]` judge 한계 공유 |
| LLM-as-judge 자체 구현 (G-Eval 류) | 도메인 특화 루브릭 | judge 보정 없이 운영 지표로 쓰기 | 중~상 | 안정 | `[검증]` 편향 연구 다수 |
| 결정 모델을 judge로 | 합격/불합격·점수처럼 닫힌 판정, 대량·저비용 온라인 판정 | 서술형 피드백 필요 | 하 (호출) | 신생 | `[2차]` 사례 미확인 |
| 사람 평가 | judge 보정, 고위험, 정기 감사 | 전수 | 상 | 표준 | `[검증]` |
| OTel GenAI 컨벤션 | 벤더 중립, 기존 OTel 인프라 보유 | 속성 안정성 필요(아직 Development) | 중 | 신생 | `[2차]` |
| 벤더 관측 SDK (Langfuse, LangSmith, Arize 등) | 즉시 UI·평가 통합, 소규모 팀 | 벤더 종속 회피 | 하~중 | 안정 | `[벤더]` |

### 선택 가이드

- **아직 아무것도 없다면** → 골든셋 30건 + 규칙 체크 + 벤더 SDK 트레이싱. 이유: 하루면 갖출 수 있고 이후 모든 결정의 기반
- **RAG 품질을 측정한다면** → RAGAS 류 표준 지표 + 자체 골든셋. 이유: 지표 정의를 새로 만들지 않아도 됨. 단 judge 보정 필수
- **판정 지점(라우팅·게이트)의 품질이라면** → 정확도 + 보정 곡선. 결정 모델을 썼다면 특히 보정 확인
- **기존 OTel 인프라가 있다면** → OTel GenAI 컨벤션으로 통일하되 속성명 변경에 대비해 매핑 계층
- **판단이 어려우면** → 벤더 SDK로 시작하고 OTel 익스포트를 켜 둔다. 이유: 전환 비용 최소화

## 설계 시 고려사항 (체크리스트)

- [ ] 첫 프롬프트 작성 전에 골든셋 20건 이상이 있는가
- [ ] 골든셋에 한국어·혼합 언어·비격식·적대적 입력이 포함되는가
- [ ] 개발셋과 홀드아웃이 분리되어 있는가
- [ ] 규칙 체크가 CI에서 돌고 실패 시 배포가 막히는가
- [ ] LLM-as-judge를 사람 라벨과 비교해 보정했는가, judge 모델 버전을 고정했는가
- [ ] judge 파싱 실패가 집계에서 조용히 빠지지 않고 별도 집계되는가
- [ ] 단계별(판정·검색·생성·툴·검증·UI) 지표가 분리되어 있는가
- [ ] 모든 환경에서 트레이스가 기록되고, 한 턴을 끝까지 따라갈 수 있는가
- [ ] 프롬프트·출력 본문의 PII 처리 정책이 있는가
- [ ] 운영 실패 사례가 골든셋으로 환류되는 주기와 담당이 있는가
- [ ] 모델·프롬프트·인덱스·컴포넌트 카탈로그 버전이 트레이스에 기록되는가 ([Part 5/05](../05-cross-cutting/05-llmops-agentops.md))

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| LLM-as-judge 편향 | 긴 답·자기 생성물 선호로 지표 왜곡 | 사람 라벨로 보정, 쌍대 비교 시 순서 무작위화, 여러 judge |
| 골든셋 과적합 | 골든셋 점수는 오르는데 운영 품질은 그대로 | 홀드아웃 분리, 운영 샘플 환류, 골든셋 주기 갱신 |
| OTel GenAI 컨벤션 미안정 | 속성명 변경으로 대시보드·쿼리 깨짐 | 매핑 계층, 버전 고정, 레지스트리 직접 확인 |
| 비용 | judge를 전수 적용하면 서빙 비용을 넘음 | 샘플링, 규칙 체크 우선, 결정 모델 judge 검토 |
| 트레이스의 PII | 프롬프트 본문에 개인정보 | opt-in 기록, 마스킹, 별도 저장소 |
| 단계별 지표가 End-to-End와 어긋남 | 검색 recall은 높은데 과업 완료율은 낮음 | E2E 지표를 최상위로, 단계 지표는 진단용 |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [07 운영 용어](07-operations-vocabulary.md). 평가·관측 체계는 다른 단계의 운영 설계를 **검증하는 수단**이면서 그 자체가 운영되는 시스템이다. 확장성·안정성·유지보수 소절은 후자("평가 파이프라인과 트레이스 저장소가 10배가 되면·죽으면·바뀌면")를, 변화 대응 소절은 전자("다른 레이어의 변화를 무엇으로 잡아내나")를 다룬다. 레이어 간 비교는 [Part 5/06](../05-cross-cutting/06-operational-design-matrix.md), 도구 비교는 [Part 5/03](../05-cross-cutting/03-observability-tracing.md).

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 골든셋 크기 | 200건 → 2,000건이면 전체 회귀 1회의 judge 토큰 비용과 소요 시간이 배포를 막을 만큼 커진다 | 층 구분: 규칙·참조 평가는 전수(싸다), judge는 **카테고리별 층화 샘플링**(예시: 카테고리당 최소 10건 + 변경 영향 카테고리는 전수). 변경 유형별로 돌리는 부분집합을 정의(변화 대응 표) | 골든셋 건수 × judge 호출 비용 |
| 운영 트래픽 (judge 모니터링) | 운영 요청 전수에 judge를 걸면 서빙 비용을 넘는다("한계와 리스크") | 샘플링률을 설정으로(예시: 1~5%), 고위험 카테고리·사람 개입 건은 전수, 닫힌 판정은 결정 모델 judge로 저비용화 | 요청 수 × 샘플링률 × judge 비용 |
| 트레이스 저장량 | 스팬 수 = 요청 수 × 턴당 호출 수. 본문(프롬프트·출력)까지 넣으면 저장량이 수십 배 | 스팬 메타데이터와 본문 저장소 분리(본문은 참조만, opt-in), 테일 샘플링(오류·느린 요청·사람 개입은 보존, 정상은 비율 보존), 보존 기간 계층(예시: 전체 7일, 샘플 90일, 감사 레코드는 별도 장기) | 요청 수 × 턴당 스팬 수 × 본문 크기 |
| 테넌트 | 테넌트별 품질 지표가 필요한데 테넌트 키가 트레이스에 없으면 집계 불가 | 테넌트 키를 모든 스팬·평가 레코드에, 집계는 테넌트를 차원으로 한 번에 | 테넌트 수 × 지표 수 |

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| judge 모델 변경·드리프트로 지표 점프 | 없음(내부). 품질 지표가 하루 만에 크게 움직여 거짓 알림 또는 거짓 안심 | judge 모델 버전 변경 이벤트와 지표 변동의 시각 일치, judge-사람 라벨 일치율 하락 | judge 버전 고정이 예방. 변경 시에는 **같은 골든셋을 구·신 judge로 병렬 채점**해 보정 오프셋을 산출한 뒤 전환 | 일치율이 보정 기준 아래 |
| 트레이스 유실 (수집기 다운, 큐 포화) | 없음. 대시보드 공백, 사후 분석 불가 | 수집된 스팬 수 vs 요청 수 비율 | 로컬 버퍼 + 재전송. 트레이스 실패가 **요청 처리를 막지 않게**(비동기) 하되 감사 레코드만은 동기 기록 | 유실률이 기준 초과(예시: 1%) |
| OTel 속성명 변경 (Development 컨벤션) | 없음. 대시보드·알림 쿼리가 빈 값 | 매핑 계층의 미지 속성 경고, 주요 지표가 0으로 떨어짐 | 수집 측 매핑 계층(원시 속성 → 내부 이름)이 흡수. 대시보드는 내부 이름만 본다 | 새 속성명이 매핑 표에 없음 |
| 평가 파이프라인 자체 장애 (judge API 다운, 골든셋 저장소 접근 불가) | 없음. 단 CI가 멈춰 **배포가 막힌다** | 평가 작업 실패율·대기 시간 | **폴백 게이트**: 규칙 체크 + 참조 평가(judge 없이)만으로 통과 여부를 정하되 "축소 게이트 통과"를 기록하고 judge 평가는 배포 후 비동기로 보완. 등급 1~2 변경에만 허용 | 폴백 게이트가 일정 시간 이상 지속(예시: 4시간) 또는 등급 3 이상 변경이 대기 중 |

이 체계의 장애는 대부분 **사용자에게 보이지 않아** 늦게 발견된다. "품질이 좋아 보이는데 측정이 깨진" 상태가 가장 위험하므로, 환류 건은 검수 대기 → 승인 후 편입으로 골든셋 오염을 막고, judge 파싱 실패는 분모에 유지한다(설계 체크리스트). SLI 후보(이 체계 자체의): 트레이스 수집률, 평가 파이프라인 완료 시간, judge-사람 일치율, 골든셋 환류 리드타임. SLO 초안(예시): 수집률 ≥ 99%, 배포 전 전체 회귀 ≤ 30분, judge 일치율은 보정 시점 대비 -5%p 이내. 쓰기 행동: 평가 레코드·감사 레코드는 추가 전용(append-only), 평가 작업은 (변경 ID, 골든셋 버전, judge 버전) 키로 멱등.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| 골든셋 (건·라벨·카테고리) | 모든 점수의 비교 가능성. 셋이 바뀌면 전후 점수를 직접 비교할 수 없다 | 구·신 셋을 같은 시스템 버전으로 채점해 베이스라인 재설정 | 베이스라인 점수 기록 |
| judge 프롬프트·루브릭·모델 버전 | 3층 지표 전부 | 사람 라벨 셋과의 일치율(보정) | 보정 오프셋, 알림 임계값 |
| 트레이스 스키마 (내부 속성명·스팬 구조) · 매핑 계층 (OTel·벤더 SDK 속성 → 내부) | 대시보드, 알림, 감사 레코드 추출 | 스키마 호환 테스트(추가 자유, 삭제·의미 변경은 버전 상승), 샘플 스팬 재생 → 내부 스키마 검증 | 매핑 계층 ↔ 계측 SDK 버전, 대시보드 정의 |

롤백 단위: (골든셋 버전, judge 버전, 규칙 체크 세트 버전)을 **평가 베이스라인** 한 묶음으로 태그한다. 어느 하나만 바꿔도 점수 비교가 깨지므로 "베이스라인 v12로 측정한 시스템 v3.4 점수"처럼 항상 쌍으로 기록한다. 샘플링률·알림 임계값·보존 기간은 설정만 바꾸되 과거 데이터로 알림을 시뮬레이션한 뒤 적용한다.

기술 부채로 기록할 것: Development 상태인 OTel 속성에 직접 의존하는 쿼리, 보정 안 된 judge를 운영 지표로 쓰는 곳, 홀드아웃 없이 개발셋만 있는 카테고리, 본문을 스팬에 직접 넣고 있는 경로.

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

평가 체계는 다른 모든 레이어가 변화를 흡수할 때의 **안전망**이다. [07](07-operations-vocabulary.md)의 "변화 유형별 흡수 지점" 표가 "어디서 흡수하나"를 말한다면, 아래 표는 "흡수했다고 믿어도 되는지 무엇으로 확인하나"를 말한다. 이 **변경 유형 → 트리거되는 평가 집합** 표(배포 게이트 기본값, 수치는 예시) 자체가 코드 밖 설정이며, CI는 변경된 파일·설정의 유형을 읽어 해당 행의 평가 집합을 큐에 넣는다.

| 변경 유형 (레이어) | 반드시 돌릴 것 | 샘플링으로 돌릴 것 | 추가로 볼 것 |
|---|---|---|---|
| 모델 버전·벤더 교체 (Reasoning) | 전체 골든셋 규칙+참조, 스키마 테스트, 보정 곡선 | judge 전 카테고리 층화 | 지연·비용 베이스라인 비교, 섀도 1~2주 |
| 프롬프트 (해당 과업) | 과업 골든셋 전수 | 인접 과업 judge | 과업 밖 카테고리에 회귀 없음 확인 |
| 임베딩 모델·인덱스 재구축 (Knowledge) | 검색 recall@k·MRR 전체 | 생성 faithfulness 샘플 | 근거 ID 변경에 따른 골든셋 기대 근거 재매핑 |
| 지식 증분 (문서 추가·삭제·만료) | 삭제 전파 확인(삭제된 문서가 근거로 안 나오는지) | 영향 카테고리 recall | 자동 실행. 배포 게이트 아님 |
| 규칙·가드레일·승인 정책 | 규칙 테스트 스위트, 게이트 검출률·오탐률 | 차단된 정당 요청 샘플 리뷰 | 규칙 버전이 감사 레코드에 찍히는지 |
| 온톨로지·추출 스키마 / 컴포넌트 카탈로그·UI 스키마 | 추출 검증 통과율·매핑 테이블 테스트 / 스키마 호환·선택 정확도 | 필터 어휘 영향 카테고리 / 렌더 스냅샷 | 결정 enum·UI 매핑 재검증 |
| 프로토콜·SDK 어댑터 | 어댑터 계약 테스트, 이벤트 재생 | E2E 과업 완료율 샘플 | 에이전트 루프 변경 없음 확인 |

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| 지식·사용자 환경 (운영 분포 이동) | 골든셋이 현실을 대표하지 못하게 됨 | 골든셋 레코드 스키마(입력·기대·근거 ID·카테고리·버전) | 골든셋 내용 | **환류 주기**(예시: 2주마다 운영 실패·불만·사람 개입 건을 검수 후 편입, 분기마다 카테고리 분포 재점검) + 베이스라인 재설정 | 베이스라인 점수 |
| 모델 (judge 모델) | 채점 분포 | judge 포트 `judge(sample, rubric) → score` | judge 모델·프롬프트 | 구·신 병렬 채점 → 보정 오프셋 → 전환 | 3층 지표 전부 |
| 프로토콜·SDK (OTel 컨벤션, 벤더 관측 SDK) · 규칙(감사 요건 변경) | 속성명·스팬 구조, 감사 레코드 필드 | 내부 트레이스 스키마, 감사 레코드 스키마(추가 자유) | 매핑 계층, 필드 추출 로직 | 매핑 표 갱신. Development 상태인 `gen_ai.*`를 **매핑 계층 안에 격리**해 대시보드·감사 추출이 원시 속성을 직접 보지 않게 | 매핑 계층만 |

- **가장 자주 바뀌는 것**: 골든셋 내용(운영 환류)과 변경 유형 → 평가 집합 표의 행. 그다음 judge 프롬프트, 가장 드문 것이 트레이스 스키마
- **코드 밖 설정으로 둘 것**: 골든셋, judge 프롬프트·루브릭, 규칙 체크 정의, 변경 유형 → 평가 집합 표, 샘플링률, 알림 임계값, 매핑 표, 보존 기간
- **포트·어댑터 뒤에 둘 외부 의존**: judge 모델, 트레이스 수집기·백엔드(벤더 SDK ↔ OTel 전환 가능), 골든셋 저장소
- **시점 재현성**: 모든 평가 결과 레코드에 (시스템 구성 버전 — 모델·프롬프트·인덱스·규칙, 골든셋 버전, judge 버전)을 남긴다. 없으면 "지난달 점수가 더 좋았다"를 검증할 수 없다

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 | 평가·관측 자체는 사용자 대상 행동이 아니라 등급 없음. 단 **감사 추적 저장소**는 법적·규제 영향(조직 외부)이 있으므로 그 변경·삭제는 등급 4~5로 다룬다 — 에이전트·자동화는 삭제 불가, 사람만 |
| 가드레일 위치 | 이 단계는 가드레일을 두는 곳이 아니라 **가드레일이 작동했는지 측정하는 곳**(검출률·오탐률). 예외: 트레이스 본문 기록 전 PII 마스킹은 출력 가드레일 |
| 배포 게이트 절차 | 변경 유형 → 평가 집합 표에 따라 자동 실행 → 규칙 체크 실패 = 자동 차단 → 골든셋 회귀 하락(예시: 베이스라인 대비 -2%p 초과) = 차단, 승인으로 예외 가능 → judge 지표 하락 = 경고 + 리뷰 필수. **승인자**: 등급 1~2 변경은 AI 엔지니어 리드, 등급 3 이상 또는 폴백 게이트 사용 시 제품 책임자 + 보안. 승인 기록은 감사 레코드에 |
| 감사 추적 vs 관측 로그 분리 | 같은 트레이스에서 분기하되 **저장소·보존·접근권한을 분리**. 관측 로그: 샘플링 가능, 단기(예시: 7~90일), 엔지니어 접근. 감사 레코드: 전수, 장기(규제 요건에 따라 수년), 추가 전용·변조 방지, 감사자·법무 접근. 필드는 설계 시 확정([07](07-operations-vocabulary.md)의 감사 추적 표) |
| 소유자 (A) | 골든셋: 제품 책임자(R: 도메인 전문가가 라벨, AI 엔지니어가 환류). judge 보정: AI 엔지니어 리드. 트레이스 스키마·매핑: 플랫폼 아키텍트. 감사 저장소·보존 정책: 운영 책임자(C: 법무). PII 처리 정책: 보안 책임자 |
| PII 처리 | 프롬프트·출력 본문은 **기본 미기록**, 기록 시 마스킹 후 별도 저장소. 골든셋에 실 로그를 쓰면 익명화 후 편입하고 원본 참조를 끊는다. judge에 보내는 샘플도 같은 규칙. 삭제 요청 시 트레이스·골든셋·judge 캐시까지 전파 삭제 |
| 감사 추적에 남길 필드 | 요청 ID·테넌트·요청자, 시스템 구성 버전(모델·프롬프트·인덱스·규칙), 판정과 확신도, 근거 ID, 게이트 판정·적용 규칙 버전, 승인자, 배포 게이트 결과(평가 베이스라인 버전·통과/폴백 여부·승인자) |

### 운영 준비도 체크
- [ ] judge는 샘플링, 규칙·참조 평가는 전수라는 층 구분이 설정에 있고, 트레이스 본문은 별도 저장소에 참조만 남으며, 트레이스 유실이 요청 처리를 막지 않되 감사 레코드만은 동기 기록되는가
- [ ] judge 모델 버전이 고정되어 있고, 변경 시 구·신 병렬 채점 절차가 있는가
- [ ] 평가 파이프라인 장애 시 폴백 게이트(규칙+참조만)의 허용 범위와 승인자가 정해져 있는가
- [ ] 변경 유형 → 평가 집합 표가 설정으로 존재하고 CI가 그것을 읽는가
- [ ] OTel·벤더 SDK 속성이 매핑 계층 뒤에 있어 대시보드·감사 추출이 원시 속성명을 직접 참조하지 않는가
- [ ] 평가 결과·감사 레코드에 (시스템 구성 버전, 골든셋 버전, judge 버전)이 남아 과거 점수를 재현할 수 있고, 감사 저장소는 관측 저장소와 보존·접근권한이 분리되어 삭제 권한이 사람에게만 있는가
