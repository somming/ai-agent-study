# 운영 용어와 판단 기준: 거버넌스 · 가드레일 · 안정성 · 확장성 · 유지보수

> **범위**: AI Agent 시스템을 **운영 가능한 상태로 설계**하기 위해 모든 단계 페이지가 공유하는 용어의 정의, 용어 사이의 관계, 그리고 "이 단계에는 어떤 통제가 필요한가"를 판단하는 기준. 각 단계의 구체적 운영 설계는 그 단계 페이지의 "운영 설계" 섹션에, 레이어를 가로지르는 정책은 [Part 5](../05-cross-cutting/00-overview.md)에 있다.

## 요약 (3줄)

1. **거버넌스는 "누가 결정하고 책임지는가"의 체계**이고, **가드레일은 그 결정을 런타임에 강제하는 기술적 통제**다. 가드레일 없는 거버넌스는 문서일 뿐이고, 거버넌스 없는 가드레일은 누가 왜 그 규칙을 정했는지 아무도 모르는 코드다.
2. 통제는 **예방(가드레일·게이트) → 탐지(관측·감사) → 교정(폴백·롤백·킬 스위치)** 세 층으로 쌓는다. 어느 층을 얼마나 두꺼이 할지는 그 단계 행동의 **가역성과 영향 범위**가 정한다.
3. AI 시스템은 지식·모델·규칙·사용자 환경·프로토콜이 **계속 바뀐다**. 각 레이어는 안정적인 계약 뒤에 가변 구현을 두는 **추상화 경계**로 설계해, 변화를 재배포 없이 또는 국소적으로 흡수해야 한다. 모든 단계 페이지는 "10배가 되면 무엇이 깨지는가", "죽으면 어떻게 보이는가", "무엇이 바뀌면 어디까지 번지는가"에 답해야 한다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** | 운영 용어의 공통 정의, 통제 수단 선택 기준(위험 등급표), 각 단계 페이지의 "운영 설계" 섹션이 답해야 하는 질문 4개 |
| **언제** | 설계 리뷰 전. 팀이 "가드레일"을 입력 필터로만, "거버넌스"를 규제 대응으로만 이해하고 있다면 이 페이지부터 |
| **어떻게** | ① 용어를 맞춘다 → ② 시스템의 모든 **행동**(툴 실행, 데이터 변경, 외부 전송, 사용자에게 보여주기)을 위험 등급표에 놓는다 → ③ 등급별로 필요한 통제 층을 정한다 → ④ 각 단계 페이지의 "운영 설계" 섹션을 채운다 → ⑤ [Part 5/06 종합 매트릭스](../05-cross-cutting/06-operational-design-matrix.md)에서 레이어 간 불균형을 본다 |
| **왜** | PoC는 "되는가"를 묻지만 운영은 "안 될 때 어떻게 되는가", "열 배가 되면 어떻게 되는가", "바꾸면 무엇이 깨지는가"를 묻는다. 이 질문을 설계 단계에서 하지 않으면 운영 단계에서 비용이 열 배로 든다 |

## 문제와 맥락

에이전트 프로젝트의 운영 실패는 기술 실패보다 **책임과 통제의 공백**에서 온다. 전형적 장면:

- 프롬프트를 누가 바꿨는지 모른다. 바꾼 뒤 품질이 떨어졌는데 되돌릴 버전이 없다
- 에이전트가 툴로 데이터를 지웠다. "가드레일이 있었다"는데 입력 필터였고, 행동 직전 검사는 없었다
- 모델 API가 10분 장애를 겪었다. 에이전트는 빈 응답을 사용자에게 그대로 보여줬다
- 문서가 10배로 늘자 인덱싱이 하루 넘게 걸리고 검색 지연이 3배가 됐다. 어느 단계가 병목인지 아무도 모른다
- 감사에서 "이 답변의 근거가 무엇이었나"를 물었는데, 트레이스에 근거 ID가 없다

각각 거버넌스(소유·변경 관리), 가드레일(행동 게이트), 안정성(폴백), 확장성(병목 예측), 감사 추적(기록 설계)의 공백이다.

## 핵심 개념

### 거버넌스 (governance)

**정의**: 시스템에 대해 **누가 무엇을 결정·승인·책임지는가**를 정한 체계. 구성 요소는 ① 정책(policy) ② 역할과 책임(RACI) ③ 변경 관리(change management) ④ 감사(audit) ⑤ 예외 처리 절차.

| 구성 요소 | 답하는 질문 | AI Agent 시스템에서의 대상 |
|---|---|---|
| 정책 | 해도 되는 것과 안 되는 것은? | 에이전트가 할 수 있는 행동 범위, 접근 가능한 데이터, 응답해도 되는 주제, 모델·데이터 사용 조건 |
| RACI | 누가 실행(R)·책임(A)·자문(C)·통보(I)인가? | 프롬프트, 모델 선택, 인덱스, 툴 권한, 컴포넌트 카탈로그, 온톨로지, 가드레일 규칙 각각의 소유자 |
| 변경 관리 | 바꾸려면 누가 승인하고 무엇을 검증하나? | 모델 버전 교체, 프롬프트 수정, 규칙 추가, 툴 권한 확대 |
| 감사 | 사후에 "왜 그렇게 됐나"를 재구성할 수 있나? | 요청 → 판정 → 근거 → 생성 → 행동 → 승인의 트레이스 |
| 예외 처리 | 정책 밖 상황은 누가 결정하나? | 가드레일이 막은 정당한 요청, 승인 지연, 긴급 변경 |

거버넌스는 **규제 대응이 아니다**. 규제(EU AI Act 등)는 거버넌스가 충족해야 할 외부 요구 중 하나일 뿐이다. 규제가 없어도 "프롬프트를 누가 바꿀 수 있는가"는 정해져야 한다. 규제 맥락은 [Part 5/04](../05-cross-cutting/04-governance-explainability.md).

### 정책 → 규칙 → 가드레일 → 게이트

네 용어는 같은 것의 다른 층위다.

```
정책 (policy)        사람이 읽는 선언. "고객 데이터는 고객 본인과 담당자만 조회할 수 있다"
   ↓ 번역
규칙 (rule)          기계가 평가할 수 있는 조건. "requester.role ∈ {owner, assigned_agent} AND tenant 일치"
   ↓ 배치
가드레일 (guardrail)  규칙을 런타임 경로에 심은 기술적 통제. 입력·출력·행동 세 지점
   ↓ 실행 형태
게이트 (gate)        흐름을 통과 / 차단 / 승인 요청 / 저하로 분기하는 판정 지점
```

- **가드레일 (guardrail)**: 정책을 런타임에 **예방적으로** 강제하는 통제. 세 지점에 둔다. **입력** 가드레일(인젝션·유해·범위 밖 요청), **출력** 가드레일(PII·근거 없음·정책 위반 응답), **행동** 가드레일(툴 실행·데이터 변경·외부 전송 직전). 입력 필터만 있는 시스템은 가드레일이 "있다"고 말할 수 없다. 상세: [Part 3/12](../03-agent-workflow-rag/12-guardrails-hitl.md)
- **게이트 (gate)**: 가드레일이 흐름에 개입하는 **형태**. 출력은 통과 / 차단 / 승인 요청 / 저하(degrade, 예: 읽기 전용으로 축소) 네 가지 중 하나다. 게이트의 판정 수단은 규칙 → 결정 모델 → LLM 순으로 쓴다([1/02](02-system1-vs-system2.md)). 보안·권한·한도 게이트는 규칙만 쓴다
- **정책 엔진 (policy engine)**: 규칙을 코드와 분리해 중앙에서 평가하는 컴포넌트. 규칙이 수십 개를 넘거나 여러 서비스가 같은 규칙을 써야 할 때 도입. 그 전에는 코드 안의 함수로 충분하다

### 승인 (approval)과 HITL

**정의**: 게이트의 네 출력 중 "승인 요청"이 사람에게 가는 것. 승인은 가드레일의 **대체가 아니라 보완**이다. 사람이 승인해도 규칙(한도·권한)은 다시 검사한다(Rule ∧ Human).

| 승인 설계 요소 | 결정할 것 |
|---|---|
| 승인 매트릭스 | 행동 유형 × 영향 범위 × 요청자 역할 → 승인자·승인 수(1인/2인) |
| 동기 vs 비동기 | 사용자가 기다리는가(대화 중 승인 카드) / 큐에 쌓이는가(운영자 승인함) |
| 타임아웃 | 시한 내 미승인 시 기본 결정. **기본은 거부**(만료 = 거부) |
| 에스컬레이션 | 승인자 부재 시 다음 승인자, 긴급 경로 |
| 승인 피로 | 승인 요청이 너무 많으면 사람이 전부 승인한다. 확신도 임계값·배치 승인·규칙 승격으로 양을 줄인다 |
| 기록 | 누가 무엇을 어떤 정보를 보고 승인했는가. 승인 카드에 보여준 내용도 기록 |

### 감사 추적 (audit trail)과 관측성 (observability)

둘 다 "기록"이지만 목적이 다르다.

| | 관측성 | 감사 추적 |
|---|---|---|
| 목적 | 시스템이 **지금** 어떻게 동작하는지 이해 (디버깅·성능·품질) | 사후에 **왜 그 결정이 났는지** 재구성 (책임·규제·분쟁) |
| 소비자 | 엔지니어 | 감사자·법무·고객 |
| 보존 | 짧음(일~주), 샘플링 가능 | 김(년), **샘플링 불가**, 변조 방지 |
| 내용 | 지연·토큰·오류·트레이스 | 요청자, 시각, 판정과 확신도, 근거 ID, 생성 결과, 행동, 승인자, 적용된 규칙 버전 |

같은 트레이스에서 나오되 **저장소와 보존 정책을 분리**한다. 감사 추적에 필요한 필드는 설계 시 정한다. 나중에 "그때 어떤 프롬프트 버전이었나"를 복원할 수 없으면 감사 추적이 아니다. 상세: [1/06](06-evaluation-observability.md), [Part 5/03](../05-cross-cutting/03-observability-tracing.md)

### 통제의 세 층: 예방 · 탐지 · 교정

| 층 | 수단 | 질문 |
|---|---|---|
| **예방** (preventive) | 가드레일, 게이트, 권한 최소화, 스키마 검증, 승인 | 나쁜 일이 일어나기 전에 막는가 |
| **탐지** (detective) | 관측 지표, 알림, 감사 로그, 샘플링 리뷰, 드리프트 모니터 | 나쁜 일이 일어났을 때 아는가, 얼마나 빨리 |
| **교정** (corrective) | 폴백, 롤백, 킬 스위치, 재처리, 보상 트랜잭션 | 알았을 때 되돌리거나 멈출 수 있는가 |

세 층이 모두 있어야 한다. 예방만 있으면 예방이 뚫렸을 때 모르고, 탐지만 있으면 알아도 못 멈춘다.

### 위험 등급과 통제 수준 — 판단 기준

이 단계의 행동이 어떤 통제를 필요로 하는지는 **가역성**과 **영향 범위** 두 축으로 판단한다.

| | 영향: 요청자 본인 | 영향: 여러 사용자·고객 | 영향: 조직 외부·금전·법적 |
|---|---|---|---|
| **가역** (되돌릴 수 있음) | 등급 1: 출력 가드레일 + 로그 | 등급 2: + 행동 게이트(규칙) + 감사 | 등급 3: + 승인(1인) + 폴백 |
| **부분 가역** (비용 들여 되돌림) | 등급 2 | 등급 3 | 등급 4: + 승인(2인) + 섀도 기간 |
| **비가역** (되돌릴 수 없음) | 등급 3 | 등급 4 | 등급 5: 에이전트 자동 실행 금지. 제안만, 실행은 사람 |

예: 문서 QA의 답변 표시는 등급 1. 장바구니 담기는 등급 1~2. 환불 접수는 등급 3. 운영 서버 설정 변경은 등급 4. 결제·송금·데이터 영구 삭제는 등급 5.

### 운영 안정성 (operational stability)

**정의**: 구성 요소가 실패해도 시스템이 **정의된 방식으로** 동작하는 성질. 핵심은 실패를 없애는 것이 아니라 **실패 모드를 설계**하는 것.

| 용어 | 정의 | 설계 질문 |
|---|---|---|
| **장애 모드** (failure mode) | 구성 요소가 실패하는 방식의 목록. 모델 API 다운, 지연 급증, 인덱스 불일치, 툴 타임아웃, 결정 모델 오판, 스키마 검증 실패 폭증 | 이 단계가 실패하는 방식을 다 적었나 |
| **폴백** (fallback) | 1차 수단 실패 시 대체 수단. 다른 모델, 캐시된 응답, 규칙 기반 경로, 키워드 검색 | 각 장애 모드에 폴백이 있나, 폴백도 실패하면 |
| **우아한 저하** (graceful degradation) | 전체 중단 대신 기능을 줄여 계속 동작. "답변은 하되 citation 없음을 표시", "읽기 전용 모드" | 사용자에게 저하 상태가 보이나 |
| **서킷 브레이커** (circuit breaker) | 실패율이 임계값을 넘으면 호출을 일시 차단해 연쇄 장애 방지 | 외부 의존(모델·툴·DB)마다 있나 |
| **타임아웃·재시도·멱등성** | 응답 상한, 재시도 횟수·간격, 재시도해도 부작용이 중복되지 않음 | 쓰기 툴이 멱등한가, 재시도 상한이 있나 |
| **백프레셔** (backpressure) | 처리 능력 초과 시 입력을 늦추거나 거부 | 큐 길이 상한, 거부 응답이 있나 |
| **킬 스위치** (kill switch) | 특정 기능·툴·모델을 즉시 끄는 스위치 | 배포 없이 끌 수 있나, 누가 누르나 |
| **SLI / SLO** | 측정 지표(가용성, p95 지연, 근거 부합률, 승인 응답 시간) / 그 목표치 | 단계별 SLI가 있나, SLO 위반 시 누가 뭘 하나 |
| **오류 예산** (error budget) | SLO가 허용하는 실패량. 소진되면 신규 변경 동결 | 변경 속도와 안정성의 균형 장치 |
| **런북** (runbook) | 알림별 대응 절차 | 알림마다 런북이 있나 |

### 확장성 (scalability)

**정의**: 부하(데이터·사용자·툴·팀)가 커져도 비용과 지연이 **예측 가능하게** 증가하는 성질. 설계 시 질문은 하나다. **"10배가 되면 무엇이 먼저 깨지는가."**

| 확장 축 | 10배가 되면 흔히 깨지는 것 | 설계 수단 |
|---|---|---|
| 데이터 (문서·레코드) | 전체 재색인 시간, 벡터 인덱스 메모리, 그래프 구축 LLM 비용 | 증분 처리, 파티셔닝, 배치 창, 양자화, 추출 모델 티어 하향 |
| 사용자·요청 | 모델 API 레이트 리밋, 동시 승인 큐, 세션 상태 저장소 | 무상태 설계, 큐, 캐시(프롬프트·시맨틱·결과), 모델 라우팅, 레이트 리밋 |
| 툴·소스 | 툴 정의 컨텍스트 비용, 툴 선택 정확도, 커넥터 운영 | 툴 라우팅·그룹화, MCP로 표준화, 커넥터 소유자 지정 |
| 테넌트·조직 | ACL 복잡도, 인덱스 분리 비용, 정책 분기 | 테넌트 키를 처음부터 모든 레코드·트레이스에 |
| 팀·기여자 | 프롬프트·규칙·컴포넌트의 충돌, 누가 뭘 바꿨는지 | 버전 관리 대상 명시, 소유자, 변경 절차, CI 게이트 |

**상태 분리**가 확장성의 전제다. 요청 처리 경로는 무상태로 두고, 상태(세션·체크포인트·승인 큐)는 외부 저장소에. MCP 2026-07-28 개정이 무상태 코어로 간 것도 같은 이유다([1/05](05-agentic-protocols.md)).

### 유지보수성 (maintainability)

**정의**: 시스템을 **안전하게 바꿀 수 있는** 성질. AI 시스템은 바뀌는 것이 많다. 다섯 가지를 버전 관리 대상으로 명시한다.

| 버전 관리 대상 | 바뀌면 무엇이 영향받나 | 회귀 테스트 |
|---|---|---|
| 모델 (버전·파라미터) | 모든 출력 분포, 구조화 출력 동작, 판정 보정 | 전체 골든셋, 보정 곡선 |
| 프롬프트·질문 정의 | 해당 단계 출력 | 단계 골든셋 |
| 인덱스·임베딩 모델·온톨로지 | 검색 결과, 근거 단위, 추출 스키마 | 검색 recall, 추출 검증 통과율 |
| 툴·MCP 서버·규칙 세트 | 행동, 게이트 판정 | 툴 계약 테스트, 규칙 테스트 스위트 |
| 컴포넌트 카탈로그·UI 스키마 | 렌더, 의도→UI 매핑 | 스키마 호환, 선택 정확도 |

이 다섯은 **함께 배포되어야 하는 조합**이 있다(프롬프트가 특정 모델 버전을 전제, UI 스키마가 특정 응답 스키마를 전제). 호환 매트릭스를 두고 롤백 단위를 정한다. 상세: [Part 5/05](../05-cross-cutting/05-llmops-agentops.md)

| 용어 | 정의 |
|---|---|
| **카나리** (canary) | 일부 트래픽에만 새 버전. 지표 비교 후 확대 |
| **섀도** (shadow) | 새 버전을 실제 트래픽으로 실행하되 결과는 사용자에게 안 보냄. 결정 모델 도입의 표준 절차 |
| **피처 플래그** (feature flag) | 배포 없이 기능 켜고 끄기. 킬 스위치의 구현 수단 |
| **롤백 단위** | 함께 되돌려야 하는 구성 요소의 묶음 |
| **운영 준비도 리뷰** (operational readiness review, ORR) | 배포 전 "장애 모드·폴백·알림·런북·롤백·소유자"가 있는지 확인하는 점검 |
| **기술 부채 기록** | 알면서 미룬 것(예: "ACL은 메타데이터 필터로만, 쿼리 조인은 2차")의 목록과 재검토 시점 |

### 변화 대응 설계 (design for change) — 추상화 경계와 교체 가능성

**정의**: 바뀌는 것과 바뀌지 않는 것을 분리해, 변화를 **코드 재배포 없이 또는 국소적 재배포로** 흡수하는 설계. AI Agent 시스템은 전통 소프트웨어보다 변화 축이 많다. 지식(문서·데이터)이 바뀌고, 모델이 바뀌고, 규칙·정책이 바뀌고, 사용자 환경(디바이스·언어·권한·조직)이 바뀌고, 프로토콜·SDK가 바뀐다. 각 변화를 **어느 경계에서 흡수할지**를 단계마다 정해야 확장성과 안정성이 유지된다.

**원칙**

1. **안정 계약 vs 가변 구현**: 레이어 사이의 계약(근거 단위·응답 스키마·이벤트 스키마, [Part 0/01](../00-overview/01-reference-architecture.md))은 느리게 바꾸고 버전을 붙인다. 계약 뒤의 구현(어떤 모델, 어떤 벡터DB, 어떤 청킹, 어떤 렌더러)은 계약을 지키는 한 자유롭게 바꾼다
2. **코드가 아닌 데이터로**: 프롬프트, 결정 질문 정의, 규칙, 컴포넌트 카탈로그, 온톨로지, 라우팅 표, 임계값은 **코드 밖의 버전 관리되는 설정**으로 둔다. 바꿀 때 배포가 아니라 설정 교체 + 회귀 평가가 된다
3. **포트와 어댑터**: 외부 의존(모델 API, 벡터DB, MCP 서버, UI 프로토콜, 결정 모델)은 내부 인터페이스(포트) 뒤에 어댑터로 둔다. 벤더·버전 교체가 어댑터 교체로 끝나야 한다. `decide()`, `retrieve()`, `render()` 같은 추상화가 그 자리
4. **스키마 진화**: 계약 스키마는 **추가는 자유, 삭제·의미 변경은 버전 상승**. 소비자가 모르는 필드를 무시하도록 설계(tolerant reader)
5. **시점 재현성**: "그때 어떤 지식·모델·규칙 버전으로 그 답이 나왔나"를 재현할 수 있어야 한다. 모든 레코드와 트레이스에 버전 키
6. **변화 전파 범위 명시**: 한 곳의 변화가 어디까지 번지는지(온톨로지 변경 → 추출 스키마·검증 규칙·UI 매핑·결정 enum) 표로 두고, 전파가 넓은 것일수록 변경 절차를 무겁게

**변화 유형별 흡수 지점**

| 변화 유형 | 무엇이 바뀌나 | 안정적으로 유지할 것 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|
| **지식** (문서·레코드·그래프) | 내용 추가·수정·삭제·만료, 소스 추가 | 근거 단위 스키마(계약 ①), 메타데이터 어휘 | 증분 인덱싱, 만료·삭제 전파, 버전·시점 메타데이터, 시점 질의 | Knowledge → 캐시·메모리·트레이스까지 삭제 전파 |
| **도메인 모델** (온톨로지·택소노미) | 클래스·관계 추가, 개명, 병합 | 상위 개념, 매핑 테이블 | 온톨로지 버전 + 구→신 매핑, 라벨 재부여(재추출 없이 가능한 범위), 미분류 버킷 | 추출 스키마, SHACL, 필터 어휘, 결정 enum, UI 매핑 |
| **모델** (LLM·임베딩·결정 모델) | 버전 교체, 벤더 교체, 가격·한도 변경 | 포트 인터페이스, 프롬프트-모델 호환 매트릭스 | 어댑터 교체, 섀도·카나리, 골든셋 회귀, 임베딩 교체 시 전체 재임베딩 창 | 임베딩 교체는 Knowledge 전체, LLM 교체는 Reasoning 전체 |
| **규칙·정책** (가드레일·승인·권한) | 한도·역할·금칙·승인자 변경, 규제 신설 | 규칙 평가 인터페이스, 게이트 위치 | 정책 엔진의 규칙 버전 + 시행일, 규칙 테스트 스위트, 감사 레코드에 규칙 버전 | 해당 게이트만. 단 권한 모델 변경은 ACL 필터·UI 재검증까지 |
| **사용자 환경** (디바이스·언어·권한·조직) | 모바일 추가, 다국어, 조직 개편, 역할 변경 | 렌더 가능한 응답 스키마(계약 ②), 이벤트 스키마(계약 ③) | 렌더러 추가(선언적 UI), 언어별 평가셋·프롬프트 변형, ACL·온톨로지 외부화로 조직 개편을 데이터 변경으로 | Interaction 렌더러, ACL 필터, 골든셋 |
| **프로토콜·SDK** (MCP·A2A·AG-UI·A2UI, 프레임워크) | 스펙 개정, SDK 메이저 업 | 내부 포트 | 어댑터 계층, 버전 고정 + 계획된 업그레이드 창 | 해당 경계의 어댑터만 |
| **부하·규모** | 10배 | 무상태 경로, 계약 | 파티셔닝·큐·캐시·모델 티어 조정 | 병목 단계 |

**판단 기준**: 어떤 변화가 **가장 자주** 일어나는지 먼저 측정한다. 대개 지식 > 규칙 > 프롬프트 > 모델 > 프로토콜 순이다. 자주 바뀌는 것일수록 설정화·자동화 우선, 드물게 바뀌는 것은 어댑터로 격리하고 수동 절차를 둔다.

### 데이터 거버넌스와 모델 리스크 관리

- **데이터 거버넌스**: 데이터의 분류 등급(공개/내부/기밀/개인정보), 소유자(data owner)와 관리자(steward), 보존·삭제 정책, 출처 추적(lineage), 품질 기준. 에이전트 시스템에서는 **인덱스와 메모리도 데이터**다. 원본이 삭제되면 인덱스·캐시·메모리·트레이스에서도 전파 삭제되어야 한다([Part 2/07](../02-data-pipeline/07-freshness-and-sync.md), [2/10](../02-data-pipeline/10-access-control-governance.md))
- **모델 리스크 관리 (model risk management)**: 금융권에서 온 개념. 모델마다 ① 용도와 한계 문서(모델 카드) ② 검증 기록(골든셋 결과, 보정) ③ 변경 승인 ④ 재검증 주기 ⑤ 사용 중단 기준을 둔다. 외부 API 모델도 "우리가 쓰는 버전"에 대해 같은 기록을 둔다

### 역할과 책임 (RACI) 예시

| 대상 | R (실행) | A (책임) | C (자문) | I (통보) |
|---|---|---|---|---|
| 프롬프트·질문 정의 | AI 엔지니어 | 제품 책임자 | 도메인 전문가 | 운영 |
| 모델 버전 교체 | AI 엔지니어 | 아키텍트 | 보안·법무 | 전체 |
| 가드레일 규칙 | 보안 엔지니어 | 보안 책임자 | 제품·법무 | AI 엔지니어 |
| 인덱스·데이터 소스 | 데이터 엔지니어 | 데이터 소유자 | 보안 | AI 엔지니어 |
| 툴 권한 | 플랫폼 엔지니어 | 서비스 소유자 | 보안 | 운영 |
| 컴포넌트 카탈로그 | 프론트엔드 | 디자인 책임자 | 접근성 | AI 엔지니어 |
| 온톨로지 | 데이터 모델러 | 도메인 소유자 | AI·데이터 엔지니어 | 전체 |
| 승인 정책 | 운영 책임자 | 사업 책임자 | 법무 | 전체 |

이 표는 예시다. 프로젝트마다 채우되, **A가 비어 있는 행이 없어야** 한다.

## 아키텍처 / 파이프라인

통제 세 층이 요청 경로에 놓이는 자리:

```
요청 ─▶ [입력 가드레일] ─▶ 판정·검색·생성 ─▶ [출력 가드레일] ─▶ [행동 게이트: 규칙 ∧ 모델 → 통과/차단/승인/저하] ─▶ 실행 ─▶ 응답
          │                     │                    │                    │                        │
          └──── 트레이스(관측) + 감사 레코드(판정·근거·규칙 버전·승인자) ──────────────────────────────┘
                                │
                     [탐지] 지표·알림·드리프트 ─▶ [교정] 폴백 · 킬 스위치 · 롤백 · 재처리
```

## 기술 비교표 — 통제 수단

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 코드 내 규칙 함수 | 규칙 수십 개 이하, 단일 서비스 | 여러 서비스가 같은 규칙 공유, 비개발자가 규칙 변경 | 하 | 표준 | — |
| 정책 엔진 (OPA/Rego 류, 규칙 엔진) | 규칙 다수, 중앙 평가, 감사 가능한 규칙 버전 | 소규모 단일 서비스 | 중 | 표준 | `[검증]` |
| 가드레일 라이브러리 (입출력 필터) | 입력·출력 검사의 빠른 도입 | 행동 게이트(라이브러리가 대개 다루지 않음) | 하~중 | 안정 | `[2차]` |
| 결정 모델 기반 게이트 | 닫힌 판정 + 보정 확률로 승인 분기 | 보안·권한·한도(규칙만), 한국어 미검증 | 하~중 | 신생 | `[벤더]` |
| 승인 워크플로우 (동기 카드 / 비동기 큐) | 등급 3 이상 행동 | 등급 1~2(승인 피로) | 중 | 표준 | — |
| 감사 로그 저장소 (불변·장기 보존) | 규제·분쟁 대응 필요 | 전부 관측 로그로 대체하려는 경우(보존·변조 요건 미충족) | 중 | 표준 | — |
| 서킷 브레이커·피처 플래그 플랫폼 | 외부 의존 다수, 즉시 차단 필요 | 의존이 하나뿐인 PoC | 하~중 | 표준 | — |

### 선택 가이드

- **행동이 등급 3 이상이라면** → 규칙 게이트 + 승인 + 감사 저장소 분리는 생략 불가. 이유: 사후 재구성과 사람 책임 지점이 필요
- **규칙이 서비스 여럿에 걸치거나 비개발자가 바꿔야 한다면** → 정책 엔진. 이유: 규칙 버전·테스트·감사가 중앙화
- **외부 의존(모델·툴)이 셋 이상이라면** → 서킷 브레이커 + 킬 스위치. 이유: 하나의 장애가 전체를 멈추지 않게
- **결정 모델을 게이트에 쓰려면** → 섀도 기간 + 규칙 최종 결정권 + 폴백 규칙. 이유: 보정이 검증되기 전까지는 보조
- **판단이 어려우면** → 코드 내 규칙 함수 + 행동 직전 게이트 + 감사 필드를 트레이스에 포함. 이유: 가장 싸고 나중에 정책 엔진으로 옮길 수 있다

## 설계 시 고려사항 (체크리스트)

각 단계 페이지의 "운영 설계" 섹션은 다음 네 질문에 답한다. 이 체크리스트가 그 섹션의 기준이다.

**확장성**
- [ ] 데이터·사용자·툴·테넌트가 10배가 되면 이 단계에서 무엇이 먼저 깨지는지 적었는가
- [ ] 요청 경로가 무상태인가, 상태는 외부 저장소에 있는가
- [ ] 비용이 어느 변수에 비례하는지(문서 수? 요청 수? 툴 수?) 적었는가

**운영 안정성**
- [ ] 이 단계의 장애 모드를 목록화했는가 (최소: 의존 서비스 다운, 지연 급증, 검증 실패 폭증, 데이터 불일치)
- [ ] 장애 모드마다 탐지 신호, 자동 대응(폴백·저하), 사람 개입 기준이 있는가
- [ ] 이 단계가 죽었을 때 사용자에게 어떻게 보이는지 정했는가
- [ ] SLI 후보와 SLO 초안이 있는가
- [ ] 쓰기 행동이 있다면 멱등성·타임아웃·재시도 상한이 있는가

**유지보수**
- [ ] 이 단계의 버전 관리 대상이 무엇인지, 바꾸면 무엇을 다시 테스트하는지 적었는가
- [ ] 함께 배포되어야 하는 조합(호환 매트릭스)과 롤백 단위를 정했는가
- [ ] 알면서 미룬 것(기술 부채)을 기록했는가

**변화 대응**
- [ ] 이 단계에서 가장 자주 바뀌는 것(지식·도메인 모델·모델·규칙·사용자 환경·프로토콜)이 무엇인지 적었는가
- [ ] 바뀌는 것과 안정적으로 유지할 계약을 분리했는가 (안정 계약 vs 가변 구현)
- [ ] 프롬프트·규칙·질문 정의·카탈로그·임계값이 코드 밖 설정으로 버전 관리되는가
- [ ] 외부 의존이 포트·어댑터 뒤에 있어 교체가 국소적인가
- [ ] 변화의 전파 범위(어디까지 다시 테스트·재처리해야 하나)가 표로 있는가
- [ ] 과거 시점의 지식·모델·규칙 버전으로 결과를 재현할 수 있는가

**거버넌스 접점**
- [ ] 이 단계의 행동을 위험 등급표에 놓았는가
- [ ] 정책 → 규칙 → 가드레일 → 게이트가 이어지는가 (입력·출력·행동 세 지점 중 어디에 있는가)
- [ ] 소유자(A)가 정해져 있는가
- [ ] 감사 추적에 남길 필드가 정해져 있는가 (판정·확신도·근거 ID·규칙 버전·승인자)

| SLO를 측정 없이 선언 | 숫자가 의미 없음 | 베이스라인 측정 후 SLO 설정, 분기별 재조정 |
| 결합 시스템 V&V 미성숙 | 신경·기호 구성 요소를 따로 검증해도 전체 보장은 부분적 | E2E 골든셋, 섀도, 단계적 확대([1/04](04-neuro-symbolic-ai.md)) |
