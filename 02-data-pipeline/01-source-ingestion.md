# 소스 수집과 문서 파싱

> **범위**: 커넥터, CDC, PDF/표/이미지 파싱, 멀티모달 추출 기술 비교
> **시각화**: [`assets/html/data-pipeline-architecture.html`](../assets/html/data-pipeline-architecture.html) — 파이프라인 첫 단계

## 요약 (3줄)

1. 이 단계의 산출물은 "파일 목록"이 아니라 **구조가 보존된 정규화 문서**(제목 계층, 표, 이미지 캡션, 페이지·좌표)다. 하류의 청킹·citation·근거 렌더는 전부 이 구조에 의존한다.
2. 수집(커넥터·CDC)과 파싱(문서 → 구조화 텍스트)은 분리해서 설계한다. 수집은 "무엇이 언제 바뀌었나"를, 파싱은 "그 안에 무엇이 있나"를 책임진다.
3. 파싱 품질은 RAG 품질의 상한을 정한다. 표가 깨지면 숫자 질문은 영원히 틀리고, 좌표가 없으면 UI에서 근거 하이라이트를 할 수 없다. 파서 선택은 샘플 문서로 `[실측]`해서 정한다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 소스별 수집 커넥터와 변경 감지 방식 ② 원본 → 정규화 문서 모델(블록 단위: 제목/문단/표/그림/캡션 + 페이지·좌표·순서) ③ 파싱 품질 리포트(실패율, 표 복원율, OCR 신뢰도) |
| **언제** (When) | 외부 지식을 쓰는 모든 에이전트. 생략 가능: 소스가 이미 구조화된 API·DB뿐이고 문서 파일이 없을 때(이 경우 "파싱"은 레코드 → 텍스트 직렬화로 축소). 미뤄도 되는 것: 스캔 이미지·멀티모달 추출(텍스트 PDF만으로 PoC 가능) |
| **어떻게** (How) | ① 소스 인벤토리(유형·규모·갱신 빈도·권한 모델) → ② 소스별 수집 방식 결정(풀/푸시/CDC) → ③ 대표 샘플 50~100건으로 파서 2~3종 비교 `[실측]` → ④ 정규화 문서 스키마 확정 → ⑤ 실패·저신뢰 문서의 격리 큐와 재처리 절차 → ⑥ 원본 해시·수집 시각·파서 버전을 메타데이터로 기록([03](03-metadata-provenance.md)) |
| **왜** (Why) | 파싱이 깨진 문서는 검색은 되지만 답은 틀린다. 표의 행·열이 섞이면 숫자 질문이 환각처럼 보이고, 머리글·바닥글이 본문에 섞이면 청크마다 노이즈가 반복된다. 좌표·페이지가 없으면 Part 4의 근거 하이라이트가 불가능하다 |

## 문제와 맥락

RAG 프로젝트의 초기 실패는 대부분 "모델이 멍청해서"가 아니라 **입력이 깨져서** 생긴다. 흔한 증상은 다음과 같다.

- **표 붕괴**: PDF 표가 열 순서 없이 한 줄로 풀려 "2024년 매출"과 "2023년 매출"이 구분되지 않는다
- **2단 레이아웃 섞임**: 논문·보고서의 두 단이 줄 단위로 교차 결합되어 문장이 의미를 잃는다
- **머리글·바닥글·페이지 번호 반복**: 모든 청크에 "사내 대외비 — 3/27" 같은 노이즈가 섞여 임베딩이 오염된다
- **스캔 문서 무시**: OCR 없이 텍스트 레이어만 읽어 빈 문서로 인덱싱된다
- **이미지·도표 손실**: 아키텍처 다이어그램, 차트에 담긴 정보가 통째로 사라진다
- **변경 감지 부재**: 소스가 바뀌어도 모르거나, 매번 전체를 다시 긁어 비용과 시간이 폭발한다

이 단계가 책임지는 것은 위 증상을 **하류로 넘기지 않는 것**이다.

## 핵심 개념

### 수집(Ingestion)의 세 방식

| 방식 | 동작 | 적합 | 주의 |
|---|---|---|---|
| **풀(Pull) 배치** | 주기적으로 소스를 훑어 변경분 수집 | 파일 서버, 위키, 변경 빈도 낮은 소스 | 변경 감지를 위해 해시·수정시각 비교 필요. 삭제 감지가 어렵다 |
| **푸시(Push) / 웹훅** | 소스가 변경 이벤트를 보냄 | SaaS(문서 협업, 티켓, 메신저) | 이벤트 유실 대비 주기적 전체 대조 필요 |
| **CDC (Change Data Capture)** | DB 트랜잭션 로그를 읽어 행 단위 변경 스트림 생성 | 운영 DB, 상품·고객 레코드 | 스키마 변경 추적, 삭제 이벤트 전파 설계 필요([07](07-freshness-and-sync.md)) |

커넥터는 **매니지드(Airbyte, Fivetran 류)**와 **직접 구현**으로 나뉜다. 매니지드는 수십~수백 소스를 빠르게 붙이지만 RAG에 필요한 "본문 + 권한 + 버전" 조합이 커넥터 스키마에 없을 때 결국 직접 구현을 덧붙이게 된다. 소스가 3개 이하이고 권한 모델이 복잡하면 처음부터 직접 구현이 싸다.

### 파싱(Parsing)의 산출물: 정규화 문서 모델

파서가 돌려줘야 하는 최소 구조는 다음과 같다. 이것이 없으면 [02 청킹](02-chunking-strategies.md)의 문서 구조 기반 청킹과 [08 근거 데이터](08-grounding-data-design.md)의 위치 기반 citation이 불가능하다.

```
Document
 ├─ doc_id, source_uri, content_hash, parsed_at, parser_name/version
 ├─ Block[] (순서 보존)
 │    ├─ type: heading(level) | paragraph | table | figure | caption | list | code | header/footer(제외 대상)
 │    ├─ text (표는 셀 구조 보존: markdown 또는 JSON)
 │    ├─ page, bbox(좌표), reading_order
 │    └─ confidence (OCR·레이아웃 신뢰도)
 └─ Asset[] (이미지 원본 참조, VLM 캡션)
```

### 문서 파서의 네 계열

| 계열 | 대표 | 강점 | 약점 |
|---|---|---|---|
| **레이아웃 분석 오픈소스** | Docling(IBM) | 레이아웃·표 구조 복원, 로컬 실행, 출력 구조가 풍부 | 스캔 품질 낮은 문서에선 OCR 엔진 품질에 종속 |
| **범용 문서 처리** | Unstructured | 포맷 폭(오피스·이메일·HTML 등), 오픈소스 + API | 표·좌표 품질은 포맷·모드별 편차 |
| **LLM/VLM 보조 매니지드 파서** | LlamaParse | 복잡 레이아웃·표를 모델이 읽어 복원, 자연어 지시로 추출 조정 | 호출 비용, 데이터 외부 전송, 비결정적 출력 |
| **벤더 OCR / 문서 AI** | 클라우드 3사 문서 AI, 국내 벤더 OCR | 스캔·손글씨·양식, 한국어 OCR 품질, SLA | 비용, 벤더 종속, 출력 스키마 변환 필요 |

제품별 정확도·속도 수치는 벤더 자료가 대부분이라 여기 적지 않는다. **자기 문서 샘플로 재는 것** 외에 믿을 수 있는 수치가 없다.

### 표·이미지·멀티모달

- **표**: 셀 구조를 보존해 markdown 표 또는 JSON으로. 표 전체를 하나의 블록으로 유지하고, 긴 표는 **헤더 행을 각 분할에 복제**한다
- **이미지·도표**: VLM(Vision-Language Model) 캡셔닝으로 텍스트 설명을 생성해 별도 블록으로 둔다. 캡션은 "원본 이미지 참조 + 생성 모델 + 생성 시각"을 메타데이터로 가진다(생성된 텍스트임을 citation에서 구분해야 하므로)
- **멀티모달 임베딩**: 이미지를 직접 임베딩하는 방식은 캡셔닝과 상호 보완. 도표의 수치 질문은 캡셔닝이, 시각 유사성 검색은 이미지 임베딩이 맞다

## 아키텍처 / 파이프라인

[`data-pipeline-architecture.html`](../assets/html/data-pipeline-architecture.html)의 첫 두 노드.

```
소스 인벤토리 ─▶ 수집 (풀 / 푸시 / CDC) ─▶ 원본 저장소 (불변, 해시) ─▶ 포맷 라우터
                                                                       ├─ 텍스트 PDF/오피스 ─▶ 레이아웃 파서
                                                                       ├─ 스캔/이미지 ─▶ OCR ─▶ 레이아웃 파서
                                                                       ├─ HTML/위키/메신저 ─▶ 경량 파서
                                                                       └─ DB 레코드 ─▶ 직렬화 템플릿
                                                                                      ▼
                                                     정규화 문서 모델 + 품질 점수 ─▶ [격리 큐] 또는 ─▶ 02 청킹
```

입력은 원본 바이트와 소스 메타데이터, 출력은 정규화 문서 모델과 파싱 품질 점수다. 원본은 **불변 저장소**에 해시와 함께 보관해 재파싱(파서 업그레이드 시)과 감사가 가능하게 한다.

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 매니지드 커넥터 (Airbyte, Fivetran 류) | 소스 10개 이상, 표준 SaaS·DB, 데이터 팀이 이미 운영 중 | 소스 3개 이하, 권한·버전 필드가 커넥터 스키마에 없음, 온프레미스 폐쇄망 | 중 (라이선스 또는 운영) | 안정 | `[2차]` |
| 직접 구현 커넥터 | 소스 적음, 권한 모델 복잡, 본문·ACL·버전을 함께 가져와야 함 | 소스가 많고 자주 늘어남 | 하(초기) / 중(유지) | 표준 | `[검증]` 일반 공학 |
| CDC (Debezium 류, DB 네이티브 CDC) | 운영 DB가 소스, 행 단위 변경을 수 초 내 반영해야 함 | 소스가 파일·문서, DB 로그 접근 권한 없음 | 중~상 (스트림 인프라) | 표준 | `[검증]` |
| Docling (레이아웃 분석 오픈소스) | 텍스트 PDF·오피스 중심, 표 복원 중요, 로컬 실행 필요 | 저품질 스캔이 대부분, GPU 없음에서 대량 처리 | 하~중 (자체 호스팅) | 안정 | `[2차]` |
| Unstructured | 포맷이 다양(이메일·HTML·오피스 혼재), 빠른 PoC | 표·좌표 정밀도가 핵심인 재무·규제 문서 | 하(오픈소스) / 중(API) | 안정 | `[2차]` |
| LlamaParse (LLM 보조 매니지드) | 복잡 레이아웃·다단·표가 많고 외부 전송 허용 | 데이터 반출 불가, 결정론적 재현 필요, 대량 저비용 | 중~상 (호출 과금) | 신생~안정 | `[벤더]` |
| 벤더 OCR / 문서 AI | 스캔·양식·손글씨·한국어 OCR, SLA 필요 | 텍스트 레이어가 이미 있는 문서(불필요 비용), 폐쇄망 | 상 (페이지 과금) | 안정 | `[벤더]` |
| VLM 캡셔닝 (이미지·도표 → 텍스트) | 도표·다이어그램에 핵심 정보, 수치 질문 | 이미지가 장식용, 비용 민감한 대량 문서 | 중~상 (모델 호출) | 신생 | `[2차]` |
| 이미지 직접 임베딩 (멀티모달 임베딩) | 시각 유사 검색, 제품 이미지 | 도표의 수치·관계 질문 | 중 | 신생 | `[2차]` |

### 선택 가이드

- **소스가 운영 DB이고 신선도가 분 단위라면** → CDC. 이유: 폴링은 지연과 부하가 크고 삭제를 놓친다
- **소스가 SaaS 10개 이상이고 데이터 팀이 있다면** → 매니지드 커넥터 + 권한·버전은 보조 커넥터로 보강. 이유: 커넥터 유지 비용이 가장 큰 숨은 비용
- **텍스트 PDF·오피스 문서가 대부분이고 로컬 실행이 필요하다면** → Docling 류 레이아웃 파서 기본 + 실패분만 벤더 OCR. 이유: 표 복원과 좌표가 하류 citation의 전제
- **스캔·양식·한국어 손글씨가 많다면** → 벤더 OCR을 1차, 레이아웃 파서를 2차. 이유: OCR 품질은 오픈소스 엔진 격차가 크고 한국어는 특히 `[실측]` 필요
- **판단이 어려우면** → 기본값: 직접 구현 커넥터 + Docling 류 파서 + 실패분 격리 큐. 샘플 100건으로 2종 비교 후 교체. 이유: 가장 적은 종속성으로 시작해 하류 요구가 드러난 뒤 바꿀 수 있다

## 설계 시 고려사항 (체크리스트)

- [ ] 소스 인벤토리에 유형·규모·갱신 빈도·권한 모델·삭제 정책을 적었는가
- [ ] 원본을 불변 저장소에 해시와 함께 보관해 재파싱이 가능한가
- [ ] 파서 비교를 **자기 문서 샘플**로 했는가 (표 복원율, 2단 레이아웃, 머리글 제거, OCR 신뢰도)
- [ ] 정규화 문서 모델에 블록 유형·페이지·좌표·읽기 순서·신뢰도가 있는가
- [ ] 표는 셀 구조를 보존하고 긴 표 분할 시 헤더를 복제하는가
- [ ] VLM 캡션은 "생성된 텍스트"로 표시되어 원문 인용과 구분되는가
- [ ] 파싱 실패·저신뢰 문서의 격리 큐와 재처리·수동 검토 절차가 있는가
- [ ] 파서 이름·버전을 메타데이터에 기록해 파서 교체 시 영향 범위를 알 수 있는가
- [ ] 한국어·영문 혼합 문서, 세로쓰기·한자 혼용 등 특수 레이아웃을 샘플에 포함했는가
- [ ] 수집 단계에서 PII 탐지가 필요한지 결정했는가([10](10-access-control-governance.md))

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 파서 정확도가 문서 유형별로 크게 다름 | 특정 부서·양식의 문서만 품질 저하, 원인 추적 어려움 | 문서 유형별 품질 점수 모니터링, 유형별 파서 라우팅 |
| LLM/VLM 보조 파싱의 비결정성 | 같은 문서를 두 번 파싱하면 다른 결과 → 중복·버전 혼란 | 원본 해시 기준 캐시, 파서 버전 고정, 재파싱은 명시적 이벤트로만 |
| 벤더 OCR 비용과 데이터 반출 | 대량 문서에서 비용 급증, 규제 데이터 외부 전송 불가 | 텍스트 레이어 유무로 사전 분기, 온프레미스 OCR 옵션 검토 |
| 머리글·바닥글·워터마크 오염 | 임베딩 품질 저하, 모든 청크에 노이즈 | 반복 블록 탐지 후 제외, 페이지 상·하단 영역 규칙 |
| 변경 감지 실패 (특히 삭제) | 삭제된 문서가 계속 인용됨 | 주기적 전체 대조(reconciliation), 소프트 삭제 전파([07](07-freshness-and-sync.md)) |
| 벤치마크 부재 | 파서 간 공개 비교가 벤더·블로그 수준 | 자체 골든 문서셋 `[실측]` |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 이 단계의 쓰기 행동은 원본 저장소 적재와 격리 큐 투입이고, 하류(02~10)의 모든 재처리가 이 단계의 **불변 원본 + 파서 버전 기록**에 의존한다. 변경 감지·삭제 전파의 운영은 [07](07-freshness-and-sync.md)에, PII·인젝션 가드레일의 정책은 [10](10-access-control-governance.md)에 있다.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 데이터 (문서·페이지 수) | 전체 폴링 1회 시간이 갱신 주기를 넘어 변경 감지가 밀림. 벤더 OCR·VLM 캡션 호출 비용이 인덱싱 예산을 초과 | 소스별 증분 커서(수정시각·해시) + 변경 큐, 텍스트 레이어 유무로 OCR 사전 분기, 캡션은 도표 블록만, 파싱 워커 무상태화 + 큐 길이 기반 수평 확장 | 페이지 수(OCR·VLM), 문서 수(해시 비교), 파일 크기(파서 메모리) |
| 소스·커넥터 수 | 커넥터마다 다른 인증·레이트 리밋·장애 패턴. "누가 이 커넥터를 고치나"가 비어 있음 | 커넥터를 공통 포트(`fetch_changes(cursor) → [raw_doc]`) 뒤 어댑터로 통일, 커넥터별 소유자·레이트 리밋·재시도 정책을 설정으로 | 커넥터 수(운영 인력), 소스 API 호출 수 |
| 테넌트 | 소스 자격 증명·ACL 모델이 테넌트마다 달라 수집 코드가 분기 | 테넌트 키를 원본 레코드와 큐 메시지에 처음부터, 자격 증명은 테넌트별 시크릿 저장소 | 테넌트 수 × 커넥터 수 |

파싱 워커는 **무상태**다. 입력은 원본 저장소의 `(doc_id, content_hash)`, 출력은 정규화 문서 모델. 중간 상태를 워커 로컬에 두지 않아야 실패 시 다른 워커가 같은 입력으로 재시도할 수 있다. 대량 재파싱(파서 업그레이드)은 서빙 트래픽과 분리된 **배치 창**(예: 야간)에서 문서 유형별 파티션으로 나눠 돌린다.

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 소스 시스템·커넥터 다운 (의존 서비스 다운) | 새 문서가 검색에 안 나옴. 기존 답변은 정상 | 커서 미진행 시간, 커넥터 오류율, 변경 큐 유입 0 | 서킷 브레이커로 해당 커넥터만 격리, 다른 소스는 계속. 마지막 성공 커서 보존 | 커서 정체가 소스별 신선도 SLO(예: 24h) 초과 → 커넥터 소유자 호출 |
| 벤더 OCR·VLM API 지연 급증 | 스캔 문서만 반영 지연 | 파서별 p95 처리 시간, 큐 적체 | 타임아웃 후 격리 큐로 이동, 텍스트 레이어 있는 문서는 로컬 파서로 계속. OCR 배치 창 확대 | 격리 큐 적체가 예시 1,000건 또는 48h 초과 |
| 파싱 실패·저신뢰 폭증 (검증 실패 폭증) | 특정 양식·부서 문서가 통째로 빠짐 | 문서 유형별 실패율·`confidence` 분포가 베이스라인 대비 급변 | 해당 유형만 2차 파서로 라우팅 전환, 나머지는 통과 | 실패율이 예시 5%p 이상 상승 → 파서 버전·소스 포맷 변경 여부 확인 |
| 원본 ↔ 파싱 결과 불일치 (데이터 불일치) | 답변이 인용한 페이지에 그 내용이 없음 | 재파싱 샘플 대조(해시 동일한데 블록 수·텍스트 상이), 하류 하이라이트 실패율 | 해당 `parser.version`으로 만든 문서를 재처리 대상으로 표시 | 비결정적 파서(LLM/VLM) 사용 중이면 버전 고정·캐시 적중 여부 확인 |
| 삭제 감지 실패 (단계 고유) | 삭제된 문서가 계속 인용 | 대조 배치의 유령 문서 수 | 대조 배치가 톰스톤을 변경 큐로 재투입([07](07-freshness-and-sync.md)) | 유령 문서가 기밀·PII 문서일 때 즉시 |
| 수집 문서 속 인젝션 (단계 고유) | 하류 에이전트가 문서 속 지시를 따름 | 입력 가드레일의 패턴 탐지율 | 의심 블록에 `suspect_injection` 플래그, 컨텍스트 투입 시 격리 표시([Part 5/01](../05-cross-cutting/01-security-prompt-injection.md)) | 플래그 문서가 공식 소스에서 나오면 소스 소유자 확인 |

SLI 후보: ① 소스 변경 → 정규화 문서 생성까지의 지연 p95 ② 파싱 성공률(문서 유형별) ③ 골든 문서셋 표 복원율·OCR 신뢰도 샘플 점수. SLO 초안(예시): 지연 p95 ≤ 소스별 신선도 SLO의 절반, 파싱 성공률 ≥ 98%, 격리 큐 체류 ≤ 48h. 숫자는 베이스라인 측정 후 재설정한다.

쓰기 행동의 멱등성: 원본 적재는 `(source_uri, content_hash)` 키로 멱등(같은 바이트는 한 번만 저장). 파싱 결과는 `(doc_id, content_hash, parser.version)` 키로 캐시해 같은 입력의 재파싱이 부작용 없이 같은 결과를 반환. 재시도 상한은 예시 3회, 초과 시 격리 큐. 커넥터 호출은 레이트 리밋 + 지수 백오프.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| 파서 (이름·버전·설정) | 블록 구조·좌표·표 복원 → 02 청킹 경계, 08 citation locator | 골든 문서셋(50~100건)의 표 복원율·블록 수·좌표 일치율 | 영향 문서의 재파싱 계획(계보로 범위 산정), 정규화 문서 모델 스키마 버전 |
| 정규화 문서 모델 스키마 | 02·03·08 모든 소비자 | 스키마 호환 테스트(추가는 자유, 삭제·의미 변경은 메이저. tolerant reader) | 02 청커, 03 메타데이터 게이트 |
| 커넥터 (버전·인증 방식·커서 형식) | 변경 감지 정확성, ACL 복사 | 커넥터 계약 테스트(샘플 소스에서 추가·수정·삭제·ACL 변경 4종 이벤트) | 커서 마이그레이션 스크립트 |
| OCR·VLM 모델 버전 | 스캔 문서 텍스트, 캡션 내용 → 임베딩 | 스캔 골든셋 문자 정확도, 캡션 샘플 사람 검수 | 캡션의 `derived_from`·생성 모델 메타데이터 |
| 포맷 라우터 규칙 (어떤 파일을 어느 파서로) | 파서별 부하·품질 | 라우팅 결정 테이블 테스트 | 파서 라우팅 설정 파일 |

롤백 단위는 "파서 버전 + 정규화 스키마 버전 + 라우터 설정" 묶음이다. 기술 부채로 기록할 것: 머리글·바닥글 제거를 규칙으로만 하는 범위(모델 기반 탐지는 2차), 멀티모달 추출 미도입 소스, 샘플 `[실측]` 없이 선택한 파서, 격리 큐의 수동 검토 적체.

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **지식** (가장 잦음) | 문서 추가·수정·삭제, 소스 추가, 소스 포맷·양식 변경 | 정규화 문서 모델, 변경 큐 메시지 스키마 | 커넥터 어댑터, 포맷 라우터 규칙 | 증분 커서 + 변경 큐(재배포 없음). 새 소스는 어댑터 추가 + 라우터 설정 | 해당 문서만 → 02~10 재처리 |
| **모델** | OCR 엔진·VLM 교체, 파서 메이저 업 | `parse(raw_doc) → Document` 포트 | 파서 어댑터(레이아웃 파서 / 범용 파서 / 벤더 OCR / VLM) | 어댑터 교체 + 골든 문서셋 회귀 + 영향 문서 재파싱 창 | 재파싱 대상 문서 전체(계보로 범위 산정) |
| **규칙·정책** | PII 수집 금지 소스, 수집 제외 경로, 보존 정책 | 소스 인벤토리 스키마 | 소스별 수집 정책 설정 | 설정 교체 + 정책 테스트 | 해당 소스. 소급 적용이면 삭제 전파([10](10-access-control-governance.md)) |
| **사용자 환경** | 조직 개편으로 소스 ACL 구조 변경, 새 테넌트 | ACL 복사 포트(`acl_of(raw_doc) → principals`) | 소스별 ACL 매퍼 | 매퍼 교체 + 전체 권한 대조 1회 | 메타데이터 권한 축 전체 |
| **프로토콜** | 소스 API 버전 업, 웹훅 스키마 변경, 소스를 MCP 서버로 노출 | 커넥터 포트 | 커넥터 어댑터 | 어댑터 버전 고정 + 계획된 업그레이드 창 | 해당 커넥터만 |
| **부하** | 문서 10배 | 무상태 워커, 변경 큐 | 워커 수, 배치 창 | 수평 확장 + 문서 유형별 파티션 | 큐·워커만 |

가장 자주 바뀌는 것: **지식**(문서 내용·소스 양식), 그 다음이 소스 API·커넥터. 코드 밖 설정으로 둘 것: 소스 인벤토리(유형·주기·소유자·ACL 매핑), 포맷 라우터 테이블, 커넥터별 레이트 리밋·재시도, 머리글·바닥글 제거 패턴, 파서 선택 규칙. 포트·어댑터 뒤에 둘 외부 의존: 소스 시스템 API, 매니지드 커넥터, 벤더 OCR·VLM API, 파서 라이브러리. 시점 재현성은 **불변 원본 저장소 + `parser.version`**이 보장한다. 원본이 남아 있으면 어떤 파서 버전으로도 다시 만들 수 있다.

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성 표의 "탐지 신호"가 **실제로 어디서 나오는지**를 설계한다. 기준은 [Part 1/07 관측성 설계 요소](../01-foundations/07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md). 이 단계는 Knowledge 배치 파이프라인의 **문서 단위 트레이스가 시작되는 곳**이다 — `ingest.fetch`가 트레이스 루트가 되고, 하류(02~08)의 모든 스팬이 같은 `doc_id` 트레이스에 자식 또는 링크로 붙는다. 커넥터 단위 폴링은 문서와 무관하게 돌므로 별도 스팬(`ingest.poll`)으로 둔다.

| 기록 대상 | 스팬 / 이벤트 (이름, 부모) | 핵심 속성 (버전 키 포함) | 지표 (→ 어느 SLI) | 샘플링 · 보존 · PII |
|---|---|---|---|---|
| 커넥터 폴링·커서 진행 | `ingest.poll` (커넥터 실행 단위, 부모 없음) | `agent.source_id`, `tenant_id`, `agent.connector_version`, `agent.cursor_lag_s`(소스 최신 수정시각 − 커서), `agent.events_emitted{upsert,delete,acl}`, `agent.circuit_state`, `agent.outcome` | `ingest.poll.cursor_lag_s` 게이지(소스별), `ingest.poll.errors` 비율, `ingest.queue.inflow` 카운터 → 탐지 신호 "커서 미진행·커넥터 오류율·큐 유입 0" | 메타 전수. 자격 증명·소스 URL 쿼리스트링은 기록 금지. 보존 예시 30일 |
| 원본 적재 | `ingest.fetch` (문서 트레이스 루트) | `doc_id`, `agent.source_uri_hash`, `agent.content_hash`, `agent.doc_type`, `agent.size_bytes`, `agent.pipeline_version`, `agent.acl_snapshot_hash` | `ingest.fetch.duration_ms`, `ingest.e2e_latency_ms`(소스 수정시각 → 정규화 문서 생성) → **SLI ① 지연 p95** | 메타 전수. 원문은 원본 저장소에만, 스팬엔 해시·URI 참조 |
| 파싱·포맷 라우팅 | `ingest.parse` (부모 `ingest.fetch`), 벤더 호출은 자식 `ingest.ocr` · `ingest.caption`(`gen_ai.*` 매핑) | `agent.parser.name`·`agent.parser.version`(파서 버전 키), `agent.router_rule_id`, `agent.parse_confidence`, `agent.block_count`, `agent.table_count`, `agent.cache_hit`, `agent.degradation[]`(`ocr_fallback_local`, `caption_skipped`), `gen_ai.usage.*`, `agent.cost_estimate` | `ingest.parse.success_ratio{doc_type}` → **SLI ② 파싱 성공률**, `ingest.parse.duration_ms{parser}` 히스토그램 → "파서별 p95", `ingest.parse.confidence` 히스토그램(베이스라인 대비 분포 이동) → "저신뢰 폭증", `ingest.caption.cost` → 대시보드 ③ | 메타 전수. 블록 텍스트·캡션 본문은 opt-in 참조만. 실패·격리 건은 입력 참조 100% 보존 |
| 격리 큐 | `ingest.quarantine` 이벤트 (부모 `ingest.parse`) | `agent.quarantine_reason`(timeout / parse_fail / low_confidence / injection), `agent.retry_count`, `agent.queue_wait_ms` | `ingest.quarantine.depth` 게이지, `ingest.quarantine.dwell_h` 히스토그램 → "큐 적체", SLO "격리 체류 ≤ 48h" | 전수. 보존은 큐 체류와 동일 |
| 입력 가드레일 | `ingest.guard` (부모 `ingest.parse`) | `agent.suspect_injection`(bool), `agent.injection_pattern_id`, `agent.pii_detected_types[]`, `agent.pii_masked`(bool), `agent.rules_version`(패턴 세트 버전) | `ingest.guard.injection_hits{source}` 카운터 → "입력 가드레일 패턴 탐지율". PII 지표 자체는 [10](10-access-control-governance.md) | 적중 건 전수, 적중 블록 본문은 보안 저장소에만 참조. **PII 원문 절대 금지** |
| 재파싱 샘플 대조·골든셋 | `ingest.verify` 배치 이벤트 (부모 없음, 대상 문서 트레이스에 링크) | `agent.sample_size`, `agent.parser.version{a,b}`, `agent.mismatch_count`, `agent.golden_table_recall`, `agent.ocr_sample_score` | `ingest.verify.mismatch_ratio` → "해시 동일한데 블록 수·텍스트 상이", `ingest.verify.golden_table_recall` → **SLI ③ 표 복원율·OCR 샘플 점수** | 배치 1회/일(예시). 보존 90일(회귀 추적용) |

탐지 신호 중 "하류 하이라이트 실패율"은 [08](08-grounding-data-design.md)의 `evidence.verify` 지표를 `agent.parser.version`으로 분해해 읽고, "대조 배치의 유령 문서 수"는 [07](07-freshness-and-sync.md)의 `sync.reconcile`이 원천이며 이 단계는 `ingest.poll`의 `events_emitted.delete=0` 지속을 보조 신호로 쓴다.

| 알림 | 조건 (예시) | 심각도 | 런북 (첫 3단계) |
|---|---|---|---|
| 소스 커서 정체 (장애 모드: 커넥터 다운) | `ingest.poll.cursor_lag_s` > 소스 신선도 SLO의 50%가 30분 지속, 또는 `ingest.queue.inflow`=0이 평소 유입 주기 3배 지속 | P2 (기밀·규정 소스는 P1) | ① `ingest.poll` 최근 스팬의 `agent.circuit_state`·오류 코드 확인 ② 소스 API 상태·자격 증명 만료 확인 ③ 마지막 성공 커서 보존 확인 후 커넥터 소유자 호출 |
| 스캔 문서 반영 지연 (장애 모드: 벤더 OCR·VLM 지연) | `ingest.parse.duration_ms{parser=ocr}` p95 > 60s가 10분 지속, 또는 `ingest.quarantine.depth` > 1,000 | P2 | ① 벤더 상태 페이지·레이트 리밋 응답 비율 확인 ② `degradation=ocr_fallback_local` 비율로 로컬 파서 폴백이 작동 중인지 확인 ③ OCR 배치 창 확대 또는 텍스트 레이어 문서 우선 처리 |
| 특정 유형 문서 누락 (장애 모드: 파싱 실패·저신뢰 폭증) | `ingest.parse.success_ratio{doc_type}`가 7일 베이스라인 대비 −5%p 1시간 지속, 또는 `confidence` 분포 p50이 −0.1 이동 | P2 | ① 급변 시점과 `agent.parser.version`·`router_rule_id` 변경 이력 대조 ② 실패 샘플의 소스 포맷·양식 변경 확인 ③ 해당 유형만 2차 파서 라우팅 전환 |
| 인용 페이지에 내용 없음 (장애 모드: 원본 ↔ 파싱 불일치) | `ingest.verify.mismatch_ratio` > 0.5%, 또는 08 locator 불일치가 특정 `parser.version`에 집중 | P2 | ① 불일치 문서의 `agent.cache_hit`·파서 비결정성 여부 확인 ② 계보 쿼리로 같은 `parser.version` 문서 범위 산정 ③ 재처리 큐 투입, 버전 고정 |
| 삭제된 문서 계속 인용 (장애 모드: 삭제 감지 실패) | 07 `sync.reconcile.ghosts{source}` ≥ 1이고 해당 소스의 `events_emitted.delete`가 7일간 0 | P1 (기밀·PII) / P2 | ① 커넥터가 삭제 이벤트를 낼 수 있는 감지 방식인지(해시·수정시각은 삭제 못 봄) 확인 ② 대조 배치 톰스톤 재투입 확인 ③ 소스를 이벤트 기반 감지로 승격 검토 |
| 문서 속 지시 유입 (장애 모드: 인젝션) | `ingest.guard.injection_hits{source}`가 공식 소스에서 ≥ 1 | P2 | ① 적중 블록을 보안 저장소에서 검토(패턴 오탐 여부) ② 플래그 문서가 하류 컨텍스트에 격리 표시로 들어갔는지 확인 ③ 소스 소유자에게 편집 이력 확인 요청 |

대시보드에서 이 단계를 보는 뷰: ② 레이어별 SLI의 Knowledge 패널 — 소스별 커서 지연 히트맵·파싱 성공률(유형별)·격리 큐 깊이·체류 시간 / ③ 비용 패널 — OCR·VLM 캡션 호출 비용(`gen_ai.usage.*` 페이지당, 소스별) / 감사 추적으로 넘기는 필드(관측 로그와 분리): 거버넌스 접점 표의 필드(`doc_id`, `source_uri`, `content_hash`, `ingested_at`, `parser{name,version}`, `pipeline_run_id`, 격리 사유, ACL 스냅샷) — 관측 스팬은 `doc_id`·`content_hash`·`pipeline_run_id`만 공유하고 `source_uri` 원문·ACL 스냅샷 본문은 감사 저장소에만 / 이 단계의 관측이 없으면 못 보는 장애: **커넥터가 살아 있고 오류도 0인데 커서가 전진하지 않는 조용한 정체** — 사용자에게는 "새 문서가 없다"로만 보여 신고가 오지 않고, 하류 지표는 전부 정상이다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5, 가역성 × 영향 범위) | 원본 적재·파싱은 **등급 1**(가역, 재파싱 가능). 단 **수집 대상 소스 추가**는 등급 2~3(여러 사용자에게 새 데이터 노출, PII·기밀 유입 가능) → 데이터 소유자 승인 1인 |
| 가드레일 위치 (입력 / 출력 / 행동) | **입력**: 수집 문서의 인젝션 패턴·PII 사전 탐지, 허용 소스 목록 밖 수집 차단. **행동**: 새 소스 등록·커넥터 자격 증명 변경은 승인 게이트 |
| 게이트 출력 (통과 / 차단 / 승인 / 저하)과 판정 수단 | 파싱 품질 게이트: 통과 / 저하(저신뢰 플래그 달고 통과) / 차단(격리 큐). 판정은 규칙(텍스트 레이어·확장자) → 분류기([09](09-ai-inside-the-pipeline.md)). 허용 소스·PII 등 보안 관련은 규칙만 |
| 소유자 (A) | 소스별 데이터 소유자. 파이프라인 전체는 데이터 엔지니어링 책임자. 커넥터마다 R(실행) 지정 |
| 감사 추적에 남길 필드 | `doc_id`, `source_uri`, `content_hash`, `ingested_at`, `parser{name,version}`, `pipeline_run_id`, 격리 사유, 수집 시점 소스 ACL 스냅샷, 캡션 생성 모델·시각 |

### 운영 준비도 체크
- [ ] 소스별 신선도 SLO와 커서 정체 알림·런북이 있는가
- [ ] 파싱 워커가 무상태이고 실패 시 다른 워커가 같은 입력으로 재시도하는가
- [ ] 원본 적재·파싱 캐시가 `content_hash` 기준으로 멱등이고 재시도 상한이 있는가
- [ ] 커넥터별 서킷 브레이커·레이트 리밋·소유자가 코드 밖 설정으로 있는가
- [ ] 파서 교체 시 골든 문서셋 회귀와 영향 문서 재파싱 범위 산정(계보)이 가능한가
- [ ] 새 소스 등록이 승인 게이트를 거치고 허용 소스 목록이 코드 밖 설정인가
- [ ] 수집 시점 ACL 스냅샷과 파서 버전이 감사 레코드에 남는가
- [ ] 대량 재파싱이 서빙과 분리된 배치 창에서 파티션 단위로 실행되는가
- [ ] 운영 안정성 표의 탐지 신호마다 원천 스팬·지표(`ingest.poll.cursor_lag_s`, `ingest.parse.success_ratio`, `ingest.verify.mismatch_ratio` 등)가 있고 `agent.parser.version`으로 분해되는가
- [ ] 알림마다 런북이 있고, 커서 정체 알림이 "오류 0 + 유입 0"의 조용한 정체도 잡는가
