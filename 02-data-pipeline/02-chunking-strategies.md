# 청킹 전략

> **범위**: fixed / recursive / semantic / late chunking / contextual retrieval / parent-child 비교와 선택 기준
> **시각화**: [`assets/html/data-pipeline-architecture.html`](../assets/html/data-pipeline-architecture.html) — 벡터 경로의 첫 노드

## 요약 (3줄)

1. 청킹은 "텍스트를 몇 토큰씩 자르는가"가 아니라 **검색 단위와 근거 단위를 어떻게 분리할 것인가**의 결정이다. 검색에 좋은 크기(작게)와 생성·인용에 좋은 크기(크게)는 다르므로 둘을 따로 둔다(parent-child).
2. 2026년의 기본값 후보는 **문서 구조 기반 분할 + 맥락 보강**이다. 맥락 보강 방식으로 late chunking과 contextual retrieval이 경쟁하며, 비교 연구(arXiv 2504.19754)는 contextual이 의미 일관성은 높지만 계산 비용이 크고, late chunking은 효율적이지만 관련성·완결성이 떨어진다고 보고한다 `[검증]`.
3. 청크 크기는 임베딩 모델의 유효 입력 길이, 질문 유형(사실 조회 vs 요약), 근거 단위([08](08-grounding-data-design.md))가 결정한다. 수치는 자체 평가셋으로 `[실측]`해서 정한다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 청킹 규칙(분할 기준, 크기, 오버랩, 맥락 보강 방식) ② 청크 ↔ 원문 위치 매핑(doc_id, block_id, 페이지, 오프셋) ③ 검색 단위(child)와 근거 단위(parent)의 관계 정의 |
| **언제** (When) | 벡터·키워드 검색을 쓰는 모든 경우. 생략 가능: 문서 하나가 수 KB 이하이고 통째로 컨텍스트에 넣을 수 있을 때, 또는 레코드 단위 정형 데이터만 있을 때. 미뤄도 되는 것: late chunking·contextual retrieval 같은 맥락 보강(기본 분할로 PoC 후 지표가 부족하면 추가) |
| **어떻게** (How) | ① [01](01-source-ingestion.md)의 블록 구조를 입력으로 받음 → ② 1차 분할은 문서 구조(제목·섹션·표)로 → ③ 섹션이 크면 재귀 분할, 목표 크기는 임베딩 모델 유효 길이의 절반 이하 → ④ 검색용 child와 인용용 parent를 분리 → ⑤ 맥락 보강 방식 결정(없음 / late / contextual) → ⑥ 질문 유형별 평가셋으로 recall@k·근거 완결성 `[실측]` |
| **왜** (Why) | 너무 크면 임베딩이 희석되어 검색이 안 되고, 너무 작으면 검색은 되지만 답에 필요한 문맥이 잘려 환각이 는다. 구조를 무시하고 자르면 표의 머리글과 본문이 분리되고 "위 조항"이 무엇인지 알 수 없는 청크가 생긴다 |

## 문제와 맥락

임베딩 모델은 입력 하나를 벡터 하나로 압축한다. 길면 길수록 여러 주제가 한 벡터에 섞여 **어느 질문에도 어중간하게 가까운** 벡터가 된다. 반대로 짧게 자르면 "그 결과"·"해당 조항"·"위 표" 같은 지시어의 대상이 청크 밖으로 나가 **맥락 상실(context loss)**이 생긴다. 청킹 전략은 이 두 힘의 균형이다.

여기에 두 가지 요구가 더 얹힌다.

- **근거 단위**: 답변에 인용할 때 사용자에게 보여줄 범위는 검색에 쓴 청크와 같을 필요가 없다. 문장 하나를 하이라이트할 수도, 섹션 전체를 보여줄 수도 있다([08](08-grounding-data-design.md))
- **롱컨텍스트 모델**: 컨텍스트가 길어졌으니 청킹이 필요 없다는 주장이 있었으나, 긴 컨텍스트 중간의 정보를 놓치는 현상이 재현된다(Lost in the Middle, RULER `[검증]`). 롱컨텍스트와 RAG는 보완 관계다 `[2차]`

## 핵심 개념

### 분할 기준의 스펙트럼

| 기준 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **고정 크기 (fixed)** | N 토큰마다 자르고 M 토큰 오버랩 | 단순, 예측 가능 | 문장·표 중간이 잘림 |
| **재귀 분할 (recursive)** | 문단 → 문장 → 단어 순으로 구분자를 바꿔가며 목표 크기까지 | 자연 경계 존중, 범용 기본값 | 문서 구조(제목 계층)를 모름 |
| **문서 구조 기반** | 제목·섹션·표·리스트 블록 단위로 분할, 제목 경로를 청크에 접두 | 의미 단위 보존, citation에 섹션 제목 사용 가능 | 파서가 구조를 줘야 함([01](01-source-ingestion.md)) |
| **시맨틱 (semantic)** | 문장 임베딩 유사도가 급락하는 지점에서 분할 | 주제 전환 경계 포착 | 임베딩 비용, 경계가 불안정, 구조 정보 없음 |
| **에이전트형 (LLM 분할)** | LLM이 "여기서 자르라"고 판단 | 복잡 문서에서 품질 | 비용·비결정성, 대량 처리 부적합 |

### 맥락 보강의 두 방식

청크를 작게 유지하면서 맥락을 잃지 않으려는 접근이 둘 있다.

| 방식 | 동작 | 비용이 드는 곳 | 비교 연구의 평가 |
|---|---|---|---|
| **Late chunking** | 문서 전체(또는 긴 구간)를 장문 임베딩 모델에 한 번 통과시켜 토큰 임베딩을 얻은 뒤, **그 다음에** 청크 경계로 풀링. 청크 벡터가 문서 전체 맥락을 반영 | 장문 입력을 지원하는 임베딩 모델 필요, 인덱싱 시 한 번 | 효율↑, 관련성·완결성↓ `[검증]` arXiv 2504.19754 |
| **Contextual retrieval** | 각 청크 앞에 LLM이 생성한 "이 청크가 문서 어디에 속하는지" 요약 1문장을 접두한 뒤 임베딩·BM25 색인 | 청크마다 LLM 호출(문서 전체를 컨텍스트로) → 인덱싱 토큰 비용이 크다 | 의미 일관성↑, 계산 비용↑ `[검증]` 같은 연구. 원형은 Anthropic 방식 `[벤더]` |

둘은 배타적이지 않다. 문서 구조 기반 청킹이 **제목 경로를 접두**하는 것만으로도 contextual retrieval의 효과 일부를 비용 없이 얻는다. LLM 생성 접두는 그 위에 얹는 선택이다.

### Parent-child: 검색 단위와 근거 단위의 분리

```
Parent (섹션 또는 문단 묶음, 인용·생성용)
 ├─ Child 1 (문장 2~3개, 임베딩·검색용) ─▶ 검색 적중 시 parent를 컨텍스트로 반환
 ├─ Child 2
 └─ Child 3
```

작은 child로 검색 정밀도를 올리고, 적중한 child의 parent를 LLM에 넘겨 완결성을 확보한다. 근거 표시에서는 child(하이라이트)와 parent(펼쳐 보기)를 둘 다 쓸 수 있다. 이 구조가 [08](08-grounding-data-design.md)의 하이브리드 근거 단위의 기반이다.

### 청크 크기·오버랩 결정 기준

| 결정 | 기준 |
|---|---|
| child 크기 | 임베딩 모델의 유효 입력 길이(모델 카드의 최대 길이가 아니라 품질이 유지되는 길이)의 절반 이하. 사실 조회 질문이 많으면 더 작게 |
| parent 크기 | 생성 모델에 넘길 때 질문당 상위 k개를 합쳐도 컨텍스트 예산 안에 들어가는 크기. 섹션 하나가 자연스러운 상한 |
| 오버랩 | 문장 경계를 존중하면 오버랩은 작아도 된다. 고정 크기 분할에서만 오버랩이 맥락 보존의 유일한 수단 |
| 표 | 자르지 않는다. 불가피하게 자르면 헤더 행 복제 |
| 코드·로그 | 함수·엔트리 단위. 줄 번호 보존 |
| 한국어 | 토크나이저에 따라 같은 글자 수에서 토큰 수가 크게 다르다. 글자 수가 아니라 **대상 임베딩 모델의 토크나이저 기준 토큰 수**로 잰다 |

수치 기본값을 적지 않는 이유는 임베딩 모델·문서 유형·질문 유형에 따라 최적점이 달라서다. 2~3개 설정을 평가셋으로 비교하는 데 하루면 충분하다.

## 아키텍처 / 파이프라인

```
정규화 문서 모델 (01) ─▶ 구조 기반 1차 분할 (제목 경로 접두) ─▶ 크기 초과 섹션 재귀 분할
        ─▶ parent/child 생성 + 원문 위치 매핑 ─▶ [맥락 보강: 없음 | late chunking | contextual 접두]
        ─▶ 청크 레코드 (text, parent_id, doc_id, block_ids, page, offsets, heading_path, chunk_version) ─▶ 03 메타데이터 ─▶ 04 임베딩
```

출력 청크 레코드는 반드시 **원문 위치로 되돌아갈 수 있어야** 한다. 이것이 없으면 citation은 "문서 X 어딘가"에서 끝난다.

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 고정 크기 (fixed) | 구조 없는 평문(채팅 로그, 트랜스크립트), 빠른 PoC | 표·제목 계층이 있는 문서, citation 품질 요구 | 하 | 표준 | `[검증]` 기준선으로 널리 사용 |
| 재귀 분할 (recursive) | 구조 정보가 없거나 불안정한 문서의 범용 기본값 | 섹션 제목이 의미를 좌우하는 규정·계약서 | 하 | 표준 | `[2차]` |
| 문서 구조 기반 | 보고서·규정·매뉴얼·위키처럼 제목 계층이 있는 문서. citation에 섹션명 필요 | 파서가 구조를 못 주는 저품질 스캔, 평문 | 하~중 (파서 의존) | 안정 | `[2차]` |
| 시맨틱 청킹 | 주제가 자주 바뀌는 긴 서술문, 구조 표지가 없는 문서 | 대량 문서(임베딩 비용 2배), 경계 재현성 필요 | 중 | 안정 | `[2차]` 효과는 문서 유형 의존 보고 |
| Late chunking | 인덱싱 비용을 억제하면서 맥락을 반영하고 싶을 때, 장문 임베딩 모델 보유 | 관련성·완결성이 최우선, 임베딩 모델이 장문 미지원 | 중 (모델 제약) | 신생 | `[검증]` arXiv 2504.19754: 효율↑ 관련성·완결성↓ |
| Contextual retrieval (LLM 접두) | 문서 간 유사 청크가 많아 출처 혼동이 잦을 때, 인덱싱 비용 허용 | 문서 수백만 건, 잦은 재색인, 비용 민감 | 상 (청크당 LLM 호출) | 신생~안정 | `[검증]` 같은 연구: 일관성↑ 비용↑. 원형 `[벤더]` |
| Parent-child | 거의 모든 운영 환경. 검색 정밀도와 생성 완결성을 동시에 | 문서가 매우 짧아 parent=문서인 경우(불필요) | 중 (저장 2중, 매핑 유지) | 안정 | `[2차]` 실무 표준 |
| 에이전트형 LLM 분할 | 소량의 고가치 복잡 문서(계약서, 규격서) | 대량·반복 색인 | 상 | 실험 | `[2차]` |

### 선택 가이드

- **문서에 제목 계층이 있다면** → 문서 구조 기반 + parent-child. 이유: 비용 없이 맥락(제목 경로)과 citation 품질을 동시에 얻는다
- **평문·로그·트랜스크립트라면** → 재귀 분할 + parent-child. 이유: 구조가 없으니 자연 경계만 존중하면 된다
- **유사 문서가 많아 출처 혼동이 잦고 인덱싱 비용을 감당할 수 있다면** → contextual retrieval 접두 추가. 이유: 비교 연구에서 의미 일관성 우위 `[검증]`
- **인덱싱 비용이 제약이고 장문 임베딩 모델이 있다면** → late chunking. 이유: LLM 호출 없이 맥락 반영. 단 관련성 저하를 `[실측]`으로 확인
- **판단이 어려우면** → 기본값: 문서 구조 기반 + 재귀 보정 + parent-child, 맥락 보강 없음. 평가셋에서 출처 혼동이 보이면 contextual 추가. 이유: 가장 싸고 되돌리기 쉽다

## 설계 시 고려사항 (체크리스트)

- [ ] 근거 단위([08](08-grounding-data-design.md))를 먼저 정했는가 — 청크 설계는 그것을 역산한다
- [ ] 청크 크기를 대상 임베딩 모델의 **토크나이저 기준**으로 쟀는가 (한국어 토큰 팽창 확인)
- [ ] 표·코드·리스트는 자르지 않거나 헤더를 복제하는가
- [ ] 청크마다 제목 경로(heading path)를 접두했는가
- [ ] child → parent → 문서 → 원문 위치(페이지·오프셋)로 되돌아갈 수 있는가
- [ ] 청킹 규칙 버전(chunk_version)을 기록해 규칙 변경 시 재색인 범위를 알 수 있는가([07](07-freshness-and-sync.md))
- [ ] 질문 유형별(사실 조회 / 비교 / 요약) 평가셋으로 2~3개 설정을 비교했는가
- [ ] 맥락 보강(late / contextual)을 추가했다면 그 비용 증가분과 지표 개선분을 함께 기록했는가
- [ ] 머리글·바닥글·반복 노이즈가 청크에 섞이지 않는가([01](01-source-ingestion.md))

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 최적 청크 크기가 모델·문서·질문에 따라 달라 보편 정답이 없음 | 블로그의 "권장 크기"를 그대로 쓰면 어긋남 | 자체 평가셋 `[실측]`, 설정을 데이터로 기록 |
| 구조 기반 청킹은 파서 품질에 종속 | 파싱이 깨진 문서는 청킹도 깨짐 | 파싱 품질 점수 낮은 문서는 재귀 분할로 폴백 |
| Contextual retrieval의 인덱싱 비용 | 문서 수가 늘면 인덱싱 비용이 서빙 비용을 넘음 | 고가치 컬렉션에만 적용, 제목 경로 접두로 대체 가능한지 먼저 확인 |
| Late chunking의 관련성 저하 | 비교 연구에서 관련성·완결성 하락 보고 `[검증]` | 리랭커로 보정, 평가 후 채택 |
| 청킹 규칙 변경 = 전체 재색인 | 비용·시간, 운영 중 전환 복잡 | 규칙 버전 관리, 블루/그린 인덱스([07](07-freshness-and-sync.md)) |
| 멀티홉 질문은 청킹으로 해결 안 됨 | 여러 문서에 흩어진 답은 어떤 청크 크기로도 한 청크에 없음 | 그래프 경로([05](05-knowledge-graph-construction.md)) 또는 질의 분해(Part 3) |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 청킹은 순수 변환 단계라 외부 쓰기가 없고, 운영의 핵심은 **규칙 변경 = 전체 재색인**([한계와 리스크] 참조)이라는 비용 이벤트를 예측 가능하게 만드는 것이다.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 데이터 (문서·청크 수) | 청킹 규칙 변경 시 전체 재청킹·재임베딩 창이 하루를 넘음. contextual 접두의 LLM 호출 비용이 인덱싱 예산을 지배. parent-child 2중 저장 | 청커를 무상태 함수(`chunk(Document, rules) → [Chunk]`)로 두고 문서 단위 병렬화, 재청킹은 문서 유형별 파티션 + 배치 창, contextual 접두는 고가치 컬렉션만(설정으로 범위 지정), 제목 경로 접두로 대체 가능한지 먼저 | 청크 수(저장·임베딩), 문서 길이(접두 생성 시 문서 전체가 컨텍스트 → 토큰 비용), 규칙 변경 빈도(전체 재처리) |
| 문서 유형 수 | 유형마다 다른 분할 규칙이 코드 분기로 쌓여 "이 문서가 왜 이렇게 잘렸나"를 추적 못 함 | 유형 → 규칙 라우팅 테이블을 설정으로, 청크 레코드에 적용 규칙 ID 기록 | 유형 수 × 규칙 수(평가셋 유지) |
| 테넌트 | 테넌트별 청크 크기·접두 정책 요구 | 규칙 세트에 테넌트 키, 기본 규칙 상속 | 테넌트별 평가셋 |

청킹 자체는 CPU 작업이라 10배에 선형이다. 비선형으로 깨지는 것은 **맥락 보강(LLM 접두·시맨틱 분할의 임베딩)**과 **규칙 변경 재처리**뿐이므로, 이 둘을 설정으로 끄고 켤 수 있어야 한다.

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 상류 파서 구조 누락 (의존 서비스 저하) | 구조 기반 청크가 통째로 한 덩어리 또는 잘게 부서짐 | 입력 문서의 `quality_score`·블록 수, 청크 크기 분포 이상치 | 파싱 품질 점수 임계 미만이면 재귀 분할로 폴백하고 `chunk_rule=fallback_recursive` 기록 | 특정 소스에서 폴백 비율이 예시 20% 초과 → 파서 라우팅 점검([01](01-source-ingestion.md)) |
| contextual 접두 LLM API 다운·지연 급증 | 신규 문서 색인 지연 | 접두 생성 큐 적체, 호출 오류율·p95 | 접두 없이 색인하고 `context_prefix=none` 플래그 → 복구 후 배치로 접두 보강(멱등 재처리) | 적체가 신선도 SLO 위협 시 접두 범위 축소 또는 일시 비활성(킬 스위치) |
| 토큰 한도 초과 청크 폭증 (검증 실패 폭증) | 임베딩 절단으로 검색 품질이 조용히 하락 | 청크 토큰 수 분포(대상 토크나이저 기준) 상한 초과율 | 초과 청크는 재귀 재분할, 그래도 초과(긴 표)는 헤더 복제 분할 | 초과율 급변 → 토크나이저·모델 변경 또는 한국어 비중 변화 확인 |
| 청크 ↔ 원문 위치 불일치 (데이터 불일치) | 하이라이트가 엉뚱한 문장에 찍힘 | 샘플 검증: `original[offsets] == chunk.text` 일치율, 하류 하이라이트 실패율 | 불일치 문서를 재청킹 대상으로 표시 | 재파싱된 문서의 오프셋이 갱신되지 않은 경로 확인(계보) |
| 한 인덱스에 `chunk_version` 혼재 (단계 고유) | 같은 문서가 두 방식으로 중복 검색 | 인덱스 내 `chunk_version` 종류 수 > 1 | 쓰기 시 인덱스 메타의 허용 버전과 불일치하면 거부 | 블루/그린 전환 중이 아닌데 발생하면 즉시([07](07-freshness-and-sync.md)) |

SLI 후보: ① 청크 토큰 한도 준수율 ② 오프셋 유효율(샘플) ③ 문서 → 청크 레코드 생성 지연 p95. SLO 초안(예시): 한도 준수율 ≥ 99.5%, 오프셋 유효율 = 100%(불일치 0건 목표, 발견 즉시 재처리), 지연은 전체 신선도 SLO의 일부로. 쓰기 행동의 멱등성: 청크 ID는 `(doc_id, content_hash, chunk_version, 순번)`의 결정론적 해시로 만들어 같은 입력이 같은 ID를 낸다. 접두 생성(LLM)은 비결정적이므로 `(chunk_id, prefix_model_version)`으로 캐시하고 재시도 상한 예시 3회.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| 청킹 규칙 세트 (`chunk_version`: 분할 기준·크기·오버랩·유형 라우팅) | 전체 청크 → 임베딩·BM25·근거 단위 | 질문 유형별 평가셋 recall@k·근거 완결성, 청크 크기 분포 | 전체 재색인(블루/그린), 04 인덱스 버전, 08 parent/child 매핑 |
| 대상 토크나이저 (임베딩 모델에 종속) | 청크 크기 측정 기준 → 한도 준수 | 토큰 수 분포 재측정 | 04 임베딩 모델 버전과 묶음 |
| parent-child 매핑 스키마 | 08 근거 단위 조립, Part 3 컨텍스트 조립 | 스키마 호환(추가 전용), 매핑 왕복 테스트 | 08 citation 스키마, Part 3 검색 어댑터 |
| contextual 접두 프롬프트·모델 | 접두 텍스트 → 임베딩·BM25 | 출처 혼동 평가셋, 접두 샘플 검수 | 접두 적용 컬렉션 재색인, `derived_from` 메타데이터 |
| 제목 경로 접두 템플릿 | 청크 텍스트 앞부분 → 임베딩 | 평가셋 | 재색인 |

롤백 단위는 "청킹 규칙 + 토크나이저(=임베딩 모델) + 인덱스 버전"이다. 기술 부채로 기록할 것: 수치 기본값을 `[실측]` 없이 쓴 컬렉션, 시맨틱·에이전트형 분할을 쓰는 소량 컬렉션의 비결정성, 접두를 재귀 분할 폴백 청크에도 붙일지 미결, 한국어 문장 분할기 교체 계획.

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **지식** (가장 잦음) | 문서 추가·수정 → 해당 문서 재청킹 | 청크 레코드 스키마, 결정론적 청크 ID | — | 문서 단위 증분 재처리(재배포 없음) | 해당 문서의 청크·임베딩·근거 단위 |
| **모델** | 임베딩 모델 교체 → 유효 입력 길이·토크나이저 변경 | `chunk()` 포트, 청크 레코드 스키마 | 크기·오버랩 설정값, 토크나이저 어댑터 | 규칙 세트 새 버전(설정 교체) + 블루/그린 재청킹·재임베딩 창 | 전체 청크 |
| **도메인 모델** | 새 문서 유형(계약서·로그 등) 등장 | 유형 → 규칙 라우팅 포트 | 유형별 분할 규칙 | 라우팅 테이블에 행 추가(설정), 해당 유형만 재청킹 | 해당 유형 문서 |
| **규칙·정책** | 근거 단위 요구 변경(예: 문장 하이라이트 추가) | parent-child 매핑 스키마(추가 전용) | 문장 오프셋 생성 단계 | 스키마 필드 추가 + 배치 보강(재임베딩 없음) | 08·Part 4 렌더 |
| **사용자 환경** | 새 언어 추가(한·영 → 다국어) | 청크 레코드 스키마 | 언어별 문장 분할기·토크나이저 | 언어별 규칙 세트 + 언어별 평가셋 | 해당 언어 문서 |
| **프로토콜** | 상류 정규화 문서 모델 메이저 업 | 청크 레코드 스키마 | 입력 어댑터 | 어댑터 교체, 재청킹 여부는 블록 의미 변경 시만 | 입력 경계만 |

가장 자주 바뀌는 것: **지식**(문서) — 이것은 문서 단위 증분으로 비용 없이 흡수된다. 운영상 부담이 되는 변화는 빈도는 낮지만 전파가 넓은 **임베딩 모델 교체**와 **규칙 재조정**이다. 코드 밖 설정으로 둘 것: 유형별 분할 규칙·크기·오버랩, 접두 적용 컬렉션 목록, 제목 경로 템플릿, 접두 프롬프트, 토큰 한도. 포트·어댑터 뒤에 둘 외부 의존: 토크나이저(임베딩 모델 종속), 접두 생성 LLM, 시맨틱 분할용 임베딩 API. 시점 재현성: `chunk_version` + 원본 `content_hash`로 과거 청크를 결정론적으로 재생성할 수 있다(접두는 캐시 보관 필요).

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5, 가역성 × 영향 범위) | **등급 1**. 가역(재청킹)이고 사용자에게 직접 노출되는 행동이 없다. 단 규칙 변경에 따른 전체 재색인 **전환**은 [07](07-freshness-and-sync.md)의 블루/그린 게이트(등급 2) |
| 가드레일 위치 (입력 / 출력 / 행동) | **출력**: 청크 레코드 필수 필드(위치 매핑·`chunk_version`) 검증, 접두·생성물에 `derived_from` 강제. 행동 가드레일 해당 없음 |
| 게이트 출력 (통과 / 차단 / 승인 / 저하)과 판정 수단 | 통과 / 저하(재귀 폴백 플래그) / 차단(위치 매핑 불가 청크는 하류로 안 넘김). 판정은 규칙(토큰 수·필수 필드)만 |
| 소유자 (A) | 데이터 엔지니어링 책임자. 규칙 변경의 C는 AI 엔지니어(평가셋) |
| 감사 추적에 남길 필드 | `chunk_version`, 적용 규칙 ID, `tokenizer_id`, 접두 생성 모델·버전(있을 때), `derived_from`, 폴백 여부 |

### 운영 준비도 체크
- [ ] 청커가 무상태이고 청크 ID가 결정론적이라 재처리가 멱등한가
- [ ] 청크 토큰 수를 대상 토크나이저 기준으로 측정하고 한도 초과율을 모니터링하는가
- [ ] 파싱 품질 저하 시 재귀 분할 폴백이 자동이고 폴백 비율 알림이 있는가
- [ ] contextual 접두 생성이 킬 스위치로 꺼지고, 꺼진 동안 색인이 계속되는가
- [ ] 유형별 규칙·크기·접두 범위가 코드 밖 설정이고 버전이 있는가
- [ ] 규칙 변경 시 평가셋 회귀 → 블루/그린 전환 절차가 문서화되어 있는가
- [ ] 오프셋 유효율 샘플 검증이 주기적으로 돌고 불일치가 재처리 큐로 가는가
