# 메타데이터와 출처(Provenance) 설계

> **범위**: 출처·버전·권한·lineage 모델링, W3C PROV, 근거 추적성 확보
> **시각화**: [`assets/html/data-pipeline-architecture.html`](../assets/html/data-pipeline-architecture.html) — 모든 노드를 관통하는 메타데이터 레이어

## 요약 (3줄)

1. 메타데이터는 검색 필터용 부가 정보가 아니라 **citation·권한·신선도·감사의 유일한 근거**다. 나중에 붙일 수 없다. 청크가 만들어지는 순간 함께 만들어져야 한다.
2. 스키마는 다섯 축으로 설계한다: **출처(where from)**, **버전(which)**, **권한(who may see)**, **시점(when valid)**, **계보(how produced)**. W3C PROV의 Entity–Activity–Agent 모델이 계보 축의 표준 어휘다 `[검증]`.
3. 버전 전략은 "덮어쓰기"가 가장 싸고 가장 위험하다. 답변이 인용한 버전을 나중에 재현해야 하면 **불변 버전 + 유효 시점**이 필요하다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 문서·청크·근거 단위에 붙는 메타데이터 스키마(필수/선택 필드, 타입, 허용값) ② 버전·유효 시점 정책 ③ 계보(lineage) 기록 방식 ④ citation 렌더에 필요한 필드의 보장 |
| **언제** (When) | 모든 경우. 생략 가능한 것은 없다. 다만 **깊이**는 조절한다: 참고용 챗봇은 출처 URI + 수집 시각이면 되고, 규제·감사 대상은 PROV 수준의 계보와 불변 버전이 필요하다 |
| **어떻게** (How) | ① citation UI([Part 4/06](../04-dynamic-ui/06-hitl-ui-patterns.md))와 권한 모델([10](10-access-control-governance.md))에서 **필요한 필드를 역산** → ② 다섯 축별 필수 필드 확정 → ③ 허용값은 택소노미로(문서 유형, 부서, 기밀 등급) → ④ 버전·시점 정책 결정 → ⑤ 파이프라인 각 단계가 자기 계보(파서 버전, 청킹 규칙 버전, 임베딩 모델)를 기록하도록 → ⑥ 필수 필드 누락 시 인덱싱 거부 |
| **왜** (Why) | 출처 없는 청크는 인용할 수 없고, 버전 없는 청크는 "어제 답이 왜 달랐나"에 답할 수 없다. 권한 없는 청크는 유출 경로가 되고, 시점 없는 청크는 만료된 규정을 현행처럼 인용한다. 계보 없는 청크는 파서 버그가 발견됐을 때 영향 범위를 모른다 |

## 문제와 맥락

RAG 초기 구현은 보통 `{text, embedding, source_url}` 세 필드로 시작한다. 운영에 들어가면 다음 질문이 차례로 온다.

- "이 답의 근거가 **어느 버전** 문서인가? 지난주에 개정됐는데" → 버전 축 부재
- "이 사용자가 **볼 수 없는** 문서가 인용됐다" → 권한 축 부재
- "**2023년 규정**을 현행처럼 답했다" → 유효 시점 축 부재
- "파서 버그로 표가 깨진 문서가 **몇 건**인가? 다시 색인해야 하는데" → 계보 축 부재
- "UI에서 근거를 하이라이트하려는데 **페이지·위치**가 없다" → 출처 축이 얕음

이 질문들은 모두 메타데이터를 **처음부터** 넣었다면 쿼리 하나로 끝났을 것들이다. 사후에 넣으려면 전체 재색인이다.

## 핵심 개념

### 다섯 축과 필수 필드

| 축 | 질문 | 필수 필드 (제안) | 선택 필드 |
|---|---|---|---|
| **출처** (Source) | 어디서 왔나, 원문 어디인가 | `source_system`, `source_uri`, `doc_id`, `title`, `locator`(page, bbox 또는 char offset, heading_path) | `author`, `mime_type`, `language` |
| **버전** (Version) | 어느 판인가 | `doc_version` 또는 `content_hash`, `ingested_at` | `source_modified_at`, `supersedes`(이전 버전 ID) |
| **권한** (Access) | 누가 볼 수 있나 | `acl`(허용 주체 목록 또는 그룹), `classification`(공개/내부/대외비 등 택소노미) | `tenant_id`, `pii_flags` |
| **시점** (Temporal) | 언제 유효한가 | `valid_from`, `valid_to`(없으면 현행) | `effective_date`(문서가 말하는 효력일), `review_due` |
| **계보** (Lineage) | 어떻게 만들어졌나 | `pipeline_run_id`, `parser`(name/version), `chunker_version`, `embedding_model` | `derived_from`(VLM 캡션 등 생성물의 원본 참조), `quality_score` |

**출처와 시점은 다르다.** `ingested_at`은 우리가 가져온 시각, `effective_date`는 문서가 효력을 갖는 날, `valid_from/to`는 우리 인덱스에서 이 판이 현행인 기간이다. 셋을 섞으면 "어제 수집한 작년 규정"이 현행으로 취급된다. 두 시간축(기록 시점과 유효 시점)을 따로 두는 것을 **bitemporal** 모델이라 부른다.

### W3C PROV: 계보의 표준 어휘

PROV(2013 W3C 권고안)는 "무엇이(Entity) 어떤 활동으로(Activity) 누가·무엇에 의해(Agent) 만들어졌나"를 표현한다 `[검증]`. 핵심 관계는 세 가지다.

| 관계 | 의미 | 파이프라인에서의 대응 |
|---|---|---|
| `wasGeneratedBy` | Entity ← Activity | 청크 ← 청킹 실행(run) |
| `wasDerivedFrom` | Entity ← Entity | 청크 ← 문서 블록 ← 원본 파일; VLM 캡션 ← 이미지 |
| `wasAttributedTo` / `wasAssociatedWith` | Entity/Activity ← Agent | 실행 ← 파서 v1.4, 임베딩 모델 X, 또는 사람 |

PROV-O(OWL 온톨로지) 전체를 트리플스토어에 넣을 필요는 없다. **어휘와 관계 구조만 빌려** 관계형 또는 문서형 테이블에 담아도 "이 청크의 원본은 무엇이고 어떤 도구 버전이 만들었나"에 답할 수 있다. 외부 감사·상호운용이 필요해지면 PROV-O로 내보낸다.

### 버전 전략 세 가지

| 전략 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **덮어쓰기** | 문서가 바뀌면 기존 청크 삭제 후 재삽입 | 저장 최소, 단순 | 과거 답변의 근거 재현 불가, 삭제·삽입 사이 공백 |
| **불변 버전** | 모든 판을 보관, `is_current` 플래그로 현행 표시 | 감사·재현 가능, 롤백 쉬움 | 저장 증가, 검색 시 현행 필터 필수 |
| **불변 버전 + 유효 기간** | 위 + `valid_from/to`로 시점 질의 가능 | "2025년 3월 기준 규정은?" 답변 가능 | 스키마·질의 복잡도 |

규제·감사 대상이면 두 번째 이상이 필수다. 참고용이면 덮어쓰기로 시작하되 `content_hash`와 `ingested_at`은 남겨 최소한의 변경 추적을 한다.

### citation에 필요한 필드

[08 근거 데이터 설계](08-grounding-data-design.md)의 citation 스키마가 이 페이지의 필드를 소비한다. UI가 "제목 — 섹션 — p.12 — 2026-03 개정판 — [원문 보기]"를 그리려면 `title`, `heading_path`, `locator.page`, `doc_version`, `source_uri`가 **모든 청크에 빠짐없이** 있어야 한다. 하나라도 선택 필드로 두면 UI는 분기 처리로 지저분해진다. 필수 필드 누락은 **인덱싱 단계에서 거부**한다.

## 아키텍처 / 파이프라인

```
01 수집: source_*, doc_id, content_hash, ingested_at, acl(소스 권한 복사)
   ▼
01 파싱: parser{name,version}, locator(page,bbox), quality_score, derived_from(캡션)
   ▼
02 청킹: chunk_id, parent_id, heading_path, offsets, chunker_version
   ▼
03 메타데이터 게이트: 필수 필드 검증 → 택소노미 허용값 검증 → valid_from/to 부여 → 누락 시 거부·격리
   ▼
04 임베딩: embedding_model, embedded_at
   ▼
인덱스(들) + 메타데이터 저장소(단일 진실 원천) ─▶ 08 citation ─▶ Part 3 검색 필터 / Part 4 렌더
```

메타데이터의 **단일 진실 원천**은 벡터DB의 페이로드가 아니라 별도 저장소(관계형 또는 문서형)에 두고, 벡터DB에는 필터링에 필요한 부분집합만 복제한다. 벡터DB 교체·재색인 시 메타데이터를 잃지 않기 위해서다.

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 평면 키-값 메타데이터 (벡터DB 페이로드만) | PoC, 소스 1~2개, 참고용 챗봇, 권한 없음 | 운영, 권한·버전·감사 요구, 벡터DB 교체 가능성 | 하 | 표준 | `[2차]` |
| 구조화 스키마 + 별도 메타데이터 저장소 | 대부분의 운영 환경. 다섯 축 필수 필드, 택소노미 허용값 | 소규모 일회성 프로젝트 | 중 | 표준 | `[검증]` 일반 데이터 공학 |
| W3C PROV 어휘 차용 (관계형/문서형 저장) | 계보 추적 필요, 파서·모델 교체가 잦음, 생성물(캡션·요약) 혼재 | 계보 질문이 전혀 없는 단순 컬렉션 | 중 | 표준(W3C) | `[검증]` |
| PROV-O 전체 + 트리플스토어 | 외부 감사·규제 보고, 기관 간 계보 교환, 이미 RDF 스택 보유 | RDF 경험 없는 팀, 내부용 | 상 | 표준(W3C) | `[검증]` |
| 데이터 카탈로그·lineage 도구 연동 (OpenLineage 류) | 데이터 플랫폼 팀이 이미 카탈로그 운영, 테이블 수준 계보가 충분 | 청크·블록 수준의 세밀한 계보 필요(카탈로그는 보통 데이터셋 단위) | 중 (통합) | 안정 | `[2차]` |
| 덮어쓰기 버전 | 참고용, 저장 비용 민감, 재현 요구 없음 | 규제·감사, "어제 답이 왜 달랐나" 질문 | 하 | 표준 | — |
| 불변 버전 + 유효 기간 (bitemporal) | 규정·계약·가격처럼 시점이 의미를 좌우하는 데이터 | 시점 질의가 없는 데이터, 저장 예산 극히 제한 | 중~상 | 표준(DB 이론) | `[검증]` |

### 선택 가이드

- **참고용 챗봇이고 권한이 없다면** → 평면 메타데이터로 시작하되 `source_uri`, `content_hash`, `ingested_at`, `locator`는 반드시. 이유: 이 넷이 없으면 citation 자체가 안 된다
- **권한이 있거나 운영 서비스라면** → 구조화 스키마 + 별도 저장소 + 불변 버전. 이유: 벡터DB 페이로드는 단일 진실 원천이 될 수 없다
- **규정·계약·가격처럼 시점이 중요하다면** → bitemporal(기록 시점 + 유효 시점). 이유: "그 시점 기준 답"을 요구받는다
- **파서·모델 교체가 잦거나 생성물(캡션·요약)이 섞인다면** → PROV 어휘 차용. 이유: 영향 범위 산정과 "생성된 텍스트" 구분이 쿼리 하나로 된다
- **판단이 어려우면** → 기본값: 다섯 축 필수 필드 + 별도 저장소 + 불변 버전(`is_current`) + PROV 어휘. 이유: 어느 방향으로도 확장 가능하고 비용은 중간

## 설계 시 고려사항 (체크리스트)

- [ ] citation UI와 권한 모델에서 필요한 필드를 **역산**해 필수 필드를 정했는가
- [ ] 다섯 축(출처·버전·권한·시점·계보)에 각각 최소 하나의 필수 필드가 있는가
- [ ] `locator`가 UI 하이라이트에 충분한가 (페이지 + 좌표 또는 문자 오프셋)
- [ ] 허용값(문서 유형, 기밀 등급, 부서)을 자유 텍스트가 아닌 택소노미로 관리하는가
- [ ] 기록 시점(`ingested_at`)과 유효 시점(`valid_from/to`, `effective_date`)을 구분했는가
- [ ] 생성물(VLM 캡션, LLM 요약, contextual 접두)이 `derived_from`으로 원본과 연결되고 "생성됨"으로 표시되는가
- [ ] 파서·청커·임베딩 모델 버전이 모든 청크에 기록되는가
- [ ] 필수 필드 누락 시 인덱싱이 거부·격리되는가 (경고만 하고 통과시키지 않는가)
- [ ] 메타데이터 단일 진실 원천이 벡터DB 바깥에 있는가
- [ ] 소스의 ACL을 복사할 때 소스 권한 변경을 다시 반영하는 경로가 있는가([10](10-access-control-governance.md))

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 소스가 메타데이터를 안 줌 (저자·효력일 없는 PDF) | 필수 필드를 채울 수 없음 | 추출(LLM/규칙)로 보강하되 `derived_from`으로 "추정값" 표시, 불가하면 기본값 + 품질 등급 하향 |
| 스키마 변경 시 전체 재색인 | 필드 추가가 비용 이벤트가 됨 | 별도 저장소에 두면 벡터 재계산 없이 메타데이터만 갱신 가능 |
| 메타데이터 자체의 오류 (잘못된 ACL, 틀린 유효 기간) | 권한 누출, 만료 규정 인용 | 소스 대조 배치, 샘플 감사, 변경 이력 기록 |
| PROV의 학습 곡선 | 팀이 어휘를 일관되게 못 씀 | 세 관계(generated/derived/attributed)만 쓰는 축약 프로파일 |
| 벡터DB 메타데이터 필터의 표현력 한계 | 복잡한 ACL·시점 조건을 벡터DB가 못 거름 | 1차 필터는 벡터DB, 정밀 필터는 애플리케이션([10](10-access-control-governance.md)) |
| 저장 비용 (불변 버전) | 판이 많은 문서에서 저장 급증 | 오래된 판은 벡터 없이 메타데이터·원문만 보관 |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 메타데이터 저장소는 이 Part의 **단일 진실 원천**이자 시점 재현성의 근거라, 다른 단계의 운영 설계가 전부 여기의 필드(`pipeline_version`, `parser.version`, `acl`, `valid_to`)에 기댄다. 그래서 이 단계는 "잘 돌아가는가"보다 **"틀린 값이 들어오지 않는가"**(fail-closed 게이트)가 안정성의 중심이다.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 데이터 (문서·청크·버전 수) | 메타데이터 저장소가 모든 단계의 쓰기·조회를 받는 단일 병목. 불변 버전 보관으로 저장량이 문서 수 × 판 수로 증가. 벡터DB 필터용 부분집합 복제 지연 | 저장소를 핫(필터·현행 판)과 콜드(계보·과거 판)로 분리, `doc_id`·테넌트 키로 파티셔닝, 복제는 변경 큐 소비자로 비동기화하되 지연을 SLI로, 오래된 판은 벡터 없이 메타데이터·원문만 | 청크 수(핫), 판 수(콜드), 필터 필드 수(복제 폭) |
| 권한 주체 수 | 청크당 `acl` 목록이 그룹 평탄화로 수백 항목으로 비대. 그룹 변경 시 청크 수만큼 갱신 | 청크에는 그룹 ID만, 사용자 → 그룹 해석은 질의 시([10](10-access-control-governance.md)) | 그룹 수 × 청크 수 |
| 택소노미·필드 수 | 허용값·필수 필드가 늘며 게이트 검증 시간과 거부율 증가, 소비자(UI·필터)마다 다른 어휘 해석 | 택소노미를 SKOS 등 외부 어휘로 버전 관리([06](06-ontology-driven-modeling.md)), 스키마 진화는 추가 전용 | 필드 수 × 소비자 수 |
| 테넌트 | 테넌트별 스키마 확장 요구 | 공통 필수 축 + 테넌트 확장 네임스페이스 | 테넌트 수 |

메타데이터 게이트는 **무상태 검증 함수**다. 상태(택소노미·필수 필드 목록)는 버전 있는 설정으로 주입한다.

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 메타데이터 저장소 다운 (의존 서비스 다운) | 신규 색인 중단. 검색은 복제본 필터로 계속되나 렌더 전 재확인 실패 | 저장소 가용성, 게이트 처리량 0 | **인덱싱은 fail-closed**(메타데이터 없이 청크를 넣지 않음). 검색은 복제된 필터 필드로 계속하되 citation의 버전·유효 필드가 없으면 "근거 확인 불가" 저하 표시([08](08-grounding-data-design.md)) | 다운이 예시 15분 초과 → 온콜. ACL 재확인이 불가하면 [10](10-access-control-governance.md) 정책대로 거부 |
| 메타데이터 → 벡터DB 복제 지연 급증 | 삭제·권한 회수가 메타데이터에는 반영됐는데 검색엔 아직 보임 | 복제 지연 p95, 변경 큐 소비 적체 | 렌더 전 재확인에서 메타데이터 원천의 `is_current`·`acl`을 다시 읽어 차단(2차 방어) | 지연이 삭제 전파 SLO(예: 15분) 초과 시 즉시. 기밀 문서 포함이면 해당 컬렉션 검색 일시 차단 |
| 게이트 거부 폭증 (검증 실패 폭증) | 특정 소스 문서가 색인에서 사라짐 | 소스별 거부율이 베이스라인 대비 급변, 거부 사유 분포 | 거부 문서는 격리 큐로, 다른 소스는 계속 | 소스 스키마 변경·커넥터 ACL 매퍼 고장 여부 확인. 거부율 예시 5%p 상승 시 |
| 택소노미 밖 값 유입 (데이터 불일치) | 필터·등급 산정이 "미분류"로 쏠림 | 미분류 비율, 신규 값 출현 로그 | 허용값 밖은 거부가 아니라 `unclassified` 버킷에 넣고 통과(필터는 보수적으로 제외) | 버킷이 예시 2% 초과 → 택소노미 변경 요청([06](06-ontology-driven-modeling.md)) |
| 시점 필드 오설정 (단계 고유) | 만료 규정이 현행처럼 인용, 또는 현행이 만료로 숨음 | `valid_from > valid_to`, `effective_date` 미래값 등 규칙 위반 건수, 사용자 신고 | 규칙 위반은 게이트 차단. 효력일 추출값은 `derived_from`으로 "추정" 표시하고 등급 하향 | 추정 효력일 비율이 높은 소스는 소유자에게 메타데이터 보강 요청 |
| 소스 ACL 복사 오류 (단계 고유) | 권한 없는 문서 노출 또는 권한 있는 문서 누락 | 주기 권한 대조의 불일치 건수 | 불일치 문서는 보수적으로(더 좁은 ACL) 적용 후 재동기화 | 노출 방향 불일치 1건이라도 발견 시 즉시 보안 보고 |

SLI 후보: ① 필수 필드 완전성(색인된 청크 중 다섯 축 필수 필드 전부 보유) ② 메타데이터 → 인덱스 복제 지연 p95 ③ 권한 대조 불일치 건수. SLO 초안(예시): 완전성 = 100%(게이트가 보장), 복제 지연 p95 ≤ 5분, 대조 불일치 = 0건(주 1회). 쓰기 행동의 멱등성: 메타데이터 upsert 키는 `(doc_id, doc_version)`, 같은 판을 두 번 써도 결과 동일. 불변 버전은 갱신이 아니라 **새 행 + 이전 행 `is_current=false`**이며 이 둘을 한 트랜잭션으로. 복제 소비자는 at-least-once를 전제로 멱등하게.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| 메타데이터 스키마 (필드·타입·필수 여부) | 모든 생산자(01·02·04·05)와 소비자(08·Part 3 필터·Part 4 렌더) | 스키마 호환 테스트(추가는 자유, 삭제·의미 변경은 메이저), 소비자별 tolerant reader 테스트 | 게이트 설정, 복제 필드 목록, 08 citation 스키마 |
| 택소노미 (문서 유형·기밀 등급·부서·주제) | 필터 어휘, 신뢰도 등급 규칙, UI 표시 | 허용값 테스트, 구→신 매핑 적용 후 미분류 비율 | 매핑 테이블([06](06-ontology-driven-modeling.md)), 08 등급 규칙, Part 4 라벨 |
| 필수 필드·게이트 규칙 | 거부율 | 골든 메타데이터셋 통과·거부 테스트 | 격리 큐 처리 절차 |
| 버전·시점 정책 (덮어쓰기 / 불변 / bitemporal) | 저장량, 질의 복잡도, 재현 가능성 | 시점 질의 테스트("2025-03 기준 현행") | 07 재처리 잡, 08 `valid_*` 소비 |
| PROV 프로파일 (쓰는 관계 집합) | 계보 질의, 삭제 범위 산정 | 계보 왕복 테스트(청크 → 원본 → 생성물) | 10 삭제 절차 |
| 복제 필드 목록 (벡터DB로 보내는 부분집합) | 사전 필터 가능 범위 | 필터 쿼리 테스트 | 04 인덱스 매핑 |

롤백 단위는 "스키마 버전 + 게이트 설정 + 복제 필드 목록" 묶음. 기술 부채로 기록할 것: 덮어쓰기 버전으로 시작한 컬렉션과 불변 버전 전환 시점, 효력일을 추출로 채운 소스 목록, 복제 지연을 렌더 전 재확인으로만 보완하는 범위, PROV 축약 프로파일 사용 중인 사실(외부 감사 요구 시 PROV-O 내보내기 필요).

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **지식** (가장 잦음) | 문서 판 추가, 유효 기간 갱신, 삭제·만료 | 다섯 축 스키마, `doc_id`·`doc_version` 식별 체계 | — | 새 판 행 추가 + `is_current` 전환(재배포 없음), 톰스톤 필드 | 해당 문서의 모든 파생물 메타데이터 |
| **도메인 모델** | 택소노미 값 추가·개명·병합(부서 개편, 문서 유형 세분화) | 택소노미 참조 방식(ID 참조, 라벨 아님), 매핑 테이블 | 택소노미 버전 | 택소노미 새 버전 + 구→신 매핑으로 라벨 이전(재색인 없음), 분할은 재분류 배치 | 필터·등급 규칙·UI 라벨 |
| **모델** | 파서·청커·임베딩·추출기 버전 교체 | 계보 축 필드명(`parser`, `chunker_version`, `embedding_model`, `extractor_version`) | 값만 바뀜 | 새 `pipeline_version` 기록. 영향 범위 산정은 계보 쿼리 하나 | 재처리 대상 문서(계보로 식별) |
| **규칙·정책** | 필수 필드 추가, 보존 기간, 기밀 등급 체계 변경 | 게이트 인터페이스(`validate(record, rules_vN)`) | 게이트 규칙 설정 | 규칙 버전 + 시행일. 기존 레코드는 배치 보강 또는 유예 | 신규 색인 즉시, 기존은 배치 |
| **사용자 환경** | 조직 개편(그룹 재편), 새 테넌트 | 권한 축 스키마(그룹 ID 참조) | 그룹 해석(질의 시) | 청크엔 그룹 ID만 두므로 멤버 변경은 재색인 없음. 그룹 자체 개편은 ACL 이벤트로 갱신([07](07-freshness-and-sync.md)) | 권한 축만 |
| **프로토콜** | 메타데이터 저장소 교체, lineage 도구 연동(OpenLineage 류) | 저장소 포트(`put/get/query`), PROV 어휘 | 저장소 어댑터, PROV-O 내보내기 어댑터 | 어댑터 교체 + 전체 마이그레이션 1회 | 저장소 경계만 |

가장 자주 바뀌는 것: **지식**(문서 판·유효 기간), 그 다음 **도메인 모델**(택소노미 값). 둘 다 스키마 변경 없이 **데이터 변경**으로 흡수되어야 한다. 코드 밖 설정으로 둘 것: 필수 필드 목록, 택소노미, 게이트 규칙, 보존 기간표, 복제 필드 목록, PROV 프로파일. 포트·어댑터 뒤에 둘 외부 의존: 메타데이터 저장소, 벡터DB 페이로드 복제, lineage 카탈로그. 시점 재현성은 이 단계가 **제공자**다. 불변 버전 + `pipeline_version` + bitemporal 필드가 있어야 "그때 그 답"을 재구성할 수 있다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5, 가역성 × 영향 범위) | 자동 메타데이터 기록은 **등급 2**(여러 사용자의 필터·등급에 영향, 가역). **ACL·기밀 등급·유효 기간의 수동 수정**은 등급 3(권한 누출·만료 인용으로 직결) → 데이터 소유자 승인 1인 + 변경 이력 |
| 가드레일 위치 (입력 / 출력 / 행동) | **출력**: 인덱싱 게이트(필수 필드·택소노미·시점 규칙 검증, 누락 시 차단). **행동**: ACL·분류·유효 기간의 수동 변경과 스키마 메이저 변경은 승인 게이트 |
| 게이트 출력 (통과 / 차단 / 승인 / 저하)과 판정 수단 | 통과 / 차단(필수 필드·시점 규칙 위반) / 저하(택소노미 밖 값은 `unclassified`로 통과, 추정값은 등급 하향) / 승인(수동 수정). 판정은 **규칙만**. 효력일·분류 추출 자체는 [09](09-ai-inside-the-pipeline.md)이되 게이트는 그 결과를 규칙으로 재검증 |
| 소유자 (A) | 데이터 소유자(택소노미·ACL·보존 정책), 데이터 엔지니어링 책임자(스키마·게이트). 데이터 스튜어드가 R |
| 감사 추적에 남길 필드 | 스키마 버전, 택소노미 버전, 게이트 규칙 버전, `pipeline_run_id`, 게이트 판정(통과/차단/저하 + 사유), 수동 수정 이력(누가·언제·이전값·이후값·승인자), 소스 ACL 스냅샷 |

### 운영 준비도 체크
- [ ] 인덱싱 게이트가 fail-closed이고, 저장소 다운 시 메타데이터 없는 청크가 들어가지 않는가
- [ ] 메타데이터 → 인덱스 복제 지연을 측정하고 렌더 전 재확인이 2차 방어로 있는가
- [ ] 다섯 축 필수 필드 완전성이 100%로 모니터링되는가
- [ ] 택소노미·필수 필드·보존 기간표가 코드 밖 설정이고 버전·시행일이 있는가
- [ ] 스키마 진화가 추가 전용이고 소비자가 tolerant reader인가
- [ ] 수동 ACL·분류·유효 기간 수정이 승인 게이트와 변경 이력을 거치는가
- [ ] 계보 쿼리 하나로 "파서 vX로 만든 문서"의 재처리 범위를 산정할 수 있는가
- [ ] 과거 시점(`valid_from/to`)과 `pipeline_version`으로 그때의 근거를 재구성할 수 있는가
