# 임베딩과 인덱싱

> **범위**: dense / sparse / hybrid / multi-vector 임베딩, 벡터DB 선택, 양자화
> **시각화**: [`assets/html/data-pipeline-architecture.html`](../assets/html/data-pipeline-architecture.html) — 벡터 경로

## 요약 (3줄)

1. 2026년의 기본값은 **하이브리드(BM25 + dense + RRF)**다. 단독 dense보다 우수하다는 보고가 누적되어 있고 `[2차]`, 고유명사·코드·한국어 조사 변형에 강한 sparse가 dense의 약점을 메운다.
2. 임베딩 모델 선택은 벤치마크 순위가 아니라 **자기 도메인·언어의 평가셋**으로 한다. 한국어는 토크나이저 효율과 다국어 모델의 한국어 품질 편차가 커서 `[실측]`이 필수다.
3. 벡터DB는 "전용 vs 범용"보다 **운영 팀이 이미 아는 것**이 먼저다. 데이터 수백만 건 이하면 pgvector나 기존 검색엔진으로 충분한 경우가 많고, 전용 벡터DB는 규모·필터 복잡도·멀티테넌시가 커질 때 검토한다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 표현 방식 선택(dense / sparse / hybrid / multi-vector) ② 임베딩 모델과 그 버전 고정 ③ 인덱스 저장소와 인덱스 유형(HNSW / IVF / 평면) ④ 양자화 수준 ⑤ 메타데이터 필터와 결합 방식 ⑥ 모델 교체 절차 |
| **언제** (When) | 비정형 텍스트를 의미로 검색해야 하는 모든 경우. 생략 가능: 정형 레코드만 있어 SQL·키워드로 충분할 때. 미뤄도 되는 것: 양자화(규모가 커지기 전), multi-vector(리랭커로 충분한 동안), 그래프 경로([05](05-knowledge-graph-construction.md)) |
| **어떻게** (How) | ① 질문 유형 분포 파악(키워드형 / 의미형 / 멀티홉) → ② 평가셋 100~300 쌍 구축 → ③ 임베딩 모델 2~3종을 같은 청크로 비교 `[실측]` → ④ BM25 병행 색인 + RRF 융합 → ⑤ 저장소 선택(기존 인프라 우선) → ⑥ 인덱스 파라미터·양자화는 recall@k 손실을 재고 결정 → ⑦ 임베딩 모델 버전을 메타데이터에 고정([03](03-metadata-provenance.md)) |
| **왜** (Why) | dense만 쓰면 제품 코드·사람 이름·약어처럼 의미보다 **문자열이 중요한 질문**에서 실패한다. 모델을 고정하지 않으면 다른 모델로 만든 벡터가 한 인덱스에 섞여 검색이 조용히 망가진다. 저장소를 과잉 선택하면 운영 부담이, 과소 선택하면 필터·규모 한계가 뒤늦게 드러난다 |

## 문제와 맥락

임베딩은 텍스트를 벡터 공간의 점으로 옮겨 "의미가 가까운 것"을 찾게 한다. 이 접근은 동의어·바꿔 말하기에 강하지만 세 가지 체계적 약점이 있다.

- **정확 매칭 약함**: "ERR-4021", "김철수 과장", "SHACL" 같은 토큰은 의미보다 문자열이 중요하다. dense는 이를 비슷한 다른 코드와 혼동한다
- **도메인 어휘**: 범용 모델은 사내 용어·제품명을 모른다. 파인튜닝 없이는 "동의어"로 묶이지 않는다
- **언어 편차**: 다국어 모델은 영어 중심 학습이라 한국어 품질이 모델마다 크게 다르다. 같은 문장이 한국어에서 더 많은 토큰으로 쪼개져 유효 입력 길이가 줄어든다

sparse 표현(BM25, SPLADE)은 정확 매칭에 강하고 dense는 의미 매칭에 강하다. 둘을 합치는 하이브리드가 기본값이 된 이유다.

## 핵심 개념

### 표현 방식 네 가지

| 방식 | 표현 | 강점 | 약점 | 대표 |
|---|---|---|---|---|
| **Dense** | 고정 차원 실수 벡터 1개 | 의미·동의어·바꿔 말하기 | 정확 매칭, 도메인 신조어, 설명 불가 | 범용 임베딩 모델들 |
| **Sparse (어휘)** | 단어별 가중치(희소 벡터) | 정확 매칭, 설명 가능(어떤 단어가 맞았나), 학습 불필요 | 동의어, 바꿔 말하기 | BM25 `[검증]` |
| **Sparse (학습형)** | 모델이 확장한 단어 가중치 | 어휘 확장으로 동의어 일부 커버 + 설명 가능 | 모델 의존, 한국어 지원 모델 적음 | SPLADE `[검증]` |
| **Multi-vector (late interaction)** | 토큰마다 벡터, 질의-문서 토큰 간 최대 유사도 합 | 정밀도 높음, 긴 문서에 강함 | 저장 수십 배, 인덱스 지원 저장소 제한 | ColBERT 계열 `[검증]` |

**Hybrid**는 방식이 아니라 **융합**이다. 보통 BM25와 dense를 각각 검색해 **RRF(Reciprocal Rank Fusion)**로 순위를 합친다. RRF는 점수 스케일이 다른 두 결과를 순위만으로 합치므로 튜닝이 거의 필요 없다. 융합 뒤 **cross-encoder 리랭커**를 얹으면 난이도 높은 셋에서 추가 이득이 보고된다 `[2차]` — 리랭킹은 [Part 3/03](../03-agent-workflow-rag/03-retrieval-reranking.md).

### 임베딩 모델 선택 기준

| 기준 | 확인 방법 |
|---|---|
| 언어 품질 | 공개 벤치마크(MTEB 류)의 한국어 하위셋은 참고만. **자기 평가셋** recall@k가 결정 |
| 유효 입력 길이 | 모델 카드의 최대 길이가 아니라 품질이 유지되는 길이. 한국어 토큰 팽창 반영 |
| 차원 | 차원이 크면 저장·검색 비용↑. 차원 축소(Matryoshka 류)를 지원하면 비용 조절 가능 |
| 호스팅 | API(데이터 반출, 비용 변동) vs 자체 호스팅(GPU, 운영) |
| 비대칭 질의 | 질의와 문서에 다른 접두(instruction)를 쓰는 모델은 색인·검색 양쪽에서 일관되게 적용 |
| 안정성 | 모델 버전이 바뀌면 전체 재임베딩. 버전 고정 가능한지 확인([07](07-freshness-and-sync.md)) |
| 도메인 적응 | 파인튜닝 가능성, 또는 리랭커로 보정 가능한지 |

### 인덱스 유형 (개념)

| 유형 | 동작 | 적합 | 트레이드오프 |
|---|---|---|---|
| **평면(Flat, brute-force)** | 모든 벡터와 거리 계산 | 수십만 건 이하, 정확 recall 필요 | 규모에 선형으로 느려짐 |
| **HNSW** | 계층적 근접 그래프를 탐색 `[검증]` | 대부분의 온라인 검색. 높은 recall과 낮은 지연 | 메모리 사용 큼, 구축 시간, 삭제가 비효율 |
| **IVF** | 벡터를 클러스터로 나눠 가까운 클러스터만 탐색 `[검증]` | 메모리 제약, 대규모 배치 | 클러스터 경계의 recall 손실, 재학습 필요 |
| **디스크 기반 (DiskANN 류)** | 그래프 일부를 SSD에 | 메모리에 안 들어가는 규모 | 지연 증가 |

파라미터(HNSW의 `M`, `ef`; IVF의 `nlist`, `nprobe`)는 recall과 지연의 교환이다. 기본값으로 시작해 평가셋의 recall@k 손실을 재며 조정한다.

### 양자화

| 수준 | 저장 절감 | recall 영향 | 적합 |
|---|---|---|---|
| float32 → float16/int8 (scalar) | 2~4배 | 작음 | 대부분의 첫 단계 |
| Product Quantization (PQ) | 수십 배 | 중간, 재순위화 필요 | 대규모, 메모리 제약 |
| Binary | 수십 배, 매우 빠른 거리 | 큼, 반드시 재순위화 | 1차 후보 생성 후 원본 벡터로 재순위 |

양자화는 **2단계(후보 생성 → 원본 벡터 재순위)**와 함께 쓰면 손실을 대부분 회복한다. 규모가 수백만 건 미만이면 양자화 없이 시작하는 것이 단순하다.

### 벡터DB 유형 (제품 수치 없음, 유형별 특성만)

| 유형 | 특성 | 적합 | 한계 |
|---|---|---|---|
| **관계형 DB 확장 (pgvector 류)** | 기존 DB에 벡터 컬럼·인덱스. 트랜잭션·조인·ACL을 SQL로 | 데이터 수백만 건 이하, 메타데이터 조인·권한이 복잡, 운영 팀이 PostgreSQL에 익숙 | 초대규모·초저지연, 벡터 전용 기능(멀티벡터, 고급 양자화) |
| **전용 벡터DB** | 벡터 검색에 최적화. 필터·멀티테넌시·양자화·하이브리드 내장 | 수천만 건 이상, 복잡한 필터 + 벡터 결합, 테넌트 격리 | 새 운영 대상 추가, 트랜잭션·조인은 약함 |
| **검색엔진 (Elasticsearch / OpenSearch 류)** | BM25 네이티브 + 벡터 인덱스. 하이브리드가 한 시스템에서 | 이미 검색엔진 운영 중, 키워드 검색 비중 높음, 로그·운영 데이터 | 벡터 전용 기능은 전용 DB보다 늦게 도입, 자원 소모 |
| **매니지드 벡터 서비스** | 운영 위탁, 탄력 확장 | 운영 인력 부족, 변동 트래픽 | 데이터 반출·거주 요건, 비용 예측, 종속 |
| **그래프DB 내장 벡터** | 노드에 벡터 인덱스 | 그래프 경로가 주이고 벡터는 진입점 | 벡터 성능·기능은 전용 대비 제한 |

## 아키텍처 / 파이프라인

```
청크 레코드 (02/03)
  ├─▶ BM25 색인 (형태소 분석기 또는 서브워드 토크나이저 선택)        ─┐
  ├─▶ dense 임베딩 (모델·버전 고정, 배치, 재시도·멱등)  ─▶ 벡터 인덱스 ─┼─▶ 질의 시: 각각 top-N → RRF → (리랭커) → 근거 단위 조립 (08)
  └─▶ [선택] SPLADE / ColBERT 색인                                      ─┘
메타데이터 부분집합 복제 (필터용) ──────────────────────────────────────▶ 필터 (ACL, valid_to, 문서 유형)
```

한국어 BM25는 **토크나이저 선택이 품질을 좌우**한다. 형태소 분석기(조사·어미 분리) 또는 서브워드 토크나이저 중 평가셋으로 고른다. 공백 분리만 쓰면 "규정을"과 "규정은"이 다른 토큰이 되어 재현율이 급락한다.

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| Dense 단독 | 바꿔 말하기 많은 FAQ, 짧은 PoC | 코드·ID·고유명사 질의, 도메인 신조어 | 하~중 (모델 호출) | 표준 | `[검증]` 정확 매칭 약점 널리 보고 |
| BM25 단독 | 키워드형 질의, 로그·코드·운영 데이터, 설명 가능성 필요 | 동의어·의도 기반 질의 | 하 | 표준 | `[검증]` |
| Hybrid (BM25 + dense + RRF) | 대부분의 운영 환경. 질의 유형이 섞여 있음 | 극단적 지연 제약으로 두 검색을 못 돌릴 때 | 중 (두 인덱스 유지) | 안정 | `[2차]` 단독 대비 우수 보고 누적 |
| SPLADE (학습형 sparse) | 어휘 확장이 필요하나 설명 가능성도 원할 때, 영어 중심 | 한국어 지원 모델 부재 시, 추가 모델 운영 부담 | 중 | 안정 | `[검증]` 원 논문 / 한국어 `[실측]` 필요 |
| Multi-vector (ColBERT 계열) | 정밀도 최우선, 긴 문서, 리랭커로 부족 | 저장 예산 제한, 저장소가 미지원 | 상 (저장·인덱스) | 안정~신생(운영) | `[검증]` 원 논문 |
| pgvector 류 | 수백만 건 이하, SQL 조인·ACL, PostgreSQL 운영 경험 | 수천만 건 이상 + 초저지연, 멀티벡터 | 하~중 | 안정 | `[2차]` |
| 전용 벡터DB | 대규모, 복잡 필터, 멀티테넌시, 양자화·하이브리드 내장 필요 | 소규모, 운영 인력 부족, 트랜잭션 요구 | 중~상 | 안정 | `[2차]` `[벤더]` 성능 수치 |
| 검색엔진 (ES/OpenSearch 류) | 이미 운영 중, BM25 비중 높음, 로그 데이터 | 벡터 전용 고급 기능 필요 | 중 | 표준 | `[2차]` |
| 매니지드 벡터 서비스 | 운영 위탁, 변동 트래픽 | 데이터 거주 규제, 비용 예측 필요 | 중 (과금) | 안정 | `[벤더]` |
| 양자화 (scalar / PQ / binary) | 수백만 건 이상, 메모리 제약 | 소규모(불필요한 복잡도), 재순위화 불가 구조 | 중 | 안정 | `[검증]` PQ 원 논문 / 손실은 `[실측]` |

### 선택 가이드

- **질의가 코드·ID·고유명사 중심이라면** → BM25 비중을 높인 hybrid, 한국어 형태소 분석기 적용. 이유: dense는 문자열 정확도에 약하다
- **데이터가 수백만 건 이하이고 PostgreSQL을 운영 중이라면** → pgvector 류 + 애플리케이션 RRF. 이유: 운영 대상을 늘리지 않고 ACL 조인을 SQL로 처리
- **이미 검색엔진을 운영 중이라면** → 그 엔진의 벡터 기능으로 hybrid. 이유: BM25와 벡터가 한 시스템에서 융합되어 운영이 단순
- **수천만 건 이상이거나 테넌트 격리·복잡 필터가 핵심이라면** → 전용 벡터DB + 양자화 + 2단계 재순위. 이유: 필터·양자화·멀티테넌시가 내장
- **판단이 어려우면** → 기본값: hybrid(BM25 + dense + RRF), 기존 인프라에 가장 가까운 저장소, 양자화 없음, 모델 버전 고정, 임베딩 모델 2종 `[실측]` 후 확정. 이유: 가장 적은 운영 부담으로 시작해 규모가 커질 때 전용 DB로 옮길 수 있다

## 설계 시 고려사항 (체크리스트)

- [ ] 질의 유형 분포(키워드형 / 의미형 / 멀티홉)를 로그 또는 인터뷰로 파악했는가
- [ ] 평가셋(질의-정답 청크 쌍)이 한국어·혼합 언어·도메인 용어를 포함하는가
- [ ] 임베딩 모델 2~3종을 같은 청크·같은 평가셋으로 비교했는가 `[실측]`
- [ ] 임베딩 모델 이름·버전·차원이 모든 벡터의 메타데이터에 기록되는가
- [ ] BM25 토크나이저(형태소 vs 서브워드)를 한국어 평가셋으로 골랐는가
- [ ] RRF 융합 후 top-k가 리랭커·생성의 컨텍스트 예산에 맞는가
- [ ] 메타데이터 필터(ACL, valid_to, 문서 유형)가 벡터 검색 **전**에 적용되는가(후 필터는 결과 수 부족 유발)
- [ ] 인덱스 파라미터·양자화 변경 시 recall@k 손실을 측정했는가
- [ ] 모델 교체 시 블루/그린 인덱스로 전환할 수 있는가([07](07-freshness-and-sync.md))
- [ ] 임베딩 API 사용 시 데이터 반출·비용 상한·장애 시 폴백을 정했는가

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 이 단계는 Part 2에서 **서빙 경로에 직접 놓이는 유일한 저장소**를 운영한다. 인덱싱(쓰기)과 검색(읽기)의 장애 모드가 다르고, 임베딩 모델 교체는 Part 2 전체에서 전파 범위가 가장 넓은 변화다([한계와 리스크] 참조).

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 데이터 (청크·벡터 수) | HNSW 인덱스가 메모리에 안 들어감. 전체 재임베딩 창이 임베딩 API 레이트 리밋·비용에 묶여 며칠 단위. 강한 필터(ACL) 후 결과 부족 심화 | 양자화 + 2단계 재순위, 테넌트·문서 유형별 컬렉션 파티셔닝, 디스크 기반 인덱스 검토, 재임베딩은 배치 창 + 큐 + 블루/그린, 사전 필터 지원 저장소 | 벡터 수 × 차원(메모리), 토큰 수(임베딩 API), 삭제 비율(HNSW 재구축) |
| 사용자·요청 | 질의 시 임베딩 호출의 레이트 리밋, 두 인덱스(BM25 + dense) 동시 검색의 p95 | 질의 임베딩 캐시(정규화 질의 키), 검색 경로 무상태 + 복제본 수평 확장, `ef`/`nprobe`를 부하에 따라 동적 조정 | QPS × k, 질의 임베딩 호출 수 |
| 테넌트 | 단일 인덱스 필터 선택도 저하, 테넌트 간 노이즈 | 테넌트별 컬렉션(수가 적을 때) 또는 파티션 키([10](10-access-control-governance.md)) | 테넌트 수 × 인덱스 수 |

인덱싱 워커와 검색 서버는 **무상태**다. 상태는 인덱스 저장소와 메타데이터 저장소에만 있다. 임베딩 호출은 배치 크기·동시성 상한을 설정으로 두고, 레이트 리밋 응답에는 지수 백오프.

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 임베딩 API 다운 (의존 서비스 다운) | 색인 측: 신규 문서 반영 지연. 검색 측: 의미 검색 불가 | 호출 오류율, 색인 큐 적체, 질의 임베딩 실패율 | 색인은 큐에 보존(백프레셔). 검색은 **BM25 단독 모드**로 저하하고 응답에 `retrieval_mode=keyword_only` 표시 → Part 3 응답을 거쳐 계약 ② 봉투([Part 4/03](../04-dynamic-ui/03-component-registry-schema.md))의 `degradation[]`에 코드 `retrieval_keyword_only`로 **전달**되고, 사용자 고지는 [Part 4/09](../04-dynamic-ui/09-ux-accessibility.md)의 고지 토큰이 맡는다(불균형 ④ 반영) | 다운 예시 10분 초과 → 온콜. 자체 호스팅 폴백 모델이 있으면 **같은 모델일 때만** 전환(다른 모델 벡터는 혼합 금지) |
| 벡터DB 지연 급증 | 검색 p95 상승, 타임아웃 | 저장소 p95, 큐 깊이, 메모리 압박 | 서킷 브레이커 → `ef`/`nprobe` 하향(recall 소폭 희생), k 축소, 최후엔 BM25 단독 | p95가 SLO(예: 300ms) 2배를 5분 지속 |
| recall 회귀 (검증 실패 폭증) | 답변 품질이 조용히 하락 | 골든셋 recall@k 주기 측정(예: 일 1회), 인덱스 파라미터·양자화 변경 직후 측정 | 블루/그린 전환 게이트가 recall 하락(예: 2%p 초과)이면 **전환 차단** | 운영 중 하락이면 최근 변경(모델·파라미터·청킹) 역추적 |
| 임베딩 모델 혼재 (데이터 불일치) | 특정 문서군만 검색이 안 됨 | 인덱스 내 `embedding_model` 종류 수 > 1, 쓰기 거부 로그 | 컬렉션 메타의 허용 모델과 다른 벡터는 **쓰기 거부** | 거부 발생 = 파이프라인 설정 오류. 즉시 |
| 질의 임베딩과 색인 임베딩의 접두(instruction) 불일치 (단계 고유) | recall이 전반적으로 낮음 | 평가셋 recall 급락, 접두 설정 diff | 색인 설정과 질의 설정을 같은 버전 파일에서 읽게 하여 구조적으로 방지 | 발생 시 설정 분리 지점 수정 |
| HNSW 삭제 누적 (단계 고유) | 검색 지연·recall 서서히 악화 | 톰스톤 비율, 세그먼트 수 | 임계(예: 톰스톤 20%) 초과 시 배치 창에서 compaction | compaction이 창 안에 안 끝나면 파티션 분할 검토 |

SLI 후보: ① 골든셋 recall@k(dense·hybrid 각각) ② 검색 p95 지연 ③ 색인 지연(청크 생성 → 검색 가능) ④ 임베딩 모델 일관성(컬렉션 내 모델 종류 = 1). SLO 초안(예시): recall@10 베이스라인 대비 -2%p 이내, p95 ≤ 300ms, 색인 지연 p95 ≤ 신선도 SLO의 절반. 쓰기 행동의 멱등성: upsert 키는 `(chunk_id, embedding_model)`로 같은 청크를 두 번 써도 벡터 하나. 문서 단위 삭제는 `doc_id` 필터 삭제로 멱등([07](07-freshness-and-sync.md)). 배치 실패 시 배치 단위 재시도(상한 예시 3회), 부분 성공은 chunk_id 단위로 재개.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| 임베딩 모델 (이름·버전·차원·접두 규칙) | **전체 벡터**, 질의 임베딩, 청크 크기 기준([02](02-chunking-strategies.md)) | 평가셋 recall@k, 한국어·혼합 언어 하위셋 | 새 인덱스 버전(블루/그린), 질의 측 임베딩 설정, `embedding_model` 메타데이터 |
| BM25 분석기·토크나이저 (형태소 사전 포함) | BM25 인덱스 전체 | 키워드형 평가셋 recall | BM25 재색인, 질의 측 동일 분석기 |
| 인덱스 파라미터 (`M`, `ef`, `nlist`, `nprobe`) · 양자화 설정 | recall·지연·메모리 | 파라미터 변경 전후 recall@k·p95 | 변경은 컬렉션 재구축 또는 런타임 파라미터(저장소 의존) |
| 융합 설정 (RRF 상수, 경로별 top-N, 가중) | 하이브리드 순위 | 평가셋 | Part 3 검색 어댑터 설정 |
| 벡터DB·검색엔진 버전 | 인덱스 포맷 호환, 필터 문법 | 저장소 업그레이드 리허설(복제본) | 어댑터 버전 |
| 필터 필드 매핑 (메타데이터 부분집합) | 사전 필터 가능 범위 | 필터 쿼리 테스트 | 03 복제 필드 목록 |

롤백 단위는 "임베딩 모델 + 청킹 규칙 + 인덱스 버전(별칭) + 질의 측 설정" 묶음이며, 별칭(alias) 전환으로 즉시 되돌릴 수 있어야 한다. 기술 부채로 기록할 것: 양자화 미도입 상태의 메모리 한계 시점, 임베딩 API 단일 벤더 의존(폴백 모델 부재), 필터 후 결과 부족을 k 확대로만 보완하는 범위, multi-vector 미도입 결정과 재검토 조건.

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **지식** (가장 잦음) | 청크 upsert·삭제 | `index.upsert/delete/search` 포트, 검색 결과 스키마(chunk_id + 점수) | — | 증분 upsert(재배포 없음) | 해당 청크만 |
| **모델** (전파 최대) | 임베딩 모델 교체, 벤더 교체, 차원 변경 | `embed(texts, kind=doc/query) → vectors` 포트, 검색 결과 스키마 | 임베딩 어댑터(API / 자체 호스팅) | 어댑터 교체 + **전체 재임베딩 창** + 인덱스 버전 병행(블루/그린) + 평가셋 비교 + 별칭 전환. 두 공간은 절대 혼합하지 않음 | Part 2 Knowledge 전체(청크 크기 재검토 포함) |

| **프로토콜** | 벡터DB 클라이언트 API 변경, 저장소 교체(pgvector → 전용 DB 등) | `index.*` 포트 | 저장소 어댑터 | 어댑터 교체 + 전체 마이그레이션(블루/그린과 동일 절차) | 저장소 경계 + 운영 런북 |
| **부하** | 10배 | 무상태 검색 경로 | 복제본 수, 파티션, 양자화 수준 | 수평 확장 + 양자화 + 파티셔닝 | 인덱스 저장소 |

가장 자주 바뀌는 것: **지식**(증분 upsert) — 비용 없이 흡수. 설계가 좌우하는 것은 **임베딩 모델 교체**다. 벤더 가격·한도 변경, 한국어 품질 개선 모델 등장이 교체를 유발하며, `embed()` 포트 뒤 어댑터 + 인덱스 버전 병행 + 별칭 전환이 없으면 교체가 수개월 프로젝트가 된다. 코드 밖 설정으로 둘 것: 모델 ID·버전·차원·접두 규칙, 인덱스 파라미터, 양자화 수준, RRF 설정, 분석기·사전, 필터 필드 목록, 배치·동시성 상한, 컬렉션별 허용 모델. 포트·어댑터 뒤에 둘 외부 의존: 임베딩 API, 벡터DB, 검색엔진, 리랭커(Part 3). 시점 재현성: 모든 벡터에 `embedding_model` + 인덱스 버전 별칭 이력이 있어야 "그때 어느 인덱스가 서빙했나"를 복원한다.

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성 표의 "탐지 신호"가 **실제로 어디서 나오는지**를 설계한다. 기준은 [Part 1/07 관측성 설계 요소](../01-foundations/07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md). 이 단계는 두 트레이스에 걸친다 — **색인 측**은 문서 단위 트레이스(`index.embed` → `index.upsert`), **검색 측**은 Part 3이 소유하는 `retrieval.search` 스팬이다. 검색 측에서 이 단계가 하는 일은 스팬을 만드는 것이 아니라 **속성을 제공**하는 것(`agent.index_version`, `agent.embedding_model`, `agent.retrieval_mode`)이며, Part 3 지표를 그 속성으로 분해해 읽는다.

| 기록 대상 | 스팬 / 이벤트 (이름, 부모) | 핵심 속성 (버전 키 포함) | 지표 (→ 어느 SLI) | 샘플링 · 보존 · PII |
|---|---|---|---|---|
| 임베딩 호출 (색인) | `index.embed` (부모: 문서 트레이스 `ingest.fetch`), 배치 호출은 자식 `index.embed.call`(`gen_ai.*` 매핑) | `doc_id`, `tenant_id`, `agent.embedding_model`(이름·버전·차원 — 임베딩 버전 키), `agent.embedding.prefix_version`(접두 규칙), `agent.chunk_version`, `agent.pipeline_version`, `agent.batch_size`, `agent.rate_limited`(bool), `agent.retry_count`, `gen_ai.usage.input_tokens`, `agent.cost_estimate`, `agent.queue_wait_ms` | `index.embed.errors{code}` 비율 → "호출 오류율", `index.queue.depth` 게이지 → "색인 큐 적체", `index.embed.tokens{model}` → 대시보드 ③ | 메타 전수. 청크 본문·벡터 값은 기록 금지(청크 ID만). 실패 배치 100% |
| 인덱스 쓰기 | `index.upsert` (부모 `index.embed`) | `agent.index_version`(컬렉션·별칭), `agent.collection_allowed_model`, `agent.upserted_count`, `agent.rejected_count`, `agent.reject_reason`(`model_mismatch` / `chunk_version_mismatch`), `agent.outcome` | `index.upsert.rejected{reason}` 카운터 → "쓰기 거부 로그", `index.collection.embedding_model_distinct` 게이지 → **SLI ④ 모델 일관성**(= 1), `index.lag_ms`(`index.chunk` 시작 → `index.upsert` 완료) → **SLI ③ 색인 지연** | 전수. 거부 건 100% |
| 저장소 상태 | `index.store.health` 주기 이벤트 (부모 없음) | `agent.store_version`, `agent.memory_pressure`, `agent.segment_count`, `agent.tombstone_ratio`, `agent.ann_params{ef,nprobe}` 현재값 | `index.store.p95_ms` → "저장소 p95", `index.store.memory_pressure` → "메모리 압박", `index.tombstone_ratio`·`index.segment_count` → "HNSW 삭제 누적" | 1분 주기(예시). 보존 30일 |
| 설정 정합성 검사 | `index.config.check` 주기 이벤트 (부모 없음) | `agent.index_config_hash`(색인 측 모델·접두), `agent.query_config_hash`(질의 측), `agent.drift`(bool) | `index.config.drift` 게이지(0/1) → "접두 설정 diff" (신규 원천 — 기존 표는 recall 급락으로만 탐지) | 배포 직후 + 10분 주기(예시) |
| 골든셋 평가 | `index.eval` 배치 이벤트 (부모 없음, 전환 시 `sync.switch`에 링크) | `agent.index_version{candidate,baseline}`, `agent.eval_set_version`, `agent.recall_at_k{dense,hybrid}`, `agent.lang_subset`(한국어·혼합) | `index.eval.recall_at_k{mode,lang}` → **SLI ① recall@k**, 탐지 신호 "골든셋 recall 주기 측정·변경 직후 측정" | 일 1회(예시) + 파라미터·양자화 변경 직후. 보존 1년(회귀 추적) |
| 검색 측 속성 제공 | Part 3 `retrieval.search`에 붙는 속성 (이 단계 소유 아님) | `agent.index_version`, `agent.embedding_model`, `agent.retrieval_mode`(hybrid / keyword_only / vector_only), `agent.ann_params_lowered`(bool), `agent.query_embed_cache_hit`, `agent.degradation[]`(`retrieval_keyword_only`) | Part 3 지표 `retrieval.search.duration_ms`를 `agent.index_version`으로 분해 → **SLI ② 검색 p95**, `retrieval.query_embed.errors` → "질의 임베딩 실패율", `retrieval_mode` 분포 → 저하 비율 | Part 3 정책을 따름 |

OTel 매핑: `index.embed.call`은 `gen_ai.operation.name=embeddings`에 대응하지만 컨벤션이 Development 등급이므로 자체 속성(`agent.embedding_model`, `agent.embedding.prefix_version`)을 1차로 두고 매핑 테이블에서 변환한다([Part 5/03](../05-cross-cutting/03-observability-tracing.md)). 접두 규칙 버전은 OTel 쪽에 대응 속성이 없어 자체 속성으로만 남는다.

| 알림 | 조건 (예시) | 심각도 | 런북 (첫 3단계) |
|---|---|---|---|
| 의미 검색 불가 (장애 모드: 임베딩 API 다운) | `index.embed.errors` > 5%가 5분 지속, 또는 `retrieval_mode=keyword_only` 비율 > 50%가 5분 | P2 (10분 초과 P1) | ① 벤더 상태·레이트 리밋 응답 비율 확인 ② 색인 큐가 보존(백프레셔) 중이고 `degradation[]=retrieval_keyword_only`가 계약 ②로 전달되는지 확인 ③ 같은 모델의 자체 호스팅 폴백이 있으면 전환, 없으면 온콜 |
| 검색 지연 (장애 모드: 벡터DB 지연 급증) | `retrieval.search.duration_ms{index_version}` p95 > 600ms(SLO 2배)가 5분 지속 | P1 | ① `index.store.p95_ms`·`memory_pressure`로 저장소 원인 확인 ② 서킷 브레이커 → `ef`/`nprobe` 하향·k 축소가 작동했는지(`ann_params_lowered` 비율) 확인 ③ 복제본 확장 또는 BM25 단독 전환 |
| 조용한 품질 하락 (장애 모드: recall 회귀) | `index.eval.recall_at_k` 베이스라인 대비 −2%p (일 1회 평가), 또는 전환 게이트 차단 발생 | P2 | ① 최근 24시간 내 모델·파라미터·양자화·`chunk_version` 변경 이력 대조 ② 한국어·혼합 하위셋 분해로 범위 확인 ③ 전환 중이면 별칭 롤백([07](07-freshness-and-sync.md)), 운영 중이면 변경 되돌리기 |
| 설정 불일치 (장애 모드: 임베딩 모델 혼재 · 접두 불일치) | `index.upsert.rejected{reason=model_mismatch}` ≥ 1, `embedding_model_distinct` > 1, 또는 `index.config.drift`=1 | P1 | ① 색인·질의 설정 파일 해시 diff로 분리 지점 식별 ② 파이프라인 쓰기 일시 중단 ③ 혼입 벡터 범위 식별 후 삭제·재임베딩 |
| 서서히 악화 (장애 모드: HNSW 삭제 누적) | `index.tombstone_ratio` > 20%, 또는 `segment_count`가 7일 베이스라인 2배 | P3 | ① 다음 배치 창에 compaction 예약 ② compaction 소요 추정이 창을 넘으면 파티션 분할 검토 ③ 삭제 비율 높은 컬렉션의 변경률 원인 확인([07](07-freshness-and-sync.md)) |

대시보드에서 이 단계를 보는 뷰: ② Knowledge 패널 — recall@k 추이(인덱스 버전별), 색인 지연 p95, 색인 큐 깊이, 모델 일관성(컬렉션별 distinct=1), 톰스톤 비율; 검색 p95·`retrieval_mode` 분포는 Retrieval 패널에서 `agent.index_version`으로 분해 / ③ 비용 패널 — 임베딩 토큰 비용(모델별, 색인 vs 질의), 질의 임베딩 캐시 적중률 / 감사 추적으로 넘기는 필드(관측 로그와 분리): 벡터별 `embedding_model`·`embedded_at`, 별칭 전환 이력(시각·평가 결과·승인자), 파라미터·양자화 설정 버전, 저하 모드 진입·해제 시각 — 전환 이력은 `sync.switch` 이벤트에서 감사 저장소로 복사 / 이 단계의 관측이 없으면 못 보는 장애: **질의 측과 색인 측의 임베딩 접두(instruction)가 달라 recall이 전반적으로 낮아진 상태** — 오류도 지연도 없고 두 설정이 각자 "정상"이라, `index.config.drift`나 일 1회 골든셋 평가가 없으면 사용자 불만으로만 드러난다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5, 가역성 × 영향 범위) | 인덱스 쓰기는 **등급 1**(재색인으로 가역). **인덱스 버전 전환(별칭 스위치)**은 등급 2(모든 사용자의 검색 결과 변경, 별칭으로 즉시 롤백 가능) → 규칙 게이트(평가셋 recall) + 1인 승인 |
| 가드레일 위치 (입력 / 출력 / 행동) | **출력**: 검색 결과에 ACL·톰스톤 **사전 필터** 강제(강제 지점 자체는 [10](10-access-control-governance.md)의 게이트웨이). **행동**: 인덱스 전환·컬렉션 삭제·모델 변경은 승인 게이트. 모델 불일치 쓰기 거부는 쓰기 측 규칙 게이트 |
| 게이트 출력 (통과 / 차단 / 승인 / 저하)과 판정 수단 | 전환 게이트: 통과 / 차단(recall 하락) / 승인. 검색 게이트: 통과 / 저하(BM25 단독, 파라미터 하향) / 차단(필터 불가 시 fail-closed). 판정은 **규칙만**(평가셋 수치·설정 일치). 저하 판정은 이 단계가 내리지만 표시 끝점은 Part 4이므로, 저하는 반드시 계약 ② `degradation[]`(`retrieval_keyword_only`)로 전달되어야 "사용자에게 표시"가 성립한다(불균형 ④ 반영) |
| 소유자 (A) — 인덱스 **내용·소스·ACL** | 데이터 소유자. 어떤 문서가 어떤 ACL로 인덱스에 들어가는가([10](10-access-control-governance.md)). [Part 3/01](../03-agent-workflow-rag/01-rag-architecture-patterns.md)·[Part 3/03](../03-agent-workflow-rag/03-retrieval-reranking.md)의 "데이터 소유자(내용·ACL)"와 같은 주체(불균형 ⑨ 반영) |
| 소유자 (A) — 인덱스 **인프라·전환**(블루/그린·별칭·파라미터·저장소) | 데이터 엔지니어링 책임자. AI 엔지니어가 R(불균형 ⑨ 반영) |
| 소유자 (A) — **임베딩 모델 선택·교체** | 아키텍트. AI 엔지니어가 R, 데이터 엔지니어링 책임자가 C(재임베딩 창)(불균형 ⑨ 반영) |
| 감사 추적에 남길 필드 | 벡터별 `embedding_model`·`embedded_at`, 컬렉션 허용 모델, 인덱스 버전 별칭 전환 이력(시각·평가 결과·승인자), 인덱스 파라미터·양자화 설정 버전, 저하 모드 진입·해제 시각 |

### 운영 준비도 체크
- [ ] 임베딩 API 다운 시 BM25 단독 저하 모드가 자동이고 저하 상태가 계약 ② `degradation[]`(`retrieval_keyword_only`)로 전달되는가(불균형 ④ 반영)
- [ ] 컬렉션에 허용 임베딩 모델이 고정되어 다른 모델 벡터의 쓰기가 거부되는가
- [ ] 색인 측과 질의 측 임베딩 설정(모델·접두)이 같은 설정 파일에서 읽히는가
- [ ] 골든셋 recall@k가 주기적으로 측정되고 전환 게이트가 하락 시 차단하는가
- [ ] 인덱스 버전 별칭 전환과 즉시 롤백 절차가 리허설되었는가
- [ ] upsert가 `(chunk_id, embedding_model)` 키로 멱등하고 배치 재시도 상한이 있는가
- [ ] HNSW 톰스톤 비율 알림과 compaction 배치 창이 있는가
- [ ] 임베딩 API 비용 상한·레이트 리밋·백오프가 설정으로 있는가
- [ ] 운영 안정성 표의 탐지 신호마다 원천 스팬·지표(`index.embed.errors`, `index.eval.recall_at_k`, `index.upsert.rejected{reason}`, `index.config.drift`, `index.tombstone_ratio`)가 있고, 검색 측 지표가 `agent.index_version`으로 분해되는가
- [ ] 알림마다 런북이 있고, 설정 불일치(모델 혼재·접두 drift)가 recall 회귀와 별도 알림으로 즉시 잡히는가
