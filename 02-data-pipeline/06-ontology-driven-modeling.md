# 온톨로지 기반 데이터 모델링

> **범위**: 비즈니스 온톨로지 설계 절차, 시맨틱 레이어, 스키마 정렬과 검증(SHACL)
> **시각화**: [`assets/html/kg-construction-pipeline.html`](../assets/html/kg-construction-pipeline.html) — "온톨로지 정렬 / SHACL 검증" 노드

## 요약 (3줄)

1. 이 페이지는 **절차와 산출물**을 다룬다. 온톨로지가 무엇이고 왜 필요한지는 [Part 1/03](../01-foundations/03-knowledge-representation.md)에 있다. 여기서는 "월요일에 무엇부터 하고 금요일에 무엇을 내놓는가"를 적는다.
2. 설계는 **상향식(데이터·질의 로그 → 개념)과 하향식(도메인 전문가·표준 → 스키마)을 번갈아** 한다. 어느 한쪽만 하면 쓰이지 않는 온톨로지(하향식만) 또는 일관성 없는 온톨로지(상향식만)가 나온다.
3. 산출물은 **OWL/SHACL로 정의, LPG 스키마로 운영, 매핑 테이블로 연결**하는 혼합 전략이 기본값이다. 정의와 운영을 한 곳에 두면 둘 중 하나가 금방 낡는다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 용어집(개념·정의·동의어·소유자) ② 클래스·관계·속성 목록(도메인·레인지·카디널리티) ③ 제약(SHACL shapes 또는 코드) ④ 운영 스키마(LPG 라벨·관계 유형·속성) ⑤ 정의 ↔ 운영 매핑 테이블 ⑥ 재사용한 표준 온톨로지와 그 매핑 ⑦ 버전·변경 절차 |
| **언제** (When) | [05](05-knowledge-graph-construction.md)에서 그래프 구축을 결정했을 때, 또는 메타데이터 허용값([03](03-metadata-provenance.md))을 택소노미 이상으로 구조화해야 할 때. **생략**: 그래프도 없고 메타데이터 필터가 평면 택소노미로 충분할 때. **미뤄도 되는 것**: 정식 OWL 공리·추론기(외부 통합·규제 설명이 생길 때) |
| **어떻게** (How) | ① 범위 질문(competency questions) 20~50개 수집 → ② 상향식: 질의 로그·메타데이터·샘플 추출 결과에서 후보 개념 수집 → ③ 하향식: 도메인 전문가 인터뷰 + 표준 온톨로지 재사용 검토 → ④ 핵심 클래스 10~30개, 관계 20~50개로 경량 온톨로지 확정 → ⑤ SHACL shapes 작성 → ⑥ LPG 스키마 변환 + 매핑 테이블 → ⑦ 범위 질문으로 검수 → ⑧ 버전 태그·소유자·변경 절차 |
| **왜** (Why) | 온톨로지 없이 추출하면 관계명 폭발·엔티티 분산([05](05-knowledge-graph-construction.md)). 절차 없이 온톨로지를 만들면 수백 클래스의 아무도 안 쓰는 모델이 되거나, 두 팀이 "고객"을 다르게 정의한 채 그래프에 섞인다. 산출물이 OWL 파일 하나뿐이면 운영 스키마와 금방 어긋난다 |

## 문제와 맥락

온톨로지 프로젝트가 실패하는 전형은 둘이다.

- **하향식 과설계**: 컨설턴트와 전문가가 6개월간 300개 클래스를 정의했지만, 실제 질의는 그중 15개 클래스만 쓰고 추출 LLM은 300개 클래스를 구분하지 못한다
- **상향식 방치**: LLM 추출 결과를 그대로 스키마로 삼아 "근무/소속/재직/일함"이 네 관계로 남고, 부서마다 "고객"의 의미가 다르다

둘 다 **범위 질문(competency questions)이 없어서** 생긴다. "이 온톨로지가 답해야 하는 질문 목록"이 있으면 클래스가 필요한지 아닌지가 판정 가능해진다. 이 페이지의 절차는 범위 질문을 중심에 둔다.

## 핵심 개념

### 상향식과 하향식

| 접근 | 입력 | 산출 | 강점 | 약점 |
|---|---|---|---|---|
| **상향식** (데이터 → 개념) | 질의 로그, 기존 메타데이터·DB 스키마, 샘플 문서의 LLM 추출 결과 클러스터링 | 실제로 등장하는 개념·관계 후보와 빈도 | 쓰이는 것만 모델링, 빠름 | 명명 비일관, 도메인 전문가가 아는 암묵 개념 누락 |
| **하향식** (도메인 → 스키마) | 전문가 인터뷰, 업무 규정, 표준 온톨로지(산업·공통) | 일관된 개념 체계, 정의, 제약 | 일관성·설명 가능 | 과설계, 실제 데이터와 괴리 |
| **번갈아** (권장) | 상향식 후보 → 하향식 정리 → 상향식 검증 | 쓰이면서 일관된 경량 온톨로지 | 둘의 약점 상쇄 | 두 역할(데이터 엔지니어 + 도메인 전문가) 모두 필요 |

### 경량 vs 정식

| 항목 | 경량 온톨로지 | 정식 온톨로지 |
|---|---|---|
| 표현 | 클래스 계층, 관계(도메인·레인지), 필수 속성, 열거형 | + 공리(동치·분리·전이·역관계), 복잡 제약, 추론 규칙 |
| 도구 | 스프레드시트 → YAML/JSON-LD → SHACL | OWL 편집기, 추론기(reasoner), 트리플스토어 |
| 기간(정성) | 수 주 | 수 개월 |
| 쓰임 | 추출 스키마, 메타데이터 허용값, LPG 스키마, 검증 | + 자동 추론, 외부 온톨로지 통합, 규제 설명 |
| 시작점 | 거의 모든 에이전트 프로젝트 | 의료·금융 등 표준 온톨로지가 사실상 요구되는 도메인 |

**경량으로 시작해 정식이 필요한 부분만 승격**한다. 승격 신호는 "외부 데이터와 통합해야 한다", "추론으로만 답할 수 있는 질문이 있다", "규제가 설명을 요구한다"의 셋이다.

### 혼합 전략: 정의는 OWL/SHACL, 운영은 LPG

```
[정의 계층: 단일 진실 원천]            [변환]                    [운영 계층]
 OWL/RDFS: 클래스·관계·속성 ──▶ 자동 변환 스크립트 ──▶ LPG 라벨·관계 유형·속성 키
 SHACL shapes: 제약 ───────────▶ 변환 또는 수동 ───▶ DB 제약 + 애플리케이션 검증 코드
 SKOS: 택소노미·동의어 ────────▶ 그대로 ──────────▶ 메타데이터 허용값, 엔티티 해소 별칭 사전
 매핑 테이블: 정의 ID ↔ 운영 이름 ↔ 추출 프롬프트 레이블 ↔ UI 표시명
```

정의 계층을 바꾸면 변환을 다시 돌려 운영 계층을 갱신한다. 반대 방향(운영에서 임의로 라벨 추가)은 금지하고, 필요하면 정의 계층에 변경 요청을 낸다. **매핑 테이블**이 이 전략의 핵심 산출물이다. 추출 프롬프트의 레이블, DB의 라벨, UI의 한국어 표시명이 한 행에 묶여 있어야 어긋남을 발견할 수 있다.

### 표준 온톨로지 재사용

| 표준 | 범위 | 재사용 방식 |
|---|---|---|
| **SKOS** | 택소노미·동의어·계층 | 문서 유형·주제 분류의 어휘로 그대로 |
| **PROV-O** | 계보 | 메타데이터 계보 축([03](03-metadata-provenance.md)) |
| **Dublin Core** | 문서 기술 메타데이터(제목·저자·날짜) | 문서 노드 속성명 |
| **schema.org** | 범용(조직·사람·제품·이벤트) | 공통 클래스의 상위 개념으로 정렬 |
| **산업 표준** (FIBO 금융, SNOMED CT 의료 등) | 도메인 | 도메인 클래스를 표준에 매핑, 필요한 부분집합만 |

재사용은 "통째로 가져오기"가 아니라 **필요한 클래스·속성만 골라 자기 온톨로지에서 참조**하는 것이다. 표준 전체를 들여오면 경량 원칙이 깨진다. 모든 표준은 W3C 권고안 또는 해당 기관의 공식 명세로 `[검증]` 가능하다.

### 버전·거버넌스

| 항목 | 규칙 |
|---|---|
| 소유자 | 온톨로지 전체와 각 클래스군에 **도메인 소유자** 지정. 기술 팀은 관리자지 소유자가 아님 |
| 버전 | 시맨틱 버전. 클래스 삭제·관계 개명·레인지 변경은 메이저(그래프 마이그레이션 필요), 추가는 마이너 |
| 변경 절차 | 변경 요청 → 범위 질문으로 필요성 판정 → 영향 범위(추출 프롬프트, 검증기, 그래프, UI) 산정 → 변환 재실행 → 마이그레이션 |
| 기록 | 변경 로그에 "왜"를 적는다. 트리플 메타데이터에 온톨로지 버전 기록([03](03-metadata-provenance.md)) |
| 검수 | 범위 질문 전체를 릴리스마다 재실행. 답 못 하는 질문이 생기면 회귀 |

## 아키텍처 / 파이프라인

```
범위 질문 수집 ─▶ 상향식 후보 (질의 로그 · DB 스키마 · 추출 클러스터) ─┐
                                                                        ├─▶ 경량 온톨로지 초안 (클래스 ≤ 30, 관계 ≤ 50)
표준 온톨로지 선별 + 전문가 인터뷰 (하향식) ───────────────────────────┘
        ▼
SHACL shapes + 매핑 테이블 ─▶ 변환 ─▶ LPG 스키마 · 추출 프롬프트 레이블 · 메타데이터 허용값 · UI 표시명
        ▼
범위 질문으로 검수 ─▶ 버전 태그 ─▶ [05 추출 정렬] [03 메타데이터] [08 근거 단위] [Part 4/05 UI 매핑]
        ▲
변경 요청 루프 (추출 미분류 버킷 · 새 질의 유형 · 전문가 피드백)
```

입력은 범위 질문과 데이터·전문가·표준, 출력은 **정의 파일 + 운영 스키마 + 매핑 테이블 + 버전**이다. 미분류 버킷([05](05-knowledge-graph-construction.md))이 가장 좋은 변경 요청 공급원이다.

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 상향식만 (데이터 → 개념) | 탐색 초기, 전문가 접근 불가, 빠른 PoC | 운영 스키마 확정, 멀티 팀 일관성 | 하 | 안정 | `[2차]` |
| 하향식만 (전문가·표준 → 스키마) | 표준이 사실상 강제되는 도메인(의료·금융) | 데이터 실체와 괴리 위험, 빠른 반복 | 상 | 표준(방법론) | `[2차]` 과설계 실패 사례 다수 |
| 번갈아 (상향식 ↔ 하향식, 범위 질문 중심) | 대부분의 엔터프라이즈 에이전트 | 두 역할을 확보 못 할 때 | 중 | 안정 | `[2차]` 온톨로지 공학 방법론 일반 |
| 경량 온톨로지 (YAML/JSON-LD + SHACL) | 거의 모든 시작점. 추출 스키마·검증·메타데이터 어휘 | 자동 추론·외부 통합 필요 | 중 | 안정 | `[검증]` SHACL 표준 |
| 정식 OWL + 추론기 + 트리플스토어 | 외부 온톨로지 통합, 추론 필요, 규제 설명 | 소규모 팀, 빠른 반복, RDF 경험 없음 | 상 | 표준(W3C) | `[검증]` |
| 혼합 (OWL/SHACL 정의 + LPG 운영 + 매핑 테이블) | 개발 속도와 장기 상호운용을 모두 원할 때 | 변환 자동화를 유지할 여력 없음 | 중~상 | 안정 | `[2차]` |
| 표준 온톨로지 부분 재사용 | 공통 개념(조직·사람·문서·계보), 산업 표준 존재 | 표준이 없는 사내 고유 개념(직접 정의) | 하~중 | 표준 | `[검증]` 표준 문서 |
| LPG 스키마만 (정의 계층 없음) | 단일 팀, 단기, 외부 통합 없음 | 멀티 팀, 규제, 추출 스키마와 UI 어휘 동기화 필요 | 하(초기) / 상(유지) | 안정 | `[2차]` 어휘 드리프트 보고 |
| 시맨틱 레이어 (BI형 지표·차원 정의) | 정형 데이터 중심, Text-to-SQL 에이전트 | 비정형 문서 중심 | 중 | 신생(에이전트 용도) | `[2차]` |

### 선택 가이드

- **그래프도 없고 필터가 평면 분류로 충분하다면** → 택소노미(SKOS)만. 이유: 온톨로지 유지 비용을 정당화할 질문이 없다
- **그래프 구축을 결정했고 내부용이라면** → 번갈아 설계 + 경량 온톨로지 + 혼합 운영. 이유: 추출 스키마·검증·UI 어휘를 한 원천에서 유지
- **의료·금융처럼 산업 표준 온톨로지가 있다면** → 하향식 비중을 높이고 표준 부분집합 재사용, 정식 승격 검토. 이유: 외부 통합·규제 설명이 거의 확실히 온다
- **정형 데이터 중심에 Text-to-SQL이 핵심이라면** → 시맨틱 레이어 형태로 지표·차원·관계 정의. 이유: 테이블이 아니라 비즈니스 개념을 노출하는 것이 온톨로지의 실용 형태
- **판단이 어려우면** → 기본값: 범위 질문 30개 → 경량 온톨로지(클래스 ≤ 30) → SHACL → LPG 변환 + 매핑 테이블 → 소유자 지정. 이유: 어느 방향으로도 확장 가능하고 수 주 안에 끝난다

## 설계 시 고려사항 (체크리스트)

- [ ] 범위 질문(competency questions) 20~50개를 수집했고 각 클래스·관계가 최소 하나의 질문에 대응하는가
- [ ] 상향식 후보(질의 로그·DB 스키마·추출 클러스터)와 하향식 정리(전문가·표준)를 모두 거쳤는가
- [ ] 핵심 클래스 30개 이내, 모든 관계에 도메인·레인지가 있는가
- [ ] 각 클래스에 한국어 정의 1~2문장과 동의어·금지어가 있는가(추출 프롬프트와 UI가 공유)
- [ ] 제약을 SHACL shapes 또는 코드로 작성했고 추출 결과에 실제로 적용되는가([05](05-knowledge-graph-construction.md))
- [ ] 정의 ↔ LPG ↔ 추출 레이블 ↔ UI 표시명 매핑 테이블이 있는가
- [ ] 재사용한 표준 온톨로지의 부분집합과 매핑을 기록했는가
- [ ] 도메인 소유자가 지정되어 있고 변경 요청 절차가 있는가
- [ ] 버전 규칙(메이저 = 마이그레이션 필요)이 있고 트리플·메타데이터에 버전이 기록되는가
- [ ] 미분류 버킷·새 질의 유형이 변경 요청으로 흘러드는 경로가 있는가
- [ ] 릴리스마다 범위 질문 전체를 재검수하는가

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 도메인 전문가의 시간 확보 | 하향식이 멈추고 상향식만 진행 → 비일관 | 인터뷰를 범위 질문 검토 1~2시간 세션으로 압축, 비동기 검토 |
| 두 팀의 같은 용어 다른 의미 | "고객"이 영업·CS에서 다름 → 그래프 오염 | 용어집에 맥락별 정의, 필요 시 클래스 분리(`SalesCustomer`/`SupportCustomer`) + 상위 클래스 |
| 정의와 운영의 드리프트 | OWL은 낡고 LPG만 바뀜 | 운영 계층 직접 수정 금지, 변환 자동화, CI에서 불일치 검사 |
| 과설계 회귀 | 경량으로 시작했다가 클래스가 100개로 | 범위 질문 없는 클래스 추가 금지, 분기별 사용률 점검 |
| LLM이 스키마를 못 따름 | 클래스가 많거나 정의가 모호하면 추출 위반율↑ | 클래스 수 제한, 정의에 예시 포함, 위반율을 온톨로지 품질 지표로 |
| 표준 온톨로지의 무게 | 전체 들여오면 수천 클래스 | 부분집합 재사용, 참조만 |
| 효과의 독립 측정 부재 | 온톨로지 유무에 따른 품질 차이 벤치마크 드묾 | 자체 골든셋 `[실측]`, 추출 위반율·엔티티 분산도를 대리 지표로 |
