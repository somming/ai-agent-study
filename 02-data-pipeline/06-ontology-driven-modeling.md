# 온톨로지 기반 데이터 모델링

> **범위**: 비즈니스 온톨로지 설계 절차, 시맨틱 레이어, 스키마 정렬과 검증(SHACL)
> **시각화**: [`assets/html/kg-construction-pipeline.html`](../assets/html/kg-construction-pipeline.html) — "온톨로지 정렬 / SHACL 검증" 노드

## 요약 (3줄)

1. 이 페이지는 **절차와 산출물**을 다룬다. 온톨로지가 무엇이고 왜 필요한지는 [Part 1/03](../01-foundations/03-knowledge-representation.md)에 있다. 여기서는 "월요일에 무엇부터 하고 금요일에 무엇을 내놓는가"를 적는다.
2. 설계는 **상향식(데이터·질의 로그 → 개념)과 하향식(도메인 전문가·표준 → 스키마)을 번갈아** 한다. 어느 한쪽만 하면 쓰이지 않는 온톨로지(하향식만) 또는 일관성 없는 온톨로지(상향식만)가 나온다.
3. 산출물은 **OWL/SHACL로 정의, LPG 스키마로 운영, 매핑 테이블로 연결**하는 혼합 전략이 기본값이다. 정의와 운영을 한 곳에 두면 둘 중 하나가 금방 낡는다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 용어집(개념·정의·동의어·소유자) ② 클래스·관계·속성 목록(도메인·레인지·카디널리티) ③ 제약(SHACL shapes 또는 코드) ④ 운영 스키마(LPG 라벨·관계 유형·속성) ⑤ 정의 ↔ 운영 매핑 테이블 ⑥ 재사용한 표준 온톨로지와 그 매핑 ⑦ 버전·변경 절차 |
| **언제** (When) | [05](05-knowledge-graph-construction.md)에서 그래프 구축을 결정했을 때, 또는 메타데이터 허용값([03](03-metadata-provenance.md))을 택소노미 이상으로 구조화해야 할 때. **생략**: 그래프도 없고 메타데이터 필터가 평면 택소노미로 충분할 때. **미뤄도 되는 것**: 정식 OWL 공리·추론기(외부 통합·규제 설명이 생길 때) |
| **어떻게** (How) | ① 범위 질문(competency questions) 20~50개 수집 → ② 상향식: 질의 로그·메타데이터·샘플 추출 결과에서 후보 개념 수집 → ③ 하향식: 도메인 전문가 인터뷰 + 표준 온톨로지 재사용 검토 → ④ 핵심 클래스 10~30개, 관계 20~50개로 경량 온톨로지 확정 → ⑤ SHACL shapes 작성 → ⑥ LPG 스키마 변환 + 매핑 테이블 → ⑦ 범위 질문으로 검수 → ⑧ 버전 태그·소유자·변경 절차 |
| **왜** (Why) | 온톨로지 없이 추출하면 관계명 폭발·엔티티 분산([05](05-knowledge-graph-construction.md)). 절차 없이 온톨로지를 만들면 수백 클래스의 아무도 안 쓰는 모델이 되거나, 두 팀이 "고객"을 다르게 정의한 채 그래프에 섞인다. 산출물이 OWL 파일 하나뿐이면 운영 스키마와 금방 어긋난다 |

## 문제와 맥락

온톨로지 프로젝트가 실패하는 전형은 둘이다.

- **하향식 과설계**: 컨설턴트와 전문가가 6개월간 300개 클래스를 정의했지만, 실제 질의는 그중 15개 클래스만 쓰고 추출 LLM은 300개 클래스를 구분하지 못한다
- **상향식 방치**: LLM 추출 결과를 그대로 스키마로 삼아 "근무/소속/재직/일함"이 네 관계로 남고, 부서마다 "고객"의 의미가 다르다

둘 다 **범위 질문(competency questions)이 없어서** 생긴다. "이 온톨로지가 답해야 하는 질문 목록"이 있으면 클래스가 필요한지 아닌지가 판정 가능해진다. 이 페이지의 절차는 범위 질문을 중심에 둔다.

## 핵심 개념

### 상향식과 하향식

| 접근 | 입력 | 산출 | 강점 | 약점 |
|---|---|---|---|---|
| **상향식** (데이터 → 개념) | 질의 로그, 기존 메타데이터·DB 스키마, 샘플 문서의 LLM 추출 결과 클러스터링 | 실제로 등장하는 개념·관계 후보와 빈도 | 쓰이는 것만 모델링, 빠름 | 명명 비일관, 도메인 전문가가 아는 암묵 개념 누락 |
| **하향식** (도메인 → 스키마) | 전문가 인터뷰, 업무 규정, 표준 온톨로지(산업·공통) | 일관된 개념 체계, 정의, 제약 | 일관성·설명 가능 | 과설계, 실제 데이터와 괴리 |
| **번갈아** (권장) | 상향식 후보 → 하향식 정리 → 상향식 검증 | 쓰이면서 일관된 경량 온톨로지 | 둘의 약점 상쇄 | 두 역할(데이터 엔지니어 + 도메인 전문가) 모두 필요 |

### 경량 vs 정식

| 항목 | 경량 온톨로지 | 정식 온톨로지 |
|---|---|---|
| 표현 | 클래스 계층, 관계(도메인·레인지), 필수 속성, 열거형 | + 공리(동치·분리·전이·역관계), 복잡 제약, 추론 규칙 |
| 도구 | 스프레드시트 → YAML/JSON-LD → SHACL | OWL 편집기, 추론기(reasoner), 트리플스토어 |
| 기간(정성) | 수 주 | 수 개월 |
| 쓰임 | 추출 스키마, 메타데이터 허용값, LPG 스키마, 검증 | + 자동 추론, 외부 온톨로지 통합, 규제 설명 |
| 시작점 | 거의 모든 에이전트 프로젝트 | 의료·금융 등 표준 온톨로지가 사실상 요구되는 도메인 |

**경량으로 시작해 정식이 필요한 부분만 승격**한다. 승격 신호는 "외부 데이터와 통합해야 한다", "추론으로만 답할 수 있는 질문이 있다", "규제가 설명을 요구한다"의 셋이다.

### 혼합 전략: 정의는 OWL/SHACL, 운영은 LPG

```
[정의 계층: 단일 진실 원천]            [변환]                    [운영 계층]
 OWL/RDFS: 클래스·관계·속성 ──▶ 자동 변환 스크립트 ──▶ LPG 라벨·관계 유형·속성 키
 SHACL shapes: 제약 ───────────▶ 변환 또는 수동 ───▶ DB 제약 + 애플리케이션 검증 코드
 SKOS: 택소노미·동의어 ────────▶ 그대로 ──────────▶ 메타데이터 허용값, 엔티티 해소 별칭 사전
 매핑 테이블: 정의 ID ↔ 운영 이름 ↔ 추출 프롬프트 레이블 ↔ UI 표시명
```

정의 계층을 바꾸면 변환을 다시 돌려 운영 계층을 갱신한다. 반대 방향(운영에서 임의로 라벨 추가)은 금지하고, 필요하면 정의 계층에 변경 요청을 낸다. **매핑 테이블**이 이 전략의 핵심 산출물이다. 추출 프롬프트의 레이블, DB의 라벨, UI의 한국어 표시명이 한 행에 묶여 있어야 어긋남을 발견할 수 있다.

### 표준 온톨로지 재사용

| 표준 | 범위 | 재사용 방식 |
|---|---|---|
| **SKOS** | 택소노미·동의어·계층 | 문서 유형·주제 분류의 어휘로 그대로 |
| **PROV-O** | 계보 | 메타데이터 계보 축([03](03-metadata-provenance.md)) |
| **Dublin Core** | 문서 기술 메타데이터(제목·저자·날짜) | 문서 노드 속성명 |
| **schema.org** | 범용(조직·사람·제품·이벤트) | 공통 클래스의 상위 개념으로 정렬 |
| **산업 표준** (FIBO 금융, SNOMED CT 의료 등) | 도메인 | 도메인 클래스를 표준에 매핑, 필요한 부분집합만 |

재사용은 "통째로 가져오기"가 아니라 **필요한 클래스·속성만 골라 자기 온톨로지에서 참조**하는 것이다. 표준 전체를 들여오면 경량 원칙이 깨진다. 모든 표준은 W3C 권고안 또는 해당 기관의 공식 명세로 `[검증]` 가능하다.

### 버전·거버넌스

| 항목 | 규칙 |
|---|---|
| 소유자 | 온톨로지 전체와 각 클래스군에 **도메인 소유자** 지정. 기술 팀은 관리자지 소유자가 아님 |
| 버전 | 시맨틱 버전. 클래스 삭제·관계 개명·레인지 변경은 메이저(그래프 마이그레이션 필요), 추가는 마이너 |
| 변경 절차 | 변경 요청 → 범위 질문으로 필요성 판정 → 영향 범위(추출 프롬프트, 검증기, 그래프, UI) 산정 → 변환 재실행 → 마이그레이션 |
| 기록 | 변경 로그에 "왜"를 적는다. 트리플 메타데이터에 온톨로지 버전 기록([03](03-metadata-provenance.md)) |
| 검수 | 범위 질문 전체를 릴리스마다 재실행. 답 못 하는 질문이 생기면 회귀 |

## 아키텍처 / 파이프라인

```
범위 질문 수집 ─▶ 상향식 후보 (질의 로그 · DB 스키마 · 추출 클러스터) ─┐
                                                                        ├─▶ 경량 온톨로지 초안 (클래스 ≤ 30, 관계 ≤ 50)
표준 온톨로지 선별 + 전문가 인터뷰 (하향식) ───────────────────────────┘
        ▼
SHACL shapes + 매핑 테이블 ─▶ 변환 ─▶ LPG 스키마 · 추출 프롬프트 레이블 · 메타데이터 허용값 · UI 표시명
        ▼
범위 질문으로 검수 ─▶ 버전 태그 ─▶ [05 추출 정렬] [03 메타데이터] [08 근거 단위] [Part 4/05 UI 매핑]
        ▲
변경 요청 루프 (추출 미분류 버킷 · 새 질의 유형 · 전문가 피드백)
```

입력은 범위 질문과 데이터·전문가·표준, 출력은 **정의 파일 + 운영 스키마 + 매핑 테이블 + 버전**이다. 미분류 버킷([05](05-knowledge-graph-construction.md))이 가장 좋은 변경 요청 공급원이다.

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 상향식만 (데이터 → 개념) | 탐색 초기, 전문가 접근 불가, 빠른 PoC | 운영 스키마 확정, 멀티 팀 일관성 | 하 | 안정 | `[2차]` |
| 하향식만 (전문가·표준 → 스키마) | 표준이 사실상 강제되는 도메인(의료·금융) | 데이터 실체와 괴리 위험, 빠른 반복 | 상 | 표준(방법론) | `[2차]` 과설계 실패 사례 다수 |
| 번갈아 (상향식 ↔ 하향식, 범위 질문 중심) | 대부분의 엔터프라이즈 에이전트 | 두 역할을 확보 못 할 때 | 중 | 안정 | `[2차]` 온톨로지 공학 방법론 일반 |
| 경량 온톨로지 (YAML/JSON-LD + SHACL) | 거의 모든 시작점. 추출 스키마·검증·메타데이터 어휘 | 자동 추론·외부 통합 필요 | 중 | 안정 | `[검증]` SHACL 표준 |
| 정식 OWL + 추론기 + 트리플스토어 | 외부 온톨로지 통합, 추론 필요, 규제 설명 | 소규모 팀, 빠른 반복, RDF 경험 없음 | 상 | 표준(W3C) | `[검증]` |
| 혼합 (OWL/SHACL 정의 + LPG 운영 + 매핑 테이블) | 개발 속도와 장기 상호운용을 모두 원할 때 | 변환 자동화를 유지할 여력 없음 | 중~상 | 안정 | `[2차]` |
| 표준 온톨로지 부분 재사용 | 공통 개념(조직·사람·문서·계보), 산업 표준 존재 | 표준이 없는 사내 고유 개념(직접 정의) | 하~중 | 표준 | `[검증]` 표준 문서 |
| LPG 스키마만 (정의 계층 없음) | 단일 팀, 단기, 외부 통합 없음 | 멀티 팀, 규제, 추출 스키마와 UI 어휘 동기화 필요 | 하(초기) / 상(유지) | 안정 | `[2차]` 어휘 드리프트 보고 |
| 시맨틱 레이어 (BI형 지표·차원 정의) | 정형 데이터 중심, Text-to-SQL 에이전트 | 비정형 문서 중심 | 중 | 신생(에이전트 용도) | `[2차]` |

### 선택 가이드

- **그래프도 없고 필터가 평면 분류로 충분하다면** → 택소노미(SKOS)만. 이유: 온톨로지 유지 비용을 정당화할 질문이 없다
- **그래프 구축을 결정했고 내부용이라면** → 번갈아 설계 + 경량 온톨로지 + 혼합 운영. 이유: 추출 스키마·검증·UI 어휘를 한 원천에서 유지
- **의료·금융처럼 산업 표준 온톨로지가 있다면** → 하향식 비중을 높이고 표준 부분집합 재사용, 정식 승격 검토. 이유: 외부 통합·규제 설명이 거의 확실히 온다
- **정형 데이터 중심에 Text-to-SQL이 핵심이라면** → 시맨틱 레이어 형태로 지표·차원·관계 정의. 이유: 테이블이 아니라 비즈니스 개념을 노출하는 것이 온톨로지의 실용 형태
- **판단이 어려우면** → 기본값: 범위 질문 30개 → 경량 온톨로지(클래스 ≤ 30) → SHACL → LPG 변환 + 매핑 테이블 → 소유자 지정. 이유: 어느 방향으로도 확장 가능하고 수 주 안에 끝난다

## 설계 시 고려사항 (체크리스트)

- [ ] 범위 질문(competency questions) 20~50개를 수집했고 각 클래스·관계가 최소 하나의 질문에 대응하는가
- [ ] 상향식 후보(질의 로그·DB 스키마·추출 클러스터)와 하향식 정리(전문가·표준)를 모두 거쳤는가
- [ ] 핵심 클래스 30개 이내, 모든 관계에 도메인·레인지가 있는가
- [ ] 각 클래스에 한국어 정의 1~2문장과 동의어·금지어가 있는가(추출 프롬프트와 UI가 공유)
- [ ] 제약을 SHACL shapes 또는 코드로 작성했고 추출 결과에 실제로 적용되는가([05](05-knowledge-graph-construction.md))
- [ ] 정의 ↔ LPG ↔ 추출 레이블 ↔ UI 표시명 매핑 테이블이 있는가
- [ ] 재사용한 표준 온톨로지의 부분집합과 매핑을 기록했는가
- [ ] 도메인 소유자가 지정되어 있고 변경 요청 절차가 있는가
- [ ] 버전 규칙(메이저 = 마이그레이션 필요)이 있고 트리플·메타데이터에 버전이 기록되는가
- [ ] 미분류 버킷·새 질의 유형이 변경 요청으로 흘러드는 경로가 있는가
- [ ] 릴리스마다 범위 질문 전체를 재검수하는가

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 도메인 전문가의 시간 확보 | 하향식이 멈추고 상향식만 진행 → 비일관 | 인터뷰를 범위 질문 검토 1~2시간 세션으로 압축, 비동기 검토 |
| 두 팀의 같은 용어 다른 의미 | "고객"이 영업·CS에서 다름 → 그래프 오염 | 용어집에 맥락별 정의, 필요 시 클래스 분리(`SalesCustomer`/`SupportCustomer`) + 상위 클래스 |
| 정의와 운영의 드리프트 | OWL은 낡고 LPG만 바뀜 | 운영 계층 직접 수정 금지, 변환 자동화, CI에서 불일치 검사 |
| 과설계 회귀 | 경량으로 시작했다가 클래스가 100개로 | 범위 질문 없는 클래스 추가 금지, 분기별 사용률 점검 |
| LLM이 스키마를 못 따름 | 클래스가 많거나 정의가 모호하면 추출 위반율↑ | 클래스 수 제한, 정의에 예시 포함, 위반율을 온톨로지 품질 지표로 |
| 표준 온톨로지의 무게 | 전체 들여오면 수천 클래스 | 부분집합 재사용, 참조만 |
| 효과의 독립 측정 부재 | 온톨로지 유무에 따른 품질 차이 벤치마크 드묾 | 자체 골든셋 `[실측]`, 추출 위반율·엔티티 분산도를 대리 지표로 |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 온톨로지는 런타임 서비스가 아니라 **버전 있는 설정 아티팩트**다. 따라서 이 단계의 "운영"은 처리량이 아니라 **릴리스 절차**(검수·변환·마이그레이션·롤백)와 **다른 단계로의 전파 통제**다. 버전·거버넌스 규칙 자체는 [핵심 개념 — 버전·거버넌스] 참조.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 도메인·클래스 수 (이 단계의 "데이터") | 클래스 300개면 추출 LLM이 구분 못 해 위반율↑, 매핑 테이블이 수천 행, 범위 질문 재검수가 릴리스마다 며칠 | 모듈화(공통 코어 + 도메인 모듈), 모듈별 클래스 상한, 문서 유형별 스키마 부분집합만 추출에 주입([05](05-knowledge-graph-construction.md)), 범위 질문을 자동 테스트로 | 클래스·관계 수 × 소비자 수(프롬프트·SHACL·LPG·UI·enum) |
| 팀·기여자 수 | 두 팀이 같은 용어를 다르게 정의, 변경 요청 충돌, 소유자 부재 행 | 클래스군별 도메인 소유자, 변경 요청 큐 단일화, 네임스페이스로 팀 영역 분리, CI에서 정의↔운영 불일치 검사 | 기여 팀 수 × 변경 빈도 |
| 테넌트 | 테넌트별 확장 클래스 요구가 코어를 오염 | 코어는 공통, 테넌트 확장은 별도 네임스페이스 + 코어 클래스에 `subClassOf`로만 연결 | 테넌트 수 × 확장 클래스 수 |
| 데이터 (문서·트리플 수) | 온톨로지 메이저 변경 시 그래프 마이그레이션 시간 | 매핑 테이블로 라벨 이전(재추출 없음) 범위 극대화, 재추출은 영향 클래스만 | 영향 트리플 수 |

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 변환 스크립트·도구 체인 실패 (의존 서비스 다운) | 새 온톨로지 버전이 운영 계층에 반영 안 됨 | CI 변환 단계 실패 | 이전 버전 고정 유지(소비자는 영향 없음). 릴리스 차단 | 변환 실패가 정의 오류(순환·레인지 불일치)인지 도구 문제인지 구분 |
| 릴리스 후 추출 위반율 급등 (검증 실패 폭증) | 미분류 버킷 급증, 그래프 신규 적재 정체 | [05](05-knowledge-graph-construction.md)의 위반율이 릴리스 직후 급변 | 온톨로지 버전 **롤백**(매핑 테이블 역방향 적용, 소비자 설정을 이전 버전으로) | 위반 유형이 특정 클래스 정의에 집중되면 정의·예시 보강 후 재릴리스 |
| 정의 ↔ 운영 드리프트 (데이터 불일치) | UI 라벨·추출 레이블·DB 라벨이 서로 다름, 필터 결과 누락 | CI 불일치 검사 건수, 운영 LPG에 정의 없는 라벨 출현 | 운영 계층 직접 수정 금지(쓰기 권한 분리). 불일치 라벨은 `unmapped`로 표시하고 변경 요청 자동 생성 | 불일치 1건이라도 릴리스 차단 |
| 범위 질문 회귀 (단계 고유) | 전에 답하던 질문 유형을 못 답함 | 릴리스 테스트에서 범위 질문 실패 | 릴리스 차단 | 실패 질문이 의도된 폐기인지 확인 후 질문 세트 갱신 |
| 소유자 부재·승인 지연 (단계 고유) | 변경 요청 적체, 미분류 버킷 누적 | 승인 대기 시간, 버킷 크기 | 승인 타임아웃 = **거부**(기본), 요청은 큐에 보존 | 대기가 예시 2주 초과 → 대리 승인자 에스컬레이션 |
| 미분류 버킷 누적 (단계 고유) | 새 개념이 그래프·필터에 안 잡힘 | 버킷 비율(예: 신규 트리플의 2% 초과) | 버킷 상위 빈도 항목을 변경 요청으로 자동 승격 | 분기 점검에서 사용률 낮은 클래스 폐기 검토(과설계 회귀 방지) |

SLI 후보: ① 범위 질문 통과율(릴리스마다) ② 미분류 버킷 비율 ③ 정의↔운영 불일치 건수 ④ 추출 위반율(대리 지표, [05](05-knowledge-graph-construction.md)와 공유). SLO 초안(예시): 범위 질문 100% 통과(실패 시 릴리스 불가), 버킷 ≤ 2%, 불일치 0건. 쓰기 행동의 멱등성: 변환은 결정론적(같은 정의 파일 → 같은 LPG 스키마·매핑 테이블). 마이그레이션 스크립트는 재실행 가능(이미 이전된 라벨은 건너뜀). 라벨 이전은 매핑 테이블 역방향으로 되돌릴 수 있어야 하며, 되돌릴 수 없는 변경(클래스 분할 후 재추출)은 블루/그린 그래프로.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| 온톨로지 정의 (클래스·관계·속성, 시맨틱 버전) | 추출 스키마, SHACL, LPG 스키마, 메타데이터 허용값, 결정 enum([09](09-ai-inside-the-pipeline.md)), UI 표시명 | 범위 질문 전체, 변환 결과 diff, 추출 샘플 위반율 | 아래 전부가 **하나의 릴리스 번들** |
| SHACL shapes | 적재 통과율 | 골든 트리플셋 | 05 검증기 설정 |
| 매핑 테이블 (정의 ID ↔ LPG ↔ 추출 레이블 ↔ UI 표시명 ↔ enum) | 모든 소비자의 어휘 | 매핑 완전성(모든 정의 ID에 행 존재), 왕복 테스트 | 05 프롬프트 레이블, 03 택소노미, Part 4 라벨 |
| 변환 스크립트 | 운영 스키마 생성 | 변환 결정론 테스트 | 도구 체인 버전 고정 |
| 재사용 표준 부분집합 (SKOS·PROV-O·schema.org·산업 표준의 버전) | 외부 상호운용 | 표준 버전 업 시 매핑 재검 | 표준 매핑 테이블 |
| 범위 질문 세트 | 검수 기준 | 세트 자체의 커버리지(모든 클래스가 ≥1 질문) | 릴리스 테스트 |

롤백 단위는 "온톨로지 버전 + SHACL + 매핑 테이블 + 변환 산출물" 번들이며, 소비자(05·03·09·Part 4)는 번들 버전 하나를 참조한다. 기술 부채로 기록할 것: 정식 OWL 공리·추론기 미도입 결정과 승격 신호, 변환이 수동인 부분(SHACL → 애플리케이션 검증 코드), 사용률 점검 미실시 클래스, 표준 온톨로지 버전 고정 상태.

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

이 단계는 **다른 단계의 도메인 모델 변화를 흡수해 주는 경계**다. 따라서 여기서는 "도메인 모델 자체가 바뀔 때 어디서 멈추게 하는가"가 핵심이다.

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **도메인 모델** (가장 잦음, 이 단계의 본업) | 클래스·관계 추가(마이너), 개명·병합(메이저, 매핑으로 흡수 가능), 분할·레인지 변경(메이저, 재추출 필요) | 상위 클래스, **정의 ID**(라벨이 아님), 매핑 테이블 구조 | 라벨·표시명·레인지 | 추가 → 마이너 릴리스, 소비자 무영향. 개명·병합 → 매핑 테이블 행 추가로 라벨 이전(재추출 없음). 분할 → 영향 클래스만 재추출 + 블루/그린 | 추가: 없음 / 개명: 매핑 소비자 / 분할: 05 재추출, SHACL, 08 어휘 |
| **지식** | 새 문서 유형·소스에서 새 개념 등장 | 미분류 버킷 → 변경 요청 경로 | — | 버킷 상위 항목이 변경 요청으로 승격(데이터로 흡수, 코드 변경 없음) | 변경 요청 큐 |
| **규칙·정책** | 제약 강화(필수 속성·카디널리티), 규제가 요구하는 분류 | SHACL 검증 인터페이스 | shapes | shapes 버전 + 기존 트리플 재검증 배치 | 05 검증, 버킷 |
| **사용자 환경** | 조직 개편(부서 신설·통합), 새 테넌트 도메인 | 조직 개념은 **클래스가 아니라 인스턴스·택소노미(SKOS)**로 | 택소노미 값 | 조직 개편은 SKOS 데이터 변경 + 구→신 매핑, 온톨로지 릴리스 불필요 | 03 허용값, ACL 그룹 |
| **모델** | 새 추출 모델이 다른 레이블 표현을 선호 | 정의 ID | 매핑 테이블의 "추출 레이블" 열 | 매핑 테이블 열 값 교체(온톨로지 자체는 불변) | 05 프롬프트만 |
| **프로토콜·표준** | 표준 온톨로지 버전 업, 도구 체인 교체 | 표준 참조는 부분집합 매핑으로 | 표준 매핑, 변환 어댑터 | 매핑 재검 + 변환 재실행 | 외부 상호운용 경계만 |

가장 자주 바뀌는 것: **도메인 모델**(개념 추가·개명). 설계 원칙은 ① 소비자가 라벨이 아닌 **정의 ID를 참조**해 개명이 전파되지 않게, ② 조직·제품군처럼 자주 바뀌는 것은 클래스가 아니라 **인스턴스·택소노미**로 두어 릴리스 없이 데이터로 흡수. 코드 밖 설정으로 둘 것: 온톨로지 정의 파일(YAML/JSON-LD/OWL), SHACL shapes, 매핑 테이블, SKOS 택소노미, 범위 질문 세트, 모듈별 클래스 상한. 포트·어댑터 뒤에 둘 외부 의존: OWL 편집기·트리플스토어·추론기, 변환 도구 체인, 외부 표준 온톨로지 배포본. 시점 재현성: 모든 트리플·메타데이터에 온톨로지 버전이 있고([03](03-metadata-provenance.md)), 과거 버전 정의 파일과 매핑 테이블이 보존되어야 한다.

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성 표의 "탐지 신호"가 **실제로 어디서 나오는지**를 설계한다. 기준은 [Part 1/07 관측성 설계 요소](../01-foundations/07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md). 온톨로지는 런타임 서비스가 아니므로 이 단계의 트레이스는 **릴리스 단위**(`ontology.release` 루트)이고, 운영 중 신호는 소비자 스팬([05](05-knowledge-graph-construction.md) `kg.validate`, [03](03-metadata-provenance.md) `index.meta.gate`, [09](09-ai-inside-the-pipeline.md) `pipeline.decide`)에 붙은 **`agent.ontology_version` 속성으로 분해**해서 읽는다. 즉 이 단계가 관측에 기여하는 핵심은 "버전 키를 제공하고, 릴리스 전후를 비교 가능하게 만드는 것"이다.

| 기록 대상 | 스팬 / 이벤트 (이름, 부모) | 핵심 속성 (버전 키 포함) | 지표 (→ 어느 SLI) | 샘플링 · 보존 · PII |
|---|---|---|---|---|
| 릴리스 파이프라인 | `ontology.release` (릴리스 트레이스 루트), 자식 이벤트 `ontology.transform` · `ontology.test.scope` · `ontology.test.consistency` · `ontology.migrate` · `ontology.rollback` | `agent.ontology_version{from,to}`, `agent.release_type`(minor / major), `agent.mapping_table_version`, `agent.shacl_version`, `agent.transform_output_hash`, `agent.scope_questions{total,passed,failed_ids[]}`, `agent.mapping_completeness`, `agent.approver_role`(ID는 감사만), `agent.outcome`(success / blocked / rolled_back) | `ontology.release.outcome` 카운터, `ontology.transform.failures` → "CI 변환 단계 실패", `ontology.test.scope_pass_ratio` → **SLI ① 범위 질문 통과율**, "릴리스 테스트에서 범위 질문 실패" | 릴리스마다 전수. 보존 영구(릴리스 이력) |
| 정의 ↔ 운영 드리프트 검사 | `ontology.drift_check` 주기 배치 이벤트 (부모 없음) | `agent.ontology_version`(기준), `agent.consumer`(lpg / extract_labels / ui_labels / enum / taxonomy), `agent.drift_count`, `agent.unmapped_labels[]`(라벨 문자열은 해시, 수만 전수) | `ontology.drift.count{consumer}` → **SLI ③ 정의↔운영 불일치 건수**, `ontology.lpg.undefined_label_events` → "운영 LPG에 정의 없는 라벨 출현" | CI마다 + 일 1회(예시). 보존 90일 |
| 소비자 측 릴리스 효과 | 05 `kg.validate`·03 `index.meta.gate`·09 `pipeline.decide`의 기존 스팬 (이 단계 소유 아님) | 세 스팬 모두 `agent.ontology_version`(09는 enum 버전으로 매핑)을 가져야 함. 추가로 `agent.unmapped`(bool) | 05 `kg.validate.violation_ratio`를 `agent.ontology_version`으로 분해 → **SLI ④ 추출 위반율**(릴리스 전후 윈도 비교 = 카나리), 03 `index.meta.unclassified_ratio`·05 버킷 유입을 합쳐 `ontology.bucket.ratio` → **SLI ② 미분류 버킷 비율** | 소비자 정책을 따름 |
| 변경 요청·승인 | `ontology.change_request.open` → `ontology.change_request.resolve` 이벤트 쌍 (1/07 `approval.request → resolve` 패턴) | `agent.request_id`, `agent.class_group`, `agent.owner_assigned`(bool), `agent.origin`(bucket_promoted / manual / drift_auto), `agent.resolution`(approved / rejected / timeout_rejected), `agent.wait_hours` | `ontology.change_request.open` 게이지(적체), `ontology.change_request.wait_hours` 히스토그램 → "승인 대기 시간", `owner_assigned=false` 비율 → "소유자 부재" | 전수. 요청 본문은 변경 관리 시스템에, 스팬엔 ID |
| 사용률 점검 | `ontology.usage` 분기 배치 이벤트 | `agent.class_id`, `agent.instance_count`, `agent.query_hits`(Part 3 필터·그래프 질의에서 집계), `agent.last_used_at` | `ontology.class.usage{class}` → 과설계 회귀 방지(폐기 후보) — SLI 아님, 거버넌스 입력 | 분기 1회. 보존 영구 |

릴리스 전후 비교(카나리) 규칙: 전환 시각을 기준으로 소비자 지표를 "이전 7일 vs 이후 24시간" 두 윈도로 나눠 같은 패널에 겹쳐 그린다. 분해 축이 `agent.ontology_version` 하나뿐이면 추출 모델·프롬프트 동시 변경을 구분 못 하므로, 릴리스 번들 정책상 온톨로지 메이저 릴리스 창에는 [05](05-knowledge-graph-construction.md)의 추출기·프롬프트 변경을 **동결**한다.

샘플링·보존: 릴리스·변경 요청·드리프트 이벤트는 양이 적어 전수·장기 보존. 라벨 문자열은 해시만 남긴다(도메인 용어 자체가 기밀일 수 있음).

| 알림 | 조건 (예시) | 심각도 | 런북 (첫 3단계) |
|---|---|---|---|
| 릴리스 차단 (장애 모드: 변환 실패 · 범위 질문 회귀) | `ontology.release.outcome=blocked` — `transform.failures` ≥ 1 또는 `scope_pass_ratio` < 100% | P3 (릴리스 담당, 소비자 무영향) | ① `failed_ids[]`로 실패 질문이 의도된 폐기인지 정의 오류(순환·레인지)인지 구분 ② 변환 도구 체인 버전 고정 여부 확인 ③ 정의 수정 또는 질문 세트 갱신 후 재릴리스 |
| 릴리스 후 위반 급등 (장애 모드: 릴리스 후 추출 위반율 급등) | 전환 후 24시간 윈도의 05 `kg.validate.violation_ratio{ontology_version=new}`가 이전 7일 대비 +5%p | P2 | ① 위반 코드가 특정 클래스 정의에 집중되는지 확인 ② `agent.extractor_version`·`prompt_version`이 동시에 바뀌지 않았는지 확인(원인 귀속) ③ 온톨로지만 원인이면 매핑 테이블 역방향 롤백(`ontology.rollback`) |
| 운영 계층 직접 변경 (장애 모드: 정의 ↔ 운영 드리프트) | `ontology.lpg.undefined_label_events` ≥ 1, 또는 CI `drift.count` > 0 | P2 | ① 미정의 라벨의 쓰기 주체·시각 확인(권한 분리 위반 의심) ② `unmapped` 표시로 소비자 저하 중인지 확인 ③ 변경 요청 자동 생성 확인, 릴리스 차단 유지 |
| 승인 적체 (장애 모드: 소유자 부재·승인 지연) | `ontology.change_request.wait_hours` > 336h(2주), 또는 `owner_assigned=false` 요청 ≥ 1 | P3 | ① 해당 클래스군의 A 지정 여부 확인 ② 대리 승인자 에스컬레이션 ③ 타임아웃 = 거부 기본값이 작동했는지와 요청 보존 확인 |
| 버킷 누적 (장애 모드: 미분류 버킷 누적) | `ontology.bucket.ratio` > 2%가 7일 지속 | P3 | ① 버킷 상위 빈도 항목이 변경 요청으로 자동 승격됐는지 확인 ② 특정 소스·문서 유형 집중 여부 확인 ③ 다음 마이너 릴리스에 포함 또는 택소노미(SKOS)로 흡수 결정 |

대시보드에서 이 단계를 보는 뷰: ② Knowledge 패널 — 05 위반율·03 미분류 비율을 **온톨로지 버전별로 분해한 릴리스 전후 비교**, 드리프트 건수, 변경 요청 적체·대기 시간 / ③ 비용 패널 — 직접 비용 없음; 릴리스에 따른 재추출 비용은 05 추출 비용을 `ontology_version` 전환 시점으로 표시 / 감사 추적으로 넘기는 필드(관측 로그와 분리): 거버넌스 접점 표의 온톨로지 버전·변경 로그("왜")·승인자·범위 질문 결과·변환 산출물 해시·매핑 테이블 버전·마이그레이션 ID·롤백 이력 — 승인자 ID와 변경 사유 본문은 감사 저장소에만, 관측 스팬엔 역할·결과 코드 / 이 단계의 관측이 없으면 못 보는 장애: **릴리스 직후 위반율 상승의 원인이 온톨로지인지 추출 모델인지 구분하지 못하는 것** — 소비자 스팬에 `agent.ontology_version`과 `agent.extractor_version`이 함께 없으면 롤백 대상을 고를 수 없어 둘 다 되돌리거나 둘 다 못 되돌린다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5, 가역성 × 영향 범위) | 마이너 릴리스(추가)는 **등급 2**(여러 사용자, 가역) → 규칙 게이트(범위 질문·CI). 메이저 릴리스(개명·병합·분할·레인지 변경)는 **등급 3**(부분 가역, 그래프·UI·enum까지 전파) → 도메인 소유자 승인 1인 + 마이그레이션 계획 + 새 SHACL을 섀도로 선적용해 위반율 확인 |
| 가드레일 위치 (입력 / 출력 / 행동) | **행동**: 온톨로지 릴리스 게이트(변환 성공 ∧ 범위 질문 통과 ∧ 불일치 0 ∧ 매핑 완전성). 운영 계층 직접 쓰기 차단(권한 분리). 이 단계가 만든 SHACL은 [05](05-knowledge-graph-construction.md)의 **출력** 가드레일이 된다 |
| 게이트 출력 (통과 / 차단 / 승인 / 저하)과 판정 수단 | 통과(마이너) / 차단(테스트 실패) / 승인(메이저). 판정은 **규칙만**(테스트 결과·diff). 사용률 점검·과설계 판단은 사람 |
| 소유자 (A) | 도메인 소유자(클래스군별). 데이터 모델러가 R, AI·데이터 엔지니어가 C, 전체 I. **A가 비어 있는 클래스군이 없어야** 한다 |
| 감사 추적에 남길 필드 | 온톨로지 버전 + 변경 로그("왜"), 승인자·승인 시각, 범위 질문 결과, 변환 산출물 해시, 매핑 테이블 버전, 마이그레이션 실행 ID·범위, 롤백 이력 |

### 운영 준비도 체크
- [ ] 릴리스 게이트(변환·범위 질문·불일치 검사·매핑 완전성)가 CI로 자동화되어 있는가
- [ ] 운영 LPG에 라벨을 직접 추가할 수 없도록 쓰기 권한이 분리되어 있는가
- [ ] 개명·병합이 매핑 테이블로 재추출 없이 처리되고 역방향 롤백이 가능한가
- [ ] 소비자(05·03·09·Part 4)가 라벨이 아니라 정의 ID를 참조하는가
- [ ] 조직·제품군 같은 자주 바뀌는 개념이 클래스가 아닌 택소노미·인스턴스로 되어 있는가
- [ ] 클래스군별 도메인 소유자(A)가 지정되고 승인 타임아웃 기본값이 거부인가
- [ ] 미분류 버킷이 변경 요청으로 자동 승격되고 분기별 사용률 점검이 있는가
- [ ] 과거 온톨로지 버전 정의·매핑 테이블이 보존되어 시점 재현이 가능한가
- [ ] 소비자 스팬(05 `kg.validate`, 03 `index.meta.gate`, 09 `pipeline.decide`)이 전부 `agent.ontology_version`을 갖고, 릴리스 전후 위반율·미분류 비율을 버전별로 비교할 수 있는가
- [ ] 알림마다 런북이 있고, 릴리스 후 위반 급등 알림이 추출기·프롬프트 버전 동시 변경 여부를 먼저 확인하게 되어 있는가
