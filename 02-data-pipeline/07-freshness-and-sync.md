# 신선도와 동기화

> **범위**: 증분 인덱싱, 삭제/만료 전파, 중복 제거, 재인덱싱 전략
> **시각화**: [`assets/html/data-pipeline-architecture.html`](../assets/html/data-pipeline-architecture.html) — "동기화·ACL" 노드와 증분 루프

## 요약 (3줄)

1. 신선도(freshness)는 "얼마나 자주 긁는가"가 아니라 **소스의 변경·삭제·만료가 모든 인덱스(벡터·BM25·그래프·메타데이터)에 얼마나 늦게, 얼마나 빠짐없이 반영되는가**다. 삽입만 빠르고 삭제가 안 되는 파이프라인은 신선하지 않다.
2. 기본 구조는 **문서 단위 멱등 재처리**다. 문서 하나가 바뀌면 그 문서 유래의 청크·벡터·트리플을 모두 찾아 지우고 다시 만든다. 이것이 되려면 모든 파생물에 출처 문서 ID가 있어야 한다([03](03-metadata-provenance.md)).
3. 임베딩 모델·청킹 규칙·온톨로지 같은 **파이프라인 버전 변경**은 전체 재색인 이벤트다. 블루/그린 인덱스로 전환하고, 변경 전후를 같은 평가셋으로 비교한 뒤 스위치한다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 소스별 변경 감지 방식과 목표 반영 지연(SLO) ② 문서 단위 멱등 재처리 절차 ③ 삭제·만료 전파 규칙(소프트 삭제, 톰스톤, 유효 기간) ④ 중복 제거 정책 ⑤ 전체 재색인 절차(블루/그린)와 트리거 조건 ⑥ 정합성 대조(reconciliation) 배치 |
| **언제** (When) | 소스가 바뀌는 모든 경우. **생략**: 소스가 완전히 정적(아카이브)일 때. **미뤄도 되는 것**: 이벤트 기반 실시간 반영(배치 증분으로 시작해 SLO 미달 시 전환), 근사 중복 제거(정확 중복만 먼저) |
| **어떻게** (How) | ① 소스별 신선도 요구를 SLO로(분 / 시간 / 일) → ② 변경 감지 방식 선택(해시 비교 / 수정시각 / 웹훅 / CDC) → ③ 모든 파생물에 `doc_id` + `pipeline_version` 보장 → ④ 문서 단위 재처리 잡(삭제 → 재생성, 멱등) → ⑤ 삭제·만료는 톰스톤으로 즉시 필터 + 배치 물리 삭제 → ⑥ 주기적 전체 대조로 누락 탐지 → ⑦ 파이프라인 버전 변경은 블루/그린 |
| **왜** (Why) | 삭제가 전파되지 않으면 **퇴사자 정보·폐기 규정·철회된 가격**이 계속 인용된다. 증분 없이 전체 재색인만 있으면 갱신 주기가 비용에 묶여 길어진다. 벡터만 갱신하고 그래프를 안 하면 두 경로의 답이 서로 다르다. 모델을 바꾸면서 기존 벡터와 섞으면 검색이 조용히 망가진다 |

## 문제와 맥락

RAG 파이프라인은 처음엔 "한 번 색인"으로 시작한다. 운영 2주 뒤 생기는 문제는 정해져 있다.

- **유령 문서**: 소스에서 삭제됐는데 인덱스에 남아 인용된다. 폴링은 "없어진 것"을 감지하지 못한다
- **부분 갱신**: 문서가 수정되어 청크가 7개에서 5개로 줄었는데 기존 7개 위에 5개를 덮어써 2개가 좀비로 남는다
- **경로 불일치**: 벡터 인덱스는 갱신됐지만 그래프의 트리플은 옛 버전이다. 같은 질문에 벡터 경로와 그래프 경로가 다른 답을 낸다
- **모델 혼합**: 임베딩 모델을 바꾸고 새 문서만 새 모델로 색인했다. 두 모델의 벡터 공간은 호환되지 않으므로 검색 품질이 설명할 수 없게 떨어진다
- **중복 폭발**: 같은 문서가 공유 드라이브 세 곳에 있고, 메일 첨부로도 있다. 검색 top-5가 전부 같은 내용이다

이 단계는 위 문제를 **구조적으로** 막는다. 사람이 알아채고 고치는 것이 아니라 파이프라인이 못 생기게 한다.

## 핵심 개념

### 갱신 전략 세 가지

| 전략 | 동작 | 반영 지연 | 비용 | 적합 |
|---|---|---|---|---|
| **전체 재색인** | 주기마다 소스 전체를 다시 처리 | 주기(일~주) | 매번 전체 | 소규모, 정적에 가까움, 파이프라인 버전 변경 시 |
| **증분 배치** | 주기마다 변경분(해시·수정시각 비교)만 처리 | 주기(분~시간) | 변경분 비례 | 대부분의 문서 소스 |
| **이벤트 기반** | 웹훅·CDC 이벤트가 오면 즉시 해당 문서 재처리 | 초~분 | 이벤트 비례 + 스트림 인프라 | 운영 DB, SaaS, 신선도 SLO 분 단위 |

증분·이벤트 기반을 쓰더라도 **전체 대조(reconciliation) 배치는 유지**한다. 이벤트는 유실되고 해시 비교는 권한 변경을 못 본다. 주 1회 소스 목록과 인덱스 목록을 대조해 누락·유령을 찾는다.

### 문서 단위 멱등 재처리

```
변경 이벤트(doc_id) ─▶ 기존 파생물 조회: WHERE source_doc_id = doc_id
                        ├─ 청크·벡터 삭제 (또는 톰스톤)
                        ├─ BM25 문서 삭제
                        ├─ 그래프: 이 문서 유래 트리플 삭제 (엣지 속성 source_doc_id)
                        └─ 메타데이터: 이전 버전 is_current=false
                     ─▶ 재파싱 → 재청킹 → 재임베딩 → 재추출 → 재적재 (새 doc_version)
                     ─▶ 같은 이벤트를 두 번 받아도 결과가 같아야 함 (멱등 키 = doc_id + content_hash)
```

"덮어쓰기"가 아니라 **삭제 후 재생성**이다. 청크 수가 바뀌어도 좀비가 남지 않는다. 그래프에서는 노드가 아니라 **엣지(트리플)**를 문서 단위로 지운다. 노드는 다른 문서에서도 참조될 수 있으므로 참조 수가 0이 될 때만 정리한다.

### 삭제·만료 전파

| 유형 | 트리거 | 처리 |
|---|---|---|
| **소스 삭제** | 대조 배치에서 소스에 없음, 또는 삭제 이벤트 | 톰스톤(즉시 검색 제외) → 유예 후 물리 삭제. 감사용 메타데이터는 보존 |
| **권한 회수** | 소스 ACL 변경 | 메타데이터 ACL 갱신([10](10-access-control-governance.md)). 인덱스 분리 구조면 해당 인덱스에서 제거 |
| **만료** | `valid_to` 도래, 보존 기간 종료 | 자동 톰스톤. 규정·가격처럼 "과거 시점 질의"가 필요하면 `is_current=false`로 남기고 기본 필터에서 제외 |
| **철회·정정** | 문서가 "이 문서는 폐기됨"으로 바뀜 | 본문 분류로 감지(규칙 또는 판정 모델) → 톰스톤 + `superseded_by` 링크 |

톰스톤은 **모든 인덱스가 공통으로 보는 메타데이터 필드**(`deleted_at` 또는 `is_current`)여야 한다. 벡터DB에서만 지우고 BM25나 그래프에 남으면 전파가 아니다.

### 중복 제거

| 수준 | 방법 | 비용 | 한계 |
|---|---|---|---|
| **정확 중복** | 정규화 텍스트의 해시 비교 | 하 | 공백·머리글 하나만 달라도 놓침 |
| **근사 중복** | MinHash / SimHash로 유사 문서 후보 → 임계값 | 중 | 임계값 튜닝, 버전 차이와 중복의 구분 |
| **의미 중복** | 임베딩 코사인 유사도가 매우 높은 청크 | 중 | "비슷한 내용"과 "같은 문서"를 혼동 |
| **정책 기반** | 같은 문서가 여러 위치 → 정본(canonical) 위치 규칙 | 하 | 정본 규칙을 정해야 함 |

중복은 **지우지 않고 정본에 묶는다**(`canonical_doc_id`). 사용자가 "메일 첨부에서 봤다"고 하면 그 위치로도 찾아야 하기 때문이다. 검색 결과에서는 정본 하나만 노출한다. "버전이 다른 같은 문서"는 중복이 아니라 버전 이력이다([03](03-metadata-provenance.md)).

### 재임베딩 시점

| 트리거 | 범위 | 처리 |
|---|---|---|
| 문서 변경 | 해당 문서 | 증분 재처리 |
| 청킹 규칙 변경 | 전체 | 블루/그린 전체 재색인 |
| 임베딩 모델 교체 | 전체 (벡터 공간 비호환) | 블루/그린. **두 모델 벡터를 한 인덱스에 섞지 않는다** |
| 온톨로지 메이저 버전 | 그래프 전체 (또는 영향 클래스) | 매핑 테이블로 마이그레이션, 불가 시 재추출 |
| 파서 버그 수정 | 영향 문서(계보로 식별) | `parser.version = 버그 버전`인 문서만 재처리([03](03-metadata-provenance.md)) |

**블루/그린**: 새 인덱스(그린)를 전체 구축하고, 같은 평가셋으로 기존(블루)과 비교한 뒤 트래픽을 전환한다. 전환 후 일정 기간 블루를 유지해 롤백 가능하게 한다. 구축 중 들어온 변경은 양쪽에 적용하거나 전환 직후 증분으로 따라잡는다.

### 그래프의 증분 갱신

벡터 인덱스는 문서 단위 삭제·재삽입이 자연스럽지만 그래프는 셋이 더 어렵다.

1. **엔티티 해소 재실행**: 새 문서의 엔티티가 기존 노드와 같은지 다시 판정. `sameAs` 링크가 가역적이어야 되돌릴 수 있다([05](05-knowledge-graph-construction.md))
2. **파생 구조**: GraphRAG 식 커뮤니티 요약은 노드 하나가 바뀌어도 커뮤니티 전체 재계산이 필요. LightRAG는 증분 병합을 지원한다 `[2차]`. HippoRAG 2 식 PPR은 질의 시 계산이라 인덱싱 부담이 작다
3. **고아 노드**: 문서 삭제로 참조 수가 0이 된 노드. 즉시 삭제하지 않고 배치로 정리(다른 문서가 곧 참조할 수 있음)

## 아키텍처 / 파이프라인

```
소스 ─▶ 변경 감지 (해시 / 수정시각 / 웹훅 / CDC) ─▶ 변경 큐 (doc_id, 유형: upsert|delete|acl)
                                                        ▼
                                  문서 단위 멱등 재처리 잡 ─┬─▶ 벡터·BM25 인덱스 (톰스톤 → 재삽입)
                                                            ├─▶ 그래프 (문서 유래 엣지 삭제 → 재추출 → 재해소)
                                                            └─▶ 메타데이터 (버전, is_current, deleted_at, acl)
주 1회 전체 대조 배치 ─▶ 누락·유령 탐지 ─▶ 변경 큐로 재투입
파이프라인 버전 변경 ─▶ 블루/그린 전체 재색인 ─▶ 평가셋 비교 ─▶ 스위치 ─▶ 블루 유예 보관
```

변경 큐는 **하나**다. 벡터·그래프·메타데이터가 같은 이벤트를 소비해야 경로 불일치가 안 생긴다.

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 전체 재색인 (주기) | 수만 건 이하, 정적에 가까움, 파이프라인 버전 변경 | 신선도 SLO 시간 단위 이하, 대규모 | 하(구현) / 상(실행 비용) | 표준 | — |
| 증분 배치 (해시·수정시각 비교) | 대부분의 문서 소스, SLO 시간 단위 | 삭제 감지 필요(폴링은 못 봄 → 대조 배치 병행), SLO 분 단위 | 중 | 표준 | `[검증]` 일반 공학 |
| 이벤트 기반 (웹훅) | SaaS 소스, SLO 분 단위 | 이벤트 유실 대비 없이 단독 사용 | 중 | 안정 | `[2차]` |
| CDC (DB 로그 기반) | 운영 DB 소스, 행 단위 변경, 삭제 이벤트 포함 | 파일·문서 소스, 로그 접근 불가 | 중~상 | 표준 | `[검증]` |
| 톰스톤 + 유예 물리 삭제 | 모든 운영 환경 | 즉시 물리 삭제가 규제로 요구될 때(유예 없이) | 하 | 표준 | `[검증]` 분산 시스템 일반 |
| 정확 중복 제거 (해시) | 첫 단계, 복사본 많은 공유 드라이브 | 양식만 다른 근사 중복 | 하 | 표준 | — |
| 근사 중복 제거 (MinHash / SimHash) | 근사 복사본 많음, 웹·메일 수집 | 임계값 튜닝 여력 없음, 버전 이력과 혼동 위험 | 중 | 표준 | `[검증]` 원 논문 |
| 블루/그린 인덱스 | 모델·청킹·온톨로지 변경 | 저장 2배를 감당 못 할 때(그래도 권장) | 중 | 안정 | `[2차]` 배포 패턴 일반 |
| 그래프 증분 (LightRAG 식) | 문서 갱신 잦은 그래프 | 커뮤니티 요약 의존 구조 | 중 | 신생~안정 | `[2차]` |

### 선택 가이드

- **소스가 운영 DB이고 SLO가 분 단위라면** → CDC + 단일 변경 큐. 이유: 삭제까지 이벤트로 오는 유일한 방식
- **소스가 문서 저장소·위키이고 SLO가 시간 단위라면** → 증분 배치 + 주 1회 전체 대조. 이유: 비용 대비 충분하고 대조가 유령을 잡는다
- **공유 드라이브·메일처럼 복사본이 많다면** → 정확 중복 제거 + 정본 규칙, 근사 중복은 문제가 보일 때. 이유: 정확 중복만으로도 대부분 해결
- **임베딩 모델이나 청킹 규칙을 바꾼다면** → 블루/그린 + 평가셋 비교, 절대 섞지 않음. 이유: 벡터 공간 비호환
- **판단이 어려우면** → 기본값: 증분 배치 + 톰스톤 + 전체 대조 + 문서 단위 멱등 재처리 + 블루/그린 절차 문서화. 이유: 어떤 소스에도 통하고 이벤트 기반으로 승격하기 쉽다

## 설계 시 고려사항 (체크리스트)

- [ ] 소스별 신선도 SLO(분/시간/일)를 적었는가
- [ ] 모든 파생물(청크·벡터·트리플·캡션)에 출처 `doc_id`와 `pipeline_version`이 있는가
- [ ] 문서 재처리가 "삭제 후 재생성"이고 멱등인가(같은 이벤트 2회 → 같은 결과)
- [ ] 벡터·BM25·그래프·메타데이터가 **같은 변경 큐**를 소비하는가
- [ ] 톰스톤 필드가 모든 인덱스의 기본 필터에 포함되는가
- [ ] 삭제·권한 회수·만료·철회 네 유형의 전파 규칙이 각각 있는가
- [ ] 주기적 전체 대조 배치가 있고 누락·유령을 변경 큐로 재투입하는가
- [ ] 중복은 지우지 않고 정본에 묶으며 검색 결과에서 정본만 노출하는가
- [ ] 임베딩 모델·청킹 규칙 변경 시 블루/그린 절차와 평가셋 비교가 있는가
- [ ] 그래프의 고아 노드 정리와 엔티티 해소 재실행 절차가 있는가
- [ ] 신선도 지표(소스 변경 → 검색 반영까지의 지연, 유령 문서 수)를 모니터링하는가

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 폴링은 삭제를 못 본다 | 유령 문서 | 전체 대조 배치 필수 |
| 이벤트 유실 | 누락 갱신 | 대조 배치, 이벤트 재전송·DLQ |
| 블루/그린의 저장 2배 | 비용 | 전환 후 유예 기간 짧게, 오래된 판은 벡터 없이 보관 |
| 그래프 증분의 엔티티 해소 불안정 | 새 문서가 기존 노드를 잘못 병합 | 가역적 `sameAs`, 확신도 임계값, 샘플 감사 |
| 벡터DB의 삭제 비효율 (HNSW) | 삭제가 많으면 인덱스 성능 저하 | 톰스톤 + 주기적 재구축(compaction) |
| 중복 제거의 오탐 | 버전 이력을 중복으로 묶음 | 버전 관계(`supersedes`)를 먼저 확인, 임계값 보수적 |
| 신선도와 비용의 충돌 | SLO를 짧게 잡을수록 재처리 비용↑ | 소스별 SLO 차등, 고가치 컬렉션만 이벤트 기반 |
