# 신선도와 동기화

> **범위**: 증분 인덱싱, 삭제/만료 전파, 중복 제거, 재인덱싱 전략
> **시각화**: [`assets/html/data-pipeline-architecture.html`](../assets/html/data-pipeline-architecture.html) — "동기화·ACL" 노드와 증분 루프

## 요약 (3줄)

1. 신선도(freshness)는 "얼마나 자주 긁는가"가 아니라 **소스의 변경·삭제·만료가 모든 인덱스(벡터·BM25·그래프·메타데이터)에 얼마나 늦게, 얼마나 빠짐없이 반영되는가**다. 삽입만 빠르고 삭제가 안 되는 파이프라인은 신선하지 않다.
2. 기본 구조는 **문서 단위 멱등 재처리**다. 문서 하나가 바뀌면 그 문서 유래의 청크·벡터·트리플을 모두 찾아 지우고 다시 만든다. 이것이 되려면 모든 파생물에 출처 문서 ID가 있어야 한다([03](03-metadata-provenance.md)).
3. 임베딩 모델·청킹 규칙·온톨로지 같은 **파이프라인 버전 변경**은 전체 재색인 이벤트다. 블루/그린 인덱스로 전환하고, 변경 전후를 같은 평가셋으로 비교한 뒤 스위치한다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 소스별 변경 감지 방식과 목표 반영 지연(SLO) ② 문서 단위 멱등 재처리 절차 ③ 삭제·만료 전파 규칙(소프트 삭제, 톰스톤, 유효 기간) ④ 중복 제거 정책 ⑤ 전체 재색인 절차(블루/그린)와 트리거 조건 ⑥ 정합성 대조(reconciliation) 배치 |
| **언제** (When) | 소스가 바뀌는 모든 경우. **생략**: 소스가 완전히 정적(아카이브)일 때. **미뤄도 되는 것**: 이벤트 기반 실시간 반영(배치 증분으로 시작해 SLO 미달 시 전환), 근사 중복 제거(정확 중복만 먼저) |
| **어떻게** (How) | ① 소스별 신선도 요구를 SLO로(분 / 시간 / 일) → ② 변경 감지 방식 선택(해시 비교 / 수정시각 / 웹훅 / CDC) → ③ 모든 파생물에 `doc_id` + `pipeline_version` 보장 → ④ 문서 단위 재처리 잡(삭제 → 재생성, 멱등) → ⑤ 삭제·만료는 톰스톤으로 즉시 필터 + 배치 물리 삭제 → ⑥ 주기적 전체 대조로 누락 탐지 → ⑦ 파이프라인 버전 변경은 블루/그린 |
| **왜** (Why) | 삭제가 전파되지 않으면 **퇴사자 정보·폐기 규정·철회된 가격**이 계속 인용된다. 증분 없이 전체 재색인만 있으면 갱신 주기가 비용에 묶여 길어진다. 벡터만 갱신하고 그래프를 안 하면 두 경로의 답이 서로 다르다. 모델을 바꾸면서 기존 벡터와 섞으면 검색이 조용히 망가진다 |

## 문제와 맥락

RAG 파이프라인은 처음엔 "한 번 색인"으로 시작한다. 운영 2주 뒤 생기는 문제는 정해져 있다.

- **유령 문서**: 소스에서 삭제됐는데 인덱스에 남아 인용된다. 폴링은 "없어진 것"을 감지하지 못한다
- **부분 갱신**: 문서가 수정되어 청크가 7개에서 5개로 줄었는데 기존 7개 위에 5개를 덮어써 2개가 좀비로 남는다
- **경로 불일치**: 벡터 인덱스는 갱신됐지만 그래프의 트리플은 옛 버전이다. 같은 질문에 벡터 경로와 그래프 경로가 다른 답을 낸다
- **모델 혼합**: 임베딩 모델을 바꾸고 새 문서만 새 모델로 색인했다. 두 모델의 벡터 공간은 호환되지 않으므로 검색 품질이 설명할 수 없게 떨어진다
- **중복 폭발**: 같은 문서가 공유 드라이브 세 곳에 있고, 메일 첨부로도 있다. 검색 top-5가 전부 같은 내용이다

이 단계는 위 문제를 **구조적으로** 막는다. 사람이 알아채고 고치는 것이 아니라 파이프라인이 못 생기게 한다.

## 핵심 개념

### 갱신 전략 세 가지

| 전략 | 동작 | 반영 지연 | 비용 | 적합 |
|---|---|---|---|---|
| **전체 재색인** | 주기마다 소스 전체를 다시 처리 | 주기(일~주) | 매번 전체 | 소규모, 정적에 가까움, 파이프라인 버전 변경 시 |
| **증분 배치** | 주기마다 변경분(해시·수정시각 비교)만 처리 | 주기(분~시간) | 변경분 비례 | 대부분의 문서 소스 |
| **이벤트 기반** | 웹훅·CDC 이벤트가 오면 즉시 해당 문서 재처리 | 초~분 | 이벤트 비례 + 스트림 인프라 | 운영 DB, SaaS, 신선도 SLO 분 단위 |

증분·이벤트 기반을 쓰더라도 **전체 대조(reconciliation) 배치는 유지**한다. 이벤트는 유실되고 해시 비교는 권한 변경을 못 본다. 주 1회 소스 목록과 인덱스 목록을 대조해 누락·유령을 찾는다.

### 문서 단위 멱등 재처리

```
변경 이벤트(doc_id) ─▶ 기존 파생물 조회: WHERE source_doc_id = doc_id
                        ├─ 청크·벡터 삭제 (또는 톰스톤)
                        ├─ BM25 문서 삭제
                        ├─ 그래프: 이 문서 유래 트리플 삭제 (엣지 속성 source_doc_id)
                        └─ 메타데이터: 이전 버전 is_current=false
                     ─▶ 재파싱 → 재청킹 → 재임베딩 → 재추출 → 재적재 (새 doc_version)
                     ─▶ 같은 이벤트를 두 번 받아도 결과가 같아야 함 (멱등 키 = doc_id + content_hash)
```

"덮어쓰기"가 아니라 **삭제 후 재생성**이다. 청크 수가 바뀌어도 좀비가 남지 않는다. 그래프에서는 노드가 아니라 **엣지(트리플)**를 문서 단위로 지운다. 노드는 다른 문서에서도 참조될 수 있으므로 참조 수가 0이 될 때만 정리한다.

### 삭제·만료 전파

| 유형 | 트리거 | 처리 |
|---|---|---|
| **소스 삭제** | 대조 배치에서 소스에 없음, 또는 삭제 이벤트 | 톰스톤(즉시 검색 제외) → 유예 후 물리 삭제. 감사용 메타데이터는 보존 |
| **권한 회수** | 소스 ACL 변경 | 메타데이터 ACL 갱신([10](10-access-control-governance.md)). 인덱스 분리 구조면 해당 인덱스에서 제거 |
| **만료** | `valid_to` 도래, 보존 기간 종료 | 자동 톰스톤. 규정·가격처럼 "과거 시점 질의"가 필요하면 `is_current=false`로 남기고 기본 필터에서 제외 |
| **철회·정정** | 문서가 "이 문서는 폐기됨"으로 바뀜 | 본문 분류로 감지(규칙 또는 판정 모델) → 톰스톤 + `superseded_by` 링크 |

톰스톤은 **모든 인덱스가 공통으로 보는 메타데이터 필드**(`deleted_at` 또는 `is_current`)여야 한다. 벡터DB에서만 지우고 BM25나 그래프에 남으면 전파가 아니다.

삭제 레인의 소비자는 Part 2의 네 인덱스에 그치지 않는다. Reasoning의 결과·시맨틱 캐시([Part 3/01](../03-agent-workflow-rag/01-rag-architecture-patterns.md)·[3/03](../03-agent-workflow-rag/03-retrieval-reranking.md)·[3/04](../03-agent-workflow-rag/04-generation-grounding.md)·[Part 5/02](../05-cross-cutting/02-cost-latency-model-routing.md)), 메모리([Part 3/08](../03-agent-workflow-rag/08-state-memory-context.md)), 환류된 평가 골든셋([Part 3/13](../03-agent-workflow-rag/13-evaluation-rag-agents.md)·[Part 4/10](../04-dynamic-ui/10-evaluation-genui.md))도 같은 삭제 레인을 **구독하는 소비자로 등록**한다 — 문서 1건의 톰스톤은 인덱스 버전을 올리지 않으므로 버전 키만으로는 캐시가 비워지지 않는다. 삭제 전파 SLO는 인덱스가 아니라 **인덱스·캐시·메모리·골든셋 네 끝점 전부**까지로 정의한다([Part 5/06](../05-cross-cutting/06-operational-design-matrix.md) 공통 SLO)(불균형 ① 반영).

### 중복 제거

| 수준 | 방법 | 비용 | 한계 |
|---|---|---|---|
| **정확 중복** | 정규화 텍스트의 해시 비교 | 하 | 공백·머리글 하나만 달라도 놓침 |
| **근사 중복** | MinHash / SimHash로 유사 문서 후보 → 임계값 | 중 | 임계값 튜닝, 버전 차이와 중복의 구분 |
| **의미 중복** | 임베딩 코사인 유사도가 매우 높은 청크 | 중 | "비슷한 내용"과 "같은 문서"를 혼동 |
| **정책 기반** | 같은 문서가 여러 위치 → 정본(canonical) 위치 규칙 | 하 | 정본 규칙을 정해야 함 |

중복은 **지우지 않고 정본에 묶는다**(`canonical_doc_id`). 사용자가 "메일 첨부에서 봤다"고 하면 그 위치로도 찾아야 하기 때문이다. 검색 결과에서는 정본 하나만 노출한다. "버전이 다른 같은 문서"는 중복이 아니라 버전 이력이다([03](03-metadata-provenance.md)).

### 재임베딩 시점

| 트리거 | 범위 | 처리 |
|---|---|---|
| 문서 변경 | 해당 문서 | 증분 재처리 |
| 청킹 규칙 변경 | 전체 | 블루/그린 전체 재색인 |
| 임베딩 모델 교체 | 전체 (벡터 공간 비호환) | 블루/그린. **두 모델 벡터를 한 인덱스에 섞지 않는다** |
| 온톨로지 메이저 버전 | 그래프 전체 (또는 영향 클래스) | 매핑 테이블로 마이그레이션, 불가 시 재추출 |
| 파서 버그 수정 | 영향 문서(계보로 식별) | `parser.version = 버그 버전`인 문서만 재처리([03](03-metadata-provenance.md)) |

**블루/그린**: 새 인덱스(그린)를 전체 구축하고, 같은 평가셋으로 기존(블루)과 비교한 뒤 트래픽을 전환한다. 전환 후 일정 기간 블루를 유지해 롤백 가능하게 한다. 구축 중 들어온 변경은 양쪽에 적용하거나 전환 직후 증분으로 따라잡는다.

### 그래프의 증분 갱신

벡터 인덱스는 문서 단위 삭제·재삽입이 자연스럽지만 그래프는 셋이 더 어렵다.

1. **엔티티 해소 재실행**: 새 문서의 엔티티가 기존 노드와 같은지 다시 판정. `sameAs` 링크가 가역적이어야 되돌릴 수 있다([05](05-knowledge-graph-construction.md))
2. **파생 구조**: GraphRAG 식 커뮤니티 요약은 노드 하나가 바뀌어도 커뮤니티 전체 재계산이 필요. LightRAG는 증분 병합을 지원한다 `[2차]`. HippoRAG 2 식 PPR은 질의 시 계산이라 인덱싱 부담이 작다
3. **고아 노드**: 문서 삭제로 참조 수가 0이 된 노드. 즉시 삭제하지 않고 배치로 정리(다른 문서가 곧 참조할 수 있음)

## 아키텍처 / 파이프라인

```
소스 ─▶ 변경 감지 (해시 / 수정시각 / 웹훅 / CDC) ─▶ 변경 큐 (doc_id, 유형: upsert|delete|acl)
                                                        ▼
                                  문서 단위 멱등 재처리 잡 ─┬─▶ 벡터·BM25 인덱스 (톰스톤 → 재삽입)
                                                            ├─▶ 그래프 (문서 유래 엣지 삭제 → 재추출 → 재해소)
                                                            └─▶ 메타데이터 (버전, is_current, deleted_at, acl)
주 1회 전체 대조 배치 ─▶ 누락·유령 탐지 ─▶ 변경 큐로 재투입
파이프라인 버전 변경 ─▶ 블루/그린 전체 재색인 ─▶ 평가셋 비교 ─▶ 스위치 ─▶ 블루 유예 보관
```

변경 큐는 **하나**다. 벡터·그래프·메타데이터가 같은 이벤트를 소비해야 경로 불일치가 안 생긴다.

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 전체 재색인 (주기) | 수만 건 이하, 정적에 가까움, 파이프라인 버전 변경 | 신선도 SLO 시간 단위 이하, 대규모 | 하(구현) / 상(실행 비용) | 표준 | — |
| 증분 배치 (해시·수정시각 비교) | 대부분의 문서 소스, SLO 시간 단위 | 삭제 감지 필요(폴링은 못 봄 → 대조 배치 병행), SLO 분 단위 | 중 | 표준 | `[검증]` 일반 공학 |
| 이벤트 기반 (웹훅) | SaaS 소스, SLO 분 단위 | 이벤트 유실 대비 없이 단독 사용 | 중 | 안정 | `[2차]` |
| CDC (DB 로그 기반) | 운영 DB 소스, 행 단위 변경, 삭제 이벤트 포함 | 파일·문서 소스, 로그 접근 불가 | 중~상 | 표준 | `[검증]` |
| 톰스톤 + 유예 물리 삭제 | 모든 운영 환경 | 즉시 물리 삭제가 규제로 요구될 때(유예 없이) | 하 | 표준 | `[검증]` 분산 시스템 일반 |
| 정확 중복 제거 (해시) | 첫 단계, 복사본 많은 공유 드라이브 | 양식만 다른 근사 중복 | 하 | 표준 | — |
| 근사 중복 제거 (MinHash / SimHash) | 근사 복사본 많음, 웹·메일 수집 | 임계값 튜닝 여력 없음, 버전 이력과 혼동 위험 | 중 | 표준 | `[검증]` 원 논문 |
| 블루/그린 인덱스 | 모델·청킹·온톨로지 변경 | 저장 2배를 감당 못 할 때(그래도 권장) | 중 | 안정 | `[2차]` 배포 패턴 일반 |
| 그래프 증분 (LightRAG 식) | 문서 갱신 잦은 그래프 | 커뮤니티 요약 의존 구조 | 중 | 신생~안정 | `[2차]` |

### 선택 가이드

- **소스가 운영 DB이고 SLO가 분 단위라면** → CDC + 단일 변경 큐. 이유: 삭제까지 이벤트로 오는 유일한 방식
- **소스가 문서 저장소·위키이고 SLO가 시간 단위라면** → 증분 배치 + 주 1회 전체 대조. 이유: 비용 대비 충분하고 대조가 유령을 잡는다
- **공유 드라이브·메일처럼 복사본이 많다면** → 정확 중복 제거 + 정본 규칙, 근사 중복은 문제가 보일 때. 이유: 정확 중복만으로도 대부분 해결
- **임베딩 모델이나 청킹 규칙을 바꾼다면** → 블루/그린 + 평가셋 비교, 절대 섞지 않음. 이유: 벡터 공간 비호환
- **판단이 어려우면** → 기본값: 증분 배치 + 톰스톤 + 전체 대조 + 문서 단위 멱등 재처리 + 블루/그린 절차 문서화. 이유: 어떤 소스에도 통하고 이벤트 기반으로 승격하기 쉽다

## 설계 시 고려사항 (체크리스트)

- [ ] 소스별 신선도 SLO(분/시간/일)를 적었는가
- [ ] 모든 파생물(청크·벡터·트리플·캡션)에 출처 `doc_id`와 `pipeline_version`이 있는가
- [ ] 문서 재처리가 "삭제 후 재생성"이고 멱등인가(같은 이벤트 2회 → 같은 결과)
- [ ] 벡터·BM25·그래프·메타데이터가 **같은 변경 큐**를 소비하는가
- [ ] 톰스톤 필드가 모든 인덱스의 기본 필터에 포함되는가
- [ ] 삭제·권한 회수·만료·철회 네 유형의 전파 규칙이 각각 있는가
- [ ] 주기적 전체 대조 배치가 있고 누락·유령을 변경 큐로 재투입하는가
- [ ] 중복은 지우지 않고 정본에 묶으며 검색 결과에서 정본만 노출하는가
- [ ] 임베딩 모델·청킹 규칙 변경 시 블루/그린 절차와 평가셋 비교가 있는가
- [ ] 그래프의 고아 노드 정리와 엔티티 해소 재실행 절차가 있는가
- [ ] 신선도 지표(소스 변경 → 검색 반영까지의 지연, 유령 문서 수)를 모니터링하는가

| 한계 | 영향 | 완화책 |
|---|---|---|
| 폴링은 삭제를 못 본다 | 유령 문서 | 전체 대조 배치 필수 |
| 이벤트 유실 | 누락 갱신 | 대조 배치, 이벤트 재전송·DLQ |
| 블루/그린의 저장 2배 | 비용 | 전환 후 유예 기간 짧게, 오래된 판은 벡터 없이 보관 |
| 그래프 증분의 엔티티 해소 불안정 | 새 문서가 기존 노드를 잘못 병합 | 가역적 `sameAs`, 확신도 임계값, 샘플 감사 |
| 벡터DB의 삭제 비효율 (HNSW) | 삭제가 많으면 인덱스 성능 저하 | 톰스톤 + 주기적 재구축(compaction) |
| 중복 제거의 오탐 | 버전 이력을 중복으로 묶음 | 버전 관계(`supersedes`)를 먼저 확인, 임계값 보수적 |
| 신선도와 비용의 충돌 | SLO를 짧게 잡을수록 재처리 비용↑ | 소스별 SLO 차등, 고가치 컬렉션만 이벤트 기반 |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 이 단계는 Part 2에서 **"지식 변화"를 흡수하는 메커니즘 그 자체**다. 다른 페이지의 변화 대응 표가 "증분 재처리로 흡수"라고 쓴 것은 전부 이 단계의 변경 큐·멱등 잡·블루/그린을 가리킨다. 전략·절차는 [핵심 개념] 참조. 여기서는 그 메커니즘이 **커질 때, 죽을 때, 바뀔 때**를 다룬다.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 데이터 (문서 수) | 주 1회 전체 대조 배치가 창 안에 안 끝남. 블루/그린 전체 재색인이 저장 2배 × 며칠. HNSW 톰스톤 누적 | 대조를 소스·테넌트별 **파티션 롤링**(매일 1/7씩), 블루/그린을 컬렉션·파티션 단위로, compaction 배치 창, 증분 우선 | 문서 수(대조), 전체 재색인 빈도 × 문서 수(블루/그린) |
| 변경률 (이벤트 수) | 변경 큐 적체, 재처리 잡 처리량 한계, 한 문서의 연속 수정이 중복 재처리 | 큐를 **우선 레인**으로 분리(삭제·ACL → 수정 → 신규), 문서 단위 디바운스(예: 5분 내 연속 변경은 마지막만), 무상태 재처리 워커 수평 확장 | 이벤트 수 × 문서당 재처리 비용(파싱·임베딩·추출 전부) |
| 인덱스·경로 수 | 벡터·BM25·그래프·메타데이터 네 소비자의 지연이 제각각 → 경로 불일치. 삭제 레인은 레이어 밖 소비자(Reasoning 캐시·메모리·골든셋)까지 더해짐 | 단일 변경 큐 + 소비자별 지연 SLI(삭제 레인은 끝점별 — 인덱스·캐시·메모리·골든셋, 불균형 ① 반영), 가장 느린 소비자(그래프)가 전체 신선도를 정의 | 소비자 수 × 이벤트 수 |
| 테넌트 | 테넌트별 SLO·대조 주기 차등 요구 | 테넌트 키로 큐 파티션, 테넌트별 SLO 설정 | 테넌트 수 |

재처리 워커는 무상태다. 입력은 `(doc_id, content_hash, event_type)`, 상태는 큐와 메타데이터 저장소에만. 전체 재색인은 서빙과 분리된 배치 창에서 돌리되, 창 안에 못 끝나면 **파티션 분할 → 추출 모델 티어 하향 → 재색인 범위 축소** 순으로 결정한다.

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 변경 큐·브로커 다운 (의존 서비스 다운) | 신선도 지연이 조용히 늘어남. 검색은 정상 | 큐 유입·소비 0, 신선도 지연 SLI 상승 | 커넥터는 커서 보존(유실 없음). 복구 후 대조 배치가 누락분 보충 | 다운이 가장 짧은 소스 SLO(예: CDC 5분)의 3배 초과 |
| 재처리 잡 지연 급증 | 변경이 반영되는 데 평소보다 오래 걸림 | 소비자별 지연 p95, 큐 깊이 | 우선 레인이 삭제·ACL을 먼저 처리(누출·유령 방지). 신규 색인은 뒤로 | 삭제 레인 지연이 전파 SLO(예: 15분) 초과 |
| 재처리 실패 폭증 → DLQ 증가 (검증 실패 폭증) | 특정 소스 문서가 갱신 안 됨 | DLQ 크기·증가율, 실패 사유 분포 | 재시도 상한(예시 5회, 지수 백오프) 후 DLQ. 다른 문서는 계속 | DLQ가 예시 100건 초과 또는 단일 사유 집중 → 상류(파서·임베딩 API) 장애 확인 |
| 경로 불일치 (데이터 불일치) | 벡터 답과 그래프 답이 다름 | 소비자별 지연 차, 문서별 `pipeline_version` 불일치 수 | 단일 큐가 구조적 방지. 불일치 문서는 큐에 재투입 | 차이가 예시 1h 지속 |
| 삭제 미전파 — 유령 문서 (단계 고유) | 삭제·만료 문서가 인용됨 | 대조 배치 유령 수, 톰스톤 미적용 인덱스 탐지(톰스톤 문서로 카나리 질의) | 대조 배치가 톰스톤 이벤트 재투입. 카나리 질의 실패 시 해당 인덱스 검색 차단 | 유령이 기밀·PII·철회 문서면 즉시([10](10-access-control-governance.md)) |
| 블루/그린 전환 후 회귀 (단계 고유) | 전환 직후 검색 품질 하락 | 전환 전 평가셋 비교, 전환 후 실시간 지표(무결과율·클릭) | 평가셋 미달이면 전환 **차단**. 전환 후 회귀면 별칭을 블루로 즉시 롤백(유예 보관 덕분에 가능) | 롤백 후 원인 분석. 유예 기간(예: 7일) 내 결정 |
| 중복 제거 오탐 (단계 고유) | 다른 버전 문서가 하나로 묶여 개정판이 사라짐 | 정본 묶음에 `supersedes` 관계 포함 건수 | 버전 관계가 있으면 중복 묶음에서 제외하는 규칙 | 임계값 보수화 |

SLI 후보: ① 소스 변경 → 검색 반영 지연 p95(소스별) ② 삭제 이벤트 → **인덱스·캐시·메모리·골든셋 제거** p95(끝점별 SLI로 분리 가능: 인덱스는 이 페이지, 캐시는 3/01·3/03·3/04, 메모리는 3/08, 골든셋은 3/13·4/10이 각자 측정하고 여기서 합산)(불균형 ① 반영) ③ 대조 배치 후 유령·누락 건수 ④ DLQ 크기 ⑤ 경로별 지연 차. SLO 초안(예시): CDC 소스 ≤ 5분, SaaS 웹훅 ≤ 1h, 파일 공유 ≤ 24h; 삭제 전파 ≤ 15분(인덱스·캐시·메모리·골든셋 네 끝점 전부, 기밀·PII는 즉시); 대조 후 유령 0건; DLQ 체류 ≤ 48h. 쓰기 행동의 멱등성: 이벤트 키 `(doc_id, content_hash, event_type)`, at-least-once 전달을 전제로 모든 소비자가 멱등. 재처리는 "삭제 후 재생성". 톰스톤은 반복 적용해도 같은 상태. 물리 삭제는 유예 후 배치, 재실행 시 이미 삭제된 것은 건너뜀.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| `pipeline_version` 번들 (파서 + 청커 + 임베딩 모델 + 온톨로지 + 추출기) | **전체 인덱스**(블루/그린 트리거) | 평가셋 블루 vs 그린 비교 | 번들 구성 요소 전부 + 인덱스 별칭 |
| 변경 이벤트 스키마 (`doc_id`, `event_type`, 커서 형식) | 모든 생산자(01)·소비자(04·05·03) | 스키마 호환(추가 전용), 4종 이벤트 계약 테스트 | 소비자 어댑터 |
| 톰스톤·유예·보존 규칙 | 삭제 전파 동작, 저장량 | 삭제 시나리오 테스트(삭제·회수·만료·철회) | [10](10-access-control-governance.md) 보존 정책표 |
| 중복 제거 설정 (방식·임계값·정본 규칙) | 검색 결과 중복도, 오탐 | 라벨된 중복 쌍 셋 정밀도·재현율 | 03 `canonical_doc_id` |
| 대조 배치 설정 (주기·파티션·범위) | 유령 탐지 지연 | 의도적 삭제 주입 테스트 | 소스 인벤토리 |
| 변경 감지 방식 (소스별 해시/수정시각/웹훅/CDC) | 신선도 지연, 삭제 감지 가능성 | 소스별 변경 주입 테스트 | 01 커넥터 설정 |
| 블루/그린 런북 | 전환 안전성 | 전환 리허설 | 04 인덱스 별칭, 평가셋 |

롤백 단위는 "`pipeline_version` 번들 + 인덱스 별칭"이며, 별칭 전환 하나로 되돌아간다. 기술 부채로 기록할 것: 이벤트 기반으로 승격하지 않은 소스와 그 이유, 근사 중복 제거 미도입, 그래프 경로의 증분 미지원 범위(커뮤니티 요약 등), 블루/그린 저장 2배를 감당 못 해 유예 기간을 짧게 둔 컬렉션.

| **부하** | 변경률 10배 | 무상태 워커, 큐 | 워커 수, 레인, 파티션 | 수평 확장 + 디바운스 + 우선 레인 | 큐·워커 |

가장 자주 바뀌는 것: **지식**. 이 단계가 잘 설계되면 Part 2의 나머지 단계는 지식 변화를 "증분 재처리"라는 한 단어로 흡수할 수 있다. 두 번째는 **파이프라인 버전**(모델·규칙)이며, 이는 블루/그린이라는 단일 절차로 수렴시킨다. 코드 밖 설정으로 둘 것: 소스별 SLO·감지 방식·대조 주기, 우선 레인 정의, 디바운스 창, 톰스톤 유예·보존 기간표, 중복 임계값·정본 규칙, 재시도 상한, 블루/그린 평가 기준. 포트·어댑터 뒤에 둘 외부 의존: 메시지 브로커, 각 인덱스의 쓰기 API(`apply_change(event)` 포트 뒤에 벡터·BM25·그래프·메타데이터 어댑터), 소스 변경 감지 수단. 시점 재현성: 모든 파생물의 `pipeline_version`과 인덱스 별칭 전환 이력이 "그때 어떤 버전의 인덱스가 서빙했나"를 복원한다.

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성 표의 "탐지 신호"가 **실제로 어디서 나오는지**를 설계한다. 기준은 [Part 1/07 관측성 설계 요소](../01-foundations/07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md). 이 단계의 관측은 **흐름·적체 지표가 주력**이다(1/07 지표 3종 중 셋째). 변경 이벤트 하나가 여러 소비자(벡터·BM25·그래프·메타데이터, 삭제 레인은 캐시·메모리·골든셋까지)로 퍼지므로, `sync.propagate`는 **소비자별 자식 스팬**으로 갈라지고 원래 문서 트레이스에는 링크로 연결한다. 끝점별로 재지 않으면 "인덱스에선 지웠는데 캐시에 남은" 상태가 보이지 않는다.

| 기록 대상 | 스팬 / 이벤트 (이름, 부모) | 핵심 속성 (버전 키 포함) | 지표 (→ 어느 SLI) | 샘플링 · 보존 · PII |

샘플링·보존: 이벤트 메타는 전수, 문서 본문은 이 단계에 없다. 삭제 레인은 끝점 완료 시각까지 100% 보존하고 삭제 증명과 함께 감사 저장소로 복사한다. 테일 샘플링 대상(DLQ·카나리 실패·전환 차단)은 원 문서 트레이스까지 링크로 묶어 보존 기간을 연장한다.

|---|---|---|---|
| 신선도 조용히 악화 (장애 모드: 변경 큐·브로커 다운) | `sync.queue.consumed{*}`=0이 가장 짧은 소스 SLO의 3배(15분) 지속이면서 `sync.freshness_ms` 상승 | P1 | ① 브로커 상태·소비자 연결 확인 ② 01 커넥터 커서가 보존 중인지(유실 없음) 확인 ③ 복구 후 대조 배치로 누락분 보충 예약 |

대시보드에서 이 단계를 보는 뷰: ② Knowledge 패널 — 소스별 신선도 p95(SLO 선 포함), **끝점별 삭제 전파 p95**, 레인별 큐 깊이, DLQ 크기·사유, 경로 skew, 대조·카나리 결과, 전환 이력 타임라인 / ③ 비용 패널 — 전체 재색인(블루/그린) 1회 비용(이벤트 수 × 문서당 재처리 비용 — 04·05 비용을 `pipeline_version` 전환 시점으로 합산) / 감사 추적으로 넘기는 필드(관측 로그와 분리): 거버넌스 접점 표의 이벤트 ID·유형·수신·소비자별 완료 시각, 톰스톤 시각·사유, 물리 삭제 대상 목록·승인자, 전환 이력(번들 버전·평가 결과·승인자·롤백), 대조 결과 — 삭제 증명과 전환 승인자는 감사 저장소에만, 관측 스팬엔 `event_id`·결과 코드·끝점 목록 / 이 단계의 관측이 없으면 못 보는 장애: **톰스톤이 인덱스에는 적용됐지만 캐시·메모리·골든셋 끝점에서 빠진 상태** — 인덱스 기준 삭제 전파 SLI는 100%로 보이는데 삭제된 문서가 캐시된 답변으로 계속 나간다. `sync.delete.latency_ms{target}`와 `pending_targets[]`를 끝점별로 두지 않으면 보이지 않는다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5, 가역성 × 영향 범위) | upsert 재처리 **등급 1**. 톰스톤(검색 제외) **등급 2**(가역, 여러 사용자). 블루/그린 **전환** 등급 2(별칭 롤백 가능) → 규칙 게이트. **물리 삭제**는 두 등급으로 나눈다(기준 정의는 [10](10-access-control-governance.md)): 보존 만료 + 유예 경과의 **정책 배치 삭제 = 등급 4**(유예 중 가역, 정책 승인으로 갈음), 정보주체 요청·정책 밖 **일괄 물리 삭제 = 등급 5**(제안만 — 2인 승인 + 섀도(삭제 대상 목록 사전 검토) 후 사람이 실행). 어느 쪽이든 에이전트가 물리 삭제를 자동 실행하지 않는다(불균형 ⑧ 반영) |
| 가드레일 위치 (입력 / 출력 / 행동) | **행동**: 물리 삭제 게이트(유예·승인), 블루/그린 전환 게이트(평가셋), 전체 재색인 실행 게이트(비용 이벤트 승인). 톰스톤 적용은 모든 인덱스의 **출력** 기본 필터 |
| 게이트 출력 (통과 / 차단 / 승인 / 저하)과 판정 수단 | 전환: 통과 / 차단(평가셋 미달) / 승인. 삭제: 톰스톤 즉시 통과, 물리 삭제는 유예 후 통과 또는 승인. 판정은 **규칙만**(평가 수치·유예 시각·정책 매칭). 철회 선언 감지 같은 판정은 [09](09-ai-inside-the-pipeline.md)이되 **톰스톤 실행 전 규칙 재검증**(Rule ∧ Model) |
| 소유자 (A) | 데이터 엔지니어링 책임자(파이프라인·전환). 보존·삭제 정책은 데이터 소유자, 규제 관련 C는 법무 |
| 감사 추적에 남길 필드 | 이벤트 ID·유형·`doc_id`·`content_hash`·수신 시각·처리 완료 시각(소비자별), 톰스톤 시각·사유, 물리 삭제 시각·대상 파생물 목록·승인자, 블루/그린 전환 이력(번들 버전 전후·평가 결과·승인자·롤백 여부), 대조 배치 결과(유령·누락 건수) |

### 운영 준비도 체크
- [ ] 소스별 신선도 SLO·삭제 전파 SLO가 설정에 있고 지연 p95가 소비자별로 측정되는가
- [ ] 변경 큐가 하나이고 벡터·BM25·그래프·메타데이터가 모두 그 큐를 소비하는가
- [ ] 큐에 우선 레인(삭제·ACL 먼저)과 문서 단위 디바운스가 있는가
- [ ] 재처리 잡이 멱등(삭제 후 재생성, 같은 이벤트 2회 = 같은 결과)이고 재시도 상한·DLQ가 있는가
- [ ] 톰스톤 문서로 카나리 질의를 돌려 모든 인덱스에서 제외되는지 자동 확인하는가
- [ ] 대조 배치가 파티션 롤링으로 창 안에 끝나고 유령·누락을 큐에 재투입하는가
- [ ] 블루/그린 전환 게이트(평가셋)·별칭 롤백·유예 보관이 리허설되었는가
- [ ] 물리 삭제가 정책 배치(등급 4, 유예 후) / 요청·일괄(등급 5, 2인 승인 + 사람 실행)로 구분되어 있고, 삭제 증명이 남는가(불균형 ⑧ 반영)
- [ ] 삭제 레인 소비자에 Reasoning 결과·시맨틱 캐시, 메모리, 골든셋이 등록되어 있고 끝점별 제거 p95가 측정되는가(불균형 ① 반영)
- [ ] 운영 안정성 표의 탐지 신호마다 원천 스팬·지표(`sync.queue.consumed`, `sync.delete.latency_ms{target}`, `sync.dlq.size`, `sync.path_skew_ms`, `sync.reconcile.ghosts`, `sync.canary.fail{path}`, `sync.switch` 후 `index_version` 분해)가 있는가
- [ ] 알림마다 런북이 있고, 삭제 전파 알림이 끝점별(인덱스·캐시·메모리·골든셋)로 울리며 기밀·PII는 즉시 P1인가
