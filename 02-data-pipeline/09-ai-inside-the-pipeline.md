# 파이프라인 내부의 AI

> **범위**: 분류·정제·라벨링·추출에 LLM/결정 모델을 쓰는 법과 비용·품질 트레이드오프
> **시각화**: [`assets/html/data-pipeline-architecture.html`](../assets/html/data-pipeline-architecture.html) — 모든 노드에 걸치는 "판정 지점"

## 요약 (3줄)

1. 데이터 파이프라인 안에는 **판정 지점**이 수십 개 있다. 이 문서는 어떤 유형인가, 파싱이 쓸 만한가, 이 두 건은 중복인가, 이 트리플은 근거에 부합하는가. 이 판정을 전부 LLM에 맡기면 **문서 100만 건에서 인덱싱 비용이 서빙 비용을 넘는다**.
2. 배정 원칙은 [Part 1/02](../01-foundations/02-system1-vs-system2.md)와 같다. **규칙 → 결정 모델·소형 모델 → LLM** 순으로 가능한 가장 단순한 수단을 쓴다. 선택지가 닫혀 있으면 생성 모델이 필요 없다. 생성이 필요한 것(추출·요약·캡션)만 LLM이다.
3. 결정 모델(Jev / Decisions API)은 이 Part에서 가장 많은 적용점을 갖는 트렌드지만, 성능·비용 수치는 전부 `[벤더]`이고 **영어 중심 학습이라 한국어 평가셋 없이 채택할 수 없다**.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 파이프라인 판정 지점 목록과 각 지점의 선택지(닫힘/열림) ② 지점별 수단 배정표(규칙 / 결정 모델 / 소형 모델 / LLM) ③ 한국어 평가셋과 수단별 `[실측]` 결과 ④ 문서 건수 대비 비용 모델(정성 → 실측) ⑤ 저확신 처리 경로(사람 검토 큐) |
| **언제** (When) | 파이프라인 어느 단계든 "규칙으로 안 되는 판단"이 생길 때. **생략**: 소스가 정형이고 모든 판정이 결정론적일 때. **미뤄도 되는 것**: 결정 모델 도입(소형 분류기나 소형 LLM으로 시작해 건수가 늘면 비교) |
| **어떻게** (How) | ① 01~10 각 단계의 판정 지점을 전부 목록화 → ② 각 지점의 선택지가 닫혀 있는지 표시 → ③ 결정론으로 되는 것은 규칙 → ④ 닫힌 판정은 결정 모델·소형 분류기·소형 LLM을 **같은 한국어 평가셋**으로 비교 `[실측]` → ⑤ 열린 과업(추출·캡션·요약)만 LLM, 그 뒤에 검증기 → ⑥ 보정 확률 또는 점수로 저확신 큐 → ⑦ 건당 비용 × 예상 건수로 예산 산정 |
| **왜** (Why) | 판정을 LLM에 섞으면 ① 인덱싱 비용이 문서 수에 비례해 폭증하고 ② 같은 문서가 재처리 때마다 다른 라벨을 받아 중복·불일치가 생기며 ③ 확신도가 없어 사람 검토 임계값을 못 둔다. 반대로 전부 규칙으로 하면 자연어 판단이 필요한 지점에서 재현율이 무너진다 |

## 문제와 맥락

RAG 파이프라인의 초기 버전은 "LLM이 다 한다"로 시작하기 쉽다. 문서 유형 분류도, 품질 판정도, 중복 판정도, 메타데이터 추출도 프롬프트 하나씩. 문서 1천 건에선 문제가 없다. 10만 건부터 청구서가 보이고, 100만 건에선 다음이 동시에 터진다.

- **비용**: 판정 하나에 수십~수백 토큰을 생성. 문서당 판정이 5개면 문서당 LLM 호출 5회. 재처리·재색인 때마다 반복
- **비결정성**: 같은 문서가 어제는 "계약서", 오늘은 "합의서"로 분류. 메타데이터 필터가 흔들리고 중복 판정이 뒤집힌다
- **확신도 부재**: "이 문서는 폐기 선언인가"에 모델이 "네"라고 하면 그 "네"가 60%인지 99%인지 모른다. 사람 검토를 어디서 끊을지 정할 수 없다
- **한국어**: 영어 중심 모델이 한국어 비격식·혼합 언어·한자 혼용에서 품질이 떨어지는데, 벤치마크는 영어다

이 페이지는 판정 지점마다 **가장 싸고 가장 안정적인 수단**을 고르는 절차다.

### 수단 네 가지

| 수단 | 동작 | 비용 구조 | 확신도 | 재현성 | 변경 비용 | 한국어 |
|---|---|---|---|---|---|---|
| **규칙** | 코드·정규식·사전·택소노미 매핑 | 거의 0 | 없음(결정론) | 완전 | 코드 수정 | 사전·패턴을 직접 만들면 됨 |
| **소형 모델** (파인튜닝 분류기, NER, NLI) | 라벨 데이터로 학습한 BERT류·소형 LM | 학습 1회 + 추론 매우 저렴, 자체 호스팅 | softmax(보정 별도) | 높음 | 재학습(라벨 필요) | 한국어 사전학습 모델 존재, 자기 데이터로 학습 가능 |
| **결정 모델** (Jev / Decisions API) | 상태 + 타입드 질문 → 선택/점수/예·아니오 + 보정 확률. 텍스트 생성 없음 | 입력 토큰만 과금(보고). 출력 토큰 없음 | 보정 확률 (벤더 주장) | 높음(주장) | 질문 정의 수정 | **영어 중심 학습 → 한국어 자체 평가셋 필수** `[2차]` |
| **LLM** (소형 / 대형) | 프롬프트 → 생성 | 입력 + 출력 토큰, 출력이 비용의 큰 몫 | 없음 또는 비보정 | 낮음(온도 0이어도 흔들림) | 프롬프트 수정 | 모델별 편차, 대형은 양호 |

결정 모델 둘은 인터페이스는 같지만 내부가 다르다. **Jev는 결정 전용 모델**(비자기회귀 단일 패스, 병렬 샘플링, RLCD 주장)이고, **Decisions API는 범용 생성 모델(gpt-6-luna)의 출력을 제약한 엔드포인트**(`POST /v1/decisions`)다 `[벤더]` `[2차]`. 지연·비용·보정 품질이 다를 수 있으므로 `[실측]`은 따로 한다. 상세는 [Part 6/decision-models](../06-trends/decision-models.md).

### 문서 100만 건 기준 비용 구조 (정성)

구체 금액은 모델 단가·문서 길이·판정 수에 따라 달라 적지 않는다. **구조**만 비교한다.

| 수단 | 비용이 비례하는 것 | 100만 건에서의 양상 | 숨은 비용 |
|---|---|---|---|
| 규칙 | 거의 없음 (CPU) | 무시 가능 | 규칙 유지, 재현율 손실 |
| 소형 모델 | 추론 횟수 × 매우 작은 단가 (자체 GPU/CPU) | 낮음. 배치 처리로 더 낮음 | 라벨 데이터 구축, MLOps, 재학습 |
| 결정 모델 | 입력 토큰 수 × 단가. 출력 과금 없음(보고) | 입력만 과금이므로 LLM 대비 구조적으로 유리. **단, 수치는 `[벤더]`** | 한국어 평가셋, 벤더 종속, 보정 확인 |
| LLM 소형 | 입력 + 출력 토큰 | 판정당 출력 수십 토큰 × 판정 수 × 100만 → 인덱싱이 서빙 비용에 근접 | 비결정성 처리, 재시도 |
| LLM 대형 | 입력 + 출력 토큰 × 높은 단가 | 판정에 쓰면 인덱싱 비용이 서빙 비용을 초과 | 위와 같음 + 지연 |

보고된 단가로는 Jev $0.042 / 1M 입력 토큰, Decisions API $0.10 / 1M 입력 토큰(출력·캐시 과금 없음; 미공개라는 소스도 있음) `[2차]` 재확인 필요. Jev 측은 "LLM 워크플로우 대비 최대 200배 빠르고 400배 저렴", 지연 70~500ms E2E를 주장한다 `[벤더]` 독립 벤치마크 없음. **이 수치들로 예산을 짜지 않는다.** PoC에서 자기 문서 1천 건으로 건당 비용을 `[실측]`해 100만 건으로 외삽한다.

### 한국어 주의

| 문제 | 영향 | 대응 |
|---|---|---|
| 결정 모델의 영어 중심 학습 | 한국어 판정 정확도·보정이 영어 벤치마크와 다를 수 있음 | 한국어·혼합 언어·비격식·한자 혼용을 포함한 평가셋 필수. 불합격 시 소형 분류기 |
| 토큰 팽창 | 같은 문서가 더 많은 입력 토큰 → 입력 과금 수단의 비용↑ | 판정에 필요한 부분(제목·첫 문단·메타데이터)만 입력 |
| 한국어 소형 모델의 라벨 데이터 | 사내 라벨이 없으면 학습 불가 | LLM으로 초기 라벨 생성 → 사람 검수 → 소형 모델 학습(증류) |
| 벤치마크 부재 | 결정 모델·소형 모델의 한국어 공개 비교 없음 | 자체 `[실측]`이 유일한 근거 |

### 배정 절차

```
판정 지점 ─▶ 결정론으로 가능? ─예─▶ 규칙
                 │아니오
                 ▼
          선택지가 닫혀 있나? ─아니오─▶ LLM (추출·생성) ─▶ 검증기 (규칙·SHACL·NLI)
                 │예
                 ▼
          라벨 데이터 수천 건 이상 + 카테고리 고정? ─예─▶ 소형 분류기 (한국어 사전학습 기반)
                 │아니오 (라벨 적음 / 자주 바뀜 / 보정 확률 필요)
                 ▼
          결정 모델 vs 소형 LLM을 한국어 평가셋으로 비교 ─▶ 채택 + 저확신 큐 + 폴백(규칙 또는 보수적 기본값)
```

## 아키텍처 / 파이프라인

```
각 단계의 판정 지점 ─▶ 판정 추상화 계층 (질문 정의 + 선택지 enum + 입력 상태)
                              ├─ 규칙 엔진
                              ├─ 소형 모델 서빙 (배치)
                              ├─ 결정 모델 API (Jev | Decisions API)
                              └─ LLM (추출·캡션·요약 전용) ─▶ 검증기
                         ─▶ 결과 + 확신도 + 수단·버전 ─▶ 메타데이터 (03) 기록
                         ─▶ 확신도 < θ ─▶ 사람 검토 큐 ─▶ 라벨 축적 ─▶ 소형 모델 재학습 / 규칙 보강
```

**판정 추상화 계층**이 핵심이다. 질문 정의와 선택지 enum을 수단과 분리해 두면 결정 모델 ↔ 분류기 ↔ LLM을 같은 평가셋으로 바꿔 끼울 수 있고, 벤더 종속을 피한다. 선택지 enum은 온톨로지·택소노미([06](06-ontology-driven-modeling.md))에서 가져온다.

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 규칙 (정규식, 사전, 택소노미 매핑, 해시) | 결정론 판정: 확장자, 텍스트 레이어 유무, 정확 중복, ID 매칭, 등급 산정 | 자연어 의미 판단(문서 주제, 모순 여부) | 하 | 표준 | `[검증]` |
| 소형 분류기 (한국어 BERT류 파인튜닝) | 라벨 수천 건 이상, 카테고리 고정, 대량·저지연·자체 호스팅 | 라벨 없음, 카테고리 자주 변경 | 중 (학습·MLOps) | 표준 | `[검증]` |
| 전용 NER / PII 탐지 모델 | PII·엔티티 유형 탐지 | 사내 고유 유형(추가 학습 필요) | 하~중 | 표준 | `[검증]` |
| NLI 모델 (함의·모순) | 근거-트리플 정합성, 근거 간 모순 | 도메인 특수 추론, 긴 입력 | 중 | 안정 | `[검증]` |
| 결정 모델 — Jev | 닫힌 판정, 라벨 적음, 보정 확률 필요, 대량, 텍스트 입력 | 이미지 입력, 한국어 미검증 상태에서 채택, 설명 필요 | 하(호출) / 중(평가셋) | 신생 | `[벤더]` 성능·비용 / `[2차]` 가격 재확인 필요 |
| 결정 모델 — OpenAI Decisions API | 위와 유사 + 이미지 입력(스캔 문서 유형 판정 등), 이미 OpenAI 생태계 | 단일 모델 종속, 가격·상태 유동적 | 하~중 | 신생(베타) | `[2차]` 날짜·가격 소스 충돌 |
| 소형 LLM (프롬프트) | 프로토타입, 선택지 미확정, 초기 라벨 생성(증류용) | 대량 운영 판정, 보정 확률 필요 | 중 (토큰) | 안정 | `[검증]` 비보정·비결정 문제 |
| 대형 LLM (프롬프트) | 추출·캡션·요약 등 열린 과업, 고가치 소량 문서 | 닫힌 판정, 대량 | 상 | 안정 | `[검증]` |
| LLM → 소형 모델 증류 | 라벨 없이 시작해 대량 운영으로 가야 할 때 | 카테고리가 계속 바뀜 | 중 | 안정 | `[2차]` 실무 표준 |

### 선택 가이드

- **결정론으로 판정할 수 있다면** → 규칙. 이유: 확률로 판단할 이유가 없고 비용이 0에 가깝다
- **라벨이 수천 건 있고 카테고리가 고정이라면** → 한국어 소형 분류기. 이유: 가장 싸고 빠르며 자체 호스팅으로 데이터 반출 없음
- **라벨이 적고 질문이 자주 바뀌며 보정 확률로 검토 큐를 끊어야 한다면** → 결정 모델을 소형 LLM과 **같은 한국어 평가셋**으로 비교 후 채택. 이유: 질문 정의만 바꾸면 되고 입력만 과금(보고). 단 수치는 `[벤더]`
- **추출·캡션·요약이라면** → LLM + 뒤에 검증기. 이유: 생성이 필요한 유일한 과업. 검증기 없이 적재하지 않는다
- **판단이 어려우면** → 기본값: 규칙으로 걸러낸 뒤 소형 LLM으로 시작하고 라벨을 모아 소형 분류기로 증류, 결정 모델은 비교군으로 평가. 이유: 종속 없이 시작하고 데이터가 쌓이면 가장 싼 수단으로 이전

## 설계 시 고려사항 (체크리스트)

- [ ] 01~10 각 단계의 판정 지점을 목록화하고 선택지 닫힘/열림을 표시했는가
- [ ] 닫힌 판정 중 LLM이 맡은 것이 있다면 그 이유가 적혀 있는가
- [ ] 판정 추상화 계층(질문 정의 + enum + 수단 교체)이 있는가
- [ ] 선택지 enum이 온톨로지·택소노미에서 오는가
- [ ] 한국어·혼합 언어·비격식·한자 혼용을 포함한 평가셋이 있고 수단별 `[실측]`을 했는가
- [ ] 결정 모델의 보정 확률을 신뢰도 다이어그램으로 확인했는가
- [ ] 저확신 처리 경로(사람 검토 큐, 보수적 기본값)와 임계값이 있는가
- [ ] 수단 장애 시 폴백(규칙 또는 보수적 기본값)이 있는가
- [ ] 판정 결과·확신도·수단·버전이 메타데이터에 기록되는가([03](03-metadata-provenance.md))
- [ ] 1천 건 PoC로 건당 비용을 재고 예상 건수로 외삽했는가 (벤더 수치로 예산 짜지 않음)
- [ ] LLM 추출·생성 뒤에 검증기가 있는가
- [ ] 사람 검토 큐의 라벨이 소형 모델 재학습·규칙 보강으로 환류되는가

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 이 단계의 운영 단위는 **판정 지점**이다. 판정 추상화 계층([아키텍처 / 파이프라인] 참조)이 있어야 아래의 폴백·교체·감사가 지점마다 같은 방식으로 작동한다. 비용 구조와 벤더 수치의 검증 수준은 [핵심 개념]·[한계와 리스크] 참조 — 여기서는 반복하지 않는다.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 데이터 (문서 수) | 판정 호출 수가 선형 증가. LLM이 맡은 닫힌 판정이 비용을 지배. 결정 모델 API 레이트 리밋. 저확신 **검토 큐가 사람 처리량을 초과** | 규칙을 1차 필터로(호출 자체를 줄임), `(content_hash, question_version, method_version)` 캐시, 배치 추론, 티어 하향(LLM → 소형 분류기 증류), 검토 큐 상한에 맞춰 **임계값 동적 조정**(큐가 넘치면 확신도 임계를 올려 자동 처리 비율↑ — 단 행동 연결 판정은 제외) | 판정 지점 수 × 문서 수 × 입력 토큰(결정 모델) 또는 입출력 토큰(LLM); 저확신 비율(검토 인력) |
| 판정 지점 수 | 지점마다 다른 수단·프롬프트·임계값이 코드에 흩어져 "어디서 LLM을 쓰는지" 모름 | 판정 추상화 계층에 **배정표**(지점 → 수단 → 버전 → 임계값)를 설정으로, 프롬프트 리뷰로 숨은 판정 분리 | 지점 수 × 평가셋 유지 |
| 테넌트·도메인 | 테넌트별 라벨 체계·임계값 요구 | 질문 정의에 테넌트 키, 기본 정의 상속, 테넌트별 평가셋 | 테넌트 수 × 지점 수 |

판정 워커는 무상태다. 대량 재판정(질문 정의·모델 변경)은 배치 창에서 돌리고, 창 안에 못 끝나면 **영향 지점만 재판정 → 티어 하향 → 범위 축소** 순으로 결정한다.

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 판정 API(결정 모델·LLM) 다운 (의존 서비스 다운) | 메타데이터 라벨이 안 채워져 필터·등급이 "미분류"로 쏠림 | 호출 오류율, 판정 큐 적체 | 지점별 **보수적 기본값**으로 폴백: 분류 → `unclassified`, PII 여부 → "있음"(마스킹), 품질 합격 → "불합격"(격리), 중복 → "아님"(정본 묶음 안 함). 폴백 사용을 `method=fallback` 기록 → 복구 후 배치 재판정 | 다운 예시 30분 초과, 또는 폴백이 신선도 SLO를 위협 |
| 지연 급증 | 색인 지연 | 지점별 p95, 배치 처리량 | 배치 창 확대 → 소형 모델로 전환(배정표의 2차 수단) | 2차 수단 품질이 평가셋 기준 미달이면 사람 결정 |
| 유효하지 않은 출력·확신도 붕괴 (검증 실패 폭증) | 라벨 분포가 갑자기 바뀜 | 스키마 위반율, 확신도 분포 이동, 라벨 분포 drift | 해당 지점 수단을 **버전 고정 확인 → 2차 수단으로 전환**. 벤더 모델 묵시 업데이트 의심 시 섀도 비교 | 위반율 예시 2%p 이상 상승 |
| 재처리 간 라벨 불일치 (데이터 불일치) | 같은 문서가 어제·오늘 다른 유형. 필터·중복 판정 흔들림 | 재판정 시 라벨 변경률 | 캐시 키에 버전 포함 → 버전이 같으면 재호출 없이 캐시 반환. 변경은 버전 변경 시에만 | 캐시 미적중 재판정에서 변경률이 예시 5% 초과 → 비결정성 큰 수단 교체 검토 |
| 보정 드리프트 (단계 고유) | 검토 큐 임계값이 의미를 잃어 틀린 자동 판정 증가 | 주간 라벨 샘플의 신뢰도 다이어그램(ECE) | 임계값 보수화(검토 큐 비율↑) — 자동 이동은 이 **보수적 방향만** 허용(공통 규칙, 불균형 ⑦ 반영) | ECE가 예시 0.1 초과 → 재보정 또는 수단 교체 |
| 검토 큐 범람 (단계 고유) | 색인 지연, 검토자 피로 → 전부 승인 | 큐 크기·체류 시간, 검토자 승인률 급등 | 자동 대응은 **보수적 방향만**(보수적 기본값 처리·색인 지연 수용·검토 범위 유지). 비행동 판정의 자동 처리 비율을 높이는 임계값 조정은 **완화 방향이므로 자동 금지** — 운영 책임자 결정 + 사후 샘플 감사([Part 3/12](../03-agent-workflow-rag/12-guardrails-hitl.md)의 "임시 확대 결정, 사후 감사 대상"과 동일 절차). **행동 연결 판정(철회·PII·등급)은 임계값 유지**(불균형 ⑦ 반영) | 체류 예시 72h 초과 → 운영 책임자가 비행동 판정 임계값 완화 여부를 결정하고 결정·근거를 기록 |
| 벤더 가격·정책 변경 (단계 고유) | 비용 급증 또는 API 차단 | 건당 비용 추이, 예산 알림 | 예산 상한 도달 시 티어 하향 또는 해당 지점 폴백 | 월 예산 예시 80% 도달 |

SLI 후보: ① 1천 건당 판정 비용(지점별) ② 저확신(검토) 비율 ③ 사람 라벨 샘플 대비 정밀도 ④ 보정 오차(ECE) ⑤ 배치 판정 p95. SLO 초안(예시): 검토 비율 ≤ 5%, 정밀도 ≥ 95%(행동 연결 지점) / ≥ 90%(기타), ECE ≤ 0.05. 쓰기 행동의 멱등성: 판정 결과는 메타데이터에 `(doc_id, content_hash, question_id, question_version, method_version)` 키로 기록, 같은 키는 재호출 없이 캐시. 재판정은 버전 변경 시에만. 외부 API 재시도 상한 예시 3회, 초과 시 폴백 기본값.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| 질문 정의 (`question_id`, 선택지 enum, 입력 상태 스키마) | 해당 지점의 모든 판정, 하류 필터·등급 | 한국어 평가셋 정밀도·재현율 | enum은 온톨로지 버전([06](06-ontology-driven-modeling.md))과 묶음, 영향 문서 재판정 계획 |
| 배정표 (지점 → 1차·2차 수단 → 버전 → 임계값) | 비용·품질·폴백 동작 | 같은 평가셋으로 수단 간 비교 | 폴백 기본값 정의 |
| 프롬프트 (LLM·소형 LLM 지점) | 출력 분포 | 평가셋, 스키마 위반율 | 프롬프트-모델 호환 매트릭스 |
| 소형 모델 (버전 + 학습 데이터 스냅샷) | 해당 지점 | 홀드아웃 평가, 보정 곡선 | 서빙 설정, 라벨 스냅샷 보관 |
| 결정 모델 벤더·버전 | 해당 지점의 보정·지연·비용 | 평가셋 + 신뢰도 다이어그램 | 어댑터 버전, 임계값 재보정 |
| 임계값·검토 큐 정책 | 자동/검토 비율 | 보정 곡선 기반 시뮬레이션 | 검토 인력 계획. 자동 이동은 보수적 방향(검토 확대)만, 완화는 사람 결정 + 사후 샘플 감사(불균형 ⑦ 반영) |
| 한국어 평가셋 (지점별) | 모든 비교의 기준 | 평가셋 자체의 커버리지(비격식·혼합·한자) | — |

롤백 단위는 "질문 정의 + 수단 버전 + 임계값" 지점 단위 묶음. 기술 부채로 기록할 것: 닫힌 판정에 LLM을 쓰고 있는 지점과 증류 계획, 결정 모델을 비교군으로만 두는 이유(한국어 `[실측]` 미완), 라벨 수천 건 미확보 지점, 보정 곡선을 아직 측정하지 않은 지점, 프롬프트 안에 숨어 분리되지 않은 판정.

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **규칙·질문 정의** (가장 잦음) | 임계값 조정, 라벨 추가, 새 판정 지점, 검토 정책 | 판정 추상화 계층 `decide(question_id, state) → {choice, confidence, method, version}` | 질문 정의·임계값 설정 | **설정 교체 + 평가셋 회귀**(재배포 없음). 라벨 추가는 enum 버전 + 영향 문서만 재판정 | 해당 지점의 메타데이터 |
| **모델** (두 번째) | 결정 모델 벤더·버전 교체, 가격 변경, 소형 모델 재학습, LLM 교체 | 같은 포트 | 수단 어댑터(규칙 / 분류기 / 결정 모델 / LLM) — **인터페이스가 같아 바꿔 끼움** | 어댑터 교체 + **섀도**(새 수단 결과를 기록만) + 평가셋 비교 + 임계값 재보정 → 전환. 영향 지점만 재판정 | 해당 지점 |
| **도메인 모델** | 택소노미·온톨로지 클래스 변경 → 선택지 enum 변경 | enum은 온톨로지 참조 | enum 값 | 매핑 테이블로 라벨 이전(개명), 분할 시만 재판정 | 해당 지점 + 필터 어휘 |
| **지식** | 새 문서 유형·소스 → 판정 입력 분포 변화 | 포트 | 라우팅 규칙 | 유형별 배정표 행 추가, 평가셋에 새 유형 샘플 추가 | 해당 유형 |
| **사용자 환경** | 언어 혼합 비율 변화, 새 테넌트 도메인 | 포트 | 평가셋·임계값 | 평가셋 확장 + 테넌트별 임계값 | 평가셋, 해당 테넌트 |
| **프로토콜** | 결정 모델 API 사양 변경(베타 → GA 등), SDK 메이저 업 | 포트 | 어댑터 | 어댑터만 교체, 버전 고정 + 계획된 업그레이드 창 | 어댑터 경계만 |

가장 자주 바뀌는 것: **규칙·질문 정의**(임계값·라벨), 그 다음 **모델**(특히 결정 모델처럼 신생 벤더의 버전·가격·사양). 판정 추상화 계층이 이 둘을 모두 **설정 교체와 어댑터 교체**로 가둔다. 코드 밖 설정으로 둘 것: 질문 정의·enum, 배정표, 임계값·검토 정책, 프롬프트, 폴백 기본값, 예산 상한, 평가셋 참조. 포트·어댑터 뒤에 둘 외부 의존: 결정 모델 API(Jev / Decisions API), LLM API, 소형 모델 서빙, NLI·NER 모델. 시점 재현성: 메타데이터의 `(question_version, method, method_version, confidence, threshold_at)`로 "그때 왜 그렇게 분류됐나"를 복원한다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5, 가역성 × 영향 범위) | 메타데이터·필터로만 이어지는 판정은 **등급 2**(여러 사용자, 재판정으로 가역). **행동으로 이어지는 판정**(철회 선언 → 톰스톤, PII → 마스킹, 기밀 등급 → ACL)은 판정 자체가 아니라 **그 행동의 등급**을 따른다([07](07-freshness-and-sync.md) 톰스톤 등급 2, 물리 삭제는 정책 배치 4 / 요청·일괄 5 — 정의는 [10](10-access-control-governance.md), 정책 변경 등급 3)(불균형 ⑧ 반영). 이때 모델 판정은 보조이고 **규칙이 최종 결정권**(Rule ∧ Model) |
| 가드레일 위치 (입력 / 출력 / 행동) | **출력**: 판정 결과의 스키마 검증 + 확신도 임계 → 통과 / 저하(검토 큐) / 차단(폴백 기본값). **행동**: 행동 연결 판정은 실행 전 규칙 재검증 게이트. LLM 추출·생성 뒤 검증기(규칙·SHACL·NLI) |
| 게이트 출력 (통과 / 차단 / 승인 / 저하)과 판정 수단 | 통과(확신도 ≥ θ) / 저하(검토 큐 = 사람 승인) / 차단(스키마 위반·폴백). θ의 자동 이동은 **보수적 방향(판정 범위 축소·검토 큐 확대)만**, 완화 방향은 운영 책임자 결정 + 사후 샘플 감사(불균형 ⑦ 반영). 판정 수단 순서는 **규칙 → 결정 모델·분류기 → LLM**이며, 보안·권한·삭제 관련은 규칙만 |
| 소유자 (A) | 질문 정의·임계값은 제품 책임자(도메인 전문가 C), 수단·모델 교체는 아키텍트. AI 엔지니어가 R. 검토 큐 운영은 운영 책임자 |
| 감사 추적에 남길 필드 | `question_id`·`question_version`, `method`·`method_version`, 선택값, 확신도, 적용 임계값, 폴백 여부, 검토자 ID·시각(사람 판정 시), 캐시 적중 여부, 비용(토큰·호출) |

### 운영 준비도 체크
- [ ] 모든 판정 지점이 배정표에 있고 1차·2차 수단·폴백 기본값·임계값이 설정으로 있는가
- [ ] 판정 API 다운 시 지점별 보수적 기본값 폴백이 자동이고 `method=fallback`이 기록되는가
- [ ] 판정 결과가 `(content_hash, question_version, method_version)` 키로 캐시되어 재처리 시 재과금·불일치가 없는가
- [ ] 보정 오차(ECE)와 라벨 분포 drift를 주기적으로 측정하고 임계 초과 시 수단 전환 규칙이 있는가
- [ ] 검토 큐 상한·체류 알림이 있고, 범람 시 자동 조정은 보수적 방향만이며 비행동 판정의 완화는 운영 책임자 결정 + 사후 샘플 감사로 기록되는가(불균형 ⑦ 반영)
- [ ] 행동으로 이어지는 판정이 실행 전 규칙 재검증 게이트를 거치는가
- [ ] 수단 교체가 섀도 → 평가셋 → 전환 절차로 가능하고 어댑터 교체만으로 끝나는가
- [ ] 건당 비용·월 예산 알림이 있고 벤더 수치가 아니라 `[실측]`으로 예산을 잡았는가
