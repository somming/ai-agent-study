# 파이프라인 내부의 AI

> **범위**: 분류·정제·라벨링·추출에 LLM/결정 모델을 쓰는 법과 비용·품질 트레이드오프
> **시각화**: [`assets/html/data-pipeline-architecture.html`](../assets/html/data-pipeline-architecture.html) — 모든 노드에 걸치는 "판정 지점"

## 요약 (3줄)

1. 데이터 파이프라인 안에는 **판정 지점**이 수십 개 있다. 이 문서는 어떤 유형인가, 파싱이 쓸 만한가, 이 두 건은 중복인가, 이 트리플은 근거에 부합하는가. 이 판정을 전부 LLM에 맡기면 **문서 100만 건에서 인덱싱 비용이 서빙 비용을 넘는다**.
2. 배정 원칙은 [Part 1/02](../01-foundations/02-system1-vs-system2.md)와 같다. **규칙 → 결정 모델·소형 모델 → LLM** 순으로 가능한 가장 단순한 수단을 쓴다. 선택지가 닫혀 있으면 생성 모델이 필요 없다. 생성이 필요한 것(추출·요약·캡션)만 LLM이다.
3. 결정 모델(Jev / Decisions API)은 이 Part에서 가장 많은 적용점을 갖는 트렌드지만, 성능·비용 수치는 전부 `[벤더]`이고 **영어 중심 학습이라 한국어 평가셋 없이 채택할 수 없다**.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 파이프라인 판정 지점 목록과 각 지점의 선택지(닫힘/열림) ② 지점별 수단 배정표(규칙 / 결정 모델 / 소형 모델 / LLM) ③ 한국어 평가셋과 수단별 `[실측]` 결과 ④ 문서 건수 대비 비용 모델(정성 → 실측) ⑤ 저확신 처리 경로(사람 검토 큐) |
| **언제** (When) | 파이프라인 어느 단계든 "규칙으로 안 되는 판단"이 생길 때. **생략**: 소스가 정형이고 모든 판정이 결정론적일 때. **미뤄도 되는 것**: 결정 모델 도입(소형 분류기나 소형 LLM으로 시작해 건수가 늘면 비교) |
| **어떻게** (How) | ① 01~10 각 단계의 판정 지점을 전부 목록화 → ② 각 지점의 선택지가 닫혀 있는지 표시 → ③ 결정론으로 되는 것은 규칙 → ④ 닫힌 판정은 결정 모델·소형 분류기·소형 LLM을 **같은 한국어 평가셋**으로 비교 `[실측]` → ⑤ 열린 과업(추출·캡션·요약)만 LLM, 그 뒤에 검증기 → ⑥ 보정 확률 또는 점수로 저확신 큐 → ⑦ 건당 비용 × 예상 건수로 예산 산정 |
| **왜** (Why) | 판정을 LLM에 섞으면 ① 인덱싱 비용이 문서 수에 비례해 폭증하고 ② 같은 문서가 재처리 때마다 다른 라벨을 받아 중복·불일치가 생기며 ③ 확신도가 없어 사람 검토 임계값을 못 둔다. 반대로 전부 규칙으로 하면 자연어 판단이 필요한 지점에서 재현율이 무너진다 |

## 문제와 맥락

RAG 파이프라인의 초기 버전은 "LLM이 다 한다"로 시작하기 쉽다. 문서 유형 분류도, 품질 판정도, 중복 판정도, 메타데이터 추출도 프롬프트 하나씩. 문서 1천 건에선 문제가 없다. 10만 건부터 청구서가 보이고, 100만 건에선 다음이 동시에 터진다.

- **비용**: 판정 하나에 수십~수백 토큰을 생성. 문서당 판정이 5개면 문서당 LLM 호출 5회. 재처리·재색인 때마다 반복
- **비결정성**: 같은 문서가 어제는 "계약서", 오늘은 "합의서"로 분류. 메타데이터 필터가 흔들리고 중복 판정이 뒤집힌다
- **확신도 부재**: "이 문서는 폐기 선언인가"에 모델이 "네"라고 하면 그 "네"가 60%인지 99%인지 모른다. 사람 검토를 어디서 끊을지 정할 수 없다
- **한국어**: 영어 중심 모델이 한국어 비격식·혼합 언어·한자 혼용에서 품질이 떨어지는데, 벤치마크는 영어다

이 페이지는 판정 지점마다 **가장 싸고 가장 안정적인 수단**을 고르는 절차다.

### 수단 네 가지

| 수단 | 동작 | 비용 구조 | 확신도 | 재현성 | 변경 비용 | 한국어 |
|---|---|---|---|---|---|---|
| **규칙** | 코드·정규식·사전·택소노미 매핑 | 거의 0 | 없음(결정론) | 완전 | 코드 수정 | 사전·패턴을 직접 만들면 됨 |
| **소형 모델** (파인튜닝 분류기, NER, NLI) | 라벨 데이터로 학습한 BERT류·소형 LM | 학습 1회 + 추론 매우 저렴, 자체 호스팅 | softmax(보정 별도) | 높음 | 재학습(라벨 필요) | 한국어 사전학습 모델 존재, 자기 데이터로 학습 가능 |
| **결정 모델** (Jev / Decisions API) | 상태 + 타입드 질문 → 선택/점수/예·아니오 + 보정 확률. 텍스트 생성 없음 | 입력 토큰만 과금(보고). 출력 토큰 없음 | 보정 확률 (벤더 주장) | 높음(주장) | 질문 정의 수정 | **영어 중심 학습 → 한국어 자체 평가셋 필수** `[2차]` |
| **LLM** (소형 / 대형) | 프롬프트 → 생성 | 입력 + 출력 토큰, 출력이 비용의 큰 몫 | 없음 또는 비보정 | 낮음(온도 0이어도 흔들림) | 프롬프트 수정 | 모델별 편차, 대형은 양호 |

결정 모델 둘은 인터페이스는 같지만 내부가 다르다. **Jev는 결정 전용 모델**(비자기회귀 단일 패스, 병렬 샘플링, RLCD 주장)이고, **Decisions API는 범용 생성 모델(gpt-6-luna)의 출력을 제약한 엔드포인트**(`POST /v1/decisions`)다 `[벤더]` `[2차]`. 지연·비용·보정 품질이 다를 수 있으므로 `[실측]`은 따로 한다. 상세는 [Part 6/decision-models](../06-trends/decision-models.md).

### 문서 100만 건 기준 비용 구조 (정성)

구체 금액은 모델 단가·문서 길이·판정 수에 따라 달라 적지 않는다. **구조**만 비교한다.

| 수단 | 비용이 비례하는 것 | 100만 건에서의 양상 | 숨은 비용 |
|---|---|---|---|
| 규칙 | 거의 없음 (CPU) | 무시 가능 | 규칙 유지, 재현율 손실 |
| 소형 모델 | 추론 횟수 × 매우 작은 단가 (자체 GPU/CPU) | 낮음. 배치 처리로 더 낮음 | 라벨 데이터 구축, MLOps, 재학습 |
| 결정 모델 | 입력 토큰 수 × 단가. 출력 과금 없음(보고) | 입력만 과금이므로 LLM 대비 구조적으로 유리. **단, 수치는 `[벤더]`** | 한국어 평가셋, 벤더 종속, 보정 확인 |
| LLM 소형 | 입력 + 출력 토큰 | 판정당 출력 수십 토큰 × 판정 수 × 100만 → 인덱싱이 서빙 비용에 근접 | 비결정성 처리, 재시도 |
| LLM 대형 | 입력 + 출력 토큰 × 높은 단가 | 판정에 쓰면 인덱싱 비용이 서빙 비용을 초과 | 위와 같음 + 지연 |

보고된 단가로는 Jev $0.042 / 1M 입력 토큰, Decisions API $0.10 / 1M 입력 토큰(출력·캐시 과금 없음; 미공개라는 소스도 있음) `[2차]` 재확인 필요. Jev 측은 "LLM 워크플로우 대비 최대 200배 빠르고 400배 저렴", 지연 70~500ms E2E를 주장한다 `[벤더]` 독립 벤치마크 없음. **이 수치들로 예산을 짜지 않는다.** PoC에서 자기 문서 1천 건으로 건당 비용을 `[실측]`해 100만 건으로 외삽한다.

### 한국어 주의

| 문제 | 영향 | 대응 |
|---|---|---|
| 결정 모델의 영어 중심 학습 | 한국어 판정 정확도·보정이 영어 벤치마크와 다를 수 있음 | 한국어·혼합 언어·비격식·한자 혼용을 포함한 평가셋 필수. 불합격 시 소형 분류기 |
| 토큰 팽창 | 같은 문서가 더 많은 입력 토큰 → 입력 과금 수단의 비용↑ | 판정에 필요한 부분(제목·첫 문단·메타데이터)만 입력 |
| 한국어 소형 모델의 라벨 데이터 | 사내 라벨이 없으면 학습 불가 | LLM으로 초기 라벨 생성 → 사람 검수 → 소형 모델 학습(증류) |
| 벤치마크 부재 | 결정 모델·소형 모델의 한국어 공개 비교 없음 | 자체 `[실측]`이 유일한 근거 |

### 배정 절차

```
판정 지점 ─▶ 결정론으로 가능? ─예─▶ 규칙
                 │아니오
                 ▼
          선택지가 닫혀 있나? ─아니오─▶ LLM (추출·생성) ─▶ 검증기 (규칙·SHACL·NLI)
                 │예
                 ▼
          라벨 데이터 수천 건 이상 + 카테고리 고정? ─예─▶ 소형 분류기 (한국어 사전학습 기반)
                 │아니오 (라벨 적음 / 자주 바뀜 / 보정 확률 필요)
                 ▼
          결정 모델 vs 소형 LLM을 한국어 평가셋으로 비교 ─▶ 채택 + 저확신 큐 + 폴백(규칙 또는 보수적 기본값)
```

## 아키텍처 / 파이프라인

```
각 단계의 판정 지점 ─▶ 판정 추상화 계층 (질문 정의 + 선택지 enum + 입력 상태)
                              ├─ 규칙 엔진
                              ├─ 소형 모델 서빙 (배치)
                              ├─ 결정 모델 API (Jev | Decisions API)
                              └─ LLM (추출·캡션·요약 전용) ─▶ 검증기
                         ─▶ 결과 + 확신도 + 수단·버전 ─▶ 메타데이터 (03) 기록
                         ─▶ 확신도 < θ ─▶ 사람 검토 큐 ─▶ 라벨 축적 ─▶ 소형 모델 재학습 / 규칙 보강
```

**판정 추상화 계층**이 핵심이다. 질문 정의와 선택지 enum을 수단과 분리해 두면 결정 모델 ↔ 분류기 ↔ LLM을 같은 평가셋으로 바꿔 끼울 수 있고, 벤더 종속을 피한다. 선택지 enum은 온톨로지·택소노미([06](06-ontology-driven-modeling.md))에서 가져온다.

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 규칙 (정규식, 사전, 택소노미 매핑, 해시) | 결정론 판정: 확장자, 텍스트 레이어 유무, 정확 중복, ID 매칭, 등급 산정 | 자연어 의미 판단(문서 주제, 모순 여부) | 하 | 표준 | `[검증]` |
| 소형 분류기 (한국어 BERT류 파인튜닝) | 라벨 수천 건 이상, 카테고리 고정, 대량·저지연·자체 호스팅 | 라벨 없음, 카테고리 자주 변경 | 중 (학습·MLOps) | 표준 | `[검증]` |
| 전용 NER / PII 탐지 모델 | PII·엔티티 유형 탐지 | 사내 고유 유형(추가 학습 필요) | 하~중 | 표준 | `[검증]` |
| NLI 모델 (함의·모순) | 근거-트리플 정합성, 근거 간 모순 | 도메인 특수 추론, 긴 입력 | 중 | 안정 | `[검증]` |
| 결정 모델 — Jev | 닫힌 판정, 라벨 적음, 보정 확률 필요, 대량, 텍스트 입력 | 이미지 입력, 한국어 미검증 상태에서 채택, 설명 필요 | 하(호출) / 중(평가셋) | 신생 | `[벤더]` 성능·비용 / `[2차]` 가격 재확인 필요 |
| 결정 모델 — OpenAI Decisions API | 위와 유사 + 이미지 입력(스캔 문서 유형 판정 등), 이미 OpenAI 생태계 | 단일 모델 종속, 가격·상태 유동적 | 하~중 | 신생(베타) | `[2차]` 날짜·가격 소스 충돌 |
| 소형 LLM (프롬프트) | 프로토타입, 선택지 미확정, 초기 라벨 생성(증류용) | 대량 운영 판정, 보정 확률 필요 | 중 (토큰) | 안정 | `[검증]` 비보정·비결정 문제 |
| 대형 LLM (프롬프트) | 추출·캡션·요약 등 열린 과업, 고가치 소량 문서 | 닫힌 판정, 대량 | 상 | 안정 | `[검증]` |
| LLM → 소형 모델 증류 | 라벨 없이 시작해 대량 운영으로 가야 할 때 | 카테고리가 계속 바뀜 | 중 | 안정 | `[2차]` 실무 표준 |

### 선택 가이드

- **결정론으로 판정할 수 있다면** → 규칙. 이유: 확률로 판단할 이유가 없고 비용이 0에 가깝다
- **라벨이 수천 건 있고 카테고리가 고정이라면** → 한국어 소형 분류기. 이유: 가장 싸고 빠르며 자체 호스팅으로 데이터 반출 없음
- **라벨이 적고 질문이 자주 바뀌며 보정 확률로 검토 큐를 끊어야 한다면** → 결정 모델을 소형 LLM과 **같은 한국어 평가셋**으로 비교 후 채택. 이유: 질문 정의만 바꾸면 되고 입력만 과금(보고). 단 수치는 `[벤더]`
- **추출·캡션·요약이라면** → LLM + 뒤에 검증기. 이유: 생성이 필요한 유일한 과업. 검증기 없이 적재하지 않는다
- **판단이 어려우면** → 기본값: 규칙으로 걸러낸 뒤 소형 LLM으로 시작하고 라벨을 모아 소형 분류기로 증류, 결정 모델은 비교군으로 평가. 이유: 종속 없이 시작하고 데이터가 쌓이면 가장 싼 수단으로 이전

## 설계 시 고려사항 (체크리스트)

- [ ] 01~10 각 단계의 판정 지점을 목록화하고 선택지 닫힘/열림을 표시했는가
- [ ] 닫힌 판정 중 LLM이 맡은 것이 있다면 그 이유가 적혀 있는가
- [ ] 판정 추상화 계층(질문 정의 + enum + 수단 교체)이 있는가
- [ ] 선택지 enum이 온톨로지·택소노미에서 오는가
- [ ] 한국어·혼합 언어·비격식·한자 혼용을 포함한 평가셋이 있고 수단별 `[실측]`을 했는가
- [ ] 결정 모델의 보정 확률을 신뢰도 다이어그램으로 확인했는가
- [ ] 저확신 처리 경로(사람 검토 큐, 보수적 기본값)와 임계값이 있는가
- [ ] 수단 장애 시 폴백(규칙 또는 보수적 기본값)이 있는가
- [ ] 판정 결과·확신도·수단·버전이 메타데이터에 기록되는가([03](03-metadata-provenance.md))
- [ ] 1천 건 PoC로 건당 비용을 재고 예상 건수로 외삽했는가 (벤더 수치로 예산 짜지 않음)
- [ ] LLM 추출·생성 뒤에 검증기가 있는가
- [ ] 사람 검토 큐의 라벨이 소형 모델 재학습·규칙 보강으로 환류되는가

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 결정 모델 성능·비용이 벤더 주장뿐 | 기대 지연·비용·정확도 미달 | PoC `[실측]`, 비교군(소형 분류기·소형 LLM) 유지 |
| 영어 중심 학습 (Jev 명시) | 한국어 판정 품질 저하 | 한국어 평가셋 필수, 불합격 시 분류기 |
| 보정 확률의 실제 보정 여부 미확인 | 검토 큐 임계값이 의미 없음 | 보정 곡선 측정 후 임계값 설정 |
| 유효한 출력 ≠ 올바른 판정 | 스키마가 맞아도 틀릴 수 있음 | 행동(삭제·권한)으로 이어지는 판정은 규칙 재검증 |
| 벤더 종속 (특히 Decisions API 단일 모델) | 가격·정책 변경 | 판정 추상화 계층으로 교체 가능하게 |
| 소형 모델의 라벨 비용 | 초기 라벨 수천 건 확보 어려움 | LLM 초기 라벨 → 사람 검수 → 증류 |
| LLM 추출의 비결정성 | 재처리 때마다 다른 결과 | 원본 해시 기준 캐시, 버전 고정, 검증기 |
| 판정 지점 누락 | 암묵적으로 LLM 프롬프트 안에 숨은 판정 | 프롬프트 리뷰로 "판정"을 분리해 목록화 |
