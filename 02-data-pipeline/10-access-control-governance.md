# 접근 제어와 거버넌스

> **범위**: ACL-aware retrieval, PII 마스킹, 멀티테넌시, 데이터 보존 정책
> **시각화**: [`assets/html/data-pipeline-architecture.html`](../assets/html/data-pipeline-architecture.html) — "동기화·ACL" 노드

## 요약 (3줄)

1. RAG의 접근 제어는 "사용자가 볼 수 없는 문서가 **검색 결과에도, 컨텍스트에도, 답변에도** 들어가지 않는다"는 것이다. 셋 중 하나만 막으면 누출이다. 프롬프트로 "권한 없는 내용은 말하지 마"라고 쓰는 것은 접근 제어가 아니다.
2. 강제 지점은 세 가지 패턴(인덱스 분리 / 메타데이터 필터 / 쿼리 시 ACL 조인) 중 하나 이상이고, 어느 패턴이든 **검색 전(pre-filter)에 적용**하고 **렌더 전에 재확인**한다. 소스 권한 변경이 인덱스에 전파되는 경로([07](07-freshness-and-sync.md))가 없으면 모든 패턴이 무의미하다.
3. PII는 **가능한 한 이른 시점**(수집·파싱 직후)에 탐지·분류하고, 마스킹 시점은 용도에 따라 달리한다. 인덱스에 들어간 PII는 임베딩에서도 삭제가 어렵다. 보존·삭제 정책은 "원본 삭제 = 파생물 전체 삭제"가 되게 처음부터 계보를 설계한다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 권한 모델(주체·그룹·테넌트·기밀 등급)과 인덱스 강제 패턴 ② 소스 ACL → 인덱스 ACL 동기화 경로 ③ PII 탐지·분류·마스킹 정책(시점·방식·예외) ④ 멀티테넌시 격리 수준 ⑤ 보존 기간·삭제 요청 처리·삭제 증명 ⑥ 감사 로그(누가 무엇을 검색·열람했나) |
| **언제** (When) | 소스에 권한이 있거나 PII가 있거나 테넌트가 둘 이상이면 **처음부터**. 생략 가능: 전 직원 공개 문서만, 단일 테넌트, PII 없음 — 이 셋을 모두 **확인**했을 때만. 미뤄도 되는 것: 테넌트별 물리 분리(논리 분리로 시작), 삭제 증명 자동화 |
| **어떻게** (How) | ① 소스별 권한 모델 조사(ACL 형태, 그룹 해석 방식, 변경 빈도) → ② 강제 패턴 선택(아래 비교표) → ③ 메타데이터에 `acl`, `tenant_id`, `classification`, `pii_flags` 필수화([03](03-metadata-provenance.md)) → ④ 검색 전 필터 + 렌더 전 재확인(`acl_checked`) → ⑤ PII 탐지를 파싱 직후에, 마스킹 시점·방식 결정 → ⑥ 소스 권한 변경 → 인덱스 전파 경로 → ⑦ 보존·삭제 정책과 계보 기반 파생물 삭제 → ⑧ 감사 로그 + 정기 권한 대조 |
| **왜** (Why) | 권한 없는 문서가 컨텍스트에 들어가면 모델이 "말하지 않아도" 답변에 영향을 주고, 로그에 남는다. 후 필터(post-filter)만 쓰면 결과 수가 모자라거나 순위가 왜곡된다. PII를 인덱싱 뒤에 발견하면 벡터·BM25·그래프·캐시·로그에서 모두 지워야 하는데 임베딩에선 "부분 삭제"가 안 된다 |

## 문제와 맥락

RAG는 **권한 경계를 가로질러 데이터를 모으는** 시스템이다. 인사·재무·고객·개발 문서가 한 인덱스에 들어가고, 한 질문이 모든 컬렉션을 훑는다. 이것이 RAG의 가치이자 위험이다.

- **검색 누출**: 사용자가 못 보는 문서가 top-k에 들어가 컨텍스트로 모델에 전달된다. 모델이 그 내용을 직접 인용하지 않아도 답변에 영향을 주고, 트레이스·로그에 남는다
- **권한 드리프트**: 퇴사·부서 이동·공유 해제가 소스에선 반영됐지만 인덱스의 ACL은 색인 당시 그대로다
- **PII 확산**: 메일·채팅·티켓에 섞인 주민번호·전화번호·계좌가 청크·벡터·캡션·요약·캐시에 복제된다. 삭제 요청이 오면 어디까지 지워야 하는지 모른다
- **테넌트 혼선**: SaaS형 서비스에서 A사 질문에 B사 문서가 유사도로 끌려온다
- **보존 위반**: 보존 기간이 지난 문서가 "검색은 안 되지만 저장소에 남아" 규제 위반이 된다

이 단계는 위 문제를 **데이터 구조와 강제 지점**으로 막는다. [Part 5/01](../05-cross-cutting/01-security-prompt-injection.md)의 인젝션 방어, [Part 5/04](../05-cross-cutting/04-governance-explainability.md)의 규제 대응과 짝을 이룬다.

## 핵심 개념

### 강제 패턴 세 가지

| 패턴 | 동작 | 장점 | 단점 | 적합 |
|---|---|---|---|---|
| **인덱스 분리** | 권한 경계(테넌트·기밀 등급·부서)마다 별도 인덱스/컬렉션. 사용자는 허용된 인덱스만 검색 | 격리가 물리적, 누출 경로 단순, 필터 후 결과 부족 없음 | 인덱스 수 폭발(경계가 많으면), 교차 검색 시 결과 병합, 문서가 여러 경계에 속하면 중복 저장 | 테넌트 격리, 기밀 등급 소수 |
| **메타데이터 필터** | 청크마다 `acl`(허용 주체/그룹 목록) 저장, 검색 시 사용자의 주체 집합과 교집합 조건을 **사전 필터**로 | 단일 인덱스, 문서별 세밀 권한 | 그룹 해석(중첩 그룹)을 색인 시 평탄화해야 함, ACL 변경 시 청크 메타데이터 갱신, 벡터DB 필터 표현력 한계 | 문서별 ACL이 다양한 사내 문서 |
| **쿼리 시 ACL 조인** | 인덱스엔 `doc_id`만, 검색 후보를 권한 서비스(또는 소스 시스템)에 실시간 조회해 걸러냄 | 항상 최신 권한, 소스가 단일 진실 원천 | 지연(후보 수만큼 조회), 후 필터라 결과 부족·순위 왜곡, 권한 서비스 장애 시 검색 불가 | 권한이 매우 자주 바뀌고 지연 허용 |

운영에선 **조합**한다. 테넌트는 인덱스 분리, 테넌트 안의 문서 권한은 메타데이터 사전 필터, 렌더 직전에 소스 권한 재확인(쿼리 시 조인의 축소판). 어느 패턴이든 citation의 `acl_checked`([08](08-grounding-data-design.md))를 렌더 전에 반드시 세운다.

### 사전 필터 vs 후 필터

| | 사전 필터 (pre-filter) | 후 필터 (post-filter) |
|---|---|---|
| 동작 | 권한 조건을 만족하는 벡터만 대상으로 top-k | top-k 뽑은 뒤 권한 없는 것 제거 |
| 결과 수 | 보장 | 권한 없는 것이 많으면 k 미만 |
| 순위 | 왜곡 없음 | 권한 있는 하위 결과가 누락 |
| 누출 | 없음 | 제거 전 후보가 메모리·로그에 존재 |
| 저장소 요구 | 필터 결합 ANN 지원 필요 | 모두 가능 |

후 필터는 **보조**로만 쓴다(사전 필터가 놓친 것의 2차 방어). 주 강제 지점이 후 필터면 설계를 다시 한다.

### PII: 탐지 시점과 마스킹 시점

탐지와 마스킹은 다르다. **탐지는 항상 이르게**(파싱 직후), **마스킹은 용도별로**.

| 마스킹 시점 | 동작 | 장점 | 단점 | 적합 |
|---|---|---|---|---|
| **수집·파싱 직후** | 인덱스에 들어가기 전 마스킹·토큰화. 원본은 별도 보관(또는 폐기) | 인덱스·벡터·캐시·로그 어디에도 PII 없음. 삭제 요청이 단순 | 마스킹된 값으로는 답 못 함("고객 전화번호는?"), 오탐 시 정보 손실 | 대부분. PII가 답변에 필요 없는 경우 |
| **인덱싱 시** | 임베딩·BM25에는 마스킹본, 원문 저장소에는 원본 + 접근 통제 | 검색은 안전, 권한 있는 사용자는 원문 열람 | 원문 저장소가 보호 대상, 렌더 시 권한 확인 필요 | PII가 근거 열람에 필요한 업무 |
| **응답 시** | 인덱스엔 원본, 모델 출력에서 마스킹 | 모델이 PII를 보고 추론 가능 | 인덱스·컨텍스트·로그에 PII 존재. 출력 필터 누락 시 누출 | 권장하지 않음. 규제 검토 후 극히 제한적으로 |

탐지 수단은 규칙(패턴: 주민번호·전화·계좌·이메일) → 전용 NER/PII 모델 → 저확신만 사람([09](09-ai-inside-the-pipeline.md)). 마스킹 방식은 삭제·대체 토큰(`[PHONE]`)·가명화(일관 해시, 동일인 추적 가능)·암호화(복호 권한 분리) 중 용도로 고른다. **임베딩은 마스킹 불가**다. PII가 벡터에 들어가면 그 벡터를 지우는 수밖에 없다.

### 멀티테넌시 격리 수준

| 수준 | 동작 | 격리 강도 | 비용 |
|---|---|---|---|
| 논리 (메타데이터 `tenant_id` 필터) | 단일 인덱스, 모든 쿼리에 테넌트 필터 강제 | 중 (필터 누락 = 누출) | 하 |
| 컬렉션 분리 | 테넌트별 컬렉션/네임스페이스, 같은 클러스터 | 중~상 | 중 |
| 인스턴스·DB 분리 | 테넌트별 인프라 | 상 | 상 |
| 암호화 키 분리 | 위 어느 수준 + 테넌트별 키 | 상 (데이터 거주·삭제 증명 용이) | 중 (키 관리) |

규제·계약이 요구하는 수준으로 정하되, **필터 강제를 애플리케이션 코드 한 곳**(검색 게이트웨이)에 두어 누락이 구조적으로 불가능하게 한다. 그래프는 노드가 테넌트 간 공유될 수 있으므로(공통 엔티티) 엣지·트리플 단위로 `tenant_id`를 둔다.

### 보존·삭제

| 항목 | 규칙 |
|---|---|
| 보존 기간 | 문서 유형 택소노미별로 정의. `valid_to` 또는 `retention_until`로 메타데이터에 |
| 만료 처리 | 톰스톤(검색 제외) → 유예 → 물리 삭제. 규제가 즉시 삭제를 요구하면 유예 없음([07](07-freshness-and-sync.md)) |
| 삭제 요청 (정보주체 권리) | 원본 `doc_id` → 계보로 **모든 파생물** 식별(청크·벡터·BM25·트리플·캡션·요약·캐시) → 삭제 → 삭제 증명(무엇을 언제 지웠나) |
| 로그·트레이스 | 컨텍스트에 들어간 근거 텍스트가 트레이스에 남으면 그것도 삭제 대상. 본문 기록은 opt-in으로([Part 5/03](../05-cross-cutting/03-observability-tracing.md)) |
| 백업 | 백업에 남은 PII의 처리 정책(보존 기간 내 자동 만료) |

"원본 삭제 = 파생물 전체 삭제"는 [03](03-metadata-provenance.md)의 계보가 있어야 가능하다. 파생물에 출처 `doc_id`가 없으면 삭제 요청을 이행할 수 없다.

## 아키텍처 / 파이프라인

```
소스 (ACL, 테넌트, 분류) ─▶ 01 수집: ACL 복사 + 그룹 평탄화 ─▶ 01 파싱 직후: PII 탐지 (규칙 → 모델) ─▶ 마스킹 정책 적용
        ─▶ 03 메타데이터: acl, tenant_id, classification, pii_flags, retention_until (필수, 누락 시 거부)
        ─▶ 04/05 인덱스: [테넌트별 분리] + [메타데이터 사전 필터]
        ─▶ 질의 시: 검색 게이트웨이 (사용자 주체 집합 해석 → 사전 필터 강제) ─▶ 후보 ─▶ 렌더 전 재확인 (acl_checked) ─▶ 08 citation
소스 권한 변경 ─▶ 07 변경 큐 (유형: acl) ─▶ 메타데이터 갱신 / 인덱스 이동
삭제 요청 ─▶ 계보 조회 ─▶ 파생물 전체 삭제 ─▶ 삭제 증명
감사 로그: 누가 · 언제 · 어떤 필터로 · 무엇을 검색·열람
```

검색 게이트웨이가 **단일 강제 지점**이다. 에이전트·툴·배치가 인덱스를 직접 치지 않고 반드시 게이트웨이를 거치게 한다.

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 인덱스 분리 | 테넌트 격리, 기밀 등급 소수(3~5), 규제상 물리 격리 | 문서별 ACL이 수백 종, 교차 검색 빈번 | 중 (인덱스 수 관리) | 표준 | `[검증]` 격리 일반론 |
| 메타데이터 사전 필터 | 문서별 ACL 다양, 단일 인덱스 선호, 저장소가 필터 결합 ANN 지원 | 그룹 중첩이 깊어 평탄화 불가, 저장소가 후 필터만 지원 | 중 | 안정 | `[2차]` |
| 쿼리 시 ACL 조인 (권한 서비스 실시간) | 권한 변경 매우 잦음, 지연 허용, 렌더 전 재확인 용도 | 주 강제 지점으로 단독 사용(후 필터 문제), 저지연 | 중~상 (지연·의존) | 안정 | `[2차]` |
| 조합 (테넌트 분리 + 사전 필터 + 렌더 전 재확인) | 대부분의 운영 환경 | 단일 테넌트·전 직원 공개 (과잉) | 중~상 | 안정 | `[2차]` |
| 프롬프트 지시로 권한 통제 | 없음 (안티패턴) | 모든 운영 | 하 | — | `[검증]` 인젝션·확률적 준수 문제 |
| PII 마스킹 — 수집 직후 | PII가 답변에 불필요, 삭제 요청 대응 단순화 | PII가 업무 근거로 필요 | 중 (탐지 품질) | 표준 | `[검증]` 가명처리 일반 |
| PII 마스킹 — 인덱싱 시 (검색은 마스킹본, 원문은 통제 열람) | PII 열람이 권한 있는 업무에 필요 | 원문 저장소 보호 여력 없음 | 중~상 | 안정 | `[2차]` |
| PII 마스킹 — 응답 시만 | 거의 없음 | 인덱스·로그에 PII 잔존 | 하 | — | `[2차]` 누출 사례 |
| PII 탐지 — 규칙 (패턴) | 형식이 고정된 식별자(주민번호·전화·계좌·이메일) | 자유 서술 속 이름·주소·건강 정보 | 하 | 표준 | `[검증]` |
| PII 탐지 — 전용 NER/PII 모델 | 서술 속 개인정보, 한국어 이름·주소 | 사내 고유 식별자(추가 학습) | 중 | 안정 | `[검증]` NER 일반 / 한국어 `[실측]` |
| 테넌트별 암호화 키 | 데이터 거주·삭제 증명·계약 요구 | 단일 테넌트 | 중 (키 관리) | 표준 | `[검증]` |
| 계보 기반 파생물 삭제 | 삭제 요청·보존 만료가 있는 모든 환경 | — (계보 없으면 불가) | 중 | 안정 | `[검증]` PROV 기반 |

### 선택 가이드

- **테넌트가 둘 이상이라면** → 테넌트는 인덱스(컬렉션) 분리, 필터 강제는 게이트웨이 한 곳. 이유: 필터 한 줄 누락이 타사 데이터 누출이 되는 구조를 피한다
- **사내 문서별 ACL이 다양하다면** → 메타데이터 사전 필터(그룹 평탄화) + 렌더 전 소스 재확인. 이유: 인덱스 분리는 ACL 수만큼 폭발하고, 쿼리 시 조인만으로는 결과 부족
- **PII가 답변에 필요 없다면** → 수집 직후 탐지·마스킹, 원본은 폐기 또는 격리 보관. 이유: 인덱스에 들어간 PII는 삭제 비용이 가장 크다
- **PII 열람이 업무 근거로 필요하다면** → 인덱싱 시 마스킹(검색은 마스킹본) + 원문 통제 열람 + 열람 감사 로그. 이유: 검색 경로를 안전하게 두고 열람만 통제
- **판단이 어려우면** → 기본값: 테넌트 분리 + 메타데이터 사전 필터 + 렌더 전 재확인 + 수집 직후 PII 탐지·마스킹 + 계보 기반 삭제 + 게이트웨이 단일 강제. 이유: 모든 패턴의 공통 하한이고, 완화는 쉽지만 강화는 재색인이다

## 설계 시 고려사항 (체크리스트)

- [ ] 소스별 권한 모델(ACL 형태, 그룹 중첩, 변경 빈도)을 조사했는가
- [ ] 강제 패턴을 선택했고 **사전 필터**가 주 강제 지점인가
- [ ] 검색 게이트웨이가 단일 강제 지점이고 인덱스 직접 접근이 차단되는가
- [ ] `acl`, `tenant_id`, `classification`, `pii_flags`, `retention_until`이 필수 메타데이터이고 누락 시 인덱싱이 거부되는가
- [ ] 렌더 전 `acl_checked`가 설정되고 citation에 기록되는가([08](08-grounding-data-design.md))
- [ ] 소스 권한 변경이 변경 큐를 통해 인덱스 ACL에 전파되는가([07](07-freshness-and-sync.md))
- [ ] PII 탐지가 파싱 직후에 실행되고 한국어 식별자·이름·주소를 평가셋으로 `[실측]`했는가
- [ ] 마스킹 시점·방식이 용도별로 정해져 있고 임베딩에는 PII가 들어가지 않는가
- [ ] 삭제 요청 시 계보로 모든 파생물(청크·벡터·BM25·트리플·캡션·캐시·트레이스)을 식별·삭제·증명할 수 있는가
- [ ] 보존 기간이 문서 유형별로 정의되고 만료가 자동 톰스톤되는가
- [ ] 감사 로그가 누가·언제·어떤 필터로·무엇을 검색·열람했는지 기록하는가
- [ ] 트레이스의 본문 기록이 opt-in이고 PII·기밀이 트레이스에 남지 않는가
- [ ] 정기 권한 대조(소스 vs 인덱스)가 있는가

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 그룹 평탄화의 시차 | 그룹 멤버 변경이 청크 ACL에 늦게 반영 | 주체 집합을 질의 시 해석(그룹 → 사용자 매핑은 실시간), 청크엔 그룹 ID만 |
| 벡터DB 필터 표현력 한계 | 복잡 ACL(부정·중첩)을 사전 필터로 못 씀 | 단순 교집합 조건으로 정규화, 복잡 조건은 렌더 전 재확인 |
| 필터 후 결과 부족 | 강한 권한 제약에서 k 미만 | 사전 필터 + 넓은 후보 수, 테넌트 분리 |
| PII 탐지 오탐·미탐 | 오탐은 정보 손실, 미탐은 누출 | 규칙 + 모델 이중, 저확신 사람 검토, 한국어 `[실측]` |
| 임베딩의 부분 삭제 불가 | PII 포함 벡터는 통째로 삭제 | 수집 직후 마스킹으로 애초에 안 넣음 |
| 그래프의 테넌트 간 공유 노드 | 공통 엔티티 노드가 테넌트 경계를 흐림 | 엣지·트리플 단위 `tenant_id`, 노드는 공개 속성만 |
| 트레이스·캐시·로그의 PII 잔존 | 삭제 요청 이행 불완전 | 본문 기록 opt-in, 캐시 TTL, 삭제 범위에 포함 |
| 권한 서비스 의존 | 장애 시 검색 불가 또는 누출 | 장애 시 **거부**(fail-closed) 기본, 캐시된 권한의 TTL 짧게 |
| 규제 해석 | 개인정보·보존 규정이 국가·산업별로 다름 | 법무 검토, 정책을 메타데이터 규칙으로 코드화 |
