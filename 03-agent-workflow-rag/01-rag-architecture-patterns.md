# RAG 아키텍처 패턴

> **범위**: Naive → Advanced → Modular → Agentic RAG, GraphRAG, Hybrid 비교, 질의 시 합성 vs 사전 컴파일(LLM Wiki)
> **시각화**: [`assets/html/rag-pattern-evolution.html`](../assets/html/rag-pattern-evolution.html)

## 요약 (3줄)

1. RAG(Retrieval-Augmented Generation)는 하나의 기술이 아니라 **진화 계열**이다. Naive(검색→생성 직결) → Advanced(검색 앞뒤에 전처리·후처리) → Modular(교체 가능한 모듈의 조합) → Agentic(검색이 에이전트 루프 "안"으로)으로 갈수록 품질은 오르고 비용·지연·디버깅 난이도도 오른다.
2. GraphRAG 계열(Microsoft GraphRAG, LightRAG, HippoRAG 2)은 **멀티홉·전역 질의**에서만 가치가 뚜렷하다. 포맷 효과를 통제한 재분석(arXiv 2607.11683)에서 HippoRAG 2의 우위는 최난도 멀티홉 MuSiQue에서만 뚜렷했다(54.4 vs 40.1) `[검증]`.
3. "어떤 단일 아키텍처도 모든 시나리오에서 이기지 않는다. 그래프 RAG의 가치는 질의 복잡도에 달렸다" `[2차]`. 따라서 이 단계의 산출물은 "패턴 하나"가 아니라 **질의 복잡도별 패턴 배정표**다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 질의 복잡도 등급(단순 사실 / 다중 문서 종합 / 멀티홉 / 전역 요약)별 RAG 패턴 배정표 ② 패턴 간 공통 계약: 입력은 [Part 2/08](../02-data-pipeline/08-grounding-data-design.md)의 근거 단위(evidence) 스키마, 출력은 citation이 붙은 컨텍스트 묶음 ③ 패턴별 비용·지연 예산 |
| **언제** (When) | 근거 데이터가 모델 지식 밖에 있거나 자주 바뀌면 필요. 코퍼스가 컨텍스트 윈도우에 통째로 들어가고 요청량이 적으면 롱컨텍스트 직접 주입으로 생략 가능. GraphRAG는 멀티홉 질의 비율이 측정으로 확인될 때까지 미룬다 |
| **어떻게** (How) | ① 대표 질의 100~300건을 모아 복잡도 등급 라벨링 → ② Naive RAG로 기준선 측정(faithfulness, context precision — [13](13-evaluation-rag-agents.md)) → ③ 실패 질의를 유형별로 묶어 Advanced 모듈(재작성·리랭킹·압축) 추가 → ④ 모듈이 3개 이상이면 Modular로 재구성해 교체 가능하게 → ⑤ 멀티홉 실패가 남으면 그래프 탐색 결합 또는 Agentic 루프 → ⑥ 각 단계마다 기준선 대비 `[실측]` |
| **왜** (Why) | 처음부터 Agentic이나 GraphRAG로 시작하면 ① 인덱싱 비용이 통제되지 않고(GraphRAG "brittle and cost-prohibitive" 비판 `[벤더]`) ② 실패가 검색·그래프·루프 어디서 났는지 추적할 수 없으며 ③ 단순 질의에도 멀티홉 비용을 치른다 |

## 문제와 맥락

LLM은 학습 시점 이후의 사실과 조직 내부 데이터를 모른다. RAG는 질의 시점에 외부 근거를 찾아 컨텍스트에 넣어 이 간극을 메운다. 그런데 "벡터 검색 → top-k → 프롬프트에 붙이기"라는 가장 단순한 형태(Naive RAG)는 운영에 들어가면 다음 증상을 보인다.

- **질의-문서 어휘 불일치**: 사용자는 "연차 이월"이라 묻고 문서는 "미사용 휴가의 차기 연도 승계"라 쓴다. 임베딩이 어느 정도 흡수하지만 전문 용어·약어·한국어 조사 변형에서 자주 실패
- **다중 문서 종합 실패**: 답이 세 문서에 흩어져 있는데 top-k가 한 문서의 유사 청크로 채워진다
- **멀티홉 실패**: "A 프로젝트 담당 부서의 올해 예산은?"처럼 A→부서→예산으로 건너뛰어야 하는 질의. 한 번의 검색으로는 두 번째 홉의 문서를 찾을 수 없다
- **전역 질의 실패**: "이 코퍼스의 주요 리스크는?" 같은 질의는 특정 청크가 아니라 코퍼스 전체의 요약을 요구한다
- **컨텍스트 중간 누락**: 긴 컨텍스트의 중간 청크가 무시되는 현상(Lost in the Middle, RULER 스트레스에서 재현 `[검증]` 원 논문, `[2차]` 최근 재현 보고)

- **같은 종합 질문의 반복 재합성**: "이 프로젝트의 의사결정 이력은?" 같은 질문이 매주 들어오는데 매번 원문 청크를 다시 모아 종합하므로 느리고 답이 조금씩 달라진다. 소규모·변화 느린 코퍼스에서 두드러진다 `[2차]`

각 증상이 각 진화 단계의 등장 이유다. 어휘 불일치와 다중 문서 종합은 Advanced(쿼리 재작성, hybrid, 리랭킹)가, 멀티홉은 Agentic 루프 또는 그래프 탐색이, 전역 질의는 GraphRAG의 커뮤니티 요약이 겨냥한다. 반복 재합성은 질의 시 합성이 아니라 **사전 컴파일**(LLM Wiki)이 겨냥하는 증상이다.

## 핵심 개념

### 진화 4단계

| 단계 | 구조 | 추가되는 것 | 대표 실패 모드 |
|---|---|---|---|
| **Naive RAG** | 질의 → 임베딩 검색 → top-k → 생성 | 없음 | 어휘 불일치, 무관 청크 혼입, 다중 문서 종합 실패 |
| **Advanced RAG** | 전처리(재작성·분해·HyDE) → hybrid 검색 → 후처리(리랭킹·압축) → 생성 | 검색 앞뒤 모듈. [02](02-query-understanding.md), [03](03-retrieval-reranking.md) | 모듈이 늘수록 지연 누적, 모듈 간 상호작용 디버깅 어려움 |
| **Modular RAG** | 검색·재작성·리랭킹·메모리·융합·라우팅을 **교체 가능한 모듈**로, 라우터가 질의별 경로 선택 | 모듈 인터페이스 표준화, 질의별 라우팅. [02](02-query-understanding.md)의 라우터 | 구성 조합 폭발, 라우터 오판이 전체 품질을 좌우 |
| **Agentic RAG** | 에이전트가 "검색할지, 무엇을 검색할지, 충분한지"를 **루프 안에서** 판단. 검색이 툴이 됨 | 반복 검색, 자기 평가, 중단 판정. [06](06-agent-design-patterns.md) | LLM 호출 수 비결정적, 무한 루프, 비용 상한 필요 |

Agentic RAG의 본질은 "검색이 에이전트 루프 앞이 아니라 안으로 들어간다"는 것이다 `[2차]`. 그 결과 요청당 검색 횟수가 1회 고정에서 가변으로 바뀌고, 비용·지연을 **상한으로** 관리해야 한다.

### GraphRAG 계열

지식그래프([Part 2/05](../02-data-pipeline/05-knowledge-graph-construction.md))를 검색 구조로 쓰는 계열. 공통점은 청크 유사도가 아닌 **엔티티·관계 탐색**으로 멀티홉을 처리한다는 것, 차이점은 그래프를 어떻게 만들고 무엇을 검색 단위로 삼느냐다.

| 접근 | 그래프 구성 | 검색 방식 | 알려진 특성 | 검증 수준 |
|---|---|---|---|---|
| **Microsoft GraphRAG** | LLM으로 엔티티·관계 추출 + 커뮤니티 탐지 + 커뮤니티별 요약 | 로컬(엔티티 이웃) / 글로벌(커뮤니티 요약 map-reduce) | 전역 요약 질의에 강점. 인덱싱 비용 과다, "brittle and cost-prohibitive" 비판 | `[벤더]` 경쟁사 평가 포함 |
| **LightRAG** | 엔티티-관계 그래프, **증분 업데이트** 지원 | 저수준(엔티티)/고수준(주제) 이중 검색 | "GraphRAG 61만 토큰 쓸 때 100토큰 미만" 수치는 2차 요약 | `[2차]` |
| **HippoRAG 2** | 지식그래프 + Personalized PageRank 연상 검색 | 질의 엔티티에서 PPR로 관련 노드 확산 | arXiv 2607.11683(RAGU) 재분석: 장황한 답변 프롬프트에서의 우위는 대체로 **포맷 효과**, 포맷 통제 후 최난도 멀티홉 MuSiQue에서만 뚜렷한 우위(54.4 vs 40.1) | `[검증]` |

이 재분석 결과가 GraphRAG 계열 채택 판단의 핵심 근거다. **단순·중간 난도 질의에서는 그래프가 벡터 검색을 뚜렷이 이기지 못하고, 최난도 멀티홉에서만 이긴다**. 그러므로 그래프 도입 여부는 "우리 질의 중 최난도 멀티홉이 몇 %인가"의 측정으로 결정한다. 많은 GraphRAG 구현이 임베딩+그래프 탐색에 머물고 온톨로지를 간과한다는 지적도 있다 `[2차]` 그래프 벤더 프레이밍 — 온톨로지 기반 접지는 [Part 2/06](../02-data-pipeline/06-ontology-driven-modeling.md).

### 롱컨텍스트 직접 주입과 하이브리드

컨텍스트 윈도우가 커지면서 "검색 없이 문서를 통째로 넣는" 선택지가 생겼다. 롱컨텍스트와 RAG는 **보완 관계**다 `[2차]`. 롱컨텍스트는 검색 실패(recall 누락)가 없지만 ① 요청당 토큰 비용이 코퍼스 크기에 비례하고 ② 중간 청크 누락이 재현되며 ③ 코퍼스가 윈도우를 넘으면 결국 선별이 필요하다. 하이브리드는 RAG로 후보 문서를 좁힌 뒤 **문서 단위(청크가 아닌)**로 롱컨텍스트에 넣는 절충이다. 컨텍스트 예산 개념은 [Part 1/01](../01-foundations/01-llm-fundamentals.md).

### 질의 시 합성 vs 사전 컴파일 — LLM Wiki(사전 컴파일형 지식 베이스)

위 진화 4단계와 GraphRAG 분기는 모두 **질의 시점에 원문 청크를 검색해 매번 재합성**한다는 전제를 공유한다. 2026-04 Andrej Karpathy가 X 게시물 + GitHub Gist로 제안한 **LLM Wiki(사전 컴파일형 지식 베이스, pre-compiled knowledge base)** 패턴은 이 전제를 뒤집는다 — 제품이 아니라 패턴이며, LLM 에이전트가 원문을 읽고 **구조화·상호 링크된 마크다운 위키를 컴파일해 유지**하고, 질의는 원문이 아니라 위키를 참조한다 `[2차]`. 원 gist URL은 미확인이라 아래 서술은 전부 2차 해설 기반이다.

| 구성 | 내용 | 검증 수준 |
|---|---|---|
| **세 층** | ① 원문(`raw/`, **불변**, LLM이 수정하지 않음) ② 위키(`wiki/`, LLM 생성 마크다운 — 요약·엔티티·개념·비교·종합 페이지, `index.md`, `log.md`) ③ 스키마(`CLAUDE.md`/`AGENTS.md`류 — 소스 유형별 ingest 방법, 인덱스 형식, 백링크·명명 규칙, lint 검사, 충돌 처리) | `[2차]` |
| **연산 3종** | **ingest**(원문 추가 → 요약 페이지 작성, index 갱신, 관련 엔티티·개념 페이지 갱신, log 기록) / **query**(index 따라 탐색, 위키 내용으로 citation 포함 답 합성, 좋은 답은 새 위키 페이지로 저장 = **compounding**, 지식 누적) / **lint**(결정론 자동 수정: 인덱스 일관성·깨진 링크·원문 참조 / 휴리스틱 보고: 모순·고아 페이지·오래된 내용·후보 신규 페이지) | `[2차]` |
| **컴파일러 비유** | raw = 소스 코드, LLM = 컴파일러, wiki = 실행 파일, lint = 테스트, query = 런타임 | `[2차]` |

RAG와의 차이는 두 가지다. ① RAG는 질의마다 원문 청크를 검색해 **재합성**한다(느리고 일관성 낮음). 위키는 **사전 종합 + 누적**이다. ② 출처 추적은 RAG가 높고(청크·문장 단위), 위키는 **페이지 단위**로 보통이다 `[2차]`. 그래서 이 위키의 근거 데이터 설계([Part 2/08](../02-data-pipeline/08-grounding-data-design.md))에서 위키 페이지는 1차 원문이 아닌 **파생 근거**(derived evidence)로 취급하고 별도 등급(E·F)을 받는다. 규모 한계도 분명하다 — 인덱스 탐색은 **수백 페이지**까지 벡터 검색 없이 동작하고, 수백만 문서·실시간 갱신 운영 시스템의 RAG를 대체하지 못한다. 매 질의 컨텍스트를 과소비하면 읽기·쓰기 모두 느려지며, 오픈소스 구현은 "개인용 프로토타입, 산업급 에이전트 능력 결여"로 평가된다(arXiv 2604.11243 `[검증]`). 커뮤니티 평가는 "RAG는 죽었다" vs "캐시 계층에 이름 붙인 것"으로 양분되어 있다 `[2차]`. 이 위키의 위치는 **RAG 대체가 아니라 소규모·누적형 보완**이다.

권장 구성은 **하이브리드(위키 먼저 → 원문 RAG 폴백 → 환류)**다. ① `wiki.query`가 index를 탐색해 관련 페이지가 있고 `stale`이 아니면 그 페이지를 근거로 답한다 ② 페이지가 없거나 `stale`(원문이 컴파일 이후 변경됨)이면 원문 RAG(Advanced 경로)로 폴백한다 ③ 폴백으로 얻은 답이 [04](04-generation-grounding.md) 검증을 통과하면 새 위키 페이지로 환류(compounding)한다. 이 구조에서 위키는 RAG 앞의 **사전 종합 캐시**로 동작하고, 출력 계약("citation 붙은 컨텍스트 묶음")은 두 경로가 공유한다. 운영 지식용 메모리와의 관계는 [08](08-state-memory-context.md), 트렌드 평가는 [Part 6/agent-memory](../06-trends/agent-memory.md).

```
                     └─ 전역 요약 ──▶ GraphRAG 글로벌(커뮤니티 요약) 또는 하이브리드 롱컨텍스트 → 생성
                                                      │
                     모든 경로의 출력 ─▶ citation 붙은 컨텍스트 묶음 ─▶ [04] 생성·근거 강제
```

입력은 Part 2가 넘긴 근거 단위 스키마와 인덱스(벡터·BM25·그래프)다. 출력은 어느 경로를 탔든 동일한 "citation 붙은 컨텍스트 묶음"이어야 [04](04-generation-grounding.md)가 패턴에 무관하게 동작한다. 라우터가 복잡도를 판정하는 수단(결정 모델·분류기·규칙)은 [02](02-query-understanding.md)와 [11](11-decision-layer.md). LLM Wiki 하이브리드를 쓰면 라우터 앞에 `wiki.query`가 한 단계 더 놓인다 — 적중하면 위키 페이지(파생 근거)로 같은 출력 계약을 채우고, 없거나 `stale`이면 위 경로로 폴백한다.

### 선택 가이드

- **질의의 대부분이 단일 문서 내 사실 확인이라면** → Advanced RAG(hybrid + 리랭킹). 이유: 비용 대비 효과가 가장 크고 디버깅이 단순하다
- **답이 여러 문서에 흩어지고 질문이 복합적이라면** → Advanced에 쿼리 분해·멀티 쿼리 추가, 경로가 둘 이상이면 Modular. 이유: 검색 횟수를 고정한 채 recall을 높인다
- **최난도 멀티홉 질의가 측정으로 유의미한 비율로 확인된다면** → 그래프 탐색 결합(LightRAG 또는 HippoRAG 2) 또는 Agentic 루프. 이유: 그래프의 우위가 `[검증]`된 유일한 영역이다. 코퍼스가 자주 바뀌면 증분 업데이트가 되는 LightRAG
- **"코퍼스 전체의 주제·리스크" 같은 전역 질의가 핵심이라면** → GraphRAG 글로벌 또는 하이브리드 롱컨텍스트. 이유: 청크 검색으로는 구조적으로 답할 수 없다. 단 인덱싱 비용을 먼저 산정
- **코퍼스가 작고 요청량이 적다면** → 롱컨텍스트 직접 주입. 이유: 검색 실패 자체가 없다
- **코퍼스가 수백 페이지 이하이고 변화가 느리며, 종합·비교·누적 질문과 같은 질문의 반복이 많다면** → LLM Wiki + 원문 RAG 폴백 하이브리드를 **시험**한다(위키 유무 A/B `[실측]` 후 유지). 이유: 질의마다 재합성하는 대신 사전 종합을 재사용하므로 질의 비용과 일관성에서 유리하다 `[2차]`. 단 위키 페이지는 파생 근거(페이지 단위 출처)이므로 문장 단위 출처·규제 감사 요구가 있는 질의는 원문 RAG로 보낸다
- **판단이 어려우면** → Naive로 기준선을 재고 Advanced(hybrid + 리랭킹)를 기본값으로. 이유: 그 이상은 실패 질의 유형이 측정으로 확인된 뒤에 추가해야 비용과 디버깅 범위가 통제된다

## 설계 시 고려사항 (체크리스트)

- [ ] 대표 질의를 복잡도 등급(단순 / 다중 문서 / 멀티홉 / 전역)으로 라벨링하고 비율을 측정했는가
- [ ] Naive RAG 기준선의 faithfulness·context precision을 기록했는가 ([13](13-evaluation-rag-agents.md))
- [ ] 모든 패턴의 출력이 같은 "citation 붙은 컨텍스트 묶음" 계약을 따르는가 ([Part 2/08](../02-data-pipeline/08-grounding-data-design.md))
- [ ] Agentic 루프라면 요청당 검색 횟수·LLM 호출 수·토큰의 상한과 상한 도달 시 폴백이 있는가
- [ ] GraphRAG 계열이라면 인덱싱 비용(LLM 토큰)과 코퍼스 변경 빈도를 곱해 월 비용을 산정했는가
- [ ] 그래프 검색 결과도 원문 청크로 환원되어 citation이 가능한가 (그래프 트리플만 근거로 쓰면 출처 추적 불가)
- [ ] 롱컨텍스트를 쓴다면 중요 문서가 컨텍스트 중간에 묻히지 않도록 배치 순서를 설계했는가
- [ ] ACL 필터가 모든 경로(벡터·BM25·그래프 탐색)에 동일하게 적용되는가 ([Part 2/10](../02-data-pipeline/10-access-control-governance.md))
- [ ] 패턴 간 A/B 비교가 같은 평가셋·같은 포맷 프롬프트로 이루어지는가 (포맷 효과 통제)
- [ ] LLM Wiki 하이브리드라면 위키 페이지가 파생 등급·`derived_from[]`·`stale`을 갖고, 원문 변경이 재컴파일 트리거로 이어지며, 위키 유무 A/B 평가셋이 있는가

| **데이터** | GraphRAG 재인덱싱 LLM 비용·시간, 커뮤니티 요약 재계산 | 증분 그래프 갱신(LightRAG 류), 그래프는 멀티홉 경로에만. 상세는 [Part 2/07](../02-data-pipeline/07-freshness-and-sync.md) | 문서 수 × 변경 빈도 (Part 2 축) |
| **테넌트** | 테넌트마다 경로·인덱스가 달라 패턴 배정표 분기 폭발, 캐시 오염 | 테넌트 키를 패턴 배정표·캐시 키·트레이스에 처음부터 | 테넌트 수 × 경로 수 |
| **위키 페이지 수** (LLM Wiki 하이브리드 시) | 인덱스 탐색은 수백 페이지가 한계 — 넘으면 `wiki.query`가 매 질의 컨텍스트를 과소비해 읽기·쓰기 모두 느려짐 `[2차]`. 원문 변경당 재컴파일 LLM 비용 | 페이지 수 상한을 두고 초과 시 index를 그래프·벡터 인덱스와 결합(그래프 벤더 관점 제안 `[2차]`), 재컴파일은 `derived_from[]` 역참조로 영향 페이지만 | 페이지 수 × 질의당 탐색 페이지 수, 원문 변경 수 × 영향 페이지 수 |

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 생성 모델 API 다운·지연 | 응답 없음, 타임아웃 | 벤더별 오류율·p95, 서킷 브레이커 열림 | 호환 매트릭스에 등록된 폴백 모델 → 그것도 실패하면 캐시 응답 또는 "검색된 근거 목록만 제시(생성 없음)" 저하, 저하 상태를 응답에 표시 | 폴백 모델 사용률이 10분간 50% 초과(예시) |
| 임베딩 API·벡터DB 장애 | dense 결과 없음 → 의역 질의 recall 급락 | dense 호출 오류, 후보 수 0 | hybrid의 한쪽인 BM25 단독으로 저하 + "축소 검색" 플래그를 [04](04-generation-grounding.md)에 전달 | 5분 지속(예시) |
| 리랭커 타임아웃 | 지연 증가 또는 무관 청크 혼입 | 리랭커 p95, 타임아웃 카운트 | 타임아웃(예시 300ms) 초과 시 리랭킹 생략, RRF 순위 그대로 top-k | 생략률 20% 10분 지속(예시) |
| Agentic 루프 폭주 | 응답 지연, 비용 급등 | 요청당 검색 횟수·토큰 상한 도달률 | 상한에서 강제 종료 → 수집된 근거로 생성 또는 abstain, "부분 검색" 표시 | 상한 도달률 5% 초과(예시) → 종료 판정 점검 |
| GraphRAG 글로벌 경로 폭발 | 전역 질의가 수십 초 | map-reduce 호출 수, 커뮤니티 수 | 커뮤니티 수·요약 레벨 상한, 초과 시 하이브리드 롱컨텍스트로 저하 | 상한 도달 반복 |
| 라우터 오판으로 경로-비용 불일치 | 단순 질의에 멀티홉 비용·지연 | 경로별 비용 분포 이상, 복잡 경로 비율 급변 | 확신도 미달 시 보수적 기본 경로(Advanced)로 — [02](02-query-understanding.md) | 경로 비율이 베이스라인 ±50%(예시) |
| LLM Wiki 컴파일 실패·lint 모순 폭증 (하이브리드 시) | 새 원문이 위키에 반영되지 않음, 또는 모순된 페이지가 근거로 쓰임 | `wiki.ingest` 실패율, `wiki.lint` 모순·고아·stale 보고 수 급증, 원문 폴백률 급등 | ingest 실패 문서는 원문 RAG 경로로만 서빙(위키 미반영 표시), lint 모순이 걸린 페이지는 `stale` 처리해 폴백 유도 | lint 모순 수가 베이스라인 2배(예시) → 스키마 파일·컴파일 프롬프트 리뷰 |

SLI 후보: 경로별 p95 지연, 요청당 LLM 호출 수 분포, 경로별 근거 부합률(faithfulness, 샘플), abstain 비율, 폴백·저하 발생률, **삭제 이벤트 → 결과·시맨틱 캐시 제거 p95**(불균형 ① 반영). SLO 초안(예시, 베이스라인 측정 후 재설정): Advanced 경로 p95 ≤ 4초, 저하 모드 응답 비율 월 1% 미만, 상한 도달률 2% 미만. 서킷 브레이커 위치: 생성 모델 API(벤더별), 임베딩 API, 벡터DB, 그래프DB, 리랭커 — 외부 의존마다 독립. 쓰기 행동: 없음(캐시 쓰기만). 캐시 키에 테넌트·인덱스 버전·프롬프트 버전·**주체 집합 해시**를 넣어 멱등하고 오염되지 않게. 캐시 무효화는 인덱스 버전 상승뿐 아니라 **문서 ID 톰스톤·ACL 이벤트**에도 반응한다 — 결과·시맨틱 캐시를 [Part 2/07](../02-data-pipeline/07-freshness-and-sync.md) 변경 큐 **삭제 레인의 소비자**로 등록하고, [Part 2/08](../02-data-pipeline/08-grounding-data-design.md)의 `acl_checked` 비영속 원칙을 캐시된 답변에도 적용한다(캐시 히트도 요청 단위로 ACL 재확인) (불균형 ①·② 반영).

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| **패턴 배정표**(복잡도 등급 → 경로) — 설정 | 모든 요청의 경로·비용 | 경로별 골든셋, 경로 분포 비교 | [02](02-query-understanding.md) 라우터 질문 정의 버전 |
| 경로별 모듈 구성(재작성 on/off, 리랭커, 압축, k) — 설정 | 해당 경로의 품질·지연 | 경로 골든셋 faithfulness·context precision | 컨텍스트 예산 ↔ 생성 모델 버전 |
| 생성·재작성 모델 버전 | 모든 경로의 출력 분포 | 전체 골든셋 | 프롬프트 버전(프롬프트-모델 호환 매트릭스), 폴백 모델 목록 |
| 그래프 인덱스 스키마·커뮤니티 요약 버전 | 멀티홉·전역 경로 | 멀티홉 골든셋 | 근거 단위 스키마([Part 2/08](../02-data-pipeline/08-grounding-data-design.md)) |
| Agentic 루프 상한·종료 임계값 — 설정 | 비용·완결성 | 상한 도달률, 성공률 | 종료 판정 결정 모델 질문 정의 |
| LLM Wiki 스키마 파일(`CLAUDE.md`류)·컴파일 프롬프트·위키 버전 (하이브리드 시) | 모든 페이지의 구조·명명·lint 규칙, 재컴파일 결과, 위키 적중률 | 샘플 원문 재컴파일 diff, lint 통과율, 위키 유무 A/B 골든셋 | `compiler_version`(모델·프롬프트)을 페이지 메타에. 스키마 메이저 변경은 전체 재컴파일 창 + 파생 등급 규칙([Part 2/08](../02-data-pipeline/08-grounding-data-design.md)) |

기술 부채로 기록할 것: "그래프 경로의 ACL은 메타데이터 필터로만", "전역 경로는 캐시 없이 운영", "한국어 복잡도 라벨 평가셋 N건 미만" 같은 항목과 재검토 시점.

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **지식** | 코퍼스 증가·갱신으로 질의 복잡도 분포 이동, 그래프 재구축 | 근거 단위 스키마, "citation 붙은 컨텍스트 묶음" 출력 계약 | 인덱스(벡터·BM25·그래프), 그래프 구축 방식 | 증분 인덱싱 + 인덱스 버전 키·문서 ID 톰스톤으로 캐시 무효화(삭제 레인 소비자, 불균형 ① 반영), 패턴 배정표 분기별 재측정 | 캐시, 멀티홉 경로 골든셋 |
| **지식 — 위키(파생)** (LLM Wiki 시) | 원문 추가·변경·삭제 → 관련 위키 페이지 `stale` → 재컴파일 | 페이지 메타(`derived_from[]`, `compiled_at`, `compiler_version`, `stale`), 출력 계약 | 컴파일러(모델·프롬프트), 위키 저장소 | **원문 변경 → 재컴파일 트리거가 핵심**: 위키를 [Part 2/07](../02-data-pipeline/07-freshness-and-sync.md) 변경 큐(삭제·변경 레인) 소비자로 등록, `derived_from[]` 역참조로 영향 페이지를 `stale` 표시 → 재컴파일 전까지 원문 RAG 폴백. 삭제는 파생 페이지 제거까지 전파 | 위키 페이지·index, 그 페이지를 근거로 한 결과 캐시 |
| **모델** (LLM 교체) | 생성·재작성 모델 벤더·버전 | `generate()` 포트, 프롬프트-모델 호환 매트릭스 | 모델 어댑터 | 어댑터 교체 + 전체 골든셋 회귀 + 카나리(예시 트래픽 5%) | 모든 경로의 생성 단계, 컨텍스트 예산 재산정 |
| **도메인 모델** | 경로 추가(예: 정형 DB Text-to-SQL 경로), 복잡도 등급 정의 변경 | 경로 enum(추가는 자유, 삭제는 버전 상승) + 출력 계약 | 경로별 모듈 체인 | 패턴 배정표(설정) 변경 + 라우터 질문 정의 버전 상승. 경로 코드는 플러그인으로 등록 | 라우터 평가셋, 신규 경로 골든셋만 |
| **규칙·정책** | ACL·범위 밖 정책 | 모든 검색기 공통 필터 인터페이스 | 필터 구현 | 규칙 버전 + 시행일 | 전 경로의 pre-filter([03](03-retrieval-reranking.md)) |
| **사용자 환경** | 다국어·테넌트 추가 | 출력 계약 | 언어별 프롬프트 변형·토크나이저 | 테넌트·언어 키로 설정 분기 | 해당 언어 골든셋 |
| **프로토콜·SDK** | RAG 프레임워크·벡터DB 클라이언트 메이저 업 | 내부 `retrieve()`·`generate()` 포트 | 어댑터 | 버전 고정 + 계획된 업그레이드 창 | 어댑터만 |

가장 자주 바뀌는 것: 지식(코퍼스, 매일) > 패턴 배정표·경로 구성(주~월) > 프롬프트 > 모델 > 프레임워크. 코드 밖 설정으로 둘 것: 패턴 배정표, 경로별 모듈 구성(k·리랭커·압축), 루프 상한, 컨텍스트 예산, 폴백 모델 목록. 포트·어댑터 뒤에 둘 외부 의존: 생성 모델 API, 임베딩 API, 벡터DB, 그래프DB, 리랭커 서빙.

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성의 "탐지 신호"가 **실제로 어디서 나오는지**를 설계한다. 기준은 [Part 1/07 관측성 설계 요소](../01-foundations/07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md). 이 페이지의 관측 단위는 **경로(route)**다 — 모든 지표를 경로별로 분해하지 않으면 패턴 배정표가 맞는지 틀린지 알 수 없다. 검색·생성 내부 스팬의 상세 규약은 [02](02-query-understanding.md)·[03](03-retrieval-reranking.md)·[04](04-generation-grounding.md)에 두고, 여기서는 경로 수준에서 묶어 본다.

| 기록 대상 | 스팬 / 이벤트 (이름, 부모) | 핵심 속성 (버전 키 포함) | 지표 (→ 어느 SLI) | 샘플링 · 보존 · PII |
|---|---|---|---|---|
| 경로 선택 | `routing.decide` (부모 `invoke_agent rag`) | `agent.decision`(route), `agent.confidence`, `agent.decision_source`, `agent.rules_version`(패턴 배정표 버전), `agent.prompt_version`(라우터 프롬프트) | 경로별 요청 비율(베이스라인 대비), 경로 선택 확신도 히스토그램, 경로-비용 분포(경로 × 요청당 비용) → 라우터 오판 탐지 | 메타 전수, 질의 원문은 해시만 |
| 경로 실행 전체 | `invoke_agent rag` 루트 속성 (턴 종료 시 집계) | `agent.route`, `agent.search_count`, `agent.hop_count`, `agent.llm_call_count`, `agent.limit_hit`(search/token/time/community), `agent.outcome`, `agent.degradation[]`, 버전 키 5종 | **경로별 p95 지연**, **요청당 LLM 호출 수 분포**(p50/p95), 상한 도달률, **폴백·저하 발생률**(저하 코드별) → Agentic 루프 폭주·GraphRAG 글로벌 폭발 | 메타 전수, 상한 도달·폴백 건은 본문 전수 |
| 인덱스별 검색·리랭킹 | `retrieval.search {dense·bm25·graph}`, `retrieval.rerank` (자식, 상세 [03](03-retrieval-reranking.md)) | `agent.index_version`(인덱스별), `agent.candidate_count`, `agent.circuit_state`, `agent.degradation[]`=`dense_unavailable`·`rerank_skipped`·`graph_truncated` | 인덱스별 오류율·p95, 후보 0 비율, 리랭킹 생략률 → 임베딩·벡터DB 장애, 리랭커 타임아웃 | 메타 전수 |
| GraphRAG 글로벌 경로 | `retrieval.search graph.global` + map/reduce 모델 호출 자식(`gen_ai.*`) | `agent.community_count`, `agent.summary_level`, `agent.mapreduce_calls`, `agent.limit_hit`=community | map-reduce 호출 수 분포, 커뮤니티 상한 도달률 → 글로벌 경로 폭발 | 메타 전수, 커뮤니티 요약 본문 opt-in |
| 생성·폴백 | `generation.generate` + 모델 호출 자식(`gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`, 상세 [04](04-generation-grounding.md)) | `agent.model_version`, `agent.prompt_version`, `agent.fallback_model`, `agent.outcome`=fallback, `agent.cached_tokens`, `agent.abstain_reason` | 벤더별 오류율·p95, 폴백 모델 사용률, **abstain 비율**, **경로별 근거 부합률**(faithfulness, 샘플 judge — 비동기 트레이스를 원 trace에 링크) → 생성 모델 다운 | 메타 전수, 프롬프트·출력 본문 opt-in(예시 1~5%), 실패·abstain·폴백 건은 전수(마스킹) |
| LLM Wiki 컴파일·질의·lint (하이브리드 시) | `wiki.ingest`(문서 단위 트레이스, `ingest.*`와 나란히) / `wiki.query`(부모 `invoke_agent rag`, 폴백 시 자식으로 `retrieval.search`) / `wiki.lint`(배치, 부모 없음) — 이름은 [Part 1/07](../01-foundations/07-operations-vocabulary.md) 규약 | `agent.wiki_version`, `agent.compiler_version`, `agent.pages_touched`, `agent.wiki_hit`(bool), `agent.fallback_reason`(no_page / stale / low_confidence), 위키 근거 사용 시 `agent.evidence_derived=true`·`derived_from[]`, lint: `agent.lint_findings{contradiction,orphan,stale,candidate}` | **위키 적중률**(`wiki_hit` 비율), **원문 폴백률**(사유별), **lint 모순 수** 추이, stale 페이지 비율, 재컴파일 지연(원문 변경 → `wiki.ingest` 완료 p95) → 컴파일 실패·lint 모순 폭증 | 메타 전수. 페이지 본문은 저장소에만(ID) |
| 결과·시맨틱 캐시 | 이벤트 `cache.lookup` / `cache.invalidate` (부모 `invoke_agent rag`; 삭제 레인 소비 측은 배치 `sync.*` 트레이스) | `agent.cache_hit`, `agent.cache_kind`(result/semantic/prompt), 캐시 키 구성 버전(테넌트·인덱스 버전·프롬프트 버전·주체 집합 해시 포함 여부), 무효화 원인(index_version/tombstone/acl_event)과 원천 이벤트 ID | 캐시 히트율(종류별), **삭제 이벤트 → 결과·시맨틱 캐시 제거 p95**(톰스톤 발행 시각 − `cache.invalidate` 시각), 히트 응답의 ACL 재확인 비율(=100%) | 전수, 질의·키는 해시만 |

| 알림 | 조건 (예시) | 심각도 | 런북 (첫 3단계) |
|---|---|---|---|
| 생성 폴백 급증 | `agent.outcome=fallback` 비율이 10분간 50% 초과, 또는 생성 벤더 서킷 열림 | P1 | ① 벤더 상태·서킷 상태와 폴백 모델의 한도 잔량 확인 ② 폴백 모델 사용률이 호환 매트릭스 범위 안인지 확인 ③ 지속 시 "근거 목록만 제시" 저하를 강제하고 Interaction 고지 확인 |
| 검색 저하 지속 | `agent.degradation`에 `dense_unavailable` 또는 `bm25_unavailable`이 5분 지속, 또는 후보 0 비율 10% 초과 | P2 | ① 임베딩 API·벡터DB·BM25 서킷 상태 확인 ② 저하 플래그가 [04](04-generation-grounding.md)로 전달되어 확신도가 낮아지는지 확인 ③ 원인 추적은 [03](03-retrieval-reranking.md) 런북으로 이관 |
| 리랭킹 생략률 상승 | `rerank_skipped` 비율 20%가 10분 지속 | P2 | ① 리랭커 서빙 p95·포화 확인 ② 후보 수 N 임시 축소 ③ 고정 k 운영 중임을 [04] 측에서 인지하는지 확인 |
| 상한 도달률 상승 | `agent.limit_hit` 비율(루프·커뮤니티) 5% 초과 | P2 | ① 경로·테넌트별로 분해해 특정 경로인지 확인 ② 종료 판정 질문 정의·상한 설정의 최근 버전 변경 확인 ③ 상한을 보수적 방향(하향)으로만 임시 조정 |
| 경로 분포 이탈 | `routing.decide` 경로별 비율이 베이스라인 ±50%, 또는 경로-비용 분포 이상 | P3 | ① 패턴 배정표·라우터 모델 버전의 변경 이력 확인 ② 경로 선택 확신도 히스토그램에서 θ 주변 질량 확인 ③ [02](02-query-understanding.md) 라우터 평가셋 재측정 |
| 위키 폴백률 급등 · lint 모순 폭증 (하이브리드 시) | `agent.fallback_reason=stale` 비율이 베이스라인 2배 1시간, 또는 `lint_findings{contradiction}`이 2배(예시) | P3 | ① 최근 원문 변경량과 `wiki.ingest` 실패율 대조 ② 스키마 파일·`compiler_version` 변경 이력 확인 ③ 모순 페이지를 `stale` 처리해 원문 RAG로 보내고 lint 보고를 소유자에게 이관 |

대시보드에서 이 단계를 보는 뷰: ① E2E — 경로별 p95·폴백·저하율(저하 코드별) / ② Reasoning 패널 — 요청당 LLM 호출 수·검색 횟수 분포, 상한 도달률, 리랭킹 생략률 / ③ 비용·판정 분포 — 경로 × 요청당 비용 히트맵, 경로 선택 확신도 히스토그램, 결정 소스 분포, 캐시 히트율.
감사 추적으로 넘기는 필드(관측 로그와 분리): 요청 ID·테넌트, 선택 경로·확신도·결정 소스, 적용 ACL 필터(주체 해시·규칙 버전), `agent.evidence_ids[]`, 인덱스 버전 3종, 프롬프트·모델 버전(폴백 여부), 저하 플래그, 캐시 히트 여부 — 거버넌스 접점 표의 필드와 동일.
이 단계의 관측이 없으면 못 보는 장애: **경로-비용 불일치** — 라우터가 단순 질의를 멀티홉 경로로 보내 요청당 비용이 3배가 되어도 오류율 0, 전체 평균 지연 정상이라 경로별 분해 없이는 보이지 않는다. 그리고 **삭제된 문서를 계속 내보내는 캐시 히트** — 인덱스 버전은 그대로이므로 `cache.invalidate`의 톰스톤 원천과 제거 p95를 재지 않으면 발견 경로가 사용자 신고뿐이다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | **1** — 답변 표시는 가역이고 영향은 요청자 본인. 단, 어느 경로든 ACL 필터가 빠지면 타인 데이터 노출(여러 사용자 영향)이 되어 등급 2~3의 통제가 필요하다. 그래서 ACL은 "경로 설정"이 아니라 규칙 게이트다 |
| 가드레일 위치 | 입력 가드레일은 이 단계 앞([02](02-query-understanding.md)), 출력 가드레일은 뒤([04](04-generation-grounding.md)). 이 단계 고유: 모든 검색 경로의 ACL pre-filter(데이터 접근 = 행동에 준함), 루프·홉·커뮤니티 수 상한 |
| 게이트 출력과 판정 수단 | 통과(경로 확정) / 차단(권한 없음 → 결과 제외) / 저하(상한 도달·리랭커 생략·단일 인덱스) / 승인 요청은 해당 없음. ACL·상한은 규칙만, 경로는 결정 모델·분류기, 생성은 LLM |
| 소유자 (A) | 패턴 배정표·경로 구성: 제품 책임자(A), AI 엔지니어(R). 인덱스 **내용·ACL**: 데이터 소유자(A), 데이터 엔지니어(R) — 인덱스 인프라·전환은 데이터 엔지니어링 책임자, 임베딩 모델 선택은 아키텍트([Part 2/04](../02-data-pipeline/04-embedding-indexing.md) 세 행 분리, 불균형 ⑨ 반영) |
| 감사 추적에 남길 필드 | 요청 ID, 테넌트, 선택 경로와 판정 확신도, 적용 필터(ACL 주체·규칙 버전), 검색 횟수·홉 수, 근거 ID 목록(source_id·span), 인덱스 버전(벡터·BM25·그래프), 프롬프트 버전, 모델 버전(폴백 여부), 저하 플래그, 캐시 히트 여부 |
| LLM Wiki 사용 시 추가 | 위키 페이지의 **작성자는 LLM**이므로 파생 근거 등급([Part 2/08](../02-data-pipeline/08-grounding-data-design.md) E·F)을 받고 원문 등급(A~D)과 섞이지 않는다. 위키 내용·등급은 데이터 소유자(A), 스키마 파일·컴파일 프롬프트는 AI 엔지니어(R). **lint 결과의 소유자**를 지정한다 — 모순·고아·stale 보고를 처리하는 사람이 없으면 lint는 탐지 통제가 아니라 로그다. 감사 추적에 `derived_from[]`·`compiler_version`·`compiled_at`·`wiki_hit` 추가 |

### 운영 준비도 체크
- [ ] 경로별 p95 지연·요청당 호출 수의 베이스라인을 측정했고 SLO 초안이 있는가
- [ ] 생성·임베딩·벡터DB·그래프DB·리랭커 각각에 타임아웃·서킷 브레이커·폴백이 있고, 폴백 모델이 호환 매트릭스에 등록되어 있는가
- [ ] Agentic 루프·글로벌 경로의 상한 도달 시 저하 경로를 실제로 실행해 봤는가
- [ ] 패턴 배정표·경로 구성·상한이 코드 밖 설정으로 버전 관리되고 변경 절차(골든셋 회귀 → 카나리)가 있는가
- [ ] 캐시 키에 테넌트·인덱스 버전·프롬프트 버전·주체 집합 해시가 포함되고, TTL ≤ 주체 해석 TTL이며, 문서 톰스톤·ACL 이벤트가 캐시를 무효화하는가 (불균형 ①·② 반영)
- [ ] 트레이스에 경로·근거 ID·인덱스·프롬프트·모델 버전이 있어 과거 응답을 시점 재현할 수 있는가
- [ ] 패턴 배정표와 ACL 각각의 A가 지정되어 있는가
- [ ] 모든 지표가 경로별(`agent.route`)로 분해되고, `routing.decide`의 확신도·결정 소스가 대시보드 ③ 히스토그램·분포에 올라가는가
- [ ] `cache.invalidate`에 무효화 원천(톰스톤·ACL 이벤트) ID가 남아 "삭제 이벤트 → 결과·시맨틱 캐시 제거 p95"를 실제로 측정하고 있는가
- [ ] (LLM Wiki 하이브리드 시) 원문 변경·삭제 이벤트가 `stale` → 재컴파일로 이어지고, 위키 적중률·원문 폴백률·lint 모순 수가 대시보드에 있으며 lint 보고의 소유자가 있는가
