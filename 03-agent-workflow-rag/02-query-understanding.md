# 질의 이해와 라우팅

> **범위**: rewrite, decomposition, HyDE, intent 분류, 결정 모델 기반 라우팅

## 요약 (3줄)

1. 이 단계는 두 가지 다른 일을 한다. **질의 변환**(재작성·분해·HyDE·step-back·멀티 쿼리)은 검색 recall을 높이는 생성 과업이고, **라우팅**(어느 경로·인덱스·툴로 보낼까)은 선택지가 닫힌 판정 과업이다. 둘을 같은 LLM 호출에 섞지 않는다.
2. 라우터는 규칙 → 결정 모델 → 파인튜닝 분류기 → 프롬프트 LLM 순으로 가능한 가장 단순한 수단을 쓴다. 결정 모델(Jev / Decisions API)은 라벨이 적고 경로가 자주 바뀔 때의 새 선택지지만, 영어 중심 학습이라 **한국어 자체 평가셋이 필수**다 `[2차]`.
3. 한국어 질의는 조사·띄어쓰기·영한 혼용 때문에 영어 기준으로 설계한 변환·라우팅이 그대로 작동하지 않는다. 변환 전 정규화와 한국어 평가셋이 없으면 이 단계의 효과를 측정조차 할 수 없다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 정규화·변환된 검색 질의 집합(원 질의 + 재작성본 + 하위 질문) ② 라우팅 결정(경로·인덱스·툴 + 확신도) ③ 추출된 메타데이터 필터(기간·부서·문서 유형) ④ 명확화 필요 여부. 품질 기준은 변환 후 context recall 상승과 라우팅 정확도·보정 |
| **언제** (When) | 라우팅은 경로가 2개 이상이면 항상. 질의 변환은 Naive RAG 기준선에서 어휘 불일치·복합 질의 실패가 측정될 때 추가. 코퍼스가 작고 용어가 통일되어 있으면 변환 생략 가능. 명확화 질문은 모호 질의 비율이 확인된 뒤 |
| **어떻게** (How) | ① 질의 로그 수백 건으로 유형(단순 사실 / 복합 / 멀티홉 / 모호 / 범위 밖) 라벨링 → ② 한국어 정규화(띄어쓰기·조사·영한 혼용 처리) → ③ 규칙으로 처리 가능한 라우팅(키워드·권한·명시적 필터) 분리 → ④ 나머지 라우팅을 결정 모델 또는 분류기로, 확신도 임계값 미만은 명확화 → ⑤ 유형별 변환 전략 배정(복합→분해, 어휘 불일치→재작성·HyDE, 추상→step-back) → ⑥ 변환 전후 recall과 라우팅 정확도 `[실측]` |
| **왜** (Why) | 라우팅을 프롬프트 LLM에 맡기면 요청당 비용의 상당 부분이 판정에 쓰이고 같은 질의가 다른 경로로 가서 디버깅이 불가능하다. 변환 없이 검색하면 사용자 어휘와 문서 어휘의 간극이 그대로 recall 손실이 된다. 범위 밖 질의를 걸러내지 못하면 [04](04-generation-grounding.md)의 "근거 없음" 처리가 작동할 기회가 없다 |

## 문제와 맥락

사용자 질의는 검색에 최적화되어 있지 않다. 짧고, 대명사와 생략이 많고, 이전 대화에 의존하며, 하나의 문장에 여러 질문이 들어 있다. 검색 인덱스는 문서 어휘로 만들어져 있다. 이 간극을 좁히는 것이 질의 변환이고, 질의를 적절한 처리 경로로 보내는 것이 라우팅이다.

이 단계가 없거나 약하면 다음 증상이 나타난다.

- **대화 맥락 소실**: "그럼 작년은?"이 단독 질의로 검색되어 아무것도 못 찾음
- **복합 질의의 부분 답변**: "A의 가격과 B와의 차이는?"에서 A 가격만 답함
- **범위 밖 질의의 환각**: 코퍼스에 없는 주제를 묻는데 가장 유사한 무관 청크로 답을 만듦
- **잘못된 인덱스 조회**: 인사 규정 질의가 기술 문서 인덱스로 감
- **비결정적 경로**: 같은 질의가 오늘은 FAQ 경로, 내일은 복잡 문의 경로로

### 한국어 질의의 특성

영어 기준 RAG 설계가 한국어에서 깨지는 지점은 세 가지다.

| 특성 | 문제 | 대응 |
|---|---|---|
| **조사·어미 변형** | "연차는", "연차를", "연차가"가 BM25에서 다른 토큰. 임베딩은 일부 흡수하지만 희귀 용어에서 실패 | 형태소 분석기 기반 토크나이저로 BM25 인덱싱, 질의도 같은 분석기로 |
| **띄어쓰기 불일치** | "데이터베이스 백업"과 "데이터베이스백업", "DB백업"이 공존 | 띄어쓰기 정규화 또는 n-gram 보조 인덱스, 동의어 사전 |
| **영한 혼용·약어** | "MCP 서버 설정"과 "엠씨피 서버 설정", "PR 리뷰"와 "풀리퀘 리뷰" | 도메인 동의어 사전(온톨로지 레이블에서 생성 가능), 재작성 시 양쪽 표기 생성 |
| **높임·비격식** | "알려주세요"/"알려줘"/"궁금합니다"가 의도 분류기에 노이즈 | 분류·결정 모델 평가셋에 격식 변형 포함 |

결정 모델 Jev는 영어 중심 학습이 명시되어 있어 한국어 라우팅 정확도를 가정할 수 없다 `[2차]`. 분류기든 결정 모델이든 **한국어·혼합 언어·비격식 변형을 포함한 평가셋**으로 `[실측]`한 뒤 채택한다.

## 핵심 개념

### 질의 변환 기법

| 기법 | 동작 | 겨냥하는 실패 | 비용 |
|---|---|---|---|
| **재작성 (rewrite)** | 대화 맥락을 반영해 독립 질의로, 구어를 문서 어휘로 | 맥락 소실, 어휘 불일치 | LLM 1회 (소형 가능) |
| **분해 (sub-question decomposition)** | 복합 질의를 독립적으로 검색 가능한 하위 질문으로 | 복합 질의 부분 답변, 멀티홉 | LLM 1회 + 하위 질문 수만큼 검색 |
| **HyDE (Hypothetical Document Embeddings)** | 가상의 답변 문서를 생성해 그 임베딩으로 검색 | 질의-문서 어휘·형식 간극 | LLM 1회 + 환각된 가상 문서가 검색을 오도할 위험 |
| **Step-back** | 구체 질의를 상위 개념 질의로 추상화해 함께 검색 | 세부 사항만 묻는데 원리·배경 문서가 필요 | LLM 1회 + 검색 1회 추가 |
| **멀티 쿼리** | 같은 의도의 변형 질의 N개를 생성해 결과를 융합(RRF) | recall 부족, 표현 다양성 | LLM 1회 + 검색 N회 |
| **메타데이터 추출** | 질의에서 기간·부서·문서 유형을 구조화 출력으로 추출해 필터로 | 무관 기간·조직 문서 혼입 | LLM 1회(구조화 출력) 또는 규칙 |

변환은 모두 생성 과업이므로 LLM이 맡는다. 단, **어떤 변환을 적용할지**는 판정이므로 라우터가 결정한다. 모든 질의에 모든 변환을 적용하면 지연이 선형으로 누적된다.

### 라우팅의 세 층위

1. **경로 라우팅**: 단순 사실 / 복합 / 멀티홉 / 전역 / 범위 밖 / 명확화 필요 → [01](01-rag-architecture-patterns.md)의 패턴 배정표로 연결
2. **소스 라우팅**: 어느 인덱스·컬렉션·툴·DB로 보낼까 (인사 규정 vs 기술 문서 vs 정형 DB의 Text-to-SQL)
3. **모델 라우팅**: 어느 크기의 모델이 생성을 맡을까 — [Part 5/02](../05-cross-cutting/02-cost-latency-model-routing.md)

세 층위 모두 선택지가 닫혀 있다. 판정 수단의 일반 원칙은 [Part 1/02](../01-foundations/02-system1-vs-system2.md), 배치 설계는 [11](11-decision-layer.md).

### 라우터 수단 비교의 핵심 차이

- **규칙**: 명시적 필터("2025년", "@인사팀"), 권한, 금칙어. 결정론적이고 설명 가능. 의미 판단 불가
- **파인튜닝 분류기**: 라벨 수천 건 이상이면 가장 싸고 빠름. 경로 추가 시 재학습
- **결정 모델**: 상태(질의 + 대화 요약) + 타입드 질문("이 질의의 경로는 {A,B,C,D} 중?") → 선택 + 보정 확률. 경로 변경은 질문 정의 수정. Jev와 Decisions API는 인터페이스는 같지만 내부가 다르다(Jev는 결정 전용 비자기회귀 모델, Decisions API는 gpt-6-luna 출력 제약) `[벤더]` `[2차]`
- **프롬프트 LLM**: 선택지가 아직 안 굳었거나 설명이 함께 필요할 때. 비보정, 비용·지연 큼

## 아키텍처 / 파이프라인

```
원 질의 + 대화 히스토리
   │
   ▼
[정규화] 띄어쓰기·조사·영한 혼용 처리, 명시적 필터 파싱 (규칙)
   │
   ▼
[규칙 라우팅] 권한 없음 → 거부 / 명시적 필터 → 메타데이터 / 금칙 → 가드레일([12])
   │ 통과
   ▼
[판정 라우팅] 결정 모델 또는 분류기: 경로? 소스? 확신도?
   ├─ 확신 < θ 또는 "모호" ──▶ 명확화 질문 생성(LLM) ──▶ 사용자
   ├─ "범위 밖" ──▶ [04] 근거 없음 응답
   └─ 경로 확정 ──▶ [변환] 경로별 전략: 재작성 / 분해 / HyDE / step-back / 멀티 쿼리 (LLM)
                         │
                         ▼
                    검색 질의 집합 + 필터 + 라우팅 결정 + 확신도 ──▶ [03] 검색·리랭킹
```

출력 계약: `{ queries: [...], filters: {...}, route: enum, source: enum, confidence: float, needs_clarification: bool }`. 라우팅 결정과 확신도는 트레이스에 기록한다([Part 5/03](../05-cross-cutting/03-observability-tracing.md)).

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 쿼리 재작성 | 멀티턴 대화, 구어·약어 질의, 어휘 불일치 | 단발 질의에 용어가 이미 문서와 일치, 지연 예산 극소 | 하~중 — 소형 LLM 1회 | 표준 | `[2차]` |
| 분해 (sub-question) | 복합·비교 질의, 멀티홉 | 단순 질의(불필요한 검색 N회), 하위 질문 간 의존이 강해 순차 필요 | 중 — LLM 1회 + 검색 N회 | 안정 | `[2차]` |
| HyDE | 질의가 짧고 문서가 서술형, 임베딩 전용 검색 | 코퍼스에 없는 주제(가상 문서가 환각을 검색으로 전파), hybrid로 이미 충분 | 중 — LLM 1회, 오도 위험 | 안정 | `[검증]` 원 논문, 효과 코퍼스 의존 |
| Step-back | 구체 질의에 배경·원리 문서가 필요 | 사실 조회 위주 | 중 — 검색 1회 추가 | 안정 | `[검증]` 원 논문 |
| 멀티 쿼리 + RRF | recall 부족이 주 실패, 표현 다양성 큼 | 지연 예산 빡빡, precision이 더 문제 | 중 — 검색 N회 | 안정 | `[2차]` |
| 라우터: 규칙 | 명시적 필터·권한·금칙, 감사 대상 | 의미 기반 경로 판단 | 하 | 표준 | `[검증]` |
| 라우터: 파인튜닝 분류기 | 라벨 수천 건, 경로 고정, 초저지연·온프레미스 | 경로 자주 변경, 라벨 없음 | 중 — 학습·MLOps | 표준 | `[검증]` |
| 라우터: 결정 모델 (Jev / Decisions API) | 라벨 적음, 경로 자주 바뀜, 보정 확률로 명확화 임계값 필요 | 한국어 미검증 상태로 바로 운영, 판정 사유 설명 필수 | 하(호출) / 중(평가셋) | 신생 | `[벤더]` 지연 70~500ms 주장, `[2차]` 영어 중심 |
| 라우터: 프롬프트 LLM | 프로토타입, 경로 미확정, 설명 동반 필요 | 대량·저지연, 보정 확률 필요 | 중 — 토큰 | 안정 | `[검증]` 비보정 널리 보고 |
| 명확화 질문 생성 | 모호 질의 비율 높음, 대화형 UI | 단발 API, 사용자가 되묻기를 싫어하는 맥락 | 중 — LLM 1회 + 왕복 | 안정 | `[2차]` |

### 선택 가이드

- **경로가 2~3개로 고정이고 라벨 로그가 수천 건 있다면** → 파인튜닝 분류기 + 규칙. 이유: 가장 싸고 빠르며 한국어 데이터로 직접 학습하므로 언어 문제가 없다
- **경로가 자주 바뀌거나 라벨이 적고, 확신도로 명확화를 트리거하고 싶다면** → 결정 모델. 이유: 질문 정의만 수정하면 되고 보정 확률이 임계값 설계에 쓰인다. 단 한국어 평가셋 `[실측]` 선행, 불합격 시 분류기
- **멀티턴 대화형이라면** → 재작성은 항상, 분해는 라우터가 "복합"으로 판정한 경우만. 이유: 재작성 없이는 맥락 소실, 모든 질의 분해는 지연 낭비
- **임베딩 검색만 쓰고 recall이 낮다면** → HyDE보다 먼저 hybrid 검색([03](03-retrieval-reranking.md))을 시도. 이유: HyDE는 범위 밖 질의에서 환각을 검색으로 전파한다
- **판단이 어려우면** → 규칙 + 소형 LLM 라우터 + 재작성으로 시작하고, 라우팅 로그가 쌓이면 분류기 또는 결정 모델로 이전. 이유: 라벨 데이터가 자연스럽게 축적된다

## 설계 시 고려사항 (체크리스트)

- [ ] 질의 로그를 유형별로 라벨링했고 각 유형의 비율을 아는가
- [ ] 한국어 정규화(띄어쓰기·조사·영한 혼용)가 검색 인덱스의 토크나이저와 일치하는가
- [ ] 변환과 라우팅이 분리되어 있는가 (한 프롬프트에 "경로를 고르고 질의를 다시 써라"를 섞지 않았는가)
- [ ] 라우터 평가셋에 한국어·혼합 언어·비격식·오타 변형이 포함되어 있는가
- [ ] 라우팅 확신도 임계값 미만의 경로(명확화 / 보수적 기본 경로 / 사람)가 정의되어 있는가
- [ ] "범위 밖" 경로가 있고 [04](04-generation-grounding.md)의 근거 없음 응답으로 연결되는가
- [ ] 변환된 질의가 아닌 **원 질의**도 검색에 포함되는가 (변환 실패 시 안전망)
- [ ] 하위 질문 수·멀티 쿼리 수에 상한이 있는가
- [ ] 라우팅 결정·확신도·적용된 변환이 트레이스에 기록되는가
- [ ] 라우터 장애 시 폴백 경로(규칙 기반 기본 경로)가 있는가

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 변환이 의도를 왜곡 | 재작성·HyDE가 사용자가 묻지 않은 것을 검색 | 원 질의 병행 검색, 변환 결과를 사용자에게 노출(확인 가능) |
| HyDE의 환각 전파 | 코퍼스에 없는 주제에서 그럴듯한 무관 문서 검색 | 범위 밖 판정을 HyDE 앞에, hybrid 우선 |
| 라우터 오판의 증폭 | 잘못된 경로는 이후 모든 단계를 무효화 | 확신도 임계값, 경로별 품질 모니터링, 오판 로그 리뷰 |
| 결정 모델의 한국어 품질 미검증 | 영어 기준 정확도가 한국어에서 재현되지 않을 수 있음 | 한국어 평가셋 `[실측]`, 비교군으로 분류기 유지 |
| 보정 확률의 보정 여부 미확인 | 명확화 임계값이 무의미 | 신뢰도 다이어그램으로 보정 확인 후 임계값 설정 |
| 지연 누적 | 정규화 + 라우팅 + 변환 + 검색 N회가 직렬이면 체감 지연 큼 | 변환과 검색 병렬화, 단순 경로는 변환 생략 |
| 명확화 피로 | 되묻기가 잦으면 사용자 이탈 | 임계값 조정, 가장 가능성 높은 해석으로 답하되 가정을 명시 |
