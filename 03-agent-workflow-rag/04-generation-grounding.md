# 생성과 근거 강제

> **범위**: citation 강제, 구조화 출력, 근거 검증기, 환각 가드

## 요약 (3줄)

1. "출처를 밝혀라"는 프롬프트 지시만으로는 근거가 강제되지 않는다. 근거는 **입력에서 강제하고**(citation 필드가 있는 구조화 출력) **출력에서 검증한다**(근거-답변 정합성 검증기). 둘 중 하나만 하면 그럴듯한 가짜 citation이 통과한다.
2. 검증기는 NLI 모델 → 결정 모델 → LLM judge → 규칙 순으로 비용·정밀도·설명 가능성이 다르다. 온라인 경로에는 싸고 빠른 것(NLI·결정 모델·규칙)을, 오프라인 평가에는 LLM judge를 둔다.
3. "근거 없음"은 실패가 아니라 **정상 출력**이다. 검색 결과가 질문에 답하지 못하면 모델이 그렇게 말하도록 스키마에 경로를 만들고, 그 비율을 품질 지표로 추적한다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | [03](03-retrieval-reranking.md)의 근거 단위 묶음을 받아 **렌더 가능한 응답 스키마**를 만든다: 답변 텍스트 + 문장(또는 주장) 단위 citation + 확신도 + 근거 없음 플래그. citation은 [Part 2/08](../02-data-pipeline/08-grounding-data-design.md)의 스키마(source_id, span)를 그대로 참조한다. 품질 기준은 faithfulness와 citation 정확도(인용된 근거가 실제로 해당 주장을 지지하는 비율) |
| **언제** (When) | 답변이 사실 주장을 포함하면 항상. 창작·브레인스토밍처럼 근거가 없는 과업은 생략. 검증기는 답변이 의사결정·행동·규제 대상으로 이어지면 필수, 탐색적 내부 도구면 샘플링 검증으로 미룰 수 있음 |
| **어떻게** (How) | ① 응답 스키마 정의(답변 + citations[] + abstain) → ② 컨텍스트에 근거 단위를 ID와 함께 배치, "ID 없는 주장 금지·근거 없으면 abstain" 지시 → ③ 구조화 출력 모드로 생성 → ④ 규칙 검증(ID 존재·span 유효) → ⑤ 정합성 검증(NLI·결정 모델) → ⑥ 불합격 주장 제거·재생성·abstain, 상한 도달 시 폴백 → ⑦ faithfulness·citation 정확도·abstain 비율 `[실측]` |
| **왜** (Why) | 검증 없는 citation은 **신뢰의 외관**만 준다. 사용자는 출처가 붙어 있으면 확인하지 않는다. 가짜 citation은 citation 없는 환각보다 해롭다. 근거 없음 경로가 없으면 모델은 가장 유사한 무관 근거로 답을 만든다 |

## 문제와 맥락

RAG의 전제는 "근거를 주면 모델이 근거대로 답한다"이다. 실제로는 세 가지 방식으로 깨진다.

| 환각 유형 | 증상 | 원인 | 1차 대응 |
|---|---|---|---|
| **근거 외 생성 (extrinsic)** | 컨텍스트에 없는 사실을 모델 지식으로 채움 | 근거가 불충분하거나 모델이 사전 지식을 선호 | abstain 경로, "컨텍스트에 없으면 모른다고 답하라" + 검증기 |
| **근거 왜곡 (intrinsic)** | 근거는 인용했으나 내용을 바꿈(숫자·조건·부정 반전) | 요약 과정의 압축 오류, 긴 컨텍스트 중간 누락 | 문장 단위 NLI 검증, 숫자·날짜 규칙 대조 |
| **가짜 citation** | 존재하지 않거나 무관한 근거 ID를 붙임 | "출처를 밝혀라" 지시가 형식만 학습시킴 | ID 존재·span 규칙 검증, 정합성 검증 |
| **범위 밖 답변** | 코퍼스 주제가 아닌 질문에 답함 | [02](02-query-understanding.md)의 범위 밖 판정 누락 | 라우터에서 차단 + abstain |
| **근거 과잉 일반화** | 특정 조건의 근거를 일반 규칙으로 서술 | 근거의 적용 범위(기간·조직·버전)를 무시 | 메타데이터를 컨텍스트에 명시, 조건 포함 여부 검증 |

프롬프트 지시는 이 모든 유형에 대해 **확률적 준수**만 제공한다. 1만 건 중 몇 건은 어긴다. 그 몇 건이 의사결정으로 이어진다면 검증 없는 생성은 운영 불가다. 원칙은 [Part 1/04](../01-foundations/04-neuro-symbolic-ai.md)의 검증기 패턴(Generate → Verify)이다.

## 핵심 개념

### citation 강제 방식 3종

| 방식 | 동작 | 보장하는 것 | 보장하지 않는 것 |
|---|---|---|---|
| **프롬프트 지시** | "각 문장 끝에 [n]으로 출처를 표시하라" | 형식의 확률적 준수 | ID 유효성, 근거-주장 정합성 |
| **구조화 출력** | 스키마 `{claims: [{text, citations: [{source_id, span}]}], abstain: bool}`를 스키마 보장 모드로 생성 | 스키마 적합(ID 필드 존재, 타입), 파싱 안정 | ID가 실제 컨텍스트에 있는지, 근거가 주장을 지지하는지 |
| **사후 검증** | 생성 후 규칙(ID·span 존재) + 정합성 검증기(NLI·결정 모델·LLM judge) | ID 유효성, 근거-주장 정합성(검증기 정밀도 한도 내) | 검증기 자체의 오류, 검증기가 못 보는 의미 오류 |

세 방식은 대체재가 아니라 **층**이다. 구조화 출력이 형식을, 규칙이 참조 무결성을, 정합성 검증기가 의미를 맡는다. 구조화 출력 수단의 비교는 [Part 1/01](../01-foundations/01-llm-fundamentals.md).

### 근거-답변 정합성 검증기

| 검증기 | 동작 | 지연·비용 | 정밀도 | 설명 가능성 | 적합 |
|---|---|---|---|---|---|
| **규칙** | citation ID가 컨텍스트에 존재, span이 범위 내, 숫자·날짜가 근거 텍스트에 문자열로 존재 | 극소 | 다루는 범위 내 100% | 완전 | 모든 운영 시스템의 1차 |
| **NLI 모델** | (근거, 주장) 쌍을 entailment / neutral / contradiction으로 분류하는 소형 모델 | 수십 ms, 저렴 | 중 — 긴 근거·복합 주장에서 약화, 한국어 모델 제한 | 낮음 | 온라인 경로의 문장 단위 검증 |
| **결정 모델** | "이 주장은 이 근거에 의해 지지되는가" 타입드 질문 → 보정 확률 | 낮음(주장) | 미검증 | 낮음 | 보정 확률로 임계값·HITL 설계. 한국어 `[실측]` 선행 |
| **LLM judge** | LLM에 근거·주장을 주고 지지 여부와 사유를 생성 | 높음 | 높음(복합 추론) — 단 편향·일관성 한계 | 사유 생성(사후 합리화 위험) | 오프라인 평가, 골든셋 구축, 고위험 샘플링 |
| **뉴로심볼릭 검증기** | 주장을 구조화(트리플·수식)해 온톨로지·KG·규칙으로 대조 | 중 | 다루는 범위 내 높음 | 높음 | 규제 도메인, 정형 사실(금액·기간·자격) |

### "근거 없음" 처리

abstain은 스키마의 1급 출력이다. 세 지점에서 발생한다. ① [02](02-query-understanding.md) 라우터가 범위 밖 판정 ② [03](03-retrieval-reranking.md) 리랭커 최고 점수가 임계값 미만 ③ 생성 모델이 컨텍스트로 답할 수 없다고 판단. 세 경우 모두 같은 응답 형태("이 질문에 답할 근거를 찾지 못했습니다" + 가능하면 대안 제시)로 수렴시키고, abstain 비율을 추적한다. 비율이 너무 낮으면 모델이 억지로 답하고 있고, 너무 높으면 검색이 약하다.

### 뉴로심볼릭 검증기 패턴

[Part 1/04](../01-foundations/04-neuro-symbolic-ai.md)의 검증기 패턴을 이 단계에 적용하면: LLM이 답변과 함께 **구조화된 주장**(예: `{subject, predicate, object, source_id}`)을 생성 → 규칙이 참조 무결성 검증 → 온톨로지·KG에 같은 트리플이 있는지 또는 모순되는지 대조 → 불합격 주장은 제거하고 오류를 구조화해 재생성. 설명 가능성이 필요한 규제 도메인에서 LLM judge를 대체하거나 보완한다. 구체적 배치는 [10](10-neuro-symbolic-reasoning.md).

### Part 2/08 citation 스키마와의 계약

이 단계는 citation 스키마를 **정의하지 않는다**. [Part 2/08](../02-data-pipeline/08-grounding-data-design.md)이 정의한 근거 단위의 식별자(source_id)와 위치(span)를 그대로 참조한다. 생성 모델에게 노출하는 ID는 짧은 별칭(`[1]`, `[2]`)이어도 되지만, 응답 스키마에서는 원래 식별자로 환원한다. 이 계약이 지켜져야 [Part 4/06](../04-dynamic-ui/06-hitl-ui-patterns.md)의 citation 렌더가 원문으로 점프할 수 있다.

## 아키텍처 / 파이프라인

```
[03] 근거 단위 묶음 {id, text, source_id, span, metadata}
   │
   ▼
[컨텍스트 조립] ID 라벨링, 메타데이터(기간·조직) 명시, "ID 없는 주장 금지 / 근거 없으면 abstain" 지시
   │
   ▼
[생성] 구조화 출력: {claims: [{text, citations: [{id, span}]}], abstain, confidence}
   │
   ▼
[규칙 검증] ID 존재? span 유효? 숫자·날짜가 근거에 존재? ──불합격──▶ 오류 구조화 → 재생성(≤N) → 폴백
   │ 합격
   ▼
[정합성 검증] 문장 단위 NLI 또는 결정 모델 ──지지 안 됨──▶ 해당 주장 제거 / 재생성 / abstain
   │ 합격                                   └─ 확신 낮음 ──▶ 샘플링 LLM judge 또는 사람([12])
   ▼
[응답 스키마] 텍스트 + citations(원 식별자로 환원) + confidence + abstain ──▶ [Part 4]
```

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 프롬프트 지시만 | 프로토타입, 내부 탐색 도구, 위반 비용 낮음 | 의사결정·행동·규제 연결, 외부 사용자 노출 | 하 | 표준 | `[검증]` 확률적 준수 한계 널리 보고 |
| 구조화 출력 citation | 모든 운영 시스템의 기본. 스키마 보장 모드 사용 가능 | 자유 형식 산문이 UX상 필수이고 citation 렌더가 없음 | 하~중 — 스키마 설계 | 안정 | `[벤더]` 스키마 보장 모드, `[2차]` |
| 규칙 검증 (ID·span·숫자 대조) | 항상. 가장 싸고 즉시 효과 | 자유 텍스트 출력만 있어 대조할 ID·span이 없음(그 경우 구조화 출력부터) | 하 | 표준 | `[검증]` |
| NLI 검증기 | 온라인 경로, 문장 단위 사실 주장 | 복합·조건부 주장, 긴 근거, 한국어 모델 부재 | 중 — 모델 서빙, 한국어 `[실측]` | 안정 | `[검증]` NLI 기반 faithfulness 연구 다수, 도메인 전이 한계 |
| 결정 모델 검증기 (Jev / Decisions API) | 보정 확률로 HITL 임계값, 대량 저지연 | 한국어 미검증, 설명 필요, 사례 없음 | 하(호출) / 중(평가) | 신생 | `[벤더]` `[2차]` 사례 미확인 |
| LLM judge | 오프라인 평가, 골든셋, 고위험 샘플링 | 온라인 전수 검증(비용·지연), 판정 일관성 요구 | 상 | 안정 | `[검증]` 편향·일관성 한계, `[2차]` RAGAS judge 정렬 가이드 |
| 뉴로심볼릭 검증기 (온톨로지·KG·규칙 대조) | 규제 도메인, 정형 사실(금액·기간·자격·관계), 설명 필수 | 온톨로지·KG 없음, 주장이 비정형 서술 | 중~상 — 기호 체계 구축 | 시험 | `[검증-단일저자]` 2604.00555, `[검증]` V&V 서베이(결합 전체는 미성숙) |
| abstain 경로 | 사실 주장을 포함하는 모든 답변 | 근거 개념이 없는 창작·브레인스토밍 과업(abstain이 무의미) | 하 | 표준 | `[2차]` |
| 재생성 루프 (검증 실패 → 오류 피드백) | 검증 실패율이 낮고 실패가 교정 가능 | 실패율 높음(비용 폭증), 지연 예산 빡빡 | 중 — 호출 수 가변 | 안정 | `[2차]` |

### 선택 가이드

- **답변이 의사결정·행동·규제로 이어진다면** → 구조화 출력 + 규칙 검증 + NLI(또는 결정 모델) 검증기 + abstain은 필수. 이유: 확률적 준수로는 안 되는 영역이다
- **금액·기간·자격 같은 정형 사실이 핵심이고 설명이 필요하다면** → 뉴로심볼릭 검증기 추가. 이유: 규칙·온톨로지 대조는 결정론적이고 판정 사유를 보여줄 수 있다. 단 온톨로지 먼저([Part 2/06](../02-data-pipeline/06-ontology-driven-modeling.md))
- **대량 요청에 보정된 확신도로 사람 검토를 트리거하고 싶다면** → 결정 모델 검증기를 NLI와 같은 평가셋으로 비교 후 선택. 이유: 보정 확률이 임계값 설계에 쓰인다. 한국어 `[실측]` 선행
- **품질을 측정·개선하려는 단계라면** → LLM judge를 오프라인에서, judge 자체를 사람 라벨과 정렬. 이유: 온라인에 두기엔 비싸지만 복합 추론 판정은 가장 정확하다
- **판단이 어려우면** → 구조화 출력 + 규칙 검증 + abstain을 기본값으로, NLI는 faithfulness 측정 결과를 본 뒤 추가. 이유: 가장 싸고 즉시 효과가 있으며 측정 기반으로 다음 층을 결정할 수 있다

## 설계 시 고려사항 (체크리스트)

- [ ] 응답 스키마에 claims[].citations[]와 abstain 필드가 있고 스키마 보장 모드로 생성하는가
- [ ] citation의 source_id·span이 [Part 2/08](../02-data-pipeline/08-grounding-data-design.md) 스키마와 동일한 식별 체계인가
- [ ] 규칙 검증(ID 존재·span 유효·숫자 대조)이 모든 응답 경로 앞에 있는가 (우회 경로 없음)
- [ ] 정합성 검증기가 문장(주장) 단위로 동작하는가 (답변 전체 단위는 부분 환각을 놓친다)
- [ ] 검증 실패 시 처리(주장 제거 / 재생성 / abstain)가 정의되고 재생성 상한이 있는가
- [ ] abstain 비율을 추적하고 너무 낮거나 높을 때의 조사 절차가 있는가
- [ ] 근거의 적용 조건(기간·조직·버전)이 컨텍스트에 명시되고 답변에 반영되는지 확인하는가
- [ ] 한국어 NLI·judge 품질을 자체 평가셋으로 `[실측]`했는가
- [ ] LLM judge를 쓴다면 사람 라벨과의 정렬을 측정했는가 ([13](13-evaluation-rag-agents.md))
- [ ] 검증 결과(합격·불합격 주장, 확신도)가 트레이스에 기록되는가
- [ ] 압축·요약된 근거를 썼다면 citation이 요약이 아닌 원문 위치를 가리키는가 ([03](03-retrieval-reranking.md))

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 검증기도 틀린다 | NLI·judge의 거짓 합격이 가짜 citation을 통과시킴 | 다층 검증(규칙 + NLI), 샘플링 사람 리뷰, 검증기 정밀도 측정 |
| 한국어 NLI·judge 모델 품질 | 영어 벤치마크 성능이 재현되지 않음 | 다국어 모델 `[실측]`, 도메인 데이터로 미세조정 |
| 문장 단위 검증의 한계 | 여러 근거를 종합한 주장은 단일 (근거, 주장) 쌍으로 검증 불가 | 복수 근거 결합 검증, 복합 주장은 LLM judge 샘플링 |
| 재생성 비용 | 검증 실패율이 높으면 요청당 호출 수 배 | 실패 패턴을 프롬프트·스키마에 반영, 상한 + 폴백 |
| abstain 남용 | 모델이 어려운 질문을 모두 회피 | abstain 비율 상한 모니터링, 검색 품질 점검 |
| citation 과잉 | 모든 문장에 citation을 붙여 가독성 저하, 사용자가 무시 | 사실 주장에만 citation, UI에서 접기([Part 4/06](../04-dynamic-ui/06-hitl-ui-patterns.md)) |
| 결합 시스템 V&V 미성숙 | 생성 + 검증기 전체의 정확성을 보장하는 방법론이 부분적 | Renkhoff et al. 2024 `[검증]`의 결론. End-to-End 골든셋으로 보완 |
| 스키마 적합 ≠ 사실 정확 | 구조화 출력이 완벽해도 내용은 틀릴 수 있음 | 구조화 출력을 검증의 전제로만 보고 정합성 검증을 생략하지 않음 |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 이 단계는 **출력 가드레일이 실제로 놓이는 자리**이고, 요청당 토큰 비용의 대부분이 발생하는 자리다. 운영 설계의 핵심 질문은 둘이다. 검증기가 죽었을 때 응답을 내보낼 것인가, 모델이 바뀌었을 때 무엇을 다시 재야 하는가. 레이어 간 종합은 [Part 5/06](../05-cross-cutting/06-operational-design-matrix.md).

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| **요청 수** (중심 축) | 생성 모델 API의 토큰 한도(TPM)가 요청 한도보다 먼저. 재생성 루프가 호출 수를 1 → N으로 늘림. NLI 검증기 처리량 | 프롬프트 캐시(시스템 지시·스키마 정의 고정 접두사), 결과 캐시(근거 묶음 해시 + 정규화 질의 + 프롬프트 버전), 경로별 모델 라우팅(단순 경로는 소형 모델, [Part 5/02](../05-cross-cutting/02-cost-latency-model-routing.md)), 재생성 상한, 스트리밍으로 체감 지연 분리, 요청 경로 무상태 | 요청 수 × (1 + 재생성 횟수) × 컨텍스트 토큰 |
| **컨텍스트 길이** | top-k·청크 길이가 늘면 토큰 비용·지연이 선형 증가, 중간 누락 심화 | 컨텍스트 예산 고정([03](03-retrieval-reranking.md)의 컷오프), 추출형 압축 | 근거 토큰 수 |
| **주장 수 × 근거 수** | 문장 단위 검증은 (주장, 근거) 쌍마다 NLI 추론 | 주장당 상위 근거 1~2개만 대조, 배치 추론, 등급 1 경로는 샘플링 검증 | 주장 수 × 대조 근거 수 |
| **테넌트** | 테넌트별 프롬프트 변형·금칙·면책 문구 | 프롬프트 템플릿 + 테넌트 설정 레이어(상속), 캐시 키에 테넌트 | 테넌트 수(설정만) |

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 생성 모델 API 다운·지연 | 응답 없음, 첫 토큰 지연 | 벤더별 오류율·p95, 서킷 브레이커 열림 | 호환 매트릭스에 등록된 폴백 모델(같은 프롬프트 버전으로 골든셋 통과한 것만) → 실패 시 "근거 목록만 제시(생성 없음)" 저하 또는 캐시 응답 | 폴백 모델 사용률 10분간 50%(예시) |
| 구조화 출력 스키마 검증 실패 폭증 | 재생성으로 지연, abstain 급증 | 스키마 실패율 | 재생성(예시 ≤ 2회) → 실패 시 등급 1 경로는 자유 텍스트 + "citation 없음" 표시로 저하, 등급 2 이상은 abstain | 실패율 5% 초과(예시) → 모델 버전 변경 의심 |
| 재생성 루프 폭주 | 비용·지연 | 요청당 호출 수 분포, 상한 도달률 | 상한에서 합격 주장만으로 축약 응답 또는 abstain | 상한 도달률 3%(예시) |
| **검증기(NLI·결정 모델) 다운·지연** | 검증 없이 응답이 나갈 위험 | 검증기 오류율·p95 | 등급 1: 규칙 검증만으로 저하 + "미검증" 플래그 — 저하 코드 `grounding_unverified`로 계약 ② `degradation[]`([Part 0/01](../00-overview/01-reference-architecture.md))에 담아 Interaction 끝점(4/03 "부분" variant·4/09 고지)까지 전달한다(불균형 ④ 반영). **등급 2 이상: fail-closed** — 응답 보류·abstain | 즉시 |
| 검증기 거짓 합격률 상승(드리프트) | 가짜 citation 통과 | 샘플링 사람 리뷰·judge와의 불일치율 | 자동 대응은 보수적 방향만(검증 엄격화·사람 검토 비율↑). 임계값 완화는 사람 결정 + 사후 샘플 감사([3/12](12-guardrails-hitl.md) 공통 규칙) (불균형 ⑦ 반영) | 불일치율 ±5%p(예시) |
| abstain 비율 급변 | 너무 낮음(억지 답변) / 너무 높음(검색 약화) | abstain 비율, 사유 코드 분포 | 없음 — 알림. 원인은 [02](02-query-understanding.md)·[03](03-retrieval-reranking.md)에 있을 가능성 | 베이스라인 ±50%(예시) |
| 프롬프트 캐시 오염 | 구 프롬프트·구 테넌트 설정으로 응답 | 캐시 키에 버전 미포함 탐지(배포 검증) | 캐시 키 설계로 예방, 배포 시 전체 무효화 | 배포 검증 실패 시 |

SLI 후보: 근거 부합률(faithfulness, 샘플 judge), citation 정확도, 스키마 실패율, 재생성 횟수 분포, abstain 비율, 생성 p95·첫 토큰 지연, 검증기 적용률, **삭제 이벤트 → 결과 캐시 제거 p95**(불균형 ① 반영). SLO 초안(예시): 샘플 faithfulness ≥ 0.9, 스키마 실패율 < 1%, 첫 토큰 ≤ 1.5초·완료 p95 ≤ 6초, 등급 2 이상 경로 검증기 적용률 = 100%. 서킷 브레이커 위치: 생성 API(벤더별), 검증기 서빙, LLM judge API. 쓰기 행동: 없음(캐시만). 결과 캐시(근거 묶음 해시 키)는 [Part 2/07](../02-data-pipeline/07-freshness-and-sync.md) 변경 큐 **삭제 레인의 소비자**로 등록해, 삭제된 문서를 근거로 가진 캐시 항목은 인덱스 버전과 무관하게 **문서 ID 톰스톤**으로 제거한다 (불균형 ① 반영).

가장 자주 바뀌는 것: 프롬프트(주 단위) ≈ 모델 버전(벤더 일정, 월~분기) > 응답 스키마 > 검증기 모델. 코드 밖 설정으로 둘 것: 생성 프롬프트 템플릿, 응답 스키마 정의, 검증기 임계값, 재생성 상한, 폴백 모델 매트릭스, 금칙·면책 규칙. 포트·어댑터 뒤에 둘 외부 의존: 생성 모델 API(벤더 둘 이상), NLI·결정 모델 서빙, LLM judge, 온톨로지·KG 조회.

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성의 "탐지 신호"가 **실제로 어디서 나오는지**를 설계한다. 기준은 [Part 1/07 관측성 설계 요소](../01-foundations/07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md). 이 단계는 요청당 토큰 비용의 대부분과 **검증 판정**이 발생하는 자리라, 모델 호출 스팬(`gen_ai.*`)과 검증 스팬을 분리해 기록해야 "비용은 어디서, 거부는 왜"를 따로 답할 수 있다. OTel GenAI 속성은 Development 등급이므로 매핑 계층을 거쳐 붙인다.

| 출력 가드레일 | `gate.evaluate output_policy` (부모 `invoke_agent`, 검증 뒤) | `agent.decision`(pass/block/degrade), `agent.rule_ids[]`, `agent.rules_version`(금칙·PII), `agent.pii_detected`·`agent.pii_masked` | 출력 차단률(사유별), PII 탐지율 | 차단 건 전수, 본문은 마스킹 후 참조만 |

| 결과·프롬프트 캐시 | 이벤트 `cache.lookup` / `cache.invalidate`, 배포 시 `cache.key_schema_check` | `agent.cache_hit`, `agent.cache_kind`(result/prompt), 키 구성 버전(프롬프트·모델·테넌트·인덱스·근거 묶음 해시 포함 여부), 무효화 원인(tombstone/version)·원천 이벤트 ID | 캐시 히트율, **삭제 이벤트 → 결과 캐시 제거 p95**, 배포 검증 실패 건수(키에 버전 미포함) → 프롬프트 캐시 오염 | 전수, 키는 해시만 |

| 알림 | 조건 (예시) | 심각도 | 런북 (첫 3단계) |
|---|---|---|---|
| 생성 폴백 급증 | `agent.outcome=fallback` 비율 10분간 50% 초과, 또는 벤더 서킷 열림 | P1 | ① 벤더 상태·서킷·폴백 모델 한도 잔량 확인 ② 폴백 모델이 현재 프롬프트 버전으로 호환 매트릭스에 "통과"인지 확인 ③ 지속 시 "근거 목록만 제시" 저하 강제, 첫 토큰 지연 SLO 위반 공지 |
| 스키마 실패·재생성 상승 | 스키마 실패율 5% 초과, 또는 재생성 상한 도달률 3% 초과 | P2 | ① 모델 버전별로 분해 — 벤더 자동 업데이트 여부 확인 ② 프롬프트·스키마 최근 버전 변경 확인, 필요 시 롤백 ③ 등급 1 자유 텍스트 저하 비율과 등급 2 abstain 비율 확인 |
| **검증기 장애(등급 2 이상)** | `generation.verify grounding` 오류 1건 이상, 또는 등급 2 이상 경로 검증기 적용률 < 100% | **P1 즉시** | ① fail-closed 동작 확인 — `agent.outcome=blocked` 증가와 검증 스팬 없는 등급 2 응답 0건 ② 검증기 서빙 상태·p95 확인 ③ 등급 1 `grounding_unverified`가 Interaction 끝점까지 전달·고지되는지 확인 |
| 거짓 합격 드리프트 | judge-사람 불일치율 또는 "검증 통과 ∧ judge 불합격" 비율이 ±5%p 이동 | P2 | ① 검증기·judge·모델 버전 변경 이력 확인 ② 샘플 리뷰 비율 상향(보수적 방향만) ③ 임계값 완화는 사람 결정 + 사후 샘플 감사([12](12-guardrails-hitl.md)) |
| abstain 비율 급변 | abstain 비율이 베이스라인 ±50% | P2 | ① 사유 코드 분포 확인 — 근거 부족 vs 불합격 vs 정책 ② 검색 저하 플래그(`dense_unavailable` 등)와의 교차 비율로 원인이 [02](02-query-understanding.md)·[03](03-retrieval-reranking.md)인지 분리 ③ 억지 답변 쪽(너무 낮음)이면 faithfulness 샘플 즉시 확대 |

대시보드에서 이 단계를 보는 뷰: ② Reasoning 패널 "생성·검증" — 생성 p95·첫 토큰 지연, 스키마 실패율, 검증 통과·거부 사유 분포, abstain 사유, `grounding_unverified` 비율 / ③ 비용·판정 분포 — 요청당 토큰·비용 분포, 캐시 토큰 비율, 모델 티어 비중, 재생성 분포, 응답 확신도 히스토그램 / ① E2E — 저하율 중 `grounding_unverified` 분해, faithfulness 샘플 추이.
감사 추적으로 넘기는 필드(관측 로그와 분리): 프롬프트·모델 버전(폴백 여부), 응답 스키마 버전, 주장별 citation(source_id·span), 검증기 종류·버전·판정·확신도, 불합격 주장과 처리, 재생성 횟수, abstain 사유 코드, 캐시 히트 여부 — 거버넌스 접점 표와 동일. 생성 출력 원문은 감사 저장소에 장기 보존, 관측 로그에는 참조만.
이 단계의 관측이 없으면 못 보는 장애: **검증 없이 나간 답** — 검증기 다운이 저하로 처리되면 오류율은 0이고 지연은 오히려 줄어든다. `generation.verify` 스팬의 적용률과 `grounding_unverified` 비율을 세지 않으면 가짜 citation은 몇 주 뒤 사용자 신고로 발견된다. 그리고 **벤더의 조용한 모델 업데이트** — 같은 모델 ID로 출력 분포가 바뀌면 스키마 실패율을 모델 버전별로 분해하지 않는 한 "프롬프트 탓"으로 오진한다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | 답변 표시는 **1**. 답변이 의사결정·규제 대상·외부 고객으로 이어지면 **2**(여러 사용자 영향) — 검증기 필수, 검증기 장애 시 fail-closed, 거짓 합격 샘플 리뷰. 행동은 없음(행동은 [06](06-agent-design-patterns.md)·[09](09-tools-and-mcp.md)) |
| 가드레일 위치 | **출력 가드레일의 실제 자리**. 순서: 규칙 검증(ID·span·숫자) → 정합성 검증(NLI·결정 모델) → PII·금칙 출력 검사([12](12-guardrails-hitl.md)). 입력 측은 [02](02-query-understanding.md) |
| 게이트 출력과 판정 수단 | 통과 / 차단(PII·금칙·전 주장 불합격 → abstain) / 저하("미검증" 플래그 = 계약 ② `degradation[]`의 `grounding_unverified`, 불합격 주장 제거 — 불균형 ④ 반영) / 승인 요청(확신 낮음 ∧ 등급 2 → 사람 샘플 리뷰, 비동기). 규칙 → NLI·결정 모델 → judge 샘플링 순 |
| 소유자 (A) | 프롬프트·응답 스키마: 제품 책임자(A), AI 엔지니어(R). 검증기 임계값: 아키텍트(A). 금칙·PII 규칙: 보안 책임자(A), 법무(C) |
| 감사 추적에 남길 필드 | 프롬프트 버전, 모델 버전(폴백 사용 여부), 응답 스키마 버전, 주장별 citation(source_id·span), 검증기 종류·버전·판정·확신도, 불합격 주장과 처리(제거/재생성/abstain), 재생성 횟수, abstain 사유 코드, 캐시 히트 여부 |

### 운영 준비도 체크
- [ ] 등급 2 이상 경로에서 검증기 장애 시 fail-closed가 코드로 강제되는가 (저하가 아니라 보류)
- [ ] 폴백 모델이 현재 프롬프트 버전으로 골든셋을 통과해 호환 매트릭스에 등록되어 있는가
- [ ] 스키마 실패율·재생성 횟수·abstain 비율·faithfulness 샘플의 베이스라인과 SLO 초안이 있는가
- [ ] 프롬프트·스키마·임계값·폴백 매트릭스가 코드 밖 설정으로 버전 관리되고, 프롬프트 변경이 골든셋 회귀를 거치는가
- [ ] 캐시 키에 프롬프트 버전·모델 버전·테넌트·인덱스 버전이 포함되는가
- [ ] 트레이스에 주장별 citation·검증 판정·버전 키가 있어 "그때 그 답의 근거가 무엇이었나"를 재구성할 수 있는가
- [ ] 검증기 거짓 합격률을 주기적 샘플 리뷰로 측정하는 절차와 담당(R)이 있는가
- [ ] `generation.verify grounding` 스팬 적용률을 위험 등급별로 세고, 등급 2 이상에서 100% 미만이면 P1 알림이 되는가
- [ ] 스키마 실패율·요청당 토큰이 모델 버전별로 분해되어 벤더의 조용한 모델 업데이트를 프롬프트 문제와 구분할 수 있는가
