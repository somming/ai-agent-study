# 워크플로우 vs 에이전트

> **범위**: 결정론적 워크플로우와 자율 에이전트의 스펙트럼, 선택 기준

## 요약 (3줄)

1. **워크플로우**는 코드가 제어 흐름을 정하고 LLM은 정해진 자리에서만 호출되는 구조, **에이전트**는 LLM이 다음 행동과 종료 시점을 스스로 정하는 구조다. 둘은 이분법이 아니라 "제어 흐름을 누가 결정하는가"의 스펙트럼이다.
2. 선택 기준은 네 가지다. 과업의 **예측 가능성**, 실패 **비용**, 허용 **지연**, **디버깅 가능성**. 네 가지 중 셋 이상이 엄격하면 워크플로우, 과업이 열려 있고 경로를 미리 열거할 수 없을 때만 에이전트다.
3. "가장 단순한 형태에서 시작한다"가 이 Part의 첫 원칙이다. 단일 프롬프트 → 체이닝 → 라우팅 → 병렬화 → 오케스트레이터-워커 → 평가자-최적화 → 자율 에이전트 순으로, 측정된 실패가 다음 단계를 정당화할 때만 올라간다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 과업별 자율성 수준 결정(어느 부분이 코드가 정한 흐름이고 어느 부분이 모델 판단인지 그린 **실행 그래프**) ② 각 LLM 호출 노드의 입출력 계약 ③ 에이전트 구간의 상한(최대 반복·비용·시간)과 종료 조건 |
| **언제** (When) | 모든 Part 3 설계의 첫 결정. 단일 프롬프트로 끝나는 과업이면 이 페이지만 읽고 끝. 에이전트 구간은 "경로를 미리 열거할 수 없다"가 측정·사례로 확인될 때만 도입. 멀티 에이전트([07](07-multi-agent-orchestration.md))는 단일 에이전트가 컨텍스트·역할 한계에 부딪힌 뒤 |
| **어떻게** (How) | ① 과업을 입력 → 출력으로 정의하고 성공 기준을 적음 → ② 단일 프롬프트로 시도, 실패 유형 기록 → ③ 실패가 "단계 분리로 해결"되면 체이닝, "입력 유형별 처리 차이"면 라우팅, "독립 부분 과업"이면 병렬화, "동적 분해"면 오케스트레이터-워커, "품질 반복 개선"이면 평가자-최적화 → ④ 어느 패턴으로도 경로를 열거할 수 없을 때만 에이전트 루프, 상한·종료 조건·관측 함께 설계 → ⑤ 각 단계에서 비용·지연·성공률 `[실측]` |
| **왜** (Why) | 워크플로우로 충분한 것을 에이전트로 만들면 ① 요청당 LLM 호출 수가 비결정적이라 비용·지연 예측이 불가능하고 ② 같은 입력에 다른 경로가 선택되어 디버깅·회귀 테스트가 안 되며 ③ 실패가 어느 판단에서 났는지 재구성할 수 없다. 반대로 열린 과업을 워크플로우로 고정하면 열거하지 못한 경로에서 깨진다 |

## 문제와 맥락

"에이전트"라는 단어가 LLM에 툴을 붙인 모든 것을 가리키면서, 결정론적으로 처리할 수 있는 과업까지 자율 루프로 만드는 경향이 생겼다. 그 결과 흔히 보이는 증상은 다음과 같다.

- 같은 질문에 어제는 3회, 오늘은 11회 LLM을 호출. 비용 예측 불가
- 실패 재현 불가. 로그를 봐도 "모델이 그때는 다른 툴을 골랐다"
- 테스트 불가. 입력-출력 쌍으로 회귀 테스트를 짜도 중간 경로가 매번 다름
- 무한 루프 또는 조기 종료. 모델이 "충분하다"고 판단하는 기준이 불안정
- 단순 FAQ에 복잡 과업과 같은 비용·지연

반대 방향의 증상도 있다. 사용자 요청이 설계자가 열거한 경로 밖이면 "처리할 수 없습니다"로 끝나고, 새 경로를 추가할 때마다 코드 변경이 필요하다. 두 증상 사이의 균형점이 이 페이지의 결정이다.

## 핵심 개념

### 결정론 ↔ 자율성 스펙트럼

```
결정론 ◀──────────────────────────────────────────────────────────▶ 자율성

단일 프롬프트 → 프롬프트 체이닝 → 라우팅 → 병렬화 → 오케스트레이터-워커 → 평가자-최적화 → 자율 에이전트
                                                                              (루프 + 툴 + 종료 판단)
[코드가 흐름 결정, LLM은 노드]                     [LLM이 분해·반복 결정]         [LLM이 흐름 전체 결정]
비용·지연 예측 가능                                 상한 내 가변                   상한으로만 통제
디버깅: 노드 단위                                   디버깅: 분해 결과 단위          디버깅: 트레이스 전체
```

### 기본 워크플로우 패턴 5종

| 패턴 | 구조 | 해결하는 실패 | 비용(LLM 호출) | 적합 |
|---|---|---|---|---|
| **프롬프트 체이닝** | 단계 1 출력 → (코드 게이트) → 단계 2 입력. 직렬 | 한 프롬프트에 너무 많은 지시, 중간 검증 필요 | 단계 수만큼 고정 | 번역 후 검수, 초안 후 서식화, 추출 후 정규화 |
| **라우팅** | 분류 → 유형별 전용 프롬프트·모델·경로 | 입력 유형이 이질적이라 하나의 프롬프트가 모두 못 다룸 | 1(분류) + 1(처리). 분류는 결정 모델·분류기로 | FAQ/복잡 문의, 소형/대형 모델 분기 — [02](02-query-understanding.md) |
| **병렬화** | 독립 부분 과업 동시 실행 후 집계(sectioning) 또는 같은 과업 N회 후 투표(voting) | 지연, 단일 호출의 신뢰도 부족 | N + 1(집계) | 다관점 검토, 가드레일 병렬 검사, 섹션별 생성 |
| **오케스트레이터-워커** | 오케스트레이터 LLM이 과업을 **동적으로** 분해 → 워커들이 처리 → 종합 | 부분 과업을 미리 열거할 수 없음 | 1 + 워커 수(가변) + 1 | 다중 파일 코드 수정, 다중 소스 조사 — [06](06-agent-design-patterns.md) |
| **평가자-최적화** | 생성 → 평가자가 기준으로 채점·피드백 → 재생성, 합격 또는 상한까지 반복 | 명확한 평가 기준이 있고 반복으로 개선됨 | 2 × 반복 수(상한) | 번역 품질, 검색 충분성, 코드 테스트 통과 — [04](04-generation-grounding.md) 재생성 루프 |

이 다섯 패턴은 모두 **코드가 흐름을 정한다**. 오케스트레이터-워커와 평가자-최적화는 LLM이 분해·반복 여부를 결정하지만 그 결정이 작동하는 틀(워커 종류, 평가 기준, 반복 상한)은 코드다.

### 자율 에이전트

LLM이 루프 안에서 ① 현재 상태를 보고 ② 다음 행동(툴 호출·검색·질문·종료)을 고르고 ③ 결과를 관찰해 ①로 돌아간다. 설계자는 툴 집합·시스템 프롬프트·상한·종료 조건만 정하고 경로는 열거하지 않는다. 루프 패턴의 상세는 [06](06-agent-design-patterns.md). 에이전트가 적합한 과업의 조건은 다음 세 가지가 **모두** 충족될 때다.

1. 경로를 미리 열거할 수 없다 (열거할 수 있으면 라우팅·체이닝)
2. 각 행동의 결과를 관찰해 다음 행동을 바꿔야 한다 (아니면 병렬화·체이닝)
3. 실패 비용이 상한·검증·HITL로 통제 가능하다 (아니면 사람이 해야 한다)

### 뉴로심볼릭 관점: Symbolic[Neural]

[Part 1/04](../01-foundations/04-neuro-symbolic-ai.md)의 Kautz 분류에서 워크플로우는 **Symbolic[Neural]** — 기호 체계(워크플로우 엔진·상태 머신·규칙)가 신경망(LLM)을 서브루틴으로 호출하는 구조다. 반대로 자율 에이전트는 **Neural[Symbolic]** — 신경망이 기호 도구(툴·검색·검증기)를 호출한다. 이 구분이 실무적으로 뜻하는 것: 워크플로우에서는 제어 흐름이 결정론적이므로 **검증·감사·회귀 테스트가 기호 체계 수준에서 가능**하고, 에이전트에서는 제어 흐름 자체가 확률적이므로 검증은 트레이스 사후 분석과 상한·게이트에 의존한다. "어디까지 워크플로우로 고정할 것인가"는 "어디까지 기호 체계가 제어권을 가질 것인가"와 같은 질문이다.

### 결정 모델이 바꾸는 것

워크플로우 패턴의 분기 노드(라우팅의 분류, 평가자-최적화의 합격 판정, 오케스트레이터의 "분해 필요?" 판정)는 선택지가 닫힌 **판정**이다. 이 자리를 프롬프트 LLM 대신 결정 모델(Jev / Decisions API)·분류기·규칙이 맡으면 분기가 빠르고 싸고 보정 확률을 가진다 — [Part 1/02](../01-foundations/02-system1-vs-system2.md). 자율 에이전트의 "다음 행동 선택"에 결정 모델을 쓰는 변형은 [06](06-agent-design-patterns.md), 배치 설계는 [11](11-decision-layer.md).

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 단일 프롬프트 | 입출력이 단순, 한 번의 생성으로 충분 | 중간 검증 필요, 입력 유형 이질 | 하 — 호출 1회 | 표준 | — |
| 프롬프트 체이닝 | 단계가 명확히 분리되고 순서 고정, 중간 게이트 필요 | 단계 수가 많아 지연 누적, 단계 간 의존이 동적 | 하~중 — 고정 호출 수 | 표준 | `[2차]` |
| 라우팅 | 입력 유형별 최적 처리가 다름, 비용 차등(소형/대형 모델) | 유형 경계가 불명확, 라벨 데이터 없음 | 하~중 — 분류기·결정 모델 + 경로 | 표준 | `[2차]` |
| 병렬화 (sectioning / voting) | 독립 부분 과업, 지연 민감, 단일 판정 신뢰도 부족 | 부분 과업 간 의존, 비용 민감(N배) | 중 — N배 호출, 집계 로직 | 안정 | `[2차]` |
| 오케스트레이터-워커 | 부분 과업을 미리 열거 불가, 다중 소스·파일 | 과업 구조가 고정(체이닝으로 충분), 비용 상한 어려움 | 중~상 — 가변 호출, 종합 품질 | 안정 | `[2차]` |
| 평가자-최적화 | 명확한 평가 기준, 반복으로 측정 가능하게 개선 | 기준이 주관적, 반복해도 개선 없음 | 중 — 2 × 반복 | 안정 | `[2차]` |
| 자율 에이전트 (단일) | 경로 열거 불가, 관찰 의존, 실패 비용 통제 가능 | 지연 SLA 엄격, 비용 예측 필수, 감사·재현 요구, 실패 비용 높고 HITL 불가 | 상 — 비결정적 호출, 관측·상한·게이트 필수 | 신생~안정 | `[2차]` |
| 멀티 에이전트 | 단일 에이전트의 컨텍스트·역할 한계 확인됨 | 단일로 충분, 디버깅 역량 부족 | 상 | 신생 | `[2차]` — [07](07-multi-agent-orchestration.md) |

### 선택 가이드

- **과업의 경로를 종이에 그릴 수 있다면** → 워크플로우(체이닝·라우팅·병렬화 조합). 이유: 그릴 수 있는 것은 코드로 고정하는 편이 싸고 빠르고 테스트 가능하다
- **입력 유형에 따라 처리가 달라진다면** → 라우팅, 분류는 결정 모델·분류기·규칙으로. 이유: 분류는 판정이지 생성이 아니다
- **결과를 보고 다음 행동을 바꿔야 하고 경로를 열거할 수 없다면** → 자율 에이전트, 단 상한·종료 조건·게이트·트레이스를 함께. 이유: 이 조건이 아니면 에이전트의 비결정성은 비용만 된다
- **실패 비용이 높고(금전·법적·비가역) HITL이 어렵다면** → 워크플로우로 고정하거나 사람이 한다. 이유: 자율성은 실패 비용이 통제될 때만 정당화된다
- **지연 SLA가 수 초 이내라면** → 워크플로우. 이유: 에이전트 루프의 호출 수는 상한으로만 통제된다
- **판단이 어려우면** → 단일 프롬프트 → 체이닝 → 라우팅 순으로 올라가고, 측정된 실패가 다음 단계를 정당화할 때만 진행. 이유: 가장 단순한 형태에서 시작하는 것이 이 Part의 첫 원칙이다

## 설계 시 고려사항 (체크리스트)

- [ ] 과업의 입력·출력·성공 기준을 적었고 단일 프롬프트로 먼저 시도했는가
- [ ] 실행 그래프에서 코드가 정하는 간선과 모델이 정하는 간선을 색으로 구분했는가
- [ ] 모든 분기 노드의 판정 수단(규칙 / 결정 모델 / 분류기 / LLM)을 배정했는가 ([Part 1/02](../01-foundations/02-system1-vs-system2.md))
- [ ] 에이전트 구간에 최대 반복·비용·시간 상한과 상한 도달 시 폴백이 있는가
- [ ] 종료 조건이 명시적인가 ("충분하다"를 모델 판단에만 맡기지 않았는가)
- [ ] 행동(툴 실행·외부 전송) 직전에 규칙 게이트가 있는가 ([12](12-guardrails-hitl.md))
- [ ] 각 LLM 노드의 입출력이 스키마로 정의되어 노드 단위 테스트가 가능한가
- [ ] 트레이스가 노드·판정·확신도·호출 수를 기록하는가 ([Part 5/03](../05-cross-cutting/03-observability-tracing.md))
- [ ] 요청당 비용·지연의 분포(평균이 아닌 p95)를 측정하는가
- [ ] 자율성을 올릴 때 그 근거가 된 측정 결과를 기록했는가

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 에이전트의 비결정적 비용·지연 | 예산 초과, SLA 위반 | 상한, 결정 모델로 분기 비용 절감, 단순 경로는 워크플로우로 분리 |
| 재현 불가 | 실패 디버깅·회귀 테스트 불가 | 트레이스 전수 기록, 트래젝토리 평가([13](13-evaluation-rag-agents.md)), 온도 0 + 시드 |
| 무한 루프·조기 종료 | 비용 폭증 또는 미완 결과 | 종료 판정을 결정 모델·규칙으로, 상한, 진행 없음 감지 |
| 워크플로우의 경직성 | 열거 밖 입력에서 실패, 경로 추가마다 코드 변경 | 라우터에 "기타" 경로 + 에이전트 폴백, 경로를 설정으로 외부화 |
| 패턴 과잉 조합 | 체이닝 + 라우팅 + 병렬화 + 평가자가 얽혀 워크플로우 자체가 디버깅 불가 | 패턴 수 제한, 실행 그래프 문서화, 노드 단위 테스트 |
| 오케스트레이터의 분해 품질 | 잘못된 분해는 워커가 아무리 잘해도 실패 | 분해 결과를 스키마로 검증, 분해 예시 제공, 분해 단계만 별도 평가 |
| 평가자의 기준 드리프트 | 평가자 LLM이 일관되지 않아 반복이 수렴하지 않음 | 평가 기준을 규칙·결정 모델로 고정, 반복 상한 |
| "에이전트" 용어 혼란 | 팀 내 설계 논의가 어긋남 | 실행 그래프로 소통, "모델이 결정하는 간선"으로 정의 통일 |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 이 페이지의 결정(어디까지 워크플로우, 어디부터 에이전트)은 그 자체가 **운영 가능성의 결정**이다. 워크플로우 구간은 호출 수가 고정이라 확장성·안정성이 예측 가능하고, 에이전트 구간은 상한으로만 통제된다. 아래는 두 구간을 구분해 적는다. 레이어 간 종합은 [Part 5/06](../05-cross-cutting/06-operational-design-matrix.md).

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| **요청 수** (중심 축) | 워크플로우: 노드 수 × 요청 수의 고정 호출이라 레이트 리밋 도달 시점이 예측됨. 에이전트: 호출 수가 가변이라 **p95 꼬리**에서 레이트 리밋이 먼저 터짐 | 요청 경로 무상태 + 실행 상태(체크포인트)는 외부 저장소([08](08-state-memory-context.md)). 에이전트 구간은 큐 + 비동기 응답, 동시 활성 루프 수 상한(세마포어). 분기 노드를 결정 모델·규칙으로 바꿔 LLM 호출 수 자체를 축소. 프롬프트 캐시(노드별 고정 접두사) | 워크플로우: 요청 수 × 노드 수. 에이전트: 요청 수 × 스텝 수(p95) |
| **동시 세션** (장기 실행) | 체크포인트 저장소 쓰기량, 세션 상태 메모리 | 체크포인트 외부화 + TTL, 상태 요약 | 동시 세션 수 × 체크포인트 크기 |
| **패턴 조합 깊이** | 오케스트레이터-워커 안에 평가자-최적화가 중첩되면 호출 수가 곱 | 조합 깊이 ≤ 2, 워커 수·반복 수 상한 | 조합 깊이 × 워커 수 × 반복 수 |
| **경로 수** (라우팅 패턴) | 경로마다 전용 프롬프트·골든셋·모델 배정 → 운영 비용 | 경로를 설정으로 외부화([02](02-query-understanding.md) 라우팅 표), 경로별 소유자 | 경로 수(운영 비용) |

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 모델 API 다운·지연(노드) | 워크플로우: 해당 노드 실패 → 전체 실패 또는 부분 결과 | 노드별 오류율·p95, 서킷 브레이커 열림 | 노드 단위 폴백 모델(호환 매트릭스 내), 필수 아닌 노드(검수·서식화) 생략 저하, 체크포인트에서 재개 | 폴백률 10분간 50%(예시) |
| **에이전트 무한 루프·스텝 상한 도달** | 응답 없음, 비용 급등 | 스텝·토큰·시간 상한 도달률, 진행 없음 감지(동일 상태 해시 N회) | 상한에서 강제 종료 → 부분 결과 + "미완" 표시, 또는 **워크플로우 폴백**(같은 요청을 기본 경로로 재실행) | 상한 도달률 5%(예시) → 종료 조건 점검 |
| 평가자-최적화 비수렴 | 반복 상한까지 불합격 | 반복 수 분포, 비수렴률 | 상한에서 최고 점수 결과 반환 + 플래그 | 비수렴률 10%(예시) → 평가 기준·모델 점검 |
| 오케스트레이터 분해 실패(스키마 불합격·워커 0) | 빈 결과 | 분해 스키마 실패율 | 재분해 1회 → 실패 시 단일 프롬프트 폴백 | 실패율 5%(예시) |
| 라우팅 오분류 | 품질 저하, 경로-비용 불일치 | 경로별 품질·비용 이상 | 확신 < θ → 보수적 기본 경로 — [02](02-query-understanding.md) | 경로 비율 급변 |
| 체크포인트 저장소 다운 | 장기 과업 재개 불가 | 저장소 오류율 | 단기 과업은 메모리 내 진행 + "재개 불가" 표시, 장기 과업은 접수 거부(백프레셔) | 즉시 |
| 병렬화 부분 실패 | 일부 섹션 누락 | 섹션별 성공률 | 성공 섹션으로 집계 + 누락 표시. 투표(voting)는 과반 미달 시 abstain | 특정 섹션 실패 지속 |

SLI 후보: 요청당 LLM 호출 수 분포(p50/p95), 스텝 상한 도달률, E2E p95 지연(구간별), 과업 성공률(골든셋), 비수렴률, 폴백·저하율. SLO 초안(예시): 워크플로우 경로 p95 ≤ 5초, 에이전트 구간 상한 도달률 < 2%, 호출 수 p95 ≤ 12. 서킷 브레이커 위치: 모델 API(노드별·벤더별), 툴([09](09-tools-and-mcp.md)), 체크포인트 저장소. 쓰기 행동: 에이전트 구간의 쓰기 툴은 멱등 키·타임아웃·재시도 상한([09]), 체크포인트에서 재개할 때 "실행 완료" 기록으로 중복 실행 방지.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| **실행 그래프 정의**(노드·간선·분기 조건) — 선언적 설정 권장 | 전체 흐름 | E2E 골든셋 + 노드 단위 테스트 | 노드 입출력 스키마 버전 |
| 노드 프롬프트 | 해당 노드 출력 | 노드 골든셋 | 노드 모델 버전(프롬프트-모델 호환 매트릭스) |
| 분기 판정 수단·질문 정의·θ | 경로 분포 | 분기 평가셋·보정 | [02](02-query-understanding.md)·[11](11-decision-layer.md) |
| **패턴 설정**: 상한(스텝·비용·시간·반복·조합 깊이), 종료 조건, 재계획 트리거 — 설정 | 비용·완결성 | 상한 도달률·성공률 | — |
| 노드별 모델 버전 | 노드 출력 → E2E | 노드 골든셋 → E2E | 프롬프트 버전 |
| 체크포인트 스키마 | 진행 중 과업의 재개 가능성 | 구버전 체크포인트 재개 테스트 | 마이그레이션 스크립트([08](08-state-memory-context.md)) |

기술 부채로 기록할 것: "분기 노드를 프롬프트 LLM으로 시작, 결정 모델 전환 예정", "실행 그래프가 코드에 하드코딩", "요청당 비용 p95 미측정(평균만)".

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **규칙·정책** ★ 가장 빈번 | 상한·종료 조건·행동 게이트 규칙·승인 기준 | 게이트 위치(행동 직전), 상한 평가 인터페이스 | 상한 값·규칙 세트 | 설정 버전 + 시행일. 배포 없음 | 해당 구간만 |
| **도메인 모델** | 경로 추가, 새 과업 유형, 워커 종류 추가 | 노드 입출력 스키마, 실행 그래프 선언 형식 | 노드 구현, 경로 핸들러 | 라우팅 표(설정) + 새 노드 등록 + 간선 추가(선언적이면 설정). 그래프 엔진 코드 불변 | 라우터 평가셋, 신규 경로 골든셋 |
| **모델** | 노드 LLM 교체, 분기 판정 수단 교체(LLM → 결정 모델) | `generate()` / `decide()` 포트, 호환 매트릭스 | 어댑터 | 노드 단위 어댑터 교체 + 노드 골든셋 + 카나리. 판정 수단 교체는 **섀도**(예시 2주, 기록만) → 보정 확인 → 전환 | **워크플로우: 해당 노드만**(핵심 이점). 에이전트 구간: 트래젝토리 전체 재평가 |
| **지식** | 검색·툴 결과의 내용 변화 | 노드 입출력 스키마 | — | [03](03-retrieval-reranking.md)·[09](09-tools-and-mcp.md)에서 흡수 | 노드 영향 없음 |
| **사용자 환경** | 채널·언어, 조직 역할 변경 → 승인 경로 | 이벤트 스키마(계약 ③), 노드 스키마 | 프롬프트 변형, 승인 매트릭스([12](12-guardrails-hitl.md)) | 설정 | 승인 매트릭스, 골든셋 |
| **프로토콜·SDK** | 오케스트레이션 프레임워크 교체·메이저 업, MCP 개정 | **프레임워크 중립 실행 그래프 정의**(노드·간선·상태 스키마), 포트 | 프레임워크 런타임 어댑터 | 버전 고정 + 업그레이드 창. 그래프 정의는 런타임 밖에 둔다 | 런타임 어댑터 + 체크포인트 마이그레이션 |
| **자율성 수준 자체** | 워크플로우 → 에이전트 승격(또는 반대) | 구간의 입출력 계약 | 구간 구현 | 피처 플래그로 두 구현 병행 → 카나리 비교 → 전환. 플래그는 **킬 스위치**(에이전트 구간 off = 워크플로우 폴백) 겸용 | 해당 구간 전체 |

가장 자주 바뀌는 것: 상한·임계값·노드 프롬프트(주 단위) > 경로 추가(월) > 노드 모델(분기) > 자율성 수준 승격 > 프레임워크. 코드 밖 설정으로 둘 것: 라우팅 표·θ, 상한 5종, 종료 조건, 노드 프롬프트, 노드별 모델 배정, 자율성 피처 플래그. 포트·어댑터 뒤에 둘 외부 의존: 모델 API, 결정 모델, 툴/MCP, 체크포인트 저장소, 프레임워크 런타임.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | 워크플로우(읽기·생성만) **1~2**. 에이전트 구간이 행동(툴 쓰기·외부 전송)을 포함하면 행동별로 **3~4**. 등급 5(결제·송금·영구 삭제)는 에이전트 자동 실행 금지 — 제안만. **자율성 수준 결정 = 위험 등급 배정**이다 |
| 가드레일 위치 | 입력([02](02-query-understanding.md))·출력([04](04-generation-grounding.md))은 구간 밖. **행동**: 에이전트 구간의 툴 실행 직전 규칙 게이트([12](12-guardrails-hitl.md)). 워크플로우에서는 노드 사이의 코드 게이트가 같은 역할 |
| 게이트 출력과 판정 수단 | 통과 / 차단(권한·한도) / 승인 요청(등급 3 이상 행동 — 동기 카드 또는 비동기 큐, 만료 = 거부) / 저하(상한 도달 → 워크플로우 폴백·읽기 전용). 보안·권한·한도는 규칙만, 분기는 결정 모델·분류기, 생성은 LLM |
| 소유자 (A) | 실행 그래프·자율성 수준: 아키텍트(A), AI 엔지니어(R). 상한·종료 조건: 제품 책임자(A). 행동 게이트 규칙: 보안 책임자(A). 승인 정책: 사업 책임자(A), 운영 책임자(R) |
| 감사 추적에 남길 필드 | 실행 그래프 버전, 노드별 프롬프트·모델 버전, 분기 판정·확신도·수단, 스텝·호출 수·토큰, 상한 도달·폴백 여부, 행동 게이트 판정과 규칙 버전, 승인자·승인 시각·승인 카드에 보여준 내용, 체크포인트 ID, 근거 ID |

### 운영 준비도 체크
- [ ] 실행 그래프에서 에이전트 구간을 끄고 워크플로우로 폴백하는 킬 스위치(피처 플래그)가 배포 없이 동작하는가
- [ ] 모든 가변 루프에 상한 5종(스텝·비용·시간·반복·조합 깊이)이 설정으로 있고, 상한 도달 시 저하 경로를 실행해 봤는가
- [ ] 요청당 호출 수·지연의 p95(평균 아님)를 구간별로 측정하고 SLO 초안이 있는가
- [ ] 노드 단위 폴백 모델이 호환 매트릭스에 있고, 노드 교체가 다른 노드의 재테스트 없이 가능한가
- [ ] 실행 그래프 정의가 프레임워크 중립 형식으로 런타임 밖에 있는가
- [ ] 등급 3 이상 행동 노드에 규칙 게이트 + 승인 경로(만료 = 거부)가 있는가
- [ ] 트레이스에 분기 판정·버전 키·체크포인트 ID가 있어 실패 경로를 재구성할 수 있는가
