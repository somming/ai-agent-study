# 에이전트 설계 패턴

> **범위**: ReAct, Plan-and-Execute, Reflection, Router, Orchestrator-Worker 비교
> **시각화**: [`assets/html/agent-design-patterns.html`](../assets/html/agent-design-patterns.html)

## 요약 (3줄)

1. 에이전트 패턴은 **루프의 모양**으로 구분된다. ReAct는 "생각-행동-관찰"을 매 스텝 반복, Plan-and-Execute는 계획을 먼저 세우고 실행, Reflection은 출력을 스스로 비판해 재생성, Tool-use는 모델이 함수를 고르는 기본 단위, Router는 분기, Orchestrator-Worker는 동적 분해·위임이다.
2. 패턴의 비용은 **LLM 호출 수**로 비교한다. ReAct는 스텝 수에 비례해 가변, Plan-and-Execute는 1(계획) + 단계 수 + 재계획, Reflection은 2 × 반복, Router는 1 + 1. 호출 수가 가변인 패턴은 반드시 상한을 갖는다.
3. 모든 패턴에서 "다음 행동 선택"·"충분한가"·"어느 워커에게"는 선택지가 닫힌 **판정**이다. 이 자리를 결정 모델(Jev / Decisions API)·분류기·규칙이 맡는 변형이 비용과 비결정성을 줄이는 최근 1년의 방향이다 — 다만 사례는 아직 `[2차]` 수준이다.

| 질문 | 답 |

| **언제** (When) | [05](05-workflow-vs-agent.md)의 세 조건(경로 열거 불가, 관찰 의존, 실패 비용 통제 가능)이 충족된 뒤. 툴이 하나이고 호출이 한 번이면 Tool-use만으로 충분하고 루프가 필요 없다. 멀티 에이전트([07](07-multi-agent-orchestration.md))는 단일 루프의 컨텍스트·역할 한계가 확인된 뒤 |
| **어떻게** (How) | ① 과업의 관찰-행동 의존 구조를 그림(계획 가능한가, 중간 결과가 다음을 바꾸는가) → ② 계획 가능하면 Plan-and-Execute, 매 스텝 의존이면 ReAct, 품질 반복이면 Reflection, 분해·위임이면 Orchestrator-Worker → ③ 판정 지점(다음 행동, 종료, 워커 선택)의 수단 배정 → ④ 상한·종료·폴백·게이트 → ⑤ 트레이스로 스텝 수·비용·실패 모드 `[실측]` → ⑥ 실패 모드가 패턴 고유의 것이면 패턴 교체 또는 조합 |
| **왜** (Why) | 패턴을 고르지 않고 "LLM에 툴 주고 루프 돌리기"로 시작하면 ReAct의 가장 취약한 형태가 된다. 매 스텝 전체 히스토리를 다시 읽어 비용이 스텝 수의 제곱으로, 중간 관찰에 흔들려 목표를 잃고, 종료 판단이 불안정하다. 패턴은 이 실패 모드들에 대한 구조적 대응이다 |

## 문제와 맥락

단일 LLM 호출이 못 하는 것은 "결과를 보고 다시 하기"다. 에이전트 루프는 이것을 가능하게 하지만, 루프를 어떻게 구성하느냐에 따라 전혀 다른 비용·안정성 특성을 갖는다. 루프 설계가 없을 때의 증상은 다음과 같다.

- **목표 이탈**: 중간 관찰(검색 결과, 툴 오류)에 반응하다 원래 질문을 잊음
- **반복 행동**: 같은 툴을 같은 인자로 여러 번 호출. 관찰을 해석하지 못하거나 상태를 잃음
- **조기 종료 / 종료 불능**: "충분하다"는 판단이 불안정. 스텝 수 분포가 넓음
- **컨텍스트 폭증**: 매 스텝 전체 히스토리 + 툴 출력이 쌓여 뒤로 갈수록 품질 저하·비용 증가
- **계획 경직**: 처음 세운 계획이 틀렸는데 수정하지 못함(Plan-and-Execute의 고유 실패)
- **자기 비판의 무효**: 평가자와 생성자가 같은 모델이라 같은 오류를 못 봄(Reflection의 고유 실패)

각 패턴은 일부 증상을 줄이는 대신 다른 증상을 키운다. 그래서 "최선의 패턴"은 없고 과업의 의존 구조에 맞는 패턴이 있다.

## 핵심 개념

### 6개 패턴의 루프 구조

시각화: [`agent-design-patterns.html`](../assets/html/agent-design-patterns.html) — 6개 패턴의 루프를 나란히 비교.

| 패턴 | 루프 | 설계자가 정하는 것 | 모델이 정하는 것 | LLM 호출 수 |
|---|---|---|---|---|
| **Tool-use** | 질의 → 모델이 함수·인자 선택 → 실행 → 결과로 답변 | 툴 스키마, 실행 코드 | 어느 툴, 어떤 인자 | 1~2 (선택 + 답변) |
| **ReAct** | [생각 → 행동(툴) → 관찰] 반복 → 종료 판단 → 답변 | 툴 집합, 상한, 종료 조건 | 매 스텝의 행동과 종료 | 스텝 수에 비례(가변) |
| **Plan-and-Execute** | 계획 수립(단계 목록) → 단계별 실행 → (필요 시) 재계획 → 종합 | 계획 스키마, 재계획 트리거 | 계획 내용, 재계획 여부 | 1 + 단계 수 + 재계획 횟수 |
| **Reflection** | 생성 → 자기 비판(기준 대비) → 수정 → 합격 또는 상한 | 비판 기준, 상한 | 비판 내용, 수정 | 2 × 반복 수 |
| **Router** | 분류 → 전용 핸들러(프롬프트·에이전트·워크플로우) | 경로 집합, 핸들러 | 어느 경로 | 1 + 핸들러 비용 |
| **Orchestrator-Worker** | 오케스트레이터가 분해 → 워커 병렬·순차 실행 → 결과 종합 | 워커 종류·능력, 종합 방식 | 분해 내용, 워커 배정 | 1 + 워커 수 + 1 |

### 패턴별 적합·부적합과 실패 모드

| 패턴 | 적합 | 부적합 | 고유 실패 모드 | 완화 |
|---|---|---|---|---|
| **Tool-use** | 툴 1~N개 중 하나를 한 번 호출하면 끝 | 결과를 보고 다시 호출해야 함 | 잘못된 인자, 불필요한 호출 | 인자 스키마 검증, 호출 전 규칙 게이트 |
| **ReAct** | 탐색적 과업, 매 스텝 결과가 다음을 결정, 스텝 수 적음(≤10) | 긴 과업(컨텍스트 폭증), 지연 민감, 계획 가능한 과업 | 목표 이탈, 반복 행동, 종료 불안정 | 상한, 상태 요약, 종료 판정을 결정 모델·규칙으로 |
| **Plan-and-Execute** | 단계를 미리 그릴 수 있는 다단계 과업, 비용 예측 필요 | 중간 결과가 계획 전체를 바꾸는 과업 | 계획 경직, 틀린 계획 끝까지 실행 | 재계획 트리거(단계 실패·관찰 불일치), 계획을 스키마로 검증 |
| **Reflection** | 명확한 품질 기준, 반복으로 측정 가능하게 개선(코드 테스트, 형식 준수) | 기준 주관적, 생성자와 평가자가 같은 맹점 | 자기 비판 무효, 수렴 안 함 | 평가자를 다른 모델·규칙·결정 모델로, 상한 |
| **Router** | 입력 유형 이질, 유형별 전용 처리 | 유형 경계 불명확 | 오분류의 증폭(이후 전부 무효) | 확신도 임계값 + 폴백 경로, 분류는 결정 모델·분류기 |
| **Orchestrator-Worker** | 부분 과업 열거 불가, 다중 소스·파일·관점 | 과업 구조 고정(체이닝으로 충분) | 분해 오류, 워커 결과 충돌·중복, 종합 품질 | 분해 스키마 검증, 워커 출력 스키마, 종합 전 중복 제거 |

### 패턴은 조합된다

실무 에이전트는 한 패턴이 아니다. 흔한 조합은 ① Router → 경로별 Plan-and-Execute ② Plan-and-Execute의 각 단계가 ReAct ③ 어느 패턴이든 마지막에 Reflection ④ Orchestrator-Worker의 워커가 Tool-use 또는 ReAct. 조합할수록 호출 수가 곱해지므로 **조합의 깊이에 상한**을 둔다(보통 2단).

### 결정 모델이 "다음 행동 선택"을 맡는 변형

ReAct의 매 스텝 "다음 행동"은 툴 집합 + 종료라는 **닫힌 선택지**다. Plan-and-Execute의 "재계획 필요?", Reflection의 "합격?", Router의 "어느 경로?", Orchestrator의 "어느 워커?"도 마찬가지다. 이 판정을 생성 모델이 아니라 결정 모델(Jev / Decisions API)이 맡으면:

- 판정 1회가 생성 1회보다 싸고 빠르다(Jev 70~500ms E2E 주장 `[벤더]`, 독립 벤치마크 없음)
- 보정 확률이 나와 "확신 낮음 → 사람" 임계값을 둘 수 있다
- 판정 결과가 타입드라 트레이스·회귀 테스트가 쉽다

단, 툴 **인자** 생성은 여전히 생성 과업이라 LLM이 맡는다. 즉 "무엇을 할까"는 결정 모델, "어떻게 할까(인자·내용)"는 LLM으로 분리된다. 두 결정 모델은 내부가 다르고(Jev는 결정 전용 비자기회귀 모델, Decisions API는 gpt-6-luna 출력 제약) 한국어 평가셋 `[실측]`이 선행되어야 한다. 배치 설계는 [11](11-decision-layer.md), 원칙은 [Part 1/02](../01-foundations/02-system1-vs-system2.md).

### 선택 가이드

- **툴 한 번으로 끝난다면** → Tool-use. 루프를 만들지 않는다. 이유: 루프의 비결정성은 필요할 때만 치른다
- **단계를 미리 그릴 수 있다면** → Plan-and-Execute + 재계획 트리거. 이유: 비용 예측이 가능하고 계획 자체를 검증·수정할 수 있다
- **매 스텝 결과가 다음을 바꾸고 스텝이 10개 이내라면** → ReAct + 상한 + 상태 요약. 이유: 탐색적 과업에 가장 유연하다. 종료 판정은 결정 모델·규칙으로
- **출력 품질에 명확한 기준이 있다면** → 마지막에 Reflection, 평가자는 다른 모델·규칙·결정 모델로. 이유: 같은 모델의 자기 비판은 같은 맹점을 공유한다
- **부분 과업을 미리 열거할 수 없고 병렬화 여지가 있다면** → Orchestrator-Worker, 분해·워커 출력을 스키마로. 이유: 분해 품질이 전체를 좌우하므로 검증 가능하게
- **판단이 어려우면** → Router → Plan-and-Execute를 기본값으로, 각 단계는 Tool-use. 이유: 호출 수가 거의 고정이라 비용·디버깅이 통제되고, 필요한 단계만 ReAct로 바꿀 수 있다

## 설계 시 고려사항 (체크리스트)

- [ ] 과업의 관찰-행동 의존 구조를 그렸고 그에 맞는 패턴을 골랐는가 (기본값 ReAct가 아닌가)
- [ ] 모든 가변 루프에 최대 스텝·비용·시간 상한과 상한 도달 시 폴백이 있는가
- [ ] 종료 조건이 명시적이고 판정 수단(결정 모델 / 규칙 / LLM)이 배정되어 있는가
- [ ] 매 스텝 상태가 "목표 + 요약 히스토리 + 최근 관찰"로 압축되는가 (전체 히스토리 누적이 아닌가) — [08](08-state-memory-context.md)
- [ ] 반복 행동 감지(같은 툴·같은 인자 N회)가 있는가
- [ ] 툴 실행 직전 규칙 게이트가 있는가 ([12](12-guardrails-hitl.md)), 툴 인자는 스키마 검증되는가 ([09](09-tools-and-mcp.md))
- [ ] Reflection의 평가자가 생성자와 분리되어 있는가
- [ ] Plan-and-Execute의 재계획 트리거가 정의되어 있는가
- [ ] Orchestrator의 분해 결과와 워커 출력이 스키마로 검증되는가
- [ ] 트레이스가 스텝별 판정·확신도·툴 호출·토큰을 기록하는가 ([Part 5/03](../05-cross-cutting/03-observability-tracing.md))
- [ ] 스텝 수·비용의 분포(p95)와 실패 모드별 발생률을 측정하는가 ([13](13-evaluation-rag-agents.md))

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 컨텍스트 폭증 (ReAct) | 스텝이 늘수록 비용 증가·품질 저하 | 상태 요약·compaction, 툴 출력 절단, 스텝 상한 |
| 계획 경직 (Plan-and-Execute) | 틀린 계획을 끝까지 실행 | 단계 실패·관찰 불일치 시 재계획, 계획 검증 |
| 자기 비판 무효 (Reflection) | 반복해도 같은 오류 | 평가자 분리(다른 모델·규칙·결정 모델), 외부 신호(테스트 결과) |
| 분해 오류 (Orchestrator) | 워커가 잘해도 전체 실패 | 분해 스키마 검증, 분해 예시, 분해만 별도 평가 |
| 판정의 비결정성 | 같은 상태에 다른 행동 | 판정을 결정 모델·규칙으로, 온도 0, 트레이스 비교 |
| 결정 모델 사례 부족 | "다음 행동 선택" 변형의 실효가 미검증 | 소형 LLM 판정과 같은 평가셋으로 `[실측]` 후 채택 |
| 프레임워크 추상화 누수 | 기본 루프의 종료·재시도 동작을 모르고 사용 | 프레임워크의 루프 코드 읽기, hooks로 관측 |
| 벤치마크와 실무의 괴리 | 원 논문 성과가 자체 툴·도메인에서 재현 안 됨 | 자체 과업 평가셋, 트래젝토리 평가 |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 에이전트 루프는 **행동 가드레일이 매 스텝 실행되는 자리**이고, 비용이 요청 수가 아니라 스텝 수에 비례하는 유일한 구간이다. 루프 안의 툴 집합이 곧 위험 등급의 상한이다. 레이어 간 종합은 [Part 5/06](../05-cross-cutting/06-operational-design-matrix.md).

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| **요청 수 × 스텝 수** (중심 축) | 모델 API 토큰 한도(TPM). ReAct는 스텝 n의 입력이 히스토리 누적으로 커져 요청 수보다 훨씬 빨리 소진 | 상태 요약·compaction([08](08-state-memory-context.md)), 프롬프트 캐시(시스템 프롬프트 + 툴 정의 고정 접두사), 동시 활성 루프 세마포어, 요청 큐, 스텝 실행은 무상태로 두고 루프 상태는 외부 저장소에 | 요청 수 × Σ(스텝별 컨텍스트 토큰) — 요약 없으면 스텝 수의 제곱에 가까움 |
| **툴 수** | 툴 정의가 매 스텝 컨텍스트에 실림. 툴 50개면 정의만 수천 토큰, 툴 선택 정확도 하락 | 툴 라우팅·그룹화(과업·역할별 서브셋), 지연 로딩, 툴 정의 캐시([09](09-tools-and-mcp.md)) | 툴 수 × 스텝 수 |
| **워커 수** (Orchestrator-Worker) | 병렬 워커가 레이트 리밋을 순간 소진 | 워커 동시성 상한, 워커 큐 | 워커 수 |
| **반복 수** (Reflection) | 2 × 반복 | 반복 상한, 평가자를 규칙·결정 모델로(생성 호출 1 → 0) | 반복 수 |
| **동시 세션** | 루프 상태 메모리, 체크포인트 쓰기 | 상태 외부화, TTL | 세션 수 × 상태 크기 |

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 모델 API 다운·지연(스텝 중) | 루프 중단 | 스텝 오류율·p95, 서킷 브레이커 열림 | 스텝 재시도(예시 2회, 지수 백오프) → 폴백 모델(호환 매트릭스 내, 툴 호출 형식 호환 확인된 것만) → 체크포인트에서 재개 또는 부분 결과 | 폴백률 10분간 50%(예시) |
| **무한 루프·스텝 상한 도달** | 응답 없음, 비용 급등 | 상한 도달률, 진행 없음 감지(상태 해시 반복) | 상한(예시 ReAct 10스텝·토큰·시간)에서 강제 종료 → 수집된 관찰로 종합 답변 + "미완" 플래그, 또는 Plan-and-Execute·워크플로우 폴백 | 상한 도달률 5%(예시) |
| 반복 행동(같은 툴·같은 인자) | 비용 낭비, 진행 없음 | 반복 카운터 | 예시 3회째에 캐시된 결과 반환 + "이미 시도함"을 관찰로 주입, 지속 시 종료 | 반복률 급증 |
| 툴 타임아웃·오류 | 관찰 없음 → 모델이 결과를 지어낼 위험 | 툴별 오류율·p95([09](09-tools-and-mcp.md)) | **구조화 오류를 관찰로 주입**(빈 결과 아님). 툴 서킷이 열리면 그 툴을 툴 목록에서 제거(모델이 다른 경로를 찾게) | 툴별 오류율 10%(예시) |
| 계획 경직(Plan-and-Execute) | 틀린 계획을 끝까지 | 단계 연속 실패 수 | 재계획 트리거(예시 연속 2회 실패) → 재계획 상한(예시 2회) → 종료 | 재계획 상한 도달 반복 |
| Reflection 비수렴 | 반복 상한까지 불합격 | 반복 수 분포 | 최고 점수 출력 + 플래그 | 비수렴률 10%(예시) |
| 판정 수단(결정 모델 API) 다운 | 다음 행동을 못 고름 | 판정 API 오류 | 섀도 기간에 비교한 소형 LLM 판정으로 폴백, 그것도 실패하면 규칙 기본 행동(안전 종료) | 즉시 |
| 컨텍스트 폭증(요약 실패) | 후반 스텝 품질 저하, 컨텍스트 초과 오류 | 스텝별 토큰 추이, 초과 오류 | 강제 compaction, 툴 출력 절단 | 초과 오류 발생 시 |

SLI 후보: 과업 성공률(골든셋), 스텝 수 분포(p50/p95), 상한 도달률, 요청당 토큰·비용 p95, 반복 행동 발생률, 툴 오류율, E2E p95. SLO 초안(예시): 상한 도달률 < 2%, 스텝 p95 ≤ 8, 성공률 ≥ 85%. 서킷 브레이커 위치: 모델 API, **툴/MCP 서버마다 독립**, 결정 모델 API. 쓰기 행동: 쓰기 툴은 멱등 키(요청 ID + 스텝 번호), 타임아웃, 재시도 상한, 재개 시 체크포인트의 "실행 완료" 기록으로 중복 실행 방지 — 상세 [09](09-tools-and-mcp.md).

| 상태 스키마(요약 형식·관찰 구조) | 재개·요약 품질 | 구버전 체크포인트 재개 테스트 | [08](08-state-memory-context.md) |

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **도메인 모델** ★ 가장 빈번 | 툴 추가·제거·스키마 변경, 워커 종류 추가, 과업 유형 추가 | 툴 정의 스키마([09](09-tools-and-mcp.md)·MCP), 워커 입출력 스키마, 판정 선택지 enum | 툴 구현, 워커 구현 | 툴 레지스트리(설정·MCP 서버 목록)에 등록 + 판정 질문 정의 버전 상승(선택지 추가) + 툴 선택 평가셋 추가. **루프 코드 불변** | 판정 평가셋, 시스템 프롬프트 툴 설명 |
| **모델** | LLM 교체; 판정 수단 교체(LLM → 결정 모델) | `generate()`·`decide(state, question)` 포트, 호환 매트릭스 | 어댑터 | 어댑터 교체 + 트래젝토리 골든셋 + 카나리(예시 5%). 판정 수단은 섀도(기록만) → 보정 확인 → 전환 | 루프 전체 — 툴 호출 형식 차이에 특히 주의 |
| **규칙·정책** | 행동 게이트 규칙, 툴 권한, 상한 | 게이트 인터페이스(행동 직전), 상한 평가 인터페이스 | 규칙 세트 | 규칙 버전 + 시행일 | 게이트·상한만 |
| **지식** | 툴이 반환하는 데이터 구조·검색 결과 | 관찰 스키마(툴 출력 정규화 계약) | 툴 어댑터 | 어댑터에서 정규화, 관찰 스키마는 tolerant reader | 해당 툴 어댑터만 |
| **사용자 환경** | 사용자 역할 → 툴 권한 서브셋, 언어 | 툴 정의 스키마 | 역할별 툴 서브셋(설정) | 설정 | 툴 선택 평가셋 |
| **프로토콜·SDK** | MCP 스펙 개정, Agent SDK 메이저 업, 함수 호출 API 변경 | 내부 툴 포트, 루프 상태 스키마 | MCP 클라이언트 어댑터, SDK 런타임 어댑터 | 버전 고정 + 업그레이드 창 | 어댑터만 |
| **패턴 자체** | ReAct → Plan-and-Execute 등 | 에이전트 구간의 입출력 계약([05](05-workflow-vs-agent.md)), 상태 스키마 | 루프 구현 | 패턴을 피처 플래그로 선택 → 카나리 비교 | 에이전트 구간 전체 |

가장 자주 바뀌는 것: 툴 집합(툴 추가·스키마 변경) ≈ 시스템 프롬프트(주 단위) > 상한·θ > 모델(분기) > 패턴 교체 > 프레임워크·프로토콜. 코드 밖 설정으로 둘 것: 시스템 프롬프트, 툴 레지스트리·역할별 서브셋, 상한 6종, 종료 조건, 재계획 트리거, 판정 θ, 패턴 선택 플래그. 포트·어댑터 뒤에 둘 외부 의존: 모델 API, 결정 모델 API, 툴/MCP 서버, 체크포인트 저장소, SDK 런타임.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | 읽기 툴만이면 **1~2**. 쓰기·외부 전송 툴이 있으면 툴별로 **3~4**(예: 환불 접수 3, 운영 서버 설정 변경 4). 등급 5 툴은 에이전트에 노출하지 않는다(제안만). **루프의 툴 집합 = 위험 등급의 상한** |
| 가드레일 위치 | **행동 가드레일의 핵심 자리** — 매 스텝 툴 실행 직전 규칙 게이트(권한·한도·인자 스키마·금지 조합). 입력([02](02-query-understanding.md))·출력([04](04-generation-grounding.md))은 루프 밖. 상세 [12](12-guardrails-hitl.md) |
| 게이트 출력과 판정 수단 | 통과 / 차단(권한 없음·한도 초과 → 구조화 오류를 관찰로 주입) / 승인 요청(등급 3 이상 → 루프 일시 중단 → 체크포인트 → 승인 후 재개, 만료 = 거부) / 저하(상한 도달 → 읽기 전용으로 종료). 규칙이 최종 결정권, 결정 모델 확신도는 "승인 필요 여부" 보조 |
| 소유자 (A) | 시스템 프롬프트·패턴 설정: 제품 책임자(A), AI 엔지니어(R). 툴 권한: 서비스 소유자(A), 플랫폼 엔지니어(R). 행동 게이트 규칙: 보안 책임자(A) |
| 감사 추적에 남길 필드 | 세션·요청 ID, 스텝 번호, 스텝별 판정(다음 행동)·수단·확신도, 툴 호출(이름·인자 해시·멱등 키·결과 요약), 게이트 판정·규칙 버전, 승인자·시각, 프롬프트 버전, 모델 버전(폴백 여부), 상한 도달·폴백 여부, 체크포인트 ID, 최종 답변 근거 ID |

### 운영 준비도 체크
- [ ] 상한 6종이 설정으로 있고, 상한 도달·진행 없음·반복 행동 각각의 저하 경로를 실행해 봤는가
- [ ] 툴마다 독립 서킷 브레이커가 있고, 열렸을 때 툴 목록에서 제거되며 오류가 구조화 관찰로 주입되는가
- [ ] 쓰기 툴이 멱등 키를 갖고 체크포인트 재개 시 중복 실행이 방지되는가
- [ ] 스텝 수·토큰·성공률의 p95 베이스라인과 SLO 초안이 있는가
- [ ] 툴 추가가 레지스트리 등록 + 판정 질문 정의 버전 상승만으로 끝나고 루프 코드 변경이 없는가
- [ ] 폴백 모델이 툴 호출 형식까지 포함해 호환 매트릭스에서 검증되었는가
- [ ] 등급 3 이상 툴에 승인 요청 → 체크포인트 → 재개 흐름이 있고 만료 시 거부되는가
- [ ] 트레이스에 스텝별 판정·툴 호출·게이트 판정·버전 키가 있어 트래젝토리를 재구성할 수 있는가
