# 에이전트 설계 패턴

> **범위**: ReAct, Plan-and-Execute, Reflection, Router, Orchestrator-Worker, CodeAct(코드 실행형 행동 공간) 비교
> **시각화**: [`assets/html/agent-design-patterns.html`](../assets/html/agent-design-patterns.html)

## 요약 (3줄)

1. 에이전트 패턴은 **루프의 모양**으로 구분된다. ReAct는 "생각-행동-관찰"을 매 스텝 반복, Plan-and-Execute는 계획을 먼저 세우고 실행, Reflection은 출력을 스스로 비판해 재생성, Tool-use는 모델이 함수를 고르는 기본 단위, Router는 분기, Orchestrator-Worker는 동적 분해·위임이다. **CodeAct**는 ReAct의 행동 공간을 "JSON 툴 호출 1회"에서 "실행 가능한 코드 1블록"으로 바꾼 변형으로, 중간 데이터가 컨텍스트를 거치지 않는 대신 샌드박스와 `call_tool` 경계 게이트가 전제다.
2. 패턴의 비용은 **LLM 호출 수**로 비교한다. ReAct는 스텝 수에 비례해 가변, Plan-and-Execute는 1(계획) + 단계 수 + 재계획, Reflection은 2 × 반복, Router는 1 + 1. 호출 수가 가변인 패턴은 반드시 상한을 갖는다.
3. 모든 패턴에서 "다음 행동 선택"·"충분한가"·"어느 워커에게"는 선택지가 닫힌 **판정**이다. 이 자리를 결정 모델(Jev / Decisions API)·분류기·규칙이 맡는 변형이 비용과 비결정성을 줄이는 최근 1년의 방향이다 — 다만 사례는 아직 `[2차]` 수준이다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | [05](05-workflow-vs-agent.md)에서 "에이전트 구간"으로 결정된 부분의 **루프 구조**: 어떤 패턴을 쓰는지, 각 스텝의 입출력 스키마, 종료 조건, 상한, 판정 지점의 수단 배정. 품질 기준은 과업 성공률·스텝 수 분포·비용 p95·실패 모드별 발생률 |
| **언제** (When) | [05](05-workflow-vs-agent.md)의 세 조건(경로 열거 불가, 관찰 의존, 실패 비용 통제 가능)이 충족된 뒤. 툴이 하나이고 호출이 한 번이면 Tool-use만으로 충분하고 루프가 필요 없다. 멀티 에이전트([07](07-multi-agent-orchestration.md))는 단일 루프의 컨텍스트·역할 한계가 확인된 뒤 |
| **어떻게** (How) | ① 과업의 관찰-행동 의존 구조를 그림(계획 가능한가, 중간 결과가 다음을 바꾸는가) → ② 계획 가능하면 Plan-and-Execute, 매 스텝 의존이면 ReAct, 품질 반복이면 Reflection, 분해·위임이면 Orchestrator-Worker → ③ 판정 지점(다음 행동, 종료, 워커 선택)의 수단 배정 → ④ 상한·종료·폴백·게이트 → ⑤ 트레이스로 스텝 수·비용·실패 모드 `[실측]` → ⑥ 실패 모드가 패턴 고유의 것이면 패턴 교체 또는 조합 |
| **왜** (Why) | 패턴을 고르지 않고 "LLM에 툴 주고 루프 돌리기"로 시작하면 ReAct의 가장 취약한 형태가 된다. 매 스텝 전체 히스토리를 다시 읽어 비용이 스텝 수의 제곱으로, 중간 관찰에 흔들려 목표를 잃고, 종료 판단이 불안정하다. 패턴은 이 실패 모드들에 대한 구조적 대응이다 |

## 문제와 맥락

단일 LLM 호출이 못 하는 것은 "결과를 보고 다시 하기"다. 에이전트 루프는 이것을 가능하게 하지만, 루프를 어떻게 구성하느냐에 따라 전혀 다른 비용·안정성 특성을 갖는다. 루프 설계가 없을 때의 증상은 다음과 같다.

- **목표 이탈**: 중간 관찰(검색 결과, 툴 오류)에 반응하다 원래 질문을 잊음
- **반복 행동**: 같은 툴을 같은 인자로 여러 번 호출. 관찰을 해석하지 못하거나 상태를 잃음
- **조기 종료 / 종료 불능**: "충분하다"는 판단이 불안정. 스텝 수 분포가 넓음
- **컨텍스트 폭증**: 매 스텝 전체 히스토리 + 툴 출력이 쌓여 뒤로 갈수록 품질 저하·비용 증가
- **계획 경직**: 처음 세운 계획이 틀렸는데 수정하지 못함(Plan-and-Execute의 고유 실패)
- **자기 비판의 무효**: 평가자와 생성자가 같은 모델이라 같은 오류를 못 봄(Reflection의 고유 실패)

각 패턴은 일부 증상을 줄이는 대신 다른 증상을 키운다. 그래서 "최선의 패턴"은 없고 과업의 의존 구조에 맞는 패턴이 있다.

## 핵심 개념

### 7개 패턴의 루프 구조

시각화: [`agent-design-patterns.html`](../assets/html/agent-design-patterns.html) — 7개 패턴의 루프를 나란히 비교.

| 패턴 | 루프 | 설계자가 정하는 것 | 모델이 정하는 것 | LLM 호출 수 |
|---|---|---|---|---|
| **Tool-use** | 질의 → 모델이 함수·인자 선택 → 실행 → 결과로 답변 | 툴 스키마, 실행 코드 | 어느 툴, 어떤 인자 | 1~2 (선택 + 답변) |
| **ReAct** | [생각 → 행동(툴) → 관찰] 반복 → 종료 판단 → 답변 | 툴 집합, 상한, 종료 조건 | 매 스텝의 행동과 종료 | 스텝 수에 비례(가변) |
| **Plan-and-Execute** | 계획 수립(단계 목록) → 단계별 실행 → (필요 시) 재계획 → 종합 | 계획 스키마, 재계획 트리거 | 계획 내용, 재계획 여부 | 1 + 단계 수 + 재계획 횟수 |
| **Reflection** | 생성 → 자기 비판(기준 대비) → 수정 → 합격 또는 상한 | 비판 기준, 상한 | 비판 내용, 수정 | 2 × 반복 수 |
| **Router** | 분류 → 전용 핸들러(프롬프트·에이전트·워크플로우) | 경로 집합, 핸들러 | 어느 경로 | 1 + 핸들러 비용 |
| **Orchestrator-Worker** | 오케스트레이터가 분해 → 워커 병렬·순차 실행 → 결과 종합 | 워커 종류·능력, 종합 방식 | 분해 내용, 워커 배정 | 1 + 워커 수 + 1 |
| **CodeAct** (코드 실행형 행동 공간) | [생각 → 코드 1블록 작성 → 샌드박스 실행(내부에서 `call_tool` ×N) → 결과 요약만 컨텍스트로] 반복 → 종료 → 답변 | 샌드박스, `call_tool`로 노출할 툴 집합, 자원 상한, 블록 수 상한 | 코드 내용(어느 툴을 어떤 순서·조건·반복으로), 종료 | 코드 블록 수에 비례 — ReAct보다 적음(원 논문 평균 턴 5.5 vs 7.6 `[검증]`) |

### 패턴별 적합·부적합과 실패 모드

| 패턴 | 적합 | 부적합 | 고유 실패 모드 | 완화 |
|---|---|---|---|---|
| **Tool-use** | 툴 1~N개 중 하나를 한 번 호출하면 끝 | 결과를 보고 다시 호출해야 함 | 잘못된 인자, 불필요한 호출 | 인자 스키마 검증, 호출 전 규칙 게이트 |
| **ReAct** | 탐색적 과업, 매 스텝 결과가 다음을 결정, 스텝 수 적음(≤10) | 긴 과업(컨텍스트 폭증), 지연 민감, 계획 가능한 과업 | 목표 이탈, 반복 행동, 종료 불안정 | 상한, 상태 요약, 종료 판정을 결정 모델·규칙으로 |
| **Plan-and-Execute** | 단계를 미리 그릴 수 있는 다단계 과업, 비용 예측 필요 | 중간 결과가 계획 전체를 바꾸는 과업 | 계획 경직, 틀린 계획 끝까지 실행 | 재계획 트리거(단계 실패·관찰 불일치), 계획을 스키마로 검증 |
| **Reflection** | 명확한 품질 기준, 반복으로 측정 가능하게 개선(코드 테스트, 형식 준수) | 기준 주관적, 생성자와 평가자가 같은 맹점 | 자기 비판 무효, 수렴 안 함 | 평가자를 다른 모델·규칙·결정 모델로, 상한 |
| **Router** | 입력 유형 이질, 유형별 전용 처리 | 유형 경계 불명확 | 오분류의 증폭(이후 전부 무효) | 확신도 임계값 + 폴백 경로, 분류는 결정 모델·분류기 |
| **Orchestrator-Worker** | 부분 과업 열거 불가, 다중 소스·파일·관점 | 과업 구조 고정(체이닝으로 충분) | 분해 오류, 워커 결과 충돌·중복, 종합 품질 | 분해 스키마 검증, 워커 출력 스키마, 종합 전 중복 제거 |
| **CodeAct** | 툴 다수·조합, 대량 중간 데이터, 반복·조건·집계가 있는 배치형 과업 | 행동 1~2개 단순 과업, 샌드박스 운영 불가, 모든 툴 호출에 사람 승인이 필요한 고위험 경로 | 코드 오류 루프, 샌드박스 탈출 시도, 게이트 우회, 디버깅 난이도 | 코드 오류 상한 후 Tool-use 폴백, 네트워크·파일 격리 + 자원 상한, 모든 호출을 `call_tool` 경계 게이트로, 코드 원문 감사 |

### 패턴은 조합된다

실무 에이전트는 한 패턴이 아니다. 흔한 조합은 ① Router → 경로별 Plan-and-Execute ② Plan-and-Execute의 각 단계가 ReAct ③ 어느 패턴이든 마지막에 Reflection ④ Orchestrator-Worker의 워커가 Tool-use 또는 ReAct. 조합할수록 호출 수가 곱해지므로 **조합의 깊이에 상한**을 둔다(보통 2단).

### 결정 모델이 "다음 행동 선택"을 맡는 변형

ReAct의 매 스텝 "다음 행동"은 툴 집합 + 종료라는 **닫힌 선택지**다. Plan-and-Execute의 "재계획 필요?", Reflection의 "합격?", Router의 "어느 경로?", Orchestrator의 "어느 워커?"도 마찬가지다. 이 판정을 생성 모델이 아니라 결정 모델(Jev / Decisions API)이 맡으면:

- 판정 1회가 생성 1회보다 싸고 빠르다(Jev 70~500ms E2E 주장 `[벤더]`, 독립 벤치마크 없음)
- 보정 확률이 나와 "확신 낮음 → 사람" 임계값을 둘 수 있다
- 판정 결과가 타입드라 트레이스·회귀 테스트가 쉽다

단, 툴 **인자** 생성은 여전히 생성 과업이라 LLM이 맡는다. 즉 "무엇을 할까"는 결정 모델, "어떻게 할까(인자·내용)"는 LLM으로 분리된다. 두 결정 모델은 내부가 다르고(Jev는 결정 전용 비자기회귀 모델, Decisions API는 gpt-6-luna 출력 제약) 한국어 평가셋 `[실측]`이 선행되어야 한다. 배치 설계는 [11](11-decision-layer.md), 원칙은 [Part 1/02](../01-foundations/02-system1-vs-system2.md).

### CodeAct — 행동 공간을 코드로 바꾼 ReAct 변형

ReAct의 한 스텝은 "JSON 툴 호출 1회 → 관찰 전체가 컨텍스트로"다. **CodeAct**(Wang et al., ICML 2024 `[검증]`)는 이 행동 공간을 **실행 가능한 코드 1블록**으로 바꾼다. 모델은 매 턴 짧은 코드를 쓰고, 샌드박스가 그 코드를 실행하며, 코드 안에서 `call_tool(…)`이 N번 호출된다. 컨텍스트로 돌아오는 것은 **결과 요약(또는 코드가 명시적으로 출력한 값)뿐**이다.

- **이점**: ① 중간 데이터(수천 행 조회 결과, 파일 내용)가 컨텍스트를 거치지 않는다 ② 반복·조건·집계를 코드가 처리하므로 "툴 호출 → 관찰 → 다음 툴 호출"을 턴마다 되풀이하지 않는다 ③ 턴 수가 준다. 원 논문은 17개 LLM에서 JSON/텍스트 행동 대비 최대 20% 높은 성공률, GPT-4 기준 74.4% vs 52.4%·평균 턴 5.5 vs 7.6을 보고한다 `[검증]`. 절감 폭은 툴 수·중간 데이터 크기에 비례하며 단순 과업에서는 작다
- **고유 실패 모드**: ① **코드 오류 루프** — 문법·런타임 오류를 고치느라 턴을 소모(ReAct의 반복 행동에 대응) ② **샌드박스 탈출 시도** — 생성 코드가 네트워크·파일시스템·자격 증명에 직접 닿으려 함(인젝션의 새 경로) ③ **게이트 우회** — 툴 호출이 코드 안에서 일어나므로 "툴 실행 직전 규칙 게이트"가 모델 바깥 어디에 있는지 설계하지 않으면 사라진다 ④ **디버깅 난이도** — 한 턴에 N개 호출이 묶여 트래젝토리 평가 단위가 바뀐다
- **이 위키의 설계 함의**: 이 페이지의 거버넌스 입장(행동 직전 규칙 게이트 필수, 등급 5 자동 실행 금지)은 그대로다. 게이트가 모델 바깥 **샌드박스의 `call_tool` 경계**로 이동할 뿐이다 — 코드 안의 모든 툴 호출은 `call_tool`을 통해서만 가능하고, 그 함수 안에서 등급별 규칙 게이트·멱등 키·트레이스가 적용되며, 승인이 필요한 호출이 코드 중간에 나오면 실행을 **중단하고 체크포인트** 후 승인 → 재개한다. 등급 5 툴은 `call_tool`에 노출하지 않는다. **생성 코드 자체가 감사 레코드**다. 원칙의 상세는 [09 `call_tool` 경계 게이트](09-tools-and-mcp.md), 게이트 설계는 [12](12-guardrails-hitl.md)
- **구현체(2025-09 ~ 2026)**: 세 벤더 구현을 "코드 실행형 행동 공간(CodeAct 계열)"으로 묶는다. Anthropic "Code execution with MCP"(2025-11, MCP 서버를 코드 API로 노출·Programmatic Tool Calling·Tool Search Tool) `[벤더]`, Cloudflare Code Mode(2025-09 공개, `search()` + `execute()` 두 툴, 샌드박스 JS) `[벤더]`, Microsoft Agent Framework CodeAct(BUILD 2026, `call_tool(…)` 파이썬 1회 작성, Hyperlight 마이크로 VM 호출당 격리, 알파) `[벤더]`. Hugging Face smolagents는 `CodeAgent`가 기본값이고 `ToolCallingAgent`가 JSON이다 `[벤더]`. 토큰 절감 수치("98.7%", "99.9%", 6,890 → 2,489)는 전부 `[벤더]`·`[2차]`이며 소스 간 차이가 크다(독립 테스트 78.5%, 독립 보도 단순 32% / 복잡 배치 81% `[2차]`) — 설계 근거로 쓰지 않고 자체 과업에서 `[실측]`한다

| Router | 유형 이질, 유형별 전용 경로 | 경계 불명확 | 하~중 | 표준 | `[2차]` — [02](02-query-understanding.md) |

### 선택 가이드

- **툴 한 번으로 끝난다면** → Tool-use. 루프를 만들지 않는다. 이유: 루프의 비결정성은 필요할 때만 치른다
- **단계를 미리 그릴 수 있다면** → Plan-and-Execute + 재계획 트리거. 이유: 비용 예측이 가능하고 계획 자체를 검증·수정할 수 있다
- **매 스텝 결과가 다음을 바꾸고 스텝이 10개 이내라면** → ReAct + 상한 + 상태 요약. 이유: 탐색적 과업에 가장 유연하다. 종료 판정은 결정 모델·규칙으로
- **출력 품질에 명확한 기준이 있다면** → 마지막에 Reflection, 평가자는 다른 모델·규칙·결정 모델로. 이유: 같은 모델의 자기 비판은 같은 맹점을 공유한다
- **부분 과업을 미리 열거할 수 없고 병렬화 여지가 있다면** → Orchestrator-Worker, 분해·워커 출력을 스키마로. 이유: 분해 품질이 전체를 좌우하므로 검증 가능하게
- **툴이 수십 개 이상이고 중간 결과가 크다면** → CodeAct 계열. 단 **샌드박스와 `call_tool` 경계 게이트가 먼저**다. 이유: 중간 데이터가 컨텍스트를 거치지 않아 턴·토큰이 줄지만, 게이트가 모델 바깥으로 옮겨지지 않으면 행동 가드레일이 사라진다. 모든 호출에 승인이 필요한 경로라면 ReAct·Tool-use가 낫다
- **판단이 어려우면** → Router → Plan-and-Execute를 기본값으로, 각 단계는 Tool-use. 이유: 호출 수가 거의 고정이라 비용·디버깅이 통제되고, 필요한 단계만 ReAct로 바꿀 수 있다

## 설계 시 고려사항 (체크리스트)

- [ ] 과업의 관찰-행동 의존 구조를 그렸고 그에 맞는 패턴을 골랐는가 (기본값 ReAct가 아닌가)
- [ ] 모든 가변 루프에 최대 스텝·비용·시간 상한과 상한 도달 시 폴백이 있는가
- [ ] 종료 조건이 명시적이고 판정 수단(결정 모델 / 규칙 / LLM)이 배정되어 있는가
- [ ] 매 스텝 상태가 "목표 + 요약 히스토리 + 최근 관찰"로 압축되는가 (전체 히스토리 누적이 아닌가) — [08](08-state-memory-context.md)
- [ ] 반복 행동 감지(같은 툴·같은 인자 N회)가 있는가
- [ ] 툴 실행 직전 규칙 게이트가 있는가 ([12](12-guardrails-hitl.md)), 툴 인자는 스키마 검증되는가 ([09](09-tools-and-mcp.md))
- [ ] CodeAct라면 모든 툴 호출이 샌드박스의 `call_tool` 경계를 통해서만 가능하고(네트워크·파일 직접 접근 차단), 승인 필요 호출에서 실행 중단 → 체크포인트 → 재개가 되는가. 등급 5 툴이 `call_tool`에 노출되지 않는가
- [ ] Reflection의 평가자가 생성자와 분리되어 있는가
- [ ] Plan-and-Execute의 재계획 트리거가 정의되어 있는가
- [ ] Orchestrator의 분해 결과와 워커 출력이 스키마로 검증되는가
- [ ] 트레이스가 스텝별 판정·확신도·툴 호출·토큰을 기록하는가 ([Part 5/03](../05-cross-cutting/03-observability-tracing.md))
- [ ] 스텝 수·비용의 분포(p95)와 실패 모드별 발생률을 측정하는가 ([13](13-evaluation-rag-agents.md))

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 컨텍스트 폭증 (ReAct) | 스텝이 늘수록 비용 증가·품질 저하 | 상태 요약·compaction, 툴 출력 절단, 스텝 상한 |
| 계획 경직 (Plan-and-Execute) | 틀린 계획을 끝까지 실행 | 단계 실패·관찰 불일치 시 재계획, 계획 검증 |
| 자기 비판 무효 (Reflection) | 반복해도 같은 오류 | 평가자 분리(다른 모델·규칙·결정 모델), 외부 신호(테스트 결과) |
| 분해 오류 (Orchestrator) | 워커가 잘해도 전체 실패 | 분해 스키마 검증, 분해 예시, 분해만 별도 평가 |
| 샌드박스 전제 (CodeAct) | 샌드박스 인프라·자원 상한·탈출 방어가 없으면 생성 코드가 임의 코드 실행 경로가 됨. 절감 수치는 `[벤더]`뿐 | 네트워크·파일 격리 + 자원 상한 + `call_tool` 단일 경계, 자체 과업에서 토큰·턴 `[실측]` 후 채택 |
| 판정의 비결정성 | 같은 상태에 다른 행동 | 판정을 결정 모델·규칙으로, 온도 0, 트레이스 비교 |
| 결정 모델 사례 부족 | "다음 행동 선택" 변형의 실효가 미검증 | 소형 LLM 판정과 같은 평가셋으로 `[실측]` 후 채택 |
| 프레임워크 추상화 누수 | 기본 루프의 종료·재시도 동작을 모르고 사용 | 프레임워크의 루프 코드 읽기, hooks로 관측 |
| 벤치마크와 실무의 괴리 | 원 논문 성과가 자체 툴·도메인에서 재현 안 됨 | 자체 과업 평가셋, 트래젝토리 평가 |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 에이전트 루프는 **행동 가드레일이 매 스텝 실행되는 자리**이고, 비용이 요청 수가 아니라 스텝 수에 비례하는 유일한 구간이다. 루프 안의 툴 집합이 곧 위험 등급의 상한이다. 레이어 간 종합은 [Part 5/06](../05-cross-cutting/06-operational-design-matrix.md).

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| **요청 수 × 스텝 수** (중심 축) | 모델 API 토큰 한도(TPM). ReAct는 스텝 n의 입력이 히스토리 누적으로 커져 요청 수보다 훨씬 빨리 소진 | 상태 요약·compaction([08](08-state-memory-context.md)), 프롬프트 캐시(시스템 프롬프트 + 툴 정의 고정 접두사), 동시 활성 루프 세마포어, 요청 큐, 스텝 실행은 무상태로 두고 루프 상태는 외부 저장소에 | 요청 수 × Σ(스텝별 컨텍스트 토큰) — 요약 없으면 스텝 수의 제곱에 가까움 |
| **툴 수** | 툴 정의가 매 스텝 컨텍스트에 실림. 툴 50개면 정의만 수천 토큰, 툴 선택 정확도 하락 | 툴 라우팅·그룹화(과업·역할별 서브셋), 지연 로딩, 툴 정의 캐시([09](09-tools-and-mcp.md)) | 툴 수 × 스텝 수 |
| **워커 수** (Orchestrator-Worker) | 병렬 워커가 레이트 리밋을 순간 소진 | 워커 동시성 상한, 워커 큐 | 워커 수 |
| **반복 수** (Reflection) | 2 × 반복 | 반복 상한, 평가자를 규칙·결정 모델로(생성 호출 1 → 0) | 반복 수 |
| **동시 세션** | 루프 상태 메모리, 체크포인트 쓰기 | 상태 외부화, TTL | 세션 수 × 상태 크기 |
| **코드 실행 수** (CodeAct) | 샌드박스 인스턴스 풀 고갈, 실행당 CPU·메모리·시간. 토큰은 줄지만 컴퓨트가 늘어 비용 축이 바뀜 | 샌드박스 풀 + 큐, 실행당 자원 상한, 호출당 격리(마이크로 VM)와 세션당 재사용의 트레이드오프 | 코드 블록 수 × 실행 자원 |

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 모델 API 다운·지연(스텝 중) | 루프 중단 | 스텝 오류율·p95, 서킷 브레이커 열림 | 스텝 재시도(예시 2회, 지수 백오프) → 폴백 모델(호환 매트릭스 내, 툴 호출 형식 호환 확인된 것만) → 체크포인트에서 재개 또는 부분 결과 | 폴백률 10분간 50%(예시) |
| **무한 루프·스텝 상한 도달** | 응답 없음, 비용 급등 | 상한 도달률, 진행 없음 감지(상태 해시 반복) | 상한(예시 ReAct 10스텝·토큰·시간)에서 강제 종료 → 수집된 관찰로 종합 답변 + "미완" 플래그, 또는 Plan-and-Execute·워크플로우 폴백 | 상한 도달률 5%(예시) |
| 반복 행동(같은 툴·같은 인자) | 비용 낭비, 진행 없음 | 반복 카운터 | 예시 3회째에 캐시된 결과 반환 + "이미 시도함"을 관찰로 주입, 지속 시 종료 | 반복률 급증 |
| 툴 타임아웃·오류 | 관찰 없음 → 모델이 결과를 지어낼 위험 | 툴별 오류율·p95([09](09-tools-and-mcp.md)) | **구조화 오류를 관찰로 주입**(빈 결과 아님). 툴 서킷이 열리면 그 툴을 툴 목록에서 제거(모델이 다른 경로를 찾게) | 툴별 오류율 10%(예시) |
| 계획 경직(Plan-and-Execute) | 틀린 계획을 끝까지 | 단계 연속 실패 수 | 재계획 트리거(예시 연속 2회 실패) → 재계획 상한(예시 2회) → 종료 | 재계획 상한 도달 반복 |
| Reflection 비수렴 | 반복 상한까지 불합격 | 반복 수 분포 | 최고 점수 출력 + 플래그 | 비수렴률 10%(예시) |
| 판정 수단(결정 모델 API) 다운 | 다음 행동을 못 고름 | 판정 API 오류 | 섀도 기간에 비교한 소형 LLM 판정으로 폴백, 그것도 실패하면 규칙 기본 행동(안전 종료) | 즉시 |
| 컨텍스트 폭증(요약 실패) | 후반 스텝 품질 저하, 컨텍스트 초과 오류 | 스텝별 토큰 추이, 초과 오류 | 강제 compaction, 툴 출력 절단 | 초과 오류 발생 시 |
| **생성 코드 오류 루프 / 샌드박스 자원 고갈 / 게이트 우회 시도**(CodeAct) | 진행 없음·비용 급등 / 실행 중단 / 보이지 않음 | `agent.code_exec` 연속 오류 수, `agent.sandbox_exit_reason`=resource_limit, 샌드박스 네트워크·파일 거부 이벤트, `agent.inner_tool_calls`와 자식 `tool.invoke` 수 불일치 | 코드 오류 N회(예시 3)에 구조화 오류를 관찰로 주입 → 상한에서 Tool-use(JSON) 폴백 / 자원 상한에서 실행 강제 종료 + 부분 결과 / 우회 시도는 즉시 차단 + 세션 격리 모드(전송·쓰기 툴 비활성). 샌드박스·`call_tool` 게이트 다운은 **fail-closed**(코드 실행 경로 닫힘) | 우회 시도 1건 즉시(보안), 자원 상한 도달률 5%(예시) |

SLI 후보: 과업 성공률(골든셋), 스텝 수 분포(p50/p95), 상한 도달률, 요청당 토큰·비용 p95, 반복 행동 발생률, 툴 오류율, E2E p95. CodeAct 추가: 코드 실행 오류율, 블록당 내부 호출 수, 샌드박스 경계 이탈 시도 건수(0이어야). SLO 초안(예시): 상한 도달률 < 2%, 스텝 p95 ≤ 8, 성공률 ≥ 85%. 서킷 브레이커 위치: 모델 API, **툴/MCP 서버마다 독립**, 결정 모델 API. 쓰기 행동: 쓰기 툴은 멱등 키(요청 ID + 스텝 번호), 타임아웃, 재시도 상한, 재개 시 체크포인트의 "실행 완료" 기록으로 중복 실행 방지 — 상세 [09](09-tools-and-mcp.md).

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성의 "탐지 신호"가 **실제로 어디서 나오는지**를 설계한다. 기준은 [Part 1/07 관측성 설계 요소](../01-foundations/07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md). 에이전트 루프의 관측 단위는 **스텝**이다 — `agent.step {n}` 아래에 판정·툴·게이트가 자식으로 매달리고, 루프 전체 지표는 턴 종료 시 `invoke_agent` 루트에 집계한다. 비용이 스텝 수에 비례하는 유일한 구간이므로 "스텝 번호 × 토큰" 분포가 이 단계의 고유 지표다.

| 기록 대상 | 스팬 / 이벤트 (이름, 부모) | 핵심 속성 (버전 키 포함) | 지표 (→ 어느 SLI) | 샘플링 · 보존 · PII |
|---|---|---|---|---|
| 루프 전체 | `invoke_agent {name}` (부모 `turn`) — 턴 종료 시 집계 | `agent.pattern`(react/plan_execute/reflection/orchestrator), `agent.step_count`, `agent.limit_hit`(step/token/time/iteration/replan/depth), `agent.outcome`, `agent.degradation[]`=`partial`·`plan_fallback`·`workflow_fallback`, 토큰 합계·`agent.cost_estimate`, 버전 키 5종(`agent.catalog_version`=툴 레지스트리 버전) | **과업 성공률**(골든셋 + 샘플 judge 링크), **스텝 수 분포(p50/p95)**, **상한 도달률**, **요청당 토큰·비용 p95**, **E2E p95** | 메타 전수, 상한 도달·실패 트래젝토리는 본문 전수(골든셋 환류) |
| 스텝 | `agent.step {n}` (부모 `invoke_agent`); 모델 호출은 자식 `generation.generate` + `gen_ai.*` | `agent.state_hash`, `agent.no_progress_count`, `agent.context_tokens`(스텝 입력), `agent.compaction_applied`, `agent.truncated_outputs`, 스텝 지연, `agent.outcome`=fallback(모델) | 스텝 오류율·p95, 진행 없음 감지율(동일 해시 N회), **스텝 번호 × 토큰 히트맵**(추이), 컨텍스트 초과 오류율, 모델 폴백률 → 모델 다운(스텝 중), 컨텍스트 폭증 | 메타 전수 |
| 다음 행동 판정 | `routing.decide next_action` (부모 `agent.step`) | `agent.decision`(tool/answer/replan/stop), `agent.confidence`, `agent.decision_source`, 질문 정의 버전, `agent.outcome`=fallback(결정 모델 → 소형 LLM → 규칙 안전 종료) | 판정 API 오류율·p95, 판정 폴백률(수단별), 행동 선택 분포, 확신도 히스토그램 → 판정 수단 다운 | 메타 전수 |
| 툴 호출 | `tool.invoke {tool}` (부모 `agent.step`; 상세 [09](09-tools-and-mcp.md)) | 툴 이름·스키마 버전, MCP 서버 ID, `agent.args_hash`, `agent.idempotency_key`(요청 ID + 스텝), 결과 크기·`agent.result_truncated`, `agent.error_code`, `agent.error_injected`(구조화 오류를 관찰로 주입했는지), `agent.circuit_state`, `agent.repeat_count`(같은 툴·같은 인자 해시 반복 횟수) | **툴 오류율**·p95·타임아웃(툴별), **반복 행동 발생률**(`repeat_count` ≥ 3 비율), 서킷 열림으로 툴 목록에서 제거된 건수 → 툴 타임아웃·오류, 반복 행동 | 메타 전수, 인자·결과 본문 opt-in(마스킹), 오류 건 전수 |
| 행동 게이트·승인 | `gate.evaluate action_policy` → `approval.request` / `approval.resolve` (부모 `agent.step`, 툴 실행 직전) | `agent.risk_level`, `agent.rule_ids[]`·`agent.rules_version`, 게이트 출력 4종, 승인자 역할 해시, 승인 결과(approved/rejected/expired), `agent.queue_wait_ms`, 재개 체크포인트 ID | 차단률(사유별), 승인 요청률, 승인 대기 p95, 만료=거부 비율, 승인 후 재개 성공률 | **전수**(샘플링 금지), 승인 카드 내용은 감사 저장소에 |
| 패턴 전용 | Plan-and-Execute `agent.plan` / `agent.replan {n}`; Reflection `agent.iteration {n}` (부모 `invoke_agent`) | `agent.consecutive_failures`, 재계획 상한 도달; `agent.score`·`agent.converged` | 재계획율·재계획 상한 도달률, 단계 연속 실패 분포, 반복 수 분포·비수렴률 → 계획 경직, Reflection 비수렴 | 메타 전수 |
| 체크포인트 | 이벤트 `checkpoint.save` / `checkpoint.resume` | `agent.checkpoint_id`, 상태 스키마 버전, "실행 완료" 기록 히트 | 재개 성공률, 중복 실행 차단 건수 ([08](08-state-memory-context.md)) | 전수, 상태 본문은 저장소에만 |
| 코드 실행 (CodeAct) | `agent.code_exec` (부모 `agent.step`); 자식 `tool.invoke {tool}` ×N — 샌드박스 `call_tool` 경계에서 생성, 각각 아래에 `gate.evaluate` | `agent.code_hash`(코드 원문은 감사 레코드, 스팬에는 해시), `agent.inner_tool_calls`, `agent.sandbox_exit_reason`(ok / error / timeout / resource_limit / gate_block / approval_pause), 코드 오류 재시도 횟수, 실행 자원(CPU·메모리·시간), 폴백=`tool_use_fallback` | 코드 실행 오류율·연속 오류 분포(→ 코드 오류 루프), 자원 상한 도달률(→ 샌드박스 자원 고갈), 샌드박스 거부 이벤트 수 + `inner_tool_calls` ≠ 자식 `tool.invoke` 수 건수(→ 게이트 우회 시도), 블록당 내부 호출 수 분포(절감 `[실측]`의 근거) | 메타 전수, 코드 원문은 감사 저장소 전수, 샌드박스 stdout/stderr는 opt-in(마스킹) |

|---|---|---|---|
| 스텝 모델 폴백 급증 | 스텝 `agent.outcome=fallback` 비율 10분간 50% 초과, 또는 모델 서킷 열림 | P1 | ① 벤더·서킷 상태 확인 ② 폴백 모델이 **툴 호출 형식까지** 호환 매트릭스에서 검증된 것인지 확인 ③ 체크포인트 재개 대기와 부분 결과 반환 비율 확인 |
| 상한 도달·반복 행동 | `agent.limit_hit` 비율 5% 초과, 진행 없음 감지율 급증, 또는 `repeat_count` ≥ 3 비율 급증 | P2 | ① 패턴·툴·테넌트별로 분해, `repeat_count` 상위 툴 확인 ② 시스템 프롬프트·종료 조건·모델 버전의 최근 변경 확인 ③ 상한 하향 또는 Plan-and-Execute·워크플로우 폴백 플래그 검토 |
| 툴 오류율 상승 | 특정 툴 오류율 10% 초과 | P2 | ① 툴 서킷 상태와 툴 목록에서 제거되었는지 확인 ② 오류가 구조화 관찰로 주입되는지(`error_injected`=true 비율) 확인 — 빈 결과면 모델이 지어낸다 ③ MCP 서버 소유자 통보([09](09-tools-and-mcp.md)) |

| 컨텍스트·수렴 이상 | 컨텍스트 초과 오류 1건 이상, 비수렴률 10% 초과, 또는 재계획 상한 도달 반복 | P2 | ① 스텝 번호 × 토큰 히트맵에서 폭증 스텝 확인 ② compaction 발동 여부·툴 출력 절단 설정 확인 ③ 평가 기준·재계획 트리거 설정 점검 |

대시보드에서 이 단계를 보는 뷰: ② Reasoning 패널의 핵심 공급원 — 스텝 수 분포, 상한 도달률, 툴별 오류율, 스텝 × 토큰 히트맵, 행동 선택 분포, 승인 대기 / ③ 비용·판정 분포 — 요청당 토큰·비용 p95, 캐시 토큰 비율(시스템 프롬프트 + 툴 정의 접두사), 판정 확신도 히스토그램·결정 소스 분포 / ① E2E — 과업 성공률, 승인 대기 시간, 저하율.
감사 추적으로 넘기는 필드(관측 로그와 분리): 세션·요청 ID, 스텝 번호, 스텝별 판정·수단·확신도, 툴 호출(이름·인자 해시·멱등 키·결과 요약), 게이트 판정·규칙 버전, 승인자·시각, 프롬프트·모델 버전(폴백 여부), 상한 도달·폴백 여부, 체크포인트 ID, 최종 답변 근거 ID — 거버넌스 접점 표와 동일.
이 단계의 관측이 없으면 못 보는 장애: **지어낸 관찰** — 툴 타임아웃이 빈 결과로 들어가면 모델은 결과를 추정해 루프를 정상 종료하고, 성공률도 정상처럼 보인다. `tool.invoke` 오류와 바로 다음 `agent.step`의 답변 근거를 같은 트레이스에서 잇지 않으면 발견되지 않는다. 그리고 **쓰기 툴 중복 실행** — 멱등 키와 "실행 완료" 히트를 세지 않으면 외부 시스템의 이중 처리로만 드러난다. CodeAct에서는 **게이트를 거치지 않은 툴 호출** — `agent.inner_tool_calls`와 자식 `tool.invoke` 수를 대조하지 않으면 코드가 `call_tool` 밖에서 한 일은 성공 응답 속에 묻힌다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | 읽기 툴만이면 **1~2**. 쓰기·외부 전송 툴이 있으면 툴별로 **3~4**(예: 환불 접수 3, 운영 서버 설정 변경 4). 등급 5 툴은 에이전트에 노출하지 않는다(제안만). **루프의 툴 집합 = 위험 등급의 상한** |
| 가드레일 위치 | **행동 가드레일의 핵심 자리** — 매 스텝 툴 실행 직전 규칙 게이트(권한·한도·인자 스키마·금지 조합). CodeAct에서는 같은 게이트가 모델 바깥 **샌드박스의 `call_tool` 경계**로 이동해 코드 1블록 안의 N개 호출 각각에 적용된다. 입력([02](02-query-understanding.md))·출력([04](04-generation-grounding.md))은 루프 밖. 상세 [12](12-guardrails-hitl.md) |
| 게이트 출력과 판정 수단 | 통과 / 차단(권한 없음·한도 초과 → 구조화 오류를 관찰로 주입) / 승인 요청(등급 3 이상 → 루프 일시 중단 → 체크포인트 → 승인 후 재개, 만료 = 거부) / 저하(상한 도달 → 읽기 전용으로 종료). 규칙이 최종 결정권, 결정 모델 확신도는 "승인 필요 여부" 보조 |
| 소유자 (A) | 시스템 프롬프트·패턴 설정: 제품 책임자(A), AI 엔지니어(R). 툴 권한: 서비스 소유자(A), 플랫폼 엔지니어(R). 행동 게이트 규칙: 보안 책임자(A) |
| 감사 추적에 남길 필드 | 세션·요청 ID, 스텝 번호, 스텝별 판정(다음 행동)·수단·확신도, 툴 호출(이름·인자 해시·멱등 키·결과 요약), 게이트 판정·규칙 버전, 승인자·시각, 프롬프트 버전, 모델 버전(폴백 여부), 상한 도달·폴백 여부, 체크포인트 ID, 최종 답변 근거 ID. **CodeAct: 생성 코드 원문은 감사 레코드에**(스팬에는 `agent.code_hash`), 블록 안의 내부 호출 목록·샌드박스 종료 사유 |

### 운영 준비도 체크
- [ ] 상한 6종이 설정으로 있고, 상한 도달·진행 없음·반복 행동 각각의 저하 경로를 실행해 봤는가
- [ ] 툴마다 독립 서킷 브레이커가 있고, 열렸을 때 툴 목록에서 제거되며 오류가 구조화 관찰로 주입되는가
- [ ] 쓰기 툴이 멱등 키를 갖고 체크포인트 재개 시 중복 실행이 방지되는가
- [ ] 스텝 수·토큰·성공률의 p95 베이스라인과 SLO 초안이 있는가
- [ ] 툴 추가가 레지스트리 등록 + 판정 질문 정의 버전 상승만으로 끝나고 루프 코드 변경이 없는가
- [ ] 폴백 모델이 툴 호출 형식까지 포함해 호환 매트릭스에서 검증되었는가
- [ ] 등급 3 이상 툴에 승인 요청 → 체크포인트 → 재개 흐름이 있고 만료 시 거부되는가
- [ ] 트레이스에 스텝별 판정·툴 호출·게이트 판정·버전 키가 있어 트래젝토리를 재구성할 수 있는가
- [ ] `tool.invoke`에 `error_injected`·`repeat_count`·멱등 키가 남고, 툴 오류 직후 스텝의 답변 근거를 같은 트레이스에서 이어 "지어낸 관찰"을 찾을 수 있는가
- [ ] 스텝 번호 × 토큰 히트맵·상한 도달률·툴별 오류율이 대시보드 ②에 있고, 상한·툴 알림마다 런북 첫 3단계가 적혀 있는가
- [ ] CodeAct라면 샌드박스 다운·`call_tool` 게이트 다운이 fail-closed(코드 실행 경로 닫힘)인지, `agent.code_exec` 아래 `tool.invoke` 자식이 `inner_tool_calls`와 일치하는지, 코드 원문이 해시로 감사 레코드와 연결되는지 확인했는가
