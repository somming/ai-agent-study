# 멀티 에이전트 오케스트레이션

> **범위**: Supervisor / Hierarchical / Handoff 토폴로지, A2A, 상태 공유
> **시각화**: [`assets/html/multi-agent-topologies.html`](../assets/html/multi-agent-topologies.html)

## 요약 (3줄)

1. 멀티 에이전트는 **단일 에이전트의 한계가 측정으로 확인된 뒤**의 선택이다. 한계는 두 가지뿐이다 — 컨텍스트(한 루프에 다 못 넣음)와 역할(한 프롬프트가 상충하는 역할을 동시에 못 함). 둘 다 아니면 멀티 에이전트는 과잉이다.
2. 토폴로지는 네 가지로 정리된다. **Supervisor**(중앙이 위임·종합), **Hierarchical**(Supervisor의 다층화), **Handoff/Swarm**(에이전트가 다음 에이전트에게 제어를 넘김), **그래프**(명시적 노드·간선과 공유 상태). 제어 흐름을 누가 쥐는지와 상태를 어떻게 공유하는지가 차이다.
3. 비용은 LLM 호출 수의 곱이고, 디버깅 난이도는 에이전트 수의 곱 이상이다. 조직 간 연동은 A2A(Linux Foundation 이관, 2025-06)가 표준 후보지만 1.0 전용 발표는 미확인이다 `[2차]`.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 에이전트 역할 분할표(각 에이전트의 책임·툴·컨텍스트 범위) ② 토폴로지와 제어 흐름(누가 누구를 호출·위임·핸드오프하는가) ③ 상태 공유 방식(공유 상태 스키마 또는 메시지 스키마) ④ 조직 간 경계가 있으면 A2A Agent Card와 태스크 생명주기 ⑤ 전체 트레이스 상관 ID 체계. 품질 기준은 단일 에이전트 대비 성공률·비용·지연의 `[실측]` 차이 |
| **언제** (When) | 단일 에이전트([06](06-agent-design-patterns.md))가 컨텍스트 한계 또는 역할 상충으로 실패하는 것이 측정됐을 때. 생략 가능: 과업이 하나의 컨텍스트 윈도우와 하나의 역할로 처리됨. 미룰 수 있음: 역할은 다르지만 순차 실행이면 워크플로우 체이닝([05](05-workflow-vs-agent.md))으로 충분. A2A는 다른 조직·벤더의 에이전트와 연동할 때만 |
| **어떻게** (How) | ① 단일 에이전트 실패를 컨텍스트/역할로 분류 → ② 역할 분할표 작성, 각 에이전트의 툴·컨텍스트를 최소로 → ③ 제어 흐름이 중앙 집중 가능하면 Supervisor, 역할 수가 많으면 Hierarchical, 대화형으로 제어가 자연스럽게 넘어가면 Handoff, 흐름이 복잡하고 재현·체크포인트가 필요하면 그래프 → ④ 상태 공유 방식 결정(공유 상태 vs 메시지) → ⑤ 위임·핸드오프 판정 수단 배정(결정 모델·규칙·LLM) → ⑥ 상관 ID로 전체 트레이스, 상한(총 호출·깊이·시간) → ⑦ 단일 에이전트 기준선 대비 `[실측]` |
| **왜** (Why) | 멀티 에이전트를 먼저 도입하면 ① 비용이 에이전트 수 × 루프 수로 곱해지고 ② 실패가 어느 에이전트의 어느 스텝인지 추적하려면 분산 트레이싱이 필요하며 ③ 에이전트 간 상태 불일치·메시지 유실·순환 위임 같은 분산 시스템 문제가 LLM의 비결정성과 결합한다. 반대로 컨텍스트·역할 한계를 단일 에이전트로 밀어붙이면 품질이 스텝이 늘수록 떨어진다 |

## 문제와 맥락

단일 에이전트 루프가 벽에 부딪히는 지점은 두 가지다. 첫째, **컨텍스트**. 다중 소스 조사·다중 파일 수정처럼 중간 산출물이 많은 과업은 한 루프의 컨텍스트에 다 들어가지 않고, 들어가더라도 뒤로 갈수록 품질이 떨어진다. 둘째, **역할**. "엄격한 검토자"와 "창의적 작성자"를 한 프롬프트에 넣으면 둘 다 약해진다. 멀티 에이전트는 컨텍스트를 분할하고 역할을 분리하는 수단이다.

그런데 멀티 에이전트는 분산 시스템이다. LLM의 비결정성 위에 분산 시스템의 문제가 얹힌다.

- **순환 위임**: A가 B에게, B가 다시 A에게. 상한 없이는 종료 불능
- **상태 불일치**: 공유 상태를 두 에이전트가 동시에 갱신, 또는 메시지로 전달한 상태가 오래됨
- **책임 공백**: 핸드오프 후 원래 에이전트의 컨텍스트가 사라져 사용자 의도가 유실
- **종합 실패**: 워커 결과가 서로 모순인데 Supervisor가 그냥 이어 붙임
- **비용 폭발**: 에이전트 5개가 각각 ReAct 10스텝이면 50회 + 조정 호출
- **추적 불능**: 어느 에이전트의 어느 스텝에서 틀렸는지 트레이스가 분산

이 문제들이 "멀티 에이전트가 과잉인가"를 묻는 이유다. 사람 조직에 비유하면 직관적이지만, 사람 조직도 조정 비용이 크다는 점을 잊기 쉽다.

## 핵심 개념

### 4가지 토폴로지

시각화: [`multi-agent-topologies.html`](../assets/html/multi-agent-topologies.html).

| 토폴로지 | 제어 흐름 | 상태 공유 | 적합 | 부적합 | 고유 실패 |
|---|---|---|---|---|---|
| **Supervisor** | 중앙 에이전트가 워커에게 위임하고 결과를 받아 종합. 워커끼리는 통신 안 함 | Supervisor가 상태 보유, 워커는 과업 단위 입출력 | 역할 3~6개, 중앙 조정이 자연스러움, 종합 품질 중요 | 역할 수 많음(Supervisor 컨텍스트 폭증), 워커 간 직접 협업 필요 | Supervisor가 병목·단일 실패점, 위임 오판 |
| **Hierarchical** | Supervisor의 Supervisor. 팀 단위로 묶어 다층화 | 계층별 상태, 위로 요약 전달 | 역할 7개 이상, 도메인별 팀 구분 명확 | 과업이 작음, 계층 간 정보 손실 민감 | 계층마다 요약 손실, 지연 누적, 깊이 폭발 |
| **Handoff (Swarm)** | 현재 에이전트가 다음 에이전트에게 **제어를 넘김**. 중앙 없음 | 대화 히스토리(또는 그 일부)가 함께 이동 | 대화형, 단계가 자연스럽게 전문가를 바꿈(접수→기술→결제) | 병렬 처리, 종합 필요, 복잡 흐름 | 순환 핸드오프, 컨텍스트 유실, 흐름 추적 어려움 |
| **그래프** | 노드(에이전트·함수)와 간선(조건)을 명시, 엔진이 실행 | **공유 상태** 객체를 모든 노드가 읽고 씀 | 흐름 복잡, 재현·체크포인트·내구 실행 필요 | 흐름이 단순(과잉), 학습 곡선 부담 | 상태 스키마 비대, 간선 조건 디버깅 |

Supervisor와 Orchestrator-Worker([06](06-agent-design-patterns.md))는 같은 구조다. 차이는 워커가 단일 LLM 호출인지(Orchestrator-Worker) 자체 루프를 가진 에이전트인지(Supervisor)다. Handoff는 OpenAI Swarm이 널리 알린 패턴이고 Swarm은 OpenAI Agents SDK로 이어졌다 `[2차]`. 그래프 토폴로지는 LangGraph가 대표하며 방향 그래프 + 공유 상태 + 체크포인팅·내구 실행을 제공하지만 학습 곡선이 가장 가파르다 `[2차]`.

### 공유 상태 vs 메시지 전달

| 방식 | 동작 | 장점 | 단점 | 적합 토폴로지 |
|---|---|---|---|---|
| **공유 상태** | 하나의 상태 객체(스키마 정의)를 모든 에이전트가 읽고 갱신 | 전역 일관성, 체크포인트·재개 용이, 디버깅 시 상태 스냅샷 | 동시 갱신 충돌, 스키마 비대, 모든 에이전트가 전체 상태를 봄(컨텍스트 낭비·권한) | 그래프, Supervisor |
| **메시지 전달** | 에이전트 간 타입드 메시지(과업·결과·핸드오프)만 교환 | 결합도 낮음, 에이전트별 컨텍스트 최소, 조직 간 경계에 자연스러움 | 상태가 분산되어 전역 뷰 없음, 메시지 유실·순서 문제 | Handoff, Hierarchical, A2A |

실무 절충은 **공유 상태는 스키마로 최소화하고, 에이전트에게는 필요한 뷰만 투영**하는 것이다. 상태 모델링은 [08](08-state-memory-context.md).

### 위임·핸드오프 판정

"어느 워커에게", "핸드오프할까", "종합할 만큼 모였나"는 선택지가 닫힌 판정이다. 이 자리를 결정 모델(Jev / Decisions API)·분류기·규칙이 맡으면 조정 비용이 줄고 보정 확률로 "확신 낮음 → 사람" 경로를 둘 수 있다 — [11](11-decision-layer.md). Supervisor의 조정 호출이 전체 비용의 상당 부분을 차지하므로 효과가 크지만 사례는 미확인이다 `[2차]`.

### A2A: 조직 간 경계

같은 시스템 안의 하위 에이전트는 함수 호출·프레임워크 내부 메커니즘으로 충분하다. **다른 조직·벤더의 에이전트**와 연동할 때 A2A(Agent2Agent)가 표준 후보다. Google 2025-04 공개, 2025-06 Linux Foundation 이관, 100+ 기업 참여 `[2차]`. Agent Card로 능력을 공개하고 태스크 생명주기·메시지·아티팩트를 교환한다. 1.0 도달 정황(A2UI가 "A2A 1.0 통합" 언급)은 있으나 전용 발표는 미확인이다 `[2차]`. MCP(툴·데이터)와는 보완 관계다. 프로토콜 비교는 [Part 1/05](../01-foundations/05-agentic-protocols.md).

### 선택 가이드

- **단일 에이전트의 컨텍스트·역할 한계가 측정되지 않았다면** → 멀티 에이전트를 도입하지 않는다. 이유: 비용은 곱, 디버깅은 곱 이상이다
- **역할은 다르지만 순서가 고정이라면** → 워크플로우 체이닝. 이유: 에이전트 간 조정 없이 역할 분리를 얻는다
- **역할 3~6개를 중앙에서 위임·종합한다면** → Supervisor, 위임 판정은 결정 모델·규칙으로. 이유: 가장 단순한 멀티 에이전트이고 종합 지점이 하나라 품질 통제가 쉽다
- **대화 중 전문가가 자연스럽게 바뀐다면** → Handoff, 핸드오프 시 전달할 컨텍스트를 스키마로. 이유: 중앙 조정 없이 흐름이 사용자 대화를 따른다. 순환 상한 필수
- **흐름이 복잡하고 재현·체크포인트·장기 실행이 필요하다면** → 그래프 + 공유 상태. 이유: 내구 실행과 상태 스냅샷을 프레임워크가 제공한다. 학습 곡선을 감수
- **다른 조직의 에이전트와 연동한다면** → A2A + 메시지 전달. 이유: 벤더 중립 거버넌스, 능력 발견·태스크 생명주기 내장
- **판단이 어려우면** → Supervisor + 최소 공유 상태 스키마를 기본값으로. 이유: 토폴로지 중 가장 추적하기 쉽고, 필요 시 Hierarchical로 확장하거나 워커를 그래프로 바꿀 수 있다

## 설계 시 고려사항 (체크리스트)

- [ ] 단일 에이전트 기준선의 실패를 컨텍스트/역할로 분류한 기록이 있는가
- [ ] 역할 분할표에 각 에이전트의 책임·툴·컨텍스트 범위·권한이 최소로 정의되어 있는가
- [ ] 총 LLM 호출·위임 깊이·실행 시간의 상한과 상한 도달 시 폴백이 있는가
- [ ] 순환 위임·핸드오프 감지(같은 에이전트 쌍 N회)가 있는가
- [ ] 공유 상태 스키마가 정의되어 있고 에이전트별로 필요한 뷰만 투영되는가
- [ ] 핸드오프 시 전달되는 컨텍스트(사용자 의도·제약·지금까지의 결정)가 스키마로 명시되어 유실되지 않는가
- [ ] 워커 결과의 충돌·중복을 종합 전에 검사하는가
- [ ] 위임·핸드오프·종합 판정의 수단(결정 모델 / 규칙 / LLM)이 배정되어 있는가
- [ ] 상관 ID로 전체 트레이스가 묶이고 `invoke_agent` 스팬 아래 모델·툴 스팬이 중첩되는가 (원격 에이전트는 CLIENT, 인프로세스는 INTERNAL `[2차]`) — [Part 5/03](../05-cross-cutting/03-observability-tracing.md)
- [ ] 각 에이전트의 툴 실행에 규칙 게이트가 있고 에이전트 간 권한 상승이 없는가 ([12](12-guardrails-hitl.md), [Part 5/01](../05-cross-cutting/01-security-prompt-injection.md))
- [ ] A2A를 쓴다면 Agent Card 공개 범위·인증·태스크 타임아웃을 정했는가
- [ ] 단일 에이전트 대비 성공률·비용·지연을 같은 평가셋으로 `[실측]`했는가

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 비용 곱 | 에이전트 수 × 루프 수 × 조정 호출 | 상한, 조정 판정을 결정 모델·규칙으로, 워커 컨텍스트 최소화 |
| 디버깅·관측 난이도 | 실패 위치 추적에 분산 트레이싱 필수. OTel GenAI 컨벤션은 2026-10 현재 전 속성 Development 등급 `[2차]` | 상관 ID, 에이전트별 스팬, 상태 스냅샷, 트래젝토리 평가([13](13-evaluation-rag-agents.md)) |
| 순환 위임·종료 불능 | 비용 폭증, 응답 없음 | 깊이·횟수 상한, 순환 감지, 종료 판정 분리 |
| 상태 불일치 | 오래된 상태로 판단, 동시 갱신 충돌 | 스키마·버전, 단일 작성자 원칙, 체크포인트 |
| 핸드오프 컨텍스트 유실 | 사용자 의도가 중간에 사라짐 | 핸드오프 페이로드 스키마, 의도·제약을 상태에 고정 |
| 종합 품질 | 워커 결과 모순을 그냥 이어 붙임 | 충돌 검사, 종합 전 검증기([04](04-generation-grounding.md)) |
| 에이전트 간 인젝션 전파 | 한 에이전트가 오염된 툴 출력을 받으면 다른 에이전트로 전파 | 신뢰 경계 설계, 에이전트별 권한 최소화([Part 5/01](../05-cross-cutting/01-security-prompt-injection.md)) |
| 프레임워크 종속 | 토폴로지가 프레임워크 추상화에 묶임. AutoGen 유지보수 모드처럼 프레임워크 자체가 바뀜 | 역할·상태·메시지 스키마를 프레임워크 중립으로 정의 |
| A2A 성숙도 | 1.0 전용 발표 미확인, 보안은 프로토콜 밖 | 인증·권한·감사 별도 설계, 조직 간에만 사용 |
| 멀티 에이전트 벤치마크 부재 | 단일 대비 우위를 가정하기 어려움 | 자체 과업으로 `[실측]`, 기준선 유지 |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 멀티 에이전트는 **분산 시스템**이다. 단일 에이전트([06](06-agent-design-patterns.md))의 운영 설계에 더해 조정 비용, 에이전트 간 경계, 상태 일관성, 상관 추적이 추가된다. 가장 중요한 폴백은 "단일 에이전트로 되돌아가기"다. 레이어 간 종합은 [Part 5/06](../05-cross-cutting/06-operational-design-matrix.md).

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| **요청 수 × 에이전트 수 × 스텝 수** (중심 축) | 모델 API 레이트 리밋. 에이전트 5개 × 10스텝 = 요청당 50회 + Supervisor **조정 호출**. 조정 호출이 전체의 상당 비중 | 조정 판정(위임·핸드오프·종합 시점)을 결정 모델·규칙으로, 워커 동시성 상한, 요청 큐 + 비동기 응답, 에이전트별 프롬프트 캐시 | 요청 수 × Σ(에이전트별 스텝) + 조정 호출 수 |
| **에이전트 수** (역할 증가) | Supervisor 컨텍스트에 모든 워커 설명·결과가 실려 폭증, 위임 정확도 하락 | 역할 ≤ 6이면 Supervisor, 초과 시 Hierarchical(계층 ≤ 2), 워커 결과는 요약 스키마로 반환, 역할 설명은 레지스트리에서 자동 생성 | 에이전트 수(Supervisor 컨텍스트), 계층 수(지연) |
| **공유 상태 크기** | 체크포인트 쓰기·직렬화 비용, 동시 갱신 충돌 | 상태 스키마 최소화 + 에이전트별 투영 뷰, 단일 작성자 원칙, 체크포인트 외부 저장소([08](08-state-memory-context.md)) | 상태 크기 × 스텝 수 |
| **메시지·핸드오프 수** | 브로커·태스크 저장소 처리량, 핸드오프마다 컨텍스트 복사 | 핸드오프 페이로드 스키마 최소화, 메시지 큐 | 핸드오프 수 × 페이로드 크기 |
| **원격 에이전트 수** (A2A) | 원격의 지연·가용성이 내 SLO에 편입 | 원격별 타임아웃·비동기 태스크·서킷 브레이커 | 원격 에이전트 수 |

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 모델 API 다운·지연 | 특정 에이전트 중단 → 전체 지연 | 에이전트별 오류율·p95, 서킷 브레이커 열림 | 에이전트별 폴백 모델, 필수 아닌 워커(검토자 등) 생략 저하, **단일 에이전트 폴백**(Supervisor가 핵심 역할만 직접 수행) | 폴백률 10분간 50%(예시) |
| **순환 위임·핸드오프** | 종료 불능, 비용 급등 | 같은 에이전트 쌍 N회(예시 3), 위임 깊이·총 호출 상한 도달률 | 상한에서 강제 종료 → Supervisor 종합 또는 사람 인계 | 상한 도달률 3%(예시) |
| 워커 실패·타임아웃 | 종합에 구멍 | 워커별 오류율·타임아웃 | 워커 재시도(예시 1회) → 생략하고 종합에 "누락" 표시, 또는 Supervisor 직접 수행 | 워커별 오류율 10%(예시) |
| **핸드오프 실패**(대상 없음·페이로드 스키마 불합격) | 대화 끊김, 의도 유실 | 핸드오프 실패율 | 원 에이전트로 복귀 + 사용자에게 재확인. 스키마 불합격은 필수 필드만으로 1회 재시도 | 실패율 2%(예시) |
| 공유 상태 동시 갱신 충돌 | 오래된 상태로 판단, 모순 결과 | 버전 충돌 카운트 | 낙관적 잠금(버전 비교) → 재읽기·재시도 1회 → 실패 시 Supervisor 중재 | 충돌률 1%(예시) |
| 종합 시 워커 결과 모순 | 모순된 답변 | 충돌 검사 불합격률 | 충돌 주장 제거 또는 양쪽 명시, 재위임 1회 → [04](04-generation-grounding.md) 검증기 | 불합격률 급증 |
| 원격 에이전트(A2A) 다운·지연 | 외부 조회 미완 | 원격 태스크 타임아웃·오류 | 원격별 서킷 브레이커 → 내부 대체 에이전트 또는 "외부 조회 불가" 저하 | 즉시 통보(I) |
| 트레이스 상관 유실 | 실패 위치 추적 불가 | 상관 ID 없는 스팬 비율 | 예방(컨텍스트 전파 강제), 알림 | 0 초과 |

SLI 후보: 단일 에이전트 기준선 대비 성공률·비용·지연 비율, 총 LLM 호출 수 분포, 위임 깊이 분포, 상한 도달률, 핸드오프 실패율, 워커 오류율, 상태 충돌률, E2E p95. SLO 초안(예시): 상한 도달률 < 1%, 핸드오프 실패율 < 0.5%, 성공률 ≥ 단일 기준선 + 10%p — 미달이면 단일로 회귀한다. 서킷 브레이커 위치: 모델 API(에이전트별), 각 툴, 원격 A2A 에이전트별, 상태 저장소·메시지 브로커. 쓰기 행동: 멱등 키에 에이전트 ID 포함(두 에이전트가 같은 행동을 중복 실행하지 않게), 메시지 재전송은 메시지 ID로 중복 제거.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| **에이전트 역할 정의**(책임·툴·컨텍스트 범위·권한) — 설정 | 위임 정확도, 권한 경계 | 역할별 골든셋 + E2E | 토폴로지 설정, 툴 권한 |
| **토폴로지 정의**(노드·간선·위임 규칙) — 선언적 설정 | 전체 흐름 | E2E 골든셋, 트래젝토리 평가([13](13-evaluation-rag-agents.md)) | 상태·메시지 스키마 |
| 공유 상태 스키마 / 메시지·핸드오프 페이로드 스키마 | 모든 에이전트 | 스키마 호환(추가 자유, 삭제는 버전) + 구버전 체크포인트 재개 | 모든 에이전트 어댑터(롤백 단위가 큼 — 변경 절차를 무겁게) |
| 조정 판정 질문 정의·θ(위임 대상·핸드오프·종합 시점) | 조정 비용·정확도 | 판정 평가셋·보정 | 결정 모델 버전 |
| 에이전트별 시스템 프롬프트·모델 버전 | 해당 에이전트 | 역할 골든셋 → E2E | 에이전트별 호환 매트릭스(에이전트마다 모델이 달라도 됨) |
| 상한(총 호출·깊이·시간·순환) — 설정 | 비용·종료 | 상한 도달률 | — |
| Agent Card(A2A) | 외부 발견·호출 | 계약 테스트 | 인증 설정 |

기술 부채로 기록할 것: "토폴로지가 프레임워크 코드에 결합", "상태 단일 작성자 미강제", "원격 에이전트 서킷 브레이커 미구현".

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **도메인 모델** ★ 가장 빈번 | 새 에이전트·역할 추가, 역할 분할 조정 | 에이전트 인터페이스(과업 입력 스키마·결과 출력 스키마), Agent Card 형식, 상태·메시지 스키마 | 에이전트 구현 | **역할 정의·Agent Card(설정)에 등록 + 위임 판정 질문 정의 버전 상승 + 역할 골든셋. 토폴로지 코드 불변**(Supervisor는 레지스트리에서 워커 목록을 읽는다) | 위임 평가셋, Supervisor 프롬프트의 역할 설명(자동 생성) |
| **모델** | 에이전트별 LLM 교체 | `generate()` 포트, 에이전트별 호환 매트릭스 | 어댑터 | 에이전트 단위로 **한 번에 하나씩** 교체 + 역할 골든셋 + E2E 카나리 | 해당 에이전트 + 종합 품질 |
| **규칙·정책** | 에이전트별 툴 권한, 위임 허용 매트릭스, 상한 | 게이트 인터페이스, 권한 평가 인터페이스 | 규칙 세트 | 규칙 버전 + 시행일 + 권한 상승 테스트 재실행 | 게이트, 역할 정의 |
| **지식** | 워커가 쓰는 소스·툴의 결과 | 워커 결과 스키마 | 워커 내부([06](06-agent-design-patterns.md)) | 워커 어댑터 | 해당 워커만 — 멀티 에이전트의 격리 이점 |
| **사용자 환경** | 조직 개편 → 역할·승인자 변경, 다국어 | 역할 정의 형식, 승인 매트릭스 | 역할·승인자 설정 | 설정(데이터) 변경. 조직 개편이 코드 변경이 되면 설계 실패 | 승인 매트릭스, 역할 정의 |
| **프로토콜·SDK** | A2A 스펙 개정·1.0, 프레임워크 교체(AutoGen 유지보수 모드 류), MCP 개정 | **프레임워크 중립 메시지·상태 스키마**, 에이전트 포트 | A2A 어댑터, 프레임워크 런타임 어댑터 | 버전 고정 + 업그레이드 창. 토폴로지 정의는 런타임 밖에 | 어댑터 + 체크포인트 마이그레이션 |
| **토폴로지 교체** | Supervisor → Hierarchical 등 | 에이전트 인터페이스·상태 스키마 | 조정 계층 | 선언적 토폴로지 설정 변경 + E2E 섀도·카나리 | 조정 계층 전체 |

가장 자주 바뀌는 것: 에이전트 역할 정의·프롬프트(역할 추가·책임 조정, 주~월) > 조정 θ·상한 > 모델 > 토폴로지 > 프레임워크·프로토콜. 코드 밖 설정으로 둘 것: 역할 정의표, 토폴로지 선언, 위임 허용 매트릭스, 상한, 조정 θ, 에이전트별 모델 배정, Agent Card, 승인 매트릭스. 포트·어댑터 뒤에 둘 외부 의존: 모델 API(에이전트별), 결정 모델, 툴/MCP, 상태 저장소·메시지 브로커, 원격 A2A 에이전트, 프레임워크 런타임.

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성의 "탐지 신호"가 **실제로 어디서 나오는지**를 설계한다. 기준은 [Part 1/07 관측성 설계 요소](../01-foundations/07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md). 멀티 에이전트는 분산 시스템이므로 관측의 전제는 **상관 전파**다 — `turn` 아래 `invoke_agent supervisor`, 그 아래 `agent.delegate {from→to}` / `agent.handoff {from→to}`, 그 아래 워커의 `invoke_agent {worker}`(내부는 [06](06-agent-design-patterns.md) 규약)가 한 트레이스로 이어져야 하고, 원격 A2A는 상대 trace를 **링크**로 잇는다. 상관이 끊긴 스팬은 그 자체가 장애 신호다.

| 기록 대상 | 스팬 / 이벤트 (이름, 부모) | 핵심 속성 (버전 키 포함) | 지표 (→ 어느 SLI) | 샘플링 · 보존 · PII |
|---|---|---|---|---|
| 루트·상관 | `invoke_agent supervisor` (부모 `turn`) — 턴 종료 시 집계 | `agent.topology_version`, `agent.correlation_id`(= trace_id, 모든 하위 스팬·메시지 헤더에 전파), `agent.agent_count`, `agent.total_llm_calls`, `agent.coordination_calls`(Supervisor 자신의 호출), `agent.delegation_depth_max`, `agent.outcome`, `agent.degradation[]`=`single_agent_fallback`·`worker_omitted`·`remote_unavailable`, 버전 키 5종 | **총 LLM 호출 수 분포**, 조정 호출 비중, **위임 깊이 분포**, **E2E p95**, **단일 에이전트 기준선 대비 성공률·비용·지연 비율**(같은 골든셋, 비교 패널), **상관 ID 없는 스팬 비율**(수집기에서 `parent_span_id`·`correlation_id` 누락 카운트) → 트레이스 상관 유실 | 메타 전수 |
| 위임 | `agent.delegate {from→to}` (부모 `invoke_agent supervisor`) → 하위 `invoke_agent {worker}` | `agent.decision`(대상 에이전트), `agent.confidence`, `agent.decision_source`, `agent.delegation_depth`, `agent.pair_count`(같은 from→to 쌍 반복 횟수), `agent.limit_hit`(depth/calls/cycle), `agent.rules_version`(위임 허용 매트릭스), 차단 사유(not_allowed/privilege_escalation) | 위임 판정 분포·확신도 히스토그램, 순환 감지율(`pair_count` ≥ N, 예시 3), **상한 도달률**, 위임 차단률(권한 상승 시도 포함) → 순환 위임 | **전수**(샘플링 금지) |
| 워커 실행 | `invoke_agent {worker}` (부모 `agent.delegate`) | `agent.agent_id`, `agent.role_version`, 에이전트별 `agent.model_version`·`agent.prompt_version`, `agent.outcome`, `agent.retry_count`, `agent.omitted`(생략 저하), `agent.circuit_state` | 에이전트별 RED(오류율·p95·타임아웃), **워커 오류율**, 워커 생략률, 에이전트별 폴백률 → 모델 다운(에이전트별), 워커 실패·타임아웃 | 메타 전수, 워커 결과 요약은 스키마 필드만 |
| 핸드오프 | `agent.handoff {from→to}` 이벤트 쌍(요청·수락) (부모 `invoke_agent supervisor` 또는 원 에이전트) | `agent.message_id`, 페이로드 스키마 버전·`agent.payload_hash`·크기, 스키마 검증 결과, `agent.payload_scan`(인젝션 검사 결과), `agent.handoff_result`(ok/target_missing/schema_fail/returned_to_origin) | **핸드오프 실패율**(사유별), 원 에이전트 복귀 비율, 페이로드 크기 분포 → 핸드오프 실패 | 메타·검사 결과 전수, 페이로드 본문 opt-in(마스킹), 실패 건 전수 |
| 공유 상태 | 이벤트 `state.read` / `state.write` (부모 해당 에이전트 스팬) | `agent.state_version`, `agent.writer_agent_id`(단일 작성자 검증), `agent.conflict`(낙관적 잠금 실패), 재시도·Supervisor 중재 여부, `agent.checkpoint_id` | **상태 충돌률**, 재시도·중재 비율, 작성자 분포(단일 작성자 위반 건수), 상태 저장소·브로커 RED → 동시 갱신 충돌 | 전수, 상태 본문은 저장소에만 |
| 종합 | `agent.synthesize` (부모 `invoke_agent supervisor`) + 모델 호출 자식(`gen_ai.*`) | 워커 결과 수·누락 수, `agent.conflict_check`(pass/fail), 재위임 여부, `agent.evidence_ids[]`(워커별 근거 합집합), 이후 [04](04-generation-grounding.md) 검증 스팬으로 연결 | 충돌 검사 불합격률, 누락 포함 종합 비율, 재위임률 → 워커 결과 모순 | 메타 전수, 불합격 건 본문 전수 |
| 원격 A2A | `agent.delegate remote {agent}` (span kind CLIENT) + 상대 trace 링크, 비동기 완료는 결과 수신 시 링크 | 상대 에이전트 ID·Agent Card 버전, `agent.remote_task_id`, 타임아웃·`agent.circuit_state`, 인증 결과 | 원격별 오류율·p95·타임아웃, 원격 서킷 열림 건수, 비동기 완료 지연 → 원격 다운·지연 | 메타 전수, 응답은 요약 스키마만 |

| 알림 | 조건 (예시) | 심각도 | 런북 (첫 3단계) |
|---|---|---|---|
| 에이전트 장애·폴백 | 특정 에이전트 폴백률 10분간 50% 초과, 또는 워커 오류율 10% 초과 | P1 | ① 어느 에이전트·모델인지 에이전트별 RED로 확인 ② 생략된 워커가 필수 역할인지 확인, 필수면 **단일 에이전트 폴백 플래그** 활성화 ③ 누락 표시가 종합·사용자 고지에 반영되는지 확인 |
| 순환·상한 도달 | `agent.limit_hit` 비율 3% 초과, 또는 `pair_count` ≥ 3 비율 급증 | P2 | ① 상위 반복 쌍(from→to)과 위임 확신도 확인 ② 위임 질문 정의·토폴로지·역할 정의의 최근 버전 변경 확인 ③ 깊이·총 호출 상한 하향, 사람 인계 큐 적체 확인 |
| 핸드오프 실패 | 핸드오프 실패율 2% 초과 | P2 | ① 사유 분포 — target_missing(레지스트리 불일치) vs schema_fail(스키마 버전 불일치) ② 역할 레지스트리·페이로드 스키마 버전을 에이전트별로 대조 ③ 원 에이전트 복귀와 사용자 재확인이 동작하는지 확인 |
| 상태 충돌·종합 모순 | 상태 충돌률 1% 초과, 또는 충돌 검사 불합격률 급증 | P2 | ① 작성자 분포에서 단일 작성자 위반 확인 ② 상태 스키마 버전·낙관적 잠금 재시도 설정 확인 ③ Supervisor 중재·재위임 비율과 [04](04-generation-grounding.md) 검증기 거부율 교차 확인 |
| 상관 유실·원격 장애 | 상관 ID 없는 스팬 1건 이상, 또는 원격 A2A 서킷 열림 | P2 (원격은 사업 책임자 통보 I) | ① 유실 스팬의 발생 에이전트·전파 경로(메시지 헤더·A2A 헤더) 확인 ② 컨텍스트 전파 강제가 빠진 어댑터 식별 ③ 원격이면 내부 대체 에이전트·"외부 조회 불가" 저하 발동 확인 |

대시보드에서 이 단계를 보는 뷰: ① E2E — **멀티 vs 단일 기준선 비교 패널**(성공률·비용·지연 비율), 폴백·저하율 / ② Reasoning 패널 — 에이전트별 RED, 위임 깊이 분포, 핸드오프 실패율, 상태 충돌률, 트레이스 상관 유실률 / ③ 비용·판정 분포 — 조정 호출 비중(Supervisor 호출 ÷ 총 호출), 에이전트별 비용 분해, 위임 확신도 히스토그램, 결정 소스 분포.
감사 추적으로 넘기는 필드(관측 로그와 분리): 상관 ID, 에이전트 ID·역할 정의 버전, 메시지 ID·핸드오프 페이로드 해시, 위임 판정·확신도·수단·깊이, 에이전트별 프롬프트·모델 버전, 툴 호출·게이트 판정·규칙 버전, 승인자·시각, 상태 버전(체크포인트 ID), 충돌 검사 결과, 근거 ID, 원격 A2A 태스크 ID — 거버넌스 접점 표와 동일.
이 단계의 관측이 없으면 못 보는 장애: **조정 비용의 잠식** — 성공률은 단일과 같은데 Supervisor의 조정 호출이 전체의 40%(예시)로 불어 멀티 에이전트가 단일보다 비싸진 상태. 에이전트별 스팬과 단일 기준선 비교 패널 없이 총 비용만 보면 "트래픽이 늘었나 보다"로 넘어간다. 그리고 **위임을 통한 권한 상승** — 낮은 등급 에이전트가 높은 등급 에이전트에 위임해 행동이 실행되어도 각 에이전트의 게이트는 개별적으로 통과이므로, `agent.delegate`에 위임 매트릭스 판정을 남기지 않으면 트레이스 어디에도 "넘지 말아야 할 경계를 넘었다"는 기록이 없다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | 에이전트 집합 중 **최고 등급 툴이 전체 등급**. 읽기 전용 조사 멀티 에이전트 1~2, 행동 포함 3~4. 낮은 등급 에이전트가 높은 등급 에이전트에 위임해 행동을 유발하는 **권한 상승 금지** — 위임 허용 매트릭스로 차단. 등급 5는 자동 실행 금지 |

| 게이트 출력과 판정 수단 | 통과 / 차단(위임 불허·권한 상승·순환) / 승인 요청(등급 3 이상 행동 — 어느 에이전트가 요청했든 승인자는 사람, 승인 카드에 전체 트레이스 요약, 만료 = 거부) / 저하(상한 → 단일 에이전트 폴백·부분 종합). 권한·위임 매트릭스·상한은 규칙만, 위임 대상·종합 시점은 결정 모델·분류기, 종합 내용은 LLM |
| 소유자 (A) | 역할 정의·토폴로지: 아키텍트(A), AI 엔지니어(R). 에이전트별 툴 권한: 서비스 소유자(A). 위임 매트릭스·에이전트 간 경계 규칙: 보안 책임자(A). A2A 외부 연동: 사업 책임자(A), 법무(C) |
| 감사 추적에 남길 필드 | 상관 ID(요청 전체), 에이전트 ID·역할 정의 버전, **에이전트 간 메시지 ID**·핸드오프 페이로드 해시, 위임 판정·확신도·수단, 위임 깊이, 에이전트별 프롬프트·모델 버전, 툴 호출·게이트 판정·규칙 버전, 승인자·시각, 상태 버전(체크포인트 ID), 종합 시 충돌 검사 결과, 근거 ID, 원격 A2A 태스크 ID |

### 운영 준비도 체크
- [ ] 단일 에이전트 폴백(Supervisor 직접 수행 또는 단일 루프 재실행)이 피처 플래그로 배포 없이 켜지는가
- [ ] 순환 위임·깊이·총 호출 상한이 설정으로 있고 상한 도달 시 종합·인계 경로를 실행해 봤는가
- [ ] 핸드오프 페이로드 스키마가 있고 실패 시 원 에이전트 복귀가 동작하는가
- [ ] 상관 ID가 모든 에이전트·툴 스팬에 전파되고 유실률이 SLI로 측정되는가
- [ ] 새 에이전트 추가가 역할 정의·Agent Card 등록 + 판정 질문 정의 버전 상승만으로 끝나고 토폴로지 코드 변경이 없는가
- [ ] 위임 허용 매트릭스가 규칙으로 강제되어 에이전트 간 권한 상승이 불가능한가(테스트 포함)
- [ ] 멀티 에이전트 성공률·비용·지연을 단일 기준선과 같은 평가셋으로 비교하고, 미달 시 회귀하는 기준이 있는가
- [ ] 트레이스에 메시지 ID·위임 판정·에이전트별 버전 키가 있어 "어느 에이전트의 어느 스텝에서 틀렸나"를 재구성할 수 있는가
- [ ] `agent.delegate`에 위임 허용 매트릭스 판정·`pair_count`·깊이가 전수 기록되어 권한 상승 시도와 순환을 트레이스에서 셀 수 있는가
- [ ] 단일 에이전트 기준선 비교 패널(성공률·비용·지연 비율, 조정 호출 비중)이 대시보드 ①·③에 있고 회귀 기준과 연결되어 있는가
