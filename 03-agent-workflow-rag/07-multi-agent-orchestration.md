# 멀티 에이전트 오케스트레이션

> **범위**: Supervisor / Hierarchical / Handoff 토폴로지, A2A, 상태 공유
> **시각화**: [`assets/html/multi-agent-topologies.html`](../assets/html/multi-agent-topologies.html)

## 요약 (3줄)

1. 멀티 에이전트는 **단일 에이전트의 한계가 측정으로 확인된 뒤**의 선택이다. 한계는 두 가지뿐이다 — 컨텍스트(한 루프에 다 못 넣음)와 역할(한 프롬프트가 상충하는 역할을 동시에 못 함). 둘 다 아니면 멀티 에이전트는 과잉이다.
2. 토폴로지는 네 가지로 정리된다. **Supervisor**(중앙이 위임·종합), **Hierarchical**(Supervisor의 다층화), **Handoff/Swarm**(에이전트가 다음 에이전트에게 제어를 넘김), **그래프**(명시적 노드·간선과 공유 상태). 제어 흐름을 누가 쥐는지와 상태를 어떻게 공유하는지가 차이다.
3. 비용은 LLM 호출 수의 곱이고, 디버깅 난이도는 에이전트 수의 곱 이상이다. 조직 간 연동은 A2A(Linux Foundation 이관, 2025-06)가 표준 후보지만 1.0 전용 발표는 미확인이다 `[2차]`.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 에이전트 역할 분할표(각 에이전트의 책임·툴·컨텍스트 범위) ② 토폴로지와 제어 흐름(누가 누구를 호출·위임·핸드오프하는가) ③ 상태 공유 방식(공유 상태 스키마 또는 메시지 스키마) ④ 조직 간 경계가 있으면 A2A Agent Card와 태스크 생명주기 ⑤ 전체 트레이스 상관 ID 체계. 품질 기준은 단일 에이전트 대비 성공률·비용·지연의 `[실측]` 차이 |
| **언제** (When) | 단일 에이전트([06](06-agent-design-patterns.md))가 컨텍스트 한계 또는 역할 상충으로 실패하는 것이 측정됐을 때. 생략 가능: 과업이 하나의 컨텍스트 윈도우와 하나의 역할로 처리됨. 미룰 수 있음: 역할은 다르지만 순차 실행이면 워크플로우 체이닝([05](05-workflow-vs-agent.md))으로 충분. A2A는 다른 조직·벤더의 에이전트와 연동할 때만 |
| **어떻게** (How) | ① 단일 에이전트 실패를 컨텍스트/역할로 분류 → ② 역할 분할표 작성, 각 에이전트의 툴·컨텍스트를 최소로 → ③ 제어 흐름이 중앙 집중 가능하면 Supervisor, 역할 수가 많으면 Hierarchical, 대화형으로 제어가 자연스럽게 넘어가면 Handoff, 흐름이 복잡하고 재현·체크포인트가 필요하면 그래프 → ④ 상태 공유 방식 결정(공유 상태 vs 메시지) → ⑤ 위임·핸드오프 판정 수단 배정(결정 모델·규칙·LLM) → ⑥ 상관 ID로 전체 트레이스, 상한(총 호출·깊이·시간) → ⑦ 단일 에이전트 기준선 대비 `[실측]` |
| **왜** (Why) | 멀티 에이전트를 먼저 도입하면 ① 비용이 에이전트 수 × 루프 수로 곱해지고 ② 실패가 어느 에이전트의 어느 스텝인지 추적하려면 분산 트레이싱이 필요하며 ③ 에이전트 간 상태 불일치·메시지 유실·순환 위임 같은 분산 시스템 문제가 LLM의 비결정성과 결합한다. 반대로 컨텍스트·역할 한계를 단일 에이전트로 밀어붙이면 품질이 스텝이 늘수록 떨어진다 |

## 문제와 맥락

단일 에이전트 루프가 벽에 부딪히는 지점은 두 가지다. 첫째, **컨텍스트**. 다중 소스 조사·다중 파일 수정처럼 중간 산출물이 많은 과업은 한 루프의 컨텍스트에 다 들어가지 않고, 들어가더라도 뒤로 갈수록 품질이 떨어진다. 둘째, **역할**. "엄격한 검토자"와 "창의적 작성자"를 한 프롬프트에 넣으면 둘 다 약해진다. 멀티 에이전트는 컨텍스트를 분할하고 역할을 분리하는 수단이다.

그런데 멀티 에이전트는 분산 시스템이다. LLM의 비결정성 위에 분산 시스템의 문제가 얹힌다.

- **순환 위임**: A가 B에게, B가 다시 A에게. 상한 없이는 종료 불능
- **상태 불일치**: 공유 상태를 두 에이전트가 동시에 갱신, 또는 메시지로 전달한 상태가 오래됨
- **책임 공백**: 핸드오프 후 원래 에이전트의 컨텍스트가 사라져 사용자 의도가 유실
- **종합 실패**: 워커 결과가 서로 모순인데 Supervisor가 그냥 이어 붙임
- **비용 폭발**: 에이전트 5개가 각각 ReAct 10스텝이면 50회 + 조정 호출
- **추적 불능**: 어느 에이전트의 어느 스텝에서 틀렸는지 트레이스가 분산

이 문제들이 "멀티 에이전트가 과잉인가"를 묻는 이유다. 사람 조직에 비유하면 직관적이지만, 사람 조직도 조정 비용이 크다는 점을 잊기 쉽다.

## 핵심 개념

### 4가지 토폴로지

시각화: [`multi-agent-topologies.html`](../assets/html/multi-agent-topologies.html).

| 토폴로지 | 제어 흐름 | 상태 공유 | 적합 | 부적합 | 고유 실패 |
|---|---|---|---|---|---|
| **Supervisor** | 중앙 에이전트가 워커에게 위임하고 결과를 받아 종합. 워커끼리는 통신 안 함 | Supervisor가 상태 보유, 워커는 과업 단위 입출력 | 역할 3~6개, 중앙 조정이 자연스러움, 종합 품질 중요 | 역할 수 많음(Supervisor 컨텍스트 폭증), 워커 간 직접 협업 필요 | Supervisor가 병목·단일 실패점, 위임 오판 |
| **Hierarchical** | Supervisor의 Supervisor. 팀 단위로 묶어 다층화 | 계층별 상태, 위로 요약 전달 | 역할 7개 이상, 도메인별 팀 구분 명확 | 과업이 작음, 계층 간 정보 손실 민감 | 계층마다 요약 손실, 지연 누적, 깊이 폭발 |
| **Handoff (Swarm)** | 현재 에이전트가 다음 에이전트에게 **제어를 넘김**. 중앙 없음 | 대화 히스토리(또는 그 일부)가 함께 이동 | 대화형, 단계가 자연스럽게 전문가를 바꿈(접수→기술→결제) | 병렬 처리, 종합 필요, 복잡 흐름 | 순환 핸드오프, 컨텍스트 유실, 흐름 추적 어려움 |
| **그래프** | 노드(에이전트·함수)와 간선(조건)을 명시, 엔진이 실행 | **공유 상태** 객체를 모든 노드가 읽고 씀 | 흐름 복잡, 재현·체크포인트·내구 실행 필요 | 흐름이 단순(과잉), 학습 곡선 부담 | 상태 스키마 비대, 간선 조건 디버깅 |

Supervisor와 Orchestrator-Worker([06](06-agent-design-patterns.md))는 같은 구조다. 차이는 워커가 단일 LLM 호출인지(Orchestrator-Worker) 자체 루프를 가진 에이전트인지(Supervisor)다. Handoff는 OpenAI Swarm이 널리 알린 패턴이고 Swarm은 OpenAI Agents SDK로 이어졌다 `[2차]`. 그래프 토폴로지는 LangGraph가 대표하며 방향 그래프 + 공유 상태 + 체크포인팅·내구 실행을 제공하지만 학습 곡선이 가장 가파르다 `[2차]`.

### 공유 상태 vs 메시지 전달

| 방식 | 동작 | 장점 | 단점 | 적합 토폴로지 |
|---|---|---|---|---|
| **공유 상태** | 하나의 상태 객체(스키마 정의)를 모든 에이전트가 읽고 갱신 | 전역 일관성, 체크포인트·재개 용이, 디버깅 시 상태 스냅샷 | 동시 갱신 충돌, 스키마 비대, 모든 에이전트가 전체 상태를 봄(컨텍스트 낭비·권한) | 그래프, Supervisor |
| **메시지 전달** | 에이전트 간 타입드 메시지(과업·결과·핸드오프)만 교환 | 결합도 낮음, 에이전트별 컨텍스트 최소, 조직 간 경계에 자연스러움 | 상태가 분산되어 전역 뷰 없음, 메시지 유실·순서 문제 | Handoff, Hierarchical, A2A |

실무 절충은 **공유 상태는 스키마로 최소화하고, 에이전트에게는 필요한 뷰만 투영**하는 것이다. 상태 모델링은 [08](08-state-memory-context.md).

### 위임·핸드오프 판정

"어느 워커에게", "핸드오프할까", "종합할 만큼 모였나"는 선택지가 닫힌 판정이다. 이 자리를 결정 모델(Jev / Decisions API)·분류기·규칙이 맡으면 조정 비용이 줄고 보정 확률로 "확신 낮음 → 사람" 경로를 둘 수 있다 — [11](11-decision-layer.md). Supervisor의 조정 호출이 전체 비용의 상당 부분을 차지하므로 효과가 크지만 사례는 미확인이다 `[2차]`.

### A2A: 조직 간 경계

같은 시스템 안의 하위 에이전트는 함수 호출·프레임워크 내부 메커니즘으로 충분하다. **다른 조직·벤더의 에이전트**와 연동할 때 A2A(Agent2Agent)가 표준 후보다. Google 2025-04 공개, 2025-06 Linux Foundation 이관, 100+ 기업 참여 `[2차]`. Agent Card로 능력을 공개하고 태스크 생명주기·메시지·아티팩트를 교환한다. 1.0 도달 정황(A2UI가 "A2A 1.0 통합" 언급)은 있으나 전용 발표는 미확인이다 `[2차]`. MCP(툴·데이터)와는 보완 관계다. 프로토콜 비교는 [Part 1/05](../01-foundations/05-agentic-protocols.md).

### 선택 가이드

- **단일 에이전트의 컨텍스트·역할 한계가 측정되지 않았다면** → 멀티 에이전트를 도입하지 않는다. 이유: 비용은 곱, 디버깅은 곱 이상이다
- **역할은 다르지만 순서가 고정이라면** → 워크플로우 체이닝. 이유: 에이전트 간 조정 없이 역할 분리를 얻는다
- **역할 3~6개를 중앙에서 위임·종합한다면** → Supervisor, 위임 판정은 결정 모델·규칙으로. 이유: 가장 단순한 멀티 에이전트이고 종합 지점이 하나라 품질 통제가 쉽다
- **대화 중 전문가가 자연스럽게 바뀐다면** → Handoff, 핸드오프 시 전달할 컨텍스트를 스키마로. 이유: 중앙 조정 없이 흐름이 사용자 대화를 따른다. 순환 상한 필수
- **흐름이 복잡하고 재현·체크포인트·장기 실행이 필요하다면** → 그래프 + 공유 상태. 이유: 내구 실행과 상태 스냅샷을 프레임워크가 제공한다. 학습 곡선을 감수
- **다른 조직의 에이전트와 연동한다면** → A2A + 메시지 전달. 이유: 벤더 중립 거버넌스, 능력 발견·태스크 생명주기 내장
- **판단이 어려우면** → Supervisor + 최소 공유 상태 스키마를 기본값으로. 이유: 토폴로지 중 가장 추적하기 쉽고, 필요 시 Hierarchical로 확장하거나 워커를 그래프로 바꿀 수 있다

## 설계 시 고려사항 (체크리스트)

- [ ] 단일 에이전트 기준선의 실패를 컨텍스트/역할로 분류한 기록이 있는가
- [ ] 역할 분할표에 각 에이전트의 책임·툴·컨텍스트 범위·권한이 최소로 정의되어 있는가
- [ ] 총 LLM 호출·위임 깊이·실행 시간의 상한과 상한 도달 시 폴백이 있는가
- [ ] 순환 위임·핸드오프 감지(같은 에이전트 쌍 N회)가 있는가
- [ ] 공유 상태 스키마가 정의되어 있고 에이전트별로 필요한 뷰만 투영되는가
- [ ] 핸드오프 시 전달되는 컨텍스트(사용자 의도·제약·지금까지의 결정)가 스키마로 명시되어 유실되지 않는가
- [ ] 워커 결과의 충돌·중복을 종합 전에 검사하는가
- [ ] 위임·핸드오프·종합 판정의 수단(결정 모델 / 규칙 / LLM)이 배정되어 있는가
- [ ] 상관 ID로 전체 트레이스가 묶이고 `invoke_agent` 스팬 아래 모델·툴 스팬이 중첩되는가 (원격 에이전트는 CLIENT, 인프로세스는 INTERNAL `[2차]`) — [Part 5/03](../05-cross-cutting/03-observability-tracing.md)
- [ ] 각 에이전트의 툴 실행에 규칙 게이트가 있고 에이전트 간 권한 상승이 없는가 ([12](12-guardrails-hitl.md), [Part 5/01](../05-cross-cutting/01-security-prompt-injection.md))
- [ ] A2A를 쓴다면 Agent Card 공개 범위·인증·태스크 타임아웃을 정했는가
- [ ] 단일 에이전트 대비 성공률·비용·지연을 같은 평가셋으로 `[실측]`했는가

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 비용 곱 | 에이전트 수 × 루프 수 × 조정 호출 | 상한, 조정 판정을 결정 모델·규칙으로, 워커 컨텍스트 최소화 |
| 디버깅·관측 난이도 | 실패 위치 추적에 분산 트레이싱 필수. OTel GenAI 컨벤션은 2026-10 현재 전 속성 Development 등급 `[2차]` | 상관 ID, 에이전트별 스팬, 상태 스냅샷, 트래젝토리 평가([13](13-evaluation-rag-agents.md)) |
| 순환 위임·종료 불능 | 비용 폭증, 응답 없음 | 깊이·횟수 상한, 순환 감지, 종료 판정 분리 |
| 상태 불일치 | 오래된 상태로 판단, 동시 갱신 충돌 | 스키마·버전, 단일 작성자 원칙, 체크포인트 |
| 핸드오프 컨텍스트 유실 | 사용자 의도가 중간에 사라짐 | 핸드오프 페이로드 스키마, 의도·제약을 상태에 고정 |
| 종합 품질 | 워커 결과 모순을 그냥 이어 붙임 | 충돌 검사, 종합 전 검증기([04](04-generation-grounding.md)) |
| 에이전트 간 인젝션 전파 | 한 에이전트가 오염된 툴 출력을 받으면 다른 에이전트로 전파 | 신뢰 경계 설계, 에이전트별 권한 최소화([Part 5/01](../05-cross-cutting/01-security-prompt-injection.md)) |
| 프레임워크 종속 | 토폴로지가 프레임워크 추상화에 묶임. AutoGen 유지보수 모드처럼 프레임워크 자체가 바뀜 | 역할·상태·메시지 스키마를 프레임워크 중립으로 정의 |
| A2A 성숙도 | 1.0 전용 발표 미확인, 보안은 프로토콜 밖 | 인증·권한·감사 별도 설계, 조직 간에만 사용 |
| 멀티 에이전트 벤치마크 부재 | 단일 대비 우위를 가정하기 어려움 | 자체 과업으로 `[실측]`, 기준선 유지 |
