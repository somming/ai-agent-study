# 상태·메모리·컨텍스트 엔지니어링

> **범위**: 단기/장기 메모리, 메모리 프레임워크 비교, compaction, no-memory 베이스라인 평가
> 에이전트 실행 상태의 모델링(체크포인팅·내구 실행), 세션 안팎의 메모리 계층, 매 호출의 컨텍스트 조립 규칙까지 다룬다. 컨텍스트 예산의 구성 요소 자체는 [Part 1/01](../01-foundations/01-llm-fundamentals.md), 메모리 생태계의 트렌드 심화는 [Part 6/agent-memory](../06-trends/agent-memory.md), 컨텍스트 엔지니어링 트렌드는 [Part 6/context-engineering](../06-trends/context-engineering.md).

## 요약 (3줄)

1. 상태(state)·메모리(memory)·컨텍스트(context)는 서로 다른 것이다. 상태는 실행 그래프가 **지금 어디에** 있는지, 메모리는 세션을 넘어 **무엇을 기억**할지, 컨텍스트는 **이번 호출에 무엇을 넣을지**다. 셋을 "대화 히스토리 리스트" 하나로 뭉개면 셋 다 망가진다.
2. 컨텍스트 엔지니어링(context engineering)은 무엇을 넣을지보다 **무엇을 뺄지**의 설계다. 넣는 것은 쉽고, 빼는 결정에만 규칙·요약·지연 로딩이 필요하다.
3. 메모리는 **no-memory 베이스라인 대비**로만 채택한다. MemTrapBench에서 메모리 프레임워크 5종 모두가 no-memory 베이스라인보다 나빴다는 보고가 있다 `[2차]`.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 타입드 상태 스키마와 체크포인트 정책 ② 메모리 계층별 저장소·수명·쓰기 규칙 ③ 매 호출의 컨텍스트 조립 규칙(예산 배분, 필터, 요약, 지연 로딩) ④ no-memory 베이스라인을 포함한 메모리 평가셋 |
| **언제** (When) | 상태 모델링은 **다중 턴 또는 다중 단계가 있으면 항상**. 체크포인팅은 HITL 대기·장기 실행·재시도가 있을 때 필수. 장기 메모리는 "같은 사용자가 반복 방문하고 이전 맥락이 과업 품질을 바꾼다"가 확인된 뒤에만. 단일 턴 QA라면 이 페이지의 컨텍스트 조립 절만 적용 |
| **어떻게** (How) | ① 실행 그래프의 상태 필드를 타입으로 정의(입력, 현재 단계, 중간 산출물, 툴 이력, 보류 승인, 예산 소비) → ② 노드 전이마다 체크포인트, 재개·분기 경로 확인 → ③ 컨텍스트 예산을 구성 요소별로 배분하고 "뺄 것" 규칙 작성 → ④ compaction 전략 선택(요약·승격·외부화) → ⑤ 장기 메모리는 no-memory 대비 `[실측]` 후 채택 → ⑥ 상태·메모리 변화를 트레이스에 기록 |
| **왜** (Why) | 상태가 암묵적이면 재시작·재시도·HITL 대기가 불가능하고 디버깅은 로그 추측이 된다. 컨텍스트를 빼지 않으면 턴마다 비용이 누적되고 중간 정보가 묻힌다(Lost in the Middle `[검증]`). 메모리를 검증 없이 넣으면 이전 과업의 프레임에 모델이 고착되어 **없는 것보다 나빠질 수 있다** `[2차]` |

## 문제와 맥락

"LLM에 대화 히스토리를 전부 넣는다"는 가장 단순한 구현은 네 가지 증상을 낳는다. ① 턴이 길어지면 초반 지시를 잊거나 중간 근거를 놓친다. ② 프로세스가 죽거나 사람 승인을 기다리는 동안 상태를 잃어 처음부터 다시 한다. ③ 비용과 지연이 턴 수에 비례해 증가한다. ④ 멀티 에이전트에서 각 에이전트가 서로 다른 "현재 상황"을 본다.

여기에 2025~2026년에 새 증상이 추가됐다. ⑤ 장기 메모리를 붙였더니 **이전 과업의 기억이 새 과업을 오염**시킨다. 벤치마크 점수(LoCoMo, LongMemEval)는 "기억을 잘 회상하는가"를 재지만, 운영에서 중요한 것은 "기억이 과업을 개선하는가"이고 둘은 다르다.

## 핵심 개념

### 세 층의 구분

| 층 | 질문 | 수명 | 저장 위치 | 소유자 |
|---|---|---|---|---|
| **상태** (state) | 실행이 어디까지 왔고 무엇을 들고 있는가 | 한 실행(run) | 체크포인트 저장소 | 오케스트레이터 |
| **메모리** (memory) | 세션을 넘어 무엇을 기억하는가 | 사용자·조직 단위, 영속 | 메모리 저장소(벡터·그래프·KV) | 메모리 서비스 |
| **컨텍스트** (context) | 이번 호출에 무엇을 넣는가 | 한 LLM 호출 | 없음(매번 조립) | 컨텍스트 조립기 |

상태는 코드가 읽고, 컨텍스트는 모델이 읽는다. 상태의 일부만 컨텍스트로 투영(projection)하는 것이 설계의 핵심이다.

### 상태 모델링: 체크포인팅과 내구 실행

- **타입드 상태 스키마**: 히스토리 배열이 아니라 필드다. 최소 구성은 `입력`, `현재 노드`, `중간 산출물`, `툴 호출 이력(요약)`, `보류 중 승인`, `예산 소비(토큰·비용·시간)`, `재시도 횟수`
- **체크포인트**(checkpoint): 노드 전이마다 상태 스냅샷을 저장. 효과는 네 가지 — 재개(resume), 분기(fork, 같은 지점에서 다른 경로 실험), 시간 여행 디버깅, HITL 대기 중 프로세스 종료 허용. LangGraph가 방향 그래프 + 공유 상태 위에 체크포인팅·내구 실행을 제공하는 대표 사례다 `[2차]`
- **내구 실행**(durable execution): 프로세스가 죽어도 마지막 체크포인트에서 이어 간다. 툴 호출이 부수효과를 가지면 재개 시 중복 실행 위험이 있으므로 [09](09-tools-and-mcp.md)의 멱등성 설계와 함께 간다. MCP 2026-07-28 개정의 Tasks 확장은 장기 실행 툴 쪽의 대응물이다 `[2차]`
- **공유 상태 vs 메시지**: 멀티 에이전트에서 상태를 공유 저장소로 둘지 메시지로 넘길지는 [07](07-multi-agent-orchestration.md)

### 메모리 계층

| 층 | 내용 | 쓰기 시점 | 읽기 방식 | 주의 |
|---|---|---|---|---|
| 작업 메모리 | 현재 턴의 컨텍스트 윈도우 | 매 호출 | 전부 | 예산의 대상 |
| 세션(단기) 메모리 | 대화 히스토리, 중간 요약 | 매 턴 | 최근 N턴 + 요약 | compaction 대상 |
| 장기 — 의미(semantic) | 사용자 선호·사실·설정 | 턴 종료 후 추출 | 질의 관련도 기반 k개 | 충돌·갱신 규칙 필요 |
| 장기 — 에피소드(episodic) | 과거 과업의 경과·결과 | 과업 종료 후 | 유사 과업 조회 | **MemTrap 위험이 가장 큰 층** |
| 장기 — 절차(procedural) | 학습된 작업 방식, 성공한 툴 시퀀스 | 평가 통과 후 | 과업 유형별 | 프롬프트·스킬로 승격 검토 |
| 운영 지식 | 조직 문서·데이터·그래프 | 파이프라인 | RAG | 메모리가 아니라 [Part 2](../02-data-pipeline/00-overview.md)의 영역 |

### 메모리 프레임워크의 두 유형

메모리 생태계는 **대화 컨텍스트용**과 **운영 지식용**으로 분화하고 있다 `[2차]`. 분류는 벤더의 자기 설명을 따른 것이며, 경계는 흐리다.

- **대화 컨텍스트용**: 사용자별 선호·사실을 턴에서 추출해 갱신하고 다음 세션에 주입. Mem0가 LoCoMo·LongMemEval·BEAM을 표준 벤치마크로 삼아 결과를 보고한다 `[벤더]`. Letta는 에이전트가 자기 메모리 블록을 툴로 읽고 쓰는 접근으로 설명된다 `[벤더]`
- **운영 지식용**: 문서·데이터를 그래프·시맨틱 레이어로 만들어 에이전트가 조회. cognee가 이 계열로 소개된다 `[벤더]`. 실질적으로 Part 2의 지식그래프 구축([Part 2/05](../02-data-pipeline/05-knowledge-graph-construction.md))과 겹치므로, 이미 파이프라인이 있다면 중복 도입을 피한다

### 벤치마크와 MemTrapBench

- LoCoMo, LongMemEval, BEAM은 장기 대화에서의 **회상 정확도**를 잰다. 표준화는 진행 중이나 보고 주체가 벤더인 경우가 많다 `[벤더]`
- **MemTrapBench**는 다른 질문을 던진다. "관련 있어 보이는 기억이 과업을 **해치는가**." 결과는 메모리 프레임워크 5종 모두 no-memory 베이스라인보다 나빴고, 원인은 관련 기억이 이전 과업의 프레임에 모델을 고착시킨 것이다 `[2차]`
- **설계 원칙**: 메모리 평가셋에는 "기억이 도움되는 케이스"(선호 회상, 이어 하기)와 "기억이 방해되는 케이스"(과업 전환, 이전 결정 번복, 유사하지만 다른 요청)를 **둘 다** 넣고, no-memory 구성을 항상 비교군으로 둔다. 후자에서 지면 메모리를 끄거나 주입 조건을 좁힌다

### compaction·요약 전략

| 전략 | 동작 | 장점 | 비용 |
|---|---|---|---|
| 슬라이딩 윈도우 | 최근 N턴만 유지 | 단순 | 오래된 지시·제약 소실 |
| 재귀 요약 | 오래된 구간을 요약으로 교체, 요약을 다시 요약 | 토큰 상한 유지 | 요약 LLM 비용, 세부 손실, 요약 오류 누적 |
| **구조화 상태로 승격** | 히스토리에서 결정·제약·수집된 값을 상태 필드로 옮기고 원문 제거 | 손실 없이 압축, 코드가 검증 가능 | 상태 스키마 설계 |
| 툴 출력 외부화 | 큰 툴 결과를 저장소에 두고 컨텍스트에는 요약 + 참조 ID | 가장 큰 토큰 절감 | 모델이 필요 시 다시 조회하는 툴 필요 |
| 선택적 재주입 | 현재 질의와 관련된 과거 턴만 검색해 주입 | 긴 세션에 효과 | 세션 내 검색 인덱스 |

기본값은 **구조화 상태 승격 + 툴 출력 외부화**다. 요약은 그 위에 보조로 쓴다. 요약만으로 compaction하면 "요약이 틀렸을 때" 복구 수단이 없다.

### 컨텍스트 엔지니어링: 무엇을 뺄지

Google ADK는 세션·메모리·툴 출력·아티팩트를 구조화된 뷰로 조립하고, 자동 요약·무관 이벤트 필터·지연 로딩·토큰 추적을 제공한다고 설명한다 `[벤더]`. 프레임워크를 쓰지 않더라도 같은 네 가지가 설계 항목이다.

| 뺄 대상 | 규칙 | 대체 |
|---|---|---|
| 완료된 서브태스크의 중간 로그 | 결과만 남긴다 | 상태 필드 |
| 실패한 툴 호출 원문 | 1회는 유지(재시도 근거), 이후 요약 | "툴 X 실패: 사유 Y" 한 줄 |
| 현재 경로와 무관한 툴 정의 | 라우팅 후 관련 툴만 노출 | [09](09-tools-and-mcp.md) 툴 라우팅 |
| 오래된 검색 결과 | 질의가 바뀌면 제거 | 필요 시 재검색 |
| 대용량 아티팩트(파일·표) | 참조 ID + 요약 | 지연 로딩 툴 |
| 관련도 낮은 장기 기억 | 임계값 미만은 주입 안 함 | — |

예산 배분의 출발점은 [Part 1/01](../01-foundations/01-llm-fundamentals.md)의 구성 요소 표다. 각 요소에 상한을 두고, 상한 초과 시 어느 요소를 먼저 줄일지 우선순위를 코드로 정한다.

## 아키텍처 / 파이프라인

```
턴 시작
  ─▶ [상태 로드: 마지막 체크포인트]
  ─▶ [메모리 조회: 질의 관련 장기 기억 k개, 관련도 임계값]
  ─▶ [컨텍스트 조립: 예산 배분 → 무관 항목 필터 → 요약/외부화 → 지연 로딩 훅]
  ─▶ LLM ↔ 툴 루프 (각 전이마다 상태 갱신 + 체크포인트)
  ─▶ [상태 확정] ─▶ 응답
  ─▶ (비동기) [메모리 쓰기: 추출 → 기존 기억과 충돌 해소 → 저장] ─▶ [평가: no-memory 대비 샘플링]
```

메모리 쓰기는 응답 경로 밖(비동기)에 두어 지연에 영향을 주지 않게 한다. 메모리 읽기는 응답 경로 안에 있으므로 조회 지연 상한을 둔다.

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 히스토리 전량 누적 (베이스라인) | 단일 세션, 10턴 이내, 프로토타입 | 긴 세션, 재시작 필요, 멀티 에이전트 | 하 | 표준 | `[검증]` 긴 컨텍스트의 중간 누락 보고(Lost in the Middle) |
| 슬라이딩 윈도우 + 재귀 요약 | 세션이 길고 과거 세부가 덜 중요한 대화 | 초반 제약·수집값이 끝까지 필요한 과업 | 하~중 (요약 호출) | 표준 | `[2차]` |
| 구조화 상태 + 체크포인팅 (LangGraph 류 또는 자체 상태 저장소) | 다단계 과업, HITL 대기, 재시도·재개, 디버깅 재현 | 단일 턴 QA | 중 (스키마·저장소) | 안정 | `[2차]` |
| 내구 실행 런타임 (프레임워크 내장 또는 범용 워크플로우 엔진) | 수 분~수 일 걸리는 과업, 외부 승인 대기 | 수 초 내 끝나는 요청 | 중~상 | 안정 | `[2차]` |
| 프레임워크 컨텍스트 관리 (Google ADK 등) | 세션·툴 출력·아티팩트가 많아 조립 규칙이 복잡 | 프레임워크 종속을 피하려는 팀 | 중 | 신생 | `[벤더]` |
| 대화 컨텍스트용 메모리 프레임워크 (Mem0, Letta 류) | 반복 방문 사용자, 선호·설정 회상이 품질을 바꿈이 확인됨 | 일회성 사용자, 과업 전환이 잦은 도메인(MemTrap 위험) | 중 (저장소·추출 비용) | 신생 | `[벤더]` 벤치마크 자체 보고, `[2차]` MemTrapBench 부정 결과 |
| 운영 지식용 메모리/시맨틱 레이어 (cognee 류) | 문서·데이터를 그래프로 조회해야 하고 Part 2 파이프라인이 없음 | 이미 KG·RAG 파이프라인 보유(중복) | 중~상 | 신생 | `[벤더]` |
| 자체 메모리 (DB + 추출 프롬프트 + 관련도 조회) | 저장할 항목이 명확하고 적음(선호 10여 종), 통제 필요 | 자유 형식 기억 대량 | 중 | 안정 | `[2차]` |
| no-memory + RAG만 | 대부분의 사내 QA, 비교 기준선 | 사용자 맥락 의존 과업 | 하 | 표준 | `[2차]` MemTrapBench에서 비교군으로 우위 |

### 선택 가이드

- **다단계·툴 실행·HITL이 있다면** → 구조화 상태 + 체크포인팅. 이유: 재개·재시도·디버깅이 모두 여기에 의존한다. 프레임워크 선택은 [14](14-frameworks-landscape.md)
- **세션이 길어 비용이 문제라면** → 구조화 상태 승격 + 툴 출력 외부화를 먼저, 요약은 보조. 이유: 요약은 손실이 있고 복구가 안 된다
- **반복 방문 사용자의 선호가 품질을 바꾼다면** → 자체 메모리(항목 제한)로 시작, no-memory 대비 `[실측]` 후 프레임워크 검토. 이유: MemTrap 위험을 항목 제한으로 통제
- **조직 지식을 "메모리"로 넣으려 한다면** → 하지 않는다. [Part 2](../02-data-pipeline/00-overview.md)의 RAG·KG로. 이유: 수명·소유자·갱신 규칙이 메모리와 다르다
- **판단이 어려우면** → 구조화 상태 + 체크포인팅 + no-memory. 이유: 상태는 없으면 운영이 안 되고, 메모리는 없어도 되며 있으면 해로울 수 있다

## 설계 시 고려사항 (체크리스트)

- [ ] 상태가 타입드 스키마로 정의되어 있고 히스토리 배열이 유일한 상태가 아닌가
- [ ] 체크포인트에서 재개했을 때 부수효과 있는 툴이 중복 실행되지 않는가 ([09](09-tools-and-mcp.md) 멱등성)
- [ ] HITL 대기 중 프로세스를 내려도 상태가 보존되는가
- [ ] 컨텍스트 구성 요소별 상한과 초과 시 축소 우선순위가 코드로 있는가
- [ ] 툴 출력이 크면 외부화하고 참조만 넣는가, 모델이 다시 조회할 수단이 있는가
- [ ] 요약으로 compaction한다면 요약 전 원문을 상태 저장소에 보존하는가
- [ ] 장기 메모리 평가셋에 "기억이 방해되는 케이스"와 no-memory 비교군이 있는가
- [ ] 메모리 쓰기가 응답 경로 밖(비동기)에 있고 읽기에 지연 상한이 있는가
- [ ] 기억 간 충돌(선호 변경)의 해소 규칙(최신 우선, 명시 우선)이 있는가
- [ ] 메모리에 PII가 들어간다면 보존 기간·삭제 요청 처리가 있는가 ([Part 2/10](../02-data-pipeline/10-access-control-governance.md))
- [ ] 상태 전이·메모리 주입 항목·compaction 발생을 트레이스에 기록하는가 ([Part 5/03](../05-cross-cutting/03-observability-tracing.md))

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 메모리가 no-memory보다 나쁠 수 있음 (MemTrapBench `[2차]`) | 이전 과업 프레임 고착, 과업 전환 실패 | no-memory 비교군, 주입 관련도 임계값, 에피소드 메모리는 보수적으로 |
| 벤치마크가 회상만 측정 | 벤치마크 점수와 운영 품질 불일치 | 과업 완료율·사람 개입률로 `[실측]` |
| 요약 오류 누적 | 잘못된 요약이 이후 모든 턴을 오염 | 구조화 승격 우선, 원문 보존, 요약 검증 샘플링 |
| 체크포인트 저장 비용·지연 | 전이마다 I/O | 전이 단위 조정, 비동기 저장, 큰 산출물은 참조 |
| 재개 시 중복 부수효과 | 중복 결제·중복 발송 | 멱등 키, 툴 호출 이력을 상태에 포함 |
| 프레임워크별 상태 모델 종속 | 프레임워크 교체 시 상태 마이그레이션 | 상태 스키마를 프레임워크와 분리해 정의 |
| 컨텍스트 조립 규칙의 불투명성 | "왜 이 정보가 빠졌나"를 재현 불가 | 조립 결정을 트레이스에 기록 |
| 메모리의 개인정보 | 보존·삭제·접근 통제 의무 | 수명 정책, 삭제 API, 접근 제어 |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 이 단계는 **상태 저장소가 곧 실행의 단일 장애점**이고, 메모리는 "있으면 좋은 것"이 아니라 오염·개인정보·비용의 세 리스크를 함께 들여오는 데이터라는 전제로 설계한다.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 동시 실행(run) 수 | 체크포인트 저장소의 쓰기 IOPS. 전이마다 전체 상태를 스냅샷하면 쓰기량 = 실행 수 × 전이 수 × 상태 크기 | 증분 체크포인트(변경 필드만), 큰 산출물은 참조 ID, 비동기 저장, 저장소를 실행 경로와 분리(무상태 워커 + 외부 저장소) | 실행 수 × 노드 전이 수 × 상태 크기 |
| 세션 길이(턴 수) | 컨텍스트 조립 비용과 compaction 요약 호출. 요약만으로 압축하면 턴마다 요약 LLM 호출이 추가되어 요청당 비용이 두 배 | 구조화 상태 승격 우선(요약 호출 없음), 요약은 N턴마다 배치, 툴 출력 외부화 | 턴 수 × compaction 전략의 LLM 호출 수 |
| 사용자 수(장기 메모리) | 메모리 저장소 크기와 조회 지연. 사용자당 항목 수를 제한하지 않으면 벡터 조회가 전체 사용자 규모에 비례 | 사용자·테넌트 키로 파티셔닝, 항목 수 상한(예시: 사용자당 선호 50건), 관련도 임계값으로 주입 수 제한 | 사용자 수 × 사용자당 항목 수 |
| 테넌트 수 | 상태·메모리에 테넌트 키가 없으면 분리 비용이 사후에 폭증, 삭제 전파 불가 | 처음부터 모든 체크포인트·메모리 레코드에 `tenant_id`, 테넌트별 보존 정책 | 테넌트 수 (키가 있으면 선형, 없으면 재설계) |

요청 처리 경로는 무상태로 두고 상태는 외부 저장소에 둔다. 메모리 **쓰기**는 응답 경로 밖(비동기 큐)에 있어 부하가 늘어도 응답 지연에 직접 영향하지 않지만, 큐 적체 시 "최근 턴의 기억이 다음 세션에 없음"으로 나타나므로 큐 길이를 지표로 둔다.

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| **체크포인트 저장소 장애**(다운·지연 급증) | 다단계 과업이 중간에 멈추거나 처음부터 다시 시작, HITL 대기 중 재개 불가 | 체크포인트 쓰기 오류율·p95 지연, 재개 실패 수 | 쓰기 실패 시 **새 전이를 중단**하고 "잠시 후 다시 시도" 안내(상태를 잃은 채 진행하지 않음). 읽기 전용 질의는 상태 없이 계속(저하 모드) | 쓰기 오류율이 임계값(예시: 5분간 1%)을 넘으면 온콜. 쓰기 툴이 있는 실행은 자동 재개 금지, 수동 확인 |
| **메모리 오염**(잘못된 추출, 이전 과업 프레임 고착) | "그런 말 한 적 없다"는 사용자 불만, 과업 전환 실패, 엉뚱한 선호 적용 | no-memory 대비 샘플 품질 저하, 메모리 주입 건의 부정 피드백률, 선호 충돌 해소 횟수 급증 | 관련도 임계값 상향, 에피소드 메모리 주입 **킬 스위치**(의미 메모리만 유지), 충돌 시 "최신·명시 우선" 규칙 | 부정 피드백률이 베이스라인 대비 상승 시 메모리 소유자가 추출 프롬프트·주입 조건 리뷰 |
| **요약 오류 누적**(compaction) | 이전에 합의한 제약·값이 사라지거나 바뀜 | 요약 전후 상태 필드 불일치 검사 실패, 요약 검증 샘플 불합격 | 요약 대신 **구조화 승격분만 유지**, 원문은 저장소에서 지연 로딩 | 샘플 불합격률 상승 시 요약 프롬프트 수정, 영향 세션 재처리 여부 결정 |
| **재개 시 중복 부수효과** | 중복 결제·중복 발송 | 멱등 키 충돌 로그, 툴 호출 이력과 외부 시스템 상태 불일치 | 멱등 키로 중복 무시([09](09-tools-and-mcp.md)), 마지막 툴 호출 상태 불명이면 **조회 후 재호출** | 멱등 키 미지원 툴에서 재개가 필요하면 사람 확인 후 수동 재개 |
| **메모리 조회 지연** | 턴 시작이 느려짐 | 메모리 읽기 p95, 타임아웃 수 | 읽기 타임아웃(예시: 200ms) 초과 시 **메모리 없이 진행**하고 트레이스에 표시 | 타임아웃률이 지속되면 저장소 용량·인덱스 점검 |
| **컨텍스트 예산 초과 폭증** | 응답 거부·절단, 비용 급증 | 예산 초과 축소 발생률, 턴당 토큰 | 축소 우선순위에 따라 자동 삭감, 상한 도달 시 "대화를 나눠서 진행" 안내 | 특정 경로에서 초과가 집중되면 조립 규칙 재설계 |

SLI 후보: 체크포인트 쓰기 성공률, 재개 성공률(HITL 대기 후 재개 건 중 성공), 메모리 읽기 p95, 메모리 주입 건의 부정 피드백률(no-memory 대비), 턴당 컨텍스트 토큰 p95, **삭제 이벤트 → 메모리 제거 p95**(불균형 ① 반영). SLO 초안(예시): 체크포인트 쓰기 성공률 99.9%, 재개 성공률 99%, 메모리 읽기 p95 200ms 이내. 쓰기 행동의 멱등성·타임아웃·재시도는 [09](09-tools-and-mcp.md) 등급표를 따르고, 이 단계는 **툴 호출 이력(멱등 키 포함)을 상태에 포함**해 재개 시 판단 근거를 제공한다. 메모리 저장소는 [Part 2/07](../02-data-pipeline/07-freshness-and-sync.md) 변경 큐 **삭제 레인의 소비자**로 등록해, 소스 문서·사용자 삭제 이벤트가 메모리 레코드(출처 턴·근거 ID 기준)까지 닿는 시간을 위 SLI로 잰다 (불균형 ① 반영). **체크포인트 TTL 불변식**: HITL 대기 중인 체크포인트의 TTL ≥ [12](12-guardrails-hitl.md) 승인 매트릭스의 **최대 승인 시한(에스컬레이션 포함) + 재시도 창** — 시한의 단일 소스는 3/12 매트릭스이고, 이 부등식은 매트릭스·TTL 설정이 바뀔 때마다 CI에서 검사한다(TTL이 시한보다 짧으면 승인 후 재개가 깨진다) (불균형 ⑤ 반영).

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| **상태 스키마** | 저장된 체크포인트의 역직렬화, 프레임워크 어댑터, 컨텍스트 투영 규칙 | 구버전 체크포인트 로드 테스트, 재개 테스트 | 마이그레이션 스크립트 또는 tolerant reader. 필드 추가는 자유, 삭제·의미 변경은 버전 상승 |
| **메모리 스키마·추출 프롬프트** | 기존 기억의 해석, 충돌 해소 규칙, 주입 필터 | 메모리 평가셋(도움/방해 케이스 + no-memory 비교군) | 추출 프롬프트가 전제하는 모델 버전 |
| **컨텍스트 조립 규칙**(예산 배분·축소 우선순위·관련도 임계값) | 모든 턴의 입력 구성, 비용 | 단계 골든셋 + 턴당 토큰 회귀 | 모델의 컨텍스트 윈도우 크기(모델 교체 시 재배분) |
| **compaction 전략·요약 프롬프트** | 긴 세션의 품질 | 긴 세션 시뮬레이션 셋, 요약 전후 상태 일치 검사 | 상태 스키마(승격 대상 필드) |
| **체크포인트 저장소·프레임워크 버전** | 저장 포맷, 재개 동작 | 구버전 체크포인트 호환 테스트 | 상태 스키마 어댑터 |

롤백 단위: 상태 스키마 + 프레임워크 어댑터 + 마이그레이션은 한 묶음. 기술 부채로 기록할 것: "메모리는 자체 KV로 시작, 프레임워크 검토는 `[실측]` 후", "체크포인트는 전체 스냅샷, 증분은 실행 수 10배 시", "에피소드 메모리 미도입".

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **지식** | 사용자 선호·사실의 추가·변경·삭제 요청 | 메모리 레코드 스키마(`subject, predicate, value, source_turn, ts, tenant_id`) | 저장소(KV·벡터·그래프), 추출 프롬프트 | 데이터 변경. 삭제는 2/07 삭제 레인 이벤트를 소비해 메모리 → 캐시 → 트레이스까지 전파(제거 p95를 SLI로, 불균형 ① 반영) | 메모리 계층만. 상태·컨텍스트 규칙 불변 |
| **모델** | 컨텍스트 윈도우 크기·가격·요약 품질 | 컨텍스트 조립기 인터페이스(`assemble(state, budget) → messages`) | 예산 배분 표, 요약 모델 | 예산 표를 **코드 밖 설정**으로 두고 모델별 프로파일 교체 | 조립 규칙 + 턴당 토큰 회귀 |
| **규칙·정책** | 메모리 보존 기간, PII 저장 금지 항목, 테넌트별 메모리 허용 여부 | 메모리 쓰기 게이트 인터페이스 | 보존·마스킹 규칙 세트 | 규칙 버전 + 시행일, 기존 레코드는 배치 재처리 | 메모리 쓰기 경로 + 삭제 배치 |
| **사용자 환경** | 조직 개편(테넌트 분리·병합), 다국어 | 테넌트 키, 메모리 레코드 스키마 | 파티션 매핑 | 테넌트 매핑 표 변경 + 레코드 재할당 배치 | 메모리·체크포인트 저장소의 키 범위 |
| **프로토콜·SDK** | 프레임워크 상태 모델·체크포인트 포맷 변경, MCP Tasks 도입 | **자체 상태 스키마**(프레임워크 클래스를 감싼 타입) | 프레임워크 어댑터, 체크포인트 직렬화기 | 어댑터 교체 + 구버전 체크포인트 마이그레이션, 계획된 창 | 어댑터와 저장 포맷만. 노드 로직 불변 |
| **부하·규모** | 실행 수·세션 길이·사용자 수 10배 | 무상태 처리 경로 | 저장소 파티셔닝, 증분 체크포인트 | 저장소 교체·샤딩 | 저장소 계층 |

가장 자주 바뀌는 것: **메모리 내용(지식)** > 컨텍스트 조립 임계값 > 상태 스키마 > 프레임워크. 코드 밖 설정으로 둘 것: 예산 배분 표, 축소 우선순위, 관련도 임계값, 사용자당 항목 상한, 보존 기간. 포트·어댑터 뒤에 둘 외부 의존: 체크포인트 저장소, 메모리 저장소, 요약 모델, 프레임워크 상태 클래스.

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성의 "탐지 신호"가 **실제로 어디서 나오는지**를 설계한다. 기준은 [Part 1/07 관측성 설계 요소](../01-foundations/07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md). 이 단계의 특수성은 두 가지다 — 상태·메모리 **본문은 스팬에 넣지 않고 ID·개수·해시만** 남기며, 메모리 쓰기는 응답 경로 밖(비동기)이므로 원 턴의 트레이스에 **링크**로 잇는다.

| 기록 대상 | 스팬 / 이벤트 (이름, 부모) | 핵심 속성 (버전 키 포함) | 지표 (→ 어느 SLI) | 샘플링 · 보존 · PII |
|---|---|---|---|---|
| 체크포인트 쓰기·복원 | `state.checkpoint`(전이마다) / `state.restore`(재개 시), 부모 `invoke_agent {name}` | `run_id, checkpoint_id, agent.state_schema_version, agent.checkpoint_bytes, agent.incremental`(변경 필드만 여부), `agent.tool_calls_in_flight[]`(복원 시 마지막 툴 호출 상태), `agent.outcome`, `tenant_id` | 쓰기 성공률·오류율·p95(→ 체크포인트 쓰기 성공률), 재개 성공률(HITL 대기 후 `restore` 성공 비율 → 재개 성공률), 쓰기 지연(흐름·적체) | 메타 전수. 상태 본문은 저장소에만(참조 ID). 실패·재개 건 전수 보존 |
| 재개 후 중복 부수효과 | `tool.invoke {tool}`의 이벤트 `idempotency_conflict`에 `agent.resumed_from_checkpoint_id` 전파([09](09-tools-and-mcp.md) 멱등 규약) | `agent.idempotency_key_hash, checkpoint_id` | 재개 건 중 멱등 키 충돌률, 조회 후 재호출 발생 수 | 전수, 감사와 겸함 |
| 메모리 읽기·주입 | `memory.read`, 부모 `invoke_agent` | `agent.memory_ids_injected[]`, `agent.memory_count`, `agent.memory_relevance_min`, `agent.memory_conflicts_resolved`, `agent.degradation[]=memory_skipped`(타임아웃 시), `tenant_id` | 읽기 p95·타임아웃률(→ 메모리 읽기 p95), 턴당 주입 건수 분포, 충돌 해소 횟수 추이(품질) | 메모리 값 본문 opt-in(해시만). 타임아웃·테넌트 불일치 차단 건 전수 |
| 메모리 쓰기(비동기 큐) | `memory.write`, 비동기 작업 트레이스의 루트 — 원 `turn`에 스팬 링크 | `agent.memory_record_id, agent.extraction_rules_version, agent.pii_masked, agent.queue_wait_ms, agent.outcome`(blocked = PII·금지 항목·테넌트 불일치) | 쓰기 큐 깊이·대기 p95(흐름·적체 — "최근 턴 기억이 다음 세션에 없음"의 선행 신호), 쓰기 차단률(품질) | 메타·차단 건 전수. 값 본문은 저장소에만 |
| 메모리 삭제 전파 | 이벤트 `memory.delete`([Part 2/07](../02-data-pipeline/07-freshness-and-sync.md) 삭제 레인 소비자) | `source_event_id, source_event_ts, agent.records_removed, agent.caches_invalidated, tenant_id` | 삭제 이벤트 → 메모리 제거 p95(→ 동명 SLI), 미처리 잔량·DLQ 크기(흐름·적체) | 전수. 감사 레코드로 복제 |
| 컨텍스트 조립·축소 | `context.assemble`, 부모 `invoke_agent` | `agent.context_tokens, agent.context_budget, agent.trimmed_items[]`(종류·개수·우선순위), `agent.prompt_version, agent.model_version`(예산 프로파일 키) | 턴당 컨텍스트 토큰 p95(→ 동명 SLI), 예산 초과 축소 발생률(경로별), 상한 도달 "대화 나누기" 안내율 | 메타 전수. 조립된 메시지 본문 opt-in |
| compaction과 효과 측정 | `memory.compact`(자식 `verify.rules` = 요약 전후 필드 불일치 검사), 부모 `invoke_agent`; 온라인 `eval.sample`에 `ui.event` 피드백을 `request_id`로 조인 | `agent.compaction.strategy`(summary / promote), `agent.compaction.field_mismatch_count, agent.promoted_fields[]`, 요약 모델 버전; 샘플에는 `agent.memory_count`와 피드백 라벨 | 필드 불일치 검사 실패율·요약 검증 샘플 불합격률(품질), compaction 호출 수·비용(RED), **메모리 주입 건의 부정 피드백률(no-memory 대비 → 동명 SLI)** | 불일치 건은 요약 전후 본문 전수. 효과 샘플 1~5%, 부정 피드백 건 전수 |

| 알림 | 조건 (예시) | 심각도 | 런북 (첫 3단계) |
|---|---|---|---|
| 체크포인트 쓰기 장애 | `state.checkpoint` 오류율 > 1% 5분 지속, 또는 p95 > 500ms 10분 | P1 | ① 저장소 헬스·IOPS·파티션 핫스팟 확인 ② "새 전이 중단 + 읽기 전용 저하" 동작을 저하율로 확인 ③ 쓰기 툴 포함 실행 목록 추출, 자동 재개 차단 상태 확인 |
| 메모리 오염 의심 | 메모리 주입 건 부정 피드백률이 no-memory 대비 베이스라인 +3%p(7일 이동), 또는 충돌 해소 횟수 2배 | P2 | ① `extraction_rules_version` 변경 시점과 겹치는지 확인 ② 부정 피드백 건의 `memory_ids_injected[]` 샘플 20건 리뷰 ③ 에피소드 메모리 킬 스위치 가동 여부를 메모리 소유자가 결정 |
| compaction 불일치 | `field_mismatch_count > 0` 비율 > 0.5% 1시간 | P2 | ① 요약 모델·프롬프트 버전 변경 확인 ② "구조화 승격분만 유지" 모드 전환 ③ 영향 세션 목록 추출, 재처리 여부 결정 |
| 메모리 읽기 저하 | `degradation=memory_skipped` 비율 > 5% 15분 | P2 | ① 저장소 지연·인덱스 상태 ② 사용자당 항목 상한 초과 테넌트 확인 ③ 타임아웃 임시 상향은 사람 결정 |
| 삭제 전파 지연 | 삭제 이벤트 → 제거 p95 > SLO 1시간, 또는 DLQ 잔량 증가 | P2 (PII 포함 테넌트는 P1) | ① 소비자 프로세스 상태·오프셋 ② DLQ 건 재처리 ③ 영향 레코드 수·테넌트를 데이터 소유자에 보고 |

- **대시보드에서 이 단계를 보는 뷰**: ② Reasoning 패널 — 체크포인트 쓰기 성공률·p95, 재개 성공률, 메모리 읽기 p95·저하율, 턴당 컨텍스트 토큰 p95, compaction 불일치율. ③ 비용·판정 분포 — compaction 호출 비용 비중, 컨텍스트 토큰 분포(축소 발생 구간 표시), 메모리 쓰기 큐 대기.
- **감사 추적으로 넘기는 필드(관측 로그와 분리)**: `run_id, checkpoint_id, state_schema_version`, 컨텍스트 조립의 포함·제외 항목 ID와 사유, 주입된 메모리 ID 목록, 메모리 쓰기 레코드(출처 턴·추출 규칙 버전), compaction 승격 필드, 삭제 요청 처리 결과. 관측 스팬에는 개수·해시·버전만 남는다.
- **이 단계의 관측이 없으면 못 보는 장애**: 메모리가 **조용히 틀려가는 것**. 오염된 메모리와 누적된 요약 오류는 오류율·지연 어디에도 안 잡힌다 — 주입 메모리 ID와 사용자 피드백의 조인, 요약 전후 불일치 검사가 없으면 "그런 말 한 적 없다"는 불만이 쌓인 뒤에야 안다. 삭제 전파 지연도 마찬가지로 민원·감사에서만 드러난다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | 상태 저장·컨텍스트 조립 자체는 등급 1(가역, 본인 영향). **메모리 쓰기는 등급 2**(여러 세션에 영향, 되돌리려면 삭제 전파 필요). 메모리에 PII가 들어가면 등급 3으로 상향하고 보존·삭제 정책 승인 필수 |
| 가드레일 위치 | **출력** 지점: 메모리 쓰기 직전 PII·금지 항목 필터(저장 금지). **입력** 지점: 메모리 주입 직전 관련도 임계값과 테넌트 일치 검사(다른 테넌트 기억 주입 차단은 규칙만) |
| 게이트 출력과 판정 수단 | 메모리 쓰기 게이트: 통과 / 차단(PII·테넌트 불일치, 규칙) / 저하(에피소드 메모리 비활성 킬 스위치). 승인은 없음 — 메모리 쓰기에 사람 승인을 걸면 승인 피로만 생긴다 |
| 소유자 (A) | 상태 스키마: 아키텍트. 메모리 스키마·추출 규칙·보존 정책: 제품 책임자(데이터 소유자 자문). 체크포인트 저장소 운영: 플랫폼 엔지니어 |
| 감사 추적에 남길 필드 | `run_id, checkpoint_id, state_schema_version`, 컨텍스트 조립 결정(포함·제외 항목 ID와 사유), 주입된 메모리 ID 목록, 메모리 쓰기 레코드(출처 턴·추출 규칙 버전), compaction 발생과 승격 필드, 삭제 요청 처리 결과 |

- [ ] 체크포인트 저장소 장애 시 "상태 없이 진행하지 않는다"가 코드로 보장되고, 읽기 전용 저하 모드가 있는가
- [ ] 에피소드 메모리 주입을 배포 없이 끄는 킬 스위치가 있는가
- [ ] 메모리 읽기 타임아웃과 초과 시 메모리 없이 진행하는 경로가 있는가
- [ ] 구버전 체크포인트를 새 상태 스키마로 로드하는 테스트가 CI에 있는가
- [ ] 모든 체크포인트·메모리 레코드에 `tenant_id`와 스키마 버전이 있는가
- [ ] 메모리 삭제 요청이 메모리 → 캐시 → 트레이스까지 전파되는 절차와 담당자가 있고, 메모리가 2/07 삭제 레인 소비자로 등록되어 "삭제 이벤트 → 메모리 제거 p95"를 재는가 (불균형 ① 반영)
- [ ] 체크포인트 TTL ≥ 3/12 최대 승인 시한 + 재시도 창 불변식이 CI에서 검사되는가 (불균형 ⑤ 반영)
- [ ] 메모리 주입 건의 부정 피드백률을 no-memory 대비로 상시 측정하는가
- [ ] 예산 배분 표·관련도 임계값·항목 상한이 코드 밖 설정으로 버전 관리되는가
- [ ] `state.checkpoint`·`memory.read/write/compact` 스팬에 `tenant_id`·`state_schema_version`·`agent.memory_ids_injected[]`가 있어 부정 피드백을 메모리 ID 단위로 조인할 수 있는가
- [ ] 체크포인트 쓰기 오류율(P1)·삭제 전파 지연·compaction 불일치 알림에 런북이 연결되어 있고, 메모리 쓰기 큐 깊이를 대시보드에서 보는가
