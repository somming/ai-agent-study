# 뉴로심볼릭 추론 적용

> **범위**: LLM + 규칙엔진 / 온톨로지 reasoner / 제약 검증기 결합 패턴과 적용 사례
> [Part 1/04](../01-foundations/04-neuro-symbolic-ai.md)가 정의한 네 패턴(검증기·변환기·접지·게이트)을 **Part 3의 어느 자리에 어떻게 배치**하는지, 그리고 자기 수정 루프를 어떻게 설계하는지. 패턴의 분류와 개념은 반복하지 않는다. 트렌드 심화는 [Part 6/neuro-symbolic](../06-trends/neuro-symbolic.md).

## 요약 (3줄)

1. 뉴로심볼릭(neuro-symbolic) 적용의 실무 질문은 "어떤 기법인가"가 아니라 **"실행 그래프의 어느 노드 뒤에 어떤 기호 검증기를 꽂는가"**다. Part 3의 각 단계(질의·검색·생성·툴·결정·가드레일)마다 꽂을 자리와 적합한 기호 체계가 다르다.
2. 검증기는 **표현력 순서**로 쌓는다. JSON Schema → 규칙 엔진 → SHACL/온톨로지 추론기 → 제약 솔버. 아래 층이 거르지 못한 것만 위 층으로 올린다. 처음부터 솔버를 두는 것은 과잉이다.
3. 자기 수정 루프(self-correction loop)는 **상한과 환류**가 있어야 루프다. 상한 없는 재생성은 비용 폭주이고, 환류 없는 실패는 같은 실패의 반복이다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 실행 그래프의 노드별 검증기 배치표(노드 → 기호 체계 → 불합격 처리) ② 기호 체계(규칙·SHACL·온톨로지·솔버·실행기)의 소스와 소유자 ③ 자기 수정 루프의 상한·폴백·환류 규칙 ④ 검증 실패율 지표 |
| **언제** (When) | LLM 출력이 **행동**(툴 실행·데이터 변경·전송)이나 **규제 대상 판단**으로 이어지거나, 출력이 정형 구조(쿼리·추출·UI 트리)일 때. 출력이 사람이 읽는 자유 텍스트로 끝나면 [12](12-guardrails-hitl.md)의 가드레일로 충분하고 이 페이지는 생략 가능 |
| **어떻게** (How) | ① 노드별로 "틀리면 안 되는 제약"을 목록화 → ② 각 제약을 가장 낮은 표현력의 기호 체계로 작성 → ③ 노드 뒤에 검증기 배치, 오류를 구조화 → ④ 재생성 상한·폴백 결정 → ⑤ 변환기 패턴(쿼리·코드)은 샌드박스·읽기 전용 실행 → ⑥ 실패 로그를 프롬프트·스키마·골든셋에 환류 → ⑦ 검증 실패율·오탐률을 [13](13-evaluation-rag-agents.md)에서 추적 |
| **왜** (Why) | 프롬프트의 규칙은 확률적으로 지켜진다. 1만 건 중 몇 건의 위반이 금전·법적 결과를 낳는 영역에서는 결정론적 검증기만이 준수를 보장한다. 그리고 검증기 없는 에이전트는 **왜 틀렸는지** 재구성할 수 없어 개선 루프가 돌지 않는다 |

## 문제와 맥락

[Part 1/04](../01-foundations/04-neuro-symbolic-ai.md)에서 네 패턴을 정의했지만, 설계자가 실제로 마주하는 상황은 "이 LangGraph 노드의 출력이 Cypher 쿼리인데 어디까지 검사하지", "툴 인자가 스키마는 맞는데 금액이 한도를 넘었다", "추출된 트리플이 온톨로지에 없는 관계를 쓴다"처럼 **구체적인 자리**다. 자리마다 ① 출력 형식 ② 틀렸을 때의 비용 ③ 검증 가능한 기준의 존재 여부가 다르므로 하나의 검증기로 통일할 수 없다.

또 하나의 문제는 루프다. 검증 실패 시 LLM에 오류를 돌려주고 재생성하면 많은 경우 고쳐지지만, 어떤 실패는 영원히 고쳐지지 않는다(모델이 할 수 없는 것). 이를 구분하지 않으면 요청당 LLM 호출이 몇 배로 늘어난다.

### 기호 체계별 적용 방법

**규칙 엔진 (OPA/Rego, Drools류, 자체 DSL)**
if-then 정책을 코드 밖에서 관리한다. 적용 자리는 툴 게이트·승인 정책·가드레일. LLM 출력(툴 인자 JSON)과 컨텍스트(사용자 권한·세션 상태)를 입력으로 받아 허가/거부/승인필요를 반환하게 설계한다. 규칙도 코드이므로 버전·테스트·소유자가 필요하다. 규칙 수가 수십 개를 넘으면 충돌 탐지 기능이 있는 엔진이 필요하다.

**온톨로지 추론기 (OWL reasoner)**
클래스 계층·속성 제약·일관성 검사. 적용 자리는 추출 결과의 일관성(한 엔티티가 서로 배타적인 클래스에 동시 속함), 상위 개념 추론으로 질의 확장(접지), 답변에 등장한 개념이 온톨로지에 존재하는지 확인. 표현력이 높은 프로파일일수록 느리므로 응답 경로에서는 경량 프로파일(RL·EL 계열)로 제한하고 무거운 추론은 배치로.

**SHACL (Shapes Constraint Language)**
RDF 그래프 데이터의 형상·카디널리티·값 범위 검증. 적용 자리는 LLM이 추출·생성한 그래프 데이터(트리플, 구조화 프로필)의 검증. 검증 보고서가 구조화되어 있어 재생성 오류 메시지로 바로 쓸 수 있다. LPG(Neo4j 등)를 쓴다면 변환 또는 등가 제약을 직접 작성.

**제약 솔버 (SMT·CP)**
조합 제약 충족·최적화. 적용 자리는 일정·배치·구성 같은 **조합 문제**. LLM은 자연어를 제약으로 변환(변환기)하고 솔버가 해를 찾는다. LLM이 직접 "가능한 일정"을 생성하게 하면 제약 위반이 잦고 검증도 어렵다. 모델링 난이도가 높으므로 조합 문제가 실제로 있을 때만.

**프로그램 합성·실행 (PAL, 코드 인터프리터)**
수치·날짜·집계·알고리즘. LLM이 코드를 쓰고 샌드박스가 실행한다. 실행 결과가 근거가 되므로 환각이 구조적으로 억제되고, 오류는 실행 오류로 드러나 재생성 신호가 된다. 샌드박스(네트워크·파일 격리, 시간 제한, 읽기 전용 자격)가 없으면 쓰지 않는다. [09](09-tools-and-mcp.md)의 코드 실행 툴과 같은 것이다.

**KG 제약**
지식그래프를 검증 기준으로 쓴다. 답변에 등장한 엔티티가 그래프에 존재하는가, 주장한 관계가 그래프에 있거나 모순되지 않는가. 온톨로지 추론기보다 가볍고, "존재하지 않는 엔티티 언급"을 가장 직접적으로 잡는다. 그래프가 불완전하면 오탐(맞는 답을 거부)이 생기므로 "그래프에 없음"을 "틀림"이 아니라 "미확인"으로 등급화한다.

### 자기 수정 루프 설계

```
LLM 출력 ─▶ 검증기 층 1 (스키마) ─▶ 층 2 (규칙/SHACL) ─▶ 층 3 (솔버/실행) ─▶ 합격 ─▶ 다음 노드
                 │ 불합격                │ 불합격              │ 불합격
                 └──────── 오류 구조화 {layer, code, path, expected, got, hint} ────────┐
                                                                                    ▼
                                          재시도 횟수 < 상한? ──예──▶ 오류를 컨텍스트에 추가 → 재생성
                                                  │ 아니오
                                                  ▼
                                   폴백 (보수적 기본값 / 이전 합격 출력 / 사람) + 실패 패턴 로그
```

- **오류는 구조화**한다. "검증 실패"가 아니라 "인자 `amount`가 한도 1,000,000을 초과(값 1,500,000). 한도 이내로 조정하거나 승인 요청 툴을 사용"처럼 위치·기대·실제·조치를 담는다. 자유 텍스트 오류는 모델이 다른 곳을 고친다
- **재생성 상한**: 권장 기본값은 2~3회. 상한에 도달한 실패는 대부분 "모델이 할 수 없는 것"이므로 더 돌려도 비용만 든다. 상한은 노드별로 다르게(쿼리 변환은 높게, 툴 인자는 낮게)
- **고칠 수 있는 실패 vs 없는 실패**: 스키마·구문 오류는 재생성으로 잘 고쳐진다. 규칙 위반(한도 초과·권한 없음)은 모델이 고칠 수 없다 — 재생성하지 않고 즉시 폴백·승인으로. 이 구분을 오류 코드에 넣는다(`retryable`)
- **폴백 순서**: 보수적 기본값(아무것도 하지 않음, 읽기 전용 경로) → 마지막 합격 출력 → 사람. [12](12-guardrails-hitl.md)
- **실패 패턴 환류**: 검증 실패 로그를 주기적으로 묶어 ① 반복 실패는 프롬프트·few-shot에 반영 ② 스키마가 모호해서 생긴 실패는 스키마 수정 ③ 검증기가 맞는 출력을 거부한 오탐은 규칙·온톨로지 수정 ④ 대표 사례는 골든셋에 추가. 환류가 없으면 실패율은 내려가지 않는다

### 결정 모델과의 결합

게이트 패턴의 "모델" 자리에 결정 모델([11](11-decision-layer.md))을 두면 "규칙 통과 ∧ 확신 ≥ θ → 실행, 규칙 통과 ∧ 확신 < θ → 사람, 규칙 위반 → 차단"의 세 갈래가 한 자리에서 처리된다. 규칙이 항상 우선한다는 것을 코드 구조(규칙 평가가 모델 평가보다 먼저, 모델 결과가 규칙 결과를 덮어쓸 수 없음)로 보장한다.

| 제약 솔버 (SMT·CP) | 일정·배치·구성 등 조합 문제 | 조합 제약이 없는 과업, 모델링 역량 없음 | 상 | 안정 | `[검증]` 솔버 자체, LLM 결합은 `[2차]` |
| 프로그램 합성·실행 (PAL, 코드 인터프리터) | 수치·날짜·집계·알고리즘, Text-to-SQL/Cypher | 샌드박스 불가, 파괴적 API 접근 | 중~상 (샌드박스) | 안정 | `[검증]` Text-to-SQL·PAL 벤치마크 다수 |
| KG 제약 (엔티티·관계 존재 검사) | 존재하지 않는 엔티티 언급 억제, 답변 주장 검증 | 그래프가 불완전(오탐), 그래프 없음 | 중 | 시험 | `[2차]` |
| 근거-주장 정합성 검사기 (NLI·judge) | citation이 실제로 주장을 뒷받침하는지 | 결정론이 필요한 영역(검사기 자체가 확률적) | 중 | 안정 | `[2차]` [04](04-generation-grounding.md) |
| 프롬프트에 규칙 명시만 | 프로토타입, 위반 비용 낮음 | 행동·규제·금전 연결 | 하 | 표준 | `[검증]` 확률적 준수 한계 |

### 선택 가이드

- **툴 인자·행동이 있다면** → JSON Schema + 규칙 엔진 게이트. 이유: 가장 싸고 가장 자주 쓰이며, 행동 앞의 결정론적 차단은 다른 수단으로 대체 불가
- **정형·그래프 데이터를 질의한다면** → 변환기 패턴(Text-to-SQL/Cypher) + 읽기 전용 실행. 이유: 실행 결과가 근거라 환각이 구조적으로 억제
- **추출 결과를 그래프에 쓴다면** → SHACL(RDF) 또는 등가 제약(LPG) + 필요 시 경량 OWL 일관성. 이유: 검증 보고서가 구조화되어 재생성 루프에 바로 쓰임
- **조합 제약(일정·배치)이 과업의 본질이라면** → 제약 솔버. 이유: LLM이 직접 해를 생성하면 위반이 잦고 검증 불가
- **판단이 어려우면** → JSON Schema + 규칙 게이트 + 재생성 상한 2회 + 실패 로그. 이유: 즉시 효과가 있고 위 층은 실패 로그를 보고 추가하면 된다

## 설계 시 고려사항 (체크리스트)

- [ ] 노드별 "틀리면 안 되는 제약" 목록과 각 제약의 기호 체계·소유자가 있는가
- [ ] 검증기가 LLM 출력의 **모든** 행동 경로 앞에 있고 우회 경로가 없는가
- [ ] 검증 오류가 구조화(`layer`, `code`, `path`, `expected`, `got`, `hint`, `retryable`)되어 있는가
- [ ] 고칠 수 있는 실패(스키마·구문)와 없는 실패(규칙 위반)를 구분해 후자는 재생성하지 않는가
- [ ] 노드별 재생성 상한과 상한 도달 시 폴백 순서가 있는가
- [ ] 규칙이 모델(LLM·결정 모델)보다 우선한다는 것이 코드 구조로 보장되는가
- [ ] 변환기 패턴의 실행이 샌드박스·읽기 전용·시간 제한 안에 있는가
- [ ] KG·온톨로지 기반 검증에서 "없음"을 "틀림"과 "미확인"으로 구분하는가 (오탐 통제)
- [ ] 검증 실패율·오탐률·재생성 횟수를 노드별로 측정하는가 ([13](13-evaluation-rag-agents.md))
- [ ] 실패 로그를 프롬프트·스키마·규칙·골든셋에 환류하는 주기와 담당자가 있는가
- [ ] 규칙·온톨로지·SHACL 변경에 테스트 스위트가 있는가 (기호 체계도 코드다)

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 검증기는 통제 세 층 중 **예방** 층의 구성 요소이고, 검증 실패율은 **탐지** 신호이며, 재생성 상한과 폴백은 **교정** 수단이다. 이 단계의 운영 설계는 "검증기 자체가 장애를 일으킬 때"를 다룬다.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 규칙 수(수십 → 수백) | 규칙 충돌·우선순위 모순, 평가 지연, "어느 규칙이 막았나" 추적 난이도 | 충돌 탐지 기능이 있는 정책 엔진, 도메인별 규칙 세트 분할, 규칙마다 소유자·테스트 | 규칙 수 × 규칙 간 상호작용(테스트 수) |
| 요청 수(검증기 호출량) | 응답 경로의 검증기 지연 누적. 온톨로지 추론기·NLI 검사기처럼 무거운 층이 매 요청에 돌면 p95가 수 초 | 층별 지연 예산, 경량 프로파일만 온라인, 무거운 추론은 배치·비동기, 검증 결과 캐시(동일 출력) | 요청 수 × 검증기 층 수 × 층별 지연 |
| 검증 실패율(재생성 루프) | 실패율이 조금 올라도 재생성 상한까지 돌면 LLM 호출이 상한 배수로 증가. 실패율 10% × 상한 3회면 요청당 호출 1.3배, 실패율 50%면 2.5배 | 고칠 수 없는 실패는 즉시 폴백(재생성 안 함), 상한을 노드별로, 실패 패턴 환류로 실패율 자체를 낮춤 | 실패율 × 재생성 상한 × LLM 단가 |
| 온톨로지·KG 크기 | 추론기 메모리와 일관성 검사 시간, KG 존재 검사의 조회 지연 | 추론은 배치로 구체화(materialize)해 온라인은 조회만, KG 검사는 인덱스된 존재 조회로 제한 | 온톨로지 공리 수, KG 엔티티 수 |

비용이 비례하는 핵심 변수는 **검증 실패율**이다. 검증기 수를 늘리는 것보다 실패율을 낮추는 환류 루프가 확장성에 더 기여한다.

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| **검증기 오탐 폭증**(규칙·온톨로지가 현실과 어긋남, 배포 직후) | 정당한 출력이 대량 거부, "처리할 수 없다" 응답 급증, 재생성 비용 급증 | 노드별 검증 실패율이 베이스라인 대비 급등(예시: 2배), 거부 로그 샘플에서 정당 출력 비율 상승 | 실패율 임계값 초과 시 해당 **규칙 세트 버전을 직전 버전으로 자동 롤백**(규칙은 데이터이므로 재배포 불필요). 롤백 불가 시 해당 층을 "미확인" 등급으로 저하(차단 대신 플래그 + 사후 리뷰) — 단 **보안·권한·한도 규칙은 저하 대상에서 제외** | 규칙 소유자가 거부 샘플 리뷰 후 수정 버전 배포 |
| **검증기 다운**(정책 엔진·추론기·샌드박스 불가) | 행동이 있는 경로 전체 중단 또는 검증 없이 통과 | 검증기 호출 오류율, 헬스체크 | **보수적 기본 경로**: 행동 노드는 "검증 불가 = 차단"(fail-closed), 자유 텍스트 응답 노드는 "검증 없음 표시 + 응답"(fail-open, 등급 1에 한함). 어느 쪽인지 노드별로 사전 결정 | 정책 엔진 다운은 즉시 온콜. 복구까지 쓰기 툴 경로 전면 중단 |
| **재생성 루프 비용 폭주** | 지연 증가, 비용 알림 | 요청당 LLM 호출 수 p95, 상한 도달률 | 상한 도달 시 폴백 순서(보수적 기본값 → 마지막 합격 출력 → 사람). 특정 노드 상한 도달률이 임계값 초과 시 상한을 1로 임시 축소(피처 플래그) | 상한 도달이 특정 입력 유형에 집중되면 프롬프트·스키마 수정 |
| **변환기 실행 오류**(Text-to-SQL/Cypher 실행 실패·타임아웃) | 정형 질의 결과 없음 | 실행 오류율, 쿼리 타임아웃률 | 구문 오류 → 재생성(상한), 실행 오류·타임아웃 → **벡터 검색 폴백** + "정확한 집계 불가" 표시 | 특정 스키마 변경 후 집중 발생 시 스키마 설명 갱신 |
| **샌드박스 탈출 시도·자원 고갈** | 응답 지연, 다른 요청에 영향 | 샌드박스 자원 사용량, 네트워크 시도 로그 | 시간·메모리 제한 초과 시 즉시 종료, 네트워크·파일 시도는 차단 + 플래그, 반복 시 코드 실행 툴 **킬 스위치** | 탈출 시도 패턴은 보안 책임자에게 |
| **온톨로지 추론 지연 급증** | 응답 p95 상승 | 추론기 지연 | 온라인 추론 타임아웃(예시: 300ms) 초과 시 **추론 생략 + 미확인 표시**, 배치 구체화 결과만 사용 | 공리 추가 후 지연 상승 시 프로파일 재검토 |

SLI 후보: 노드별 검증 실패율, 오탐률(거부 샘플 중 정당 출력 비율), 요청당 재생성 횟수 p95, 상한 도달률, 검증기 가용성, 검증기 p95 지연. SLO 초안(예시): 툴 인자 노드 검증 실패율 5% 이하, 오탐률 1% 이하, 상한 도달률 0.5% 이하, 정책 엔진 가용성 99.95%. 쓰기 행동의 멱등성·타임아웃·재시도는 [09](09-tools-and-mcp.md)를 따르고, 이 단계는 **재생성이 쓰기 툴의 중복 실행으로 이어지지 않도록** 검증기가 실행 **전**에 위치함을 보장한다.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| **규칙 세트**(정책 엔진 규칙, 자체 DSL) | 게이트 판정, 차단·승인 비율 | **규칙 테스트 스위트**(허가·거부·승인 케이스 각각), 골든 트래젝토리 게이트 차단율 | 규칙이 참조하는 툴 스키마 버전, 온톨로지 enum |
| **JSON Schema**(툴 인자·추출·UI 트리) | 1층 검증 통과율, 재생성 횟수 | 스키마 통과율 골든셋 | 모델의 구조화 출력 모드 호환, 하류 파서 |
| **SHACL 형상·온톨로지** | 추출 검증 통과율, 접지 enum, 일관성 검사 | 추출 검증 통과율, 알려진 정답 트리플 셋 | [Part 2/06](../02-data-pipeline/06-ontology-driven-modeling.md) 온톨로지 버전 + 구→신 매핑 |
| **재생성 상한·폴백 순서·타임아웃** | 비용, 지연, 폴백 비율 | 비용 회귀(요청당 호출 수) | — (설정 단독 변경 가능) |
| **검증 오류 메시지 템플릿**(`hint`) | 재생성 성공률 | 재생성 1회 성공률 | 프롬프트 버전 |
| **모델 버전** | 스키마 준수율, 재생성 성공률 | 전체 노드 검증 실패율 | 프롬프트-모델 호환 매트릭스 |

롤백 단위: 규칙 세트는 단독 롤백 가능(데이터). 온톨로지 + SHACL + 추출 프롬프트는 한 묶음. 기술 부채로 기록할 것: "규칙 30개 이하라 코드 내 함수, 정책 엔진은 50개 또는 두 번째 서비스 공유 시", "KG 존재 검사는 '미확인'으로만, 차단 승격은 그래프 커버리지 `[실측]` 후".

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **규칙·정책**(가장 잦음) | 한도 금액, 허용 조합, 금칙 표현, 규제 신설 | 검증기 인터페이스(`validate(output, ctx) → {ok, errors[]}`), 구조화 오류 스키마 | 규칙 세트, 정책 엔진 | **규칙 버전 + 시행일**로 설정 교체, 규칙 테스트 스위트 통과 후 반영. 코드 불변 | 해당 노드 게이트. 감사 레코드에 규칙 버전 기록으로 시점 재현 |
| **도메인 모델**(온톨로지·택소노미) | 클래스·관계 추가, 개명 | 상위 개념, 구→신 매핑 테이블 | SHACL 형상, enum 소스 | 온톨로지 버전 + 매핑, 접지 enum은 온톨로지에서 **자동 생성** | 접지 enum·SHACL·결정 enum([11](11-decision-layer.md))·UI 매핑까지 — 전파가 가장 넓으므로 변경 절차 무겁게 |
| **지식**(KG 내용) | 엔티티·관계 추가·삭제 | KG 존재 검사 인터페이스 | 그래프 저장소 | 데이터 변경. "없음 = 미확인" 등급이 불완전 그래프를 흡수 | 오탐률 모니터만 |
| **모델** | 스키마 준수율, 오류 메시지 해석 | 구조화 오류 스키마 | 재생성 프롬프트, `hint` 템플릿 | 모델별 `hint` 변형, 상한 재조정 | 검증 실패율 회귀 |
| **사용자 환경** | 다국어 금칙 표현, 조직별 한도 | 규칙 평가 인터페이스 | 언어별·조직별 규칙 세트 | 규칙 세트를 테넌트·언어 키로 분기 | 해당 테넌트 게이트 |
| **프로토콜·SDK** | 정책 엔진 교체(OPA → 자체), 샌드박스 런타임 변경 | 검증기 포트 | 엔진 어댑터, 샌드박스 어댑터 | 어댑터 교체 + 규칙 테스트 스위트 전체 통과 | 어댑터만 |
| **부하·규모** | 검증기 호출량 10배 | 무상태 검증기 | 캐시, 배치 구체화 | 수평 확장 | 추론기 계층 |

가장 자주 바뀌는 것: **규칙·한도** > 온톨로지 > 스키마 > 모델 > 엔진. 코드 밖 설정으로 둘 것: 규칙 세트, 재생성 상한, 폴백 순서, 타임아웃, `hint` 템플릿, 접지 enum(온톨로지에서 생성). 포트·어댑터 뒤에 둘 외부 의존: 정책 엔진, 온톨로지 추론기, 제약 솔버, 코드 실행 샌드박스, KG 저장소.

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성의 "탐지 신호"가 **실제로 어디서 나오는지**를 설계한다. 기준은 [Part 1/07 관측성 설계 요소](../01-foundations/07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md). 검증기는 "거부"가 정상 동작이므로 **오류율만 보면 건강해 보인다** — 거부 사유 코드 분포와 거부 샘플의 리뷰 라벨(오탐률)이 이 단계의 핵심 품질 신호다. 검증기 스팬은 `verify.schema / verify.rules / verify.solver` 세 이름으로 층을 구분한다.

| 기록 대상 | 스팬 / 이벤트 (이름, 부모) | 핵심 속성 (버전 키 포함) | 지표 (→ 어느 SLI) | 샘플링 · 보존 · PII |
|---|---|---|---|---|
| 검증기 층별 판정 | `verify.schema`(구조·타입·enum) / `verify.rules`(정책·한도·SHACL) / `verify.solver`(제약 솔버·온톨로지 추론기), 부모는 해당 노드의 `invoke_agent {name}` — 툴 인자 게이트면 `tool.invoke` 직전 | `agent.node_id, agent.verify_layer, agent.outcome`(pass / reject / error), `agent.error_codes[]`(`layer, code, path`), `agent.rules_applied[]`(규칙 ID·버전), `agent.rules_version, agent.ontology_version, agent.shacl_version, agent.fail_mode`(closed / open) | 노드·층별 검증 실패율(→ 동명 SLI), 거부 사유 코드 분포, 검증기 오류율·가용성·p95(→ 검증기 가용성·p95), **fail-open 통과 건수**(검증 없이 지나간 응답) | 메타 전수. 거부 건 출력 본문 전수(마스킹) — 오탐 리뷰 재료. 통과 건 본문 opt-in |
| 오탐 측정 | `eval.sample`(거부 건을 노드·규칙 ID로 층화 샘플링, 부모 `turn`) + 리뷰 라벨 | `agent.review_label`(legit / correct_reject), `agent.rules_version, agent.rule_id` | 오탐률(→ 동명 SLI), **규칙 ID별 오탐 기여도**(어느 규칙이 정당 출력을 막나) | 거부 건 중 샘플(예시: 일 50건 또는 5%), 라벨 결과 전수 보존 |
| 재생성 루프 | 노드 `invoke_agent` 속성 + 자식 `generation.generate`×N(`gen_ai.*` 토큰) | `agent.regen_count, agent.regen_cap, agent.regen_cap_hit, agent.fallback_path`(default / last_pass / human), `agent.hint_template_version, agent.model_version, agent.prompt_version` | 요청당 재생성 횟수 p95·상한 도달률(→ 동명 SLI), 재생성이 차지하는 토큰·비용 비중, 폴백 경로 분포 | 메타 전수. 상한 도달 건은 전 시도 본문 전수 |
| 변환기 실행(Text-to-SQL / Cypher) | `tool.invoke query_exec`, 앞에 `verify.schema`(구문·허용 테이블·읽기 전용), 부모 노드 `invoke_agent` | `agent.query_lang, agent.query_hash, agent.schema_version, agent.rows_returned, agent.error_class`(syntax / exec / timeout), `agent.degradation[]=vector_fallback` | 실행 오류율·쿼리 타임아웃률, 벡터 폴백률, "정확한 집계 불가" 표시율 | 쿼리 본문 opt-in(해시). 실패·폴백 건 전수 |
| 코드 샌드박스 | `tool.invoke code_sandbox` | `agent.sandbox.cpu_ms, agent.sandbox.mem_peak_mb, agent.sandbox.net_attempts, agent.sandbox.fs_attempts, agent.sandbox.killed_reason`(time / mem / policy), `agent.code_hash` | 자원 초과 종료율, **네트워크·파일 시도 건수**(0이어야), 킬 스위치 상태 | 시도·종료 건 전수 + 코드 해시, 보안 이벤트 스트림으로 복제 |
| 온톨로지 추론·KG 존재 검사 | `verify.solver`(온라인 추론기), `tool.invoke kg_lookup` | `agent.ontology_version, agent.inference_mode`(online / materialized), `agent.degradation[]=inference_skipped, agent.kg_result`(found / unverified) | 추론기 p95·타임아웃률, "미확인" 등급 비율(노드별), 배치 구체화 경과 시간 | 메타 전수 |

| 알림 | 조건 (예시) | 심각도 | 런북 (첫 3단계) |
|---|---|---|---|
| 검증 실패율 급등 | 노드별 실패율 > 베이스라인 2배 15분; `rules_version` 변경 후 24시간은 1.5배 | P2 (툴 인자 노드는 P1) | ① 직전 규칙 세트 버전 자동 롤백 발동 여부·보안 규칙 제외 확인 ② 거부 사유 코드 상위 3개와 규칙 ID 식별 ③ 거부 샘플 20건 리뷰 → 오탐이면 규칙 소유자, 정당 거부면 상류 프롬프트 |
| 검증기 다운 | `verify.*` 오류율 > 5% 1분, 또는 정책 엔진·추론기 헬스 실패 | P1 | ① fail-closed 노드(등급 3 이상)가 실제로 차단 중인지 — 쓰기 경로 호출 수 0 확인 ② 엔진·추론기 인스턴스 상태 ③ fail-open 노드의 "검증 없음 표시"가 붙었는지 `fail_mode=open` 통과 건수로 확인 |
| 재생성 폭주 | 상한 도달률 > 0.5% 30분, 또는 요청당 `generation.generate` 수 p95 > 3 | P2 | ① 노드·입력 유형별 집중 확인 ② 상한 1로 임시 축소 피처 플래그 ③ `hint` 템플릿·스키마·모델 버전 변경 이력 대조 |
| 샌드박스 이상 | `net_attempts` 또는 `fs_attempts` 1건 이상; 자원 초과 종료율 > 5% 1시간 | P1 (시도) / P3 (자원) | ① 코드 해시·세션·테넌트 격리 ② 반복 시 코드 실행 툴 킬 스위치 ③ 보안 책임자 통보, 패턴을 규칙 1층에 추가 |
| 변환기·추론기 지연 | 쿼리 타임아웃률 > 3% 또는 추론기 p95 > 300ms 15분 | P3 | ① 스키마·공리 변경 이력 ② 벡터 폴백·추론 생략 저하가 표시와 함께 동작하는지 확인 ③ 프로파일 재검토 요청 |

- **대시보드에서 이 단계를 보는 뷰**: ② Reasoning 패널 — 노드·층별 검증 실패율, 거부 사유 코드 분포, 검증기 가용성·p95, 재생성 횟수 히스토그램. ③ 비용·판정 분포 — 재생성 토큰 비중, 게이트 출력 분포(통과 / 차단 / 승인 / 미확인 저하), 규칙 ID별 오탐 기여도.
- **감사 추적으로 넘기는 필드(관측 로그와 분리)**: 노드 ID, 층별 결과(`layer, code, path`), 적용 규칙 ID·규칙 세트 버전, 온톨로지·SHACL 버전, 재생성 횟수, 최종 경로(합격 / 폴백 / 차단 / 승인), 폴백 사유, 변환기 패턴의 실행 쿼리·코드 해시와 실행 결과 요약. 관측 스팬에는 코드·개수·해시만.
- **이 단계의 관측이 없으면 못 보는 장애**: **오탐 폭증**. 검증기 입장에서는 거부가 성공이라 오류율 0%·지연 정상이다. 거부 건 샘플링과 리뷰 라벨이 없으면 정당한 출력이 대량 거부되는 것을 재생성 비용 상승이나 "처리할 수 없다" 민원으로만 안다. 반대편의 fail-open 통과(검증 없이 나간 응답)도 `fail_mode` 속성이 없으면 흔적이 남지 않는다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | 검증기 자체는 등급을 갖지 않고 **보호하는 행동의 등급을 따른다**. 자유 텍스트 검증 = 1, 추출 데이터 검증 = 2(그래프에 쓰임), 툴 인자 게이트 = 해당 툴 등급(2~5). 등급 3 이상 행동 앞의 검증기는 fail-closed 필수 |
| 가드레일 위치 | **출력** 지점(생성 결과의 citation·정합성 검증기, 추출 트리플의 SHACL)과 **행동** 지점(툴 인자 스키마 → 규칙 게이트). 이 페이지의 "게이트 패턴"이 1/07의 행동 가드레일 그 자체 |
| 게이트 출력과 판정 수단 | 통과(모든 층 합격) / 차단(규칙 위반 — `retryable=false`, 규칙만) / 승인 요청(규칙 통과 ∧ 결정 모델 p 낮음, [12](12-guardrails-hitl.md)로) / 저하(검증기 다운 시 등급 1 노드만 "검증 없음 표시", KG "미확인" 등급). 규칙이 최종 결정권 |
| 소유자 (A) | 규칙 세트: 보안 책임자(권한·한도) 또는 제품 책임자(도메인 규칙) — 규칙마다 명시. 온톨로지·SHACL: 도메인 소유자. 스키마·재생성 정책: AI 엔지니어 책임, 아키텍트 A. 샌드박스: 플랫폼 엔지니어 |
| 감사 추적에 남길 필드 | 노드 ID, 검증기 층별 결과(`layer, code, path`), 적용 규칙 ID·**규칙 세트 버전**, 온톨로지·SHACL 버전, 재생성 횟수, 최종 경로(합격·폴백·차단·승인), 폴백 사유, 변환기 패턴이면 실행된 쿼리·코드 해시와 실행 결과 요약 |

### 운영 준비도 체크
- [ ] 노드마다 검증기 다운 시 fail-closed / fail-open이 사전 결정되어 있고, 등급 3 이상은 fail-closed인가
- [ ] 규칙 세트가 코드 밖 버전 데이터이고 직전 버전으로 즉시 롤백할 수 있는가
- [ ] 보안·권한·한도 규칙은 자동 저하·롤백 대상에서 제외되어 있는가
- [ ] 검증 실패율 급등 알림과 거부 샘플 리뷰 런북이 있는가
- [ ] 재생성 상한을 배포 없이 조정하는 피처 플래그가 있는가
- [ ] 규칙 테스트 스위트가 CI에 있고 규칙 변경 시 자동 실행되는가
- [ ] 온톨로지 변경의 전파 범위(enum·SHACL·결정 enum·UI)를 표로 추적하는가
- [ ] 감사 레코드에 규칙 세트 버전이 있어 과거 판정을 재현할 수 있는가
- [ ] 거부 건을 노드·규칙 ID로 층화 샘플링해 리뷰 라벨(정당 / 정당 거부)을 붙이고, 오탐률을 규칙 ID별 기여도로 보는가
- [ ] `verify.schema/rules/solver` 스팬에 `agent.rules_version`·`agent.fail_mode`가 있어 fail-open으로 통과한 응답을 트레이스에서 식별할 수 있는가
