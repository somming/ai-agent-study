# 결정 레이어: System One 모델과 Decisions API ★

> **범위**: Jev, OpenAI Decisions API 등 결정 모델을 게이팅·라우팅·판정에 배치하는 설계와 한계
> "판정과 생성을 분리한다"는 원칙([Part 1/02](../01-foundations/02-system1-vs-system2.md))을 Part 3의 실행 그래프에 **어디에 어떻게** 구현하는가. 결정 모델의 개념·제품 비교의 심화는 [Part 6/decision-models](../06-trends/decision-models.md)에 두고, 여기서는 배치 지점·질문 정의·임계값·폴백·평가셋·트레이스를 다룬다.

## 요약 (3줄)

1. 결정 레이어(decision layer)는 별도 컴포넌트가 아니라 **실행 그래프 곳곳에 꽂히는 판정 노드의 집합**이다. 대표 지점은 다섯 곳 — intent 라우팅, 검색 결과 필터, 다음 행동 선택, 승인 필요 판정, 출력 품질 게이트.
2. 결정 모델(Jev / Decisions API)의 가치는 "답"이 아니라 **보정 확률(calibrated probability)**이다. 확률이 있어야 "자동 / 명확화 / 사람" 세 갈래 임계값을 둘 수 있다. 단 보정 여부는 벤더 주장이므로 한국어 평가셋으로 `[실측]`해야 한다.
3. 결정 모델은 **규칙 뒤, LLM 앞**에 선다. 규칙이 결정할 수 있는 것은 규칙이, 선택지가 열린 것은 LLM이, 그 사이의 닫힌 판정만 결정 모델이 맡는다. 결정 모델 장애 시 폴백은 규칙 또는 보수적 기본 경로다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 판정 지점 목록과 각 지점의 타입드 질문 정의(버전 관리) ② 지점별 임계값(θ)과 세 갈래 경로 ③ 폴백·장애 대응 ④ 한국어 평가셋과 보정 측정 결과 ⑤ 판정 트레이스 스키마 |
| **언제** (When) | 실행 그래프에 분기가 있으면 항상 (분기 = 판정). 결정 모델 **도입**은 ① 선택지가 닫혀 있고 ② 라벨 데이터가 적거나 질문이 자주 바뀌며 ③ 확신도가 필요할 때. 라벨 수천 건이 있고 카테고리가 고정이면 분류기가, 결정론이면 규칙이 먼저다 |
| **어떻게** (How) | ① [Part 1/02](../01-foundations/02-system1-vs-system2.md) 절차로 분기점 목록화 → ② 다섯 배치 지점에 대응시켜 타입드 질문 정의 → ③ 한국어 평가셋 구축(지점별) → ④ 결정 모델·분류기·소형 LLM을 같은 셋으로 비교, 보정 곡선 측정 → ⑤ 비용 비대칭으로 θ 설정 → ⑥ 섀도 모드 → 부분 트래픽 → 전환 → ⑦ 트레이스와 사람 판정을 라벨로 환류 |
| **왜** (Why) | 판정을 LLM 프롬프트에 두면 요청당 비용의 큰 몫이 판정에 쓰이고, 같은 입력에 다른 경로가 나와 재현이 안 되며, "확률 80%"라는 텍스트는 보정되지 않아 임계값이 의미가 없다. 결정 레이어가 없으면 HITL은 "항상 승인" 아니면 "절대 승인 안 함"의 양자택일이 된다 |

## 문제와 맥락

Part 3의 실행 그래프를 그려 보면 LLM 호출보다 분기가 많다. "어느 경로인가", "이 청크를 넣을까", "툴을 부를까 답할까", "승인을 받을까", "이 답을 내보낼까". 2025년까지 이 분기들은 대부분 소형 LLM 프롬프트("다음 중 하나로 답하라")로 처리됐다. 2026-09 이후 TypeSafe AI **Jev**(2026-09-15 얼리액세스)와 OpenAI **Decisions API**(2026-09-29 DevDay 발표, 10월 초 퍼블릭 베타 보도 — 날짜는 소스 간 충돌 `[2차]`)가 "생성 없이 타입드 판정만 돌려주는" 상용 선택지를 열었다.

두 제품은 인터페이스가 비슷하지만 내부가 다르다. Jev는 비자기회귀(non-autoregressive) 단일 패스의 **결정 전용 모델**이고 `[벤더]`, Decisions API는 범용 생성 모델(gpt-6-luna)의 출력을 제약한 **엔드포인트**(`POST /v1/decisions`)로 별도 결정 전용 모델이 아니다 `[2차]`. 지연·비용·보정 품질이 다를 수 있으므로 같은 범주로 설계하되 `[실측]`은 따로 한다.

## 핵심 개념

### 배치 지점 5곳과 타입드 질문

타입드 질문(typed question)은 코드로 정의한 닫힌 질문이다. 세 형태만 쓴다 — **선택**(choice: 선택지 중 하나), **예/아니오**(boolean: 조건 참 확률), **점수**(score: 루브릭 0~1). 아래는 의사 코드 예시이며 실제 SDK 문법은 제품마다 다르다.

| # | 지점 | 그래프 위치 | 질문 정의 예 | 출력 | 규칙과의 관계 |
|---|---|---|---|---|---|
| 1 | **intent 라우팅** | 입력 직후, [02](02-query-understanding.md) | `choice("요청의 의도", options=[faq, 주문조회, 불만접수, 범위밖], state={user_msg, last_turns})` | 선택 + 확률 분포 | 금칙어·권한은 규칙이 먼저 |
| 2 | **검색 결과 필터** | 검색 후 생성 전, [03](03-retrieval-reranking.md) | 청크별 `boolean("이 청크는 질의에 답하는 데 필요한가", state={query, chunk})` 병렬 | 청크별 확률 | 접근 권한 필터는 규칙 |
| 3 | **다음 행동 선택** | 에이전트 루프 각 스텝, [06](06-agent-design-patterns.md) | `choice("다음 행동", options=[추가검색, 툴:X, 툴:Y, 답변, 명확화질문, 에스컬레이션], state={goal, progress, budget})` | 선택 + 확률 | 예산 초과·허용 행동 집합은 규칙 |
| 4 | **승인 필요 판정** | 툴 실행 직전, [09](09-tools-and-mcp.md)·[12](12-guardrails-hitl.md) | `boolean("이 툴 호출은 사람 승인이 필요한가", state={tool, args, user_role, policy_summary})` | 확률 | **규칙이 최종**. 규칙 "필수 승인"이면 모델 무시 |
| 5 | **출력 품질 게이트** | 응답 직전, [04](04-generation-grounding.md)·[12](12-guardrails-hitl.md) | `score("답변이 제시된 근거에 부합하는 정도", state={answer, citations})`, `boolean("범위 밖 내용 포함")` | 점수·확률 | PII·금칙어는 규칙 |

질문 정의는 **버전 관리**한다. 선택지 하나를 추가해도 분포가 바뀌므로 평가셋 재측정 대상이다. 선택지 enum을 온톨로지 클래스에서 가져오면 데이터 모델과 동기화된다.

### 보정 확률과 임계값 설계

결정 모델이 돌려주는 확률 p가 **보정**되어 있다는 것은 "p=0.8인 판정 100건 중 약 80건이 맞다"는 뜻이다. 벤더는 보정을 주장하지만(Jev의 RLCD `[벤더]`) 한국어·도메인에서의 보정은 측정 전까지 모른다.

- **측정**: 평가셋에서 신뢰도 다이어그램(reliability diagram)과 ECE(expected calibration error)를 지점별로. 보정이 나쁘면 사후 보정(temperature scaling 류)을 호출자 측에서 적용하거나 임계값을 경험적으로 잡는다
- **세 갈래 임계값**: θ_high 이상 → 자동 진행, θ_low 미만 → 보수적 경로(사람·거부·기본값), 사이 → 명확화 질문 또는 추가 정보 수집 후 재판정
- **비용 비대칭으로 θ 결정**: 오탐(해도 되는 것을 막음)과 미탐(막아야 할 것을 통과)의 비용이 다르다. 승인 판정(#4)은 미탐 비용이 크므로 θ_high를 높게, 검색 필터(#2)는 오탐(필요한 청크 제거)이 더 아프므로 낮게. "θ=0.5"는 설계가 아니다
- **지점별·세그먼트별 θ**: 한국어와 영어, 신규 사용자와 기존 사용자의 보정이 다를 수 있다. 트레이스로 세그먼트별 정확도를 보고 θ를 분리
- **재보정 주기**: 질문 정의·모델 버전·입력 분포가 바뀌면 재측정. 월 1회 이상 드리프트 점검

### 결정 레이어의 위치: 규칙 → 결정 모델 → LLM

```
입력 ─▶ [규칙: 권한·금칙어·한도·형식] ─▶ [결정 모델: 닫힌 판정 + p] ─┬─ p ≥ θ_high ─▶ 자동 (LLM 생성 또는 툴 실행)
                                                                  ├─ θ_low ≤ p < θ_high ─▶ 명확화 / 추가 정보 → 재판정
                                                                  └─ p < θ_low ─▶ 사람 승인 / 거부 / 보수적 기본값
결정 모델 장애·타임아웃 ─▶ [폴백: 규칙 기본 경로 또는 보수적 경로] ─▶ 트레이스에 폴백 표시
```

규칙이 결정한 것을 모델이 뒤집을 수 없게 코드 구조로 보장한다([10](10-neuro-symbolic-reasoning.md) 게이트 패턴). 결정 모델이 LLM 뒤에 서는 경우는 #5 품질 게이트뿐이다.

### 폴백과 장애 대응

- **판정 인터페이스 추상화**: `decide(question, state) → {choice, p, meta}` 한 인터페이스 뒤에 Jev / Decisions API / 분류기 / 소형 LLM / 규칙을 구현체로. 벤더 교체·A/B·폴백이 코드 변경 없이 가능해진다
- **타임아웃은 짧게**: 결정 모델의 존재 이유가 저지연이므로(Jev 70~500ms E2E 주장 `[벤더]`) 타임아웃을 수백 ms 수준으로 두고 초과 시 즉시 폴백. 결정 모델을 기다리느라 LLM보다 느려지면 의미가 없다
- **폴백 순서**: 규칙 기본 경로(가능하면) → 캐시된 동일 입력 판정 → 보수적 경로(사람·거부). "폴백 = LLM 프롬프트"는 비용·지연이 튀므로 마지막 수단. 보수적 경로의 방향은 지점과 위험 등급에 따라 다르며(등급 1 읽기 경로는 기본 경로 계속, 권한·행동 경로는 사람 연결) 지점별 표는 아래 "운영 안정성" 소절 (불균형 ③ 반영)
- **섀도 모드 도입**: 기존 수단이 결정하고 결정 모델은 기록만 하는 기간을 거쳐 불일치 사례를 분석한 뒤 트래픽을 넘긴다
- **이중 벤더**: 고위험 지점은 두 결정 모델(또는 결정 모델 + 분류기)의 불일치를 사람 경로로 보내는 Parallel Vote([Part 1/02](../01-foundations/02-system1-vs-system2.md)) 가능

### 한국어 평가셋 설계

Jev는 영어 중심 학습이 명시되어 있고 `[2차]`, Decisions API의 한국어 성능도 독립 보고가 없다. **한국어 평가셋 없이 결정 모델을 채택하지 않는다.**

| 항목 | 지침 |
|---|---|
| 출처 | 실제 로그(익명화) > 도메인 전문가 작성 > LLM 합성(검수 필수). [Part 1/06](../01-foundations/06-evaluation-observability.md) 골든셋 규칙 |
| 구성 | 지점별 별도 셋. 선택지(카테고리)별 최소 수십 건, 보정 곡선을 그리려면 지점당 수백 건 |
| 언어 변이 | 한국어 격식/비격식, 존댓말/반말, 한영 혼합, 오타·띄어쓰기 오류, 영어 전용, 숫자·단위 표기 변이 |
| 경계 사례 | 두 선택지에 걸치는 입력, 범위 밖, 선택지에 없는 새 의도 — 이 사례에서 p가 낮게 나와야 보정된 것이다 |
| 라벨 | 라벨러 2인 이상 합의, 불일치 사례 별도 표시(모델에게도 어려운 것) |
| 비교군 | 같은 셋으로 파인튜닝 분류기·소형 LLM 프롬프트·규칙을 측정. 결정 모델이 **정확도와 보정 둘 다**에서 비교군을 이기지 못하면 채택하지 않는다 |
| 환류 | 운영 중 사람 판정(HITL 결과)과 불일치·폴백 사례를 주기적으로 셋에 추가 |

### 트레이스 기록 항목

판정 1건마다 다음을 기록한다. [Part 5/03](../05-cross-cutting/03-observability-tracing.md)의 스팬 안에 자식 스팬 또는 이벤트로.

`decision_point_id`, `question_version`, 입력 참조(본문은 opt-in, 해시·ID), 선택지 목록, 선택 결과, 확률 분포(전체), 적용된 θ_high/θ_low, 결과 경로(자동/명확화/사람/폴백), 규칙 게이트 결과(있다면), 구현체(제품·모델 버전), 지연, 비용, 최종 결과(사람이 판정했다면 그 라벨 → 평가셋 환류 후보).

이 기록이 있어야 ① 보정을 운영 데이터로 재측정하고 ② "왜 이 경로로 갔나"를 재현하며 ③ 결정 모델 교체 시 회귀를 잡는다.

## 아키텍처 / 파이프라인

```
요청 ─▶ 규칙 ─▶ ①intent 라우팅(p) ─▶ 검색 ─▶ ②청크 필터(p 병렬) ─▶ 에이전트 루프 ┐
                                                                                 ▼
                                   ③다음 행동(p) ─▶ 툴 호출 의도 ─▶ 규칙 게이트 ─▶ ④승인 필요(p) ─▶ 실행 / HITL
                                                                                 ▼
                                                      LLM 생성 ─▶ ⑤품질 게이트(score, p) ─▶ 응답 / 재생성 / 사람
모든 ①~⑤ ─▶ decide() 인터페이스 ─▶ {Jev | Decisions API | 분류기 | 소형 LLM | 규칙} ─▶ 트레이스
```

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

연구 노트의 결정 모델 비교표를 기준으로 하며, 성능 수치는 모두 `[벤더]`다.

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| **TypeSafe AI Jev** (결정 전용 모델, 비자기회귀 단일 패스, RLCD 주장) | 선택지 닫힘, 라벨 적음, 질문이 자주 바뀜, 보정 확률·저지연 필요(70~500ms E2E 주장), 대량 판정 | 이미지·음성 입력, 영어 외 언어 미검증(한국어 `[실측]` 전), 판정 사유 설명 필요 | 하 (호출, $0.042/1M 입력 보고) / 중 (평가셋·보정 측정) | 신생 (2026-09-15 EA) | `[벤더]` 지연·비용·보정 독립 벤치마크 없음. LangChain 테스트 1건 외 미확인 `[2차]` |

### 선택 가이드

- **결정론으로 답할 수 있다면** → 규칙. 이유: 확률로 판단하면 안 되는 영역이고 가장 싸다
- **라벨 수천 건·카테고리 고정·온프레미스라면** → 파인튜닝 분류기. 이유: 가장 빠르고 데이터 반출이 없다. 보정은 별도로
- **라벨 적음·질문 자주 변경·보정 확률 필요라면** → 결정 모델. 한국어 평가셋에서 분류기·소형 LLM과 비교 후. Jev와 Decisions API 중에서는 이미지 입력 필요·OpenAI 생태계면 후자, 지연·비용 민감이면 전자를 `[실측]`. 이유: 질문 정의만 바꾸면 되고 보정 확률로 세 갈래 임계값이 가능
- **선택지가 아직 정해지지 않았다면** → 소형 LLM으로 시작해 선택지가 굳으면 `decide()` 구현체만 교체. 이유: 인터페이스 추상화가 있으면 이전 비용이 작다
- **판단이 어려우면** → 규칙 + 소형 LLM 프롬프트로 시작하되 `decide()` 인터페이스와 트레이스를 먼저 만든다. 이유: 결정 모델은 아직 `[벤더]` 단계이고, 인터페이스·트레이스·평가셋이 있으면 언제든 교체·비교할 수 있다

## 설계 시 고려사항 (체크리스트)

- [ ] 실행 그래프의 모든 분기점이 다섯 배치 지점 중 하나에 대응되거나 "규칙" 또는 "LLM(열린 선택지)"로 분류되어 있는가
- [ ] 각 지점의 타입드 질문이 코드로 정의되고 버전 관리되는가
- [ ] 규칙 → 결정 모델 → LLM 순서가 코드 구조로 보장되고, 모델이 규칙을 뒤집을 수 없는가
- [ ] 지점별 θ_high/θ_low가 비용 비대칭을 근거로 설정되고 문서화되어 있는가
- [ ] 한국어·혼합·비격식·경계 사례를 포함한 지점별 평가셋이 있고 보정 곡선을 측정했는가
- [ ] 같은 평가셋으로 분류기·소형 LLM 비교군을 측정했는가
- [ ] `decide()` 인터페이스로 구현체가 추상화되어 교체·A/B·폴백이 가능한가
- [ ] 결정 모델 타임아웃이 수백 ms 수준이고 초과 시 폴백 경로가 있는가
- [ ] 섀도 모드 기간과 전환 기준(불일치율 상한)이 정해져 있는가
- [ ] 판정 트레이스에 확률 분포·θ·경로·구현체·사람 라벨이 기록되는가
- [ ] 사람 판정(HITL 결과)이 평가셋으로 환류되는 주기가 있는가
- [ ] 결정 모델에 보내는 상태에 불필요한 PII가 포함되지 않는가 (외부 API 전송)

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 결정 레이어는 **외부 API 하나(결정 모델)가 실행 그래프의 모든 분기에 꽂히는 구조**이므로, 그 API의 장애·드리프트·가격 변경이 그래프 전체로 번진다. 운영 설계의 핵심은 `decide()` 포트 뒤에서 이 전파를 끊는 것이다.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 판정 호출량 | 결정 모델 API의 **레이트 리밋**. 요청 1건이 다섯 지점을 지나고 #2 청크 필터는 청크 수만큼 병렬 호출하므로, 요청 수 10배 = 판정 호출 수 10배 × (5 + 청크 수) | 지점별 호출 예산, #2는 상위 k개만 또는 배치 질문, 동일 입력 판정 캐시, 레이트 리밋 도달 시 규칙 폴백 | 요청 수 × 지점 수 × 지점당 호출 수(청크 필터가 지배) |
| 질문 수(결정 지점 수) | 질문 정의 수가 늘면 평가셋·보정 측정·θ 관리가 질문 수에 비례. 각 질문에 수백 건 평가셋이면 질문 50개 = 수만 건 라벨 | 질문 템플릿화(같은 유형은 하나의 정의 + 파라미터), 평가셋을 질문 유형별로 공유, 보정 재측정 자동화 | 질문 수 × 질문당 평가셋 크기 × 재측정 주기 |
| 선택지 수(질문당) | 선택지가 수십 개면 분포가 평탄해져 p가 낮아지고 명확화 경로가 급증 | 계층 질문(상위 → 하위 2단계), 선택지 enum을 온톨로지에서 생성해 관리 | 선택지 수 × 경계 사례 수 |
| 테넌트·세그먼트 수 | 세그먼트별 θ가 테넌트 × 지점 × 세그먼트로 폭발 | θ를 기본값 + 오버라이드 구조로, 오버라이드는 보정 차이가 측정된 세그먼트에만 | 보정이 다른 세그먼트 수 |

결정 모델의 존재 이유가 저비용·저지연이므로, 호출량이 늘어도 **LLM 프롬프트 폴백으로 넘치면 비용이 수십 배 튄다**. 폴백은 규칙·캐시·보수적 경로가 먼저다.

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| **결정 모델 API 다운·타임아웃** | 분기가 전부 보수적 경로로 가서 승인·명확화가 급증, 지연 증가 | 결정 모델 오류율, 타임아웃률(수백 ms 상한), 폴백율 | `decide()` 폴백 순서: **규칙 기본 경로 → 동일 입력 캐시 → 보수적 경로**. 보수적 경로의 방향은 1/07 위험 등급으로 **배치 지점별**로 다르다 — #1 라우팅: 등급 1 **읽기 전용 경로**(기본 소스, 본인 권한 안)는 규칙 기반 기본 경로로 계속 + `routing_fallback`([02](02-query-understanding.md) 방식), **권한 경계를 넘거나 행동으로 이어지는 경로**는 "범위밖·사람 연결" / #2 청크 필터: 상위 k 그대로(등급 1) / #3 다음 행동: 선택된 행동 등급이 2 이상이면 "승인 필요", 1이면 규칙 기본 경로 / #4 승인 판정: 항상 "승인 필요" / #5 품질 게이트: 등급 1은 "미검증 표시 후 표시", 등급 2 이상은 "표시 보류". 서킷 브레이커 개방 시 트레이스에 `fallback=true`, 사용자 영향이 있는 폴백은 저하 코드 `decision_fallback`(라우팅은 `routing_fallback`)으로 계약 ② `degradation[]`([Part 0/01](../00-overview/01-reference-architecture.md))에 전달해 고지한다. 이 표가 라우팅 폴백 방향의 단일 기준이며 [02](02-query-understanding.md)·[Part 4/05](../04-dynamic-ui/05-intent-to-ui-mapping.md)가 참조한다 (불균형 ③ 반영) | 폴백율이 임계값(예시: 5분간 20%) 초과 시 온콜. 장기화 시 분류기 구현체로 전환 결정 |
| **보정 드리프트**(입력 분포 변화, 벤더 측 모델 업데이트) | θ가 맞지 않아 자동 비율이 갑자기 늘거나(미탐 증가) 줄어듦(승인 피로) | 세 갈래 비율의 주간 이동, ECE 상승, 사람 판정과의 불일치율 상승 | 세 갈래 비율이 범위를 벗어나면 **θ를 보수적 방향으로 자동 이동**(자동 비율 축소) + 알림. 자동 완화 방향으로는 이동하지 않음 — 완화(자동 비율 확대)는 **사람 결정 + 사후 샘플 감사**로만, [12](12-guardrails-hitl.md) "임시 확대 결정, 사후 감사 대상"과 같은 공통 규칙(2/09·3/02·4/05·4/06 동일, 불균형 ⑦ 반영) | 보정 재측정 후 θ 재설정. 벤더 모델 업데이트가 원인이면 질문 정의·평가셋 재검증 |
| **벤더 측 무통보 모델 변경** | 같은 입력에 다른 판정, 회귀 테스트 통과율 하락 | 섀도 비교(이전 판정 캐시 대비 불일치율), 야간 L2 라우팅 정확도 | 불일치율 급등 시 **이전 구현체(분류기·규칙)로 자동 전환**하고 결정 모델은 섀도로 강등 | 벤더 변경 내역 확인, 평가셋 재측정 후 복귀 |
| **레이트 리밋 도달** | 피크 시간대에 폴백 급증 | 429 응답률 | 지점 우선순위에 따라 **저위험 지점부터 규칙·캐시로 전환**(#2 청크 필터 먼저, #4 승인 판정은 마지막) | 한도 상향 협의 또는 분류기 병행 |
| **질문 정의 배포 오류**(선택지 누락·오타) | 특정 의도가 전부 "범위밖"으로, 또는 존재하지 않는 선택지 반환 | 선택지 분포 급변, 스키마 검증 실패(반환값이 enum 밖) | 반환값 enum 검증 실패 시 **직전 질문 버전으로 롤백**(질문은 데이터) | 질문 소유자가 수정 버전 배포 |
| **외부 전송 데이터에 PII 포함** | 즉시 보이지 않음 — 감사에서 발견 | 전송 전 PII 스캐너 플래그율 | 전송 직전 마스킹, 마스킹 불가 필드는 **전송 차단 + 규칙 폴백** | 플래그 반복 시 상태 구성 재설계 |

SLI 후보: 결정 모델 가용성(성공 응답 비율), p95 지연(수백 ms 상한 대비), 폴백율, 지점별 ECE, 세 갈래 비율(자동/명확화/사람), 사람 판정 불일치율. SLO 초안(예시): 가용성 99.9%, p95 500ms 이내, 폴백율 2% 이하, 승인 판정(#4) ECE 0.05 이하, 세 갈래 비율은 지점별 범위(예시: #1 자동 85~95%) 유지. 쓰기 행동은 이 단계에 없다. 단 #4 승인 판정의 결과가 쓰기 실행으로 이어지므로 **규칙 재검증(Rule ∧ Model)이 결정 모델 결과 뒤에 반드시** 있어야 하고, 폴백 시 "승인 필요"로 가는 것이 미탐 방지의 마지막 선이다.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| **결정 질문 정의**(`question_version`) | 해당 지점의 분포 전체. 선택지 하나 추가도 재측정 대상 | 지점별 평가셋 정확도·F1·혼동 행렬 + **보정 재측정** | θ(질문이 바뀌면 θ도 재설정), 온톨로지 enum(선택지 소스) |
| **임계값 θ_high/θ_low**(지점·세그먼트별) | 세 갈래 비율, 승인량, 미탐·오탐 | 세 갈래 비율 시뮬레이션(평가셋 재적용), 비용 비대칭 재계산 | 보정 측정 결과(θ는 보정의 함수) |
| **결정 모델 구현체·버전**(Jev / Decisions API / 분류기 / 소형 LLM) | 모든 지점의 정확도·보정·지연·비용 | 전체 지점 평가셋 + 보정 곡선 + 섀도 비교 | 질문 정의 포맷 어댑터, θ 전체 재측정 |
| **한국어 평가셋** | 측정값 자체(셋이 바뀌면 비교 불가) | 셋 버전 간 공통 부분으로 연속성 확인 | 라벨 가이드 버전 |
| **폴백 순서·타임아웃·캐시 정책** | 가용성, 폴백 시 경로 | 장애 주입 테스트(결정 모델 차단 후 경로 확인) | — (설정 단독) |
| **트레이스 스키마**(판정 기록 항목) | 보정 재측정·환류 파이프라인 | 스키마 호환 | 평가 파이프라인 파서 |

롤백 단위: 질문 정의 + θ + 보정 측정 결과는 한 묶음(질문만 롤백하고 θ를 두면 어긋남). 구현체 교체는 `decide()` 어댑터 단독. 기술 부채로 기록할 것: "#2 청크 필터는 소형 LLM, 결정 모델 전환은 호출량 `[실측]` 후", "θ는 전 세그먼트 공통, 한국어/영어 분리는 보정 차이 측정 후", "Parallel Vote 미도입".

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **모델**(결정 모델 벤더 교체·버전 업·가격 변경) | Jev ↔ Decisions API ↔ 분류기, 모델 내부 업데이트 | **`decide(question, state) → {choice, p, meta}` 포트** | 구현체 어댑터 | **어댑터 교체 + 섀도 기간**(기존 구현체가 결정, 신규는 기록만) → 불일치율 상한 통과 후 전환 → θ 재측정 | `decide()` 뒤만. 호출 측 코드 불변. 단 θ 전체 재측정 |
| **규칙·정책**(질문 정의·임계값·선택지) | 선택지 추가, θ 조정, 비용 비대칭 변경 | 질문 정의 스키마(choice / boolean / score), 트레이스 스키마 | 질문 정의 파일, θ 표 | **코드 밖 버전 데이터**로 설정 교체 + 평가셋 재측정. 시행일 기록 | 해당 지점 + 하류 경로의 분포 |
| **도메인 모델**(온톨로지) | 선택지 enum의 소스 변경 | 온톨로지 → enum 생성 규칙 | enum 생성기 | 온톨로지 버전 상승 시 질문 정의 자동 재생성 + 재측정 | 질문 정의 → 평가셋 라벨 → θ |
| **지식**(평가셋·라벨) | 운영 HITL 결과 환류, 새 경계 사례 | 평가셋 스키마, 라벨 가이드 | 셋 내용 | 주기적 추가(월 1회 예시) + 셋 버전 | 보정 측정값만 |
| **사용자 환경**(언어·세그먼트) | 한국어 비율 변화, 신규 사용자군 | θ 기본값 + 오버라이드 구조 | 세그먼트별 θ, 언어별 평가셋 | 세그먼트 키로 θ 분기, 보정 측정 후 오버라이드 추가 | 해당 세그먼트 θ |
| **프로토콜·SDK** | 벤더 SDK 문법 변경 | `decide()` 포트 | 어댑터 | 어댑터 교체, 버전 고정 | 어댑터만 |
| **부하·규모** | 판정 호출량 10배 | 포트, 캐시 키 규약 | 캐시, 배치 질문 | 캐시 + 지점별 예산 | 레이트 리밋 협의 |

가장 자주 바뀌는 것: **θ와 질문 정의(규칙·정책)** > 평가셋 > 결정 모델 벤더·버전 > 온톨로지. 결정 모델 벤더 교체는 드물지만 영향이 가장 넓으므로 `decide()` 포트와 섀도 절차를 처음부터 둔다. 코드 밖 설정으로 둘 것: 질문 정의, θ 표, 폴백 순서, 타임아웃, 캐시 TTL, 지점별 호출 예산. 포트·어댑터 뒤에 둘 외부 의존: 결정 모델 API(둘 다), 분류기 서빙, 소형 LLM.

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성의 "탐지 신호"가 **실제로 어디서 나오는지**를 설계한다. 기준은 [Part 1/07 관측성 설계 요소](../01-foundations/07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md). 결정 레이어의 장애는 대부분 **오류 없이** 온다 — API는 응답하고 지연도 정상인데 θ가 현실과 어긋나는 것이다. 그래서 이 단계의 1차 신호는 RED가 아니라 **지점별 확신도 분포·결정 소스 분포·폴백률**이고, 보정(ECE)은 주기적으로 재측정하는 지표다. 결정 모델 스팬은 출력 토큰이 없어 `gen_ai.*` 매핑이 얕으므로 `agent.*` 자체 속성이 주가 된다.

| 기록 대상 | 스팬 / 이벤트 (이름, 부모) | 핵심 속성 (버전 키 포함) | 지표 (→ 어느 SLI) | 샘플링 · 보존 · PII |
|---|---|---|---|---|
| 판정 1건 | `decision.decide {question}`, 부모 `invoke_agent {name}`(배치 지점 #1~#5) | `agent.decision_point_id, agent.question_version, agent.decision`(선택), `agent.confidence`(선택 p), `agent.confidence_dist_hash`(분포 전체는 감사로), `agent.threshold_high / threshold_low, agent.route`(auto / clarify / human), `agent.decision_source`(rule / decision_model / classifier / llm), `agent.impl_version, agent.model_version, agent.rules_version`(후속 규칙 게이트) | 지점별 호출 수·오류율·p95(→ 가용성·p95 SLI), **확신도 히스토그램**(지점·버전별, 0.05 버킷), **세 갈래 비율**(→ 동명 SLI), **결정 소스 분포**(규칙이 얼마나 가로채나) | 메타 **전수, 샘플링 없음**(보정 재측정의 모집단). 입력 본문 opt-in(해시) |
| 폴백·저하 | `decision.decide` 속성 `agent.outcome=fallback` + `agent.fallback_reason`(timeout / error / rate_limited / circuit_open / enum_invalid), `agent.fallback_impl`(rule / cache / conservative), `agent.degradation[]=decision_fallback` 또는 `routing_fallback`(계약 ②) | 지점 ID, 보수적 경로 방향(승인 필요 / 범위밖 / 기본 경로) | **폴백률**(지점별 → 동명 SLI), 429 비율, 서킷 개방 시간, 보수적 경로 유입량(→ [12](12-guardrails-hitl.md) 승인 큐의 선행 신호) | 폴백 건 전수 |
| 보정 모니터링 | 오프라인 `eval.run calibration {question}` — **주 1회 예시 + 벤더 모델 업데이트 공지 시 즉시 + 질문·θ 버전 변경 시**; 온라인 `eval.sample`(사람 최종 라벨이 붙은 턴) | `agent.eval_suite_version, agent.evalset_version, agent.question_version, agent.ece, agent.bins[]`(버킷별 평균 p·실제 양성률·표본 수) | **지점별 ECE**(→ 동명 SLI), 신뢰도 곡선의 버킷별 이동, 라벨 표본 수(신뢰구간) | 전수(결과는 작음). 라벨 표본은 환류 후보로 보존 |
| 사람 판정 환류 | `approval.resolve`(#4), 명확화 응답 `ui.event`(#1·#3), 사후 리뷰 라벨을 `request_id`로 `decision.decide`에 조인 | `agent.human_label, agent.label_source`(approval / clarify / review), `agent.label_lag_ms` | 사람 판정 불일치율(→ 동명 SLI), #4 승인 후 되돌림률, 라벨 지연(보정 재측정이 얼마나 최신인가) | 전수 — 평가셋 환류 후보 |
| 섀도 비교 | `decision.decide {question}`의 자식 `decision.decide {question}:shadow`(기록만, 경로에 영향 없음) | `agent.shadow_impl, agent.shadow_version, agent.shadow_choice, agent.shadow_mismatch` | 섀도 불일치율(일·주, 지점별), 야간 `eval.run routing_l2` 정확도 | 불일치 건 전수 |
| 질문 정의 검증·외부 전송 PII | `verify.schema`(반환값이 선택지 enum 안인지), `gate.evaluate pii_outbound`(결정 모델로 보내는 상태의 스캔), 둘 다 부모 `decision.decide` | `agent.enum_invalid, agent.question_version, agent.pii_flag, agent.pii_masked, agent.fields_dropped[]` | 선택지 분포(지점·질문 버전별 — 급변이 배포 오류 신호), enum 밖 반환률, 전송 전 PII 플래그율·차단률 | 플래그 건 전수(마스킹). 전송 본문은 기록하지 않음 |

| 알림 | 조건 (예시) | 심각도 | 런북 (첫 3단계) |
|---|---|---|---|
| 폴백률 | 지점별 폴백률 > 20% 5분(SLO 2% 대비) | P1 (#4 승인 판정 포함) / P2 | ① `fallback_reason` 분포로 timeout·429·circuit 구분 ② 벤더 상태·레이트 한도 확인 ③ 보수적 경로 유입에 따른 승인 큐·"범위밖" 응답 증가를 [12](12-guardrails-hitl.md) 대시보드에서 확인 |
| 확신도 분포 드리프트 | 지점별 확신도 히스토그램의 7일 이동 PSI > 0.2, 또는 세 갈래 비율이 지점 범위(예시: #1 자동 85~95%) 이탈 1일 | P2 | ① θ 보수적 자동 이동이 발동했는지, 완화 방향 이동이 없었는지 확인 ② 섀도 불일치율을 같이 봐서 입력 분포 변화인지 벤더 모델 변경인지 분리 ③ ECE 즉시 재측정 예약, 결과까지 θ 완화 금지 |
| ECE 상승 | 재측정에서 #4 ECE > 0.05, 또는 어느 지점이든 전주 대비 +0.02 | P2 | ① 평가셋 버전·신규 라벨 유입량 확인(표본 부족인지) ② 깨진 버킷 식별(고확신 구간이면 미탐 위험) ③ θ 재설정 제안서 — 완화 방향은 사람 결정 + 사후 샘플 감사 |
| 섀도 불일치 | 일 불일치율 > 베이스라인 +5%p | P2 | ① 벤더 변경 공지·`model_version` 변화 확인 ② 이전 구현체 자동 전환 동작 확인(결정 모델은 섀도로 강등) ③ 평가셋 재측정 후 복귀 결정 |
| 질문 정의 배포 오류 | `enum_invalid` 1건 이상, 또는 한 선택지 비중이 1시간 내 ±30%p | P2 | ① 직전 `question_version` 롤백 발동 확인 ② 질문 정의 diff(선택지 누락·오타) ③ 질문 소유자 통보, 영향 구간의 판정 재처리 여부 결정 |

- **대시보드에서 이 단계를 보는 뷰**: **③ 비용·판정 분포가 이 페이지의 주 화면** — 지점별 확신도 히스토그램(현재 vs 7일 전 겹침), 결정 소스 분포(rule / decision_model / classifier / llm), 세 갈래 비율 추이, 폴백률·폴백 사유, 지점별 호출 비용. ② Reasoning 패널 — 지점별 RED, ECE 추이(재측정 시점 표시), 섀도 불일치율.
- **감사 추적으로 넘기는 필드(관측 로그와 분리)**: "트레이스 기록 항목" 전체 — `decision_point_id, question_version`, 입력 해시, 선택지 목록, **확률 분포 전체**, 적용 θ, 결과 경로, 규칙 게이트 결과, 구현체·모델 버전, 폴백 여부·사유, 사람 최종 판정. **샘플링 없이 장기 보존**(#4 필수). 관측 스팬에는 선택 p와 분포 해시만.
- **이 단계의 관측이 없으면 못 보는 장애**: **보정 드리프트**. 오류율 0%, p95 정상인데 θ가 어긋나 자동 비율이 슬금슬금 늘고(미탐 증가) 또는 줄어(승인 피로) 간다. 지점별 확신도 히스토그램과 사람 라벨 조인이 없으면 수주 뒤 사고 또는 승인자 불만으로만 안다. 결정 소스 분포가 없으면 "규칙이 다 가로채서 결정 모델이 사실상 꺼져 있는" 상태도 못 본다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | 판정 자체는 등급이 없고 **판정이 이끄는 경로의 등급을 따른다**. #1 라우팅·#2 필터·#5 품질 게이트 = 1~2. #3 다음 행동 = 선택된 행동의 등급. **#4 승인 필요 판정 = 보호하는 툴의 등급(2~5)**이며, 등급 4~5 행동은 결정 모델 결과와 무관하게 규칙이 `require_approval` 또는 자동 실행 금지로 고정 |
| 가드레일 위치 | 결정 레이어는 가드레일의 **판정 수단**이지 가드레일 자체가 아니다. 입력 지점(#1 인젝션 의심 boolean), 출력 지점(#5 근거 부합 score), 행동 지점(#4 승인 필요 boolean)에 판정을 공급한다. 보안·권한·한도는 결정 모델에 묻지 않는다(규칙만) |
| 게이트 출력과 판정 수단 | 세 갈래가 게이트 4출력으로 매핑: p ≥ θ_high → 통과, θ_low ≤ p < θ_high → 저하(명확화·추가 정보), p < θ_low → 승인 요청 또는 차단(지점별). 규칙 위반은 p와 무관하게 차단. 수단은 규칙 → 결정 모델 → LLM 순 |
| 소유자 (A) | 질문 정의·θ: 제품 책임자(AI 엔지니어 R, 도메인 전문가 C). 결정 모델 벤더 선택·교체: 아키텍트(보안·법무 C — 외부 전송 데이터). 평가셋·라벨: AI 엔지니어 R, 제품 책임자 A. #4 승인 판정의 θ는 [12](12-guardrails-hitl.md) 승인 정책 소유자(운영 책임자)와 공동 |
| 감사 추적에 남길 필드 | 이 페이지 "트레이스 기록 항목" 전체가 감사 필드다: `decision_point_id, question_version`, 입력 해시, 선택 결과, **확률 분포 전체**, 적용 θ, 결과 경로, 규칙 게이트 결과, **구현체·모델 버전**, 폴백 여부·사유, 사람 최종 판정. 관측 로그와 달리 **샘플링 없이 장기 보존**(#4는 특히) |

### 운영 준비도 체크
- [ ] `decide()` 포트 뒤에 결정 모델 외 폴백 구현체(규칙·캐시·분류기)가 실제로 연결되어 있고 장애 주입 테스트를 통과했는가
- [ ] 결정 모델 타임아웃이 수백 ms 수준이고 초과 시 지점·등급별 폴백 표대로(등급 1 읽기 경로는 기본 경로 + `routing_fallback`, 권한·행동 경로는 사람 연결, 승인 판정은 "승인 필요")로 가며 `decision_fallback`이 계약 ②로 전달되는가 (불균형 ③ 반영)
- [ ] 세 갈래 비율의 범위 이탈 알림과 θ 보수적 자동 이동이 있는가(완화 방향 자동 이동은 없는가)
- [ ] 질문 정의·θ가 코드 밖 버전 데이터이고 질문 + θ + 보정 결과가 한 롤백 단위인가
- [ ] 섀도 비교(이전 구현체 대비 불일치율)가 상시 또는 주기적으로 도는가
- [ ] 등급 4~5 행동이 결정 모델 결과와 무관하게 규칙으로 고정되어 있는가
- [ ] 결정 모델로 전송되는 상태에 PII 마스킹이 있고 데이터 처리 계약을 확인했는가
- [ ] 판정 트레이스가 샘플링 없이 감사 저장소에 장기 보존되는가(#4 승인 판정 필수)
- [ ] 지점별 확신도 히스토그램·결정 소스 분포·폴백률이 대시보드 ③에 있고, 분포 드리프트(PSI) 알림이 θ 보수적 자동 이동과 연결되어 있는가
- [ ] ECE 재측정이 `eval.run calibration {question}`으로 자동화되어 주기(주 1회 예시)·벤더 변경 공지·질문/θ 버전 변경 시 돌고, 사람 라벨이 `request_id`로 판정 스팬에 조인되는가
