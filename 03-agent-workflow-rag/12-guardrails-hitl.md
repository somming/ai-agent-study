# 가드레일과 Human-in-the-Loop

> **범위**: 입출력 가드레일, 정책 엔진, 승인 흐름 설계
> 에이전트의 입력·출력·행동 세 지점에 두는 안전장치와, 사람이 개입하는 승인 흐름의 백엔드 설계. 승인 **화면**의 패턴은 [Part 4/06](../04-dynamic-ui/06-hitl-ui-patterns.md), 인젝션 공격 분류와 방어 전반은 [Part 5/01](../05-cross-cutting/01-security-prompt-injection.md), 판정 수단 자체는 [11](11-decision-layer.md)에 있으므로 여기서는 배치와 흐름을 다룬다.

## 요약 (3줄)

1. 가드레일(guardrail)은 세 지점에 둔다 — **입력**(인젝션·유해·범위 밖), **출력**(PII·근거 없음·정책 위반), **행동**(툴 실행 전 규칙 게이트). 세 지점의 위협이 다르므로 수단도 다르다. 출력 가드레일만 두고 "안전하다"고 하는 것이 가장 흔한 실수다.
2. HITL(Human-in-the-Loop)은 "위험하면 사람에게"가 아니라 **확신도와 비용 비대칭으로 라우팅되는 세 갈래 경로**다. 모든 것을 승인받게 하면 승인 피로(approval fatigue)로 사람이 보지 않고 승인하고, 아무것도 안 받으면 사고가 난다.
3. 승인 흐름은 **상태 머신**이다. 요청·대기·승인/거부/수정·만료·에스컬레이션의 상태와 전이를 명시하고, 대기 중에는 체크포인트([08](08-state-memory-context.md))로 실행을 멈춘다. Part 4의 HITL UI와는 이벤트 스키마로 계약한다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 세 지점별 가드레일 목록(위협 → 수단 → 실패 시 처리) ② 정책 엔진의 정책 집합과 테스트 ③ 승인 흐름 상태 머신(동기/비동기, 타임아웃, 에스컬레이션) ④ 확신도 기반 HITL 라우팅 임계값 ⑤ Part 4 HITL UI와의 이벤트 스키마 계약 ⑥ 감사 로그 |
| **언제** (When) | 입력 가드레일과 출력 PII는 **항상**. 행동 가드레일은 쓰기 이상 등급 툴이 있으면 항상. HITL 승인은 외부 전송·파괴적·금전·규제 행동이 있을 때. 읽기 전용 사내 QA라면 입력·출력 가드레일 + 사후 샘플링 리뷰로 충분하고 승인 흐름은 생략 |
| **어떻게** (How) | ① 세 지점의 위협을 목록화 → ② 각 위협에 규칙 → 분류기/결정 모델 → LLM judge 순으로 가장 단순한 수단 배정 → ③ 툴 등급([09](09-tools-and-mcp.md))별 행동 정책을 정책 엔진에 작성 → ④ 승인 필요 행동의 승인자·시한·에스컬레이션·만료 기본값 결정 → ⑤ 확신도 θ로 자동/명확화/사람 분기 → ⑥ 이벤트 스키마를 Part 4와 합의 → ⑦ 승인률·거부율·만료율·오탐률을 모니터링 |
| **왜** (Why) | 입력 가드레일이 없으면 인젝션이 그대로 모델에 닿고, 출력 가드레일이 없으면 PII·근거 없는 주장이 사용자에게 가며, 행동 가드레일이 없으면 모델의 확률적 판단이 곧 실행이 된다. HITL이 설계되지 않으면 승인은 "항상" 아니면 "절대"의 양자택일이 되어 둘 다 실패한다 |

## 문제와 맥락

가드레일 논의는 "유해 콘텐츠 필터"에서 시작했지만, 에이전트에서 더 큰 위험은 **행동**이다. 유해한 문장은 사용자가 보고 무시할 수 있지만, 잘못 실행된 환불·삭제·전송은 되돌리기 어렵다. 그리고 행동의 위험은 입력에서 온다 — 툴이 읽어 온 외부 문서의 한 줄이 다음 행동을 바꾼다([09](09-tools-and-mcp.md) 신뢰 경계).

HITL은 그 반대편 문제를 가진다. 승인을 너무 많이 요구하면 사람이 내용을 보지 않고 승인한다. 승인 피로는 보안 분야에서 오래 알려진 현상이며, 에이전트 승인에서도 같은 일이 벌어진다. 따라서 HITL 설계의 핵심 질문은 "무엇을 승인받을까"가 아니라 **"무엇을 승인받지 않아도 되게 만들까"**다.

## 핵심 개념

### 세 지점의 가드레일

| 지점 | 위협 | 1차 수단 (결정론) | 2차 수단 (판정) | 실패 시 처리 |
|---|---|---|---|---|
| **입력** | 직접 프롬프트 인젝션(지시 덮어쓰기) | 알려진 패턴 규칙 | 인젝션 분류기 / 결정 모델 `boolean("지시 주입 시도인가")` | 거부 또는 격리 모드(툴 비활성) |
| 입력 | 유해·불법 요청 | 금칙어 사전 | 모더레이션 분류기 | 거부 + 안내 |
| 입력 | 범위 밖 요청 | — | intent 라우팅의 `범위밖` 선택지([11](11-decision-layer.md) #1) | 범위 안내, 사람 연결 |
| **출력** (입력도 동일) | PII 노출·입력 | 패턴(주민번호·카드번호·전화) | NER 분류기 | 마스킹 또는 차단, 원문 저장 금지 |
| 출력 | 근거 없는 주장 | citation 존재·유효성 규칙 | 근거 정합성 검사기([04](04-generation-grounding.md)), 결정 모델 `score` | 문장 제거·재생성·"확인 불가" 표시 |
| 출력 | 정책 위반(약속·법적 단언·경쟁사 언급 등) | 금칙 표현 규칙 | 정책 분류기 / 결정 모델 | 재생성(상한) → 템플릿 폴백 |
| **행동** | 권한 밖 툴 호출 | 정책 엔진(사용자 역할 × 툴) | — | 차단 + 사용자 안내 |
| 행동 | 한도 초과(금액·건수·빈도) | 정책 엔진 | — | 차단 또는 승인 요청 |
| 행동 | 외부 데이터 읽은 후 전송(유출 패턴) | 시퀀스 규칙(등급 상향) | 결정 모델 `boolean("승인 필요")` | 승인 요청 |
| 행동 | 되돌릴 수 없는 작업 | 등급 "파괴적" 규칙 | — | 항상 승인 |

1차 수단이 결정할 수 있으면 2차는 호출하지 않는다. 2차 수단은 1차가 "모르겠다"일 때만 돈다.

### 정책 엔진

정책 엔진(policy engine, OPA/Rego류 또는 자체 규칙 엔진)은 행동 가드레일의 중심이다. 입력은 `{사용자(역할·권한), 툴(이름·등급), 인자, 세션 상태(외부 데이터 읽음 여부, 누적 금액), 시간}`, 출력은 `allow | deny | require_approval(approver_role, timeout)`의 세 값이다.

- 정책은 코드다. 저장소·리뷰·테스트·배포가 있다. "정책 변경 → 평가셋 통과 → 배포"의 CI
- 정책 결정은 트레이스에 남긴다(어느 규칙이 어떤 입력으로 어떤 결과를)
- 정책 엔진은 **모델보다 먼저, 모델 결과와 무관하게** 평가된다. 모델(LLM·결정 모델)이 "실행해도 됨"이라 해도 정책이 deny면 deny ([10](10-neuro-symbolic-reasoning.md) 게이트 패턴)
- 정책이 `require_approval`을 돌려주면 승인 흐름으로 넘어간다

### 승인 흐름 설계

```
[요청] ─▶ 대기(pending) ─┬─ 승인(approved) ─▶ 인자 해시 재검증 ─▶ 실행
                          ├─ 수정(edited) ─▶ 수정 인자 재게이트 ─▶ 실행
                          ├─ 거부(rejected) ─▶ 사용자 안내 + 대안 경로
                          ├─ 시한 초과 ─▶ 에스컬레이션(escalated) ─▶ 2차 승인자 대기 ─▶ (위와 동일)
                          └─ 최종 시한 초과 ─▶ 만료(expired) ─▶ 기본값 적용 (기본값 = 거부)
모든 전이 ─▶ 감사 로그 + 체크포인트 갱신
```

| 설계 항목 | 지침 |
|---|---|
| **동기 vs 비동기** | 동기: 요청한 사용자 본인이 대화 안에서 즉시 승인(수 초~수 분). 비동기: 승인자가 다른 사람·다른 채널(수 분~수 일). 비동기는 체크포인트 필수, 프로세스 종료 허용 |
| **승인 단위** | 단건 / 배치(같은 유형 N건 묶음) / 세션 사전 승인("이 세션에서 X 유형은 자동"). 승인 피로를 줄이는 주요 수단은 배치와 사전 승인 |
| **타임아웃** | 등급별로. 만료 시 기본값은 **거부**(안전 측). "만료 = 승인"은 쓰지 않는다 |
| **에스컬레이션** | 1차 승인자 미응답 → 2차 승인자. 단계·시한을 정책에. 최종 미응답은 만료 |
| **승인 내용** | 무엇을(행동·인자), 왜(근거·요청 맥락), 얼마나 확신하는가(결정 모델 p), 되돌릴 수 있는가, 대안. 인자를 원문으로 보여준다(요약만 보여주면 승인자가 틀린 것을 승인) |
| **승인 후 불변성·수정** | 승인된 인자의 해시를 저장하고 실행 직전 재검증. 승인자가 인자를 고쳐 승인하면 수정 인자를 다시 정책 엔진에 통과시킨다 |
| **감사 로그** | 요청·승인자·시각·결정·사유·실행 결과. 규제 대상이면 보존 기간 명시 |

### 확신도 기반 HITL 라우팅

[11](11-decision-layer.md)의 세 갈래를 승인 흐름에 연결한다.

| 정책 엔진 결과 | 결정 모델 p ("승인 필요") | 경로 |
|---|---|---|
| deny | — | 차단 |
| require_approval | — | 승인 (정책이 강제) |
| allow | p < θ_low (승인 불필요 확신) | 자동 실행 |
| allow | θ_low ≤ p < θ_high | 사용자에게 확인 질문(동기, 가벼운 HITL) |
| allow | p ≥ θ_high | 승인 요청 (비동기 가능) |

θ는 행동 등급별로 다르다. 되돌릴 수 있는 행동은 θ_high를 높게(자동 많이), 되돌릴 수 없는 행동은 정책에서 require_approval로 고정. **결정 모델이 없으면** 이 표는 정책 엔진 결과만으로 축소되고, 그 경우 승인 대상이 늘어 승인 피로가 커진다 — 결정 모델 도입의 가장 직접적인 효용이 여기다. 단 p의 보정은 `[실측]` 전제.

### Part 4 HITL UI와의 계약: 이벤트 스키마

백엔드는 이벤트를 발행하고 UI는 렌더·응답한다. 전송은 [AG-UI](../04-dynamic-ui/02-protocols-ag-ui-a2ui-mcp-apps.md)류 이벤트 스트림이든 자체 SSE든 무관하나 **스키마는 고정**한다. 최소 필드:

```
approval_requested {
  approval_id, run_id, checkpoint_id,
  action: { tool, args, effect_grade, reversible },
  rationale: { summary, evidence_refs[] },
  confidence: { p, threshold, source },          # 결정 모델이 있을 때
  options: [approve, reject, edit],
  approver: { role, user_id? }, expires_at, escalation: { to_role, after }
}
approval_resolved { approval_id, decision: approve|reject|edit, edited_args?, actor, timestamp, comment? }
approval_escalated { approval_id, from_role, to_role, timestamp }
approval_expired   { approval_id, applied_default: reject, timestamp }
```

UI 측 패턴(인라인 카드, 사이드 패널, 별도 큐)은 [Part 4/06](../04-dynamic-ui/06-hitl-ui-patterns.md). 백엔드 약속은 세 가지 — `approval_resolved`를 받으면 해당 `checkpoint_id`에서 재개한다, 같은 `approval_id`의 중복 응답은 첫 번째만 유효, 만료 후 응답은 무시하고 알린다.

## 아키텍처 / 파이프라인

```
입력 ─▶ [입력 가드레일: 규칙 → 분류기/결정 모델] ─▶ 라우팅·검색·루프
루프 ─▶ 툴 호출 의도 ─▶ [정책 엔진: allow/deny/require_approval] ─▶ [결정 모델: 승인 필요 p] ─▶ 자동 / 확인 / 승인 흐름(체크포인트 대기)
                                                                                                  └─ approval_* 이벤트 ⇄ Part 4 HITL UI
LLM 생성 ─▶ [출력 가드레일: PII 규칙 → 근거 검사 → 정책 분류기] ─▶ 응답 / 재생성 / 폴백
모든 판정·승인 ─▶ 감사 로그 + 트레이스 ─▶ 오탐·미탐·승인률·만료율 모니터링 ─▶ 정책·θ 조정
```

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 프롬프트 지시만 ("안전하게 답하라") | 프로토타입 | 운영 전부. 확률적 준수 | 하 | 표준 | `[검증]` 우회 사례 다수 |
| 규칙·패턴·사전 (금칙어, PII 정규식, 시퀀스 규칙) | 모든 시스템의 1층. 결정론이 필요한 PII·권한·한도 | 의미 기반 판단(우회 표현) | 하 | 표준 | `[검증]` |
| 가드레일 라이브러리 (오픈소스·벤더, 입출력 분류기 묶음) | 입출력 가드레일을 빠르게 갖춤, 소규모 팀 | 도메인 특화 정책, 행동 가드레일(대부분 미지원), 한국어 성능 미검증 | 하~중 | 안정 | `[2차]` 한국어 `[실측]` 필요 |
| 정책 엔진 (OPA/Rego류, 자체 규칙 엔진) | 행동 가드레일의 중심. 권한·한도·승인 정책을 코드로 | 자연어 의미 판단 | 중 (정책 관리) | 표준 | `[검증]` 엔진 자체, LLM 결합은 `[2차]` |
| 결정 모델 게이트 (Jev / Decisions API) | 승인 필요·인젝션 의심·근거 부합 같은 닫힌 판정을 보정 확률과 함께, 승인 피로 완화 | 보정 미검증, 한국어 미검증, 외부 전송 불가 데이터 | 하 (호출) / 중 (평가셋) | 신생 | `[벤더]` `[2차]` |
| LLM-as-judge 온라인 | 미묘한 정책 판단, 지연 허용 | 대량·저지연, 비용 | 상 | 안정 | `[검증]` 편향 보고 |
| 동기 HITL (대화 내 확인) | 요청자 본인이 승인 가능, 되돌릴 수 있는 행동, 수 초 내 응답 기대 | 승인자가 제3자, 규제상 분리 필요 | 하~중 | 표준 | — |
| 비동기 HITL (별도 승인자·큐) | 금전·규제·파괴적 행동, 승인자 분리 | 수 초 내 응답이 필요한 대화형 과업 | 중~상 (체크포인트·큐·에스컬레이션) | 표준 | — |
| 사후 샘플링 사람 리뷰 | 읽기 전용 QA, 가드레일 오탐·미탐 측정 | 되돌릴 수 없는 행동의 유일한 통제 | 중 | 표준 | `[검증]` |

### 선택 가이드

- **읽기 전용 QA라면** → 규칙 1층 + 입출력 가드레일 라이브러리 + 사후 샘플링 리뷰. 승인 흐름은 생략. 이유: 행동이 없으면 되돌릴 수 없는 위험도 없다
- **쓰기 이상 툴이 있다면** → 정책 엔진을 행동 가드레일의 중심으로, 등급별 정책. 이유: 모델의 확률적 판단이 곧 실행이 되는 것을 결정론으로 막는 유일한 수단
- **승인이 너무 많아 피로가 보인다면** → 배치·세션 사전 승인 + 결정 모델 확신도 라우팅. 이유: 승인 수를 줄이는 것이 승인 품질을 올리는 길. 단 p 보정 `[실측]`
- **금전·규제·파괴적 행동이라면** → 비동기 HITL + 체크포인트 + 에스컬레이션 + 만료=거부. 이유: 승인자 분리와 감사 추적이 요구된다
- **판단이 어려우면** → 규칙 1층 + 정책 엔진(allow/deny/require_approval) + 동기 HITL. 이유: 가장 단순하면서 세 지점을 다 덮고, 결정 모델·비동기 승인은 나중에 추가해도 구조가 바뀌지 않는다

## 설계 시 고려사항 (체크리스트)

- [ ] 입력·출력·행동 세 지점 모두에 가드레일이 있는가 (출력만 있지 않은가)
- [ ] 각 위협에 결정론 1차 수단이 있고, 판정 2차 수단은 1차가 "모르겠다"일 때만 도는가
- [ ] 정책 엔진이 모델 결과와 무관하게 먼저 평가되고 deny를 모델이 뒤집을 수 없는가
- [ ] 승인 흐름의 상태(대기·승인·수정·거부·에스컬레이션·만료)와 전이가 코드로 정의되어 있고 만료 기본값이 거부인가
- [ ] 비동기 승인 대기 중 체크포인트로 프로세스를 내릴 수 있는가 ([08](08-state-memory-context.md))
- [ ] 승인된 인자의 해시를 실행 직전 재검증하는가
- [ ] 승인 화면에 인자 원문·근거·확신도·되돌림 가능 여부가 전달되는가 (이벤트 스키마)
- [ ] 외부 데이터를 읽은 뒤의 전송 행동에 등급 상향 규칙이 있는가
- [ ] 승인률·거부율·만료율·평균 대기 시간·가드레일 오탐/미탐을 모니터링하는가
- [ ] 감사 로그의 보존 기간·접근 통제가 규제 요건과 맞는가 ([Part 5/04](../05-cross-cutting/04-governance-explainability.md))
