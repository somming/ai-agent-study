# 가드레일과 Human-in-the-Loop

> **범위**: 입출력 가드레일, 정책 엔진, 승인 흐름 설계
> 에이전트의 입력·출력·행동 세 지점에 두는 안전장치와, 사람이 개입하는 승인 흐름의 백엔드 설계. 승인 **화면**의 패턴은 [Part 4/06](../04-dynamic-ui/06-hitl-ui-patterns.md), 인젝션 공격 분류와 방어 전반은 [Part 5/01](../05-cross-cutting/01-security-prompt-injection.md), 판정 수단 자체는 [11](11-decision-layer.md)에 있으므로 여기서는 배치와 흐름을 다룬다.

## 요약 (3줄)

1. 가드레일(guardrail)은 세 지점에 둔다 — **입력**(인젝션·유해·범위 밖), **출력**(PII·근거 없음·정책 위반), **행동**(툴 실행 전 규칙 게이트). 세 지점의 위협이 다르므로 수단도 다르다. 출력 가드레일만 두고 "안전하다"고 하는 것이 가장 흔한 실수다.
2. HITL(Human-in-the-Loop)은 "위험하면 사람에게"가 아니라 **확신도와 비용 비대칭으로 라우팅되는 세 갈래 경로**다. 모든 것을 승인받게 하면 승인 피로(approval fatigue)로 사람이 보지 않고 승인하고, 아무것도 안 받으면 사고가 난다.
3. 승인 흐름은 **상태 머신**이다. 요청·대기·승인/거부/수정·만료·에스컬레이션의 상태와 전이를 명시하고, 대기 중에는 체크포인트([08](08-state-memory-context.md))로 실행을 멈춘다. Part 4의 HITL UI와는 이벤트 스키마로 계약한다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 세 지점별 가드레일 목록(위협 → 수단 → 실패 시 처리) ② 정책 엔진의 정책 집합과 테스트 ③ 승인 흐름 상태 머신(동기/비동기, 타임아웃, 에스컬레이션) ④ 확신도 기반 HITL 라우팅 임계값 ⑤ Part 4 HITL UI와의 이벤트 스키마 계약 ⑥ 감사 로그 |
| **언제** (When) | 입력 가드레일과 출력 PII는 **항상**. 행동 가드레일은 쓰기 이상 등급 툴이 있으면 항상. HITL 승인은 외부 전송·파괴적·금전·규제 행동이 있을 때. 읽기 전용 사내 QA라면 입력·출력 가드레일 + 사후 샘플링 리뷰로 충분하고 승인 흐름은 생략 |
| **어떻게** (How) | ① 세 지점의 위협을 목록화 → ② 각 위협에 규칙 → 분류기/결정 모델 → LLM judge 순으로 가장 단순한 수단 배정 → ③ 툴 등급([09](09-tools-and-mcp.md))별 행동 정책을 정책 엔진에 작성 → ④ 승인 필요 행동의 승인자·시한·에스컬레이션·만료 기본값 결정 → ⑤ 확신도 θ로 자동/명확화/사람 분기 → ⑥ 이벤트 스키마를 Part 4와 합의 → ⑦ 승인률·거부율·만료율·오탐률을 모니터링 |
| **왜** (Why) | 입력 가드레일이 없으면 인젝션이 그대로 모델에 닿고, 출력 가드레일이 없으면 PII·근거 없는 주장이 사용자에게 가며, 행동 가드레일이 없으면 모델의 확률적 판단이 곧 실행이 된다. HITL이 설계되지 않으면 승인은 "항상" 아니면 "절대"의 양자택일이 되어 둘 다 실패한다 |

## 문제와 맥락

가드레일 논의는 "유해 콘텐츠 필터"에서 시작했지만, 에이전트에서 더 큰 위험은 **행동**이다. 유해한 문장은 사용자가 보고 무시할 수 있지만, 잘못 실행된 환불·삭제·전송은 되돌리기 어렵다. 그리고 행동의 위험은 입력에서 온다 — 툴이 읽어 온 외부 문서의 한 줄이 다음 행동을 바꾼다([09](09-tools-and-mcp.md) 신뢰 경계).

HITL은 그 반대편 문제를 가진다. 승인을 너무 많이 요구하면 사람이 내용을 보지 않고 승인한다. 승인 피로는 보안 분야에서 오래 알려진 현상이며, 에이전트 승인에서도 같은 일이 벌어진다. 따라서 HITL 설계의 핵심 질문은 "무엇을 승인받을까"가 아니라 **"무엇을 승인받지 않아도 되게 만들까"**다.

## 핵심 개념

### 정의와 층위

용어는 [Part 1/07](../01-foundations/07-operations-vocabulary.md)의 정의를 그대로 쓴다. 이 페이지는 그 정의를 **런타임 경로에 배치하는 방법**이다.

```
정책 (policy)       사람이 읽는 선언          "환불은 담당자 승인 없이 50만 원을 넘을 수 없다"
   ↓ 번역
규칙 (rule)         기계가 평가하는 조건       refund.amount > 500_000 → require_approval(role=cs_lead)
   ↓ 배치
가드레일 (guardrail) 규칙을 심은 지점         입력 · 출력 · 행동 — 이 페이지의 "세 지점"
   ↓ 실행 형태
게이트 (gate)        흐름 분기               통과 / 차단 / 승인 요청 / 저하
```

- **가드레일은 거버넌스 결정의 런타임 강제**다. 거버넌스([1/07](../01-foundations/07-operations-vocabulary.md))가 "누가 무엇을 결정·승인·책임지는가"를 정하면, 가드레일은 그 결정을 요청 경로에서 매번 집행한다. 규칙에 소유자(A)와 버전이 없으면 "누가 왜 정했는지 모르는 코드"이고, 정책에 대응 규칙·게이트 위치가 없으면 "실행되지 않는 문서"다. 둘을 잇는 것이 아래 "규칙의 수명주기"다
- **세 지점**: 입력(인젝션·유해·범위 밖), 출력(PII·근거 없음·정책 위반), 행동(툴 실행·데이터 변경·외부 전송 직전). 입력 필터만 있는 시스템은 가드레일이 "있다"고 말할 수 없다
- **게이트 4출력**: 통과 / 차단 / 승인 요청 / 저하(degrade — 격리 모드·툴 비활성·읽기 전용·"미확인" 표시). 이 페이지의 정책 엔진 출력 `allow | deny | require_approval`은 앞의 셋이고, 저하는 가드레일 자체의 장애·불확실 상황에서 쓰는 네 번째 출력이다("운영 설계" 참조)
- **통제 세 층에서의 자리**: 가드레일·게이트·승인은 **예방** 층이다. 탐지(승인률·오탐·미탐 모니터링, 사후 샘플링)와 교정(규칙 롤백, 킬 스위치, 승인 취소·보상)이 함께 있어야 한 층이 뚫렸을 때 알고 멈출 수 있다. 이 페이지의 모니터링 항목은 탐지 층, "운영 설계"의 폴백·롤백은 교정 층에 해당한다
- **판정 수단 순서**: 규칙 → 결정 모델·분류기 → LLM judge. 보안·권한·한도 게이트는 규칙만 쓴다. 사람이 승인해도 규칙은 다시 검사한다(Rule ∧ Human)

### 세 지점의 가드레일

| 지점 | 위협 | 1차 수단 (결정론) | 2차 수단 (판정) | 실패 시 처리 |
|---|---|---|---|---|
| **입력** | 직접 프롬프트 인젝션(지시 덮어쓰기) | 알려진 패턴 규칙 | 인젝션 분류기 / 결정 모델 `boolean("지시 주입 시도인가")` | 거부 또는 격리 모드(툴 비활성) |
| 입력 | 유해·불법 요청 | 금칙어 사전 | 모더레이션 분류기 | 거부 + 안내 |
| 입력 | 범위 밖 요청 | — | intent 라우팅의 `범위밖` 선택지([11](11-decision-layer.md) #1) | 범위 안내, 사람 연결 |
| **출력** (입력도 동일) | PII 노출·입력 | 패턴(주민번호·카드번호·전화) | NER 분류기 | 마스킹 또는 차단, 원문 저장 금지 |
| 출력 | 근거 없는 주장 | citation 존재·유효성 규칙 | 근거 정합성 검사기([04](04-generation-grounding.md)), 결정 모델 `score` | 문장 제거·재생성·"확인 불가" 표시 |
| 출력 | 정책 위반(약속·법적 단언·경쟁사 언급 등) | 금칙 표현 규칙 | 정책 분류기 / 결정 모델 | 재생성(상한) → 템플릿 폴백 |
| **행동** | 권한 밖 툴 호출 | 정책 엔진(사용자 역할 × 툴) | — | 차단 + 사용자 안내 |
| 행동 | 한도 초과(금액·건수·빈도) | 정책 엔진 | — | 차단 또는 승인 요청 |
| 행동 | 외부 데이터 읽은 후 전송(유출 패턴) | 시퀀스 규칙(등급 상향) | 결정 모델 `boolean("승인 필요")` | 승인 요청 |
| 행동 | 되돌릴 수 없는 작업 | 등급 "파괴적" 규칙 | — | 항상 승인 |

1차 수단이 결정할 수 있으면 2차는 호출하지 않는다. 2차 수단은 1차가 "모르겠다"일 때만 돈다.

### 정책 엔진

정책 엔진(policy engine, OPA/Rego류 또는 자체 규칙 엔진)은 행동 가드레일의 중심이다. 입력은 `{사용자(역할·권한), 툴(이름·등급), 인자, 세션 상태(외부 데이터 읽음 여부, 누적 금액), 시간}`, 출력은 `allow | deny | require_approval(approver_role, timeout)`의 세 값이다.

- 정책은 코드다. 저장소·리뷰·테스트·배포가 있다. "정책 변경 → 평가셋 통과 → 배포"의 CI
- 정책 결정은 트레이스에 남긴다(어느 규칙이 어떤 입력으로 어떤 결과를)
- 정책 엔진은 **모델보다 먼저, 모델 결과와 무관하게** 평가된다. 모델(LLM·결정 모델)이 "실행해도 됨"이라 해도 정책이 deny면 deny ([10](10-neuro-symbolic-reasoning.md) 게이트 패턴)
- 정책이 `require_approval`을 돌려주면 승인 흐름으로 넘어간다

### 승인 흐름 설계

```
[요청] ─▶ 대기(pending) ─┬─ 승인(approved) ─▶ 인자 해시 재검증 ─▶ 실행
                          ├─ 수정(edited) ─▶ 수정 인자 재게이트 ─▶ 실행
                          ├─ 거부(rejected) ─▶ 사용자 안내 + 대안 경로
                          ├─ 시한 초과 ─▶ 에스컬레이션(escalated) ─▶ 2차 승인자 대기 ─▶ (위와 동일)
                          └─ 최종 시한 초과 ─▶ 만료(expired) ─▶ 기본값 적용 (기본값 = 거부)
모든 전이 ─▶ 감사 로그 + 체크포인트 갱신
```

| 설계 항목 | 지침 |
|---|---|
| **동기 vs 비동기** | 동기: 요청한 사용자 본인이 대화 안에서 즉시 승인(수 초~수 분). 비동기: 승인자가 다른 사람·다른 채널(수 분~수 일). 비동기는 체크포인트 필수, 프로세스 종료 허용 |
| **승인 단위** | 단건 / 배치(같은 유형 N건 묶음) / 세션 사전 승인("이 세션에서 X 유형은 자동"). 승인 피로를 줄이는 주요 수단은 배치와 사전 승인 |
| **타임아웃** | 등급별로. 만료 시 기본값은 **거부**(안전 측). "만료 = 승인"은 쓰지 않는다 |
| **에스컬레이션** | 1차 승인자 미응답 → 2차 승인자. 단계·시한을 정책에. 최종 미응답은 만료 |
| **승인 내용** | 무엇을(행동·인자), 왜(근거·요청 맥락), 얼마나 확신하는가(결정 모델 p), 되돌릴 수 있는가, 대안. 인자를 원문으로 보여준다(요약만 보여주면 승인자가 틀린 것을 승인) |
| **승인 후 불변성·수정** | 승인된 인자의 해시를 저장하고 실행 직전 재검증. 승인자가 인자를 고쳐 승인하면 수정 인자를 다시 정책 엔진에 통과시킨다 |
| **감사 로그** | 요청·승인자·시각·결정·사유·실행 결과. 규제 대상이면 보존 기간 명시 |

### 확신도 기반 HITL 라우팅

[11](11-decision-layer.md)의 세 갈래를 승인 흐름에 연결한다.

| 정책 엔진 결과 | 결정 모델 p ("승인 필요") | 경로 |
|---|---|---|
| deny | — | 차단 |
| require_approval | — | 승인 (정책이 강제) |
| allow | p < θ_low (승인 불필요 확신) | 자동 실행 |
| allow | θ_low ≤ p < θ_high | 사용자에게 확인 질문(동기, 가벼운 HITL) |
| allow | p ≥ θ_high | 승인 요청 (비동기 가능) |

θ는 행동 등급별로 다르다. 되돌릴 수 있는 행동은 θ_high를 높게(자동 많이), 되돌릴 수 없는 행동은 정책에서 require_approval로 고정. **결정 모델이 없으면** 이 표는 정책 엔진 결과만으로 축소되고, 그 경우 승인 대상이 늘어 승인 피로가 커진다 — 결정 모델 도입의 가장 직접적인 효용이 여기다. 단 p의 보정은 `[실측]` 전제.

### 승인 매트릭스 설계

승인 매트릭스는 **행동 유형 × 영향 범위 × 요청자 역할 → 승인자(역할)·승인 수·시한**의 표다. 승인자는 사람 이름이 아니라 **역할**로 적고, 역할 ↔ 사람 매핑은 조직 디렉터리에서 조회한다(조직 개편을 데이터 변경으로 흡수). 아래는 예시이며 시한·금액은 프로젝트마다 정한다.

| 행동 유형 | 영향 범위 | 요청자 역할 | 승인자 (역할) | 승인 수 | 시한 → 에스컬레이션 | 만료 시 | 1/07 위험 등급 |
|---|---|---|---|---|---|---|---|
| 읽기·조회 | 요청자 본인 | 모두 | 없음 | 0 | — | — | 1 |
| 쓰기(가역: 메모·태그·장바구니) | 요청자 본인 | 사용자 | 없음(출력 가드레일 + 로그) | 0 | — | — | 1 |
| 쓰기(가역) | 여러 고객 레코드 | 상담원 | 없음(규칙 게이트 + 감사) | 0 | — | — | 2 |
| 환불 접수 ≤ 한도(예시 50만 원) | 금전·외부 | 상담원 | 요청자 본인 확인(동기) | 1 | 5분 → 없음 | 거부 | 3 |
| 환불 접수 > 한도 | 금전·외부 | 상담원 | CS 리드(비동기) | 1 | 4시간 → CS 매니저 → 24시간 만료 | 거부 | 3 |
| 외부 데이터 읽은 뒤 외부 전송 | 조직 외부 | 모두 | 서비스 소유자 | 1 | 1시간 → 보안 당직 | 거부 | 3~4 (등급 상향 규칙) |
| 운영 설정 변경(부분 가역) | 전 사용자 | 운영자 | 변경 관리자 + 서비스 소유자 | **2** | 2시간 → 아키텍트 → 8시간 만료 | 거부 | 4 |
| 가드레일 규칙·승인 매트릭스 변경 | 전 사용자 | 보안 엔지니어 | 보안 책임자 + 제품 책임자 | **2** + 규칙 테스트 통과 + 시행일 | 1영업일 | 거부 | 4 |
| 결제·송금·데이터 영구 삭제 | 비가역·외부 | — | **에이전트 자동 실행 금지**. 제안만 생성, 실행은 사람이 자기 시스템에서 | — | — | — | 5 |

설계 규칙 세 가지. ① **등급 3 이상에 빈 행이 없어야 한다** — 매트릭스 커버리지 테스트로 CI에서 확인. ② 같은 행동이라도 요청자 역할이 높으면 승인 수를 줄일 수 있지만 **0으로 만들 수는 없다**(등급 3 이상). ③ 외부 데이터를 읽은 세션은 행동의 등급을 한 단계 올려 매트릭스를 다시 조회한다([09](09-tools-and-mcp.md) 신뢰 경계).

### 승인 피로 관리

승인 피로는 측정하지 않으면 보이지 않는다. 승인자가 "전부 승인"으로 가면 승인률은 올라가고 대기 시간은 내려가서 **지표가 좋아 보인다**.

| 측정 지표 | 피로 신호 | 임계값 예시 |
|---|---|---|
| 승인자당 일일 승인 건수 | 급증 | 50건/일 초과 시 알림 |
| 건당 검토 시간 중앙값 | 급감(카드를 읽지 않음) | 전주 대비 50% 이하 |
| 승인률 | 99%에 수렴 | 95% 초과가 2주 지속 |
| 수정(edit)·거부 비율 | 0에 수렴 | 1% 미만 |
| 승인 후 사고율(승인된 행동이 사후 리뷰에서 문제로 판정) | 상승 | 베이스라인 대비 상승 |
| 동일 유형 반복 승인 비율 | 같은 (행동, 인자 패턴)이 반복 | 주 20건 이상 동일 패턴 |

줄이는 수단은 순서대로 쓴다.

1. **임계값 조정**: 결정 모델 p의 θ_high를 올려 자동 비율을 늘린다 — 단 보정 `[실측]`과 해당 등급의 가역성이 전제. 등급 3 이상은 θ로 승인을 없앨 수 없다(정책이 `require_approval`로 고정)
2. **배치 승인**: 같은 유형·같은 승인자의 N건을 하나의 카드로. 카드에는 공통 부분과 **건별 차이점**을 함께 보여준다. 배치 안의 한 건만 거부·수정할 수 있어야 한다
3. **세션 사전 승인**: "이 세션에서 X 유형은 자동"을 승인자가 명시적으로 켠다. 범위(유형·한도·시한)를 기록하고 세션 종료 시 자동 해제
4. **규칙 승격 절차**: 반복 승인 패턴이 임계값(예시: 4주간 주 20건, 거부 0건)을 넘으면 → 규칙 후보 생성(조건·한도를 패턴에서 추출) → 규칙 소유자 검토 → 규칙 테스트 스위트에 승인 이력을 케이스로 추가 → **섀도 기간**(규칙은 allow로 판정하되 실제로는 여전히 승인 요청, 불일치 0 확인) → 시행일 지정 → 승인 매트릭스에서 해당 행의 승인 수를 조정. 승격된 규칙에는 "출처: 승인 이력 N건"을 기록한다
5. **승인 라우팅 분산**: 한 역할에 몰리면 역할을 세분하거나 라운드로빈

승인 수를 줄이는 것이 승인 품질을 올리는 길이지만, **줄인 뒤에도 사후 샘플링 리뷰는 유지**한다. 자동으로 넘어간 건의 일부를 사람이 보지 않으면 규칙 승격의 오류를 영영 모른다.

### Part 4 HITL UI와의 계약: 이벤트 스키마

백엔드는 이벤트를 발행하고 UI는 렌더·응답한다. 전송은 [AG-UI](../04-dynamic-ui/02-protocols-ag-ui-a2ui-mcp-apps.md)류 이벤트 스트림이든 자체 SSE든 무관하나 **스키마는 고정**한다. 최소 필드:

```
approval_requested {
  approval_id, run_id, checkpoint_id,
  action: { tool, args, effect_grade, reversible },
  rationale: { summary, evidence_refs[] },
  confidence: { p, threshold, source },          # 결정 모델이 있을 때
  options: [approve, reject, edit],
  approver: { role, user_id? }, expires_at, escalation: { to_role, after }
}
approval_resolved { approval_id, decision: approve|reject|edit, edited_args?, actor, timestamp, comment? }
approval_escalated { approval_id, from_role, to_role, timestamp }
approval_expired   { approval_id, applied_default: reject, timestamp }
```

UI 측 패턴(인라인 카드, 사이드 패널, 별도 큐)은 [Part 4/06](../04-dynamic-ui/06-hitl-ui-patterns.md). 백엔드 약속은 세 가지 — `approval_resolved`를 받으면 해당 `checkpoint_id`에서 재개한다, 같은 `approval_id`의 중복 응답은 첫 번째만 유효, 만료 후 응답은 무시하고 알린다.

### 예외 처리 절차

가드레일은 정당한 요청도 막는다. 막힌 요청의 처리 경로가 없으면 사용자는 우회를 찾고, 운영자는 규칙을 느슨하게 푼다 — 둘 다 가드레일을 무력화한다.

| 상황 | 경로 | 결정자 | 기록 |
|---|---|---|---|
| **가드레일이 막은 정당한 요청**(오탐) | 사용자에게 "차단됨 + 재심 요청" 선택지 → 재심 큐 → 운영자가 원문·적용 규칙·판정 근거를 보고 ① 일회 허용(해당 요청만, 규칙 불변) ② 규칙 수정 후보로 등록 ③ 기각 | 운영 책임자(규칙 소유자 자문) | 재심 ID, 원 판정, 적용 규칙 ID·버전, 재심 결정·사유, 결정자. **일회 허용도 감사 레코드** |
| **승인 지연으로 과업 불가** | 에스컬레이션 체인 → 최종 만료 = 거부. 사용자에게 대안 경로(수동 처리 창구) 안내. 시한 연장은 하지 않는다 | 자동(정책) | 만료 레코드, 안내 여부 |
| **긴급 변경 (break-glass)** | 정상 승인 경로가 작동하지 않는 장애 상황에서 사전 지정된 역할(예시: 당직 아키텍트)이 **단독으로** 규칙 비활성·승인 우회·킬 스위치 조작. 조건: 사용 사유 입력 필수, 시간 제한(예시: 4시간 후 자동 복원), 사용 즉시 보안 책임자·제품 책임자에 알림 | 사전 지정 역할 1인 | break-glass ID, 사용자, 시각, 사유, 조작 내용, 복원 시각, **사후 감사 결과**(72시간 내 2인 리뷰 — 정당성·영향 범위·재발 방지) |
| **규칙 간 충돌**(한 규칙은 allow, 다른 규칙은 deny) | 정책 엔진의 결합 규칙: **deny 우선 > require_approval > allow**. 충돌 자체를 규칙 테스트에서 탐지해 배포 전에 해소 | 규칙 소유자 | 충돌 로그 |

break-glass는 **쓰이지 않는 것이 정상**이다. 분기당 사용 건수와 사후 감사 결과를 거버넌스 리뷰에 보고하고, 반복 사용되는 상황은 정상 경로의 설계 결함으로 본다.

### 규칙의 수명주기

규칙은 코드이면서 **거버넌스 산출물**이다. 코드처럼 테스트·버전·배포를 거치고, 거버넌스 산출물처럼 소유자·시행일·감사·폐기 기준을 가진다.

```
제안 ─▶ 작성(규칙 + 테스트 케이스) ─▶ 테스트(규칙 테스트 스위트 + 충돌 탐지) ─▶ 리뷰(소유자 A 승인)
  ─▶ [선택] 섀도(판정만 기록, 미적용) ─▶ 시행일 지정 ─▶ 배포(규칙 버전 n) ─▶ 감사(차단율·오탐·재심 건수)
  ─▶ 재검토(분기 1회 예시) ─▶ 유지 / 수정(버전 n+1) / 폐기(만료일 + 사유)
```

| 단계 | 산출물 | 완료 조건 |
|---|---|---|
| 제안 | 정책 문장(사람이 읽는 선언), 출처(규제·사고·승인 이력 승격·제품 결정), 위험 등급 | 소유자(A) 지정 — **A가 없으면 진행 불가** |
| 작성 | 규칙(기계 평가 조건), 적용 지점(입력·출력·행동), 게이트 출력, **테스트 케이스**(허가·차단·승인 각 최소 1건 + 알려진 우회 패턴) | 테스트 케이스가 규칙과 함께 커밋 |
| 테스트 | 규칙 테스트 스위트 통과, 기존 규칙과의 충돌 탐지 0건, 골든 트래젝토리의 게이트 차단율 변화 확인([13](13-evaluation-rag-agents.md)) | 전부 통과 |
| 섀도 | 운영 트래픽에서 판정만 기록. 예상 차단율·오탐 샘플 | 오탐률이 임계값(예시: 2%) 이하. 보안 핫픽스 규칙은 생략 가능 |
| 시행 | 규칙 버전·시행일 기록, 감사 레코드에 버전 포함 시작 | 배포 후 24시간 차단율 모니터 |
| 감사 | 규칙별 차단 건수·오탐(재심 승인 건수)·미탐(사후 샘플) | 분기 리포트 |
| 폐기 | 만료일, 사유(규제 종료·대체 규칙·오탐 과다), 폐기 후에도 **규칙 정의는 보존**(과거 감사 레코드 해석용) | 소유자 승인 |

RACI(예시, [1/07](../01-foundations/07-operations-vocabulary.md) 표 준용): 가드레일 규칙은 보안 엔지니어 R · 보안 책임자 A · 제품·법무 C · AI 엔지니어 I. 승인 정책·매트릭스는 운영 책임자 R · 사업 책임자 A · 법무 C · 전체 I. 도메인 규칙(한도·업무 조건)은 제품 책임자가 A를 맡는다. **규칙마다 A가 한 명**이어야 하고, 규칙 메타데이터에 A의 역할을 적는다.

### 감사 레코드 스키마 예시

관측 트레이스와 같은 지점에서 나오지만 **저장소·보존·접근 통제를 분리**한다. 샘플링하지 않고, 변조 방지(append-only·해시 체인 등)를 두고, 보존 기간은 규제 요건을 따른다. 아래는 행동 게이트 + 승인 1건의 예시 스키마다.

```
audit_record {
  record_id, tenant_id, run_id, checkpoint_id, trace_id,         # 상관 키 (관측 로그와 연결)
  requester: { user_id, role, channel },                         # 요청자
  requested_at,                                                  # 시각 (UTC, 단조 시계)
  action: { type, tool, tool_version, args_hash, args_redacted,  # 무엇을 하려 했나 (PII 정책에 따라 원문 또는 마스킹)
            effect_grade, risk_level, reversible,
            session_flags: [external_data_read] },               # 등급 상향 근거
  rules_applied: [ { rule_id, rule_version, result: allow|deny|require_approval, matched_condition } ],
  decision: { source: rule|decision_model|classifier|llm_judge,  # 판정 수단
              choice, p, threshold_high, threshold_low,
              question_version, implementation, fallback: bool }, # 결정 모델이 있을 때. 폴백 여부 포함
  gate_output: pass|block|approval_required|degrade,             # 게이트 4출력
  degrade_mode?: isolation|read_only|unverified_flag,            # 저하라면 어떤 저하인가
  approval?: { approval_id, matrix_row_id, matrix_version,
               approver: { role, user_id }, approved_at, decision: approve|reject|edit,
               edited_args_hash?, comment?,
               card_shown: { args_display, rationale, evidence_refs[], p_display,
                             reversible_display, alternatives[] },   # 승인자가 실제로 본 내용
               escalations: [ { from_role, to_role, at } ], expired: bool },
  execution: { executed: bool, executed_at?, idempotency_key?, result_code?,
               args_hash_verified: bool,                           # 승인 인자 해시 재검증 결과
               result_summary_ref? },
  exception?: { type: review|break_glass, exception_id, actor, reason, post_audit_ref? },
  versions: { policy_set, rule_set, approval_matrix, guardrail_model, prompt, framework }  # 시점 재현 키
}
```

필드 선택의 기준은 하나다 — **"그때 왜 그렇게 됐나"를 이 레코드만으로 재구성할 수 있는가.** `card_shown`이 없으면 "승인자가 틀린 정보를 보고 승인했는가"를 답할 수 없고, `rule_version`이 없으면 "그때 규칙이 무엇이었나"를 복원할 수 없으며, `fallback`이 없으면 결정 모델 장애 중의 판정을 정상 판정과 구분할 수 없다. 관측 로그에 있는 지연·토큰·스팬 세부는 여기 넣지 않는다.

## 아키텍처 / 파이프라인

```
입력 ─▶ [입력 가드레일: 규칙 → 분류기/결정 모델] ─▶ 라우팅·검색·루프
루프 ─▶ 툴 호출 의도 ─▶ [정책 엔진: allow/deny/require_approval] ─▶ [결정 모델: 승인 필요 p] ─▶ 자동 / 확인 / 승인 흐름(체크포인트 대기)
                                                                                                  └─ approval_* 이벤트 ⇄ Part 4 HITL UI
LLM 생성 ─▶ [출력 가드레일: PII 규칙 → 근거 검사 → 정책 분류기] ─▶ 응답 / 재생성 / 폴백
모든 판정·승인 ─▶ 감사 로그 + 트레이스 ─▶ 오탐·미탐·승인률·만료율 모니터링 ─▶ 정책·θ 조정
```

|---|---|---|---|---|---|
| 프롬프트 지시만 ("안전하게 답하라") | 프로토타입 | 운영 전부. 확률적 준수 | 하 | 표준 | `[검증]` 우회 사례 다수 |
| 규칙·패턴·사전 (금칙어, PII 정규식, 시퀀스 규칙) | 모든 시스템의 1층. 결정론이 필요한 PII·권한·한도 | 의미 기반 판단(우회 표현) | 하 | 표준 | `[검증]` |
| 가드레일 라이브러리 (오픈소스·벤더, 입출력 분류기 묶음) | 입출력 가드레일을 빠르게 갖춤, 소규모 팀 | 도메인 특화 정책, 행동 가드레일(대부분 미지원), 한국어 성능 미검증 | 하~중 | 안정 | `[2차]` 한국어 `[실측]` 필요 |
| 정책 엔진 (OPA/Rego류, 자체 규칙 엔진) | 행동 가드레일의 중심. 권한·한도·승인 정책을 코드로 | 자연어 의미 판단 | 중 (정책 관리) | 표준 | `[검증]` 엔진 자체, LLM 결합은 `[2차]` |
| 결정 모델 게이트 (Jev / Decisions API) | 승인 필요·인젝션 의심·근거 부합 같은 닫힌 판정을 보정 확률과 함께, 승인 피로 완화 | 보정 미검증, 한국어 미검증, 외부 전송 불가 데이터 | 하 (호출) / 중 (평가셋) | 신생 | `[벤더]` `[2차]` |
| LLM-as-judge 온라인 | 미묘한 정책 판단, 지연 허용 | 대량·저지연, 비용 | 상 | 안정 | `[검증]` 편향 보고 |
| 동기 HITL (대화 내 확인) | 요청자 본인이 승인 가능, 되돌릴 수 있는 행동, 수 초 내 응답 기대 | 승인자가 제3자, 규제상 분리 필요 | 하~중 | 표준 | — |
| 비동기 HITL (별도 승인자·큐) | 금전·규제·파괴적 행동, 승인자 분리 | 수 초 내 응답이 필요한 대화형 과업 | 중~상 (체크포인트·큐·에스컬레이션) | 표준 | — |
| 사후 샘플링 사람 리뷰 | 읽기 전용 QA, 가드레일 오탐·미탐 측정 | 되돌릴 수 없는 행동의 유일한 통제 | 중 | 표준 | `[검증]` |

### 선택 가이드

- **읽기 전용 QA라면** → 규칙 1층 + 입출력 가드레일 라이브러리 + 사후 샘플링 리뷰. 승인 흐름은 생략. 이유: 행동이 없으면 되돌릴 수 없는 위험도 없다
- **쓰기 이상 툴이 있다면** → 정책 엔진을 행동 가드레일의 중심으로, 등급별 정책. 이유: 모델의 확률적 판단이 곧 실행이 되는 것을 결정론으로 막는 유일한 수단
- **승인이 너무 많아 피로가 보인다면** → 배치·세션 사전 승인 + 결정 모델 확신도 라우팅. 이유: 승인 수를 줄이는 것이 승인 품질을 올리는 길. 단 p 보정 `[실측]`
- **금전·규제·파괴적 행동이라면** → 비동기 HITL + 체크포인트 + 에스컬레이션 + 만료=거부. 이유: 승인자 분리와 감사 추적이 요구된다
- **판단이 어려우면** → 규칙 1층 + 정책 엔진(allow/deny/require_approval) + 동기 HITL. 이유: 가장 단순하면서 세 지점을 다 덮고, 결정 모델·비동기 승인은 나중에 추가해도 구조가 바뀌지 않는다

## 설계 시 고려사항 (체크리스트)

- [ ] 입력·출력·행동 세 지점 모두에 가드레일이 있는가 (출력만 있지 않은가)
- [ ] 각 위협에 결정론 1차 수단이 있고, 판정 2차 수단은 1차가 "모르겠다"일 때만 도는가
- [ ] 정책 엔진이 모델 결과와 무관하게 먼저 평가되고 deny를 모델이 뒤집을 수 없는가
- [ ] 승인 흐름의 상태(대기·승인·수정·거부·에스컬레이션·만료)와 전이가 코드로 정의되어 있고 만료 기본값이 거부인가
- [ ] 비동기 승인 대기 중 체크포인트로 프로세스를 내릴 수 있는가 ([08](08-state-memory-context.md))
- [ ] 승인된 인자의 해시를 실행 직전 재검증하는가
- [ ] 승인 화면에 인자 원문·근거·확신도·되돌림 가능 여부가 전달되는가 (이벤트 스키마)
- [ ] 외부 데이터를 읽은 뒤의 전송 행동에 등급 상향 규칙이 있는가
- [ ] 승인률·거부율·만료율·평균 대기 시간·가드레일 오탐/미탐을 모니터링하는가
- [ ] 감사 로그의 보존 기간·접근 통제가 규제 요건과 맞는가 ([Part 5/04](../05-cross-cutting/04-governance-explainability.md))

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 이 단계는 **다른 단계의 통제를 제공하는 단계**이므로, 가드레일·승인 흐름 자체의 장애가 "통제 없음"이 아니라 "보수적 통제"로 떨어지게 설계하는 것이 핵심이다.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 승인 큐 길이 | 승인자의 처리 능력. 요청 수 10배면 승인 요청도 10배인데 승인자는 10배가 되지 않는다. 대기 시간 증가 → 만료 증가 → 과업 실패 증가 → 또는 **승인 피로로 전부 승인** | 승인 피로 관리(아래 소절): 확신도 라우팅·배치 승인·규칙 승격으로 승인 **수**를 줄임. 큐 길이 상한과 백프레셔(상한 초과 시 신규 요청에 "지연 안내") | 승인 요청 수 ÷ 승인자 수 × 건당 검토 시간 |
| 승인자 수·조직 | 승인 매트릭스가 개인 이름으로 되어 있으면 승인자 추가·이동마다 매트릭스 수정. 에스컬레이션 체인도 개인 의존 | 승인자를 **역할**로 정의하고 역할 ↔ 사람 매핑을 조직 디렉터리에서 조회 | 역할 수(사람 수가 아님) |
| 가드레일 호출량 | 입력·출력 분류기와 결정 모델 호출이 요청마다 수 회. 지연 누적과 비용 | 1차 규칙이 결정하면 2차 호출 안 함(이미 원칙), 분류기 결과 캐시, 출력 가드레일은 스트리밍 중 점진 검사 | 요청 수 × 2차 수단 호출 비율 |
| 규칙·정책 수 | 정책 폭발: 충돌·누락·"어느 규칙이 막았나" 불명 | 정책 엔진의 충돌 탐지, 도메인별 정책 분할, 규칙마다 소유자·테스트·시행일 | 규칙 수 × 규칙 간 상호작용 |
| 테넌트 수 | 테넌트별 승인 매트릭스·한도·금칙어가 분기 | 정책을 `tenant_id` 키로 분기하는 구조, 기본 정책 + 테넌트 오버라이드 | 오버라이드가 있는 테넌트 수 |

비용이 비례하는 가장 중요한 변수는 **승인 요청 수**다. 가드레일 비용은 선형이지만, 승인은 사람 시간이라 선형으로도 감당이 안 된다.

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| **승인 적체**(큐 길이 급증, 대기 시간 증가) | 과업이 수 시간 멈춤, 만료 증가 | 큐 길이, 승인 대기 시간 p95, 만료율 | 큐 상한 초과 시 **백프레셔**(신규 승인 필요 행동에 "지금은 처리 지연, 나중에 재시도" 안내). 에스컬레이션 시한 단축은 하지 않음(승인 품질 저하) | 큐 길이가 임계값(예시: 승인자당 20건) 초과 시 운영 책임자가 임시 승인자 투입 또는 자동 가능 범위 임시 확대 결정(사후 감사 대상) |
| **승인자 부재**(휴가·퇴사·조직 개편으로 역할에 사람 없음) | 특정 유형 승인이 전부 만료 → 거부 | 역할별 활성 승인자 수 0, 에스컬레이션 최종 단계 도달률 | 에스컬레이션 체인 다음 역할로, 체인 끝이면 **만료 = 거부** + 사용자 안내 + 운영 알림. 자동 승인으로 넘어가지 않음 | 역할에 사람이 없으면 당일 내 배정. 매트릭스 정합성 점검을 주간 배치로 |
| **가드레일 지연 급증**(분류기·결정 모델 느림) | 응답 지연 | 가드레일 단계별 p95 | 2차 수단 타임아웃(예시: 입력 300ms, 출력 500ms) 초과 시 **보수적 기본 경로**: 입력은 "격리 모드(툴 비활성)로 진행", 출력은 "표시 보류 + 재검사" 또는 등급 1이면 "검사 미완 표시 후 표시". 행동 게이트는 규칙만으로 판정(2차 생략 = 승인 필요 쪽으로) | 지연이 지속되면 2차 수단 교체 또는 규칙 보강 |
| **정책 엔진 다운** | 행동 경로 전면 중단 | 엔진 오류율·헬스체크 | **fail-closed**: 행동 게이트는 전부 차단, 읽기 전용 경로만 유지(저하). 입력·출력 가드레일의 규칙 1층은 코드 내 폴백 사본으로 계속 | 즉시 온콜. 복구 후 차단된 요청 재처리 여부 결정 |
| **가드레일 오탐 폭증**(규칙·분류기 배포 직후) | 정당한 요청 대량 거부, 사용자 이탈 | 차단율 급등, 거부 로그 샘플의 정당 비율 | 규칙 세트 직전 버전 자동 롤백(보안·권한·한도 규칙 제외), 분류기는 임계값 보수적 완화 **금지** — 대신 "미확인" 등급으로 저하(차단 대신 플래그 + 사후 리뷰, 등급 1~2 한정) | 규칙 소유자 리뷰 후 수정 배포 |
| **미탐·우회 탐지**(레드팀·사후 샘플링에서 발견) | 즉시 보이지 않음 | 사후 샘플 리뷰 미탐률, 레드팀 통과율 | 발견 패턴을 **규칙 1층에 즉시 추가**(핫픽스 규칙, 시행 즉시), 분류기 재학습은 후속 | 보안 책임자가 영향 범위 조사, 감사 레코드로 과거 통과 건 역추적 |
| **승인 이벤트 유실**(UI ↔ 백엔드 전달 실패) | 승인했는데 실행 안 됨, 또는 승인 요청이 UI에 안 뜸 | `approval_requested` 대비 `approval_resolved` 비율, 체크포인트 재개 실패 | 이벤트 재전송(멱등: 같은 `approval_id` 중복 응답은 첫 번째만), 만료 전 미응답은 UI 재알림 | 유실률이 임계값 초과 시 전송 계층 점검 |

SLI 후보: 승인 응답 시간 p50/p95(요청 → 결정), 만료율, 승인률·거부률·수정률, 승인자당 일일 승인 수(피로 지표), 가드레일 차단율과 오탐률(샘플 리뷰), 미탐률(사후 샘플), 정책 엔진 가용성·p95, 승인 이벤트 유실률. SLO 초안(예시): 동기 승인 p95 2분 이내, 비동기 승인 p95 4시간 이내, 만료율 5% 이하, 정책 엔진 가용성 99.95%·p95 50ms, 오탐률 2% 이하, 승인자당 일일 승인 수 상한 50건(초과 시 피로 알림). 쓰기 행동의 멱등성은 [09](09-tools-and-mcp.md)를 따르되, **승인된 인자의 해시 재검증**이 이 단계의 추가 멱등 장치다 — 승인과 실행 사이에 인자가 바뀌면 실행하지 않는다.

|---|---|---|---|
| **규칙 세트**(입력·출력·행동 가드레일 규칙, 정책 엔진 정책) | 차단·승인 비율, 오탐·미탐 | **규칙 테스트 스위트**(허가·차단·승인 케이스, 알려진 우회 패턴 셋) + L3 트래젝토리 게이트 차단율([13](13-evaluation-rag-agents.md)) | 툴 등급 메타데이터([09](09-tools-and-mcp.md)), 온톨로지 정책 어휘 |
| **승인 매트릭스**(행동 × 영향 × 역할 → 승인자·수·시한) | 승인 경로, 에스컬레이션, 승인량 | 매트릭스 커버리지 테스트(모든 등급 3 이상 행동에 행이 있는가), 역할 ↔ 사람 매핑 정합성 | 역할 정의(조직 디렉터리), 에스컬레이션 체인 |
| **임계값 θ**(확신도 라우팅) | 자동/확인/승인 비율 | 세 갈래 비율 시뮬레이션 | [11](11-decision-layer.md) 보정 측정 결과 |
| **분류기·결정 모델 버전**(인젝션·모더레이션·PII NER) | 입력·출력 가드레일 오탐·미탐 | 한국어 가드레일 평가셋(우회 표현 포함) | 임계값 재설정 |
| **승인 이벤트 스키마** | Part 4 HITL UI, 체크포인트 재개 | 스키마 호환 테스트(tolerant reader), E2E 승인 흐름 테스트 | [Part 4/06](../04-dynamic-ui/06-hitl-ui-patterns.md) 렌더러 버전 |
| **승인 흐름 상태 머신**(상태·전이·타임아웃) | 모든 승인 건의 수명주기 | 상태 전이 테스트(만료=거부, 중복 응답 무시, 만료 후 응답 무시) | 체크포인트 스키마([08](08-state-memory-context.md)) |
| **감사 레코드 스키마** | 사후 재구성 가능성, 규제 대응 | 필수 필드 존재 검사(CI) | 감사 저장소 파서, 보존 정책 |

롤백 단위: 규칙 세트는 단독(데이터). 승인 매트릭스 + 역할 정의는 한 묶음. 승인 이벤트 스키마 + UI 렌더러는 한 묶음. 기술 부채로 기록할 것: "승인 매트릭스에 개인 이름 2건 잔존 → 역할화 예정", "출력 가드레일은 전체 생성 후 검사, 스트리밍 점진 검사는 2차", "배치 승인 미구현".

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **규칙·정책**(가장 잦음: 한도·금칙어·승인 기준·규제 신설) | 금액 한도, 금칙 표현, 승인 필요 조건, 신규 규제 조항 | 정책 엔진 평가 인터페이스(`evaluate(ctx) → allow | deny | require_approval`), 게이트 위치 | 규칙 세트 | **규칙 버전 + 시행일**로 설정 교체, 규칙 테스트 스위트 통과 후 반영, 감사 레코드에 규칙 버전. 코드 불변 | 해당 게이트. 권한 모델 변경은 ACL 필터([Part 2/10](../02-data-pipeline/10-access-control-governance.md))·UI 재검증까지 |
| **사용자 환경**(승인자 조직 개편·역할 변경·퇴사) | 누가 승인하는가 | **역할 기반 승인 매트릭스**(사람 이름 없음), 에스컬레이션 체인 형식 | 역할 ↔ 사람 매핑(조직 디렉터리) | 매트릭스를 **역할로 외부화**하고 사람 매핑은 디렉터리 조회 → 조직 개편이 데이터 변경으로 끝남 | 매트릭스 커버리지 테스트만. 코드·규칙 불변 |
| **모델**(분류기·결정 모델 교체, 한국어 성능 개선) | 2차 수단 구현체 | 가드레일 판정 포트(`classify(text) → {label, p}`), `decide()` | 분류기·결정 모델 어댑터 | 어댑터 교체 + 섀도 + 한국어 평가셋 회귀 + θ 재설정. **1차 규칙은 영향 없음** | 2차 수단 호출 지점 |
| **지식**(새 우회 패턴·인젝션 기법·PII 유형) | 금칙·탐지 패턴 | 규칙 1층 포맷 | 패턴 사전 | 패턴 사전 핫픽스(시행 즉시) + 레드팀 셋에 추가 | 입력·출력 1차 규칙 |
| **도메인 모델**(온톨로지 정책 어휘) | 툴 등급 enum, 행동 유형 분류 | 어휘 → 매트릭스 행 매핑 | 매트릭스 행 | 온톨로지 버전 + 매트릭스 재생성 | 매트릭스 + 규칙의 enum 참조 |
| **프로토콜·SDK**(AG-UI 스펙 개정, MCP Multi Round-Trip 도입, 정책 엔진 교체) | 승인 이벤트 전송 방식, 엔진 문법 | 승인 이벤트 **스키마**(전송 무관), 정책 엔진 포트 | 전송 어댑터, 엔진 어댑터 | 어댑터 교체, 버전 고정 + 계획된 창 | 어댑터와 E2E 승인 흐름 테스트 |
| **부하·규모**(승인 요청 10배) | 승인 큐·승인자 부담 | 승인 흐름 상태 머신 | 큐 구현, 승인자 풀 | 승인 피로 관리로 **수를 줄이는 것이 먼저**, 큐 수평 확장은 그다음 | 승인 매트릭스 시한 재조정 |

가장 자주 바뀌는 것: **규칙·한도·금칙어** > 승인자 조직 > 우회 패턴 > 분류기 모델 > 프로토콜. 코드 밖 설정으로 둘 것: 규칙 세트, 승인 매트릭스, 역할 매핑, θ, 타임아웃·에스컬레이션 시한, 패턴 사전, 배치 승인 조건. 포트·어댑터 뒤에 둘 외부 의존: 정책 엔진, 분류기·결정 모델, 승인 이벤트 전송 계층(AG-UI·SSE), 조직 디렉터리.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | 이 단계는 모든 등급의 행동에 통제를 공급한다. 등급별 필수 통제는 1/07 위험 등급표와 위 "승인 매트릭스 설계" 소절의 등급 열을 따른다. **가드레일 규칙·승인 매트릭스를 바꾸는 행위 자체는 등급 4**(여러 사용자에 영향, 되돌리려면 영향 건 역추적 필요) — 변경 관리 승인 2인 + 규칙 테스트 통과 + 시행일 |
| 가드레일 위치 | 세 지점 모두가 이 페이지의 주제. 입력(인젝션·유해·범위 밖) / 출력(PII·근거 없음·정책 위반) / 행동(권한·한도·시퀀스·파괴적). **출력만 있는 시스템은 가드레일이 없는 것** |
| 게이트 출력과 판정 수단 | 통과(규칙 allow ∧ p < θ_low) / 차단(규칙 deny, 또는 입력·출력 1차 규칙 위반) / 승인 요청(규칙 require_approval, 또는 allow ∧ p ≥ θ_high) / 저하(격리 모드·툴 비활성·"미확인" 표시·읽기 전용). 보안·권한·한도는 규칙만, 그 외는 규칙 → 분류기·결정 모델 → LLM judge 순 |
| 소유자 (A) | 가드레일 규칙: 보안 책임자(보안 엔지니어 R, 제품·법무 C). 승인 정책·매트릭스: 사업 책임자(운영 책임자 R, 법무 C). 분류기·결정 모델 선택: 아키텍트. 승인 이벤트 스키마: 아키텍트(Part 4 디자인 책임자 C). 예외 재심: 운영 책임자. **A가 비어 있는 규칙은 배포 불가** |
| 감사 추적에 남길 필드 | "감사 레코드 스키마 예시" 소절 전체. 핵심: 요청자, 시각, 적용 규칙 ID·**버전**, 판정·확신도, 게이트 출력, 승인자·승인 시각·**승인 카드에 보여준 내용**, 실행 결과. 관측 로그와 저장소·보존 정책 분리, 샘플링 불가, 변조 방지 |

### 운영 준비도 체크
- [ ] 정책 엔진 다운 시 행동 게이트가 fail-closed이고 읽기 전용 저하 경로가 있는가
- [ ] 승인자 부재 시 에스컬레이션 체인 끝이 "만료 = 거부"이고 자동 승인 경로가 없는가
- [ ] 승인 매트릭스에 개인 이름이 없고 역할 ↔ 사람 매핑이 디렉터리 조회인가
- [ ] 승인자당 일일 승인 수·승인 응답 시간·만료율을 측정하고 피로 임계값 알림이 있는가
- [ ] 규칙 세트가 코드 밖 버전 데이터이고 직전 버전 자동 롤백(보안·권한·한도 제외)이 있는가
- [ ] 규칙 테스트 스위트(허가·차단·승인·우회 패턴)가 CI에 있고 규칙 변경마다 실행되는가
- [ ] 감사 레코드에 규칙 버전·승인 카드 내용이 있고, 관측 로그와 저장소·보존이 분리되어 있는가
- [ ] break-glass 경로가 있고 사용 시 사후 감사가 자동으로 생성되는가
- [ ] 반복 승인을 규칙으로 승격하는 절차와 주기가 정해져 있는가
