# RAG·에이전트 평가

> **범위**: RAG 지표, LLM-as-judge, 트래젝토리 평가, 회귀 테스트
> [Part 1/06](../01-foundations/06-evaluation-observability.md)의 평가 4층·골든셋·트레이싱을 전제로, **Part 3 단계에 특화된 지표**와 회귀·모니터링 구성을 다룬다. 평가 수단의 일반론과 judge의 편향은 반복하지 않는다. UI 평가는 [Part 4/10](../04-dynamic-ui/10-evaluation-genui.md), 관측 인프라는 [Part 5/03](../05-cross-cutting/03-observability-tracing.md).

## 요약 (3줄)

1. RAG·에이전트 평가의 핵심은 **단계별 분리**다. End-to-End 점수 하나로는 검색이 틀렸는지, 생성이 근거를 무시했는지, 라우팅이 잘못됐는지 알 수 없다. 단계별 지표가 있어야 어느 노드를 고칠지 결정된다.
2. 에이전트는 **결과만이 아니라 경로**를 평가한다. 같은 답에 도달해도 툴을 10번 부른 경로와 2번 부른 경로는 다르다. 트래젝토리(trajectory) 평가는 비용·지연·재시도·가드레일 트리거를 함께 본다.
3. 에이전트는 비결정적이므로 회귀 테스트는 **반복 실행과 통과율 임계**로 설계한다. 한 번 통과한 것은 통과가 아니다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 단계별 지표 정의(RAG·라우팅·툴·트래젝토리·E2E)와 목표값 ② 지점별 평가셋(골든 질의·골든 근거·골든 경로) ③ 회귀 테스트 스위트와 트리거 ④ 온라인 샘플링·모니터링 규칙 ⑤ 실패 사례 환류 절차 |
| **언제** (When) | 평가셋은 **설계와 동시에**(Part 3의 각 단계 페이지가 "~를 측정한다"고 할 때 그 셋). 회귀 스위트는 첫 배포 전. 트래젝토리 평가는 툴 호출이 있으면 항상. 멀티에이전트 평가는 [07](07-multi-agent-orchestration.md) 채택 시 |
| **어떻게** (How) | ① 실행 그래프의 노드마다 "무엇이 맞는 출력인가"를 정의 → ② 노드별 골든 데이터(근거 ID, 경로, 툴 인자) 수집 → ③ 규칙 지표는 전수, judge 지표는 샘플 → ④ 변경 유형별 회귀 트리거 매핑 → ⑤ N회 반복 통과율로 비결정성 흡수 → ⑥ 온라인 층화 샘플링 → ⑦ 실패 → 골든셋 환류 |
| **왜** (Why) | 단계별 지표가 없으면 개선이 추측이 된다. 경로를 보지 않으면 비용 폭주·무한 루프를 배포 후에 안다. 반복 없는 회귀는 운으로 통과하고 운으로 실패해 신뢰를 잃는다 |

## 문제와 맥락

RAG 평가는 2024~25년에 RAGAS류 라이브러리로 표준 지표가 자리잡았지만 `[2차]`, 에이전트 평가는 아직 그렇지 않다. 이유는 세 가지다. ① 정답이 하나가 아니다(여러 경로가 유효). ② 비결정적이다(같은 입력에 다른 경로). ③ 실패가 늦게 드러난다(5번째 툴 호출에서 잘못된 인자). 여기에 Part 3가 추가한 결정 레이어([11](11-decision-layer.md))는 **보정**이라는 새 평가 축을 요구하고, 멀티에이전트([07](07-multi-agent-orchestration.md))는 **책임 귀속**을 어렵게 한다.

## 핵심 개념

### RAG 지표와 진단 매핑

| 지표 | 정의 | 참조 필요 | 낮으면 의심할 단계 |
|---|---|---|---|
| **context precision** | 검색된 청크 중 실제로 관련 있는 비율(순위 가중) | 선택(judge 가능) | [03](03-retrieval-reranking.md) 리랭킹, [11](11-decision-layer.md) #2 필터 |
| **context recall** | 답에 필요한 근거 중 검색된 비율 | 필요(골든 근거) | [03](03-retrieval-reranking.md) 검색, [02](02-query-understanding.md) 질의 재작성, [Part 2/02](../02-data-pipeline/02-chunking-strategies.md) 청킹 |
| **faithfulness** | 답변의 주장 중 제시된 근거로 뒷받침되는 비율 | 불필요 | [04](04-generation-grounding.md) 생성·근거 강제 |
| **answer relevancy** | 답이 질문에 답하는 정도(불필요한 내용·회피 감점) | 불필요 | [04](04-generation-grounding.md) 프롬프트, [01](01-rag-architecture-patterns.md) 패턴 |
| citation 정확도 | 인용된 근거 ID가 존재하고 해당 문장을 실제로 뒷받침하는 비율 | 불필요(규칙 + judge) | [04](04-generation-grounding.md) |
| 거부 정확도 | 근거가 없을 때 "모른다"고 하는 비율, 근거가 있을 때 거부하지 않는 비율 | 필요 | [04](04-generation-grounding.md), [12](12-guardrails-hitl.md) 출력 가드레일 |

- recall이 낮고 precision이 높으면 검색 폭 문제, 반대면 리랭킹·필터 문제. faithfulness가 낮은데 recall이 높으면 생성 문제. 이 매핑이 단계별 분리의 이유다
- RAGAS는 judge 정렬 가이드를 제공하지만 **judge JSON 파싱 실패가 NaN이 되어 집계에서 조용히 제외**된다 `[2차]`. NaN 수를 반드시 함께 보고한다. 전용 OTel 계측기는 없어 수동 스팬이 필요하다 `[2차]`
- 한국어 judge 프롬프트와 영어 judge 프롬프트의 결과가 다를 수 있다. 사람 라벨과의 정렬을 한국어로 따로 측정한다

### 트래젝토리 평가

트래젝토리는 한 실행의 **노드·행동·툴 호출 시퀀스**다. 평가는 결과(outcome)와 과정(process)을 분리한다.

| 관점 | 방법 | 비고 |
|---|---|---|
| 경로 일치 | 골든 경로와 **정확 일치** / **필수 단계 포함** / **허용 경로 집합 중 하나** | 정확 일치는 너무 엄격. 기본은 필수 단계 포함 + 금지 단계 부재 |
| 효율 | 스텝 수, 툴 호출 수, 토큰, 비용, 지연 — 골든 대비 비율 | 상한 초과는 실패로 |
| 안정성 | 재시도 수, 루프 감지(같은 상태 반복), 상한 도달 | 무한 루프는 배포 전에 잡는다 |
| 안전 | 가드레일 트리거 수, 승인 요청 수, 차단된 행동 | 트리거 0이 좋은 것은 아니다(미탐일 수 있음) |
| 개입 | 사람 개입 횟수·시점, 명확화 질문 수 | 과업 유형별 기대치와 비교 |
| 과정 judge | LLM judge가 각 스텝의 합리성 평가(루브릭) | 비용 크므로 샘플링, 결과 지표와 상관 확인 후 사용 |

트래젝토리는 트레이스([Part 5/03](../05-cross-cutting/03-observability-tracing.md))에서 추출한다. 평가용 트래젝토리 포맷과 운영 트레이스 포맷을 같게 두면 운영 실패를 바로 회귀 케이스로 만들 수 있다.

### 멀티에이전트 평가의 난점

- **책임 귀속**: 최종 실패가 어느 에이전트의 어느 스텝에서 비롯됐는지. 에이전트별 입력·출력을 스팬으로 분리 기록하고, 에이전트 단위 평가(단위 테스트)와 통합 평가를 분리
- **핸드오프 정확도**: 올바른 에이전트에 올바른 맥락이 넘어갔는가. 핸드오프 자체를 라우팅 지점으로 보고 라우팅 지표 적용
- **전파 오류**: 상위의 작은 오류가 하위에서 증폭. 중간 산출물 골든셋 필요
- **비결정성 증폭**: 에이전트 수에 따라 경로 조합이 급증. 반복 횟수를 늘리거나 핵심 경로만 고정
- **비용 귀속**: 에이전트별 토큰·비용을 분리 집계해 비효율 에이전트 식별

### 회귀 테스트 구성

| 층 | 내용 | 실행 시점 | 비용 |
|---|---|---|---|
| L1 규칙 체크 | 스키마, citation 유효성, 금칙어, 지연 상한, 툴 인자 통과율 | 모든 커밋(CI) | 하 |
| L2 골든셋 단계 평가 | 라우팅 정확도, recall@k, 툴 선택·인자, 거부 정확도 | 프롬프트·모델·인덱스·툴 스키마·정책·질문 정의 변경 시 | 중 |
| L3 트래젝토리 | 필수 단계·금지 단계·효율 상한·루프 | 그래프 구조·에이전트 패턴 변경 시, 야간 | 중~상 |
| L4 judge 샘플 | faithfulness, relevancy, 과정 합리성 | 배포 전, 주간 | 상 |

- **변경 → 트리거 매핑**: 임베딩 모델 교체 → L2 검색, 프롬프트 수정 → L2 생성 + L4, 툴 설명 수정 → L2 툴, 정책 수정 → L1 게이트 + L3, 결정 모델 질문 정의 수정 → L2 라우팅 + 보정 재측정
- **비결정성 처리**: 케이스당 N회(3~5회 권장) 실행, 통과율 임계(예: 필수 케이스 100%, 일반 케이스 ≥ 80%)로 판정. 단일 실행 통과/실패로 판정하지 않는다
- **비용 통제**: 커밋마다 소규모 스모크(수십 건), 야간 전체. judge 호출은 캐시(같은 입력·출력이면 재평가 안 함)
- **셋 분리**: 프롬프트 튜닝용 개발셋과 최종 판정용 홀드아웃 분리([Part 1/06](../01-foundations/06-evaluation-observability.md))
- **메모리 평가**: no-memory 베이스라인 구성을 회귀에 포함([08](08-state-memory-context.md))

### 온라인 모니터링 샘플링

- **전수**: 규칙 지표(지연, 비용, 토큰, 스키마 실패, 게이트 차단, 폴백, 재시도, 루프 상한 도달)
- **샘플링**: judge 지표. Datadog 등은 Ragas 평가 자동 트레이싱에 샘플링을 권고한다 `[벤더]`. 비율은 비용 예산에서 역산
- **층화**: 경로(intent)·언어·위험 등급·신규/기존 사용자별로 최소 표본 확보. 전체 평균은 소수 경로의 붕괴를 가린다
- **실패 신호 우선**: 결정 모델 p가 낮은 건, 재시도 발생 건, 가드레일 트리거 건, 사람 개입 건, 부정 피드백 건은 샘플링 비율을 높이거나 전수
- **드리프트**: 지표의 주간 이동, 입력 분포(길이·언어·intent 비율) 변화, 보정 곡선 이동
- **환류**: 샘플 중 실패 사례를 라벨링해 골든셋·트래젝토리 셋에 추가. 주기와 담당자를 정한다

## 아키텍처 / 파이프라인

```
개발:  변경 ─▶ L1 규칙(CI) ─▶ L2 골든셋(변경 유형별) ─▶ L3 트래젝토리(N회 반복, 통과율) ─▶ L4 judge 샘플 ─▶ 배포 판단
                                                                                                    ▲
운영:  요청 ─▶ 트레이스(스팬·판정·툴·게이트) ─▶ 전수 규칙 지표 ─▶ 층화·실패 우선 샘플링 ─▶ judge ─▶ 실패 사례 ─▶ 라벨링 ─▶ 골든셋·트래젝토리 셋 환류
                                                                                   └─▶ 사람 리뷰 (고위험·불만·낮은 p)
```

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| RAGAS / DeepEval 류 라이브러리 | RAG 표준 지표 빠른 도입, judge 정렬 가이드 활용 | 도메인 특화 루브릭, 트래젝토리 평가(제한적), NaN 처리 무관심 | 중 | 안정 | `[2차]` NaN 조용한 제외 주의 |
| 자체 judge (G-Eval 류 루브릭) | 도메인 특화 품질, 과정 평가 | judge 보정 없이 운영 지표로 | 중~상 | 안정 | `[검증]` 편향 연구 다수 |
| 규칙 기반 체크 | L1 전수, CI 게이트, 전수 모니터링 | 의미 품질 | 하 | 표준 | `[검증]` |
| 골든 경로 트래젝토리 비교 | 툴 호출이 있는 모든 에이전트, 루프·비용 회귀 | 유효 경로가 매우 다양해 골든 정의 불가(허용 집합으로 완화) | 중 | 신생~안정 | `[2차]` |
| 결정 모델을 judge로 (Jev / Decisions API) | 합격/불합격·점수처럼 닫힌 판정의 대량·저비용 온라인 평가 | 서술형 피드백, 보정 미검증 | 하 (호출) | 신생 | `[2차]` 사례 미확인 |
| 시뮬레이션 사용자 (LLM 생성 대화) | 다중 턴 과업 완료율, 명확화 질문 품질, 회귀 자동화 | 실제 사용자 분포와 괴리, 시뮬레이터 자체의 편향 | 중~상 | 신생 | `[2차]` |
| 사람 평가 | judge 보정, 고위험 샘플, 트래젝토리 과정 판단 | 전수 | 상 | 표준 | `[검증]` |
| 벤더 관측 플랫폼 평가 통합 (Langfuse, LangSmith, Arize, Datadog 등) | 트레이스와 평가를 한 곳에서, 소규모 팀 | 벤더 종속 회피, 자체 지표 체계 | 하~중 | 안정 | `[벤더]` |
| 온라인 A/B | 프롬프트·모델·θ 변경의 실사용 영향 | 트래픽 적음, 고위험 행동 | 중 | 표준 | `[검증]` |

### 선택 가이드

- **RAG가 중심이라면** → RAGAS류로 4지표 + 자체 citation·거부 정확도 규칙. 이유: 표준 지표를 빨리 갖추고, 라이브러리가 못 재는 것만 추가
- **툴 호출이 있다면** → 골든 경로 트래젝토리(필수 단계 + 금지 단계 + 효율 상한) + N회 반복. 이유: 루프·비용 폭주는 결과 지표로 안 보인다
- **결정 레이어를 썼다면** → 지점별 정확도 + ECE + 세 갈래 비율을 L2에 고정. 이유: θ의 전제가 보정이고, 질문 정의 변경마다 재측정이 필요
- **멀티에이전트라면** → 에이전트 단위 평가 + 핸드오프 라우팅 지표 + 통합 트래젝토리. 이유: 통합 점수만으로는 책임 귀속 불가
- **판단이 어려우면** → L1 규칙 CI + L2 골든셋(라우팅·검색·툴) + 운영 층화 샘플링 judge. 이유: 가장 적은 비용으로 단계별 분리가 되고, 트래젝토리·시뮬레이션은 그 위에 추가

## 설계 시 고려사항 (체크리스트)

- [ ] 실행 그래프의 노드마다 "맞는 출력"의 정의와 지표가 있는가
- [ ] 골든셋에 근거 ID(recall용), 골든 경로(트래젝토리용), 골든 툴 인자가 있는가
- [ ] judge 결과의 NaN·파싱 실패 수를 함께 보고하고, judge를 한국어 사람 라벨과 정렬했는가
- [ ] 결정 지점별 ECE·세 갈래 비율·폴백율을 측정하는가
- [ ] 트래젝토리 평가에 필수 단계·금지 단계·효율 상한·루프 감지가 있는가
- [ ] 회귀 케이스를 N회 반복해 통과율로 판정하는가
- [ ] 변경 유형 → 회귀 층 매핑이 문서화되어 있는가
- [ ] 메모리 회귀에 no-memory 베이스라인이 포함되는가
- [ ] 온라인 샘플링이 경로·언어·위험 등급으로 층화되고 실패 신호 우선인가
- [ ] 운영 실패를 골든셋으로 환류하는 주기·담당자가 있는가

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| judge의 편향·비일관성 | 지표가 실제 품질과 어긋남 | 사람 라벨 정렬, 복수 judge, 규칙 지표와 교차 확인 |
| NaN 조용한 제외 (RAGAS `[2차]`) | 실패가 많을수록 점수가 좋아 보임 | NaN 수 보고, NaN을 실패로 집계하는 옵션 |
| 골든 경로의 경직성 | 유효한 다른 경로를 실패로 | 허용 집합·필수 단계 방식 |
| 비결정성 | 회귀 결과 흔들림 | N회 반복, 통과율 임계, 핵심 케이스는 온도 0 + 시드 |
| 평가 비용 | judge·트래젝토리 호출 비용이 운영 비용에 근접 | 캐시, 스모크/야간 분리, 샘플링, 결정 모델 judge 검토 |
| 멀티에이전트 책임 귀속 | 개선 지점 불명 | 에이전트별 스팬·단위 평가, 중간 산출물 골든 |
| OTel GenAI 컨벤션 미성숙 | 평가-트레이스 연결의 속성 변경 | 버전 고정, 어댑터 ([Part 1/06](../01-foundations/06-evaluation-observability.md)) |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 평가는 통제 세 층 중 **탐지** 층의 핵심 수단이다. 평가 자체가 깨지면 다른 모든 단계의 회귀와 드리프트를 못 본다 — "탐지기의 탐지"가 이 단계 운영 설계의 주제다.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 골든셋 크기 | L2 실행 시간과 **라벨 유지 비용**. 수천 건 골든셋은 모델·인덱스가 바뀔 때마다 라벨 유효성 재검토가 필요하고, N회 반복까지 곱하면 야간 창을 넘김 | 셋 계층화(커밋 스모크 수십 건 / 야간 전체 / 주간 홀드아웃), 케이스 우선순위 태그, 라벨 유효기간과 소유자 | 골든셋 크기 × 반복 횟수 N × 변경 빈도 |
| judge 호출량 | L4 judge와 온라인 샘플링 judge의 LLM 비용이 운영 비용에 근접. 요청 수 10배면 같은 샘플 비율로 judge 비용도 10배 | 샘플 비율을 **비용 예산에서 역산**(절대 건수 상한), judge 캐시(동일 입력·출력), 닫힌 판정은 결정 모델 judge 검토, 실패 신호 우선 샘플링 | 요청 수 × 샘플 비율 × judge 단가 |
| 트래젝토리 길이·에이전트 수 | L3 트래젝토리 평가 시간. 멀티에이전트는 경로 조합이 급증해 N회 반복으로도 커버 안 됨 | 핵심 경로 고정(온도 0 + 시드), 에이전트 단위 평가 분리, 필수·금지 단계만 검사 | 케이스 수 × 평균 스텝 수 × N × 에이전트 수 |
| 변경 빈도(팀 수) | 변경 → 회귀 트리거 매핑이 없으면 모든 변경에 전체 스위트가 돌아 CI가 병목 | 변경 유형별 트리거 매핑(이미 원칙), 영향 범위 분석으로 해당 층만 | 일일 변경 수 × 트리거되는 층의 비용 |
| 테넌트·언어·경로 수(층화 차원) | 층화 샘플링의 셀 수가 곱으로 늘어 셀당 최소 표본 확보 불가 | 층화 차원을 위험 등급 기준으로 우선순위화, 저위험 셀은 병합 | 층화 셀 수 × 셀당 최소 표본 |

비용이 비례하는 핵심 변수는 **judge 호출 수**다. 규칙 지표는 전수로 돌려도 싸지만 judge는 그렇지 않으므로, 확장 설계는 "무엇을 judge에 보내지 않을 것인가"를 정하는 일이다.

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| **judge 모델 변경으로 지표 점프**(벤더 업데이트·버전 교체) | 사용자에게는 안 보임. 운영 지표가 하루아침에 바뀌어 **거짓 회귀 또는 거짓 개선** | 지표 급변이 시스템 변경 없이 발생, judge 보정 셋(사람 라벨 고정 셋) 점수 이동 | judge 버전을 **고정**(pinned)하고 변경은 명시적으로만. 고정 불가 벤더면 judge 보정 셋을 매일 돌려 이동 감지 시 지표에 "judge 변경 의심" 플래그 | 보정 셋 이동이 임계값(예시: 일치율 3%p) 초과 시 새 judge를 사람 라벨과 재정렬 후 베이스라인 재설정. 이전 지표와 비교 금지 기간 선언 |
| **judge NaN·파싱 실패 증가** | 안 보임. 점수가 좋아 보임(실패 건 제외) | NaN 비율, 파싱 실패 수 | NaN을 **실패로 집계**하는 옵션 기본 켬, NaN 비율 자체를 지표로 | NaN 비율 상승 시 judge 프롬프트·출력 스키마 점검 |
| **평가 파이프라인 다운**(CI·야간 배치 실패) | 안 보임. 회귀 없이 배포됨 | 배치 완료 신호 부재, 마지막 성공 시각 경과 | **배포 게이트는 "평가 결과 없음 = 배포 불가"**(fail-closed). 야간 실패 시 다음날 배포 동결. 예외는 [Part 1/06](../01-foundations/06-evaluation-observability.md)의 축소 게이트 기준 하나뿐: **등급 1~2 변경**은 규칙 체크(L1) + 참조 평가(judge 없는 L2) 통과 시 "축소 통과"를 배포 판정 레코드에 기록하고 judge(L4)를 배포 후 비동기로 보완해 배포 가능. **등급 3 이상은 배포 불가** (불균형 ⑥ 반영) | 평가 파이프라인 복구를 배포보다 우선. 축소 게이트가 4시간(예시) 넘게 지속되거나 등급 3 이상 변경이 대기 중이면 에스컬레이션 |
| **골든셋 오염**(라벨 오류, 데이터 유출로 개발셋 = 홀드아웃) | 회귀 통과하는데 운영 품질 하락 | 홀드아웃과 개발셋 점수 괴리 소멸, 운영 샘플 지표와 L2 괴리 확대 | 홀드아웃은 접근 통제, 환류 시 중복 검사 | 괴리 패턴 발견 시 홀드아웃 재구성 |
| **온라인 샘플링 편향**(실패 신호 우선이 과도해 전체 추정 왜곡) | 안 보임. 품질이 실제보다 나빠 보임 | 샘플 구성 비율과 모집단 비율 차이 | 층화 가중치로 전체 추정치 보정, 무작위 기저 샘플 유지 | 가중 추정과 비가중 추정 차이가 크면 샘플링 규칙 재설계 |
| **트레이스 스키마 변경으로 트래젝토리 추출 실패**(OTel 컨벤션 변경, 프레임워크 업) | 안 보임. L3가 조용히 0건 | 추출 건수 급감, 파서 오류 | 어댑터 버전 고정, 추출 건수 하한 알림 | 어댑터 수정 |
| **비결정성으로 회귀 결과 흔들림** | 배포 지연(재시도 반복) | 같은 케이스의 run 간 통과율 분산 | N회 반복 + 통과율 임계(이미 원칙), 분산 큰 케이스는 "불안정" 태그로 분리 보고 | 불안정 케이스가 늘면 그래프·프롬프트 점검(비결정성 자체가 회귀 신호) |

SLI 후보: 평가 파이프라인 가용성(야간 배치 성공률), judge 보정 셋 일치율(사람 라벨 대비), NaN 비율, 회귀 케이스 통과율 분산, 온라인 샘플 커버리지(층화 셀당 최소 표본 충족률), 운영 실패 → 골든셋 환류 리드타임, **삭제 이벤트 → 골든셋 케이스 제거·갱신 p95**(불균형 ① 반영). 골든셋은 [Part 2/07](../02-data-pipeline/07-freshness-and-sync.md) 변경 큐 **삭제 레인의 소비자**로 등록한다 — 삭제·만료된 문서를 기대 근거(근거 ID)로 가진 케이스는 자동으로 "검수 대기"로 빠지고, 재매핑 또는 폐기 후 셋 버전을 올린다. 환류된 셋에 삭제 항목이 남아 있으면 삭제 전파 회귀(1/06 "지식 증분" 행)가 거짓 실패를 낸다. SLO 초안(예시): 야간 배치 성공률 99%, judge-사람 일치율 85% 이상 유지(이동 3%p 이내), NaN 비율 2% 이하, 층화 셀 커버리지 95%, 환류 리드타임 2주 이내. 쓰기 행동은 이 단계에 없다. 단 **시뮬레이션 사용자·트래젝토리 평가가 운영 툴을 실제로 호출하지 않도록** 평가 환경의 툴은 모의(mock) 또는 샌드박스로 격리한다 — 평가가 운영 데이터를 바꾸는 사고가 실제로 난다.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| **골든셋**(질의·근거·경로·인자, 개발/홀드아웃) | 모든 L2·L3 측정값. 셋이 바뀌면 이전 결과와 비교 불가 | 셋 버전 간 공통 부분으로 연속성, 라벨 2인 합의 | 라벨 가이드 버전, 지표 베이스라인 |
| **judge 버전**(모델·프롬프트·루브릭) | 모든 L4·온라인 judge 지표 | **judge 보정 셋**(사람 라벨 고정 셋) 일치율 | 지표 베이스라인(judge 바뀌면 베이스라인 재설정) |
| **지표 정의·임계값**(통과율 기준, 효율 상한) | 배포 판정 | 과거 결과 재적용 시뮬레이션 | — |
| **변경 → 트리거 매핑** | 어떤 변경에 어떤 층이 도는가 | 매핑 커버리지(모든 버전 관리 대상에 트리거가 있는가) | 각 단계의 버전 관리 대상 목록 |
| **트래젝토리 포맷·추출 어댑터** | L3, 운영 실패 → 회귀 케이스 변환 | 추출 건수·필드 존재 검사 | 트레이스 스키마([Part 5/03](../05-cross-cutting/03-observability-tracing.md)), 프레임워크 버전 |
| **샘플링 규칙**(비율·층화·실패 우선) | 온라인 지표의 대표성 | 가중 vs 비가중 추정 비교 | 비용 예산 |

롤백 단위: judge 버전 + 지표 베이스라인은 한 묶음(judge만 되돌리면 베이스라인이 어긋남). 골든셋 + 라벨 가이드도 한 묶음. 기술 부채로 기록할 것: "judge는 벤더 최신 모델 사용 중 → 고정 가능한 버전으로 전환 예정", "L3는 야간만, 커밋 스모크에 트래젝토리 없음", "한국어 judge 정렬은 샘플 100건으로만".

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약·인터페이스 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **지식**(골든셋 내용 — 가장 잦음) | 운영 실패 환류, 새 의도·경로 추가, 낡은 케이스 폐기, **소스 삭제로 기대 근거가 사라진 케이스** | 골든셋 스키마(질의·근거 ID·골든 경로·인자·라벨·우선순위·유효기간) | 셋 내용 | 주기적 추가(2주 예시) + 셋 버전 + 변경 로그. 베이스라인은 공통 부분으로 연속. 삭제는 2/07 삭제 레인 이벤트로 근거 ID 매칭 케이스를 즉시 검수 대기로(불균형 ① 반영) | 측정값 연속성만 |
| **모델**(judge 모델 교체·업데이트) | judge 출력 분포 | judge 포트(`judge(input, output, rubric) → {score, rationale?}`), 루브릭 포맷 | judge 구현체(LLM·결정 모델·규칙) | 어댑터 교체 + **보정 셋 재정렬 + 베이스라인 재설정**. 교체 전후 지표 비교 금지 기간 명시 | 모든 judge 지표의 베이스라인 |
| **모델**(피평가 시스템의 LLM 교체) | 전체 지표 | 지표 정의 | — | 전체 골든셋 회귀(트리거 매핑의 "모델" 행) | 전 층 |
| **규칙·정책**(통과율 임계, 효율 상한, 샘플 비율) | 배포 판정 엄격도, 비용 | 지표 정의 | 임계값 표 | 코드 밖 설정 교체 + 과거 결과 재적용으로 영향 확인 | 배포 게이트 |
| **도메인 모델**(온톨로지 → 라우팅 선택지·툴 enum 변경) | 골든 라벨의 enum 값 | 라벨 ↔ enum 매핑 | 라벨 값 | 온톨로지 구→신 매핑으로 라벨 **자동 재부여**, 매핑 불가 케이스는 재라벨 | 라우팅·툴 골든셋 |
| **사용자 환경**(언어·테넌트 추가) | 층화 차원, 언어별 judge 정렬 | 층화 키 규약 | 셀 정의 | 셀 추가 + 언어별 보정 셋 | 샘플링 규칙 |
| **프로토콜·SDK**(OTel GenAI 컨벤션 개정, 프레임워크 트레이스 포맷 변경, 평가 라이브러리 업) | 트래젝토리 추출, 지표 계산 | **자체 트래젝토리 포맷**, 지표 정의 | 추출 어댑터, 라이브러리 | 어댑터 교체, 버전 고정 + 계획된 창 | 어댑터만 |
| **부하·규모**(요청 10배) | judge 비용 | 샘플링 인터페이스 | 샘플 비율·캐시 | 절대 건수 상한으로 비용 고정 | 온라인 지표 신뢰구간 |

가장 자주 바뀌는 것: **골든셋 내용** > 임계값 > judge 모델 > 트레이스 포맷. judge 모델 변경은 빈도는 낮지만 "모든 지표가 동시에 움직이는" 유일한 변화이므로 고정 + 보정 셋을 처음부터 둔다. 코드 밖 설정으로 둘 것: 골든셋, 루브릭, 임계값 표, 트리거 매핑, 샘플링 규칙, 층화 셀 정의. 포트·어댑터 뒤에 둘 외부 의존: judge 모델, 평가 라이브러리(RAGAS류), 트레이스 백엔드, 벤더 관측 플랫폼.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | 평가 자체는 사용자 행동이 아니므로 등급 없음. 단 **평가 결과가 배포 게이트를 통과시키는 행위는 등급 3**(여러 사용자에 영향, 롤백으로 가역) — 임계값 완화·케이스 제외는 변경 관리 승인 대상. 평가 환경이 운영 툴을 호출하면 그 툴의 등급을 따르므로 **모의 툴 강제** |
| 가드레일 위치 | 평가는 가드레일이 아니라 **탐지** 층. 단 배포 파이프라인에서 "L1 통과 ∧ L2 통과율 ≥ 임계"는 **배포 행동 앞의 게이트**(규칙만)로 동작한다 |
| 게이트 출력과 판정 수단 | 배포 게이트: 통과(모든 층 임계 충족) / 차단(필수 케이스 실패, L1 위반) / 승인 요청(일반 케이스 통과율이 임계 미만이나 사유 있음 → 제품 책임자 승인) / 저하(평가 결과 없음 = 배포 불가 — 단 등급 1~2 변경은 1/06 축소 게이트로 "축소 통과" 기록 후 배포, 등급 3 이상 불가(불균형 ⑥ 반영); 또는 카나리 비율 축소 배포). 판정 수단은 규칙(통과율 집계)이며 judge는 **입력**이지 판정자가 아니다 |
| 소유자 (A) | 골든셋·라벨 가이드: 제품 책임자(AI 엔지니어 R, 도메인 전문가 C). judge 선택·보정: AI 엔지니어 R, 아키텍트 A. 배포 임계값: 제품 책임자. 환류 주기·담당: 운영. 홀드아웃 접근 통제: 아키텍트 |
| 감사 추적에 남길 필드 | 배포 판정 건마다: 평가 대상 버전 조합(모델·프롬프트·인덱스·툴·규칙·질문 정의 버전), 골든셋 버전, judge 버전, 층별 결과와 통과율, 적용 임계값 버전, 판정(통과·차단·승인), 승인자(있다면)와 사유, 제외된 케이스와 제외 사유. 이 레코드가 있어야 "그때 왜 배포됐나"를 재구성한다 |

### 운영 준비도 체크
- [ ] 배포 게이트가 "평가 결과 없음 = 배포 불가"(fail-closed)이고, 예외는 1/06 축소 게이트(등급 1~2, "축소 통과" 기록 + 사후 judge)뿐이며 등급 3 이상은 예외가 없는가 (불균형 ⑥ 반영)
- [ ] 골든셋이 2/07 삭제 레인 소비자로 등록되어 삭제된 문서를 기대 근거로 가진 케이스가 자동으로 검수 대기로 빠지는가 (불균형 ① 반영)
- [ ] judge 버전이 고정되어 있거나, 고정 불가 시 사람 라벨 보정 셋이 매일 돌아 이동을 감지하는가
- [ ] NaN·파싱 실패를 실패로 집계하고 NaN 비율을 지표로 보는가
- [ ] 평가 환경의 툴이 모의·샌드박스로 격리되어 운영 데이터를 바꾸지 않는가
- [ ] judge 호출에 절대 건수 상한(비용 예산)과 캐시가 있는가
- [ ] 변경 → 회귀 트리거 매핑이 모든 버전 관리 대상을 덮는가(커버리지 테스트)
- [ ] 골든셋·judge·임계값이 버전 관리되고 judge + 베이스라인이 한 롤백 단위인가
- [ ] 배포 판정 레코드에 평가 대상 버전 조합과 골든셋·judge 버전이 남는가
