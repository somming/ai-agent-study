# 프레임워크 비교

> **범위**: LangGraph, Claude Agent SDK, OpenAI Agents SDK, Google ADK, CrewAI, Semantic Kernel 등 선택 기준
> Part 3의 01~13에서 내린 설계 결정을 **무엇으로 구현할 것인가**. 프레임워크의 API 사용법은 다루지 않는다. 각 프레임워크의 기능 서술은 공개 문서와 해설 기반(`[2차]` `[벤더]`)이며, 성능·인기 지표(GitHub 스타 수 등)는 소스 충돌로 인용하지 않는다.

## 요약 (3줄)

1. 2026년의 프레임워크 지형은 **벤더 네이티브 SDK**(Claude Agent SDK, OpenAI Agents SDK, Google ADK)와 **독립 프레임워크**(LangGraph, CrewAI, Pydantic AI, Semantic Kernel, AutoGen)로 나뉜다 `[2차]`. 첫 번째 선택 기준은 기능이 아니라 **벤더 종속을 허용할 것인가**다.
2. 최근 1년은 재편기였다. Swarm → OpenAI Agents SDK, Claude Code SDK → Claude Agent SDK, AutoGen 유지보수 모드, ADK의 다언어화(Java 1.0.0 2026-03) `[2차]`. 프레임워크는 **교체 가능하게** 쓴다 — 상태 스키마·툴 카탈로그·평가셋·판정 인터페이스를 프레임워크 밖에 둔다.
3. 선택 기준은 네 가지다. 벤더 종속 허용 여부, 상태·내구 실행 필요 여부, 팀 언어, 관측성 통합. 이 넷으로 후보가 1~2개로 좁혀지지 않으면 직접 구현도 진지한 선택지다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 프레임워크 선택과 그 근거(네 기준의 답) ② 프레임워크 밖에 둘 것의 목록(상태 스키마, 툴 카탈로그, `decide()` 인터페이스, 평가셋, 정책) ③ 교체·업그레이드 전략 |
| **언제** (When) | 01~13의 설계가 끝난 뒤. 프레임워크를 먼저 고르고 설계를 끼워 맞추면 프레임워크의 기본값이 아키텍처가 된다. 단일 프롬프트·단일 툴 수준이면 프레임워크 없이 SDK 직접 호출로 시작 |
| **어떻게** (How) | ① 벤더 종속 허용 여부 결정(모델 다변화 계획, 조달 정책) → ② 상태·내구 실행·HITL 대기 요구 확인([08](08-state-memory-context.md), [12](12-guardrails-hitl.md)) → ③ 팀 언어·기존 스택 → ④ 관측성·평가 통합 경로 → ⑤ 후보 1~2개로 핵심 경로 PoC `[실측]` → ⑥ 프레임워크 밖에 둘 것을 먼저 구현 |
| **왜** (Why) | 프레임워크는 가장 바뀌기 쉬운 층이다(1년 새 이름·소유·상태가 바뀐 것이 넷). 프레임워크에 설계를 묶으면 재편 때마다 재작성한다. 반대로 프레임워크 없이 상태·체크포인트·HITL을 직접 만들면 그 자체가 프로젝트가 된다 |

## 문제와 맥락

2024년의 질문은 "LangChain을 쓸까 말까"였다. 2026년의 질문은 다르다. 모델 벤더 셋이 각자 에이전트 SDK를 내놓았고(Anthropic은 Claude Code 런타임을 프로그래밍 노출한 Claude Agent SDK, OpenAI는 Swarm을 잇는 Agents SDK, Google은 ADK), 독립 프레임워크는 그래프·상태(LangGraph), 역할 기반 팀(CrewAI), 타입 안전(Pydantic AI), 엔터프라이즈 .NET 통합(Semantic Kernel)으로 각자 자리를 잡았다 `[2차]`. AutoGen은 유지보수 모드로 들어갔다 `[2차]`.

벤더 SDK는 자사 모델의 기능(hooks, 컨텍스트 관리, 툴 실행 환경)을 가장 빨리 쓰게 해 주지만 모델을 바꾸기 어렵게 만든다. 독립 프레임워크는 모델 중립이지만 벤더 신기능 지원이 늦고 추상화 비용이 있다. 이 트레이드오프가 선택의 중심이다.

## 핵심 개념

### 벤더 네이티브 vs 독립

| 구분 | 프레임워크 | 장점 | 비용 |
|---|---|---|---|
| **벤더 네이티브 SDK** | Claude Agent SDK, OpenAI Agents SDK, Google ADK | 자사 모델 신기능 즉시 반영, 벤더 지원, 런타임 통합(Claude Agent SDK는 Claude Code 런타임·hooks) | 모델 교체 비용, 벤더 로드맵 종속 |
| **독립 프레임워크** | LangGraph, CrewAI, Pydantic AI, Semantic Kernel, AutoGen(유지보수) | 모델 중립, 멀티 벤더 라우팅([Part 5/02](../05-cross-cutting/02-cost-latency-model-routing.md)) 용이 | 추상화 비용, 벤더 신기능 지연, 프레임워크 자체의 재편 위험 |
| **직접 구현** | 벤더 API + 자체 오케스트레이션 | 완전한 통제, 의존성 최소 | 체크포인트·HITL·트레이싱을 직접 만듦 |

출처: 벤더 네이티브 vs 독립 구분과 재편 사실은 `[2차]`.

### 네 가지 선택 기준

| 기준 | 질문 | 답에 따른 방향 |
|---|---|---|
| **벤더 종속 허용** | 향후 2년 내 모델 벤더를 바꾸거나 섞을 계획이 있는가, 조달 정책이 단일 벤더를 허용하는가 | 허용 → 벤더 SDK 후보. 불허 → 독립 프레임워크 또는 직접 구현 |
| **상태·내구 실행** | 다단계 과업, HITL 대기, 재개·분기·시간 여행 디버깅이 필요한가 | 필요 → 체크포인팅 내장(LangGraph) 또는 내구 실행 런타임 결합. 불필요 → 경량 SDK |
| **팀 언어** | Python 외 언어(Java, .NET, Go, TypeScript)로 운영하는가 | Java/Go/TS → Google ADK(다언어) `[2차]`, .NET → Semantic Kernel `[2차]`. Python만 → 전부 후보 |
| **관측성 통합** | 기존 OTel·APM 인프라가 있는가, 벤더 관측 플랫폼을 쓸 것인가 | OTel → OTel 익스포트 지원 확인. 벤더 플랫폼 → 해당 플랫폼과 궁합 좋은 프레임워크 |

### 프레임워크 밖에 둘 것

프레임워크를 교체 가능하게 만드는 핵심이다. 아래는 프레임워크의 객체가 아니라 **자체 모듈**로 정의한다.

- **상태 스키마** ([08](08-state-memory-context.md)): 프레임워크의 상태 클래스를 감싸는 자체 타입. 체크포인트 저장 포맷도 자체 정의
- **툴 카탈로그** ([09](09-tools-and-mcp.md)): 툴 정의·등급·정책을 프레임워크 데코레이터가 아닌 카탈로그에. MCP를 쓰면 자연히 분리된다
- **`decide()` 인터페이스** ([11](11-decision-layer.md)): 판정 수단을 프레임워크 노드 안에 하드코딩하지 않는다
- **정책·가드레일** ([12](12-guardrails-hitl.md)): 정책 엔진은 프레임워크 밖. 프레임워크의 hooks/guardrails 기능은 정책 엔진을 **호출하는 자리**로만
- **평가셋·트래젝토리 포맷** ([13](13-evaluation-rag-agents.md)): 프레임워크 트레이스 포맷에서 자체 포맷으로 변환하는 어댑터
- **프롬프트**: 버전 관리되는 자체 저장소

표의 기능 서술은 공개 문서·해설 기반이며 버전에 따라 바뀐다. 채택 전 현재 문서로 재확인한다.

## 아키텍처 / 파이프라인

```
[자체 모듈: 상태 스키마 · 툴 카탈로그 · decide() · 정책 엔진 · 평가셋 · 프롬프트 저장소]
                 │ 어댑터
                 ▼
[프레임워크: 그래프/루프 실행 · 체크포인트 저장 · hooks 호출 · 트레이스 방출]
                 │
                 ▼
[모델 벤더 API] · [MCP 서버] · [관측 플랫폼(OTel / 벤더)]
```

프레임워크는 가운데 층이다. 위 층(자체 모듈)이 두꺼울수록 가운데 층 교체가 쉽다.

### 선택 가이드

- **벤더 중립이 필수이고 상태·HITL이 복잡하다면** → LangGraph. 이유: 체크포인팅·내구 실행이 내장된 독립 프레임워크. 학습 곡선은 감수
- **단일 벤더를 허용하고 그 벤더의 런타임 기능을 쓰고 싶다면** → 해당 벤더 SDK(Claude Agent SDK / OpenAI Agents SDK / ADK). 이유: 신기능·hooks·컨텍스트 관리가 가장 빠르다. 단 프레임워크 밖 모듈로 교체 가능성 확보
- **Java·Go·TypeScript·.NET 팀이라면** → ADK(Java/Go/TS) 또는 Semantic Kernel(.NET). 이유: 언어 지원이 선택지를 결정한다
- **요구가 단순하다면** → 벤더 API 직접 호출 + 자체 루프. 이유: 프레임워크의 추상화 비용이 이득보다 크다. 복잡해지면 그때 옮긴다
- **판단이 어려우면** → 프레임워크 밖 모듈(상태 스키마·툴 카탈로그·`decide()`·정책·평가셋)을 먼저 만들고, LangGraph와 벤더 SDK 하나로 핵심 경로를 PoC해 `[실측]` 비교. 이유: 밖 모듈이 있으면 어느 쪽을 골라도 되돌릴 수 있다

## 설계 시 고려사항 (체크리스트)

- [ ] 벤더 종속 허용 여부가 조달·보안·모델 다변화 계획과 함께 문서화되어 있는가
- [ ] 상태·내구 실행·HITL 대기 요구를 [08](08-state-memory-context.md)·[12](12-guardrails-hitl.md)에서 확인한 뒤 프레임워크를 골랐는가
- [ ] 상태 스키마·툴 카탈로그·`decide()`·정책·평가셋·프롬프트가 프레임워크 밖 자체 모듈인가
- [ ] 프레임워크의 hooks/guardrails 기능이 정책 엔진을 호출하는 자리로만 쓰이는가
- [ ] 프레임워크 트레이스를 자체 트래젝토리 포맷·OTel로 내보내는 어댑터가 있는가
- [ ] 버전 고정과 업그레이드 절차가 있는가 (재편기)

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 프레임워크는 Part 3에서 **가장 자주 바뀌는 외부 의존**이자 **가장 넓게 번지는 의존**이다. 이 단계의 운영 설계는 다른 단계와 달리 "프레임워크가 제공하는 기능"이 아니라 "프레임워크가 바뀌어도 다른 단계가 안 바뀌는가"를 다룬다.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 팀 수(프레임워크를 쓰는 팀 1 → 10) | 팀마다 다른 버전·다른 패턴·다른 트레이스 포맷. 업그레이드가 팀 수만큼 반복되고 공통 모듈(상태 스키마·툴 카탈로그·`decide()`)이 포크됨 | **공통 밖 모듈을 내부 라이브러리로** 배포(버전 관리, 소유 팀), 프레임워크 버전 허용 범위를 플랫폼이 선언, 팀별 어댑터는 금지하고 공통 어댑터만 | 팀 수 × (프레임워크 버전 수 + 포크된 모듈 수) |
| 프레임워크 업그레이드 빈도 | 재편기라 메이저 업·개명·유지보수 모드 전환이 연 수 회. 매번 전 팀이 멈추면 업그레이드 자체가 운영 부담 | **계획된 업그레이드 창**(분기 1회 예시), 버전 고정, 어댑터 계층에서 흡수, 카나리 팀 먼저 | 업그레이드 횟수 × 영향 팀 수 × 어댑터 두께의 역수 |
| 실행 수(런타임 부하) | 프레임워크 내장 체크포인트 저장소·세션 저장소의 기본 구현(로컬·단일 인스턴스)이 한계. 기본값이 운영 저장소가 되어 있으면 수평 확장 불가 | 체크포인트·세션 저장소를 **외부 저장소 어댑터**로 교체([08](08-state-memory-context.md)), 무상태 워커 | 실행 수 × 프레임워크 상태 쓰기량 |
| 모델 벤더 수 | 벤더 SDK는 멀티 벤더 라우팅이 어렵고, 독립 프레임워크는 벤더 신기능 어댑터가 벤더 수만큼 | 모델 호출 포트 + 벤더 어댑터([Part 5/02](../05-cross-cutting/02-cost-latency-model-routing.md)), 벤더 SDK 선택 시 멀티 벤더 포기를 명시적 결정으로 | 벤더 수 × 어댑터 유지 비용 |
| 트레이스 양 | 프레임워크 기본 트레이스가 상세해 저장 비용 폭증, 자체 포맷 변환 비용 | 샘플링은 관측 로그에만(감사 레코드는 별도·전수), 변환 어댑터 배치화 | 실행 수 × 스텝당 스팬 수 |

비용이 비례하는 핵심 변수는 **"프레임워크 안에 있는 코드의 양"**이다. 밖 모듈이 두꺼울수록 팀 수·업그레이드 빈도의 비용 계수가 작아진다.

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| **프레임워크 메이저 업으로 호환 깨짐**(상태 클래스 변경, hooks 시그니처 변경, 체크포인트 포맷 변경) | 배포 직후 재개 실패, hooks(가드레일 호출 자리) 미실행 → **가드레일 없이 동작** | CI 어댑터 계약 테스트 실패, 재개 테스트 실패, hooks 호출 수 0 | **버전 고정**으로 비계획 업그레이드 자체를 차단. 계획 업그레이드는 카나리 팀·카나리 트래픽. hooks 호출 수가 0이면 **배포 자동 롤백**(가드레일 미실행은 등급 최상 장애) | 어댑터 수정 후 재배포. 업그레이드 창 밖 메이저 업은 아키텍트 승인 |
| **프레임워크 유지보수 모드·폐기**(AutoGen 사례) | 즉시 증상 없음. 보안 패치 중단, 벤더 SDK 호환 끊김이 수개월 뒤 | 프레임워크 릴리스 주기 모니터, 의존성 보안 알림 | 없음(자동 대응 불가). 대신 **교체 시나리오 추정이 사전에 있어야** 함 | 유지보수 모드 선언 시 분기 내 교체 계획 수립. 신규 의존 추가 즉시 금지(CI 규칙) |
| **프레임워크 내장 상태 저장소 장애**(기본 구현 사용 시) | 재개 불가, 세션 유실 | 저장소 오류율 | 외부 저장소 어댑터로 이미 교체되어 있으면 [08](08-state-memory-context.md) 대응. 기본 구현이면 **읽기 전용 저하**만 가능 | 기본 구현을 운영에서 쓰고 있었다면 ORR 위반으로 기록 |
| **벤더 SDK의 벤더 API 변경 종속**(모델 폐기·가격·한도 변경이 SDK 업데이트 강제) | 특정 모델 호출 실패, 비용 급증 | 모델 호출 오류율, 비용 알림 | 모델 호출 포트 뒤 어댑터에서 **모델 ID 매핑 표**로 대체 모델 라우팅(설정) | 벤더 공지 확인, 매핑 표 갱신 |
| **프레임워크 추상화 누수**(기본 루프의 종료·재시도 동작이 바뀜) | 무한 루프·조기 종료가 갑자기 발생 | 스텝 수 p95 급변, 상한 도달률, L3 트래젝토리 효율 지표 | 실행 전체 상한(스텝·토큰·시간)은 **프레임워크 밖**에서 강제 — 프레임워크 상한에 의존하지 않음 | 업그레이드 후 효율 지표 변동 시 루프 코드 변경 사항 확인 |
| **멀티 프레임워크 혼용 시 트레이스·상태 포맷 불일치** | 멀티에이전트 경계에서 컨텍스트 유실, 트래젝토리 추출 실패 | 핸드오프 실패율, 추출 건수 감소 | 자체 포맷 어댑터가 변환 실패 시 **해당 핸드오프 차단 + 사람 경로** | 포맷 통일 작업 |
| **MCP 클라이언트 개정 미지원**(2026-07-28) | 신 서버와 통신 실패 | MCP 핸드셰이크 오류 | 호환 레이어 또는 구서버 유지 | SDK 업그레이드 계획 |

SLI 후보: hooks 호출률(게이트가 있어야 할 툴 호출 대비 hooks 실행 비율 — **100% 아니면 장애**), 재개 성공률, 어댑터 계약 테스트 통과율, 프레임워크 버전 분산(팀 간 버전 수), 업그레이드 리드타임(릴리스 → 전 팀 적용). SLO 초안(예시): hooks 호출률 100%, 재개 성공률 99%, 팀 간 버전 수 2 이하, 메이저 업 적용 리드타임 1분기 이내. 쓰기 행동은 이 단계에 없다. 단 **프레임워크 hooks가 유일한 가드레일 호출 자리라면 hooks 미실행 = 가드레일 없음**이므로, 행동 게이트는 hooks와 무관하게 툴 실행 포트([09](09-tools-and-mcp.md)) 안에서도 한 번 더 평가되게 둔다(이중 호출은 멱등).

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| **프레임워크 버전**(및 하위 의존) | 상태 클래스, 체크포인트 포맷, hooks 시그니처, 트레이스 포맷, MCP 클라이언트 | **어댑터 계약 테스트**(상태 변환·hooks 호출·트레이스 변환·재개), 전체 L2·L3 | 어댑터 버전, 체크포인트 마이그레이션 |
| **어댑터 계층**(상태·hooks·트레이스·MCP) | 밖 모듈과 프레임워크의 연결 | 계약 테스트 | 프레임워크 버전 범위 선언 |
| **밖 모듈**(상태 스키마·툴 카탈로그·`decide()`·정책·평가셋·프롬프트 저장소) | 각 단계 페이지의 버전 관리 대상 그대로. 이 페이지에서는 "내부 라이브러리 버전"으로 묶임 | 각 단계의 회귀 | 모듈 간 호환 매트릭스(상태 스키마 v3는 체크포인트 어댑터 v2 이상) |
| **프레임워크 버전 허용 범위**(플랫폼 선언) | 팀의 업그레이드 가능 범위 | 범위 내 모든 버전으로 계약 테스트 | — |
| **모델 ID 매핑 표**(벤더 SDK 사용 시) | 실제 호출 모델 | 모델 골든셋 | 프롬프트-모델 호환 |

롤백 단위: 프레임워크 버전 + 어댑터 + 체크포인트 마이그레이션은 한 묶음(프레임워크만 되돌리면 새 포맷 체크포인트를 못 읽음 — **다운그레이드 가능성을 업그레이드 전에 확인**). 기술 부채로 기록할 것: "팀 B는 프레임워크 내장 체크포인트 저장소 사용 중 → 외부 어댑터 전환 예정", "트레이스 변환 어댑터는 OTel Development 등급 속성에 의존 → 컨벤션 안정화 시 재작성", "교체 시나리오 추정 미실시".

| **사용자 환경**(팀 추가, 언어 스택 추가 — Java·.NET 팀 합류) | 지원 언어, 팀별 프레임워크 | 밖 모듈의 **언어 중립 계약**(스키마는 JSON Schema, 정책은 엔진 API, 툴은 MCP) | 언어별 프레임워크(ADK·Semantic Kernel) | 계약을 언어 중립으로 두어 프레임워크가 달라도 같은 상태·툴·정책 공유 | 어댑터 추가만 |
| **지식·도메인 모델** | 해당 없음 — 프레임워크 레이어는 지식을 들지 않는다. 들고 있으면 설계 오류 | — | — | — | — |
| **부하·규모** | 실행 수 10배 | 무상태 워커, 외부 저장소 | 프레임워크 내장 저장소 → 외부 | 저장소 어댑터 교체 | 저장소 계층 |

가장 자주 바뀌는 것: **프레임워크 자체(프로토콜·SDK)** — 다른 단계와 달리 이 단계에서는 지식·규칙보다 프레임워크가 더 자주 바뀐다(1년 새 넷). 그래서 흡수 경계는 "두꺼운 밖 모듈 + 얇은 어댑터"이고, 판단 기준은 **"프레임워크를 바꿀 때 01~13 페이지의 산출물 중 무엇이 바뀌는가 — 답이 '없음'이어야 한다"**. 코드 밖 설정으로 둘 것: 프레임워크 버전 허용 범위, 모델 ID 매핑 표, 실행 상한(스텝·토큰·시간), 업그레이드 창 일정. 포트·어댑터 뒤에 둘 외부 의존: 프레임워크(상태·hooks·트레이스·MCP 클라이언트), 모델 벤더 API, 관측 플랫폼.

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성의 "탐지 신호"가 **실제로 어디서 나오는지**를 설계한다. 기준은 [Part 1/07 관측성 설계 요소](../01-foundations/07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md). 프레임워크는 **스팬을 내는 자리**(hooks·콜백·트레이스 익스포터)를 제공할 뿐이므로, 이 단계의 고유한 관측 대상은 "스팬이 **빠지는** 지점"이다 — 장애가 지표 값이 아니라 **없는 스팬**으로 나타나기 때문에, 기대 스팬 대비 실제 스팬을 세는 **계측 커버리지**를 별도 지표로 둔다. 다른 모든 단계의 관측이 이 커버리지에 기댄다.

| 기록 대상 | 스팬 / 이벤트 (이름, 부모) | 핵심 속성 (버전 키 포함) | 지표 (→ 어느 SLI) | 샘플링 · 보존 · PII |
|---|---|---|---|---|
| hooks → 게이트 호출 | hooks가 내는 `gate.evaluate {gate}`(부모 `tool.invoke {tool}`), 툴 실행 포트의 재평가는 같은 이름에 `agent.gate_caller=port` | `agent.gate_caller`(hook / port), `agent.hook_name, agent.framework_version, agent.adapter_version, agent.rules_version` | **hooks 호출률**(게이트가 필요한 `tool.invoke` 중 `gate_caller=hook` 자식을 가진 비율 → 동명 SLI, 100% 아니면 장애), hook·port 판정 불일치 건수(이중 호출 멱등 검증) | 전수. hook 없이 port만 판정한 건은 감사 레코드로 복제 |
| 계측 커버리지 | 배치 `trace.completeness_check`(시간 단위, 종료된 트레이스 대상) | 스팬 종류별 기대 vs 실제 — `agent.coverage{span}`(state.checkpoint / gate.evaluate / generation.generate / tool.invoke / memory.*), 버전 키 5종 + `agent.framework_version / adapter_version` 누락률, `gen_ai.*` 매핑 누락률 | **계측 커버리지**(스팬 종류 × 프레임워크 × 팀), 속성 누락률, 고아 스팬(부모 없음) 비율 | 전수(집계만 저장) |
| 어댑터 경계 | `agent.handoff {from→to}`(멀티 프레임워크·멀티에이전트 경계, 부모 `invoke_agent {name}`); `state.checkpoint` / `state.restore`에 `agent.store_impl`(builtin / external), `agent.checkpoint_format_version` | `agent.framework_from / framework_to, agent.format_adapter_version, agent.outcome`(ok / convert_failed → 사람 경로) | 핸드오프 실패율, 재개 성공률(→ 동명 SLI), **builtin 저장소로 돈 운영 실행 수**(0이어야), 포맷 버전 혼재 수 | 실패 건 전수 |
| 실행 상한 | `invoke_agent {name}` 속성 `agent.steps, agent.tokens_total, agent.wall_ms, agent.cap_hit`(step / token / time / none), `agent.cap_enforced_by`(external / framework) | 프레임워크·어댑터 버전 | 스텝 수 p95(프레임워크 버전별 — 추상화 누수 신호), 상한 도달률, `cap_enforced_by=framework` 비율(0이어야 — 외부 강제가 먼저 걸려야 한다) | 상한 도달 건 전수 |
| 모델 호출 매핑 | `generation.generate`(`gen_ai.*`) + `agent.model_alias, agent.model_mapping_version, agent.sdk_version` | 벤더·모델 ID, 비용 | 모델별 오류율(폐기 모델 `not_found` 급증), 매핑 표 폴백 발동률, 모델별 비용 비중 | 메타 전수 |
| 프로토콜·의존성 | `mcp.connect {server}`(`agent.mcp_protocol_version_client / server`); 배치 `ci.dependency_audit` | `agent.framework_release_age_days, agent.deps_vuln_count, agent.framework_versions_in_fleet[]`, 유지보수 모드 플래그 | MCP 핸드셰이크 오류율, 팀 간 프레임워크 버전 수(→ 동명 SLI), 업그레이드 리드타임(→ 동명 SLI), 유지보수 모드 의존 수 | 전수 |

| 알림 | 조건 (예시) | 심각도 | 런북 (첫 3단계) |
|---|---|---|---|
| hooks 호출률 < 100% | 10분 창에서 게이트 필요 `tool.invoke` 중 `gate_caller=hook` 자식이 없는 건 1건 이상 | **P1** (가드레일 미실행) | ① 배포 자동 롤백 발동 확인 ② 해당 건을 포트 재평가(`gate_caller=port`)가 막았는지 감사 레코드로 확인 — 못 막았으면 [12](12-guardrails-hitl.md) 미탐 절차 ③ 어댑터 계약 테스트 재실행, 프레임워크·어댑터 버전 diff |
| 계측 커버리지 하락 | 스팬 종류별 커버리지 < 99% 1시간, 또는 버전 키 누락률 > 1%(업그레이드 직후 24시간은 민감도 상향) | P2 | ① 프레임워크·어댑터 버전 변경 시점과 대조 ② 누락 스팬 종류와 팀·서비스 식별 ③ 해당 구간 트레이스는 L3 평가([13](13-evaluation-rag-agents.md))에서 "불완전" 태그, 품질 지표에 주석 |
| 상한 동작 변화 | 스텝 수 p95 전주 대비 ±50%, 또는 `cap_enforced_by=framework` 1건 | P2 | ① 업그레이드 diff에서 루프 종료·재시도 동작 변경 확인 ② 외부 상한 강제 코드가 프레임워크 상한보다 먼저 걸리는지 확인 ③ L3 효율 지표 전후 비교 |
| 재개·핸드오프 실패 | 재개 실패율 > 1%, 또는 `convert_failed` > 0.5% 15분 | P2 | ① 체크포인트 포맷 버전 혼재 확인 ② 구버전 마이그레이션 실행 ③ 사람 경로 유입량 확인, 포맷 통일 작업 등록 |
| builtin 저장소·폐기 의존 | `store_impl=builtin` 운영 트레이스 1건, 또는 유지보수 모드 프레임워크에 신규 의존 추가 | P3 (ORR 위반으로 기록) | ① 해당 팀·서비스 식별 ② 외부 저장소 어댑터 전환 계획 ③ CI 규칙 보강 |

- **대시보드에서 이 단계를 보는 뷰**: ② 레이어·단계별 SLI 패널 하단에 "계측 커버리지" 행(스팬 종류 × 프레임워크 × 팀) — 위쪽 모든 패널의 **신뢰도 주석** 역할. hooks 호출률은 Action 패널에 100% 기준선과 함께. ③ 비용·판정 분포 — 프레임워크·버전별 비용 비중, 스텝 수 분포(버전 전환선 표시), 모델 매핑 폴백 발동률.
- **감사 추적으로 넘기는 필드(관측 로그와 분리)**: 실행 레코드마다 프레임워크·어댑터 버전(시점 재현의 전제). 업그레이드 건마다 전후 버전, 계약 테스트 결과, 카나리 지표, 승인자 2인, 체크포인트 마이그레이션 실행 여부, 롤백 가능 확인 결과 — 변경 관리 저장소. hooks 미실행 건에서 포트 재평가가 내린 판정은 감사 레코드 필수.
- **이 단계의 관측이 없으면 못 보는 장애**: **가드레일이 호출되지 않는 것**. 모든 요청이 성공하고 지연도 정상이다 — 게이트가 빠졌다는 사실은 어떤 지표 값에도 나타나지 않고 **있어야 할 스팬이 없다**는 형태로만 존재한다. hooks 호출률과 계측 커버리지가 없으면 이 장애를 못 볼 뿐 아니라, 다른 모든 단계의 관측이 "빠진 스팬 = 발생하지 않은 일"로 읽혀 통째로 거짓 안심이 된다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | 프레임워크 선택·교체·메이저 업은 사용자 행동이 아니라 **변경 관리 대상**. 영향이 전 사용자·전 팀이고 롤백에 체크포인트 마이그레이션이 필요하므로 **등급 4 변경**(승인 2인: 아키텍트 + 플랫폼 소유자, 카나리 기간 = 섀도 기간) |
| 가드레일 위치 | 프레임워크는 가드레일을 **호출하는 자리**(hooks·콜백·필터)를 제공할 뿐 가드레일이 아니다. 세 지점의 가드레일은 밖 모듈([12](12-guardrails-hitl.md))에 있고, hooks 미실행 시에도 툴 실행 포트에서 행동 게이트가 재평가되게 둔다 |
| 게이트 출력과 판정 수단 | 업그레이드 배포 게이트: 통과(계약 테스트 + L2·L3 + 카나리 지표 충족) / 차단(hooks 호출률 100% 미만, 재개 실패) / 승인 요청(창 밖 긴급 업그레이드 — 보안 패치) / 저하(카나리 비율 유지, 확대 보류). 판정 수단은 규칙(테스트·지표 집계) |
| 소유자 (A) | 프레임워크 선택·버전 범위·업그레이드 창: 아키텍트(플랫폼 엔지니어 R, 각 팀 리드 C, 전체 I). 어댑터 계층: 플랫폼 엔지니어. 밖 모듈 각각: 해당 단계 페이지의 소유자. 벤더 종속 허용 결정: 아키텍트 + 조달·보안 C |
| 감사 추적에 남길 필드 | 실행 레코드마다 **프레임워크 버전·어댑터 버전**(시점 재현의 전제). 업그레이드 건마다: 변경 전후 버전, 계약 테스트 결과, 카나리 지표, 승인자 2인, 체크포인트 마이그레이션 실행 여부, 롤백 가능 확인 결과 |

### 운영 준비도 체크
- [ ] 프레임워크 버전이 고정되어 있고 비계획 업그레이드가 CI에서 차단되는가
- [ ] 어댑터 계약 테스트(상태 변환·hooks 호출·트레이스 변환·재개)가 있고 업그레이드 시 자동 실행되는가
- [ ] hooks 호출률을 측정하고 100% 미만이면 배포 자동 롤백인가
- [ ] 행동 게이트가 hooks 외에 툴 실행 포트에서도 평가되는가(hooks 미실행 대비)
- [ ] 실행 상한(스텝·토큰·시간)이 프레임워크 밖에서 강제되는가
- [ ] 체크포인트·세션 저장소가 프레임워크 기본 구현이 아닌 외부 저장소 어댑터인가
- [ ] 프레임워크 교체 시나리오(비용·기간·바뀌는 산출물 목록)를 추정해 두었고 "바뀌는 01~13 산출물"이 없는가
- [ ] 유지보수 모드 프레임워크에 신규 의존 추가가 CI 규칙으로 금지되어 있는가
- [ ] 모든 실행 레코드에 프레임워크·어댑터 버전이 기록되는가
- [ ] hooks에서 나온 `gate.evaluate`와 툴 실행 포트의 재평가가 `agent.gate_caller`로 구분되어 hooks 호출률을 트레이스에서 직접 계산하는가
- [ ] 스팬 종류별 계측 커버리지와 버전 키 누락률을 재는 완결성 검사가 돌고, 업그레이드 직후 24시간 민감도를 높이는가
