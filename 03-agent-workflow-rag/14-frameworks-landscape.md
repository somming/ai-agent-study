# 프레임워크 비교

> **범위**: LangGraph, Claude Agent SDK, OpenAI Agents SDK, Google ADK, CrewAI, Semantic Kernel 등 선택 기준
> Part 3의 01~13에서 내린 설계 결정을 **무엇으로 구현할 것인가**. 프레임워크의 API 사용법은 다루지 않는다. 각 프레임워크의 기능 서술은 공개 문서와 해설 기반(`[2차]` `[벤더]`)이며, 성능·인기 지표(GitHub 스타 수 등)는 소스 충돌로 인용하지 않는다.

## 요약 (3줄)

1. 2026년의 프레임워크 지형은 **벤더 네이티브 SDK**(Claude Agent SDK, OpenAI Agents SDK, Google ADK)와 **독립 프레임워크**(LangGraph, CrewAI, Pydantic AI, Semantic Kernel, AutoGen)로 나뉜다 `[2차]`. 첫 번째 선택 기준은 기능이 아니라 **벤더 종속을 허용할 것인가**다.
2. 최근 1년은 재편기였다. Swarm → OpenAI Agents SDK, Claude Code SDK → Claude Agent SDK, AutoGen 유지보수 모드, ADK의 다언어화(Java 1.0.0 2026-03) `[2차]`. 프레임워크는 **교체 가능하게** 쓴다 — 상태 스키마·툴 카탈로그·평가셋·판정 인터페이스를 프레임워크 밖에 둔다.
3. 선택 기준은 네 가지다. 벤더 종속 허용 여부, 상태·내구 실행 필요 여부, 팀 언어, 관측성 통합. 이 넷으로 후보가 1~2개로 좁혀지지 않으면 직접 구현도 진지한 선택지다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 프레임워크 선택과 그 근거(네 기준의 답) ② 프레임워크 밖에 둘 것의 목록(상태 스키마, 툴 카탈로그, `decide()` 인터페이스, 평가셋, 정책) ③ 교체·업그레이드 전략 |
| **언제** (When) | 01~13의 설계가 끝난 뒤. 프레임워크를 먼저 고르고 설계를 끼워 맞추면 프레임워크의 기본값이 아키텍처가 된다. 단일 프롬프트·단일 툴 수준이면 프레임워크 없이 SDK 직접 호출로 시작 |
| **어떻게** (How) | ① 벤더 종속 허용 여부 결정(모델 다변화 계획, 조달 정책) → ② 상태·내구 실행·HITL 대기 요구 확인([08](08-state-memory-context.md), [12](12-guardrails-hitl.md)) → ③ 팀 언어·기존 스택 → ④ 관측성·평가 통합 경로 → ⑤ 후보 1~2개로 핵심 경로 PoC `[실측]` → ⑥ 프레임워크 밖에 둘 것을 먼저 구현 |
| **왜** (Why) | 프레임워크는 가장 바뀌기 쉬운 층이다(1년 새 이름·소유·상태가 바뀐 것이 넷). 프레임워크에 설계를 묶으면 재편 때마다 재작성한다. 반대로 프레임워크 없이 상태·체크포인트·HITL을 직접 만들면 그 자체가 프로젝트가 된다 |

## 문제와 맥락

2024년의 질문은 "LangChain을 쓸까 말까"였다. 2026년의 질문은 다르다. 모델 벤더 셋이 각자 에이전트 SDK를 내놓았고(Anthropic은 Claude Code 런타임을 프로그래밍 노출한 Claude Agent SDK, OpenAI는 Swarm을 잇는 Agents SDK, Google은 ADK), 독립 프레임워크는 그래프·상태(LangGraph), 역할 기반 팀(CrewAI), 타입 안전(Pydantic AI), 엔터프라이즈 .NET 통합(Semantic Kernel)으로 각자 자리를 잡았다 `[2차]`. AutoGen은 유지보수 모드로 들어갔다 `[2차]`.

벤더 SDK는 자사 모델의 기능(hooks, 컨텍스트 관리, 툴 실행 환경)을 가장 빨리 쓰게 해 주지만 모델을 바꾸기 어렵게 만든다. 독립 프레임워크는 모델 중립이지만 벤더 신기능 지원이 늦고 추상화 비용이 있다. 이 트레이드오프가 선택의 중심이다.

## 핵심 개념

### 벤더 네이티브 vs 독립

| 구분 | 프레임워크 | 장점 | 비용 |
|---|---|---|---|
| **벤더 네이티브 SDK** | Claude Agent SDK, OpenAI Agents SDK, Google ADK | 자사 모델 신기능 즉시 반영, 벤더 지원, 런타임 통합(Claude Agent SDK는 Claude Code 런타임·hooks) | 모델 교체 비용, 벤더 로드맵 종속 |
| **독립 프레임워크** | LangGraph, CrewAI, Pydantic AI, Semantic Kernel, AutoGen(유지보수) | 모델 중립, 멀티 벤더 라우팅([Part 5/02](../05-cross-cutting/02-cost-latency-model-routing.md)) 용이 | 추상화 비용, 벤더 신기능 지연, 프레임워크 자체의 재편 위험 |
| **직접 구현** | 벤더 API + 자체 오케스트레이션 | 완전한 통제, 의존성 최소 | 체크포인트·HITL·트레이싱을 직접 만듦 |

출처: 벤더 네이티브 vs 독립 구분과 재편 사실은 `[2차]`.

### 네 가지 선택 기준

| 기준 | 질문 | 답에 따른 방향 |
|---|---|---|
| **벤더 종속 허용** | 향후 2년 내 모델 벤더를 바꾸거나 섞을 계획이 있는가, 조달 정책이 단일 벤더를 허용하는가 | 허용 → 벤더 SDK 후보. 불허 → 독립 프레임워크 또는 직접 구현 |
| **상태·내구 실행** | 다단계 과업, HITL 대기, 재개·분기·시간 여행 디버깅이 필요한가 | 필요 → 체크포인팅 내장(LangGraph) 또는 내구 실행 런타임 결합. 불필요 → 경량 SDK |
| **팀 언어** | Python 외 언어(Java, .NET, Go, TypeScript)로 운영하는가 | Java/Go/TS → Google ADK(다언어) `[2차]`, .NET → Semantic Kernel `[2차]`. Python만 → 전부 후보 |
| **관측성 통합** | 기존 OTel·APM 인프라가 있는가, 벤더 관측 플랫폼을 쓸 것인가 | OTel → OTel 익스포트 지원 확인. 벤더 플랫폼 → 해당 플랫폼과 궁합 좋은 프레임워크 |

### 프레임워크 밖에 둘 것

프레임워크를 교체 가능하게 만드는 핵심이다. 아래는 프레임워크의 객체가 아니라 **자체 모듈**로 정의한다.

- **상태 스키마** ([08](08-state-memory-context.md)): 프레임워크의 상태 클래스를 감싸는 자체 타입. 체크포인트 저장 포맷도 자체 정의
- **툴 카탈로그** ([09](09-tools-and-mcp.md)): 툴 정의·등급·정책을 프레임워크 데코레이터가 아닌 카탈로그에. MCP를 쓰면 자연히 분리된다
- **`decide()` 인터페이스** ([11](11-decision-layer.md)): 판정 수단을 프레임워크 노드 안에 하드코딩하지 않는다
- **정책·가드레일** ([12](12-guardrails-hitl.md)): 정책 엔진은 프레임워크 밖. 프레임워크의 hooks/guardrails 기능은 정책 엔진을 **호출하는 자리**로만
- **평가셋·트래젝토리 포맷** ([13](13-evaluation-rag-agents.md)): 프레임워크 트레이스 포맷에서 자체 포맷으로 변환하는 어댑터
- **프롬프트**: 버전 관리되는 자체 저장소

표의 기능 서술은 공개 문서·해설 기반이며 버전에 따라 바뀐다. 채택 전 현재 문서로 재확인한다.

## 아키텍처 / 파이프라인

```
[자체 모듈: 상태 스키마 · 툴 카탈로그 · decide() · 정책 엔진 · 평가셋 · 프롬프트 저장소]
                 │ 어댑터
                 ▼
[프레임워크: 그래프/루프 실행 · 체크포인트 저장 · hooks 호출 · 트레이스 방출]
                 │
                 ▼
[모델 벤더 API] · [MCP 서버] · [관측 플랫폼(OTel / 벤더)]
```

프레임워크는 가운데 층이다. 위 층(자체 모듈)이 두꺼울수록 가운데 층 교체가 쉽다.

### 선택 가이드

- **벤더 중립이 필수이고 상태·HITL이 복잡하다면** → LangGraph. 이유: 체크포인팅·내구 실행이 내장된 독립 프레임워크. 학습 곡선은 감수
- **단일 벤더를 허용하고 그 벤더의 런타임 기능을 쓰고 싶다면** → 해당 벤더 SDK(Claude Agent SDK / OpenAI Agents SDK / ADK). 이유: 신기능·hooks·컨텍스트 관리가 가장 빠르다. 단 프레임워크 밖 모듈로 교체 가능성 확보
- **Java·Go·TypeScript·.NET 팀이라면** → ADK(Java/Go/TS) 또는 Semantic Kernel(.NET). 이유: 언어 지원이 선택지를 결정한다
- **요구가 단순하다면** → 벤더 API 직접 호출 + 자체 루프. 이유: 프레임워크의 추상화 비용이 이득보다 크다. 복잡해지면 그때 옮긴다
- **판단이 어려우면** → 프레임워크 밖 모듈(상태 스키마·툴 카탈로그·`decide()`·정책·평가셋)을 먼저 만들고, LangGraph와 벤더 SDK 하나로 핵심 경로를 PoC해 `[실측]` 비교. 이유: 밖 모듈이 있으면 어느 쪽을 골라도 되돌릴 수 있다

## 설계 시 고려사항 (체크리스트)

- [ ] 벤더 종속 허용 여부가 조달·보안·모델 다변화 계획과 함께 문서화되어 있는가
- [ ] 상태·내구 실행·HITL 대기 요구를 [08](08-state-memory-context.md)·[12](12-guardrails-hitl.md)에서 확인한 뒤 프레임워크를 골랐는가
- [ ] 상태 스키마·툴 카탈로그·`decide()`·정책·평가셋·프롬프트가 프레임워크 밖 자체 모듈인가
- [ ] 프레임워크의 hooks/guardrails 기능이 정책 엔진을 호출하는 자리로만 쓰이는가
- [ ] 프레임워크 트레이스를 자체 트래젝토리 포맷·OTel로 내보내는 어댑터가 있는가
- [ ] 버전 고정과 업그레이드 절차가 있는가 (재편기)

| 인기 지표의 소스 충돌 | 스타 수 등으로 판단하면 오류 | 인용하지 않음, 네 기준으로 판단 |
| 멀티 프레임워크 혼용 | 상태·트레이스 포맷 불일치 | 자체 포맷으로 통일하는 어댑터 |
