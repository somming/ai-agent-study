# Generative UI 스펙트럼

> **범위**: Controlled / Declarative / Open-ended 3패턴의 통제 vs 자유도 트레이드오프. 각 패턴이 디자인 시스템·접근성·보안·테스트 가능성에 미치는 영향과, 패턴에 대응하는 프로토콜. 프로토콜 자체의 비교는 [02](02-protocols-ag-ui-a2ui-mcp-apps.md), 컴포넌트 카탈로그 설계는 [03](03-component-registry-schema.md).
> **시각화**: [`assets/html/dynamic-ui-architecture.html`](../assets/html/dynamic-ui-architecture.html) — Part 4 전체 흐름. 이 페이지는 그 중 "통제 수준" 결정에 해당

## 요약 (3줄)

1. Generative UI(생성형 UI)는 "에이전트가 UI를 그린다"가 아니라 **"에이전트가 UI에 대해 얼마나 결정하는가"** 의 스펙트럼이다. 사전 정의 컴포넌트를 **고르기만** 하는 Controlled, UI 트리를 **기술**하는 Declarative, HTML·코드를 **생성**하는 Open-ended 세 패턴으로 정리된다 `[2차]`.
2. 자유도가 올라갈수록 표현력은 늘지만 디자인 시스템 일관성·접근성·보안·테스트 가능성은 **같은 방향으로 함께** 무너진다. 트레이드오프를 상쇄할 수단(스키마 검증, 샌드박스)은 자유도가 높은 쪽일수록 비싸진다.
3. 기본값은 Controlled다. 대부분의 팀이 프레임워크 기본값 때문에 Controlled로 흘러간다는 지적이 있는데 `[2차]`, 이 위키는 그것을 **우연이 아니라 올바른 기본값**으로 본다. Declarative·Open-ended는 Controlled로 표현할 수 없는 요구가 확인된 뒤에만 부분적으로 연다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 시스템의 UI 통제 수준 결정(세 패턴 중 하나, 또는 화면 영역별 혼합) ② 그 결정의 근거 문서 ③ 자유도가 높은 영역에 적용할 상쇄 수단 목록(스키마 검증·샌드박스·폴백) |
| **언제** (When) | Part 4 설계의 **첫 단계**. 프로토콜·레지스트리·매핑 방식이 모두 이 결정에 종속된다. 사용자가 결과를 읽기만 하는 QA 시스템이라면 "텍스트 + citation 렌더"로 충분하므로 이 결정 자체를 생략할 수 있다 |
| **어떻게** (How) | ① 사용자가 UI로 **무엇을 하는지** 열거(읽기 / 선택·비교 / 입력·수정 / 승인) → ② 각 행위에 필요한 컴포넌트를 세어 본다 → ③ 컴포넌트 수가 수십 개 이내이고 조합이 단순하면 Controlled → ④ 조합이 폭발적이거나 모바일 네이티브 렌더가 필요하면 Declarative 검토 → ⑤ 서드파티 툴이 자기 UI를 가져와야 하면 그 영역만 Open-ended(샌드박스) → ⑥ 결정과 상쇄 수단을 문서화 |
| **왜** (Why) | 통제 수준을 정하지 않고 "에이전트가 알아서 UI를 만들게" 하면 ① 같은 질문에 매번 다른 화면이 나와 사용자가 학습할 수 없고 ② 디자인 시스템 밖의 색·간격·컴포넌트가 섞이며 ③ 생성된 마크업의 접근성·보안을 사후에 검사할 방법이 없다. 반대로 과도하게 통제하면 "표를 보여 달라"에 텍스트만 돌아온다 |

## 문제와 맥락

채팅 인터페이스의 한계는 분명하다. 상품 10개를 비교하는 답을 텍스트로 읽고, 다시 텍스트로 "3번과 7번을 더 자세히"라고 쳐야 한다. UI는 이 왕복을 줄인다. 표를 띄우고 체크박스를 주면 한 번의 클릭으로 끝난다.

문제는 **누가 그 표를 결정하느냐**다. 세 가지 답이 있다.

- 개발자가 미리 만들어 둔 `ProductTable` 컴포넌트를 에이전트가 **선택**한다 (Controlled)
- 에이전트가 "열이 5개인 표, 첫 열은 이미지, 마지막 열은 버튼"이라고 **JSON으로 기술**하고 렌더러가 그린다 (Declarative)
- 에이전트가 HTML·CSS·JS를 **직접 생성**하고 브라우저가 실행한다 (Open-ended)

2026년 현재 이 세 패턴은 각각 대응하는 개방 프로토콜을 갖게 됐다. CopilotKit은 Controlled ↔ AG-UI, Declarative ↔ A2UI·Open-JSON-UI, Open-ended ↔ MCP Apps·커스텀으로 정리했다 `[2차]` — CopilotKit은 AG-UI 주도사이므로 이 프레이밍 자체가 중립적이지 않다는 점은 감안한다. 그럼에도 세 패턴의 구분은 프로토콜과 무관하게 설계 결정으로 유효하다.

## 핵심 개념

### 세 패턴의 정의

| 패턴 | 에이전트가 결정하는 것 | 에이전트가 결정하지 **않는** 것 | 전송 단위 | 대응 프로토콜 `[2차]` |
|---|---|---|---|---|
| **Controlled** | 어느 컴포넌트를, 어떤 props로 | 컴포넌트의 생김새·동작·접근성 구현 | 컴포넌트 이름 + props(JSON) | AG-UI 이벤트 + 자체 레지스트리 |
| **Declarative** | 컴포넌트 트리의 구조(어떤 컴포넌트를 어떻게 중첩·배치) | 각 컴포넌트의 구현(렌더러가 가짐) | 선언적 UI 트리(JSON) | A2UI, Open-JSON-UI |
| **Open-ended** | 마크업·스타일·스크립트 전부 | 샌드박스 경계만 호스트가 결정 | HTML(또는 코드) | MCP Apps, 커스텀 iframe |

Controlled와 Declarative의 경계는 "트리를 에이전트가 만드느냐"다. Controlled에서도 컴포넌트가 자식을 가질 수 있지만, 그 조합은 **개발자가 미리 허용한 것**이다. Declarative는 렌더러가 제공하는 컴포넌트 세트(A2UI의 "Basic" 세트 등 `[벤더]`) 안에서 에이전트가 **임의로 조합**한다.

### 자유도와 함께 움직이는 다섯 속성

| 속성 | Controlled | Declarative | Open-ended | 상쇄 수단 |
|---|---|---|---|---|
| **디자인 시스템 일관성** | 보장(컴포넌트가 곧 디자인 시스템) | 컴포넌트 단위는 보장, 배치·조합은 흔들림 | 보장 불가 | Declarative: 레이아웃 제약 규칙 / Open-ended: 없음(iframe 안이라 외부와 분리) |
| **접근성** | 컴포넌트에 구현된 만큼 | 컴포넌트는 되지만 트리 구조(헤딩 순서, 포커스 흐름)는 검증 필요 | 생성물마다 다름 | 트리 검증기, 자동 접근성 검사([09](09-ux-accessibility.md)) |
| **보안** | props 스키마 검증으로 충분 | 트리 스키마 + 데이터 바인딩 검증 | 코드 실행 → 샌드박스 필수 | [08](08-security-sandboxing.md) |
| **테스트 가능성** | 컴포넌트 단위 테스트 + "선택 정확도" | 트리 스냅샷 + 스키마 퍼징 | 거의 불가(생성물이 매번 다름) | [10](10-evaluation-genui.md) |
| **표현력** | 미리 만든 것만 | 세트 안의 조합 | 무제한 | — |

표의 핵심은 상쇄 수단의 **비용 기울기**다. Controlled의 상쇄는 "스키마 검증" 한 줄이고, Open-ended의 상쇄는 샌드박스 인프라와 정책이다.

### 혼합이 보통이다

실제 시스템은 한 패턴만 쓰지 않는다. 화면 영역이나 의도 유형별로 다른 통제 수준을 둔다.

- 커머스 상담: 상품 카드·비교표·장바구니 승인은 Controlled, "이 두 상품의 스펙을 내 기준으로 나란히"처럼 열 구성이 매번 다른 요청만 Declarative 표 컴포넌트 → [시나리오 B](../07-appendix-scenarios/02-commerce-assistant-genui.md)
- 운영 인시던트: 승인 카드·diff 뷰·진행 상태는 Controlled로 고정. 생성 자유도를 주지 않는다 → [시나리오 C](../07-appendix-scenarios/03-ops-incident-agent.md)
- 서드파티 툴의 위젯(지도, 결제, 외부 대시보드)은 그 영역만 Open-ended 샌드박스

혼합할 때 규칙은 하나다. **행동(action)으로 이어지는 UI는 Controlled로 고정한다.** 승인 버튼이 Declarative 트리 안에서 에이전트가 만든 것이면 [08](08-security-sandboxing.md)의 권한 재검증이 어려워진다.

```
에이전트 응답 (텍스트 + citations + ui_intent)
        │
        ▼
 통제 수준 결정 ───────────────────────────────────────────────┐
   ├─ Controlled ─▶ 의도→컴포넌트 선택 [05] ─▶ props 스키마 검증 [03] ─┤
   ├─ Declarative ─▶ 트리 생성 ─▶ 트리 스키마 + 제약 검증 [03·08] ──────┤
   └─ Open-ended ─▶ HTML 생성/수신 ─▶ 샌드박스 정책 적용 [08] ─────────┤
                                                                   ▼
                                     AG-UI 이벤트 스트림 [04] ─▶ 렌더러 [07] ─▶ 사용자 이벤트 ─▶ 서버 재검증 ─▶ 상태 머신(Part 3)
```

통제 수준은 런타임 분기가 아니라 **설계 시 결정**이다. 그러나 "이 의도는 Declarative 허용"처럼 의도 유형별로 다른 수준을 두면 위 분기가 런타임에도 나타난다. 그 경우 분기 조건은 [05](05-intent-to-ui-mapping.md)의 매핑 테이블에 적는다.

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| **Controlled** (사전 정의 컴포넌트 선택) | 디자인 시스템이 있고 지켜야 함, 행동(승인·실행)으로 이어지는 UI, 접근성·감사 요구, 컴포넌트 수십 개 이내로 과업이 덮임 | 사용자 요청마다 레이아웃이 달라져야 함, 컴포넌트를 미리 열거할 수 없는 탐색적 과업 | 하~중 — 컴포넌트 제작은 평소 프론트 작업, 추가 비용은 레지스트리·매핑 | 안정 (프레임워크 기본값) | `[2차]` 프레임워크 문서·CopilotKit 프레이밍 |
| **Declarative** (에이전트가 UI 트리 기술) | 컴포넌트 조합이 폭발적(대시보드, 임의 열 비교표), 웹·모바일 네이티브에 같은 UI, 프론트와 에이전트 팀이 분리 | 트리 검증 역량이 없음, 디자인 시스템이 엄격해 배치까지 통제해야 함, 행동 UI | 중~상 — 트리 스키마·제약 검증기·렌더러 유지 | 신생 (A2UI v0.9, 2026-04-17) | `[벤더]` A2UI 멀티플랫폼 주장 |
| **Open-ended** (HTML·코드 생성) | 서드파티 툴이 자기 UI를 가져옴, 일회성 시각화, 내부 도구로 신뢰 경계가 느슨 | 디자인 일관성·접근성이 요구됨, 생성 UI가 데이터 변경·결제 등 행동과 연결, 샌드박스 인프라 없음 | 상 — 샌드박스·CSP·postMessage 검증·정책 운영 | 신생 (MCP Apps 2026-01 발표, 2026-07 MCP 확장 편입) | `[2차]` |
| **텍스트 + citation만** (UI 결정 생략) | 사용자가 읽기만 함, 순수 QA | 선택·비교·입력·승인이 과업에 포함 | 하 | 표준 | — |

### 선택 가이드

- **디자인 시스템이 있고 사용자 행위가 선택·승인·입력이라면** → Controlled. 이유: 컴포넌트가 디자인 시스템이자 접근성 구현이자 보안 경계다. 추가 인프라 없이 운영 가능하다
- **열 구성·레이아웃이 요청마다 바뀌는 비교·대시보드 과업이고, 트리 검증기를 만들 여력이 있다면** → 그 의도 유형만 Declarative. 이유: Controlled로는 컴포넌트 수가 폭발한다. 단 v0.9 변경 위험 `[벤더]`을 어댑터 계층으로 격리
- **웹·Flutter·Android·iOS에 같은 에이전트 UI를 내야 한다면** → Declarative(A2UI) 검토. 이유: 선언적 데이터라 렌더러 교체가 가능하다는 주장 `[벤더]`. 네이티브 렌더러 성숙도는 `[실측]` 선행
- **서드파티 툴이 자기 위젯을 가져와야 한다면** → 그 영역만 Open-ended(MCP Apps). 이유: 툴 제공자가 UI를 유지하므로 호스트가 컴포넌트를 만들 필요가 없다. 대신 샌드박스 정책([08](08-security-sandboxing.md))이 필수
- **사용자가 읽기만 한다면** → 통제 수준 결정을 생략하고 citation 렌더([06](06-hitl-ui-patterns.md))만. 이유: UI 레이어 전체가 불필요한 복잡도
- **판단이 어려우면** → Controlled로 시작. 이유: 다른 두 패턴으로 넓히는 비용은 작고, 반대로 좁히는 비용(이미 생성된 UI에 의존하는 사용자·테스트)은 크다

## 설계 시 고려사항 (체크리스트)

- [ ] 사용자가 UI로 하는 행위(읽기 / 선택·비교 / 입력·수정 / 승인)를 열거했는가
- [ ] 과업을 덮는 데 필요한 컴포넌트 수를 세어 봤는가. 수십 개 이내인가
- [ ] 행동(툴 실행, 데이터 변경, 결제)으로 이어지는 UI는 Controlled로 고정했는가
- [ ] Declarative를 쓴다면 트리 스키마 검증 외에 **제약 검증**(필수 필드, 허용 조합, 깊이 제한)이 있는가
- [ ] Open-ended를 쓴다면 샌드박스 정책·CSP·postMessage 검증이 설계되어 있는가
- [ ] 패턴을 혼합한다면 어느 의도 유형이 어느 패턴인지 매핑 테이블에 명시했는가 ([05](05-intent-to-ui-mapping.md))
- [ ] 어떤 패턴이든 **텍스트 폴백**이 있는가 (렌더 실패, 스키마 불합격, 미지원 플랫폼)
- [ ] 통제 수준 결정과 그 근거를 문서로 남겼는가 (나중에 "왜 Declarative를 안 썼나"에 답하기 위해)
- [ ] 접근성 요구(법규·사내 기준)가 선택한 패턴에서 충족 가능한가 ([09](09-ux-accessibility.md))

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 3패턴 프레이밍이 AG-UI 주도사의 것 | Controlled ↔ AG-UI 대응이 과장되었을 수 있음. Declarative 트리도 AG-UI로 전송 가능 | 패턴은 설계 결정, 프로토콜은 전송 수단으로 분리해 생각. [02](02-protocols-ag-ui-a2ui-mcp-apps.md) |
| Controlled의 표현력 한계 | "표를 보여 달라"에 지원 컴포넌트가 없으면 텍스트로 후퇴 | 폴백률을 측정([10](10-evaluation-genui.md))해 자주 요구되는 컴포넌트를 추가 |
| Declarative의 트리 품질 | 스키마는 맞지만 헤딩 순서·포커스 흐름이 깨진 트리 | 접근성 트리 검증기, 레이아웃 제약 규칙 |
| Open-ended의 테스트 불가 | 회귀를 자동으로 잡을 수 없음 | 샌드박스 경계만 테스트. 생성물 자체는 사람 샘플링 |
| 패턴 간 이동 비용의 비대칭 | 넓히기는 쉽고 좁히기는 어려움 | 좁은 쪽(Controlled)에서 시작 |
| 성숙도 전반이 낮음 | 프로토콜·SDK가 반년 단위로 바뀜 | 어댑터 계층, 버전 고정. maturity를 "시험"으로 유지 |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 이 페이지의 결정(통제 수준)은 Part 4 나머지 페이지의 운영 비용을 결정한다 — 자유도가 한 단계 올라갈 때마다 아래 네 소절의 비용이 함께 오른다.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 의도 유형·컴포넌트 수 (Controlled) | 컴포넌트 수십 → 수백이 되면 선택 정확도와 툴 정의 컨텍스트 비용([03](03-component-registry-schema.md)) | 의도 그룹 계층화, variant 통합, 패턴 혼합 재검토(일부 의도만 Declarative) | 노출 컴포넌트 수 × 요청 수 |
| 트리 복잡도 (Declarative) | 트리 검증기 지연, 접근성 런타임 검증 실패율, 레이아웃 변형 폭발 | 깊이·노드 수 상한, 레이아웃 템플릿, 생성 결과 캐시 | 트리 노드 수 × 요청 수 |
| 서드파티 위젯 수 (Open-ended) | 샌드박스 정책 리뷰 큐, 출처(origin) 관리, iframe당 메모리 | 위젯 제공자 등록 절차, 동시 iframe 수 상한, 표시 전용 기본 | 위젯 제공자 수(사람 리뷰 비용) |
| 플랫폼 수 | 패턴별로 다르다 — Controlled는 컴포넌트 × 플랫폼 구현, Declarative는 렌더러 1개 추가 | 모바일 추가가 예정돼 있다면 그 의도 유형만 Declarative 검토 | Controlled: 컴포넌트 수 × 플랫폼 수 / Declarative: 플랫폼 수 |

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| Controlled 표현력 부족 | "표로 보여줘"에 텍스트만 | 폴백률(원인: 미지원 컴포넌트) 상승 | **텍스트 폴백** + 폴백 사실 고지([09](09-ux-accessibility.md)) | 특정 의도의 폴백률이 예시 20% 초과 2주 지속 → 컴포넌트 추가 또는 Declarative 검토 |
| Declarative 트리 검증 실패 폭증 | 비교표 대신 텍스트가 반복 | 트리 스키마·제약·접근성 검증 실패율 급등(보통 모델 교체 직후) | 텍스트 폴백, 실패율 임계 초과 시 해당 의도를 **Controlled 기본 컴포넌트로 저하** | 실패율 예시 10% 초과 → 모델·프롬프트 롤백 판단 |
| Open-ended 샌드박스 로드 실패 | 위젯 자리가 비거나 영원히 로딩 | iframe load 타임아웃, CSP 위반 리포트 | 타임아웃 후 iframe 제거 + 툴 결과를 **텍스트 요약으로 저하** | 특정 제공자 반복 실패 → 제공자 킬 스위치 |
| 패턴 경계 위반 | 승인 버튼이 에이전트 생성 트리 안에 등장 | 트리 검증기의 "행동 컴포넌트 금지" 규칙 위반 카운트 | 해당 트리 차단, 텍스트 + Controlled 승인 카드로 재구성 | 1건이라도 발생 시 매핑 테이블 리뷰(설계 결함) |
| 상쇄 수단 자체의 장애 (검증기·샌드박스 서비스 다운) | 모든 Declarative·Open-ended 영역이 텍스트 | 검증기 헬스체크 | fail-closed: 검증 못 하면 렌더하지 않음 → 텍스트 | 즉시 — 저하 상태 알림 |

SLI 후보: 패턴별 폴백률(원인별), 트리 검증 실패율, 샌드박스 로드 성공률, 패턴 경계 위반 건수. SLO 초안(예시): Controlled 폴백률 < 5%, Declarative 검증 실패율 < 3%, 경계 위반 0건. 이 페이지에는 쓰기 행동이 없다 — 행동은 항상 Controlled 승인 UI를 거쳐 [04](04-streaming-state-sync.md)·[06](06-hitl-ui-patterns.md)의 멱등성 규칙을 따른다.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| 통제 수준 결정 문서 (의도 유형 → 패턴) | 매핑 테이블([05](05-intent-to-ui-mapping.md)) 분기, 검증기 적용 범위, 보안 정책 범위 | 패턴별 골든셋(의도 → 기대 패턴·컴포넌트), 경계 위반 테스트 | 매핑 테이블 ↔ 검증기 설정 ↔ 샌드박스 정책 |
| 상쇄 수단 설정 (트리 깊이·노드 상한, 샌드박스 정책) | Declarative·Open-ended 영역의 통과율 | 제약 경계 사례(상한 ±1) | 렌더러 버전 |
| 패턴 ↔ 프로토콜 대응표 | 어댑터 선택([02](02-protocols-ag-ui-a2ui-mcp-apps.md)) | 프로토콜 어댑터 계약 테스트 | 어댑터 버전 |

기술 부채로 기록할 것: "Declarative는 비교표 하나만", "Open-ended는 표시 전용" 같은 **의도적 축소**와 그 재검토 조건(폴백률·사용자 요청 건수).

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **프로토콜** (A2UI v0.x 세트 개명, MCP Apps 스펙 변경) | 패턴 ↔ 프로토콜 대응 | 세 패턴의 정의와 "행동 UI는 Controlled" 원칙 | 전송·내용 어댑터 | 어댑터 교체, 버전 고정 + 계획된 업그레이드 창 | [02](02-protocols-ag-ui-a2ui-mcp-apps.md) 어댑터만. 패턴 결정은 불변 |
| **사용자 환경** (모바일 추가) | 플랫폼별 패턴 재평가 | 계약 ②(렌더 가능한 응답) | 렌더러 | Declarative 영역: 렌더러 추가 / Controlled 영역: 컴포넌트별 플랫폼 구현, 또는 그 의도만 Declarative로 이동 | 패턴 이동이 있으면 매핑 테이블·검증기·골든셋 |
| **사용자 환경** (디자인 시스템 개편) | 없음 — 패턴 수준에서는 영향 없음 | 패턴 정의 | 디자인 토큰([03](03-component-registry-schema.md)) | 토큰 교체 | Part 4 안에서 03·07로 한정 |
| **규칙·정책** (접근성 법규·조달 요건 신설) | 요건 영역의 허용 패턴 축소 | "요건 영역은 Controlled" 규칙 | 해당 의도의 패턴 배정 | 통제 수준 문서 개정 + 매핑 테이블의 패턴 열 변경 | 해당 의도 유형만 |
| **모델** (LLM 교체) | Declarative 트리 품질, 폴백률 분포 | 패턴 정의, 검증기 | 트리 생성 프롬프트 | 패턴별 골든셋 회귀, 실패율 급등 시 임시 Controlled 저하 | Declarative 영역 |
| **도메인 모델** (컴포넌트 추가·폐기) | 어느 패턴에 속하는지 배정 | 패턴 정의 | 카탈로그([03](03-component-registry-schema.md)) | 카탈로그 버전 상승, 폐기는 deprecated 기간 + 텍스트 폴백 | 카탈로그·매핑·골든셋 |

가장 자주 바뀌는 것: 프로토콜 버전(반년 단위) > 컴포넌트 추가 > 패턴 배정 자체(드묾). 코드 밖 설정으로 둘 것: 의도 유형 → 패턴 배정표, 트리 제약 상한, 샌드박스 정책. 포트·어댑터 뒤에 둘 외부 의존: AG-UI·A2UI·MCP Apps SDK 전부.

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성의 "탐지 신호"가 **실제로 어디서 나오는지**를 설계한다. 기준은 [Part 1/07 관측성 설계 요소](../01-foundations/07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md). 이 페이지의 관측 단위는 **패턴**이다 — 모든 Interaction 스팬에 `agent.pattern`(controlled / declarative / open_ended)을 붙여야 "어느 통제 수준이 비용을 내고 있는가"를 분해할 수 있다.

| 기록 대상 | 스팬 / 이벤트 (이름, 부모) | 핵심 속성 (버전 키 포함) | 지표 (→ 어느 SLI) | 샘플링 · 보존 · PII |
|---|---|---|---|---|
| 패턴 판정 | `ui.map` (부모 `invoke_agent`) | `agent.pattern`, `agent.intent_type`, `agent.component`, `agent.decision_source`, `agent.catalog_version`, `agent.fallback_reason`(`unsupported_component` 등) | 패턴별 요청 분포, 폴백률(원인별) → "Controlled 폴백률" SLI | 메타 전수 |
| 트리 검증 (Declarative) | `ui.validate` (부모 `ui.map`), `agent.validator=tree` | `agent.validation_result`, `agent.violation_code[]`(schema / constraint / a11y / **`action_component_in_tree`**), `agent.tree_hash`, 노드 수, 검증기 규칙 버전, `agent.model_version`·`agent.prompt_version` | 트리 검증 실패율(코드별) → "Declarative 검증 실패율"; 경계 위반 건수(=0) SLI | 메타 전수. 실패 트리 본문은 opt-in 저장소에 참조만 |
| 샌드박스 로드 (Open-ended) | 클라이언트 보고 `ui.render {iframe}` (부모 `ui.stream`, trace context 전파) | `agent.provider_id`, 위젯 출처, `agent.render_result`(ok / timeout / csp_blocked), 로드 ms, `agent.renderer_version`, `agent.platform` | 샌드박스 로드 성공률(제공자별) SLI | 실패 전수, 성공은 샘플(예시 10%) |
| CSP 위반 리포트 | 이벤트 `ui.csp_report` — 브라우저 `report-to`가 수집기로 직접 보내므로 **trace context가 없다**. 리포트 엔드포인트 경로에 `agent.provider_id`를 넣어 제공자·세션 해시로 조인 | 제공자, 위반 지시어, 차단 URI 해시, 정책 버전 | 제공자별 CSP 위반 건수 | 전수, URI는 해시 |
| 상쇄 수단 헬스 | 검증기·샌드박스 정책 서비스 헬스체크(요청 밖 지표) + 요청 쪽 `agent.fallback_reason=validator_unavailable` | 서비스명·버전 | 검증기 가용성, fail-closed 폴백 건수 | 전수 |
| 폴백 고지 표시 | 클라이언트 보고 `ui.render {notice}` | `agent.degradation_displayed`, 고지 토큰 키([09](09-ux-accessibility.md)) | 폴백 고지 표시율 → [10](10-evaluation-genui.md) 저하 플래그 표시율 | 전수 |

| 알림 | 조건 (예시) | 심각도 | 런북 (첫 3단계) |
|---|---|---|---|
| Controlled 표현력 부족 | 의도별 `unsupported_component` 폴백률 > 예시 20%가 2주 지속(주간 리뷰 알림) | P3 | ① 의도별 폴백 분포 확인 ② opt-in 본문 샘플 열람 ③ 컴포넌트 추가 vs 그 의도만 Declarative 전환을 안건화 |
| Declarative 검증 실패 폭증 | 실패율 > 예시 10%, 15분. 배포 마커 직후 민감도 상향 | P2 | ① `violation_code`별 분해 ② 모델·프롬프트 버전 변경 확인 ③ 해당 의도를 Controlled 기본 컴포넌트로 저하하는 플래그 → 롤백 판단 |
| Open-ended 로드 실패 | 제공자별 로드 성공률 < 예시 95% 10분, 또는 CSP 위반 기준선 3배 | P2 | ① 제공자·출처 분리 ② 위반 지시어 확인(정책 완화 금지) ③ 제공자 킬 스위치 |
| 패턴 경계 위반 | `action_component_in_tree` ≥ 1건 | **P1** | ① 해당 `request_id` 트레이스 열람 ② 매핑 테이블의 의도 행 확인 ③ 해당 의도의 Declarative 비활성 + 설계 결함 등록 |
| 상쇄 수단 다운 | 헬스체크 실패 또는 `validator_unavailable` 폴백 ≥ 1건/분 | **P1** | ① fail-closed 확인(Declarative·Open-ended 렌더 0건) ② 서비스 재시작·롤백 ③ 저하 배너 표시 확인 |

**대시보드에서 이 단계를 보는 뷰**: ① E2E의 폴백율을 패턴 × 원인으로 분해한 패널 / ② Interaction 패널의 "패턴별 검증 실패율·샌드박스 로드 성공률".
**감사 추적으로 넘기는 필드(관측 로그와 분리)**: 응답별 적용 패턴, 검증기 버전·결과, 폴백 원인 코드, Open-ended 제공자·출처 — 거버넌스 표와 같은 목록을 트레이스에서 추출해 별도 저장소에 둔다.
**이 단계의 관측이 없으면 못 보는 장애**: 패턴 경계 위반. 승인 버튼이 생성 트리 안에 들어가도 **렌더는 성공**하므로 사용자 불만도 오류도 없다 — `ui.validate`의 `violation_code` 없이는 영원히 모른다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | 패턴 결정 자체는 등급 1(렌더). 단 Open-ended를 여는 결정은 샌드박스 전제 아래서만 등급 1이고, 샌드박스 없는 Open-ended는 설계 금지. 행동 UI는 패턴과 무관하게 행동의 등급(3~5)을 상속 |
| 가드레일 위치 | **출력**: 패턴별 검증기(props 스키마 / 트리·제약 / 샌드박스 정책) — UI 트리 검증. **행동**: Controlled 승인 UI 뒤의 이벤트 재검증([04](04-streaming-state-sync.md)) |
| 게이트 출력과 판정 수단 | 통과(검증 합격) / 저하(텍스트 폴백) / 차단(경계 위반 트리). 판정은 규칙만 — 패턴 경계에 모델 판정을 쓰지 않는다 |
| 소유자 (A) | 통제 수준 결정: 디자인 책임자(일관성·접근성) + 보안 책임자(Open-ended 허용). R: 프론트엔드 |
| 감사 추적에 남길 필드 | 응답별 적용 패턴, 검증기 버전과 결과, 폴백 원인 코드, Open-ended 위젯의 제공자·출처 |

### 운영 준비도 체크
- [ ] 의도 유형 → 패턴 배정표가 코드 밖 설정으로 있고 버전이 있는가
- [ ] 패턴별 텍스트 폴백이 실제로 동작하며 폴백 사실이 사용자에게 보이는가
- [ ] 검증기·샌드박스 서비스가 죽었을 때 fail-closed(텍스트)로 떨어지는가
- [ ] "행동 UI는 생성 트리 안에 금지" 규칙이 검증기에 코드로 있는가
- [ ] 패턴별 폴백률·검증 실패율이 원인별로 집계되고 SLO가 선언돼 있는가
- [ ] Open-ended를 열었다면 제공자별 킬 스위치가 배포 없이 동작하는가
- [ ] 의도적으로 축소한 패턴 범위와 재검토 조건이 기술 부채로 기록돼 있는가
- [ ] `ui.validate`가 패턴 경계 위반을 `action_component_in_tree` 코드로 발행하고 1건에 P1 알림이 나가는가
- [ ] CSP 위반 리포트(trace context 없음)가 제공자 ID로 트레이스와 조인되는가
