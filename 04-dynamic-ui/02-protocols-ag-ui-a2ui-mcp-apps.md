# AG-UI · A2UI · MCP Apps 상세 비교

> **범위**: 이벤트 프로토콜 vs 선언적 UI 스펙 vs 샌드박스 앱, 조합 방법. **UI 설계 관점**에서 세 프로토콜이 어느 층을 맡고 어떻게 겹치고 어떻게 조합되는지. 다섯 프로토콜(MCP·A2A 포함)의 경계 구분은 [Part 1/05](../01-foundations/05-agentic-protocols.md)에서 끝났으므로 반복하지 않는다. 메시지 포맷의 필드 단위 설명과 SDK 사용법은 다루지 않는다.
> **시각화**: [`assets/html/dynamic-ui-architecture.html`](../assets/html/dynamic-ui-architecture.html) — "AG-UI 이벤트 스트림" 노드

## 요약 (3줄)

1. 셋은 경쟁자가 아니라 **층이 다르다**. AG-UI는 에이전트 백엔드와 프론트엔드 사이의 **이벤트 전송**, A2UI는 **UI의 내용**(선언적 트리), MCP Apps는 **툴 서버가 가져오는 UI**(샌드박스 iframe)다. 겹치는 부분은 "에이전트가 UI를 결정하느냐(AG-UI·A2UI) 툴 서버가 결정하느냐(MCP Apps)"뿐이다 `[2차]`.
2. 가장 흔한 조합은 **AG-UI 이벤트 스트림 위에 Controlled 컴포넌트 선택을 싣는 것**이고, Declarative가 필요하면 같은 스트림에 A2UI 트리를 실을 수 있다. MCP Apps는 서드파티 툴 영역에만 들어온다.
3. 셋 다 2026년에 버전·SDK가 빠르게 바뀌는 중이다(A2UI v0.9 2026-04-17 `[벤더]`, AG-UI .NET SDK 2026-09-25 `[2차]`, MCP Apps 2026-07-28 개정 편입 `[2차]`). 프로토콜 채택은 **어댑터 계층을 전제로** 한다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 프론트-백 전송층 선택(AG-UI / 프레임워크 내장 스트리밍 / 자체) ② UI 내용층 선택(자체 레지스트리 / A2UI) ③ 서드파티 UI 수용 여부(MCP Apps) ④ 세 결정 사이의 어댑터 설계 |
| **언제** (When) | [01](01-generative-ui-spectrum.md)에서 통제 수준이 정해진 직후. 프론트와 백을 같은 팀이 같은 풀스택 프레임워크로 만들고 서드파티 UI가 없다면 **프로토콜 없이** 프레임워크 내장 스트리밍으로 시작해도 된다 |
| **어떻게** (How) | ① 프론트·백이 다른 팀/다른 스택인가 → 그렇다면 AG-UI 검토 → ② 모바일 네이티브 렌더 또는 Declarative가 필요한가 → 그렇다면 A2UI 검토 → ③ 서드파티 툴이 자기 위젯을 가져오는가 → 그렇다면 MCP Apps 검토 → ④ 선택한 것들 사이의 매핑(A2UI 트리를 AG-UI 어느 이벤트에 싣나, MCP Apps iframe과 AG-UI 상태를 어떻게 잇나)을 정의 → ⑤ 버전 고정 + 어댑터 계층 |
| **왜** (Why) | 층을 혼동하면 "AG-UI vs A2UI 중 무엇을 쓸까" 같은 잘못된 질문에 시간을 쓴다. 반대로 프로토콜을 안 쓰고 자체 SSE 포맷을 만들면 프론트·백 양쪽이 커스텀 이벤트 스키마를 유지해야 하고, 백엔드 프레임워크를 바꾸는 순간 프론트가 깨진다 |

## 문제와 맥락

2025년까지 에이전트 프론트엔드는 각자 SSE 포맷을 정의했다. 토큰 델타는 어떻게 보내고, 툴 호출 중임은 어떻게 알리고, 에이전트 상태(장바구니, 진행률)는 어떻게 동기화하는지가 모두 커스텀이었다. 2026년에는 이 자리에 AG-UI가, "UI를 어떻게 기술하나"에 A2UI가, "툴이 자기 UI를 어떻게 가져오나"에 MCP Apps가 들어왔다. 세 개가 한꺼번에 등장했기 때문에 **경쟁 관계로 오해**되지만, 실제로는 서로 다른 질문에 대한 답이다 `[2차]`.

### 메시지 모델 — 개념 수준

**AG-UI: 이벤트 스트림.** 에이전트 실행(run) 하나가 시작부터 끝까지 이벤트의 시퀀스로 표현된다. 이벤트는 크게 네 범주다 `[2차]`.

| 범주 | 역할 | UI 설계에서의 의미 |
|---|---|---|
| 생명주기 | 실행 시작·종료·오류, 단계(step) 경계 | 로딩·완료·실패 상태([09](09-ux-accessibility.md))의 근거 |
| 텍스트 메시지 | 메시지 시작 → 델타(토큰 조각) → 종료 | 스트리밍 텍스트 렌더 |
| 툴 호출 | 호출 시작 → 인자 델타 → 종료 (→ 결과) | **Controlled 패턴의 핵심**: 툴 호출 = 컴포넌트 선택. 인자가 곧 props |
| 상태 | 전체 스냅샷 / 부분 패치 | 에이전트 상태(장바구니, 진행률, 선택 항목)와 UI 상태의 동기화([04](04-streaming-state-sync.md)) |

정확한 이벤트 이름과 필드는 스펙 버전에 따라 다르므로 이 위키는 범주만 적는다. 양방향이란 프론트→백 방향으로 사용자 입력·툴 결과·상태 변경을 돌려보낼 수 있다는 뜻이며, 이 역방향 채널이 [06](06-hitl-ui-patterns.md)의 승인·수정 이벤트가 흐르는 길이다.

**A2UI: 선언적 트리 + 컴포넌트 세트.** UI는 컴포넌트 노드의 트리이고, 각 노드는 타입(세트 안의 컴포넌트), 속성, 자식, 데이터 바인딩을 가진다. "실행 코드가 아니라 데이터"이므로 웹·Flutter·Android·iOS 렌더러가 같은 트리를 각자 네이티브 위젯으로 그릴 수 있다는 것이 핵심 주장이다 `[벤더]`. 컴포넌트 세트("Basic")가 표현력의 상한이고, 세트 밖 컴포넌트는 렌더러별 확장이 필요하다.

**MCP Apps: 서버 제공 UI.** MCP 서버가 툴 결과와 함께(또는 리소스로) HTML UI를 반환하고, 호스트가 그것을 샌드박스 iframe에 렌더한다. UI와 호스트는 메시지 채널(postMessage 류)로 통신한다 `[2차]`. 호스트 입장에서 UI는 **불투명한 외부 코드**이며, 설계의 전부가 샌드박스 정책([08](08-security-sandboxing.md))이다.

### 조합 방법

```
                       ┌────────────── AG-UI 이벤트 스트림 (전송층) ──────────────┐
 에이전트 백엔드 ──▶  텍스트 델타 │ 툴 호출(=Controlled 컴포넌트 선택) │ 상태 패치 │ 커스텀 이벤트(A2UI 트리 탑재)  ──▶ 프론트엔드
                       └──────────────────────────────────────────────────────┘
                                                                                      │
 MCP 툴 서버 ──(MCP Apps: HTML UI)──▶ 호스트가 샌드박스 iframe 렌더 ◀── 위 스트림과는 별도 채널(postMessage) ──┘
```

- **Controlled on AG-UI** (기본): 툴 호출 이벤트의 툴 이름 = 컴포넌트 이름, 인자 = props. 프론트는 레지스트리([03](03-component-registry-schema.md))에서 컴포넌트를 찾아 렌더. 가장 단순하고 프레임워크 지원이 두텁다
- **A2UI on AG-UI**: Declarative가 필요한 의도 유형에서 A2UI 트리를 AG-UI의 커스텀(또는 상태) 이벤트 페이로드로 전송. 전송·동기화는 AG-UI가, 내용은 A2UI가 맡는다. 실제로 가능하다는 서술은 있으나 `[2차]` 표준화된 매핑은 아니므로 **자체 어댑터**가 필요하다
- **MCP Apps 병행**: 서드파티 툴 결과 중 UI가 딸린 것은 AG-UI 스트림을 거치지 않고 호스트가 직접 iframe 렌더. iframe 안의 사용자 행위가 에이전트 상태에 반영되어야 하면 호스트가 postMessage → AG-UI 역방향 이벤트로 변환하는 **브리지**가 필요하다. 이 브리지가 가장 설계 난도가 높다

### 프레임워크 스트리밍과의 비교

Vercel AI SDK 류 풀스택 프레임워크는 "툴 호출 → React 컴포넌트"를 프레임워크 내부 규약으로 스트리밍한다. 서버 컴포넌트(RSC) 스트리밍으로 UI 조각 자체를 보내는 방식도 제공한다. 이것은 **프로토콜이 아니라 프레임워크 규약**이다.

| 비교 축 | 프레임워크 내장 스트리밍 | AG-UI |
|---|---|---|
| 프론트·백 결합 | 같은 프레임워크(주로 같은 언어·저장소) | 분리 가능. 백엔드가 Python·.NET·Java여도 됨 |
| 백엔드 교체 | 프론트도 함께 바뀜 | 이벤트 스키마만 지키면 교체 가능 |
| 개발 속도 | 빠름(통합이 끝나 있음) | 어댑터·이벤트 매핑 작업 추가 |
| 상태 동기화 | 프레임워크가 제공하는 범위 | 스냅샷·패치 이벤트로 명시적 |
| 성숙도 | 안정 | 신생→확산 |

프론트와 백을 **같은 팀이 같은 스택**으로 만든다면 내장 스트리밍이 낫다. 분리되어 있거나 백엔드 프레임워크가 여럿이면 AG-UI가 낫다. 둘을 섞는 것(내장 스트리밍 위에 AG-UI 이벤트를 흉내 내기)은 두 규약을 다 유지해야 하므로 피한다.

### 자체 프로토콜을 만들어야 하는 경우

- 전송이 SSE/HTTP가 아니다(네이티브 소켓, 메시지 큐, 임베디드)
- 이벤트에 **도메인 고유 의미**가 많아 AG-UI 커스텀 이벤트로 감싸는 것이 오히려 불투명해진다
- 규제상 프로토콜 라이브러리의 의존성 심사를 통과하기 어렵다

이 경우에도 AG-UI의 **범주 구조**(생명주기 / 텍스트 / 툴 호출 / 상태)는 빌려 쓴다. 나중에 전환할 때 매핑이 쉬워진다.

## 아키텍처 / 파이프라인

입력은 [01](01-generative-ui-spectrum.md)의 통제 수준 결정과 플랫폼 요구(웹 / 모바일 / 임베딩)이고, 출력은 **전송층 + 내용층 + 서드파티 UI 수용 여부**의 3개 결정과 그 사이의 어댑터 정의다. 다음 단계인 [03](03-component-registry-schema.md)은 내용층 결정(자체 레지스트리 또는 A2UI 세트)을 받아 카탈로그를 설계하고, [04](04-streaming-state-sync.md)는 전송층 결정을 받아 상태 동기화를 설계한다.

| 자체 프로토콜 | 비HTTP 전송, 도메인 고유 이벤트가 지배적, 의존성 심사 제약 | 그 외 전부 — 유지 비용이 가치를 넘음 | 상 — 양쪽 스키마·문서·테스트를 직접 유지 | 해당 없음 | — |

### 선택 가이드

- **프론트와 백을 다른 팀이 만들거나 백엔드 프레임워크가 둘 이상이라면** → AG-UI. 이유: 이벤트 스키마 합의 비용이 가장 작고 MS·AWS 지원으로 생태계가 넓어지는 중. 단 스타트업 거버넌스 위험은 MIT 포크 가능성으로 완화
- **웹과 모바일 네이티브에 같은 에이전트 UI를 그려야 한다면** → A2UI를 내용층으로, 전송은 AG-UI 또는 자체. 이유: 선언적 데이터라 렌더러 교체 가능 `[벤더]`. 네이티브 렌더러 품질은 `[실측]` 전까지 믿지 않는다
- **서드파티 MCP 툴의 위젯을 그대로 보여 줘야 한다면** → 그 영역만 MCP Apps. 이유: 위젯 유지 책임이 툴 제공자에게 간다. 대신 샌드박스 정책을 먼저 쓴다
- **풀스택 단일 팀이고 웹만 대상이라면** → 프레임워크 내장 스트리밍. 이유: 프로토콜의 추상화 비용을 낼 이유가 없다. 이벤트 범주 구조만 AG-UI와 맞춰 두면 전환이 쉽다
- **판단이 어려우면** → 프레임워크 내장 스트리밍으로 시작하되 Controlled 컴포넌트 선택을 "툴 호출 = 컴포넌트"로 설계. 이유: 이 구조는 AG-UI로 그대로 옮겨진다

## 설계 시 고려사항 (체크리스트)

- [ ] 전송층·내용층·서드파티 UI 수용 여부를 **따로** 결정했는가 (하나의 "프로토콜 선택"으로 뭉뚱그리지 않았는가)
- [ ] AG-UI를 쓴다면 SDK 버전을 고정하고, 이벤트 범주별 어댑터가 프론트·백 양쪽에 있는가
- [ ] A2UI를 쓴다면 "Basic" 세트로 과업이 덮이는지 확인했는가. 세트 밖 컴포넌트가 필요하면 렌더러별 확장 비용을 추정했는가
- [ ] A2UI 트리를 AG-UI에 실을 때 어느 이벤트 유형에 싣는지, 트리 검증은 어디서 하는지 정했는가
- [ ] MCP Apps를 쓴다면 iframe 안의 사용자 행위를 에이전트 상태로 되돌리는 브리지가 필요한지, 필요하다면 [08](08-security-sandboxing.md)의 검증을 거치는지 확인했는가
- [ ] 프로토콜이 정의하지 않는 것(인증, 레이트 리밋, 멀티테넌시, 재연결 정책)의 책임자를 정했는가
- [ ] 프로토콜을 쓰지 않기로 한 경계는 그 이유와 전환 조건을 기록했는가
- [ ] 세 프로토콜의 변경 로그를 추적하는 담당이 있는가 (2026년 내 반년 단위 변경)

| A2UI-on-AG-UI 매핑 비표준 | 팀마다 다른 어댑터, 재사용 불가 | 어댑터를 한 곳에서 유지, 스펙 진전 시 교체 |
| MCP Apps 브리지의 복잡도 | iframe 사용자 행위와 에이전트 상태가 어긋남 | 브리지 없이 "표시 전용"으로 시작, 필요한 행위만 화이트리스트 |
| 프로토콜이 보안을 정의하지 않음 | 이벤트·UI가 새로운 공격면 | [08](08-security-sandboxing.md), [Part 5/01](../05-cross-cutting/01-security-prompt-injection.md) |
| 3자 구도 프레이밍의 출처 편향 | CopilotKit(AG-UI 주도사)의 정리를 그대로 수용할 위험 | 층 구분은 수용하되 "Controlled = AG-UI" 등식은 전송층/내용층 분리로 교정 |
