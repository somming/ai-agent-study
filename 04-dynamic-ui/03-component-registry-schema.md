# 컴포넌트 레지스트리와 스키마

> **범위**: 컴포넌트 카탈로그, JSON Schema, 타입 안전성, 디자인 시스템 연결. 에이전트가 고를 수 있는 컴포넌트의 목록과 각 컴포넌트의 계약을 어떻게 정의·생성·버전 관리하고 에이전트에게 노출하는지. 이 페이지가 정의하는 "렌더 가능한 응답 스키마"는 레이어 간 **계약 ②**([Part 0/01](../00-overview/01-reference-architecture.md))다. 어느 컴포넌트를 고를지의 판정은 [05](05-intent-to-ui-mapping.md), 컴포넌트 구현은 [07](07-frontend-integration.md).
> **시각화**: [`assets/html/dynamic-ui-architecture.html`](../assets/html/dynamic-ui-architecture.html) — "컴포넌트 레지스트리 조회"·"스키마·제약 검증" 노드

## 요약 (3줄)

1. 컴포넌트 레지스트리(component registry)는 **에이전트가 알아도 되는 UI의 전부**다. 이름, 목적, props 스키마, 허용 조합, 데이터 바인딩을 기계가 읽을 수 있게 적은 카탈로그이며, 프론트엔드·에이전트·평가가 같은 파일을 참조한다.
2. 스키마는 한 곳(JSON Schema 또는 zod/pydantic 류 코드)에서 정의하고 나머지(타입, 툴 정의, 검증기, 문서)는 **생성**한다. 손으로 두 벌을 유지하면 반드시 어긋난다.
3. 카탈로그는 작을수록 선택 정확도가 높다. 컴포넌트가 수십 개를 넘으면 계층화(의도 그룹 → 컴포넌트)하거나 결정 모델·규칙으로 선택지를 좁힌 뒤 LLM에 넘긴다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 컴포넌트 카탈로그 파일(이름·목적·props 스키마·허용 조합·바인딩·버전) ② 거기서 생성된 타입·툴 정의·검증기 ③ 렌더 가능한 응답 스키마(계약 ②) ④ 디자인 토큰 매핑 ⑤ 버전·하위 호환 정책 |
| **언제** (When) | Controlled·Declarative 패턴을 택한 즉시. 텍스트 + citation만 쓰는 시스템은 citation 컴포넌트 하나짜리 카탈로그로 충분하므로 이 페이지의 대부분을 생략한다. Open-ended 영역은 카탈로그 밖이다 |
| **어떻게** (How) | ① [01](01-generative-ui-spectrum.md)에서 열거한 사용자 행위별로 필요한 컴포넌트를 목록화 → ② 각 컴포넌트에 목적 한 줄과 props 스키마 작성 → ③ 허용 조합(어느 컴포넌트가 어느 컴포넌트 안에 들어갈 수 있나)과 데이터 바인딩(props가 Part 2/3의 어느 스키마를 참조하나) 명시 → ④ 스키마에서 타입·툴 정의·검증기 생성 → ⑤ 디자인 토큰 연결 → ⑥ 버전 부여, 변경 절차 문서화 → ⑦ 에이전트 노출 방식 결정 |
| **왜** (Why) | 카탈로그 없이 "에이전트가 적당히 컴포넌트를 고르게" 하면 ① 프론트에 없는 컴포넌트를 호출하고 ② props 이름이 매번 달라 렌더가 깨지며 ③ 어떤 컴포넌트가 얼마나 쓰이는지 측정할 수 없다. 카탈로그는 에이전트와 프론트 사이의 **유일한 공유 어휘**다 |

## 문제와 맥락

Controlled 패턴에서 에이전트는 "컴포넌트 X를 props Y로"라고 말한다. 이 문장이 성립하려면 X의 목록과 Y의 형태가 **에이전트와 프론트 양쪽에 같은 내용으로** 존재해야 한다. 흔한 실패는 프론트 개발자가 React 컴포넌트를 바꾸고 프롬프트의 컴포넌트 설명은 안 바꾸는 것, 또는 그 반대다. 레지스트리는 이 두 세계를 한 파일로 묶는다.

Declarative 패턴에서도 레지스트리는 필요하다. A2UI의 컴포넌트 세트("Basic" `[벤더]`)가 사실상 레지스트리이고, 세트 밖 컴포넌트를 추가하면 그 정의가 레지스트리다. 차이는 Controlled가 "컴포넌트 + props"를 단위로 하고 Declarative가 "트리"를 단위로 하므로 **허용 조합 규칙**이 훨씬 중요해진다는 점이다.

## 핵심 개념

### 카탈로그 항목의 구성

| 필드 | 내용 | 누가 쓰나 |
|---|---|---|
| `name` | 고유 식별자. 툴 이름과 동일하게 | 에이전트(선택), 프론트(조회), 평가(골든셋 라벨) |
| `purpose` | 언제 쓰는 컴포넌트인지 한두 문장. **"언제 쓰지 말라"** 도 적는다 | 에이전트(선택 근거), 결정 모델 질문 정의 |
| `props` | JSON Schema. 필수/선택, enum, 범위, 최대 길이 | 검증기, 타입 생성, 툴 정의 |
| `slots` / 허용 자식 | 어느 컴포넌트를 자식으로 둘 수 있나, 최대 개수·깊이 | 트리 검증기(Declarative) |
| `bindings` | props가 참조하는 외부 스키마(예: `items[]`는 상품 레코드, `citations[]`는 Part 2/08 근거 단위) | 데이터 정합성 검증 |
| `actions` | 컴포넌트가 발생시키는 사용자 이벤트와 그 스키마(계약 ③, [04](04-streaming-state-sync.md)) | 상태 머신(Part 3) |
| `tokens` | 사용하는 디자인 토큰 그룹(색·간격·타이포). 에이전트가 넘길 수 없는 값임을 명시 | 디자인 시스템 |
| `a11y` | 접근성 역할·키보드 동작 요약, 필수 라벨 props | [09](09-ux-accessibility.md) 검증 |
| `version` | 시맨틱 버전. 하위 호환 깨지는 변경은 메이저 | 호환성 검사 |
| `examples` | 올바른 호출 예 2~3개, 잘못된 예 1개 | 프롬프트·few-shot, 테스트 |

### 렌더 가능한 응답 스키마 (계약 ②)

Part 3의 생성 단계가 Part 4로 넘기는 응답의 형태. 최소 구성은 다음과 같다.

```json
{
  "text": "요약 텍스트 (항상 존재 — 폴백)",
  "citations": [ { "...": "Part 2/08 근거 단위 스키마를 그대로 참조" } ],
  "ui_intent": {
    "intent": "compare_products",
    "component": "ProductComparisonTable",
    "props": { "items": ["..."], "columns": ["price", "rating"] },
    "confidence": 0.82,
    "requires_approval": false,
    "fallback": "text"
  },
  "catalog_version": "2.3.0"
}
```

- `text`는 **항상** 있다. UI가 실패하면 이것이 보인다
- `ui_intent`는 선택적이다. 없으면 텍스트 + citation 렌더
- `component`와 `props`는 카탈로그 스키마로 검증된다. 불합격이면 `fallback`
- `confidence`는 선택 수단이 결정 모델이면 보정 확률, LLM이면 없음(또는 비보정 표시). [05](05-intent-to-ui-mapping.md)
- `catalog_version`은 프론트가 자기 레지스트리 버전과 비교해 호환성을 판단하는 근거

Declarative에서는 `component`+`props` 자리에 `tree`가 오고, 트리 노드 각각이 카탈로그 항목을 참조한다.

### 단일 소스에서 생성

```
카탈로그 정의 (JSON Schema 또는 zod / pydantic 류 코드)
   ├─▶ 프론트 타입 (TypeScript 인터페이스)         — 컴포넌트 props 타입
   ├─▶ 백엔드 타입 (pydantic 모델 등)               — 응답 스키마 검증
   ├─▶ 툴 정의 (LLM 함수 호출 스키마)               — 에이전트 노출 방식 A
   ├─▶ 결정 모델 질문의 선택지 enum                 — 에이전트 노출 방식 C
   ├─▶ 런타임 검증기 (스키마 + 허용 조합 규칙)
   └─▶ 문서 (사람이 읽는 카탈로그 페이지)
```

zod·pydantic 류 라이브러리는 코드로 스키마를 적고 JSON Schema를 내보내는 방향, JSON Schema를 원본으로 두고 코드를 생성하는 방향 둘 다 가능하다. 어느 쪽이든 **원본은 하나**다. 원본을 프론트 쪽에 두면 컴포넌트 변경이 자동으로 반영되고, 공유 패키지에 두면 양쪽이 대칭이다. 프론트와 백이 다른 언어이면 JSON Schema를 원본으로 두는 편이 생성 도구 선택이 자유롭다.

### 디자인 시스템 토큰 연결

에이전트는 **색·간격·폰트를 넘기지 않는다.** 컴포넌트가 디자인 토큰(design token)을 참조하고, 에이전트는 의미적 변형(variant)만 고른다 — `tone: "warning"`은 되고 `color: "#ff0000"`은 안 된다. props 스키마에서 시각 속성은 enum으로 닫는다. Declarative 트리에서도 레이아웃 속성(여백·정렬)은 토큰 이름의 enum이어야 한다. 이것이 자유도가 올라가도 디자인 시스템이 유지되는 유일한 장치다.

### 버전 관리와 하위 호환

| 변경 유형 | 버전 | 호환 전략 |
|---|---|---|
| 선택 props 추가, 새 컴포넌트 추가 | 마이너 | 구 프론트는 모르는 컴포넌트를 텍스트 폴백 |
| 필수 props 추가, props 이름 변경, 컴포넌트 제거 | 메이저 | 구 버전 호출을 변환하는 어댑터 또는 양 버전 병행 기간 |
| 디자인 토큰만 변경 | 패치 | 카탈로그 무관(토큰은 에이전트가 모름) |

프론트와 백엔드가 **다른 시점에 배포**되므로 응답의 `catalog_version`과 프론트 레지스트리 버전이 다를 수 있다. 메이저가 다르면 텍스트 폴백, 마이너가 다르면 모르는 컴포넌트만 폴백이 기본 규칙이다. 프롬프트·결정 모델 질문·골든셋도 카탈로그 버전에 묶어 두어야 [10](10-evaluation-genui.md)의 회귀 비교가 성립한다.

### 에이전트에게 카탈로그를 노출하는 방식

| 방식 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **A. 툴 정의** | 컴포넌트마다 함수 호출 툴 하나. 인자 = props | 프레임워크 기본 지원, 인자 스키마 검증이 모델 측에서도 일어남 | 툴 수가 늘면 선택 정확도·토큰 비용 저하 |
| **B. 프롬프트 카탈로그** | 시스템 프롬프트에 목록·설명을 넣고 구조화 출력으로 선택 | 툴 수 제한에 영향 없음, 설명을 풍부하게 | 매 요청 토큰 비용, 모델이 목록을 무시할 위험 |
| **C. 결정 모델 선택지** | 컴포넌트 이름을 결정 모델 질문의 enum으로. props는 이후 LLM 또는 규칙이 채움 | 생성 없이 판정, 보정 확률 `[벤더]`, 저지연 주장 `[벤더]` | 2단계 구성(선택 → props 채우기), 한국어 `[실측]` 필수 |
| **D. 계층화** | 의도 그룹을 먼저 고르고(규칙·결정 모델), 그룹 안의 컴포넌트만 툴로 노출 | 큰 카탈로그에서 선택지를 줄임 | 그룹 경계 설계 필요 |

### 카탈로그 크기와 선택 정확도

선택지가 늘수록 LLM의 툴 선택 정확도는 떨어진다는 것이 실무 관찰이다 `[2차]`. 정확한 임계값은 모델·도메인마다 다르므로 수치는 `[실측]`으로만 적는다. 설계 지침은 다음과 같다.

- 한 번에 노출하는 선택지는 **수십 개 이내**로. 그 이상이면 D(계층화)
- 비슷한 컴포넌트(`ProductCard` vs `ProductCardCompact`)는 하나로 합치고 variant로
- `purpose`에 "쓰지 말아야 할 때"를 적으면 혼동 쌍(confusion pair)이 줄어든다
- 혼동 쌍은 [10](10-evaluation-genui.md)의 혼동 행렬로 찾아 카탈로그에 피드백

## 아키텍처 / 파이프라인

입력은 [01](01-generative-ui-spectrum.md)의 사용자 행위 목록과 [02](02-protocols-ag-ui-a2ui-mcp-apps.md)의 내용층 결정(자체 레지스트리 / A2UI 세트)이다. 출력은 카탈로그 파일, 생성된 타입·툴 정의·검증기, 계약 ② 스키마다. [05](05-intent-to-ui-mapping.md)는 카탈로그를 선택지로 쓰고, [04](04-streaming-state-sync.md)는 `actions` 정의를 사용자 이벤트 스키마로 이어받으며, [10](10-evaluation-genui.md)은 `name`을 골든셋 라벨로 쓴다.

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| JSON Schema 원본 + 코드 생성 | 프론트·백이 다른 언어, 스키마를 여러 소비자(툴 정의·검증기·문서)가 공유 | 단일 언어 소규모 팀(코드 원본이 더 빠름) | 중 — 생성 파이프라인 유지 | 표준 | `[검증]` JSON Schema 표준 문서 |
| zod / pydantic 류 코드 원본 → JSON Schema 내보내기 | 단일 언어 또는 TS/Python 한쪽이 주도, 타입과 런타임 검증을 한 번에 | 다언어 대칭이 필요하고 내보낸 스키마의 미세 차이가 문제되는 경우 | 하~중 | 안정 | — 라이브러리 문서 |
| A2UI "Basic" 세트를 레지스트리로 채택 | Declarative + 멀티플랫폼, 세트로 과업이 덮임 | 디자인 시스템 고유 컴포넌트가 많음, Controlled만 필요 | 중 — 세트 밖 확장 시 렌더러별 작업 | 신생 (v0.9) | `[벤더]` |
| 디자인 시스템 패키지에 카탈로그 내장 | 디자인 시스템 팀이 있고 컴포넌트 변경과 카탈로그 변경을 묶고 싶음 | 디자인 시스템이 없거나 외부 라이브러리 그대로 사용 | 중 | 안정 (조직 관행) | — |
| 프롬프트에 자유 텍스트 카탈로그 (스키마 없음) | 프로토타입, 컴포넌트 3~5개 | 운영 — 검증·버전·측정 불가 | 하 | 해당 없음 | — |

### 선택 가이드

- **프론트(TS)와 백(Python 등)이 다른 언어라면** → JSON Schema 원본 + 양쪽 생성. 이유: 어느 한쪽 라이브러리의 방언에 묶이지 않는다
- **단일 언어(예: TS 풀스택)라면** → zod 류 코드 원본, JSON Schema는 내보내기. 이유: 타입·검증·툴 정의가 한 줄로 이어진다
- **Declarative + 모바일이라면** → A2UI 세트를 기본 레지스트리로 하고 고유 컴포넌트만 확장. 이유: 렌더러를 직접 만들지 않는다. 단 세트 변경(v0.9 개명 등 `[벤더]`) 추적 필요
- **디자인 시스템 팀이 있다면** → 카탈로그를 디자인 시스템 패키지 안에. 이유: 컴포넌트와 카탈로그가 같은 PR에서 바뀐다
- **판단이 어려우면** → JSON Schema 파일 하나를 저장소 루트의 공유 위치에 두고 시작. 이유: 가장 중립적이고, 어느 방향으로도 생성 도구를 붙일 수 있다

## 설계 시 고려사항 (체크리스트)

- [ ] 카탈로그 항목마다 `purpose`에 "쓰지 말아야 할 때"가 있는가
- [ ] 시각 속성(색·간격·폰트)이 props에서 enum(토큰 이름)으로 닫혀 있는가. 자유 문자열 색상 값이 없는가
- [ ] `bindings`가 Part 2/08 근거 단위, Part 3 응답 스키마 등 **실제 스키마 파일**을 참조하는가
- [ ] 허용 조합(자식·깊이·개수)이 Declarative 트리 검증기에 반영되는가
- [ ] 타입·툴 정의·검증기·문서가 모두 **한 원본에서 생성**되는가. 손으로 유지하는 사본이 없는가
- [ ] `catalog_version`이 응답에 실리고, 프론트가 메이저·마이너 불일치를 각각 처리하는가
- [ ] 프롬프트·결정 모델 질문·골든셋이 카탈로그 버전에 묶여 있는가
- [ ] 한 번에 노출하는 선택지가 수십 개 이내인가. 넘으면 계층화했는가
- [ ] 각 컴포넌트의 `actions`(사용자 이벤트)가 [04](04-streaming-state-sync.md)의 이벤트 스키마와 일치하는가
- [ ] `a11y` 필수 라벨 props가 스키마에서 필수로 표시되는가

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 카탈로그와 구현의 드리프트 | 존재하지 않는 컴포넌트·props 호출로 렌더 실패 | 단일 원본 생성, CI에서 카탈로그 ↔ 컴포넌트 export 대조 |
| 큰 카탈로그의 선택 정확도 저하 | 잘못된 컴포넌트, 폴백 증가 | 계층화, variant 통합, 혼동 쌍 분석 |
| 스키마 통과 ≠ 의미적으로 올바른 UI | 비교표에 항목 1개, 빈 차트 | 제약 검증(최소 항목 수 등)을 스키마 밖 규칙으로 추가 |
| 버전 불일치 (프론트·백 배포 시점 차이) | 신 컴포넌트가 구 프론트에서 깨짐 | 메이저 폴백·마이너 부분 폴백 규칙, 병행 기간 |
| A2UI 세트 의존 | 세트 개명·변경에 끌려감 (v0.9에서 "Standard"→"Basic" `[벤더]`) | 어댑터 계층, 세트 버전 고정 |
| 결정 모델 enum 노출의 한국어 품질 | 영어 중심 학습으로 한국어 의도에서 선택 품질 저하 가능 | 한국어 골든셋 `[실측]` 선행, 불합격 시 툴 정의 방식 |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 카탈로그는 1/07이 말하는 **"코드가 아닌 데이터"** 의 Part 4 대표 사례다 — 바뀌는 것(컴포넌트 목록·props)을 설정으로 빼고, 바뀌지 않는 것(계약 ② 봉투)을 코드로 둔다.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 컴포넌트 수 (수십 → 수백) | 노출 방식 A(툴 정의)의 선택 정확도·요청당 컨텍스트 토큰, 번들 크기([07](07-frontend-integration.md)), 카탈로그 ↔ 구현 대조 CI 시간 | 방식 D 계층화(의도 그룹 → 그룹 내 툴만 노출), variant 통합, 지연 로딩 | 노출 컴포넌트 수 × 요청 수(토큰), 전체 컴포넌트 수(CI·번들) |
| props 스키마 크기 | 툴 정의 토큰, 검증 지연 | 깊은 중첩 대신 `bindings`로 외부 스키마 참조 | 스키마 바이트 × 요청 수 |
| 플랫폼 수 | 렌더러별 지원 매트릭스 행 수, 미지원 컴포넌트의 폴백 분기 | 카탈로그에 `platforms` 필드, 매핑 규칙에서 미리 제외 | 컴포넌트 수 × 플랫폼 수 |
| 테넌트별 디자인 시스템 | 토큰 세트 수. 카탈로그를 테넌트별로 복제하면 스키마 드리프트 | **카탈로그 스키마는 하나**, 토큰 세트만 테넌트별. 에이전트는 토큰을 모르므로 영향 없음 | 테넌트 수(토큰 세트만) |
| 카탈로그 소비자 수 (프론트·백·평가·문서) | 생성 파이프라인 실패 시 소비자 간 불일치 | 단일 원본 + 생성물 커밋 금지(빌드 시 생성) | 소비자 수(파이프라인 유지) |

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 스키마 검증 실패 폭증 (모델 교체·프롬프트 변경 직후) | UI가 떠야 할 응답에 텍스트만 | 스키마 검증 실패율 급등(컴포넌트별) | **텍스트 폴백**(`text`는 항상 있음), 실패율 임계 초과 시 해당 컴포넌트의 노출을 일시 중단(피처 플래그) | 예시 5% 초과 15분 지속 → 모델·프롬프트 롤백 판단 |
| 카탈로그 ↔ 구현 드리프트 | 존재하지 않는 컴포넌트 호출 → 렌더 실패 | 카탈로그 대조 실패 카운트(운영), CI 대조 실패(배포 전) | 모르는 `name` → 텍스트 폴백, 예외 금지 | CI에서 잡혀야 정상. 운영에서 발생하면 배포 절차 결함 |
| 버전 불일치 (프론트·백 배포 시점 차이) | 신 컴포넌트가 구 프론트에서 텍스트로 | `catalog_version` 메이저·마이너 불일치 카운트 | 메이저 불일치 → 전체 텍스트 폴백 / 마이너 → 모르는 컴포넌트만 폴백 | 불일치가 배포 창(예시 30분)을 넘어 지속 → 배포 순서 점검 |
| 생성 파이프라인 실패 (타입·툴 정의 생성 중단) | — (배포 차단) | CI 실패 | 배포 차단(fail-closed) | 즉시 |
| 디자인 토큰 세트 로드 실패 | 스타일 없는 컴포넌트 | 토큰 로드 오류 | 기본 토큰 세트로 저하 | 테넌트별 토큰 문제 → 디자인 시스템 팀 |
| 의미적으로 빈 UI (스키마 통과, 항목 0~1개) | 빈 표·빈 차트 | 제약 검증(최소 항목 수) 실패 카운트 | 제약 실패 → 폴백 체인([05](05-intent-to-ui-mapping.md)) | 반복 시 매핑 조건 보강 |

SLI 후보: 스키마 검증 실패율(컴포넌트별), 카탈로그 대조 실패 건수, 버전 불일치 비율, 제약 검증 실패율. SLO 초안(예시): 스키마 실패율 < 2%, 운영 중 카탈로그 대조 실패 0건, 메이저 불일치 지속 시간 < 배포 창. 쓰기 행동 없음 — `actions`는 정의만 하고 실행은 [04](04-streaming-state-sync.md)·[06](06-hitl-ui-patterns.md).

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| 카탈로그 (컴포넌트 목록·props 스키마·허용 조합) | 툴 정의, 결정 모델 enum, 검증기, 매핑 테이블, 골든셋, 렌더러 바인딩 | 스키마 호환 테스트(구 버전 응답이 신 검증기 통과), 선택 정확도 골든셋, 컴포넌트 렌더 스냅샷 | **카탈로그 ↔ 응답 스키마(계약 ②) ↔ 렌더러 바인딩** — 롤백 단위 |
| 계약 ② 봉투 (`text`·`citations`·`ui_intent`·`catalog_version`) | Part 3 생성 단계, Part 4 전체 | 계약 테스트(Part 3·4 양쪽) | Part 3 응답 생성기 ↔ Part 4 어댑터 |
| 디자인 토큰 세트 | 시각만. 카탈로그 무관 | 시각 회귀(스크린샷) | 렌더러만 |
| `bindings` 참조 스키마 (Part 2/08 근거 단위 등) | citation 컴포넌트 props | 참조 스키마 버전 호환 테스트 | Part 2/08 스키마 버전 |
| 렌더러별 지원 매트릭스 | 매핑 규칙의 플랫폼 제외 조건 | 플랫폼별 전수 렌더 테스트 | 렌더러 버전 |
| 생성 도구 체인 (JSON Schema → 타입·툴 정의) | 모든 생성물 | 생성물 diff 0 확인 | — |

기술 부채로 기록할 것: 수동 유지 중인 사본(있다면), 계층화 미적용 상태의 컴포넌트 수 상한, A2UI 세트를 레지스트리로 썼다면 세트 버전 고정 사실.

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **컴포넌트 추가** | 카탈로그 항목 | 계약 ② 봉투, 카탈로그 항목 스키마(필드 구조) | 컴포넌트 구현 | 카탈로그 마이너 버전 상승 → 생성 → 골든셋 추가(같은 PR). 구 프론트는 모르는 컴포넌트를 텍스트 폴백 | 카탈로그·매핑·골든셋·렌더러 바인딩 |
| **컴포넌트 폐기** | 카탈로그 항목 제거 | 계약 ② | 컴포넌트 | `deprecated: since, until` 표시 기간(예시 마이너 2개 버전) → 매핑에서 제외 → 제거는 메이저. 기간 중 호출은 대체 컴포넌트 또는 텍스트 폴백 | 매핑 테이블·골든셋 라벨 재부여 |
| **props 변경** (필수 추가·개명) | props 스키마 | 봉투 | — | 메이저 + 구→신 변환 어댑터 또는 병행 기간. 선택 props 추가는 마이너 | 툴 정의·검증기·렌더러 |
| **디자인 시스템 개편** | 토큰 세트 | **카탈로그 스키마 불변** (에이전트는 토큰을 모름) | 토큰 값, 컴포넌트 스타일 | 토큰 교체(패치), 시각 회귀 | 렌더러만. 프롬프트·골든셋 무관 |
| **사용자 환경** (모바일 추가) | `platforms` 필드, 지원 매트릭스 | 카탈로그 스키마 | 렌더러 바인딩 | Declarative: 렌더러 추가 / Controlled: 컴포넌트별 플랫폼 구현 + 매트릭스 갱신 | 매핑 규칙(플랫폼 제외 조건) |
| **다국어** | `a11y` 라벨 토큰 키, 문자열 리소스 | props는 구조화 값(`amount`, `currency`) — 표시 문자열 금지 | 문자열 리소스, RTL 레이아웃 토큰 | 문자열·레이아웃을 카탈로그 밖 리소스로 분리([09](09-ux-accessibility.md)) | 렌더러 리소스만 |
| **모델 교체** | 스키마 실패율 분포, 선택 분포 | 카탈로그 | 프롬프트·`examples` | 골든셋 회귀, `purpose`·`examples` 보강 | 프롬프트·골든셋 |
| **프로토콜** (A2UI 세트 개명) | 세트 기반 레지스트리 항목 이름 | 자체 카탈로그 `name` | 세트 ↔ 카탈로그 매핑 어댑터 | 어댑터의 이름 매핑 교체 | 어댑터 |
| **규칙·정책** (권한 모델 변경) | `actions`의 권한 요구 메타데이터 | 봉투 | 권한 규칙 | 규칙은 카탈로그가 아니라 정책 엔진에([04](04-streaming-state-sync.md) 재검증 ②) | 재검증 규칙만 |

가장 자주 바뀌는 것: **컴포넌트 추가·props 선택 필드 추가**(주 단위) > 디자인 토큰 > 폐기 > 봉투(거의 안 바뀜). 코드 밖 설정으로 둘 것: 카탈로그 파일, 토큰 세트, 지원 매트릭스, deprecated 목록. 스키마 진화 규칙을 계약 ②에 적용하면: 봉투에 필드 추가는 자유(프론트는 모르는 필드 무시), `ui_intent` 구조 변경은 봉투 버전 상승, `text`는 영구 필수.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | 카탈로그 정의·렌더는 등급 1. `actions`를 가진 컴포넌트(승인 카드)는 그 행동의 등급을 **메타데이터로 상속**해 매핑·재검증이 참조 |
| 가드레일 위치 | **출력**: 카탈로그 스키마 + 허용 조합 + 제약 검증 = UI 트리 검증(Part 0/01이 지목한 자리). **행동**: 없음(정의만) |
| 게이트 출력과 판정 수단 | 통과 / 저하(텍스트 폴백). 차단은 없음 — 렌더 실패는 항상 저하로. 규칙(스키마)만 |
| 소유자 (A) | 디자인 책임자. R: 프론트엔드. C: 접근성, AI 엔지니어(툴 정의 영향). 카탈로그 변경은 디자인 시스템 PR 절차 |
| 감사 추적에 남길 필드 | 응답별 `catalog_version`, 선택된 컴포넌트 `name`·`version`, 검증 결과(통과/실패 코드), 폴백 여부. 시점 재현을 위해 카탈로그 버전별 스냅샷 보존 |

### 운영 준비도 체크
- [ ] 카탈로그 원본이 하나이고 타입·툴 정의·검증기가 빌드 시 생성되는가(생성물 수동 수정 금지)
- [ ] 카탈로그 ↔ 컴포넌트 export 대조가 CI 게이트인가
- [ ] 응답의 `catalog_version`과 프론트 버전의 메이저·마이너 불일치 처리가 각각 구현·테스트됐는가
- [ ] 컴포넌트별 스키마 실패율 알림과 컴포넌트 단위 노출 중단 플래그가 있는가
- [ ] 폐기 절차(deprecated 기간·대체 컴포넌트·텍스트 폴백)가 문서화돼 있는가
- [ ] 카탈로그 변경 PR이 골든셋·매핑 테이블 변경을 포함하도록 강제되는가
- [ ] 과거 `catalog_version`으로 당시 응답을 재검증할 수 있는가(버전별 스냅샷)
