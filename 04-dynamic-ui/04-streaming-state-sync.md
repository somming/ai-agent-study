# 스트리밍과 상태 동기화

> **범위**: SSE, state patch, optimistic UI, 양방향 이벤트. 에이전트 백엔드의 상태 변화를 프론트에 어떻게 흘리고, 사용자 이벤트를 어떻게 되돌려 에이전트 상태 머신의 입력으로 바꾸는지. 이 페이지가 정의하는 사용자 이벤트 스키마는 레이어 간 **계약 ③**([Part 0/01](../00-overview/01-reference-architecture.md))이며 [Part 3/12](../03-agent-workflow-rag/12-guardrails-hitl.md)와 함께 설계한다. 전송 프로토콜 선택 자체는 [02](02-protocols-ag-ui-a2ui-mcp-apps.md).
> **시각화**: [`assets/html/genui-streaming-sequence.html`](../assets/html/genui-streaming-sequence.html) — 텍스트 델타 → 툴 호출 → 상태 패치 → UI 컴포넌트 → 사용자 승인 → 서버 검증 → 실행 → 완료 시퀀스

## 요약 (3줄)

1. 에이전트 UI의 스트리밍은 토큰을 빨리 보여주는 문제가 아니라 **두 개의 상태(에이전트 상태 ↔ UI 상태)를 하나로 유지하는 문제**다. 텍스트 델타, 툴 호출 진행, 상태 패치, 사용자 이벤트가 모두 같은 순서 보장 아래 흘러야 한다.
2. 전송은 서버→클라이언트 단방향이 지배적이므로 SSE(Server-Sent Events)가 기본값이고, 상태는 전체 스냅샷 + 부분 패치(JSON Patch 류)의 조합이 기본값이다. WebSocket은 고빈도 양방향이 실제로 필요할 때만.
3. 사용자 이벤트는 **신뢰 경계를 넘는 외부 입력**이다. 프론트가 optimistic하게 반영하더라도 서버가 스키마·권한·멱등성을 재검증한 뒤에야 에이전트 상태 머신의 입력이 된다. 거부되면 롤백한다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 전송 채널 결정(SSE / WebSocket / 폴링) ② 상태 동기화 방식(스냅샷 / 패치 / 혼합) ③ 사용자 이벤트 스키마(계약 ③) ④ 재연결·순서 보장·멱등성 정책 ⑤ optimistic UI 적용 범위와 롤백 규칙 |
| **언제** (When) | 에이전트 응답이 수 초 이상 걸리거나(스트리밍 필요), 에이전트가 **상태**(장바구니, 선택 항목, 진행 단계)를 들고 있어 UI와 동기화해야 하거나, 사용자 행위가 에이전트 실행 **도중**에 돌아와야 할 때. 단발 요청-응답에 UI 상태가 없다면 일반 HTTP로 충분 |
| **어떻게** (How) | ① 에이전트 상태 중 UI가 봐야 하는 부분을 정의(공유 상태) → ② 이벤트 범주(생명주기 / 텍스트 / 툴 호출 / 상태 / 사용자 이벤트) 확정 → ③ 전송 채널 선택 → ④ 스냅샷·패치 규칙과 순서 번호 → ⑤ 사용자 이벤트 스키마 + 서버 재검증 지점 → ⑥ 재연결 시 복구 절차 → ⑦ optimistic 적용 범위 결정 |
| **왜** (Why) | 동기화를 설계하지 않으면 ① 사용자가 승인을 눌렀는데 에이전트는 이미 다음 단계로 가 있고 ② 재연결 후 같은 툴 호출 카드가 두 번 보이며 ③ UI에 보이는 장바구니와 에이전트가 아는 장바구니가 다르다. 이 셋은 모두 "상태가 둘인데 하나처럼 보여야 한다"는 문제의 증상이다 |

## 문제와 맥락

채팅 UI에서 스트리밍은 토큰 델타를 보여주는 것으로 충분했다. 에이전트 UI는 다르다. 에이전트는 수십 초 동안 툴을 호출하고, 그 결과로 상태를 바꾸고, 중간에 사용자 승인을 기다린다. 프론트는 그 과정을 **실시간으로 반영**해야 하고, 사용자의 행위를 **실행 도중에** 되돌려야 한다. 결국 분산 시스템의 오래된 문제 — 순서, 중복, 유실, 분기 — 가 UI 레이어에 그대로 나타난다. AG-UI가 이벤트 범주(텍스트 델타, 툴 호출 시작/종료, 상태 패치)를 표준화한 것은 이 문제의 **어휘**를 통일한 것이지 해법을 준 것은 아니다 `[2차]`.

## 핵심 개념

### 두 개의 상태

| 상태 | 소유자 | 예 | 변경 경로 |
|---|---|---|---|
| **에이전트 상태** | 백엔드 상태 머신([Part 3/08](../03-agent-workflow-rag/08-state-memory-context.md)) | 현재 단계, 선택된 상품 목록, 승인 대기 중인 액션, 검색 결과 | 에이전트 실행, 사용자 이벤트(검증 후) |
| **UI 상태** | 프론트엔드 | 어느 카드가 펼쳐져 있나, 스크롤 위치, 입력 중인 텍스트 | 사용자 조작 |
| **공유 상태** | 양쪽이 같은 값을 봐야 하는 교집합 | 장바구니, 진행률, 승인 상태 | 백엔드가 권위(authoritative), 프론트는 복제본 |

설계의 첫 결정은 **공유 상태의 범위를 최소화**하는 것이다. UI 상태를 에이전트에 보내지 않고, 에이전트 내부 상태(프롬프트, 중간 추론)를 프론트에 보내지 않는다.

### 전송 채널

| 채널 | 방향 | 특성 | UI 설계에서의 자리 |
|---|---|---|---|
| **SSE** | 서버→클라이언트 (역방향은 별도 HTTP) | HTTP 위에서 동작, 자동 재연결(Last-Event-ID), 프록시·CDN 친화 | 기본값. AG-UI의 기반 `[2차]` |
| **WebSocket** | 양방향 | 지속 연결, 저지연, 프록시·로드밸런서 설정 필요, 재연결 직접 구현 | 사용자 이벤트가 고빈도(드래그, 공동 편집)이거나 바이너리 |

SSE에서 역방향(사용자 이벤트)은 일반 HTTP POST로 보낸다. "양방향 프로토콜"이라는 AG-UI의 서술도 이 구조다. 승인·선택·수정은 빈도가 낮으므로 이것으로 충분하다.

### 상태 동기화 — 스냅샷 vs 패치

| 방식 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **전체 스냅샷** | 상태가 바뀔 때마다 전체 상태를 보냄 | 단순, 유실에 강함(다음 스냅샷이 복구) | 상태가 크면 대역폭·렌더 비용 |
| **부분 패치** (JSON Patch 류) | 변경된 경로와 연산(add/replace/remove)만 보냄 | 작고 빠름, 부분 렌더에 적합 | 순서가 어긋나면 상태가 깨짐, 유실 시 복구 불가 |
| **혼합** (기본값) | 시작·재연결 시 스냅샷, 이후 패치, 주기적 또는 N패치마다 스냅샷 | 둘의 장점 | 패치에 순서 번호와 기준 스냅샷 ID 필요 |

JSON Patch는 IETF 표준(RFC 6902)이 있어 라이브러리가 풍부하다 `[검증]`. AG-UI의 상태 패치도 이 계열로 알려져 있으나 정확한 포맷은 스펙 버전에서 확인한다 `[2차]`.

### 부분 렌더와 점진적 표시

- **텍스트**: 델타를 이어 붙여 렌더. 마크다운이면 미완성 구문(열린 코드 블록)을 임시 닫기
- **컴포넌트**: 툴 호출 "시작" 이벤트가 오면 **스켈레톤**(자리 표시자)을 먼저, 인자가 완성되면 실제 컴포넌트. 인자 델타를 스트리밍으로 파싱해 부분 렌더하는 것은 가능하지만 스키마 검증 전 렌더이므로 **표시 전용** 컴포넌트에만 허용
- **순서 안정성**: 이미 보인 컴포넌트의 위치가 이후 이벤트로 바뀌지 않도록 한다([09](09-ux-accessibility.md))

### Optimistic UI와 롤백

사용자가 승인을 누르면 서버 응답을 기다리지 않고 "승인됨"으로 그린다(optimistic). 서버가 거부하면 되돌린다. 적용 규칙은 다음과 같다.

| 사용자 행위 | optimistic 허용 | 이유 |
|---|---|---|
| 선택·필터·펼치기 | 허용 | 되돌려도 피해 없음 |
| 피드백(좋아요) | 허용 | 멱등, 실패해도 사용자 손해 없음 |
| 승인(실행으로 이어짐) | **"전송됨" 상태까지만** | "실행됨"으로 그리면 서버 거부 시 사용자가 이미 실행됐다고 믿음 |
| 수정(데이터 변경) | 허용하되 "저장 중" 표시 | 충돌 시 서버 버전으로 덮고 알림 |

롤백은 **이벤트 단위**로 한다. 사용자 이벤트마다 클라이언트 ID를 붙이고, 서버의 수락/거부 이벤트가 그 ID를 참조한다. 거부 시 해당 이벤트의 optimistic 변경만 되돌리고 이유를 표시한다.

### 재연결·순서 보장·멱등성

- **순서 번호**: 모든 서버 이벤트에 run 내 단조 증가 번호. 프론트는 번호가 건너뛰면 스냅샷을 요청
- **재연결**: SSE의 Last-Event-ID 또는 자체 커서로 "어디까지 받았는지" 전달. 서버는 그 이후를 재전송하거나 스냅샷 + 이후 패치
- **멱등성**: 사용자 이벤트에 멱등 키(idempotency key). 네트워크 재시도로 같은 승인이 두 번 가도 서버가 한 번만 처리. 승인은 **실행으로 이어지므로** 이 키가 없으면 이중 실행이 난다
- **run 식별**: 한 대화에 여러 run이 겹칠 수 있다(사용자가 기다리지 않고 다음 질문). 모든 이벤트에 run ID

### 사용자 이벤트 스키마 (계약 ③)

```json
{
  "event_id": "evt_01H...",
  "idempotency_key": "cli_8f3a...",
  "run_id": "run_42",
  "type": "approval",
  "target": { "message_id": "msg_7", "component_id": "cmp_approve_refund_3" },
  "action": "approve",
  "payload": { "amount": 12000, "reason": "고객 요청" },
  "catalog_version": "2.3.0",
  "user": { "id": "u_1", "roles": ["cs_agent"] },
  "issued_at": "2026-10-11T09:12:33Z",
  "client_state_seq": 118
}
```

- `type`은 닫힌 enum: `approval | rejection | edit | selection | feedback | input | cancel`. [06](06-hitl-ui-patterns.md)의 패턴마다 하나
- `target`은 어느 응답·어느 컴포넌트에서 났는지. 컴포넌트는 카탈로그의 `actions` 정의([03](03-component-registry-schema.md))와 대조된다
- `user`는 **프론트가 주장하는 값**일 뿐이다. 서버는 인증 컨텍스트에서 다시 얻는다
- `client_state_seq`는 사용자가 어느 상태를 보고 행동했는지. 서버 상태가 그 이후 바뀌었다면 "오래된 화면에서의 승인"으로 거부하거나 재확인

### 서버 재검증 → 상태 머신 입력

```
사용자 이벤트 ─▶ ① 스키마 검증 (type·target·payload가 카탈로그 actions와 일치)
             ─▶ ② 권한 검증 (이 사용자가 이 액션을 이 대상에 할 수 있나 — 인증 컨텍스트 기준)
             ─▶ ③ 상태 검증 (target이 아직 유효한가, 이미 처리되지 않았나, client_state_seq가 너무 오래되지 않았나)
             ─▶ ④ 멱등성 (idempotency_key 중복이면 이전 결과 반환)
             ─▶ ⑤ 정책 게이트 (Part 3/12 — 한도·규칙·결정 모델 확신도)
             ─▶ 수락: 상태 머신 전이 이벤트로 변환 (예: AWAITING_APPROVAL → APPROVED) ─▶ 수락 이벤트 송신
             ─▶ 거부: 거부 이벤트 + 이유 코드 송신 ─▶ 프론트 롤백
```

①~④는 Part 4의 책임, ⑤는 Part 3의 책임이다. 경계를 명시하지 않으면 양쪽 다 "저쪽이 검사하겠지"가 된다.

## 아키텍처 / 파이프라인

[시각화](../assets/html/genui-streaming-sequence.html)의 시퀀스: 사용자 요청 → 프론트가 run 시작 → AG-UI 스트림으로 텍스트 델타 → 툴 호출 시작(스켈레톤) → 상태 패치 → 컴포넌트 렌더(스키마 검증 통과 후) → 사용자 승인 이벤트(optimistic "전송됨") → 서버 재검증(①~⑤) → 툴 실행 → 결과 패치 → run 종료. 입력은 [02](02-protocols-ag-ui-a2ui-mcp-apps.md)의 전송층 결정과 [03](03-component-registry-schema.md)의 `actions` 정의, 출력은 이벤트 스키마·동기화 정책·사용자 이벤트 스키마(계약 ③)다. [06](06-hitl-ui-patterns.md)이 패턴별 이벤트를 이 스키마 위에 정의한다.

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| **SSE + HTTP POST 역방향** | 서버→클라이언트 지배적, 사용자 이벤트 저빈도(승인·선택), 기존 HTTP 인프라 | 고빈도 양방향, 바이너리, 브라우저 밖 네이티브 소켓 환경 | 하 — 표준 브라우저 API, 프록시 친화 | 표준 | `[검증]` WHATWG HTML 표준(EventSource) |
| **WebSocket** | 고빈도 양방향(공동 편집, 드래그 동기화), 지연 민감 | 저빈도 이벤트만 있음(과잉), 프록시·LB 설정 권한 없음 | 중 — 재연결·하트비트 직접 구현 | 표준 | `[검증]` RFC 6455 |
| **전체 스냅샷** | 상태 작음, 유실 복구 단순화 우선 | 상태 크거나 변경 빈번 | 하 | 표준 | — |
| **JSON Patch 부분 패치** | 상태 크고 변경 국소적, 부분 렌더 | 순서 보장 인프라 없음 | 중 — 순서 번호·기준 스냅샷 관리 | 표준 | `[검증]` RFC 6902 |
| **혼합 (스냅샷 + 패치)** | 대부분의 에이전트 UI | 상태가 아주 작아 스냅샷으로 충분 | 중 | 안정 (AG-UI 류의 기본 구조) | `[2차]` |
| **optimistic UI** | 선택·피드백·비파괴적 수정 | 실행으로 이어지는 승인을 "완료"로 표시 | 중 — 롤백 경로 | 안정 (프론트 관행) | — |

### 선택 가이드

- **사용자 이벤트가 승인·선택·피드백 정도라면** → SSE + POST, 혼합 동기화. 이유: 가장 단순하고 AG-UI와 구조가 같다
- **드래그·공동 편집처럼 초당 수십 회 이벤트가 오간다면** → WebSocket. 이유: HTTP POST 오버헤드가 체감된다. 단 재연결·순서 보장을 직접 구현
- **상태가 크고(수백 항목 표) 자주 바뀐다면** → JSON Patch + 주기 스냅샷. 이유: 전체 재전송·재렌더 비용
- **승인이 실행으로 이어진다면** → optimistic은 "전송됨"까지, 멱등 키 필수. 이유: 이중 실행과 거짓 완료 표시가 최악의 실패
- **판단이 어려우면** → SSE + 혼합 동기화 + 저빈도 POST. 이유: 전부 표준이고 나중에 WebSocket으로 바꿔도 이벤트 스키마는 유지된다

## 설계 시 고려사항 (체크리스트)

- [ ] 공유 상태의 범위를 명시했는가. UI 전용 상태와 에이전트 내부 상태가 섞여 있지 않은가
- [ ] 모든 서버 이벤트에 run ID와 순서 번호가 있는가
- [ ] 재연결 시 "어디까지 받았는지"를 전달하고 스냅샷으로 복구하는 경로가 있는가
- [ ] 사용자 이벤트에 멱등 키가 있고 서버가 중복을 걸러내는가
- [ ] 사용자 이벤트의 `user`를 서버가 인증 컨텍스트로 **다시** 얻는가 (프론트 값 신뢰 금지)
- [ ] `client_state_seq`로 오래된 화면에서의 승인을 감지하는가
- [ ] 서버 재검증 ①~④(Part 4)와 ⑤ 정책 게이트(Part 3)의 책임 경계가 문서화되어 있는가
- [ ] optimistic 허용 범위가 행위 유형별로 정해져 있고 롤백이 이벤트 단위로 되는가
- [ ] 툴 호출 "시작" 시 스켈레톤을, 검증 통과 후 실제 컴포넌트를 그리는가
- [ ] 이미 렌더된 컴포넌트의 위치가 이후 이벤트로 바뀌지 않는가
- [ ] 이벤트 스트림이 트레이스에 기록되어 한 run을 끝까지 따라갈 수 있는가 ([Part 5/03](../05-cross-cutting/03-observability-tracing.md))

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 순서 어긋남 | 패치가 잘못된 상태에 적용되어 UI 깨짐 | 순서 번호, 건너뜀 감지 시 스냅샷 재요청 |
| 이중 실행 | 네트워크 재시도로 승인이 두 번 처리 | 멱등 키, 서버 측 처리 로그 |
| 거짓 완료 표시 | optimistic "실행됨" 후 서버 거부 | 승인은 "전송됨"까지만 optimistic |
| 오래된 화면에서의 승인 | 사용자가 본 것과 다른 상태에 승인 적용 | `client_state_seq` 검증, 재확인 UI |
| 동시 run 혼선 | 두 질문의 이벤트가 한 화면에 섞임 | run ID로 분리 렌더, 이전 run 취소 정책 |
| 프록시·CDN의 SSE 버퍼링 | 델타가 뭉쳐서 도착, 스트리밍 효과 상실 | 응답 헤더로 버퍼링 비활성화, 하트비트 |
| 프로토콜 미성숙 | 이벤트 포맷 변경 | 범주 구조만 의존, 어댑터 계층 ([02](02-protocols-ag-ui-a2ui-mcp-apps.md)) |
