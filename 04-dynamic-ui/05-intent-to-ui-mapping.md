# 의도 → UI 매핑

> **범위**: 어떤 UI를 띄울지 결정: 결정 모델 판정, 온톨로지 기반 매핑, 룰 기반 폴백. "이 응답에 어느 컴포넌트를 쓸까"를 **판정 문제**로 보고, 판정 수단(LLM 툴 호출 / 결정 모델 / 온톨로지 매핑 / 규칙 / 혼합)을 비교한다. 판정 일반론은 [Part 1/02](../01-foundations/02-system1-vs-system2.md), 결정 모델 배치 설계는 [Part 3/11](../03-agent-workflow-rag/11-decision-layer.md). 선택지가 되는 카탈로그는 [03](03-component-registry-schema.md).
> **시각화**: [`assets/html/dynamic-ui-architecture.html`](../assets/html/dynamic-ui-architecture.html) — "의도→UI 매핑" 노드

## 요약 (3줄)

1. "표를 보여줄까, 카드를 보여줄까, 텍스트로 끝낼까"는 생성이 아니라 **선택지가 닫힌 판정**이다. 카탈로그가 있는 한 선택지는 열거 가능하므로 System 1 수단(규칙·결정 모델)이 먼저고, LLM 툴 호출은 그것으로 안 될 때다.
2. 수단은 네 가지 — LLM 툴 호출, 결정 모델(Jev / Decisions API), 온톨로지 매핑, 규칙 — 이고 실무는 **혼합**이다. 규칙이 먼저 거르고, 결정 모델 또는 LLM이 남은 것을 고르고, 온톨로지가 선택지와 데이터 바인딩을 공급한다.
3. 어떤 수단이든 **매핑 테이블**(의도 → 컴포넌트 → 조건 → 폴백)을 문서로 두고, 확신도가 낮으면 텍스트로 떨어진다. 매핑 테이블이 곧 골든셋의 뼈대다([10](10-evaluation-genui.md)).

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 의도→UI 매핑 테이블 ② 판정 수단 배정(의도 유형별로 다를 수 있음) ③ 확신도 임계값과 폴백 규칙 ④ 매핑 결과를 담는 `ui_intent` 필드(계약 ②) ⑤ 평가 골든셋(의도 → 기대 컴포넌트) |
| **언제** (When) | 카탈로그 컴포넌트가 둘 이상일 때. 컴포넌트가 하나(예: citation 카드)뿐이면 매핑은 "있다/없다" 규칙으로 끝난다. Open-ended 영역은 매핑 대상이 아니다(툴 서버가 UI를 가져온다) |
| **어떻게** (How) | ① Part 3/02의 의도(intent) 분류 결과와 카탈로그를 나란히 놓고 매핑 테이블 초안 → ② 결정론적으로 정해지는 행(권한 없음 → 텍스트, 항목 1개 → 카드)을 규칙으로 → ③ 남은 행의 판정 수단 선택(결정 모델 vs LLM 툴 호출) → ④ 확신도 임계값과 폴백 정의 → ⑤ 한국어 골든셋으로 `[실측]` → ⑥ 운영 중 수정률·폴백률을 테이블에 피드백 |
| **왜** (Why) | LLM에 "적절한 컴포넌트를 골라라"만 맡기면 ① 같은 질문에 다른 UI가 나와 사용자가 학습하지 못하고([09](09-ux-accessibility.md)) ② 선택 비용이 생성 비용에 묻혀 측정되지 않으며 ③ 확신도가 없어 "애매하면 텍스트"를 구현할 수 없다. 반대로 규칙만 쓰면 새 의도마다 코드를 고친다 |

## 문제와 맥락

에이전트가 "상품 3개를 찾았습니다"라고 말했을 때, 그것을 비교표로 보여줄지 카드 3장으로 보여줄지 리스트로 보여줄지는 **질문의 의도**(비교하려는가, 하나를 고르려는가, 훑어보려는가)와 **데이터의 형태**(항목 수, 속성 수, 이미지 유무)와 **문맥**(모바일인가, 이미 비교표가 떠 있는가)에 달렸다. 이 결정은 설명이 아니라 **답 하나**가 필요하고, 선택지는 카탈로그로 닫혀 있다. [Part 1/02](../01-foundations/02-system1-vs-system2.md)의 기준으로 전형적인 System 1 과업이다.

그런데 대부분의 프레임워크는 이것을 LLM 툴 호출로 처리한다 — 컴포넌트마다 툴을 만들고 LLM이 고른다. 작동은 하지만 비싸고 흔들리고 확신도가 없다. 2026-09 이후 결정 모델이 상용화되면서 이 자리에 다른 선택지가 생겼다 `[2차]`. 다만 UI 선택에 결정 모델을 적용한 **사례 보고는 아직 드물다**.

## 핵심 개념

### 매핑의 입력과 출력

```
입력: 의도(intent)        ← Part 3/02 질의 이해·라우팅의 결과 (또는 응답 생성 시 LLM이 함께 출력)
      데이터 형태         ← 응답에 담긴 항목 수·속성·타입 (Part 3/04 구조화 출력)
      문맥               ← 플랫폼, 화면 크기, 직전 UI, 사용자 권한
      카탈로그           ← [03] 선택지 + purpose + bindings
출력: ui_intent { component, props(바인딩), confidence, requires_approval, fallback }   → 계약 ②
```

의도 분류 자체는 Part 3의 책임이다. 이 페이지는 **의도가 주어진 뒤** 컴포넌트를 고르는 단계만 다룬다. 다만 실무에서는 "의도 분류"와 "컴포넌트 선택"을 한 판정으로 합치는 경우도 많다(결정 모델 질문 하나, 또는 LLM 툴 호출 하나). 합치면 단계가 줄고, 나누면 의도 분류를 UI 외 용도(라우팅)로 재사용할 수 있다.

### 판정 수단 네 가지

| 수단 | 동작 | 확신도 | 변경 비용 | UI 매핑에서의 자리 |
|---|---|---|---|---|
| **규칙** | 코드·테이블 조회. "항목 1개 → 카드", "권한 없음 → 텍스트", "모바일 → 표 금지" | 없음(결정론) | 코드 수정 | 1차 필터. 결정론적으로 정해지는 모든 행 |
| **LLM 툴 호출** | 컴포넌트 = 툴. LLM이 응답 생성 중 툴을 호출하며 props를 채움 | 없음(또는 비보정 자기 보고) | 프롬프트·툴 설명 수정 | 선택지가 아직 안 굳었거나 props 채우기에 생성이 필요할 때 |
| **결정 모델** (Jev / Decisions API) | 상태(의도·데이터 요약·문맥) + "어느 컴포넌트?" 타입드 질문 → 선택 + 보정 확률 | 보정 확률 `[벤더]` | 질문 정의·선택지 수정 | 선택지 닫힘, 임계값 폴백 필요, 대량·저지연 |
| **온톨로지 매핑** | 도메인 개념(상품·주문·인시던트)과 컴포넌트를 온톨로지 관계로 연결. "응답의 주 엔티티가 `Product` 클래스 → `ProductCard` 계열" | 없음(결정론) | 온톨로지 수정 | 선택지 공급·좁히기, 데이터 바인딩 자동화 |

결정 모델 두 접근은 인터페이스는 같지만 내부가 다르다. Jev는 비자기회귀 결정 전용 모델, Decisions API는 범용 생성 모델(gpt-6-luna)의 출력 제약 엔드포인트다 `[벤더]` `[2차]`. 지연·보정 품질이 다를 수 있으니 `[실측]`은 따로 한다. 둘 다 영어 중심이라는 지적이 있으므로(Jev 명시) 한국어 의도 골든셋이 선행 조건이다 `[2차]`.

### 혼합 패턴 (기본값)

```
의도 + 데이터 + 문맥
   │
   ▼
 ① 규칙 ─── 결정론 행이면 즉시 확정 (권한, 항목 수, 플랫폼 제약) ─────────────────────┐
   │ (남은 경우)                                                                        │
   ▼                                                                                    │
 ② 온톨로지 ─ 주 엔티티 클래스로 후보 컴포넌트 집합을 좁힘 (예: 12개 → 3개) ──────────┤
   │                                                                                    │
   ▼                                                                                    ▼
 ③ 결정 모델 또는 LLM 툴 호출 ─ 후보 중 선택 (+ 확신도) ───▶ 확신 ≥ θ → ui_intent 확정 → 카탈로그 스키마 검증 → 렌더
                                                             확신 < θ → 폴백(텍스트) 또는 선택지 제시([06])
```

①이 전체 트래픽의 상당 부분을 처리하면 ③의 비용과 흔들림이 그만큼 줄어든다. ②는 온톨로지가 있을 때만. ③에서 결정 모델과 LLM 중 무엇을 쓸지는 아래 비교표.

### 매핑 테이블 설계

| intent | 조건 | component | props 바인딩 | 확신도 임계값 | 폴백 | 수단 |
|---|---|---|---|---|---|---|
| `compare_products` | 항목 2~6, 공통 속성 ≥ 2 | `ProductComparisonTable` | `items ← products[]`, `columns ← 공통 속성` | 0.7 | `ProductCardList` → 텍스트 | 결정 모델 |
| `compare_products` | 항목 > 6 | `ProductCardList` + 필터 | — | — | 텍스트 | 규칙 |
| `show_product` | 항목 1 | `ProductCard` | `item ← products[0]` | — | 텍스트 | 규칙 |
| `request_refund` | 항상 | `ApprovalCard` | `action ← refund`, `requires_approval: true` | — | 없음(승인 UI는 폴백 불가 → 에러) | 규칙 |
| `answer_question` | citations 존재 | `CitationList` | `citations ← citations[]` | — | 텍스트 | 규칙 |
| (미분류) | — | — | — | — | 텍스트 | — |

표의 원칙: **행동으로 이어지는 의도(`request_refund`)는 규칙으로 고정**한다. 확률 수단에 맡기지 않는다. 임계값은 `[실측]`으로 정하고 표에 적는다. 임계값 열이 비어 있는 행은 결정론이다.

### 폴백과 낮은 확신도 처리

| 상황 | 처리 |
|---|---|
| 확신도 < θ | 텍스트로 답하고, 필요하면 "표로 볼까요?" 같은 **선택지 제시** 컴포넌트([06](06-hitl-ui-patterns.md)) |
| 선택은 됐지만 스키마 검증 실패 | 테이블의 `fallback` 체인을 따라 내려감. 마지막은 항상 텍스트 |
| 상위 두 후보의 확신도가 비슷 | 보수적 기본값(더 단순한 컴포넌트) 또는 선택지 제시 |
| 플랫폼이 컴포넌트 미지원 | 규칙 ①에서 미리 걸러 후보에서 제외 |
| 결정 모델 장애 | 규칙 기본값(의도별 1순위 컴포넌트) 또는 텍스트. 계약 ② `degradation[]`에 `decision_fallback` 기록([03](03-component-registry-schema.md)) → [09](09-ux-accessibility.md) 고지. 3/11에서 같은 코드가 이미 와 있으면 중복 추가하지 않음 (불균형 ④ 반영) |

### 평가 방법

골든셋은 **(의도·데이터 형태·문맥) → 기대 컴포넌트** 쌍이다. 매핑 테이블의 행마다 최소 10건, 한국어·혼합 언어·비격식 입력 포함. 지표는 선택 정확도, 혼동 행렬(어느 쌍이 헷갈리는가), 보정 곡선(결정 모델 사용 시), 폴백률, 운영 중 사용자 수정률. 상세는 [10](10-evaluation-genui.md). 결정 모델과 LLM 툴 호출을 **같은 골든셋**으로 비교한 뒤 수단을 확정한다.

## 아키텍처 / 파이프라인

입력은 Part 3의 응답(텍스트 + citations + 의도·데이터), [03](03-component-registry-schema.md)의 카탈로그, 문맥. 처리는 위 혼합 패턴 ①~③. 출력은 `ui_intent`가 채워진 응답(계약 ②)이며 [04](04-streaming-state-sync.md)의 스트림을 타고 [07](07-frontend-integration.md)의 렌더러로 간다. 판정 결과와 확신도는 트레이스에 기록한다([Part 5/03](../05-cross-cutting/03-observability-tracing.md)).

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| **규칙** (테이블 조회·코드) | 결정론적 조건(권한·항목 수·플랫폼), 행동 UI, 감사 대상 | 자연어 의도의 뉘앙스 판단, 조건이 수십 개로 늘어난 경우 | 하 | 표준 | `[검증]` |
| **LLM 툴 호출** (컴포넌트 = 툴) | 프로토타입, 선택지가 아직 안 굳음, props 채우기에 생성 필요(요약 문구 등), 프레임워크 기본 지원 활용 | 대량·저지연, 확신도 임계값 필요, 선택지 수십 개 초과 | 중 — 요청마다 툴 정의 토큰, 선택 비용이 생성에 묻힘 | 안정 (프레임워크 기본값) | `[검증]` 비보정 문제는 널리 보고 |
| **결정 모델 — Jev** | 선택지 닫힘, 보정 확률로 폴백 임계값, 대량 트래픽, 텍스트/JSON 상태 입력 | 이미지 입력, 영어 외 언어 미검증, 선택 이유 설명 필요 | 하 (호출) / 중 (한국어 평가셋 구축) | 신생 (2026-09-15 EA) | `[벤더]` 지연·비용 미검증 |
| **결정 모델 — OpenAI Decisions API** | 위와 유사 + 이미지 포함 문맥(스크린샷), 이미 OpenAI 생태계 | 단일 모델(gpt-6-luna) 종속, 가격·상태 정보 유동적 | 하~중 | 신생 (베타) | `[2차]` 소스 충돌 |
| **온톨로지 매핑** | 도메인 온톨로지 보유, 엔티티 클래스가 컴포넌트와 자연스럽게 대응, 바인딩 자동화 | 온톨로지 없음, 의도가 엔티티가 아니라 행위 중심 | 중~상 — 온톨로지 유지 비용 | 신생 (UI 적용 사례 드묾) | `[2차]` |
| **파인튜닝 분류기** | 라벨 데이터 수천 건, 선택지 고정, 온프레미스 | 선택지 자주 변경, 라벨 없음 | 중 (학습·MLOps) | 표준 | `[검증]` |
| **혼합** (규칙 → 온톨로지 → 결정 모델/LLM) | 대부분의 운영 시스템 | 컴포넌트 2~3개짜리 소규모(과잉) | 중 | 안정 (구성 자체는 일반 패턴) | `[2차]` |

### 선택 가이드

- **의도가 행동(승인·실행·결제)으로 이어진다면** → 규칙. 이유: 확률로 승인 UI를 띄우지 않는다. 틀리면 승인 없이 실행되거나 승인이 안 뜬다
- **컴포넌트가 3개 이하이고 프로토타입이라면** → LLM 툴 호출. 이유: 프레임워크가 다 해 준다. 선택지가 굳으면 위로 이전
- **선택지가 굳었고 트래픽이 많으며 "애매하면 텍스트"가 필요하다면** → 결정 모델. 이유: 보정 확률로 임계값을 둘 수 있고 생성 비용이 빠진다. 단 한국어 `[실측]` 전에는 LLM과 병행 비교
- **도메인 온톨로지가 이미 있고 응답의 주 엔티티가 명확하다면** → 온톨로지로 후보를 좁히고 결정 모델/LLM으로 마무리. 이유: 선택지가 줄어 정확도가 오르고 바인딩이 자동화된다
- **판단이 어려우면** → 규칙 1차 필터 + LLM 툴 호출, 판정 결과를 트레이스에 기록. 이유: 기록이 쌓이면 그것이 결정 모델 전환용 골든셋이 된다

## 설계 시 고려사항 (체크리스트)

- [ ] 매핑 테이블이 문서로 존재하고 카탈로그 버전에 묶여 있는가
- [ ] 행동으로 이어지는 의도는 모두 규칙 행인가
- [ ] 결정론적으로 정해지는 조건(권한·항목 수·플랫폼)을 규칙으로 먼저 걸러내는가
- [ ] 확신도 임계값이 `[실측]`으로 정해졌고, 임계값 미만의 폴백 경로가 있는가
- [ ] 폴백 체인의 마지막이 항상 텍스트인가
- [ ] 결정 모델을 쓴다면 한국어·혼합 언어·비격식 입력 골든셋으로 평가했는가, 보정 곡선을 확인했는가
- [ ] 결정 모델 장애 시 규칙 기본값으로 떨어지는가
- [ ] 판정 결과·확신도·수단이 트레이스에 기록되는가
- [ ] 같은 의도·같은 데이터 형태에 같은 컴포넌트가 나오는가(일관성, [09](09-ux-accessibility.md))
- [ ] 운영 중 사용자 수정률·폴백률이 매핑 테이블 개정에 피드백되는 주기가 있는가

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 결정 모델 성능이 벤더 주장뿐 | 기대한 지연·정확도·보정이 안 나올 수 있음 | PoC `[실측]`, LLM 툴 호출을 비교군으로 유지 |
| 영어 중심 학습 | 한국어 의도에서 선택 품질 저하 | 한국어 골든셋 필수, 불합격 시 분류기 또는 LLM |
| UI 선택에 결정 모델을 쓴 사례 부족 | 설계 패턴·실패 사례를 참고할 곳이 없음 | 작은 범위(의도 2~3개)에서 시작, 결과를 [10](10-evaluation-genui.md)으로 공유 |
| 의도 분류와 컴포넌트 선택의 경계 모호 | Part 3와 Part 4 양쪽에서 중복 판정 또는 누락 | 입력(의도)과 출력(ui_intent)의 소유자를 문서화 |
| 매핑 테이블의 조합 폭발 | 의도 × 조건 × 플랫폼 행이 수백 개 | 온톨로지로 후보 좁히기, 조건을 규칙 함수로 |
| 유효한 선택 ≠ 좋은 UI | 스키마는 맞지만 사용자가 원한 형태가 아님 | 사용자 수정률 측정, 선택지 제시 패턴 |
| 온톨로지 유지 비용 | UI만을 위해 온톨로지를 만들면 비용이 가치를 넘음 | Part 2에서 이미 쓰는 온톨로지가 있을 때만 |

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 매핑은 **판정**이므로 운영 설계의 중심은 "판정 수단이 죽거나 틀릴 때"와 "선택 분포가 바뀔 때"다. 매핑 테이블이 코드 밖 설정이라는 점이 모든 소절의 전제다.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 요청 수 | LLM 툴 호출 방식의 선택 비용(요청마다 툴 정의 토큰), 결정 모델 레이트 리밋 | 규칙 ①이 처리하는 비율을 높임(결정론 행 확대), 결정 모델로 이전, 선택 결과 캐시(같은 의도·데이터 형태·문맥) | 요청 수 × (1 − 규칙 처리율) |
| 카탈로그 크기 | 선택 정확도 하락, 혼동 쌍 증가 | 온톨로지 ②로 후보 좁히기, 계층화([03](03-component-registry-schema.md)) | 노출 후보 수 |
| 매핑 테이블 행 수 (의도 × 조건 × 플랫폼) | 테이블 관리·골든셋 유지 비용, 규칙 충돌 | 조건을 규칙 함수로, 플랫폼 제외는 별도 매트릭스로 분리 | 테이블 행 수 × 행당 골든셋 10건 |
| 판정 수단 수 (규칙·온톨로지·결정 모델·LLM 병행) | 수단별 트레이스·비교 비용 | 수단을 `decide()` 포트 뒤에 두고 결과 포맷 통일 | 수단 수 |
| 테넌트별 매핑 차이 | 테넌트별 테이블 복제 → 드리프트 | 공통 테이블 + 테넌트 오버레이(행 단위 덮어쓰기) | 오버레이 행 수 |

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| 결정 모델 API 다운·지연 | UI 선택이 안 됨 | 결정 모델 오류율·p95 지연 | 서킷 브레이커 → **규칙 기본값**(의도별 1순위 컴포넌트) → 없으면 텍스트. 저하 상태 플래그 | 예시 5분 지속 → 벤더 상태 확인, 장기화 시 LLM 툴 호출로 수단 전환 |
| 의도→UI 오선택 급증 (모델·프롬프트 변경 후) | 비교 질문에 카드 1장, 단일 상품에 표 | 사용자 수정률·무시율 급등, 골든셋 샘플 재실행 정확도 하락 | 확신도 임계값 θ 상향(보수적 → 텍스트 증가), 특정 의도 행을 규칙 기본값으로 임시 고정 | 수정률 예시 15% 초과 → 모델 롤백 또는 매핑 테이블 개정 |
| 확신도 분포 이동 (보정 붕괴) | 폴백률 급변(갑자기 전부 텍스트 또는 전부 UI) | 확신도 히스토그램 드리프트, ECE 상승 | θ 재보정 전까지 규칙 행 비중 확대 | 모델 버전 변경 여부 확인, 보정 곡선 재측정 |
| 스키마 검증 실패 (선택은 됐으나 props 불합격) | 텍스트 폴백 반복 | 선택 후 스키마 실패율(컴포넌트별) | `fallback` 체인 → 텍스트 | 특정 컴포넌트 집중 → props 바인딩 규칙 결함 |
| 매핑 테이블 로드 실패·버전 불일치 | 모든 응답 텍스트 | 테이블 로드 오류, 카탈로그 버전 불일치 | 마지막 정상 테이블 캐시 사용(저하) → 없으면 텍스트 | 즉시 |
| 행동 의도가 확률 행으로 흘러감 | 승인 카드가 안 뜨거나 확률적으로 뜸 | 매핑 결과 감사: `requires_approval` 의도의 수단 ≠ 규칙 | 해당 응답 차단 + 텍스트 + 에러 기록(승인 UI는 폴백 불가) | 1건이라도 → 테이블 리뷰(설계 결함) |
| 온톨로지 조회 실패 | 후보 좁히기 생략 → 정확도 저하 | 온톨로지 서비스 오류 | ② 건너뛰고 전체 후보로 ③ 진행(저하) | 지속 시 Part 2 온톨로지 팀 |

SLI 후보: 선택 정확도(골든셋 샘플 일일 재실행), 사용자 수정률·무시율, 폴백률(원인별), 결정 모델 가용성·p95, 규칙 처리율, ECE. SLO 초안(예시): 선택 정확도 ≥ 90%(골든셋), 수정률 < 10%, 결정 모델 장애 시 규칙 폴백 전환 < 30초. 쓰기 행동 없음 — 매핑은 `ui_intent`를 채울 뿐 실행하지 않는다. θ 조정 공통 규칙([5/06](../05-cross-cutting/06-operational-design-matrix.md)): **자동 이동은 보수적 방향만**(θ 상향 = 텍스트 증가). 완화(θ 하향)는 사람 결정 + 사후 샘플 감사([3/12](../03-agent-workflow-rag/12-guardrails-hitl.md)의 "임시 확대 결정, 사후 감사 대상"과 동일) (불균형 ⑦ 반영).

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| 매핑 테이블 (의도 → 조건 → 컴포넌트 → θ → 폴백 → 수단) | 모든 UI 선택, 골든셋 카테고리 | **선택 정확도 골든셋**(행당 10건), 결정론 테스트, 혼동 행렬 비교 | 카탈로그 버전(`name` 참조) ↔ 골든셋 버전 — 같은 PR |
| 확신도 임계값 θ (행별) | 폴백률, 선택지 제시 빈도 | 보정 곡선, 경계 사례(θ ± 0.05) | 결정 모델 버전(보정은 모델별) |
| 결정 모델 질문 정의·선택지 enum | 결정 모델 출력 | 골든셋 전수 | 카탈로그(enum 원천) |
| LLM 툴 설명·프롬프트 (툴 호출 방식) | 선택 분포 | 골든셋 전수 | 모델 버전(프롬프트-모델 호환 매트릭스) |
| 온톨로지 → 컴포넌트 매핑 | 후보 집합 | 클래스별 후보 테스트 | 온톨로지 버전(Part 2/06) |
| 규칙 함수 (권한·항목 수·플랫폼) | 결정론 행 | 규칙 테스트 스위트 | 지원 매트릭스([03](03-component-registry-schema.md)) |

기술 부채로 기록할 것: 결정 모델 미도입 상태에서 LLM 툴 호출의 트레이스가 골든셋으로 환류되는지, 한국어 `[실측]` 미완 의도 목록.

### 변화 대응 — 무엇이 바뀌고, 어느 경계에서 흡수하는가

| 변화 유형 | 이 단계에서 바뀌는 것 | 안정적으로 유지할 계약 | 교체 가능한 구현 | 흡수 방식 | 전파 범위 |
|---|---|---|---|---|---|
| **모델 교체** (LLM·결정 모델 버전) | `ui_intent` 선택 분포, 확신도 분포 | `decide()` 포트(입력: 의도·데이터 요약·문맥·후보 / 출력: 컴포넌트·확신도), 매핑 테이블 | 판정 수단 구현 | 섀도(새 모델 결과를 기록만) → **매핑 골든셋 회귀** → θ 재보정 → 카나리. 분포 변화가 크면 규칙 행 확대 | 수단 어댑터 + θ. 테이블 구조 불변 |
| **판정 수단 교체** (LLM 툴 호출 → 결정 모델) | 수단 열 | 포트, 테이블 | 수단 | 같은 골든셋으로 비교 → 의도 행 단위로 점진 전환 | 해당 행 |
| **컴포넌트 추가·폐기** | 테이블 행 추가·대체 | 테이블 스키마 | — | 추가: 행 + 골든셋 10건 + 혼동 쌍 재검사 / 폐기: deprecated 기간 동안 폴백 체인에서 대체 컴포넌트로 리다이렉트 → 제거 | 테이블·골든셋·enum |
| **도메인 모델** (온톨로지 클래스 추가·개명) | ② 후보 공급 | 테이블 | 온톨로지 매핑 | 온톨로지 버전 + 구→신 클래스 매핑, 미분류 클래스는 전체 후보로 | 후보 좁히기만 |
| **규칙·정책** (권한 변경) | 규칙 ① 권한 행 | 테이블 | 권한 조회 | 권한은 매핑 안에서 판정하지 않고 **외부 권한 서비스 조회 결과를 조건으로만** 사용 → 규칙 교체 없음 | 없음(외부화됨) |
| **사용자 환경** (모바일 추가) | 플랫폼 제외 조건, 밀도 상한 | 테이블 | 지원 매트릭스 | 매트릭스에 플랫폼 열 추가 — 테이블 행은 그대로, 규칙 ①이 매트릭스를 조회 | 매트릭스만 |
| **다국어** | 의도 분류 입력 언어 | 테이블(의도 enum은 언어 중립) | 언어별 골든셋 | 언어별 골든셋 추가, 결정 모델은 언어별 `[실측]` | 골든셋 |

가장 자주 바뀌는 것: **매핑 테이블 행**(운영 피드백 반영, 주~월 단위) > θ > 모델 > 수단. 코드 밖 설정으로 둘 것: 매핑 테이블, θ, 결정 모델 질문 정의, 지원 매트릭스, 테넌트 오버레이. 포트·어댑터 뒤에 둘 외부 의존: 결정 모델 API(Jev / Decisions API), LLM, 온톨로지 서비스, 권한 서비스. 시점 재현: 트레이스에 테이블 버전·수단·모델 버전·θ를 기록해야 "그때 왜 표가 나왔나"를 재구성할 수 있다.

### 관측성 — 이 단계에서 무엇을 기록·측정·알림하는가

운영 안정성의 "탐지 신호"가 **실제로 어디서 나오는지**를 설계한다. 기준은 [Part 1/07 관측성 설계 요소](../01-foundations/07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md). 매핑은 **판정**이므로 1/07 판정 속성군(`agent.decision_source`·`agent.confidence`)이 그대로 적용되고, 테이블 버전이 버전 키 5종 바깥의 **추가 버전 키**다 — 트레이스에 없으면 "그때 왜 표가 나왔나"를 재구성할 수 없다.

| 기록 대상 | 스팬 / 이벤트 (이름, 부모) | 핵심 속성 (버전 키 포함) | 지표 (→ 어느 SLI) | 샘플링 · 보존 · PII |
|---|---|---|---|---|
| 매핑 판정 | `ui.map` (부모 `invoke_agent`). 결정 모델·LLM 호출은 `ui.map`의 자식 모델 스팬(`gen_ai.*` 매핑) | `agent.intent_type`, 후보 수, `agent.decision_source`(rule / ontology / decision_model / llm), `agent.component`, `agent.confidence`, θ(`agent.threshold`), 매핑 테이블 버전, `agent.catalog_version`, `agent.model_version`, `agent.fallback_reason`, `agent.requires_approval` | 규칙 처리율, 수단별 분포, 확신도 히스토그램·ECE(일 단위), 폴백률(원인별) → [10](10-evaluation-genui.md) ① 선택 층 | 전수 |
| 외부 판정 의존 | 자식 스팬 `tool.invoke {decision_model}` / `tool.invoke {ontology}` | 지연, 오류 코드, 서킷 상태, `agent.queue_wait_ms` | 결정 모델 가용성·p95, 온톨로지 오류율, 서킷 전환 소요 | 전수 |
| 행동 의도 불변식 | 이벤트 `ui.map.invariant_violation` — `agent.requires_approval=true` ∧ `agent.decision_source≠rule`일 때 발행 | 의도, 수단, 테이블 버전 | 위반 건수(=0) | 전수 |
| 선택 후 검증 | `ui.validate` (부모 `ui.map`) — [03](03-component-registry-schema.md) 소유. 여기서는 `agent.component` × `agent.decision_source` 교차 집계 | `failure_code` | 선택 후 스키마 실패율(수단별) | 전수 |
| 사용자 수정·무시 | 클라이언트 `ui.event {type}`(인라인 수정·재표현 요청)의 `agent.target`(컴포넌트 인스턴스 ID) → 원 `ui.render` → 원 `ui.map` 역조인. 무시는 "UI 표시 후 상호작용 없이 다음 `turn`" 배치 조인 | 인스턴스 ID, 다음 턴 의도 | 사용자 수정률·무시율(컴포넌트·수단별) → ③ 과업 층 | 이벤트 전수, 조인은 배치 |
| 테이블 로드 | 이벤트 `ui.map.table_load` (프로세스 기동·리로드 시) | 테이블 버전, 결과, 캐시 사용 여부 | 로드 실패 건수, 캐시 저하 지속 시간 | 전수 |

| 알림 | 조건 (예시) | 심각도 | 런북 (첫 3단계) |
|---|---|---|---|
| 결정 모델 다운·지연 | 오류율 > 예시 10% 또는 p95 > 지연 예산, 5분 | P2 | ① 서킷 열림·`decision_source=rule` 비율 급증으로 폴백 확인 ② 벤더 상태 ③ 장기화 시 LLM 툴 호출로 수단 전환 |
| 오선택 급증 | 수정률 > 예시 15%(1일) 또는 골든셋 일일 정확도 −5%p | P2 | ① 혼동 쌍 상위 ② 모델·프롬프트·테이블 버전 변경 확인 ③ θ 상향(보수적 방향만)·규칙 행 임시 고정 → 롤백 안건 |
| 보정 드리프트 | ECE 기준선 2배 또는 확신도 분포 이동이 통계적으로 유의(일 단위) | P3 | ① 모델 버전 변경 여부 ② 보정 곡선 재측정 ③ 재보정 전까지 규칙 행 확대 |
| 행동 의도 불변식 위반 | `ui.map.invariant_violation` ≥ 1건 | **P1** | ① 해당 트레이스·테이블 행 확인 ② 응답 차단 확인(승인 카드는 폴백 불가) ③ 테이블 핫픽스 |
| 테이블 로드 실패 | 로드 실패 또는 캐시 저하 > 예시 10분 | **P1** | ① 카탈로그 버전 불일치 확인 ② 설정 저장소 상태 ③ 마지막 정상 버전 재배포 |

**대시보드에서 이 단계를 보는 뷰**: ① E2E 폴백율의 `low_confidence` 원인 / ② Interaction 패널의 "선택 수단 분포·확신도 히스토그램·수정률" — 같은 패널이 1/07 대시보드 ③(판정 분포)에도 나타난다.
**감사 추적으로 넘기는 필드(관측 로그와 분리)**: 의도, 데이터 형태 요약, 문맥, 후보 집합, 수단, 선택 컴포넌트, 확신도와 θ, 폴백 여부·원인, 테이블·카탈로그·모델 버전.
**이 단계의 관측이 없으면 못 보는 장애**: 보정 붕괴. 폴백률은 "정상 범위" 안에서 서서히 이동하므로 `agent.confidence` 히스토그램 없이는 모델 교체 수 주 뒤 "UI가 예전보다 덜 뜬다"는 인상만 남는다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | 매핑 자체는 등급 1. 단 `requires_approval` 의도의 매핑은 **승인 카드 미표시 = 승인 없는 실행 위험**이므로 행동 등급을 상속하고 규칙으로만 판정 |
| 가드레일 위치 | **출력**: `ui_intent` 스키마 검증과 "행동 의도 → 규칙 수단" 불변 검사. **행동**: 없음(승인 카드 선택은 여기, 승인 처리는 [04](04-streaming-state-sync.md)·[06](06-hitl-ui-patterns.md)) |
| 게이트 출력과 판정 수단 | 확정(통과) / 텍스트 폴백(저하) / 선택지 제시(사용자에게 질문 — 승인이 아니라 명확화) / 차단(행동 의도가 확률 행에 걸린 경우). 판정 수단은 규칙 → 결정 모델 → LLM 순, 보안·권한 조건은 규칙만 |
| 소유자 (A) | 매핑 테이블: 제품 책임자(의도별 UI 결정) + 디자인 책임자. θ·수단: AI 엔지니어. R: AI 엔지니어 |
| 감사 추적에 남길 필드 | 의도, 데이터 형태 요약, 문맥, 후보 집합, 선택 수단, 선택 컴포넌트, 확신도와 θ, 폴백 여부·원인, 테이블·카탈로그·모델 버전 |

### 운영 준비도 체크
- [ ] 매핑 테이블이 코드 밖 설정으로 버전 관리되고 카탈로그 버전에 묶여 있는가
- [ ] 행동 의도 행이 모두 규칙 수단인지 CI가 검사하는가
- [ ] 결정 모델 장애 시 규칙 기본값 → 텍스트 전환이 서킷 브레이커로 자동화돼 있는가
- [ ] 골든셋 샘플이 매일 재실행되어 선택 정확도 SLI가 나오는가
- [ ] 모델 교체 절차에 섀도 → 골든셋 회귀 → θ 재보정 → 카나리가 명시돼 있는가
- [ ] 사용자 수정률·무시율 급등 알림과 "θ 상향·규칙 고정" 런북이 있는가
- [ ] 트레이스에 수단·확신도·θ·버전이 남아 과거 선택을 재현할 수 있는가
- [ ] 확신도 히스토그램·ECE가 일 단위로 집계되고 분포 이동 알림이 있는가
- [ ] 행동 의도 불변식 위반이 `ui.map.invariant_violation` 이벤트로 발행되어 P1 알림을 내는가
