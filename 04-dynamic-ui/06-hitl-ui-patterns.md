# Human-in-the-Loop UI 패턴

> **범위**: 승인 / 수정 / 피드백 루프 UI 패턴. 사람이 에이전트 루프에 개입하는 지점마다 어떤 UI 패턴을 쓰고, 각 패턴이 어떤 사용자 이벤트(계약 ③, [04](04-streaming-state-sync.md))를 만드는지. **언제** 사람 승인이 필요한지의 판정(게이팅)은 [Part 3/12](../03-agent-workflow-rag/12-guardrails-hitl.md)의 책임이며 여기서는 다루지 않는다. citation은 [Part 2/08](../02-data-pipeline/08-grounding-data-design.md)의 근거 단위 스키마를 **그대로** 렌더한다.
> **시각화**: [`assets/html/genui-streaming-sequence.html`](../assets/html/genui-streaming-sequence.html) — 사용자 승인 이벤트 → 서버 검증 → 실행 구간

## 요약 (3줄)

1. HITL(Human-in-the-Loop) UI는 여덟 패턴으로 거의 덮인다 — 승인 카드, 인라인 수정, diff 뷰, 선택지 제시, 피드백 캡처, citation 렌더, 진행 상태, 타임아웃·에스컬레이션. 각 패턴은 **하나의 사용자 이벤트 유형**에 대응한다.
2. HITL UI는 전부 **Controlled**로 고정한다. 승인 버튼을 에이전트가 생성한 트리 안에 두면 [08](08-security-sandboxing.md)의 권한 재검증과 [10](10-evaluation-genui.md)의 테스트가 불가능해진다.
3. 좋은 HITL UI의 기준은 "사람이 **무엇을 승인하는지 정확히 알고** 누를 수 있는가"다. 실행될 행동, 영향 범위, 근거, 되돌릴 수 있는지를 카드 안에서 보여줘야 승인이 의미 있다. 보이지 않는 것을 승인하게 하면 승인은 형식이 된다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① Part 3/12가 정의한 개입 지점마다 배정된 UI 패턴 ② 패턴별 컴포넌트(카탈로그 항목)와 이벤트 스키마 ③ 타임아웃·에스컬레이션 정책의 UI 표현 ④ citation 렌더 규칙 |
| **언제** (When) | 에이전트가 **행동**(툴 실행, 데이터 변경, 외부 전송)을 하거나, 출력이 **근거**를 요구하거나, 사용자 **피드백**으로 개선 루프를 돌릴 때. 순수 읽기 QA라면 citation 렌더와 피드백 캡처만 |
| **어떻게** (How) | ① Part 3/12의 게이팅 결과(승인 필요 / 확인 필요 / 자동)를 입력으로 받아 → ② 개입 유형별 패턴 배정 → ③ 각 패턴의 컴포넌트를 카탈로그에 등록(`actions` 포함) → ④ 이벤트 스키마를 계약 ③에 맞춤 → ⑤ 타임아웃·에스컬레이션 정책의 UI 상태 정의 → ⑥ 승인 카드의 "무엇을 승인하나" 내용 기준 수립 |
| **왜** (Why) | 패턴 없이 만들면 ① 승인 카드마다 모양·버튼 위치가 달라 사용자가 반사적으로 누르게 되고 ② 이벤트 스키마가 제각각이라 상태 머신 입력으로 변환할 수 없으며 ③ 타임아웃 시 UI가 멈춘 채 에이전트는 다른 경로로 가 있다 |

## 문제와 맥락

에이전트가 자율성을 가질수록 사람의 개입 지점은 **적어지되 중요해진다**. 100번의 자동 처리 사이에 끼는 1번의 승인은, 그 1번이 환불·배포·삭제이기 때문에 존재한다. 그런데 그 1번의 UI가 "확인 / 취소" 두 버튼뿐이면 사용자는 무엇을 승인하는지 모른 채 누른다. 반대로 매번 장황한 승인을 요구하면 사용자는 읽지 않고 누른다(승인 피로). HITL UI 설계는 **드문 개입을 의미 있게** 만드는 일이다.

## 핵심 개념

### 여덟 패턴

| 패턴 | 개입 유형 | 보여줄 것 | 사용자 이벤트 `type` | 통제 수준 |
|---|---|---|---|---|
| **① 승인 카드** (실행 전) | 행동 허가 | 실행될 행동(툴·인자 요약), 영향 범위(대상·금액·건수), 근거(citation), 되돌릴 수 있는지, 승인 안 하면 어떻게 되는지 | `approval` / `rejection` | Controlled 고정 |
| **② 인라인 수정** | 값 교정 | 에이전트가 채운 값(폼 필드·인자)을 편집 가능하게. 원래 값과 수정 표시 | `edit` | Controlled 고정 |
| **③ diff 뷰** | 변경 검토 | 변경 전/후 나란히 또는 인라인. 코드·문서·설정·데이터 레코드 | `approval` / `edit` | Controlled 고정 |
| **④ 선택지 제시** | 명확화 | 에이전트가 확신하지 못하는 분기(2~5개)를 버튼·카드로. "둘 다 아님" 포함 | `selection` | Controlled 고정 |
| **⑤ 피드백 캡처** | 품질 신호 | 좋아요/싫어요 + 수정 이유(닫힌 선택지: 틀림 / 근거 없음 / 형식 부적절 / 기타) | `feedback` | Controlled 고정 |
| **⑥ citation 렌더** | 근거 확인 | 출처(문서·위치·버전·시점), 신뢰도 등급, 하이라이트(답변의 어느 부분이 어느 근거에서 왔는지) | 없음(읽기) 또는 `feedback`(근거 틀림) | Controlled 고정 |
| **⑦ 진행 상태** | 대기·관찰 | 현재 단계, 완료/남은 단계, 지금 호출 중인 툴, 예상 소요(있다면), 취소 버튼 | `cancel` | Controlled 고정 |
| **⑧ 타임아웃·에스컬레이션** | 무응답 처리 | 남은 시간, 만료 시 기본 동작(보수적 — 실행 안 함), 다른 사람에게 넘기기 | `approval` (대리) / 시스템 이벤트 | Controlled 고정 |

### 승인 카드의 내용 기준

승인 카드는 HITL의 중심이다. 다음이 **카드 안에서** 보여야 한다. 링크를 눌러야 보이면 사용자는 안 본다.

1. **행동**: 사람이 읽을 수 있는 한 문장("고객 u_1에게 12,000원 환불") + 접힌 상세(툴 이름·인자)
2. **영향 범위**: 대상 수, 금액, 되돌릴 수 있는지(가역/비가역 배지)
3. **근거**: 왜 이 행동을 제안하는지. citation 렌더(⑥)를 카드 안에 포함
4. **확신도**: Part 3/12의 게이팅이 결정 모델 확신도를 썼다면 그 값과 임계값 `[2차]` — 사용자가 "에이전트도 애매해한다"를 알 수 있게
5. **대안**: 거절 외의 선택(수정 후 승인 → ②, 다른 사람에게 → ⑧)
6. **기본 동작**: 아무것도 안 하면 어떻게 되는지(타임아웃 정책)

### 패턴별 이벤트 스키마 (계약 ③의 `payload`)

모든 이벤트는 [04](04-streaming-state-sync.md)의 공통 봉투(`event_id`, `idempotency_key`, `run_id`, `type`, `target`, `user`, `issued_at`, `client_state_seq`)를 쓰고 `payload`만 패턴별로 다르다.

```json
// ① 승인 카드
{ "type": "approval",  "payload": { "action_id": "act_refund_3", "as_shown_hash": "sha256:..." } }
{ "type": "rejection", "payload": { "action_id": "act_refund_3", "reason_code": "wrong_amount", "comment": "..." } }

// ② 인라인 수정 → 승인
{ "type": "edit", "payload": { "action_id": "act_refund_3", "field": "amount", "from": 12000, "to": 10000 } }

// ③ diff 뷰 (승인 또는 부분 수락)
{ "type": "approval", "payload": { "change_id": "chg_9", "hunks_accepted": ["h1", "h3"], "hunks_rejected": ["h2"] } }

// ④ 선택지 제시
{ "type": "selection", "payload": { "question_id": "q_2", "option_id": "opt_b" } }   // "none" 허용

// ⑤ 피드백
{ "type": "feedback", "payload": { "rating": -1, "reason_code": "no_evidence", "citation_id": "ev_17" } }

// ⑦ 진행 상태 — 취소
{ "type": "cancel", "payload": { "step_id": "step_4", "reason_code": "user_abort" } }
```

`as_shown_hash`는 사용자가 **본 내용**의 해시다. 서버는 현재 행동 정의의 해시와 비교해, 카드가 뜬 뒤 인자가 바뀌었으면 승인을 거부한다. `client_state_seq`와 함께 "오래된 화면에서의 승인"을 막는 두 번째 장치다.

### citation 렌더 — Part 2/08 스키마 그대로

UI 레이어는 근거 형식을 **재해석하지 않는다**. 근거 단위에 있는 필드(근거 ID, 본문 또는 트리플, 출처 — 문서·위치·버전·시점, 권한 태그, 신뢰도 등급)를 그대로 표시한다.

| 필드 | 렌더 |
|---|---|
| 출처(문서·위치) | 제목 + 위치(페이지·섹션·행) 링크. 권한 태그가 사용자 권한 밖이면 "접근 불가 근거 N건"으로만 |
| 버전·시점 | 문서 버전과 기준 시각. 오래된 근거는 배지 |
| 신뢰도 등급 | Part 2/08의 등급 어휘 그대로 배지. UI가 새 등급을 만들지 않는다 |
| 하이라이트 | 답변 문장 ↔ 근거 구간을 연결. 호버·포커스 시 양쪽 강조 |
| 근거 없음 | 답변 중 근거가 없는 문장은 **없다고 표시**. 숨기지 않는다 |

### 진행 상태와 타임아웃

- 진행 상태(⑦)는 [04](04-streaming-state-sync.md)의 생명주기·툴 호출 이벤트에서 파생된다. 별도 상태를 만들지 않는다
- 타임아웃(⑧)의 기본 동작은 **보수적**이다 — 만료되면 실행하지 않는다. "만료 시 자동 승인"은 승인이 아니다
- 에스컬레이션은 승인 대상을 다른 사람에게 넘기는 것이며, 넘겨받은 사람의 승인 이벤트는 `user`가 다르고 `payload`에 `delegated_from`이 있다. 권한 검증은 넘겨받은 사람 기준

## 아키텍처 / 파이프라인

입력은 Part 3/12의 게이팅 결과(승인 필요 여부, 확신도, 행동 정의)와 Part 2/08 근거 단위다. 처리는 패턴 배정 → 카탈로그 컴포넌트 선택([05](05-intent-to-ui-mapping.md)의 규칙 행) → 렌더. 출력은 사용자 이벤트(계약 ③)이며 [04](04-streaming-state-sync.md)의 서버 재검증을 거쳐 Part 3 상태 머신에 들어간다. 피드백 이벤트는 [10](10-evaluation-genui.md)과 Part 3/13의 골든셋 환류로도 간다.

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| **승인 카드** (행동 요약 + 근거 + 가역성) | 비가역·고액·외부 전송 행동, 감사 대상 | 저위험 반복 행동(승인 피로 유발) — 자동 + 사후 알림으로 | 중 — 행동 요약 생성·해시 검증 | 안정 (패턴) | — 실무 관행 |
| **인라인 수정** | 에이전트가 채운 값에 오류 가능성, 사용자가 도메인을 잘 앎 | 수정 가능한 필드가 수십 개(폼으로 전환) | 중 | 안정 | — |
| **diff 뷰** | 코드·문서·설정 변경, 부분 수락 필요 | 구조화 안 된 긴 텍스트의 미세 변경(노이즈) | 중 — diff 알고리즘·헝크 단위 이벤트 | 표준 (코드 리뷰 도구 관행) | — |
| **선택지 제시** | 확신도 낮은 분기, 명확화 질문 | 선택지 6개 이상(검색·필터로), 열린 질문 | 하 | 안정 | — |
| **피드백 캡처** (닫힌 이유 코드) | 모든 응답. 골든셋 환류 | 자유 텍스트만 받기(집계 불가) | 하 | 표준 | `[2차]` 평가 관행 |
| **citation 렌더** (Part 2/08 스키마) | 근거 기반 답변 전부 | 근거 스키마가 아직 없음(먼저 Part 2/08) | 하~중 | 안정 | — |
| **진행 상태** | 수 초 이상 실행, 다단계 | 1초 미만 응답(깜빡임) | 하 | 표준 | — |
| **타임아웃·에스컬레이션** | 승인 대기가 업무 흐름을 막음, 담당자 부재 | 승인자가 항상 즉시 응답 | 중 — 정책·대리 권한 | 안정 (워크플로우 도구 관행) | — |
| **채팅 텍스트로 승인** ("예"라고 입력) | 프로토타입 | 운영 — 이벤트 스키마·멱등성·해시 검증 불가 | 하 | 해당 없음 | — |

### 선택 가이드

- **행동이 비가역이거나 금전·외부 전송이라면** → 승인 카드 + citation 포함 + `as_shown_hash`. 이유: 승인의 의미는 "본 것을 허가"하는 데 있다
- **에이전트가 채운 값이 틀릴 수 있고 사용자가 고칠 수 있다면** → 인라인 수정 → 승인. 이유: 거절·재요청 왕복보다 한 번의 수정이 싸다
- **변경 대상이 코드·문서·설정이라면** → diff 뷰 + 헝크 단위 수락. 이유: 전체 승인/거절은 너무 거칠다
- **에이전트 확신도가 낮다면** → 선택지 제시. 이유: 틀린 UI를 띄우는 것보다 묻는 것이 싸다([05](05-intent-to-ui-mapping.md) 폴백)
- **판단이 어려우면** → citation 렌더 + 피드백 캡처부터. 이유: 모든 시스템에 필요하고, 피드백이 쌓여야 나머지 패턴의 필요성이 보인다

## 설계 시 고려사항 (체크리스트)

- [ ] Part 3/12의 개입 지점마다 패턴이 배정되어 있는가. 배정 없는 지점이 없는가
- [ ] HITL 컴포넌트가 모두 Controlled(카탈로그 등록, 에이전트 생성 트리 밖)인가
- [ ] 승인 카드에 행동·영향 범위·근거·가역성·기본 동작이 **카드 안에** 보이는가
- [ ] 승인 이벤트에 `as_shown_hash`가 있고 서버가 대조하는가
- [ ] 거절·피드백의 이유가 닫힌 코드인가(집계 가능)
- [ ] citation 렌더가 Part 2/08 필드를 그대로 쓰고 새 등급·형식을 만들지 않는가
- [ ] 근거 없는 문장이 숨겨지지 않고 표시되는가
- [ ] 권한 밖 근거가 내용 노출 없이 건수로만 표시되는가 ([Part 2/10](../02-data-pipeline/10-access-control-governance.md))
- [ ] 타임아웃 기본 동작이 "실행 안 함"인가
- [ ] 에스컬레이션 시 권한 검증이 넘겨받은 사람 기준인가
- [ ] 저위험 반복 행동은 승인 대신 자동 + 사후 알림으로 승인 피로를 줄였는가
- [ ] 승인 카드가 키보드만으로 조작 가능하고 기본 포커스가 "승인"이 아닌가 ([09](09-ux-accessibility.md))

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 승인 피로 | 사용자가 읽지 않고 승인 → HITL이 형식화 | 게이팅 임계값 조정(Part 3/12), 저위험은 자동화, 카드 내용 압축 |
| 카드 표시 후 행동 정의 변경 | 본 것과 다른 것이 실행 | `as_shown_hash` + `client_state_seq` 검증 |
| 사람이 승인해도 틀릴 수 있음 | HITL이 정확성을 보장하지 않음 | 규칙 게이트(한도·권한)는 승인과 **별도로** 유지 |
| 피드백 희소·편향 | 불만족 사용자만 누름 | 샘플링 요청, 암묵 신호(수정·폴백) 병행 |
| citation 스키마 미확정 (Part 2/08 진행 중) | 렌더 규칙이 바뀔 수 있음 | 필드 어휘를 Part 2/08에서만 가져오고 UI에서 정의하지 않음 |
| 타임아웃 정책과 업무 흐름 충돌 | 실행 안 함이 기본이면 업무 지연 | 에스컬레이션 경로, 대기 중 상태 가시화 |
| 모바일에서 diff·비교 공간 부족 | 패턴이 작동하지 않음 | 플랫폼별 규칙([05](05-intent-to-ui-mapping.md))으로 요약 카드로 대체 |
