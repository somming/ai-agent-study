# UX와 접근성

> **범위**: 생성형 UI의 UX 원칙, 접근성, 일관성 유지. 에이전트가 고르거나 만든 UI가 **사람에게 쓸 만한가**를 다룬다 — 일관성, 로딩·실패·부분 결과 상태, 접근성 트리, 다국어·RTL, 모션·과잉 UI 억제, 사용자 통제감. 컴포넌트 구현 세부는 [07](07-frontend-integration.md), 측정은 [10](10-evaluation-genui.md).
> **시각화**: 해당 없음 — 이 페이지는 원칙·체크리스트 중심. 전체 흐름은 [`assets/html/dynamic-ui-architecture.html`](../assets/html/dynamic-ui-architecture.html)

## 요약 (3줄)

1. Generative UI의 UX 문제는 "예쁜가"가 아니라 **"예측 가능한가"** 다. 같은 의도에 같은 UI가 나와야 사용자가 학습하고, 에이전트가 무엇을 하는 중인지 보여야 기다릴 수 있으며, 실패가 실패로 보여야 신뢰가 유지된다.
2. 접근성은 Controlled에서는 컴포넌트에 구현된 만큼 자동으로 따라오지만, Declarative·Open-ended에서는 **생성된 트리마다 다시 검증**해야 한다. 자유도가 접근성을 깎는 속도는 디자인 일관성을 깎는 속도와 같다.
3. "에이전트가 UI를 만들 수 있다"는 "만들어야 한다"가 아니다. 텍스트로 충분한 답에 카드·차트·애니메이션을 얹는 **과잉 UI**는 사용자 통제감을 떨어뜨린다. 기본값은 가장 단순한 표현이다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 일관성 규칙(의도→UI 매핑의 결정론 보장) ② 상태 표현 규칙(로딩·부분·실패·완료·취소) ③ 접근성 기준과 생성 UI 검증 절차 ④ 다국어·RTL 정책 ⑤ 모션·UI 밀도 상한 ⑥ 사용자 통제 수단(취소·텍스트 전환·되돌리기) |
| **언제** (When) | 카탈로그([03](03-component-registry-schema.md)) 설계와 동시에 — 컴포넌트의 `a11y` 필드와 상태 variant가 여기서 정해진다. 접근성 법규·사내 기준이 있으면 통제 수준 결정([01](01-generative-ui-spectrum.md)) 전에 읽는다 |
| **어떻게** (How) | ① 접근성 기준 확정(WCAG 2.x 수준, 사내 기준) → ② 컴포넌트마다 상태 variant(로딩·빈·오류·부분) 정의 → ③ 매핑 결정론 확인(같은 입력 → 같은 컴포넌트) → ④ 생성 트리 접근성 검증기(헤딩 순서·라벨·포커스 흐름) → ⑤ 다국어·RTL 토큰·레이아웃 규칙 → ⑥ 모션 축소 대응, UI 밀도 상한 → ⑦ 취소·텍스트 전환·되돌리기 제공 → ⑧ [10](10-evaluation-genui.md)의 자동 검사 + 사용자 테스트 |
| **왜** (Why) | 일관성 없는 UI는 매번 새로 배워야 하는 UI다. 상태가 안 보이면 사용자는 멈춘 건지 기다리는 건지 모른다. 접근성이 없으면 일부 사용자에게는 UI가 **없는 것과 같고** 법규 위반이 된다. 과잉 UI는 "에이전트가 내 말을 못 알아듣고 쇼를 한다"는 인상을 준다 |

## 문제와 맥락

채팅 UI는 단조로웠지만 예측 가능했다. 텍스트가 위에서 아래로 쌓인다. Generative UI는 그 예측 가능성을 깨뜨린다 — 어떤 때는 표, 어떤 때는 카드, 어떤 때는 텍스트. 사용자는 화면이 어떻게 반응할지 모르게 된다. 게다가 UI가 **스트리밍으로 조립**되므로 읽는 도중 레이아웃이 바뀌고, 에이전트가 수십 초 동안 무언가를 하는 동안 화면은 멈춘 것처럼 보일 수 있다. 접근성 측면에서는 스크린 리더가 동적으로 삽입되는 영역을 어떻게 읽어야 하는지, 키보드 사용자가 새로 나타난 승인 카드에 어떻게 도달하는지가 전통 웹보다 어렵다.

## 핵심 개념

### 일관성 — 같은 의도에 같은 UI

| 수준 | 규칙 | 구현 위치 |
|---|---|---|
| 매핑 결정론 | 같은 (의도·데이터 형태·문맥)에는 같은 컴포넌트. 확률 수단을 썼더라도 운영 중 **같은 입력에 다른 결과**가 나오면 결함 | [05](05-intent-to-ui-mapping.md) 매핑 테이블, 규칙 우선 |
| 컴포넌트 안정성 | 한 세션 안에서 같은 컴포넌트는 같은 위치·크기·동작 | 카탈로그 variant 고정 |
| 어휘 일관성 | 버튼 라벨·상태 문구가 컴포넌트마다 다르지 않게 | 디자인 시스템 문구 토큰 |
| 레이아웃 안정성 | 스트리밍 중 이미 보인 요소가 밀리거나 이동하지 않음 | 스켈레톤 자리 확보, 아래로만 추가([04](04-streaming-state-sync.md)) |

Declarative에서 일관성은 가장 깨지기 쉽다. 에이전트가 매번 다른 트리를 만들기 때문이다. 완화는 **레이아웃 템플릿**(허용 배치를 몇 가지로 닫음)과 생성 결과를 캐시해 같은 입력에 재사용하는 것이다.

### 상태 표현 — 로딩 · 부분 · 실패 · 완료 · 취소

| 상태 | 보여줄 것 | 하지 말 것 |
|---|---|---|
| **로딩** | 무엇을 하는 중인지(툴 이름을 사람 말로), 진행 단계, 취소 버튼. 수 초 이상이면 예상 시간(있을 때만) | 스피너만. "생각 중..." 같은 의인화 문구만 |
| **부분 결과** | 도착한 항목부터 표시, 아직 오는 중임을 표시(마지막 행 스켈레톤) | 전부 도착할 때까지 빈 화면 |
| **실패** | 무엇이 실패했고 사용자가 할 수 있는 것(재시도·텍스트로 보기·다른 질문). 부분 성공이면 성공한 부분 유지 | 에러 코드만. 전체를 지우고 "오류가 발생했습니다" |
| **폴백** | UI 대신 텍스트가 나왔음을 **알린다**("표로 표시할 수 없어 목록으로 보여드립니다") | 조용히 텍스트만 (사용자는 왜 다른지 모름) |
| **완료** | 완료됨을 명시, 다음 가능한 행동 | 완료와 로딩이 구분 안 되는 화면 |
| **취소** | 취소됨, 어디까지 진행됐는지, 되돌릴 것이 있는지 | 취소 버튼이 있는데 눌러도 반응 없음 |

상태는 [04](04-streaming-state-sync.md)의 생명주기·툴 호출 이벤트에서 파생된다. 컴포넌트마다 상태 variant를 카탈로그에 정의해 두면 매핑이 상태를 따로 고민하지 않아도 된다.

### 접근성 트리

Controlled 컴포넌트는 구현 시점에 접근성을 갖춘다(역할·라벨·키보드·대비). 문제는 **동적 삽입**과 **생성 트리**다.

| 과제 | 대응 |
|---|---|
| 새로 나타난 UI를 스크린 리더가 알게 | 라이브 영역(`aria-live`)으로 요약 알림. 전체 표를 읽히지 말고 "비교표 3개 상품이 표시됨" 수준. 승인 카드처럼 즉시 행동이 필요한 것은 `assertive`, 나머지는 `polite` |
| 키보드 사용자가 새 UI에 도달 | 승인 카드 등장 시 포커스를 카드로 이동하되, 기본 포커스는 **"승인"이 아닌** 요소(설명 또는 "자세히")에. 스트리밍 중 포커스를 뺏지 않는다 |
| 생성 트리(Declarative)의 구조 | 헤딩 레벨 순서, 모든 상호작용 요소의 접근 가능한 이름, 표의 헤더 셀, 이미지 대체 텍스트를 **렌더 전 검증**. 실패 시 폴백 |
| 토큰 델타 스트리밍 | 글자 단위로 읽히지 않게 문장·문단 단위로 라이브 영역 갱신 |
| iframe(Open-ended) | 접근성 트리가 분리됨. iframe에 `title`, 포커스 진입·탈출 경로, 내부 접근성은 보장 불가 → 사용자에게 고지 |
| 색만으로 의미 전달 금지 | 신뢰도 등급·상태 배지에 텍스트·아이콘 병행 |

기준은 WCAG 2.x `[검증]`와 WAI-ARIA `[검증]`를 따른다. 생성 UI라고 해서 기준이 달라지지 않는다. 다만 **검증 시점**이 빌드 타임에서 **런타임**으로 옮겨진다는 것이 차이다.

### 다국어 · RTL

- 컴포넌트 문구는 토큰(키)으로, 에이전트는 문구를 만들지 않는다. 에이전트가 만든 텍스트(답변 본문)와 UI 크롬(버튼·라벨)을 분리
- 길이 변화(한국어 ↔ 영어 ↔ 독일어)에 레이아웃이 깨지지 않게 — 고정 너비 버튼 금지
- RTL(아랍어·히브리어)은 논리적 속성(start/end)으로 레이아웃. Declarative 트리의 배치 속성도 논리 방향으로
- 숫자·날짜·통화 형식은 로케일로. 에이전트가 "12,000원"을 텍스트로 만들면 UI는 그것을 **다시 파싱하지 않는다** — 구조화 값(`amount: 12000, currency: KRW`)을 받아 UI가 형식화
- 한국어 특성: 조사 처리("을/를")가 필요한 템플릿 문구는 토큰 쪽에서 해결, 에이전트 출력에 의존하지 않음

### 모션 · 과잉 UI 억제

- `prefers-reduced-motion`을 존중. 스트리밍 글자 애니메이션·카드 슬라이드는 기본 꺼짐 또는 축소
- **UI 밀도 상한**: 한 응답에 컴포넌트 N개 이하(카탈로그·플랫폼별로 정함). 넘으면 요약 + "더 보기"
- **텍스트 우선 규칙**: 매핑 테이블([05](05-intent-to-ui-mapping.md))에서 "텍스트로 충분한가"를 먼저 묻는다. 항목 1개에 비교표, 숫자 하나에 차트는 과잉
- 의인화 과잉 금지: "열심히 찾고 있어요!" 류 문구보다 "주문 내역 조회 중(2/3)"

### 사용자 통제감

| 통제 수단 | 설명 |
|---|---|
| 취소 | 실행 중 언제든. 취소 후 상태가 보임([06](06-hitl-ui-patterns.md) ⑦) |
| 텍스트로 전환 | 어떤 UI든 "텍스트로 보기"가 가능. 폴백을 사용자가 선택 |
| 되돌리기 | 수정·선택은 되돌릴 수 있고, 되돌릴 수 없는 것은 **사전에** 표시(가역성 배지) |
| 왜 이 UI인가 | 선택적으로 "왜 표로 보여주나요?" → 매핑 근거 한 줄. 결정 모델 확신도가 있으면 활용 가능 `[2차]` |
| 설정 | UI 밀도·모션·기본 표현(텍스트 선호)을 사용자가 조정 |

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| **Controlled 컴포넌트에 접근성 내장** (빌드 타임 보장) | 모든 Controlled 영역 | Declarative·Open-ended 영역(해당 없음) | 중 — 일반 프론트 접근성 작업 | 표준 | `[검증]` WCAG·ARIA |
| **런타임 접근성 트리 검증기** (헤딩·라벨·포커스) | Declarative 생성 트리 | Controlled만(과잉) | 중~상 — 검증기 유지, 폴백 연결 | 신생 (생성 UI 맥락) | — |
| **자동 접근성 검사 도구** (axe 류, CI·E2E) | 모든 영역의 회귀 검사 | 검사 도구가 못 잡는 의미적 문제(라벨이 있지만 틀림) | 하~중 | 안정 | `[2차]` 도구 문서 |
| **레이아웃 템플릿** (허용 배치 닫기) | Declarative 일관성 | Controlled(이미 고정) | 중 | 안정 (디자인 시스템 관행) | — |
| **라이브 영역 요약 알림** | 동적 삽입 전부 | — | 하 | 표준 | `[검증]` ARIA |
| **UI 밀도 상한·텍스트 우선 규칙** | 전부 | — | 하 | 안정 (관행) | — |
| **사용자 테스트** (장애 사용자 포함) | 운영 전, 큰 변경 시 | 전수 | 상 | 표준 | — |
| **생성 UI에 접근성 검증 없음** | 프로토타입 | 운영 | 하 | 해당 없음 | — |

### 선택 가이드

- **Controlled만 쓴다면** → 컴포넌트 접근성 내장 + 라이브 영역 알림 + 자동 검사 CI. 이유: 빌드 타임에 끝나고 런타임 검증기가 필요 없다
- **Declarative를 쓴다면** → 레이아웃 템플릿 + 런타임 접근성 검증기 + 폴백. 이유: 트리가 매번 다르므로 런타임에 확인하는 수밖에 없다
- **법규·조달 요건(공공·금융)이 있다면** → 기준 수준을 먼저 확정하고 통제 수준을 그에 맞춘다(사실상 Controlled). 이유: 생성 UI의 접근성 보장은 아직 검증된 방법이 없다
- **다국어 서비스라면** → 문구 토큰 분리 + 구조화 값 형식화. 이유: 에이전트 출력 텍스트를 UI가 파싱하면 로케일마다 깨진다
- **판단이 어려우면** → 텍스트 우선 + 밀도 상한 + Controlled 접근성 내장. 이유: 가장 적은 UI가 가장 접근 가능하고 가장 일관된다

## 설계 시 고려사항 (체크리스트)

- [ ] 같은 (의도·데이터 형태·문맥)에 같은 컴포넌트가 나오는 것이 테스트로 확인되는가
- [ ] 스트리밍 중 이미 보인 요소가 이동하지 않는가(스켈레톤 자리 확보)
- [ ] 로딩 상태가 "무엇을 하는 중인지"와 취소 버튼을 보여주는가
- [ ] 실패·폴백 시 사용자가 할 수 있는 행동과 폴백 사실이 표시되는가
- [ ] 부분 성공 시 성공한 부분이 유지되는가
- [ ] 새 UI 등장을 라이브 영역으로 요약 알림하는가. 승인 카드만 `assertive`인가
- [ ] 승인 카드의 기본 포커스가 "승인"이 아닌가. 스트리밍 중 포커스를 뺏지 않는가
- [ ] Declarative 트리에 렌더 전 접근성 검증(헤딩·라벨·표 헤더·대체 텍스트)이 있는가
- [ ] 색만으로 의미를 전달하는 배지가 없는가
- [ ] UI 크롬 문구가 토큰이고 에이전트가 만들지 않는가. 숫자·날짜·통화가 구조화 값으로 오는가
- [ ] RTL에서 Declarative 배치 속성이 논리 방향인가
- [ ] `prefers-reduced-motion`을 존중하는가
- [ ] 한 응답의 컴포넌트 수 상한이 있는가. 항목 1개에 표·차트가 나오지 않는가
- [ ] 어떤 UI든 "텍스트로 보기"가 가능한가
- [ ] 자동 접근성 검사가 CI·E2E에 있고 [10](10-evaluation-genui.md) 지표로 집계되는가

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 생성 UI 접근성의 검증된 방법론 부재 | 법규 요건을 Declarative·Open-ended로 충족한다는 보장 불가 | 요건 영역은 Controlled, 런타임 검증기 + 폴백 |
| 자동 검사의 한계 | 라벨이 있어도 틀린 라벨, 논리적 순서 오류를 못 잡음 | 사람 테스트 샘플링, 장애 사용자 참여 |
| 확률 수단의 비결정성 | 같은 입력에 다른 UI | 규칙 우선, 결과 캐시, 결정론 테스트 |
| 스트리밍과 스크린 리더의 충돌 | 글자 단위 낭독, 포커스 혼란 | 문단 단위 라이브 갱신, 포커스 정책 |
| iframe 접근성 트리 분리 | Open-ended 영역의 접근성 보장 불가 | 고지, 핵심 기능은 iframe 밖에 |
| 과잉 UI 유인 | "할 수 있으니 한다" | 텍스트 우선 규칙, 밀도 상한, 사용자 수정률 측정 |
| 한국어 조사·길이 특성 | 템플릿 문구 어색, 레이아웃 깨짐 | 토큰 측 조사 처리, 유동 너비 |
