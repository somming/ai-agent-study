# Generative UI 평가

> **범위**: UI 선택 정확도, 렌더 실패율, 사용자 과업 완료율 측정. Part 4의 각 단계가 "잘 된다"를 어떻게 측정하는지 — 오프라인(골든셋) 지표, 운영 지표, 접근성 자동 검사, A/B 설계. 평가 체계의 일반론(평가 4층, 골든셋 설계, 트레이싱)은 [Part 1/06](../01-foundations/06-evaluation-observability.md)을 전제로 하고 반복하지 않는다. RAG·에이전트 지표는 [Part 3/13](../03-agent-workflow-rag/13-evaluation-rag-agents.md).
> **시각화**: 해당 없음 — 지표 정의 중심. 평가 대상 흐름은 [`assets/html/dynamic-ui-architecture.html`](../assets/html/dynamic-ui-architecture.html)

## 요약 (3줄)

1. Generative UI 평가는 **네 층**이다 — ① 선택이 맞았나(의도→컴포넌트 골든셋), ② 렌더가 됐나(스키마 검증 실패율·렌더 실패율), ③ 과업이 끝났나(완료율·턴 수·수정률·폴백률), ④ 접근 가능한가(자동 검사). ①②는 결정론적으로 CI에서, ③은 운영에서, ④는 둘 다.
2. 가장 중요한 지표는 **과업 완료율과 사용자 수정률**이다. 선택 정확도가 높아도 사용자가 UI를 무시하고 텍스트로 다시 묻는다면 UI는 실패다. 단계 지표는 진단용, 과업 지표가 최상위다.
3. 이 Part는 성숙도가 낮아 **벤치마크·공개 데이터셋이 없다.** 모든 수치는 `[실측]`이다. 따라서 골든셋을 직접 만들고, 매핑 테이블([05](05-intent-to-ui-mapping.md))의 행이 곧 골든셋의 카테고리가 되게 한다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 의도→기대 컴포넌트 골든셋 ② CI 결정론 체크(스키마·카탈로그 대조·접근성) ③ 운영 지표 정의와 대시보드(완료율·턴 수·수정률·폴백률·렌더 실패율) ④ A/B 설계 템플릿 ⑤ 실패 사례 → 골든셋 환류 절차 |
| **언제** (When) | 카탈로그와 매핑 테이블 초안이 나온 **직후**, 컴포넌트 구현 전에 골든셋부터. Part 1/06의 "첫 프롬프트 전에 골든셋"과 같은 원칙. 텍스트 + citation만 쓰는 시스템은 ②의 citation 렌더 검사와 ③의 피드백만 |
| **어떻게** (How) | ① 매핑 테이블 행마다 골든셋 10건 이상(한국어·혼합·비격식 포함) → ② 선택 수단(규칙·결정 모델·LLM)을 같은 골든셋으로 비교 → ③ 스키마 검증·카탈로그 대조·접근성 검사를 CI 게이트로 → ④ 운영 지표를 트레이스에서 집계 → ⑤ A/B로 UI vs 텍스트, 패턴 vs 패턴 비교 → ⑥ 수정·폴백·불만 사례를 골든셋과 매핑 테이블에 환류 |
| **왜** (Why) | 평가 없이는 ① 카탈로그에 컴포넌트를 추가했을 때 기존 선택이 흔들렸는지 모르고 ② 결정 모델이 LLM보다 나은지 느낌으로 정하며 ③ "UI를 넣었더니 좋아졌다"를 증명할 수 없다. 특히 UI는 **없는 것이 나을 수도** 있으므로 텍스트 대비 비교가 없는 UI 도입은 가설일 뿐이다 |

## 문제와 맥락

RAG 평가에는 RAGAS 류 표준 지표와 공개 벤치마크가 있다. Generative UI에는 없다. 3패턴 프레이밍이 정리된 것이 최근이고 `[2차]`, 프로토콜은 v0.9 단계이며 `[벤더]`, 결정 모델을 UI 선택에 쓴 사례 보고는 드물다. 그래서 이 영역의 평가는 **직접 설계**해야 한다. 다행히 평가 구조는 Part 1/06의 4층(규칙 → 참조 → judge → 사람)을 그대로 쓸 수 있고, UI 특유의 지표 몇 개만 추가하면 된다.

## 핵심 개념

### 지표 체계

| 층 | 지표 | 정의 | 측정 시점 | 수단 |
|---|---|---|---|---|
| **① 선택** | UI 선택 정확도 | 골든셋 (의도·데이터·문맥) → 기대 컴포넌트와 실제 선택의 일치율 | 오프라인, CI | 참조 기반 |
| | 혼동 행렬 | 어느 컴포넌트 쌍이 서로 혼동되는가 | 오프라인 | 참조 기반 |
| | 보정 곡선 (ECE) | 결정 모델 확신도가 실제 정확도와 맞는가 | 오프라인 | 참조 기반, 결정 모델 사용 시 |
| | 결정론 | 같은 입력 N회 → 같은 선택 비율 | 오프라인 | 규칙 기반 |
| **② 렌더** | 스키마 검증 실패율 | `ui_intent`가 카탈로그 스키마를 통과하지 못한 비율 | CI + 운영 | 규칙 기반 |
| | 카탈로그 대조 실패 | 존재하지 않는 컴포넌트·props 호출 | CI + 운영 | 규칙 기반 |
| | 렌더 실패율 | 스키마는 통과했으나 렌더러에서 오류·빈 화면 | 운영(클라이언트 로그) | 규칙 기반 |
| | 폴백률 | 텍스트로 떨어진 비율(원인별: 확신도 낮음 / 스키마 실패 / 렌더 실패 / 미지원 플랫폼) | 운영 | 규칙 기반 |
| **③ 과업** | 과업 완료율 | 사용자가 목표(구매·승인·답 확인)에 도달한 비율 | 운영, A/B | 운영 로그 |
| | 턴 수 | 완료까지 사용자 발화 수. UI가 왕복을 줄였는가 | 운영, A/B | 운영 로그 |
| | 사용자 수정률 | UI 선택 후 사용자가 다른 표현을 요구("표 말고 목록으로")하거나 인라인 수정한 비율 | 운영 | 운영 로그 + 이벤트 |
| | UI 무시율 | UI가 떴지만 상호작용 없이 텍스트로 다시 질문한 비율 | 운영 | 운영 로그 |
| | 승인 처리 시간·거절률 | HITL 카드가 뜬 뒤 결정까지 시간, 거절 사유 분포 | 운영 | 이벤트 |
| | 명시 피드백 | 좋아요/싫어요, 이유 코드 분포 | 운영 | 이벤트 |
| **④ 접근성** | 자동 검사 위반 수 | WCAG 규칙 위반(컴포넌트·생성 트리) | CI + E2E | 규칙 기반(axe 류) |
| | 생성 트리 검증 실패율 | 런타임 접근성 검증기 불합격 → 폴백 비율 | 운영 | 규칙 기반 |
| | 키보드·스크린 리더 과업 완료 | 보조 기술 사용자의 완료율 | 사용자 테스트 | 사람 |

### 골든셋 — 의도 → 기대 컴포넌트

Part 1/06의 골든셋 구성에 UI 열을 추가한다.

| 필드 | 내용 |
|---|---|
| 입력 | 사용자 발화(한국어·혼합·비격식 포함), 직전 문맥 |
| 의도 | Part 3/02 분류 결과(또는 기대 의도) |
| 데이터 형태 | 응답에 담길 항목 수·속성·타입(합성 가능) |
| 문맥 | 플랫폼, 화면 크기, 권한, 직전 UI |
| **기대 컴포넌트** | 카탈로그 `name`. 복수 허용("표 또는 카드 리스트 모두 적절")이면 허용 집합 |
| **기대 폴백 여부** | 텍스트가 정답인 경우를 반드시 포함 — "UI 없음"도 정답 클래스 |
| 카탈로그 버전 | 골든셋이 유효한 버전 범위 |
| 작성자·날짜·출처 | 실 로그 / 전문가 / 합성 |

매핑 테이블([05](05-intent-to-ui-mapping.md))의 행마다 최소 10건, 특히 **경계 사례**(항목 6개 vs 7개, 확신도 임계값 근처)를 넣는다. 카탈로그에 컴포넌트를 추가·제거할 때 골든셋도 같은 PR에서 바뀐다.

### CI 결정론 체크

| 체크 | 실패 시 |
|---|---|
| 카탈로그 ↔ 컴포넌트 export 대조 (이름·props·version) | 배포 차단 |
| 골든셋 전수 → 스키마 검증 통과율 100% | 배포 차단 |
| 골든셋 선택 정확도가 이전 버전 대비 하락 | 배포 차단 또는 리뷰 |
| 결정론 테스트(같은 입력 N회) | 리뷰 |
| 컴포넌트 접근성 자동 검사 | 배포 차단(심각) / 리뷰(경미) |
| 생성 트리(Declarative) 샘플의 접근성 검증기 통과 | 리뷰 |

### A/B 설계

Generative UI의 A/B는 **"UI vs 텍스트"가 첫 실험**이다. UI가 없는 것보다 낫다는 것부터 증명한다.

| 실험 | 대조군 | 처치군 | 1차 지표 | 보조 지표 |
|---|---|---|---|---|
| UI 도입 | 텍스트 + citation | Controlled UI | 과업 완료율, 턴 수 | 수정률, 무시율, 피드백 |
| 선택 수단 | LLM 툴 호출 | 결정 모델 | 선택 정확도(오프라인 선행), 완료율 | 지연, 비용, 폴백률 |
| 패턴 | Controlled 고정 | 특정 의도만 Declarative | 완료율, 수정률 | 렌더 실패율, 접근성 위반 |
| 승인 카드 내용 | 최소 정보 | 영향 범위·근거 포함 | 거절 사유의 적절성, 처리 시간 | 사후 되돌림률 |

주의: 의도 유형별로 효과가 반대일 수 있으므로(비교 의도에는 표가, 단순 질문에는 텍스트가) **의도 유형으로 층화**한다. 전체 평균만 보면 상쇄되어 "효과 없음"으로 보인다.

### 운영 → 골든셋 환류

- 사용자 수정·무시·폴백·불만(피드백 이유 코드) 사례를 주기적으로 추출
- 사람이 "기대 컴포넌트"를 라벨 → 골든셋 추가
- 혼동 행렬에서 반복되는 쌍 → 카탈로그 `purpose`에 "쓰지 말아야 할 때" 보강, 또는 variant 통합([03](03-component-registry-schema.md))
- 폴백 원인 분포 → 자주 요구되는데 없는 컴포넌트 발견

## 아키텍처 / 파이프라인

```
개발 루프:  카탈로그·매핑 변경 ─▶ CI 결정론 체크 ─▶ 골든셋 선택 정확도 ─▶ 접근성 검사 ─▶ 배포 판단
운영 루프:  요청 ─▶ 트레이스(선택 수단·확신도·컴포넌트·검증 결과·렌더 결과·사용자 이벤트) ─▶ 지표 집계 ─▶ A/B 분석
                                                                                        └─▶ 수정·폴백·불만 사례 ─▶ 골든셋·매핑 테이블 환류
```

트레이스에는 Part 1/06의 항목에 더해 **선택 수단, 확신도, 선택된 컴포넌트, 카탈로그 버전, 검증 결과, 렌더 결과(클라이언트 보고), 사용자 이벤트**를 기록한다. 클라이언트 렌더 결과는 서버가 모르므로 프론트가 보고해야 한다.

| **CI 결정론 체크** (스키마·카탈로그·접근성) | 모든 시스템의 1층 | 의미 품질 | 하 | 표준 | `[검증]` |

| **A/B 테스트** (의도 유형 층화) | UI vs 텍스트, 수단·패턴 비교 | 트래픽 적음, 고위험 행동 UI(안전 우선) | 중~상 | 표준 | `[검증]` 실험 설계 일반론 |
| **LLM-as-judge로 UI 적절성 판정** | 골든셋 라벨 보조, 대량 사전 선별 | 운영 지표 대체(편향·비용) | 중~상 | 안정 (judge 일반) / UI 적용 신생 | `[2차]` judge 한계 공유 |
| **결정 모델을 judge로** ("이 UI 선택은 적절한가") | 닫힌 합격/불합격 판정, 대량·저비용 온라인 | 서술형 피드백 필요, 한국어 미검증 | 하 (호출) / 중 (평가셋) | 신생 | `[2차]` 사례 미확인 |
| **자동 접근성 검사** (axe 류) | 컴포넌트·생성 트리 회귀 | 의미적 접근성 문제 | 하~중 | 안정 | `[2차]` 도구 문서 |
| **사용자 테스트** (보조 기술 사용자 포함) | 출시 전, 큰 변경, judge 보정 | 전수 | 상 | 표준 | — |
| **눈대중 QA** | — | 운영 전부 — 재현 불가 | 하 | 해당 없음 | — |

### 선택 가이드

- **아직 아무것도 없다면** → 매핑 테이블 행당 10건 골든셋 + CI 스키마·카탈로그 대조 + 폴백률 로그. 이유: 하루면 되고 이후 모든 비교의 기반
- **결정 모델과 LLM 중 선택 수단을 정해야 한다면** → 같은 한국어 골든셋으로 선택 정확도·보정 곡선·지연 비교 후 A/B. 이유: 벤더 수치 `[벤더]`는 판단 근거가 아니다
- **UI 도입 효과를 증명해야 한다면** → 의도 유형 층화 A/B, 1차 지표는 완료율·턴 수. 이유: UI가 없는 게 나은 의도가 있다
- **Declarative를 쓴다면** → 생성 트리 접근성 검증기 통과율과 렌더 실패율을 운영 지표에 추가. 이유: Controlled에는 없는 실패 모드
- **판단이 어려우면** → 수정률·무시율·폴백률 세 개부터 대시보드에. 이유: 셋 다 "사용자가 UI를 거부했다"는 직접 신호이고 계측이 쉽다

## 설계 시 고려사항 (체크리스트)

- [ ] 매핑 테이블 행마다 골든셋 10건 이상, 한국어·혼합·비격식·경계 사례 포함인가
- [ ] 골든셋에 "텍스트가 정답"인 케이스가 포함되는가
- [ ] 골든셋이 카탈로그 버전에 묶여 있고 카탈로그 변경 PR에서 함께 바뀌는가
- [ ] 카탈로그 ↔ 컴포넌트 대조와 스키마 통과율이 CI 게이트인가
- [ ] 결정론 테스트(같은 입력 N회)가 있는가
- [ ] 결정 모델을 쓴다면 보정 곡선을 측정했는가
- [ ] 트레이스에 선택 수단·확신도·컴포넌트·카탈로그 버전·검증·렌더 결과·사용자 이벤트가 기록되는가
- [ ] 클라이언트가 렌더 결과(성공·실패·폴백)를 서버에 보고하는가
- [ ] 폴백률이 원인별로 분리 집계되는가
- [ ] A/B가 의도 유형으로 층화되어 있는가. 대조군이 텍스트인 실험이 있는가
- [ ] 접근성 자동 검사가 CI·E2E에 있고 위반이 지표로 집계되는가
- [ ] 수정·무시·폴백·불만 사례의 골든셋 환류 주기와 담당이 있는가
- [ ] 개발셋과 홀드아웃이 분리되어 있는가 ([Part 1/06](../01-foundations/06-evaluation-observability.md))

## 운영 설계 — 확장성 · 안정성 · 유지보수

용어·판단 기준은 [Part 1/07 운영 용어](../01-foundations/07-operations-vocabulary.md). 평가는 1/07 통제 세 층 중 **탐지(detective) 층의 본체**다 — 다른 페이지의 SLI는 이 페이지의 지표 체계에서 나오고, 모델·카탈로그 변경의 회귀 게이트도 여기다. 그래서 평가 파이프라인 자체의 장애가 "탐지 실명"이라는 2차 장애를 만든다.

### 확장성 — 10배가 되면 무엇이 먼저 깨지는가

| 확장 축 | 10배 시 깨지는 것 | 설계 수단 | 비용이 비례하는 변수 |
|---|---|---|---|
| 골든셋 크기 (매핑 행 × 10건 × 언어) | CI 전수 실행 시간, 결정 모델·LLM 호출 비용, 라벨 유지 | 커밋 시 변경 행 + 샘플, 야간 전수. 라벨은 매핑 행에 묶어 행 폐기 시 함께 정리 | 골든셋 건수 × 수단 호출 비용 |
| 운영 트레이스 양 | 지표 집계 지연, 저장 비용, 클라이언트 렌더 보고 트래픽 | 집계는 스트림 처리, 원본은 샘플링(감사 레코드는 별도·샘플링 불가), 렌더 보고는 배치 전송 | 요청 수 × 트레이스 필드 수 |
| A/B 실험 수 | 트래픽 분할 희석, 의도 유형 층화 시 셀당 표본 부족 | 실험 큐·우선순위, 층별 최소 표본 사전 계산 | 동시 실험 수 × 층 수 |
| 컴포넌트·플랫폼 수 | 접근성 자동 검사 시간, 렌더 스냅샷 수 | 변경 영향 범위만 검사, 병렬화 | 컴포넌트 수 × 플랫폼 수 |
| 테넌트 수 | 테넌트별 지표 분리, 골든셋 오버레이 | 모든 트레이스에 테넌트 키, 집계 차원 추가 | 테넌트 수 |
| 평가 수단 수 (규칙·judge·결정 모델 judge·사람) | judge 비용, 사람 라벨 큐 | judge는 사전 선별, 사람은 불일치 샘플만 | judge 호출 수 |

### 운영 안정성 — 장애 모드와 대응

| 장애 모드 | 사용자에게 보이는 증상 | 탐지 신호 | 자동 대응 (폴백·저하) | 사람 개입 기준 |
|---|---|---|---|---|
| **클라이언트 렌더 보고 유실** | — (사용자 무관) 렌더 실패율이 **과소 집계** → 탐지 실명 | 서버 측 `ui_intent` 발행 수 vs 클라이언트 보고 수 괴리 | 보고 로컬 큐·재전송, 괴리율을 자체 SLI로 | 괴리 예시 10% 초과 → 보고 경로 점검 |
| 골든셋 평가 파이프라인 실패 (결정 모델·LLM API 다운) | — 배포가 막힘 | CI 실패 원인 분류(인프라 vs 정확도 하락) | 인프라 원인이면 캐시된 직전 결과로 **리뷰 필요 표시 후 수동 승인 배포**(저하). 정확도 하락이면 차단 유지 | 지속 시 비교군 수단(LLM)으로 평가 |
| 지표 집계 지연·중단 | 대시보드 멈춤, 알림 침묵 | 집계 파이프라인 지연 지표(메타 모니터링) | 알림을 "데이터 없음"으로 전환(침묵 ≠ 정상) | 즉시 |
| 지표 드리프트 없는 품질 하락 (골든셋이 현실과 괴리) | 선택 정확도는 높은데 수정률·무시율 상승 | 오프라인 지표와 운영 지표의 괴리 추세 | 운영 사례 환류 주기 단축 | 괴리 지속 → 골든셋 재구성 |
| 모델 변경 후 스키마 실패율·폴백률 급등 | UI 대신 텍스트 증가 | 배포 마커 전후 지표 단절 | 카나리 자동 중단·롤백 트리거 | 롤백 판단 |
| 접근성 자동 검사 도구 버전 변경 | 갑자기 위반 수 급증 또는 0 | 도구 버전 변경 로그 | 도구 버전 고정, 변경 시 베이스라인 재측정 | 베이스라인 재설정 |
| A/B 할당 오염 (고위험 승인 UI가 처치군에 포함) | 안전 위험 | 실험 설정 검증 규칙 | 등급 3 이상 행동 의도는 실험 할당에서 자동 제외 | 1건이라도 → 실험 중단 |
| judge 편향 드리프트 | 장황한 UI 선호 등 | 사람 라벨 vs judge 불일치율 | judge 가중 축소, 사람 라벨 비중 확대 | 불일치율 예시 15% 초과 |

SLI 후보 — 이 페이지가 **정의하는** SLI는 지표 체계 표에 있고, 평가 파이프라인 **자체**의 SLI는 다음이다: 렌더 보고 수집률, 골든셋 평가 성공률·소요 시간, 지표 집계 지연, 오프라인-운영 지표 괴리, 환류 처리 시간(사례 발생 → 골든셋 반영). SLO 초안(예시): 렌더 보고 수집률 ≥ 95%, 집계 지연 < 15분, 환류 주기 ≤ 2주. 쓰기 행동 없음 — 평가는 읽고 판정만 한다. 단 CI 게이트의 배포 차단은 교정 층의 수단이다.

### 유지보수 — 버전·변경·호환

| 버전 관리 대상 | 바꾸면 영향받는 것 | 회귀 테스트 | 함께 배포할 것 (호환) |
|---|---|---|---|
| 골든셋 (의도·데이터·문맥 → 기대 컴포넌트·폴백 여부) | 선택 정확도 기준선, CI 게이트 | 골든셋 자체의 라벨 일관성(중복·모순 검사) | **카탈로그 버전 ↔ 매핑 테이블 ↔ 골든셋** — 같은 PR |
| 지표 정의 (분모·분자·원인 코드 enum) | 모든 대시보드·SLO·알림 | 지표 정의 변경 시 과거 재계산 또는 단절 마커 | 트레이스 스키마 |
| 트레이스 스키마 (선택 수단·확신도·컴포넌트·버전·검증·렌더 결과·이벤트) | 집계, 감사 | 스키마 호환(tolerant), 필수 필드 존재 검사 | 어댑터(프론트 보고), Part 5/03 |
| CI 게이트 임계값 (정확도 하락 허용 폭, 접근성 심각도) | 배포 속도 vs 안정성 | — (설정) | 오류 예산 정책 |
| A/B 설계 템플릿·층화 기준·제외 규칙 | 실험 유효성·안전 | 제외 규칙 테스트(등급 3 이상 미포함) | 매핑 테이블(의도 유형) |
| judge 프롬프트·결정 모델 judge 질문 | judge 결과 | 사람 라벨 교차 세트 | 모델 버전 |
| 접근성 검사 도구 버전·규칙 세트 | 위반 수 베이스라인 | 베이스라인 재측정 | — |

기술 부채로 기록할 것: 홀드아웃 미분리 상태, 렌더 보고 미구현 플랫폼, 결정 모델 judge `[실측]` 미완, OTel 자체 속성 → 표준 매핑 미완.

| **규칙·정책** (승인 매트릭스·권한) | 승인 지표 분모, A/B 제외 규칙 | 지표 정의 | — | 제외 규칙은 행동 등급 메타데이터를 조회(하드코딩 금지) | 실험 설정 |
| **관측 표준** (OTel GenAI 컨벤션 안정화) | 속성 이름 | 자체 트레이스 스키마 | 내보내기 매핑 | 매핑 계층 교체. 자체 스키마 불변 | 내보내기 |

가장 자주 바뀌는 것: **골든셋**(운영 환류, 주~격주) > 매핑 행 > 모델 > 지표 정의(거의 안 바뀜). 코드 밖 설정으로 둘 것: 골든셋, 지표 정의·원인 코드 enum, CI 임계값, A/B 템플릿·제외 규칙, judge 프롬프트, 도구 버전. 포트·어댑터 뒤에 둘 외부 의존: 평가 대상 모델 API, judge, 접근성 검사 도구, 트레이스 내보내기(OTel). 시점 재현: 골든셋·카탈로그·매핑·모델 버전 4개가 트레이스와 평가 결과에 모두 있어야 "그때 정확도 92%"가 재현된다.

### 거버넌스 접점 — 정책 · 가드레일 · 승인 · 감사

| 항목 | 이 단계에서의 답 |
|---|---|
| 위험 등급 (1~5) | 평가 자체는 행동이 아니라 등급 없음. 단 **A/B 실험은 사용자에게 다른 경험을 주는 행동**이므로 처치군에 등급 3 이상 행동 UI 포함 금지(1/07 "결합 시스템 V&V"의 안전 경계) |
| 가드레일 위치 | 평가는 가드레일이 아니라 **탐지 층**. CI 게이트(배포 차단)는 변경 관리의 예방 수단, 카나리 자동 롤백은 교정 수단. 실험 제외 규칙이 유일한 "행동" 게이트 |
| 게이트 출력과 판정 수단 | CI: 통과 / 차단(스키마·카탈로그 대조·심각 접근성) / 리뷰(정확도 하락·결정론). 카나리: 계속 / 롤백. 전부 규칙(임계값). judge는 라벨 보조이지 게이트가 아님 |
| 소유자 (A) | 지표 정의·SLO: 제품 책임자. 골든셋: AI 엔지니어(R) + 디자인 책임자(기대 컴포넌트 라벨 C). CI 임계값·오류 예산: 아키텍트. A/B 안전 규칙: 운영 책임자 |
| 감사 추적에 남길 필드 | 배포별 골든셋 평가 결과(정확도·혼동 행렬·버전 4종), CI 게이트 판정과 수동 승인자(저하 배포 시), 카나리 롤백 기록, A/B 할당·제외 규칙 버전, 골든셋 변경 이력(누가 어떤 라벨을 왜 바꿨나) |

### 운영 준비도 체크
- [ ] 클라이언트 렌더 보고 수집률이 SLI로 있고 서버 발행 수와 대조되는가
- [ ] 골든셋 평가가 CI 게이트이며 인프라 실패와 정확도 하락이 구분되는가
- [ ] 지표 집계 중단 시 알림이 "정상"이 아니라 "데이터 없음"으로 바뀌는가
- [ ] 모델 교체 절차에 섀도 → 회귀 → 카나리가 있고 골든셋은 그대로인가
- [ ] 매핑 행 ↔ 골든셋 카테고리 대조가 CI에 있는가
- [ ] 등급 3 이상 행동 UI가 A/B 할당에서 자동 제외되는가
- [ ] 트레이스·평가 결과에 골든셋·카탈로그·매핑·모델 버전 4종이 모두 있는가
- [ ] 운영 사례(수정·무시·폴백·불만) → 골든셋 환류 주기와 담당이 있는가
