# 비용·지연·모델 라우팅

> **범위**: 모델 라우팅, 캐싱, 결정 모델로 LLM 호출 절감. 요청 1건의 비용·지연을 **세 레이어에 걸쳐 분해**하고, 어디를 어떤 수단으로 줄일지 정하는 횡단 정책. 라우터 구현 자체는 [Part 3/02](../03-agent-workflow-rag/02-query-understanding.md), 결정 레이어 배치는 [Part 3/11](../03-agent-workflow-rag/11-decision-layer.md), 파이프라인(인덱싱) 비용은 [Part 2/09](../02-data-pipeline/09-ai-inside-the-pipeline.md).

## 요약 (3줄)

1. 에이전트 요청 1건의 비용은 "LLM 호출 1번"이 아니다. **판정 → 검색 → 생성 → 검증 → UI**의 합이고, 멀티스텝·멀티에이전트면 곱이다. 분해하지 않으면 어디를 줄여야 할지 모른다.
2. 절감의 순서는 **안 부르기(캐시) → 작은 수단으로 부르기(규칙·결정 모델·소형 모델) → 적게 넣기(컨텍스트 압축) → 싸게 부르기(프롬프트 캐싱·배치)** 다. 모델 라우팅은 이 중 두 번째 하나일 뿐이다.
3. 결정 모델(Jev / Decisions API)은 **판정 지점의 생성 비용을 구조적으로 없앤다**(출력 토큰 0, 단일 패스). 벤더는 수백 배 저렴하다고 주장하지만 `[벤더]`이며, 절감 폭은 요청에서 판정이 차지하는 비중에 달렸다 — 생성이 비용의 대부분이면 결정 모델은 비용 문제를 풀지 않는다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 요청 유형별 비용·지연 분해표(단계 × 모델 × 토큰) ② 라우팅 정책(어떤 요청을 어떤 수단·모델에) ③ 캐시 계층 설계 ④ 지연 예산 배분표 ⑤ 비용 계측·상한·알림 규칙 |
| **언제** (When) | 트래픽이 생기기 **전**에 분해표와 계측을. 라우팅·캐시 최적화는 실측 분포가 나온 뒤(조기 최적화는 잘못된 지점을 줄인다). 생략 가능: 내부 도구·저트래픽·단일 모델 — 단 계측과 상한은 생략하지 않는다 |
| **어떻게** (How) | ① 대표 요청 유형 5~10개를 골라 단계별 토큰·지연을 `[실측]` → ② 판정 지점을 목록화해 LLM이 맡은 닫힌 판정을 규칙·결정 모델·분류기로 이전([Part 1/02](../01-foundations/02-system1-vs-system2.md)) → ③ 반복 접두(시스템 프롬프트·툴 스키마·문서)는 프롬프트 캐싱, 반복 질의는 시맨틱·결과 캐시 → ④ 생성 모델을 복잡도별 2~3단계로 라우팅 → ⑤ 지연 예산을 단계별로 배분하고 병렬화 지점 표시 → ⑥ 요청·테넌트·기능 단위 비용 태깅과 상한 → ⑦ 레이어 간 정합성 검토 |
| **왜** (Why) | 분해 없이 "더 싼 모델로 바꾸자"를 하면 생성 품질만 떨어지고 비용은 그대로인 경우가 많다(비용의 대부분이 리랭크·judge·멀티에이전트 왕복에 있었기 때문). 상한 없는 에이전트 루프는 한 번의 버그로 월 예산을 하루에 쓴다 |

## 문제와 맥락

RAG 챗봇 시절의 비용 모델은 "입력 토큰 + 출력 토큰 × 단가"였다. 에이전트는 이 모델을 세 방향으로 깨뜨린다.

- **단계가 늘었다**: 라우팅 판정, 쿼리 재작성, 리랭크(LLM rerank면 청크 수만큼 호출), 생성, 근거 검증(judge), UI 선택, 메모리 요약. 각각이 모델 호출일 수 있다.
- **루프가 생겼다**: ReAct·Plan-and-Execute는 스텝 수가 입력에 따라 다르다. 검증 실패 → 재생성 루프는 비용을 배수로 만든다. 멀티에이전트는 에이전트 간 왕복마다 컨텍스트가 복제된다.
- **지연이 직렬로 쌓인다**: 판정 300ms + 검색 200ms + 리랭크 400ms + 생성 TTFT(time to first token) 800ms면 사용자는 첫 글자를 1.7초 뒤에 본다. 각 단계는 "빠른데" 합은 느리다.

레이어별로 최적화하면 **불균형**이 생긴다. Part 2에서 하이브리드 검색을 싸고 빠르게 만들었는데 Part 3에서 LLM rerank 20개 + 대형 모델 생성 + judge 전수 적용이면, 검색 최적화는 전체의 5%를 줄인 것이다. 이 페이지는 세 레이어의 비용·지연을 한 표에 놓는다.

## 핵심 개념

### 요청 1건의 비용·지연 분해

| 단계 | 레이어 | 비용 요인 | 지연 요인 | 줄이는 수단 |
|---|---|---|---|---|
| 판정 (라우팅·게이팅·승인 필요) | Reasoning | 판정당 호출. LLM이면 입력 토큰 + 출력 수십 토큰 | LLM 수백 ms~수 초 / 결정 모델 70~500ms `[벤더]` / 규칙 ~0 | 규칙 → 결정 모델 → 분류기 순으로 이전 |
| 검색 (쿼리 임베딩·벡터·BM25·그래프) | Knowledge | 임베딩 호출(소), 벡터DB 쿼리(인프라) | 수십~수백 ms. 그래프 멀티홉은 늘어남 | 쿼리 임베딩 캐시, 인덱스 튜닝, 병렬 검색 |
| 리랭크 | Knowledge/Reasoning | cross-encoder(자체 호스팅 GPU) 또는 LLM rerank(청크 수 × 호출) | LLM rerank가 자주 **최대 지연 요인** | cross-encoder 우선, 후보 수 축소, 결정 모델로 관련성 판정 |
| 생성 | Reasoning | **입력 토큰이 지배**(시스템 프롬프트 + 툴 스키마 + 검색 청크 + 히스토리) + 출력 토큰 | TTFT는 입력 길이에, 총 시간은 출력 길이에 비례 | 컨텍스트 압축, 프롬프트 캐싱, 모델 라우팅, 스트리밍 |
| 검증 (judge·규칙·결정 모델) | Reasoning | LLM judge면 생성과 비슷한 입력 토큰을 **한 번 더** | judge는 응답 뒤에 직렬로 붙어 체감 지연 증가 | 규칙 1차, 결정 모델 judge, 샘플링, 비동기 검증 |
| UI 선택·렌더 | Interaction | Controlled면 판정 1회(소), Open-ended면 코드 생성(생성 비용급) | 선택 판정 + 렌더. 스트리밍이면 부분 렌더 가능 | Controlled 기본값, 결정 모델·규칙으로 선택 |
| 멀티에이전트 왕복 | Reasoning | 에이전트 수 × 각자의 위 비용. 컨텍스트 복제 | 핸드오프마다 직렬 | 에이전트 수 최소화, 공유 상태로 복제 축소 ([Part 3/07](../03-agent-workflow-rag/07-multi-agent-orchestration.md)) |

### 절감 수단의 우선순위

1. **안 부르기** — 결과 캐시(동일 입력), 시맨틱 캐시(유사 입력), 쿼리 임베딩 캐시
2. **작은 수단으로 부르기** — 닫힌 판정은 규칙·결정 모델·분류기, 열린 생성만 LLM
3. **적게 넣기** — 컨텍스트 압축, 청크 수 축소, 툴 스키마 지연 로딩, 히스토리 요약 ([Part 3/08](../03-agent-workflow-rag/08-state-memory-context.md))
4. **싸게 부르기** — 프롬프트 캐싱(반복 접두), 소형 모델 라우팅, 오프라인 작업은 배치 API
5. **덜 반복하기** — 재생성 루프 상한, 에이전트 스텝 상한, 검증 실패 패턴을 프롬프트에 반영

### 결정 모델이 LLM 호출을 대체하는 지점

| 판정 지점 | LLM으로 할 때 | 결정 모델로 할 때 | 절감 구조 (정성적) |
|---|---|---|---|
| 라우팅(intent·경로·복잡도) | 소형 LLM 프롬프트, 출력 수십 토큰 | 타입드 질문 → 선택 + 보정 확률 | 출력 토큰 0, 단일 패스. 보정 확률로 "대형 모델 필요" 판정까지 한 번에 |
| 관련성 필터링(검색 후보 중 쓸 것) | LLM rerank: 후보 수만큼 호출 | 후보별 예/아니오 또는 점수를 병렬 질문으로 | 호출 수가 후보 수에 비례하던 구조가 1~2회로 |
| 승인 필요 여부·위험도 | LLM이 설명과 함께 판정 | 예/아니오 + 확률 | 설명 생성 비용 제거. 확신 낮음만 사람에게 |
| 품질 게이트(근거 부합·안전) | LLM-as-judge: 생성급 입력 토큰 재투입 | 루브릭 점수 판정 | judge 비용을 판정 비용으로. 서술형 피드백은 못 받음 |
| UI 컴포넌트 선택 | 툴 호출로 선택 | 카탈로그 enum 중 선택 | 생성 모델의 툴 호출 왕복 제거 ([Part 4/05](../04-dynamic-ui/05-intent-to-ui-mapping.md)) |
| 파이프라인 분류·중복·품질 | 문서 수 × LLM 호출 | 문서 수 × 결정 모델 호출 | 인덱싱 비용이 서빙 비용을 넘는 문제 완화 ([Part 2/09](../02-data-pipeline/09-ai-inside-the-pipeline.md)) |

벤더가 보고한 가격은 Jev $0.042/1M 입력 토큰, Decisions API $0.10/1M 입력 토큰(출력·캐시 과금 없음, 미공개라는 소스도 있음) `[2차]` 재확인 필요. Jev의 "LLM 워크플로우 대비 최대 200배 빠르고 400배 저렴"은 `[벤더]`이며 독립 벤치마크가 없다. 두 제품은 인터페이스는 비슷하나 Jev는 결정 전용 모델, Decisions API는 범용 생성 모델(gpt-6-luna)의 출력 제약이므로 지연·비용 특성이 다를 수 있다 — 같은 평가셋으로 `[실측]`한다.

### 지연 예산 배분

사용자 체감 지연은 **첫 의미 있는 피드백까지의 시간**이다. 예산을 단계별로 쪼개고, 직렬 구간과 병렬 가능 구간을 구분한다.

```
예산 예시 (대화형, 체감 목표 TTFT ≤ 1.5s — 팀이 정하는 값)
  판정(라우팅·게이트)   ≤ 0.2s   ─ 규칙·결정 모델이면 달성, LLM이면 초과
  검색 + 리랭크         ≤ 0.5s   ─ 하이브리드 병렬, cross-encoder. LLM rerank는 초과 위험
  생성 TTFT             ≤ 0.8s   ─ 프롬프트 캐싱·컨텍스트 축소로
  검증                  비동기    ─ 스트리밍 후 검증, 실패 시 정정 메시지 또는 사전 샘플링
```

병렬화 지점: 라우팅 판정과 쿼리 임베딩, 벡터·BM25·그래프 검색, UI 의도 판정과 생성 시작. 비동기화 지점: 검증·judge, 메모리 요약, 비용 집계.

### 비용 계측·상한·알림

- **태깅**: 모든 모델·검색·툴 호출에 `tenant / feature / request_type / model / prompt_version` 태그. 트레이스 스팬에 토큰·비용 속성 ([03](03-observability-tracing.md))
- **상한**: 요청당(스텝 수·토큰·시간), 세션당, 테넌트·기능당 일/월. 상한 도달 시 **거부가 아니라 축소 모드**(소형 모델·캐시만·검증 생략 금지)를 먼저 고려
- **알림**: 요청당 평균 비용 급증(루프 버그), 캐시 적중률 급락(프롬프트 변경으로 캐시 무효화), 특정 모델 호출 수 급증(라우터 오작동), 일 예산 소진율
- **귀속**: 비용을 기능·팀 단위로 보여줘야 최적화 동기가 생긴다

## 아키텍처 / 파이프라인

```
요청 ─▶ 결과 캐시 적중? ──예──▶ 응답
          │ 아니오
          ▼
       시맨틱 캐시 적중? ──예(임계 이상)──▶ 응답(출처·신선도 확인 후)
          │ 아니오
          ▼
       판정 계층: 규칙 ─▶ 결정 모델(intent·복잡도·승인 필요·UI 의도) ─▶ 확신도
          │                                    │ 저확신 → 소형 LLM 재판정 또는 사람
          ▼
       검색(병렬: dense ∥ BM25 ∥ 그래프) ─▶ cross-encoder 리랭크 ─▶ 컨텍스트 압축
          │
          ▼
       생성 라우팅: 복잡도 하 → 소형 / 중 → 중형 / 상·고위험 → 대형   (프롬프트 캐싱 접두 공유)

          ▼
       검증(비동기: 규칙 → 결정 모델 judge → LLM judge 샘플링) ─▶ 비용 집계 ─▶ 상한·알림
```

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 정적 라우팅 (기능·엔드포인트별 모델 고정) | 요청 유형이 진입점에서 구분됨(요약 API vs 상담 채팅), 소규모 | 한 진입점에 난이도가 섞여 들어오는 대화형 | 하 | 표준 | `[검증]` |
| 규칙 라우팅 (길이·언어·권한·키워드) | 결정론적 신호가 있음(첨부 유무, 사용자 등급, 금칙어) | 의미적 복잡도 판단 | 하 | 표준 | `[검증]` |
| 분류기 라우팅 (파인튜닝 소형 모델) | 라벨 데이터 수천 건, 카테고리 고정, 온프레미스·초저지연 | 라벨 없음, 카테고리 자주 변경 | 중 (학습·MLOps) | 표준 | `[검증]` |
| 결정 모델 라우팅 (Jev / Decisions API) | 라벨 적음, 질문이 자주 바뀜, 보정 확률로 에스컬레이션 임계값 운용, 저지연 | 한국어 미실측, 결정 모델 장애 시 폴백 없음, 벤더 베타 상태 의존 | 하 (호출) / 중 (평가셋) | 신생 | `[벤더]` 지연·비용, `[2차]` 사례 미확인 |
| LLM 자체 판단 (소형 LLM이 분류 후 위임) | 프로토타입, 선택지 미확정, 설명이 함께 필요 | 대량·저지연, 보정 확신도 필요 | 중 (토큰) | 안정 | `[검증]` 비보정 문제 보고 |
| 캐스케이드 (소형 먼저 → 품질 판정 실패 시 대형) | 쉬운 요청이 다수, 품질 판정이 저렴(규칙·결정 모델) | 실패율이 높아 두 번 호출이 잦음(지연·비용 역전), 판정이 LLM judge면 절감 상쇄 | 중 | 안정 | `[2차]` |
| 프롬프트 캐싱 (반복 접두 캐시, 벤더 기능) | 긴 시스템 프롬프트·툴 스키마·고정 문서가 매 요청 반복 | 접두가 요청마다 바뀜(캐시 무효화), 벤더가 미지원 | 하 (접두 순서 설계) | 안정 | `[벤더]` 할인율은 벤더별 |
| 시맨틱 캐시 (유사 질의 → 저장 응답) | FAQ성 반복 질의 비중 큼, 답이 시간에 덜 민감 | 개인화·권한별 답, 신선도 중요, 유사하지만 답이 달라야 하는 질의(오탐 위험) | 중 (임계값·무효화) | 안정 | `[2차]` 오탐 사례 보고 |
| 컨텍스트 압축·선택 (청크 압축, 히스토리 요약, 툴 스키마 지연 로딩) | 입력 토큰이 비용·TTFT를 지배 | 압축이 근거를 깎아 faithfulness 하락(측정 필요) | 중 | 안정 | `[2차]` [Part 3/03](../03-agent-workflow-rag/03-retrieval-reranking.md) |

### 선택 가이드

- **비용 대부분이 생성 입력 토큰이라면** → 프롬프트 캐싱 + 컨텍스트 압축 + 생성 모델 2단 라우팅. 이유: 결정 모델은 판정 비용만 줄이므로 이 경우 주 수단이 아니다
- **비용·지연 대부분이 판정·리랭크·judge라면** → 규칙 → 결정 모델 → 분류기로 이전, LLM rerank는 cross-encoder로. 이유: 판정은 닫힌 선택지라 생성 모델이 필요 없다. 한국어 `[실측]` 선행
- **반복 질의가 많고 답이 시간·사용자에 덜 민감하다면** → 시맨틱 캐시. 이유: 호출 자체를 없앤다. 단 권한별 답이면 캐시 키에 권한 범위를 넣거나 포기
- **멀티에이전트인데 비용이 통제 안 된다면** → 에이전트 수·핸드오프 수를 줄이고 공유 상태로. 이유: 라우팅·캐시로는 왕복 곱셈 구조를 못 푼다
- **판단이 어려우면** → 기본값: 계측·태깅·상한부터 넣고 2주 실측 → 분해표 → 가장 큰 항목 하나만 줄인다. 이유: 분포를 모르고 하는 최적화는 엉뚱한 곳을 줄인다

## 설계 시 고려사항 (체크리스트)

### 레이어별

- [ ] 대표 요청 유형별로 단계 × 토큰 × 지연 분해표가 `[실측]`으로 있는가
- [ ] 모든 모델·검색·툴 호출에 비용 태그(테넌트·기능·모델·프롬프트 버전)가 붙는가
- [ ] 요청당 스텝·토큰·시간 상한과 테넌트·기능별 일/월 상한이 있고, 상한 도달 시 동작(축소 모드·거부·알림)이 정의돼 있는가
- [ ] (Reasoning) 판정 지점 목록에서 LLM이 맡은 닫힌 판정이 식별되고 이전 계획이 있는가 ([Part 1/02](../01-foundations/02-system1-vs-system2.md))
- [ ] (Reasoning) 시스템 프롬프트·툴 스키마·고정 문서가 캐시 가능한 접두 순서로 배치되는가. 접두에 타임스탬프·사용자명 같은 가변값이 섞여 캐시를 깨지 않는가
- [ ] (Reasoning) 재생성 루프·에이전트 스텝에 상한이 있고 상한 도달 시 폴백이 있는가
- [ ] (Interaction) UI 선택이 생성 모델 툴 호출 왕복인가, 판정(규칙·결정 모델)인가. Open-ended UI 생성 비용이 분해표에 들어 있는가
- [ ] 시맨틱 캐시가 있다면 권한·개인화·신선도가 캐시 키나 무효화 규칙에 반영되는가 ([01](01-security-prompt-injection.md) — 캐시를 통한 교차 사용자 노출)
- [ ] 결정 모델을 썼다면 장애 시 폴백(규칙·보수적 기본 경로·소형 LLM)이 있는가 ([05](05-llmops-agentops.md))

### 레이어 간 정합성 검토

- [ ] Part 2에서 검색을 싸고 빠르게 만들었는데 Part 3에서 LLM rerank·대형 모델·judge 전수로 그 절감이 무의미해지지 않았는가 ("검색은 싸고 빠른데 생성이 비쌈")
- [ ] Part 2의 청크 크기·개수 설정이 Part 3의 생성 입력 토큰 예산과 맞는가(청크 20개 × 1,000토큰이면 컨텍스트만 2만 토큰)
- [ ] Part 2에서 GraphRAG 계열을 택했다면 인덱싱 비용(과다 비판 `[벤더]`)이 서빙 절감으로 회수되는가. LightRAG의 증분 업데이트 같은 대안을 봤는가 `[2차]`
- [ ] Part 3에서 결정 모델로 라우팅을 빠르게 했는데 Part 4의 UI 선택은 여전히 생성 모델 툴 호출인가(판정 수단이 레이어마다 다름)
- [ ] Part 4에서 Controlled UI로 렌더 비용을 줄였는데 Part 3의 응답 스키마가 UI 의도를 안 담아 UI 선택을 위해 한 번 더 호출하는가
- [ ] 세 레이어의 비용이 하나의 요청 단위로 합산되어 보이는가, 아니면 벡터DB 청구서·모델 청구서·프론트 인프라가 따로 보이는가

| 상한이 품질을 깎음 | 축소 모드에서 검증 생략·근거 축소 | 검증·보안 계층은 축소 대상에서 제외. 축소는 모델 크기·청크 수에서만 |
| 비용 최적화가 보안을 깎음 | 검증 샘플링 과도, 이중 LLM 제거 | 보안 계층은 비용 최적화 범위 밖임을 명시 ([01](01-security-prompt-injection.md)) |
