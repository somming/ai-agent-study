# 거버넌스와 설명가능성

> **범위**: EU AI Act, 감사 추적, 온톨로지 기반 설명가능성. 규제 맥락은 **일반 수준**으로만 다루고 조항·시행일은 법무 검토 대상으로 남긴다. 트레이스 스키마는 [03](03-observability-tracing.md), 변경 배포 절차는 [05](05-llmops-agentops.md), 인덱스 접근 제어는 [Part 2/10](../02-data-pipeline/10-access-control-governance.md).

## 요약 (3줄)

1. 거버넌스의 핵심 질문은 "**누가, 무엇을 근거로, 어떤 판정을, 어떤 확신도로** 했고, 그 결과에 **어느 사람이** 책임지는가"를 사후에 재구성할 수 있는가다. 재구성 불가능한 에이전트는 규제 대상 여부와 무관하게 운영 리스크다.
2. 설명 수단은 네 가지가 다르다. 감사 로그는 **무엇이 일어났나**, 온톨로지·그래프 경로는 **왜 이 근거인가**, 결정 모델의 보정 확률은 **얼마나 확신했나**, LLM 생성 설명은 **그럴듯한 사후 합리화**일 수 있다. 마지막 것을 설명가능성의 근거로 쓰면 안 된다.
3. 거버넌스는 레이어마다 따로 하면 구멍이 난다. Part 2의 근거 ID, Part 3의 판정 기록, Part 4의 승인 이벤트가 **같은 감사 레코드**로 모여야 "사람이 승인했다"가 증명된다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 시스템의 규제·위험 분류와 적용 의무 목록(법무 검토 결과) ② 감사 레코드 스키마와 불변 저장소 ③ 판정 지점별 설명 수단 배정표 ④ 변경 승인 절차(모델·프롬프트·데이터·규칙·컴포넌트) ⑤ 책임 지점(RACI) ⑥ 데이터 보존·삭제 정책 |
| **언제** (When) | 에이전트가 **사람에게 영향을 주는 결정**(채용·신용·의료·법률·공공 서비스·고객 처분)에 관여하거나 **되돌릴 수 없는 행동**을 하면 설계 초기부터. 내부 도구·정보 조회만이면 감사 로그와 책임 지점 정의로 축소. 미룰 수 없는 것: 감사 레코드 스키마 — 나중에 과거 결정을 재구성할 수 없다 |
| **어떻게** (How) | ① 위험 분류(법무와 함께) → ② 판정 지점 목록([Part 1/02](../01-foundations/02-system1-vs-system2.md))에 설명 요구 수준을 표시 → ③ 감사 레코드 스키마를 트레이스 스키마([03](03-observability-tracing.md))의 부분집합 + 불변성으로 정의 → ④ 설명 수단 배정(규칙 트레이스·그래프 경로·보정 확률·citation) → ⑤ 변경 승인 절차와 책임자 지정 → ⑥ 보존·삭제 정책을 인덱스·메모리·캐시·트레이스 전부에 → ⑦ 레이어 간 정합성 검토 |
| **왜** (Why) | 사고가 났을 때 "모델이 그렇게 판단했다"는 답변은 규제기관·고객·법원 어디에도 통하지 않는다. 재구성 불가능하면 원인 분석도 재발 방지도 불가능하고, 책임 지점이 없으면 아무도 고치지 않는다 |

## 문제와 맥락

전통 소프트웨어의 결정은 코드에 있다. 코드 리뷰와 로그로 재구성된다. 에이전트의 결정은 **모델 가중치, 프롬프트, 검색된 근거, 판정 모델의 확률, 사람의 승인**에 분산되어 있고 그중 일부는 비결정적이다. 같은 입력을 다시 넣어도 같은 결정이 안 나올 수 있으므로 **재실행이 아니라 기록**으로 재구성해야 한다.

규제 맥락은 이 요구를 의무로 만든다. EU AI Act는 AI 시스템을 **위험 기반**으로 분류해(허용 불가 / 고위험 / 투명성 의무 / 최소 위험) 고위험 시스템에 위험 관리·데이터 거버넌스·기술 문서·기록 보존·투명성·인간 감독·정확성·견고성 요건을 두고, 범용 AI 모델(GPAI) 제공자에게는 기술 문서·투명성·저작권 관련 의무를, 시스템적 위험이 있는 모델에는 추가 의무를 둔다 `[2차]` 일반 수준. 어떤 용도가 고위험인지, 의무의 세부와 적용 시점은 **법무 검토 사항**이며 이 위키는 조항·날짜를 적지 않는다. 다른 국가·지역의 AI 규제도 위험 기반 접근과 투명성·인간 감독을 공통 축으로 하는 흐름이다 `[2차]`. 개인정보 규제(국내 개인정보보호법, GDPR 등)는 트레이스·메모리·인덱스에 든 개인정보의 보존·삭제 의무를 부과한다.

## 핵심 개념

### 감사 추적 요건 — 재구성에 필요한 다섯 가지

| 요소 | 기록할 것 | 출처 레이어 |
|---|---|---|
| **누가** | 사용자(익명화 ID), 세션, 에이전트 ID, 위임 체인(A2A), 승인자 | Interaction, Reasoning |
| **무엇을 근거로** | 검색 근거 ID와 **그 시점의 인덱스 버전**, 툴 결과 참조, 메모리 참조, 프롬프트 버전, 모델 ID·버전 | Knowledge, Reasoning |
| **어떤 판정을** | 판정 지점 ID, 수단(규칙·결정 모델·분류기·LLM), 선택 결과, 적용된 규칙 ID, 거부·폴백 여부 | Reasoning |
| **어떤 확신도로** | 보정 확률(결정 모델), 임계값, 임계 미만 시 경로(사람·보수적 기본값) | Reasoning |
| **결과와 승인** | 실행된 행동, 사람 승인 이벤트(컴포넌트 인스턴스 ID, 승인자, 시각, 서버 재검증 결과), 사후 정정 | Interaction, Reasoning |

감사 레코드는 트레이스([03](03-observability-tracing.md))의 부분집합이지만 요건이 다르다. **불변(append-only)**, **장기 보존**(규제·내부 정책이 정하는 기간), **접근 통제·열람 기록**, 그리고 **근거의 시점 복원** — 인덱스 버전 v12의 청크 c17이 당시 어떤 내용이었는지 꺼낼 수 있어야 한다(인덱스 스냅샷 보존 또는 근거 본문 사본, [Part 2/03](../02-data-pipeline/03-metadata-provenance.md)).

### 설명 수단 네 가지와 그 성격

| 수단 | 답하는 질문 | 신뢰성 | 한계 |
|---|---|---|---|
| 감사 로그 | 무엇이 일어났나 | 높음(기록된 범위) | "왜"는 답하지 않음 |
| 규칙 트레이스 (어떤 규칙이 발화했나) | 왜 허용·거부됐나 | 높음(결정론) | 규칙이 다루는 범위만 |
| 온톨로지·그래프 경로 | 왜 이 근거가 이 질문에 관련되나 (개념 A → 관계 → 개념 B) | 중~높음(경로가 데이터에 실재) | 온톨로지 품질에 종속. 경로가 있다고 생성이 그것을 썼다는 보장은 citation으로 보완 |
| citation (근거 표시) | 어떤 문서·문장에 기반했나 | 중 (근거 ⊂ 검색 결과 자동 검증 가능) | 인용했다 ≠ 올바르게 해석했다 |
| 결정 모델 보정 확률 | 얼마나 확신했나 | 보정이 **측정된 경우에만** 의미 | 왜 그 확률인지는 설명 불가. 보정은 벤더 주장 `[벤더]` — 신뢰도 다이어그램으로 `[실측]` |
| LLM 생성 설명 | (모델이 말하는) 이유 | **낮음** | 사후 합리화(post-hoc rationalization) 위험 — 실제 결정 과정과 무관하게 그럴듯한 이유를 생성할 수 있음 `[2차]` |

원칙: **감사·규제 대응의 설명은 결정론적 수단(규칙 트레이스·그래프 경로·citation·로그)으로 구성하고, LLM 생성 설명은 사용자 편의용 보조 텍스트로만** 쓴다. 두 가지가 어긋나면 결정론적 쪽이 사실이다.

### 변경 승인 절차 — 무엇이 바뀌면 누가 승인하나

| 변경 대상 | 영향 범위 | 승인 수준 (예) | 게이트 |
|---|---|---|---|
| 모델 ID·버전·파라미터 | 전 판정·생성 | 모델 오너 + 품질 게이트 통과 | 골든셋 회귀, 보정 재측정 |
| 프롬프트·질문 정의(결정 모델) | 해당 판정·생성 | 기능 오너 + 리뷰어 | 골든셋 회귀, 레드팀 셋 |
| 인덱스 소스 추가·청킹·임베딩 모델 | 근거 전체 | 데이터 오너 + ACL 검토 | recall 프록시 비교, 접근 제어 테스트 |
| 규칙·정책(권한·한도·게이트) | 보안·행동 | 보안·컴플라이언스 + 규칙 테스트 | 규칙 테스트 스위트 — 규칙도 코드다 |
| 컴포넌트 카탈로그 | UI·승인 흐름 | 디자인·프론트 + 접근성 검토 | 스키마 호환, 렌더 테스트 |
| 툴·MCP 서버 추가·권한 변경 | 공격면·행동 범위 | 보안 + 툴 오너 | 권한 매트릭스 갱신, 툴 정의 고정 |
| 고위험 용도 신규 투입 | 규제 분류 변경 가능 | 법무 + 경영 | 위험 평가 문서 |

승인은 티켓이 아니라 **배포 게이트**로 구현한다([05](05-llmops-agentops.md)). 운영 중 프롬프트 핫패치는 승인 절차 우회이므로 금지한다.

### 사람 책임 지점 (Accountability)

- **모델 오너**: 모델·프롬프트·결정 질문 정의의 품질과 변경
- **데이터 오너**: 인덱스 소스·근거 품질·접근 정책·삭제 전파
- **규칙 오너**: 권한·한도·게이트 규칙과 그 테스트
- **승인자**(HITL): 고위험 행동의 실행 전 승인. 승인은 UI 이벤트로 기록되고 서버가 재검증
- **운영 온콜**: 장애·품질 사고 대응과 롤백 결정
- **컴플라이언스**: 위험 분류, 규제 대응, 감사 요청 처리

"에이전트가 결정했다"는 책임 지점이 아니다. 모든 자동 결정에는 **그 자동화를 승인한 사람**이 있고, 임계값·규칙·모델 선택이 그 사람의 결정이다.

### 데이터 보존·삭제 — 전파 지점

삭제 요청 하나가 도달해야 하는 곳: 원천 → 인덱스(청크·임베딩·그래프 노드) → 메모리(장기·요약) → **시맨틱·결과 캐시** → 트레이스 본문 저장소 → 감사 레코드(규제상 보존 의무와 충돌 시 익명화) → 평가셋·골든셋(운영 로그에서 환류된 것) → 파인튜닝 데이터(있다면). 가장 자주 빠지는 곳이 캐시와 골든셋이다. 삭제 전파 메커니즘은 [Part 2/07](../02-data-pipeline/07-freshness-and-sync.md).

## 아키텍처 / 파이프라인

```
요청 ─▶ [Knowledge] 근거 ID + 인덱스 버전 ─▶ [Reasoning] 판정(수단·선택·확신도·규칙 ID) ─▶ 행동 ─▶ [Interaction] 승인 이벤트
            │                                   │                                              │
            └──────────────── 감사 레코드(불변, 장기, 열람 기록) ◀───────────────────────────────┘
                                   │
                    설명 조립: 규칙 트레이스 + 그래프 경로 + citation + 확신도  ─▶ 감사·규제 대응
                                   │                                              ─▶ 사용자 설명(LLM 보조 텍스트는 여기만)
                    변경 승인 게이트 ◀── 모델·프롬프트·데이터·규칙·컴포넌트 변경 ([05])
                    삭제 전파 ──▶ 인덱스·메모리·캐시·트레이스·골든셋
```

## 기술 비교표 — 이 단계에서 쓸 수 있는 선택지

| 기술 / 접근 | 적합한 상황 | 부적합한 상황 | 비용·복잡도 | 성숙도 | 검증 수준 |
|---|---|---|---|---|---|
| 감사 로그 (불변 저장, 트레이스 부분집합) | **모든 운영 에이전트의 기반**. "무엇이 일어났나" 재구성 | "왜"를 요구하는 규제·고객 대응을 로그만으로 | 중 (불변 저장소·보존·열람 통제) | 표준 | `[검증]` |
| 규칙 트레이스 (발화 규칙 ID 기록) | 권한·한도·게이트 결정의 설명. 결정론적이라 가장 신뢰 | 자연어 의미 판단의 설명(규칙이 없는 영역) | 하 | 표준 | `[검증]` |
| 온톨로지·그래프 경로 기반 설명 | 멀티홉 근거, "왜 이 문서가 관련되나"를 개념 경로로. 규제 심사 대응 | 온톨로지 없음, 비정형 서술 단일 문서 QA(citation으로 충분) | 상 (온톨로지 구축·유지) | 시험 | `[검증-단일저자]` arXiv 2604.00555 접지 보고, `[2차]` 그래프 벤더 프레이밍 |
| citation 자동 검증 (근거 ⊂ 검색 결과) | 생성이 실제 검색 근거를 썼는지 기계 검증 | 근거 해석의 정확성(judge·사람 필요) | 하 | 안정 | `[2차]` |
| 결정 모델 보정 확률 활용 | 승인 임계값의 근거 제시("확신 0.62 < 0.8이라 사람에게"), 확신도 분포 감사 | 보정 미측정 상태, 결정 사유 설명 요구, 한국어 미실측 | 하 (호출) / 중 (보정 측정) | 신생 | `[벤더]` 보정 주장, `[2차]` |
| LLM 생성 설명 | 사용자 편의 텍스트, 비규제 맥락 | **감사·규제 설명의 근거**. 사후 합리화 위험 | 하 | 안정 | `[2차]` 불일치 사례 보고 |
| 사람 리뷰 기록 (HITL 승인·정정 이력) | 고위험 결정의 책임 증명 | 전수 적용(승인 피로) | 중 | 표준 | `[검증]` |
| 모델 카드·시스템 카드·데이터 시트 | 규제 기술 문서, 외부 공개 투명성 | 운영 중 개별 결정 설명 | 중 (작성·유지) | 안정 | `[2차]` 업계 관행 |
| 정책 엔진 (OPA 등)으로 승인·권한 중앙화 | 규칙 변경을 코드 리뷰·테스트로, 결정 로그 자동 | 규칙이 몇 개뿐인 소규모(과잉) | 중 | 안정 | `[검증]` |

### 선택 가이드

- **사람에게 영향을 주는 결정이나 되돌릴 수 없는 행동이 있다면** → 감사 로그 + 규칙 트레이스 + 사람 승인 기록은 필수, 법무와 위험 분류. 이유: 재구성과 책임 증명이 안 되면 운영 불가
- **"왜 이 근거인가"를 심사받는다면** → 온톨로지·그래프 경로 + citation 자동 검증. 이유: 결정론적이고 데이터에 실재하는 경로. 단 온톨로지 투자가 선행([Part 2/06](../02-data-pipeline/06-ontology-driven-modeling.md))
- **결정 모델로 승인을 거른다면** → 보정 곡선을 `[실측]`하고 임계값 근거를 문서화, 결정 사유는 규칙·온톨로지로 병행. 이유: 보정 확률은 "얼마나"만 답하고 "왜"는 못 답한다
- **사용자에게 이유를 보여주고 싶다면** → LLM 생성 설명은 보조 텍스트로, 감사 설명과 구분 표시. 이유: 사후 합리화를 공식 설명으로 삼으면 감사에서 뒤집힌다
- **판단이 어려우면** → 기본값: 트레이스 부분집합을 불변 저장 + 규칙 ID·citation·확신도 기록 + 책임자 표 + 삭제 전파 목록. 이유: 비용이 낮고 어떤 규제 분류에서도 기반이 된다

## 설계 시 고려사항 (체크리스트)

### 레이어별

- [ ] 시스템의 용도가 어느 위험 분류에 해당하는지 법무 검토를 받았고, 적용 의무 목록이 있는가
- [ ] 감사 레코드가 "누가·근거·판정·확신도·결과·승인" 다섯 요소를 모두 담고, 불변·장기·열람 기록 요건을 충족하는가
- [ ] (Knowledge) 근거 ID와 함께 **인덱스 버전**이 기록되고, 그 시점의 근거 본문을 복원할 수 있는가
- [ ] (Knowledge) 삭제 요청이 인덱스·그래프·임베딩에 전파되는 메커니즘이 있는가
- [ ] (Reasoning) 판정 지점마다 설명 요구 수준(없음·로그·규칙 트레이스·경로 설명)이 표시되고 수단이 배정됐는가
- [ ] (Reasoning) 발화한 규칙 ID가 기록되는가. 규칙 변경이 코드 리뷰·테스트·승인을 거치는가
- [ ] (Reasoning) 결정 모델 보정이 신뢰도 다이어그램으로 측정됐고, 임계값 근거가 문서화됐는가
- [ ] (Reasoning) LLM 생성 설명이 감사 설명과 분리되어 저장·표시되는가
- [ ] (Interaction) 승인 이벤트가 승인자·시각·대상 컴포넌트·서버 재검증 결과와 함께 기록되는가
- [ ] (Interaction) 사용자에게 보이는 설명·citation이 감사 레코드의 것과 같은 ID를 가리키는가
- [ ] 변경 대상 7종(모델·프롬프트·인덱스·규칙·컴포넌트·툴·용도)별 승인자와 게이트가 정의되고 배포 파이프라인에 연결됐는가 ([05](05-llmops-agentops.md))
- [ ] 책임 지점(모델·데이터·규칙 오너, 승인자, 온콜, 컴플라이언스)이 사람 이름으로 지정됐는가
- [ ] 삭제 전파 목록에 캐시·메모리·트레이스 본문·골든셋이 포함되는가
- [ ] 감사 레코드 보존 의무와 삭제 의무가 충돌하는 경우의 처리(익명화)가 정해졌는가

### 레이어 간 정합성 검토

- [ ] Part 2의 citation ID, Part 3의 생성 citation, Part 4의 승인 이벤트가 **하나의 감사 레코드**에 모이는가, 아니면 세 저장소를 조인해야 하는가
- [ ] Part 3에서 결정 모델 확신도를 승인 임계값으로 쓰는데, Part 4의 승인 UI는 그 확신도를 승인자에게 보여주는가(승인자가 무엇을 승인하는지 모름)
- [ ] Part 2에서 접근 제어를 정교하게 했는데 감사 레코드·트레이스 본문 저장소는 누구나 열람 가능한가(근거 본문이 감사 저장소로 우회 노출)
- [ ] Part 3의 규칙 변경은 승인을 거치는데 Part 4의 컴포넌트 카탈로그 변경(승인 카드 문구·버튼)은 프론트 배포로 그냥 나가는가 — 승인 UI 변경은 승인 흐름 변경이다
- [ ] Part 2에서 온톨로지를 구축했는데 Part 3의 설명은 LLM 생성 텍스트뿐인가(경로 설명 자산을 안 쓰고 있음)
- [ ] 삭제 요청이 Part 2 인덱스에는 전파되는데 Part 3 메모리·Part 5 캐시·트레이스에는 안 되는가
- [ ] 멀티 에이전트(A2A)에서 위임 체인이 감사 레코드에 남는가 — "어느 에이전트의 판정이었나"
- [ ] 세 레이어의 변경이 **한 릴리스 번들**로 승인되는가, 레이어별로 따로 승인되어 조합이 미승인 상태로 운영되는가 ([05](05-llmops-agentops.md))

## 한계와 리스크

| 한계 | 영향 | 완화책 |
|---|---|---|
| 규제 해석의 불확실성 | 분류·의무를 잘못 가정 | 법무 검토, 일반 요건(기록·투명성·인간 감독)은 분류와 무관하게 갖춤 |
| LLM 설명의 사후 합리화 | 감사에서 설명과 실제 과정 불일치 | 결정론적 수단 우선, LLM 설명은 보조로 분리 표시 |
| 결정 모델 보정 미확인 | 임계값이 무의미, "확신 0.9"가 감사에서 근거 못 됨 | `[실측]` 보정 곡선, 주기 재측정, 설명은 규칙·온톨로지로 |
| 온톨로지 유지 비용 | 설명 경로가 낡거나 틀림 | 소유자 지정, 변경도 승인 대상, 경로 ≠ 사용 보장이므로 citation 병행 |
| 감사 저장소의 비용·PII | 장기 보존 비용, 저장소 자체가 유출 지점 | 부분집합만, 마스킹, 접근 통제, 열람 기록 |
| 보존 의무 vs 삭제 의무 충돌 | 둘 중 하나 위반 | 익명화 보존, 법무 판단 기록 |
| 승인 피로 | 승인자가 내용 안 보고 승인 → 책임 증명 무력 | 위험 등급별 승인, 승인 UI에 근거·확신도 표시, 승인 소요 시간 모니터 |
| 뉴로심볼릭 결합 전체의 검증 미성숙 | "규칙은 검증됐다"가 시스템 검증은 아님 | 신경·기호 부분 별도 검증 + E2E 골든셋 `[검증]` Renkhoff et al. |
