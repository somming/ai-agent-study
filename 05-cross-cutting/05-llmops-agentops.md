# LLMOps / AgentOps

> **범위**: 배포, 버전 관리, 평가 파이프라인, 롤백. 세 레이어의 산출물(모델·프롬프트·인덱스·툴·컴포넌트)을 **하나의 릴리스 단위**로 다루는 운영 체계. 평가 수단 자체는 [Part 1/06](../01-foundations/06-evaluation-observability.md), 트레이스·대시보드는 [03](03-observability-tracing.md), 변경 승인 주체는 [04](04-governance-explainability.md).

## 요약 (3줄)

1. 에이전트 시스템에서 버전 관리 대상은 코드가 아니라 **다섯 가지 — 모델, 프롬프트, 인덱스, 툴·MCP 서버, 컴포넌트 카탈로그 — 의 조합**이다. 하나만 바꿔도 나머지와의 호환이 깨지므로 조합을 **릴리스 번들**로 묶어 배포·롤백한다.
2. 배포 게이트는 평가 파이프라인이다. 규칙 체크(CI) → 골든셋 회귀 → judge 샘플링 → 카나리·섀도 비교를 통과하지 못하면 번들은 나가지 않는다. "프롬프트 한 줄 고치는 건데"가 가장 흔한 사고 원인이다.
3. 장애는 모델 API만 나는 게 아니다. **결정 모델 장애, 벡터DB 장애, MCP 서버 장애, 비용 폭주, 조용한 품질 저하**가 각각 다른 폴백을 요구한다. 폴백 없는 의존성은 단일 장애점이다.

## 이 단계에서 무엇을 · 언제 · 어떻게 · 왜

| 질문 | 답 |
|---|---|
| **무엇을** (What) | ① 버전 관리 대상 목록과 저장소 ② 릴리스 번들 매니페스트(조합·호환 매트릭스) ③ 배포 파이프라인(게이트·카나리·섀도·롤백) ④ 인덱스 재구축 운영 절차 ⑤ 의존성별 장애 대응 런북과 폴백 ⑥ 환경 분리 정책 ⑦ 비용·품질 대시보드([03](03-observability-tracing.md)) |
| **언제** (When) | **첫 운영 배포 전**에 번들 매니페스트와 롤백 수단. 카나리·섀도는 트래픽이 비교 가능해진 뒤. 생략 가능: 내부 도구의 섀도 배포. 미룰 수 없는 것: 버전 기록(트레이스에 버전이 없으면 사후 비교 불가)과 폴백 |
| **어떻게** (How) | ① 다섯 대상의 버전 식별자와 저장 위치를 정한다 → ② 호환 매트릭스(무엇이 바뀌면 무엇을 다시 평가·재구축하나)를 적는다 → ③ 번들 매니페스트를 배포 단위로 → ④ 평가 게이트를 파이프라인에 → ⑤ 카나리(트래픽 %) 또는 섀도(병렬 비노출)로 비교 → ⑥ 롤백 단위·절차·소요 시간 확인 → ⑦ 의존성별 폴백과 런북 → ⑧ 레이어 간 정합성 검토 |
| **왜** (Why) | 프롬프트만 고쳤는데 결정 모델 라우팅 분포가 바뀌고, 임베딩 모델을 올렸는데 인덱스를 재구축 안 해 검색이 무너지고, 컴포넌트 카탈로그를 바꿨는데 UI 선택 프롬프트는 옛 이름을 참조한다 — 모두 "조합"을 관리하지 않아 생기는 사고다. 롤백 수단이 없으면 사고가 길어진다 |

## 문제와 맥락

MLOps는 모델 아티팩트와 학습 파이프라인을, DevOps는 코드와 인프라를 관리한다. 에이전트는 둘 사이에 **프롬프트(코드이자 설정), 인덱스(데이터이자 아티팩트), 툴 정의(외부 계약), 컴포넌트 카탈로그(프론트 계약)** 를 추가한다. 이들은 저장소도 다르고(코드 저장소, 프롬프트 레지스트리, 벡터DB, MCP 서버, 디자인 시스템 패키지) 배포 주기도 다르며 소유 팀도 다르다. 그런데 런타임에서는 한 요청 안에서 함께 동작한다.

세 레이어의 운영이 따로 돌면 생기는 전형적 사고: Part 2 팀이 임베딩 모델을 교체해 인덱스를 재구축하는 동안 Part 3의 검색이 구·신 인덱스가 섞인 결과를 받고, Part 4 팀이 컴포넌트 이름을 바꿔 배포했는데 Part 3의 의도→UI 매핑은 재평가되지 않아 렌더 실패율이 뛴다. 이 페이지는 이 조합을 **한 단위**로 다룬다.

## 핵심 개념

### 버전 관리 대상 5종 (+ 부속 3종)

| 대상 | 버전 식별자 | 저장 위치 | 바뀌면 다시 해야 하는 것 |
|---|---|---|---|
| **모델** (생성·결정·임베딩·리랭크·judge) | 모델 ID + 버전/스냅샷 + 주요 파라미터 | 설정 저장소(코드와 함께) | 골든셋 회귀, 보정 재측정(결정 모델), 임베딩 모델이면 **인덱스 전체 재구축** |
| **프롬프트** (시스템·템플릿·few-shot·결정 질문 정의) | 해시 또는 시맨틱 버전 | 코드 저장소 또는 프롬프트 레지스트리 | 골든셋 회귀, 레드팀 셋, 프롬프트 캐시 무효화 영향 확인 |
| **인덱스** (청크·임베딩·그래프·메타데이터) | 임베딩 모델 버전 + 청킹 설정 + 데이터 스냅샷 시각 | 벡터DB·그래프DB 컬렉션(버전별) | recall 프록시 비교, ACL 테스트, citation ID 호환 확인 |
| **툴·MCP 서버** | 툴 스키마 버전 + 서버 ID·버전(정의 해시) | 툴 레지스트리, MCP 서버 배포 | 툴 선택 정확도, 권한 매트릭스, 인젝션 검사([01](01-security-prompt-injection.md)) |
| **컴포넌트 카탈로그** | 패키지 시맨틱 버전 + 스키마 해시 | 디자인 시스템 패키지, 레지스트리([Part 4/03](../04-dynamic-ui/03-component-registry-schema.md)) | 의도→UI 매핑 재평가, 스키마 호환, 렌더 테스트 |
| (부속) 규칙·정책 세트 | 코드 버전 | 코드 저장소·정책 엔진 | 규칙 테스트 스위트 |
| (부속) 온톨로지 | 시맨틱 버전 | 온톨로지 저장소 | 추출 검증(SHACL), enum 접지, UI 매핑 |

### 릴리스 번들과 호환 매트릭스

```
bundle: 2026.10.11-r3
  model.generate: M-large@2026-08 / M-small@2026-08
  model.decision: Jev@ea-2026-09 (fallback: rules-v41)
  model.embed:    E@v3           ← index.v12와 묶임
  prompt.answer:  v7  (sha 3f2a…)
  index.docs:     v12 (E@v3, chunk=recursive-800, snapshot 2026-10-10T02:00)
  tools:          search@2, ticket@5 (mcp://tickets v1.3, def-hash 9c…)
  ui.catalog:     @4.2.0
  rules:          v41
```

호환 규칙의 예: `model.embed`가 바뀌면 `index.*`는 같은 번들에서 재구축본으로 교체돼야 한다. `ui.catalog`가 메이저 변경이면 `prompt.ui_select` 또는 결정 질문 정의가 재평가돼야 한다. `model.generate`가 바뀌면 `prompt.*` 전부 회귀 대상이다. 이 규칙을 매니페스트 검증기로 코드화하면 불완전한 번들이 파이프라인에서 거부된다.

### 평가 파이프라인을 게이트로

```
변경 PR ─▶ 매니페스트 검증(호환 규칙) ─▶ 규칙 체크 CI(스키마·citation·금칙어·규칙 테스트)
       ─▶ 골든셋 회귀(단계별 지표, 임계값 미달 시 차단) ─▶ judge 샘플링(보정된 judge, 버전 고정)
       ─▶ 레드팀 셋(인젝션·한국어) ─▶ 승인([04]) ─▶ 스테이징 ─▶ 섀도 또는 카나리 ─▶ 전면
```

게이트 기준은 **단계별**로 둔다([Part 1/06](../01-foundations/06-evaluation-observability.md)). 라우팅 정확도·보정, recall@k, faithfulness, 툴 선택 정확도, 검증 거부율, UI 선택 정확도, E2E 완료율. 한 지표가 오르고 다른 지표가 떨어지는 변경(예: 생성 품질↑, 지연·비용↑)은 자동 통과가 아니라 사람 판단으로 보낸다.

### 카나리 vs 섀도

- **카나리**: 트래픽 일부(1~5% → 확대)를 신 번들로. 실사용자 영향이 있으므로 롤백 자동화와 지표 비교(지연·오류·거부율·완료율)가 전제. 비용 추가 거의 없음
- **섀도**: 전 트래픽을 신 번들에도 보내되 응답은 노출하지 않음. 사용자 영향 0, 비용 2배. **행동(툴 실행)이 있는 에이전트는 섀도에서 쓰기 툴을 반드시 모의(mock)** — 섀도가 실제 티켓을 두 번 만든다

### 롤백 단위와 소요 시간

| 대상 | 롤백 방법 | 소요 | 주의 |
|---|---|---|---|
| 모델·프롬프트·규칙·툴 정의 | 번들 포인터 되돌리기 | 초~분 | 프롬프트 캐시 무효화로 일시 비용↑ |
| 인덱스 | 이전 버전 컬렉션으로 포인터 전환(**블루-그린**) | 초~분, 단 이전 버전을 보존했을 때만 | 재구축으로 롤백하면 시간~일. 최소 1세대 보존 |
| 컴포넌트 카탈로그 | 프론트 패키지 롤백 + 매핑 프롬프트/질문 정의 동반 롤백 | 분 (프론트 배포 주기) | 캐시된 프론트 자산 |
| 메모리(장기) | **롤백 불가** — 신 버전이 저장한 메모리가 남음 | — | 메모리 스키마 변경은 마이그레이션 계획, 버전 태그 |
| 외부 상태(툴이 만든 티켓·전송) | 롤백 불가 — 보상 트랜잭션 | — | 카나리 범위 최소화, 쓰기 툴 승인 |

롤백은 **번들 단위**가 기본이다. 프롬프트만 되돌리면 그 프롬프트가 전제했던 모델·카탈로그와 어긋날 수 있다.

### 인덱스 재구축·재임베딩 운영

- **트리거**: 임베딩 모델 교체, 청킹 설정 변경, 메타데이터 스키마 변경, 대규모 소스 변경, 품질 저하(recall 프록시 하락)
- **절차**: 비용 추정(문서 수 × 토큰 × 임베딩 단가 + 파이프라인 내 AI 호출([Part 2/09](../02-data-pipeline/09-ai-inside-the-pipeline.md))) → 병렬 컬렉션 구축 → 골든셋 recall@k·citation 호환 비교 → 포인터 전환 → 이전 세대 보존 → 증분 동기화 재개([Part 2/07](../02-data-pipeline/07-freshness-and-sync.md))
- **청크 ID 안정성**: 재구축으로 청크 ID가 바뀌면 감사 레코드의 citation이 끊긴다([04](04-governance-explainability.md)). 결정론적 ID(문서 ID + 오프셋 해시) 또는 구·신 ID 매핑 보존

### 온콜·장애 대응 — 의존성별 폴백

| 장애 | 증상 | 폴백 | 런북 핵심 |
|---|---|---|---|
| 생성 모델 API | 오류율·지연 급증 | 동일 벤더 다른 모델 → 타 벤더 동급 → 축소 모드(캐시·소형) | 프롬프트가 모델 간 호환되는지 사전 테스트. 게이트웨이에서 전환 |
| **결정 모델** (Jev / Decisions API) | 판정 오류·타임아웃 | 규칙 폴백(보수적 기본 경로) → 소형 LLM 재판정 → 사람 경로 확대 | "확신 없음 = 사람에게"가 기본. 베타 서비스의 상태·가격 변경 모니터 `[2차]` |
| 벡터DB·그래프DB | 검색 0건·지연 | 읽기 복제본 → 결과 캐시 → "근거 없음" 명시 응답(환각 대신) | 근거 없이 생성하지 않도록 생성 게이트 |
| MCP 서버·툴 | 툴 오류 | 해당 툴 비활성 + 사용자 안내 → 대체 툴 | 툴 정의 변경(rug pull) 감지 시 자동 차단([01](01-security-prompt-injection.md)) |
| 비용 폭주 | 요청당 비용·일 비용 급증 | 상한 차단·축소 모드([02](02-cost-latency-model-routing.md)) | 루프 버그 여부 확인, 스텝 상한 |
| 조용한 품질 저하 | judge 점수·완료율·citation율 하락, 확신도 분포 이동 | 직전 번들로 롤백 | 릴리스 직후 알림 민감도↑, 카나리 비교 |
| 보안 사고 | 인젝션 탐지·규칙 거부 급증 | 쓰기 툴 전면 승인 모드, 의심 MCP 서버 차단 | 보안 온콜 연계, 트레이스 100% 보존 |

### 환경 분리

dev / staging / prod는 **인덱스·메모리·MCP 서버·캐시·비용 계정·관측 백엔드**를 모두 분리한다. 흔한 누락: dev가 prod 벡터DB를 읽어 평가 결과가 오염되거나, staging 에이전트가 prod MCP 서버에 쓰기 호출을 한다. 운영 데이터로 평가하려면 익명화 사본을 staging으로. 프롬프트·규칙의 prod 핫패치는 금지 — 번들 파이프라인으로만.

### 1/07 정의와의 연결 — 이 페이지는 어디에 놓이는가

[Part 1/07](../01-foundations/07-operations-vocabulary.md)의 어휘로 이 페이지는 **유지보수성**("안전하게 바꿀 수 있는 성질")의 운영 체계이고, 통제 세 층 중 **교정 층**(롤백·킬 스위치·폴백)의 실행 수단이다. 1/07이 명시한 **버전 관리 대상 5종**(모델·프롬프트·인덱스·툴·컴포넌트 카탈로그)이 이 페이지 "버전 관리 대상" 표의 뼈대이고, 1/07의 카나리·섀도·피처 플래그·롤백 단위·ORR 용어를 그대로 쓴다. 평가 게이트는 변경 관리([04](04-governance-explainability.md))가 "배포 게이트로 구현"되는 자리이며, 위험 등급표의 접점은 **변경 자체의 등급**이다 — 프롬프트 한 줄은 등급 1~2 변경, 가드레일 규칙·승인 매트릭스 변경은 4([Part 3/12](../03-agent-workflow-rag/12-guardrails-hitl.md)), 프레임워크 메이저 업은 4([Part 3/14](../03-agent-workflow-rag/14-frameworks-landscape.md)), 임베딩 모델 교체는 인덱스 전환이 포함되므로 2(별칭 롤백 가능)지만 재구축 비용 때문에 절차는 무겁다. 거버넌스 구성 요소로는 "변경 관리"의 실행이고, RACI의 "모델 버전 교체 A = 아키텍트"가 번들 서명자다.

### 변화 대응 — 이 횡단 관심사가 바뀔 때

LLMOps는 다른 페이지의 변화를 **흡수하는 절차 그 자체**이므로, 여기서 "변화 대응"은 두 질문이다. ① 어떤 변경이 어떤 평가·배포 절차를 트리거하는가(이 매핑이 없으면 모든 변경에 전체 스위트가 돌거나, 아무것도 안 돈다) ② 이 절차 자체(호환 규칙·게이트 임계값·롤백 절차)가 바뀔 때 어디서 흡수하는가.

**변경 유형 → 트리거되는 평가·배포 절차 매핑** — [Part 1/06](../01-foundations/06-evaluation-observability.md)의 평가 수단 4층(규칙 · 참조/골든셋 · LLM-as-judge · 사람)과 [Part 3/13](../03-agent-workflow-rag/13-evaluation-rag-agents.md)의 L1~L4 체계(L1 규칙 / L2 골든셋 / L3 트래젝토리 / L4 judge)에 연결. 각 Part의 단계 페이지가 "회귀 테스트" 열에 적은 것을 번들 수준에서 합친 표다.

| 변경 유형 (1/07 분류) | 전형적 변경 | 트리거되는 평가 | 배포 방식 | 롤백 단위 | 변경 등급 (예시) |
|---|---|---|---|---|---|
| **모델** — 생성 LLM 버전·벤더 | 핀 이동, 벤더 교체 | L1 스키마 + **전체 L2 골든셋** + L3(에이전트 구간) + L4 샘플 + 보정 재측정, 레드팀 셋 | 카나리 5%(예시) → 확대 | 모델 핀 + 프롬프트 세트 + 파라미터 | 2~3 |
| **모델** — 임베딩 | 모델·차원 교체 | recall@k 골든셋(한국어 하위셋), ACL 필터 테스트, 청크 크기 재검토 | **인덱스 블루-그린** + 별칭 전환, 시맨틱 캐시 전체 무효화 | 임베딩 모델 + 청킹 규칙 + 인덱스 별칭 + 질의 측 설정 | 2 (전환), 재구축 비용 大 |

| **프롬프트·질문 정의** | 지시·예시·abstain 조건·선택지 | 해당 단계 L2 골든셋 + 레드팀 셋 + 스키마 실패율 | 번들 포인터(카나리 선택) | 프롬프트 + 모델(호환 매트릭스 셀) | 1~2 |
| **지식** — 소스·인덱스 내용 | 문서 변경·삭제·소스 추가 | 증분은 무평가(2/07 멱등 재처리). 소스 추가는 ACL 테스트 + recall 프록시 | 변경 큐(배포 아님). 소스 추가는 데이터 소유자 승인 | 해당 문서 파생물 / 톰스톤 | 1 (소스 추가 2~3) |
| **도메인 모델** — 온톨로지·택소노미 | 추가(마이너) / 개명·병합(매핑) / 분할(재추출) | 범위 질문 + 변환 diff + 추출 위반율 샘플 + 매핑 완전성; 분할은 enum 소비자(3/10·3/11·4/05) 골든셋까지 | 온톨로지 릴리스 번들, 분할은 블루-그린 그래프 | 온톨로지 + SHACL + 매핑 + 변환 산출물 | 2 (마이너) / 3 (메이저) |
| **규칙·정책** — 가드레일·승인·권한·한도 | 규칙 추가·한도 변경·승인자 변경 | **규칙 테스트 스위트**(허가·차단·승인·우회 패턴) + L3 게이트 차단율 + 매트릭스 커버리지 | 규칙 버전 + **시행일**(배포 아님). 보안·권한·한도는 자동 롤백 제외 | 규칙 세트 단독 / 매트릭스 + 역할 정의 | **4** (규칙·매트릭스 변경 자체) |
| **툴·MCP 서버** | 서버 등록, 스키마 변경, 등급 조정 | 툴 계약 테스트 + 툴 선택·인자 골든셋 + 인젝션 검사 + 권한 매트릭스 | 레지스트리 등록(설정). 등급 3 이상 툴은 보안 검토 | 툴 스키마 + 결과 파서 + 게이트 규칙 | 툴 등급 1:1 |
| **컴포넌트 카탈로그·UI 스키마** | 컴포넌트 추가·폐기·props 변경 | 스키마 호환 + 선택 정확도 골든셋 + 렌더 스냅샷 + 접근성 자동 검사 | 카탈로그 마이너/메이저, deprecated 기간, 프론트 배포를 번들과 동기화 | 카탈로그 ↔ 응답 스키마 ↔ 렌더러 바인딩 ↔ 매핑 테이블 | 1 (`actions` 보유 컴포넌트는 상속) |
| **사용자 환경** — 조직·언어·플랫폼 | 승인자·그룹 변경, 언어 추가, 모바일 | 조직: 매트릭스 정합성 검사만. 언어: 언어별 골든셋·보정 셋. 플랫폼: 렌더러 `[실측]` + 지원 매트릭스 | 데이터 변경(조직) / 리소스 추가(언어) / 바인딩 추가(플랫폼) | 매핑 데이터 / 리소스 / 바인딩 | 1 (조직은 데이터) |
| **프로토콜·SDK** — 프레임워크·MCP·AG-UI·A2UI | 메이저 업, 스펙 개정 | **어댑터 계약 테스트**(상태·hooks·트레이스·재개·이벤트 녹화본) + 전체 L2·L3 + hooks 호출률 100% | 버전 고정 → **계획된 업그레이드 창**(분기 1회 예시) → 카나리 팀 | 프레임워크 + 어댑터 + 체크포인트 마이그레이션 | **4** (2인 승인) |
| **부하** | 10배 | 부하 테스트(캐시 적중률·큐 깊이·p95) | 인프라 변경, 설정(상한·배치 크기) | 설정 | 1 |

이 표가 **변경 → 트리거 매핑 커버리지**([Part 3/13](../03-agent-workflow-rag/13-evaluation-rag-agents.md))의 번들 수준 원본이다. 어떤 버전 관리 대상이 이 표에 행이 없으면 그 변경은 평가 없이 나가고 있다.

**절차 자체의 변화 흡수**

| 변화 | 바뀌는 것 | 안정적으로 유지할 것 | 흡수 방식 |
|---|---|---|---|
| 호환 규칙 추가·변경(예: "카탈로그 메이저 → 매핑 재평가") | 매니페스트 검증기의 규칙 | 번들 매니페스트 스키마 | **호환 매트릭스를 코드 밖 데이터**(규칙 테이블)로 두고 검증기는 테이블을 읽는다. 규칙 추가 = 행 추가 |
| 게이트 임계값(통과율·faithfulness 하한·카나리 비율) | 배포 엄격도 | 지표 정의 | 임계값 표(설정) + 과거 결과 재적용으로 영향 확인. 완화는 변경 관리 승인(등급 3 상당, [Part 3/13](../03-agent-workflow-rag/13-evaluation-rag-agents.md)) |
| 평가 수단 교체(judge 모델, 평가 라이브러리) | L4 결과 분포 | judge 포트, 지표 정의 | judge 고정 + 보정 셋 재정렬 + 베이스라인 재설정, 비교 금지 기간 선언 |
| 배포 도구·레지스트리 교체(프롬프트 레지스트리, 모델 게이트웨이) | 저장 위치·전환 방식 | 번들 매니페스트(도구 중립 형식) | 어댑터 교체. 매니페스트가 도구 API를 참조하면 안 된다 |
| 환경 추가(새 리전, 새 테넌트 전용 환경) | 분리 대상 6종의 인스턴스 | 환경 분리 원칙 | 환경 레지스트리에 행 추가, 교차 접근 카나리(dev → prod 읽기 0건) |

코드 밖 설정으로 둘 것: 호환 매트릭스(규칙 테이블), 게이트 임계값 표, 카나리 비율·확대 조건, 변경 → 트리거 매핑표, 인덱스 보존 세대 수, 환경 레지스트리, 롤백 소요 시간 목표. 시점 재현: 모든 트레이스·감사 레코드에 **릴리스 번들 버전**이 있으면 다섯 대상의 조합을 한 번에 복원한다 — 이것이 번들을 두는 가장 큰 이유다.

판단 기준: 변경 유형마다 **"배포인가, 설정 교체인가, 데이터 변경인가"**를 먼저 묻는다. 모델·프레임워크는 배포(번들·카나리·2인), 규칙·θ·프롬프트·카탈로그는 설정 교체(버전·시행일·골든셋), 지식·조직은 데이터 변경(큐·매핑, 평가 없음). 세 범주의 절차 무게를 뒤섞으면 — 규칙 변경에 전체 L2를 돌리거나, 모델 교체를 설정 교체로 처리하거나 — 어느 쪽이든 사고가 난다.

### 선택 가이드

- **대상이 3종 이상이고 팀이 여럿이라면** → 릴리스 번들 매니페스트 + 호환 검증기 + 평가 게이트. 이유: 조합 사고를 파이프라인에서 막는 유일한 수단
- **임베딩 모델·청킹을 바꾼다면** → 인덱스 블루-그린 + recall 비교 + 청크 ID 안정성 확보. 이유: 재구축 롤백은 시간~일, 포인터 전환은 초
- **행동(쓰기 툴)이 있는 에이전트를 비교 배포한다면** → 카나리 소량 또는 쓰기 모의 섀도. 이유: 섀도가 실제 행동을 중복 실행하면 안 된다
- **결정 모델·단일 벤더 의존이 크다면** → 모델 게이트웨이 + 규칙 폴백 + 베타 상태 모니터. 이유: 신생 서비스의 가격·상태 변경과 장애를 흡수
- **판단이 어려우면** → 기본값: Git에 프롬프트·설정, 번들 매니페스트 1장, 규칙 CI + 골든셋 회귀 게이트, 카나리 5%, 인덱스 1세대 보존, 의존성별 폴백 표. 이유: 모두 기존 DevOps 도구로 가능

## 설계 시 고려사항 (체크리스트)

### 레이어별

- [ ] 다섯 대상(+부속)의 버전 식별자가 정의되고 **트레이스에 기록**되는가 ([03](03-observability-tracing.md))
- [ ] 평가 게이트가 단계별 지표로 구성되고 임계 미달 시 배포가 차단되는가. judge 모델 버전이 고정됐는가
- [ ] (Knowledge) 인덱스가 버전별 컬렉션으로 관리되고 최소 1세대가 보존되는가. 청크 ID가 재구축에도 안정적인가
- [ ] (Reasoning) 결정 모델 장애 시 규칙 폴백·보수적 기본 경로가 **코드로** 있고 테스트됐는가. 보정 재측정이 모델 변경 게이트에 포함되는가
- [ ] (Interaction) 컴포넌트 카탈로그 변경이 의도→UI 매핑 재평가를 트리거하는가. 프론트 배포가 번들과 동기화되는가
- [ ] 롤백이 번들 단위로 수행되고, 소요 시간이 측정·연습됐는가. 롤백 불가 대상(메모리·외부 상태)의 계획이 있는가
- [ ] 환경별로 인덱스·메모리·MCP 서버·캐시·비용 계정·관측 백엔드가 분리됐는가. prod 핫패치가 기술적으로 막혀 있는가

### 레이어 간 정합성 검토

- [ ] Part 2의 인덱스 재구축과 Part 3의 검색 설정(top-k·리랭크)·Part 4의 citation 렌더가 **같은 번들**에서 바뀌는가, 아니면 Part 2가 먼저 나가 구·신 혼재 구간이 생기는가
- [ ] Part 4의 카탈로그 변경이 프론트 팀 배포 주기로 따로 나가고 Part 3의 매핑은 그대로인가 — 렌더 실패율 급증의 전형
- [ ] Part 3에서 결정 모델을 라우팅에 쓰는데, 폴백(규칙)이 Part 2의 인덱스 구조·Part 4의 UI 의도까지 커버하는가(폴백 경로에서 UI 의도가 비어 렌더 실패)
- [ ] Part 2 임베딩 모델 교체 시 Part 3의 시맨틱 캐시([02](02-cost-latency-model-routing.md))도 무효화되는가(구 임베딩 공간의 캐시 적중)
- [ ] 섀도 배포에서 Part 3의 쓰기 툴은 모의했는데 Part 4의 승인 이벤트가 실제 승인 큐로 들어가는가
- [ ] 장애 시 축소 모드가 Part 3의 검증·Part 1/01의 보안 계층을 생략하지 않는가
- [ ] 세 레이어의 변경 승인자([04](04-governance-explainability.md))가 한 번들에 서명하는가, 레이어별 승인이 조합 미승인 상태를 만드는가
