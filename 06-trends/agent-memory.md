# 에이전트 메모리 생태계

> **범위**: 메모리 프레임워크 분화, 벤치마크(LoCoMo, LongMemEval), no-memory 베이스라인 교훈

> **한 줄 정의**: 에이전트가 턴·세션을 넘어 정보를 **저장·조회·갱신**하는 계층과 그 전용 프레임워크·벤치마크의 생태계. 최근 1년에 **대화 컨텍스트용**과 **운영 지식용**으로 분화했고, 벤치마크가 표준화되는 한편 **"메모리가 없는 편이 나았다"는 역결과**(MemTrapBench)가 나와 평가 기준 자체가 바뀌었다.
> **레이더 위치**: **관찰** — 벤치마크 표준화 보고가 메모리 벤더(Mem0) 발이라 `[벤더]`이고, 독립 결과(MemTrapBench)는 메모리 프레임워크 5종 모두가 no-memory 베이스라인보다 **나쁘다**고 보고한다 `[2차]`. 효과가 입증되기는커녕 역효과 증거가 있으므로 시험 전 단계에 둔다.

## 무엇이 바뀌었나 (최근 1년)

| 시점 | 사건 | 검증 수준 |
|---|---|---|
| 2025~26 | 메모리 생태계가 **대화 컨텍스트용**(사용자 선호·이전 대화 요약)과 **운영 지식용**(절차·사실·조직 지식)으로 분화 | `[2차]` |
| 2026 | **LoCoMo, LongMemEval, BEAM**이 메모리 프레임워크 비교의 표준 벤치마크로 자리잡았다는 보고 — Mem0 발 | `[벤더]` |
| 2026 | **MemTrapBench**: 메모리 프레임워크 5종 모두 **no-memory 베이스라인보다 나쁨**. 관련 기억이 이전 과업 프레임에 모델을 고착시킴 | `[2차]` |
| 2026 | 벤더 네이티브 SDK(Claude Agent SDK, OpenAI Agents SDK, Google ADK)가 세션·메모리를 런타임 기능으로 흡수. ADK는 메모리를 컨텍스트 뷰의 한 원천으로 조립 | `[2차]` `[벤더]` |

이전에는 "메모리 = 대화 이력을 벡터 DB에 넣고 유사한 것을 꺼내기"였다. 바뀐 것은 ① 용도 분화, ② 표준 벤치마크의 등장, ③ **평가의 기준점이 "메모리 A vs 메모리 B"에서 "메모리 vs 메모리 없음"으로 이동**한 것이다. 상태·메모리의 단계별 구현은 [Part 3/08](../03-agent-workflow-rag/08-state-memory-context.md), 벤치마크의 평가 맥락은 [Part 1/06](../01-foundations/06-evaluation-observability.md)에 있다.

## 왜 주목받나

1. **멀티세션 에이전트의 필요**: 세션을 넘어 사용자 선호·진행 중 과업·조직 지식을 기억해야 하는 사용 사례가 늘었다. 매번 다시 묻는 에이전트는 쓸모가 떨어진다.
2. **컨텍스트 예산**: 전부 컨텍스트에 넣을 수 없으므로 "저장해 두고 필요할 때 꺼내는" 계층이 필요하다. 메모리는 [context-engineering](context-engineering.md)의 "선택" 결정에 공급되는 원천 중 하나다.
3. **벤더 생태계 형성**: 전용 메모리 프레임워크가 등장하고 벤치마크를 내세우며 경쟁한다. 이 경쟁이 "메모리를 넣으면 좋아진다"를 **전제**로 깔았다는 점이 문제였다.
4. **역결과의 충격**: MemTrapBench는 그 전제를 흔들었다. 관련성 높은 기억이 오히려 모델을 **이전 과업의 프레임에 고착**시켜 새 과업을 잘못 해석하게 한다 `[2차]`. 이는 메모리 설계의 핵심이 "무엇을 기억하나"가 아니라 **"언제 기억을 쓰지 않나"** 임을 시사한다.

## 핵심 메커니즘

### 용도 분화

| 구분 | 대화 컨텍스트용 메모리 | 운영 지식용 메모리 |
|---|---|---|
| 저장하는 것 | 사용자 선호, 이전 대화 요약, 진행 중 과업 상태 | 절차, 사실, 조직 규칙, 과거 해결 사례 |
| 생명주기 | 사용자·세션 단위. 갱신·망각 빈번 | 조직 단위. 검수·버전 관리 대상 |
| 실패 모드 | 오래된 선호 고착, 사생활 침해 | 잘못된 절차의 영속화, 근거 데이터와의 중복 |
| 경계 | [Part 3/08](../03-agent-workflow-rag/08-state-memory-context.md) | 사실상 RAG 코퍼스·근거 데이터와 겹침 → [Part 2/08](../02-data-pipeline/08-grounding-data-design.md) |

운영 지식용 메모리는 **근거 데이터 파이프라인과 경계가 모호**하다. "에이전트가 스스로 적어 두는 지식"이 검수 없이 쌓이면 근거 데이터의 거버넌스([Part 2/10](../02-data-pipeline/10-access-control-governance.md))를 우회하는 통로가 된다.

### 벤치마크가 측정하는 것

LoCoMo, LongMemEval, BEAM은 긴 대화·다중 세션에서 과거 정보를 정확히 회상·갱신하는 능력을 측정하는 벤치마크로 보고된다 `[벤더]`. 공통적으로 **"기억해야 할 것을 기억했는가"** 를 묻는다. MemTrapBench는 반대 질문 — **"기억하지 말아야 할 때 기억이 방해했는가"** — 을 묻고, 그 답이 5개 프레임워크 모두에서 부정적이었다 `[2차]`.

### no-memory 베이스라인 원칙

MemTrapBench의 방법론적 교훈은 한 문장이다: **메모리는 다른 메모리가 아니라 "메모리 없음"과 비교해 평가한다.** 메모리 프레임워크 간 순위는 둘 다 베이스라인보다 나쁠 때 무의미하다. 이 원칙은 [Part 1/06](../01-foundations/06-evaluation-observability.md)의 평가 설계에 반영한다.

## 벤더 주장 vs 검증된 사실

| 주장 | 출처 | 검증 수준 | 우리의 판단 |
|---|---|---|---|
| LoCoMo / LongMemEval / BEAM이 메모리 평가의 표준이 되었다 | Mem0 보고 | `[벤더]` | 메모리 벤더의 보고. 벤치마크 자체는 유용하나 "표준"이라는 지위 주장은 벤더 이해와 겹친다. 세 벤치마크의 원 논문은 노트에 미기록 → 확인 필요 |
| 특정 메모리 프레임워크가 벤치마크에서 우위 | 각 메모리 벤더 | `[벤더]` | 벤더 간 순위보다 **no-memory 대비** 수치를 요구한다. 그 수치가 없으면 판단 보류 |
| 메모리 프레임워크 5종 모두 no-memory 베이스라인보다 나쁘다 | MemTrapBench | `[2차]` | **가장 중요한 결과이나 `[2차]`**. 원 논문·측정 조건(과업 유형, 메모리 주입 방식) 확인 전까지 "메모리는 기본적으로 해롭다"로 일반화하지 않는다. 다만 평가 원칙(no-memory 대비)은 즉시 채택 |
| 관련 기억이 모델을 이전 과업 프레임에 고착시킨다 | MemTrapBench | `[2차]` | 메커니즘 설명으로 설득력 있음. 우리 과업에서 재현 테스트 가치 높음 |
| 벤더 SDK의 내장 메모리로 충분하다 | 각 벤더 SDK | `[벤더]` | 내장 메모리도 같은 기준(no-memory 대비)으로 평가한다. "내장"이 효과를 보장하지 않는다 |
| 메모리가 대화용·운영지식용으로 분화했다 | 생태계 관찰 | `[2차]` | 구분으로 채택. 운영 지식용은 근거 데이터 거버넌스와 통합해 다룬다 |

## 한계와 미해결 질문

| 한계 / 질문 | 왜 문제인가 | 현재 상태 |
|---|---|---|
| **역결과의 검증 수준** | MemTrapBench가 `[2차]`. 원 논문·조건 미확인 | 원문 확보 시 재조정 |
| **벤치마크의 벤더 편향** | "표준" 보고가 메모리 벤더 발 | 독립 재현 없음 |
| **과업 프레임 고착** | 관련성 기반 조회가 구조적으로 이 문제를 만든다면, 조회 방식 자체를 바꿔야 함 | 해법 미정립 — "언제 조회하지 않나"의 설계 |
| **망각·갱신 정책** | 오래된 선호·틀린 사실의 수정 절차 | 프레임워크마다 상이, 표준 없음 |
| **운영 지식 메모리의 거버넌스 우회** | 검수 없는 지식 축적 | 근거 데이터 파이프라인으로 편입 외 방법 없음 |
| **프라이버시** | 대화 메모리는 개인정보 저장소 | 보존 기간·삭제권·마스킹 설계 필요 |
| 한국어 대화 메모리 품질 | 벤치마크가 영어 중심일 가능성 | 미확인 |

## 우리 프로젝트에서의 채택 기준

"관찰"에서 "시험"으로: 멀티세션 요구가 실제 사용 사례에서 확인될 때. "시험"에서 "채택"으로 올리려면 아래가 `[실측]`되어야 한다. **비교군은 반드시 no-memory 구성**이다.

1. **no-memory 대비 효과 `[실측]`**: 같은 멀티세션 시나리오 골든셋에서 (a) 메모리 없음, (b) 메모리 있음의 과업 완료율·정답률·사용자 재질문 횟수를 비교. (b)가 (a)보다 **유의하게 나아야** 한다. 비슷하면 채택하지 않는다 — 비용과 프라이버시 부담만 남는다.
2. **과업 프레임 고착 재현 `[실측]`**: 이전 세션과 표면적으로 유사하지만 다른 과업을 주는 테스트 케이스를 만들어, 메모리 있음 구성이 이전 과업 프레임으로 잘못 해석하는 비율을 측정. MemTrapBench 결과를 우리 데이터로 재현하는 것이다.
3. **조회 게이팅 설계**: "이 턴에 메모리를 조회할지"를 판정하는 단계가 있고(규칙 또는 결정 모델, [decision-models](decision-models.md)), 조회하지 않은 경우의 품질이 기록된다.
4. **망각·갱신 정책 운영**: 틀린 기억을 사용자가 수정하거나 운영자가 삭제하는 경로가 있고 테스트되어 있다.
5. **거버넌스 통합**: 운영 지식용 메모리는 근거 데이터 파이프라인([Part 2/08](../02-data-pipeline/08-grounding-data-design.md))의 검수·권한을 거친다. 에이전트가 직접 쓴 지식은 검수 전까지 "미확인" 표시로 분리된다.
6. **프라이버시 설계**: 대화 메모리의 보존 기간·삭제·마스킹이 문서화되고 구현되어 있다.
7. **한국어 재현**: 위 1~2를 한국어 대화로 수행한다.
