# 컨텍스트 엔지니어링

> **범위**: 프롬프트 엔지니어링에서 컨텍스트 엔지니어링으로, 프레임워크 지원 현황

> **한 줄 정의**: 모델에 **무엇을 넣고 무엇을 뺄지, 어떤 순서·구조로 넣을지, 토큰 예산을 어디에 쓸지**를 설계하는 공학. "지시문을 잘 쓰는 법"(프롬프트 엔지니어링)에서 "모델이 보는 창(window) 전체를 설계하는 법"으로 관심이 이동한 것을 가리킨다.
> **레이더 위치**: **시험** — [00-overview](00-overview.md)는 "채택 후보"로 두었다. 개념은 운영 경험과 일치하고 `[검증]`된 기반 연구(Lost in the Middle, RULER)가 있지만, "컨텍스트 엔지니어링"이라는 **방법론 자체**의 효과는 `[2차]`·`[벤더]`뿐이다. 작성 가이드 5절에 따라 채택은 `[실측]` 뒤에 올린다.

## 무엇이 바뀌었나 (최근 1년)

| 시점 | 사건 | 검증 수준 |
|---|---|---|
| 2023~24 (기반) | **Lost in the Middle**, **RULER** (2023~24): 롱컨텍스트에서 중간 위치 정보 누락, 공칭 창 길이와 유효 길이의 괴리 | `[검증]` |
| 2025-04 | **Google ADK** 출시. 이후 Python / Java(1.0.0 2026-03) / Go / TypeScript로 확대 | `[2차]` |
| 2025 하반기 ~ | "프롬프트 엔지니어링 → 컨텍스트 엔지니어링" 어휘 전환이 커뮤니티에 확산 | `[2차]` |
| 2026 | **ADK 컨텍스트 관리**: 세션·메모리·툴 출력·아티팩트를 **구조화된 뷰**로 조립. 자동 요약, 무관 이벤트 필터, 지연 로딩, 토큰 추적 | `[벤더]` |
| 2026 | **Claude Agent SDK**(Claude Code 런타임의 프로그래밍 노출, hooks), **OpenAI Agents SDK**(Swarm 후속) 등 벤더 네이티브 SDK가 컨텍스트 조립을 런타임 책임으로 흡수 | `[2차]` |
| 2026 | 롱컨텍스트 vs RAG 논쟁이 "대체"에서 **"보완"** 으로 정리. RULER 스트레스에서 중간 청크 누락 재현 | `[2차]` (원 논문 `[검증]`) |

바뀐 것은 **책임의 위치**다. 이전에는 애플리케이션 코드가 문자열을 이어 붙여 프롬프트를 만들었다. 지금은 프레임워크가 세션·메모리·툴 결과·검색 결과를 **구조화된 컨텍스트**로 조립하고 예산을 관리하는 기능을 1급으로 제공한다. 상태·메모리·컨텍스트의 단계별 설계는 [Part 3/08](../03-agent-workflow-rag/08-state-memory-context.md)이 맡는다.

## 왜 주목받나

1. **창이 커졌는데 품질은 비례하지 않았다.** 공칭 컨텍스트 길이가 늘어도 유효 길이는 그보다 짧고(RULER), 중간에 놓인 정보는 놓친다(Lost in the Middle) `[검증]`. "다 넣으면 된다"가 틀렸음이 확인되자 **무엇을 뺄지**가 설계 문제가 되었다.
2. **에이전트 루프가 컨텍스트를 오염시킨다.** 멀티스텝 에이전트는 툴 출력·중간 추론·이전 턴이 누적된다. 관련 없는 이벤트가 쌓이면 비용이 늘 뿐 아니라 모델이 이전 프레임에 고착된다 — [agent-memory](agent-memory.md)의 MemTrapBench 교훈과 같은 현상이다.
3. **비용이 컨텍스트에 비례한다.** 입력 토큰이 비용의 지배 항이 되면서 "컨텍스트 예산(context budget)"이 운영 지표가 되었다 ([Part 5/02](../05-cross-cutting/02-cost-latency-model-routing.md)).
4. **RAG가 사라지지 않았다.** 롱컨텍스트가 RAG를 대체한다는 예측은 빗나갔고, 둘은 **보완 관계**로 정리되었다 `[2차]`. 검색은 "컨텍스트에 무엇을 넣을지"를 결정하는 수단 중 하나가 되었다.

## 핵심 메커니즘

컨텍스트 엔지니어링은 네 가지 결정으로 분해된다.

| 결정 | 질문 | 수단 | 관련 페이지 |
|---|---|---|---|
| **선택** (무엇을 넣나) | 이 턴에 필요한 정보는 무엇인가 | 검색(RAG), 메모리 조회, 툴 출력 필터, 무관 이벤트 제거 | [Part 3/03](../03-agent-workflow-rag/03-retrieval-reranking.md), [Part 3/08](../03-agent-workflow-rag/08-state-memory-context.md) |
| **압축** (얼마나 줄이나) | 들어가야 하지만 길다면 | 자동 요약, 지연 로딩(필요 시에만 본문), 아티팩트 참조로 치환 | [Part 3/08](../03-agent-workflow-rag/08-state-memory-context.md) |
| **구조화** (어떻게 배치하나) | 모델이 놓치지 않게 하려면 | 섹션·태그로 구분된 뷰, 중요 정보를 앞·뒤에 배치(중간 회피), 스키마화된 툴 결과 | [Part 3/04](../03-agent-workflow-rag/04-generation-grounding.md) |
| **예산** (얼마나 쓰나) | 토큰을 어디에 배분하나 | 토큰 추적, 구성 요소별 상한, 초과 시 압축·축출 정책 | [Part 5/02](../05-cross-cutting/02-cost-latency-model-routing.md) |

**프레임워크 지원의 두 갈래** `[2차]`:
- **벤더 네이티브 SDK** (Claude Agent SDK, OpenAI Agents SDK, Google ADK): 런타임이 컨텍스트 조립·예산을 맡는다. ADK는 세션·메모리·툴 출력·아티팩트를 구조화된 뷰로 조립하고 자동 요약·무관 이벤트 필터·지연 로딩·토큰 추적을 제공한다고 설명한다 `[벤더]`.
- **독립 프레임워크** (LangGraph, CrewAI, Smolagents, Pydantic AI, AutoGen — AutoGen은 유지보수 모드): LangGraph는 방향 그래프 + 공유 상태, 체크포인팅으로 상태를 명시적으로 관리하되 컨텍스트 조립은 개발자 몫이 크다. 학습 곡선이 가장 가파르다 `[2차]`.

**롱컨텍스트와 RAG의 보완 관계**: 롱컨텍스트는 "넣을 수 있는 양"을, RAG는 "넣을 것의 선택"을 담당한다. 창이 커질수록 선택의 정밀도가 덜 중요해지는 것이 아니라, **잘못 선택한 것이 더 많이 들어가** 중간 누락과 비용을 키운다. [graphrag-evolution](graphrag-evolution.md)의 그래프 RAG도 결국 "어떤 청크를 컨텍스트에 넣을지"의 선택 수단이다.

## 우리 프로젝트에서의 채택 기준

"시험"에서 "채택"으로 올리려면 다음이 `[실측]`되어야 한다. 비교군은 "현재의 단순 이어 붙이기" 구성이다.

1. **선택·압축 효과 `[실측]`**: 같은 골든셋에서 (a) 전부 넣기, (b) 선택·압축 적용 구성의 정답률·근거 충실도·비용을 비교. (b)가 비용을 줄이면서 품질을 유지하거나 올려야 한다.
2. **중간 누락 재현 테스트 `[실측]`**: 핵심 근거를 컨텍스트 앞·중간·뒤에 배치한 세 변형으로 정답률 차이를 측정. 차이가 있으면 구조화 규칙(앞·뒤 배치)을 표준으로.
3. **자동 요약 손실률 `[실측]`**: 프레임워크 자동 요약 전후로 골든셋 점수와 "요약에서 사라진 핵심 사실" 샘플 검수.
4. **컨텍스트 예산 지표 운영**: 요청별 구성 요소(지시문 / 검색 결과 / 메모리 / 툴 출력 / 대화 이력) 토큰 분포가 트레이스에 기록되고 대시보드에 있다.
5. **한국어 토큰 효율 측정**: 대표 문서 샘플의 토큰/문자 비율을 사용 모델별로 기록해 예산 계산에 반영.
6. **조립 로직의 관측 가능성**: 최종 컨텍스트가 트레이스에 저장(PII 마스킹)되어 "모델이 무엇을 봤는지"를 사후 확인할 수 있다.
