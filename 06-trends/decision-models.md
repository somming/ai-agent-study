# 결정 모델: Jev와 OpenAI Decisions API ★

> **범위**: System One 모델의 등장, 두 접근의 비교, 벤더 주장과 검증 수준

> **한 줄 정의**: 텍스트를 생성하지 않고, 개발자가 코드로 정의한 질문(선택 / 점수 / 예·아니오)에 대한 **판정과 확신도만** 돌려주는 모델 또는 API 범주. TypeSafe AI의 **Jev**와 OpenAI의 **Decisions API**가 2026-09에 거의 동시에 등장하면서 범주로 묶여 불리기 시작했다.
> **레이더 위치**: **관찰** — 공개된 지 한 달 남짓이고 성능 수치가 전부 `[벤더]`이며 독립 벤치마크가 없다. 한국어 평가셋으로 PoC를 시작하는 시점에 "시험"으로 올린다 ([00-overview](00-overview.md)의 잠정 위치 "관찰 → 시험"을 따름).

|---|---|---|

| 2026-09-29 | OpenAI DevDay에서 **Decisions API** 발표(제한 프리뷰). 엔드포인트 `POST /v1/decisions` | `[2차]` |

이전까지 "판정" 작업(라우팅, 분류, 게이팅, 품질 판정)은 ① 규칙, ② 파인튜닝 분류기, ③ 프롬프트 LLM의 구조화 출력 중 하나로 처리했다. 판정 수단의 스펙트럼과 System 1/2 역할 분담은 [Part 1/02](../01-foundations/02-system1-vs-system2.md)에 정리되어 있다. 이 페이지는 그 스펙트럼에 새로 들어온 네 번째 수단이 **무엇인지, 벤더가 무엇을 주장하는지, 무엇이 검증되지 않았는지**에 집중한다.

## 왜 주목받나

프롬프트 LLM으로 판정을 처리할 때의 세 가지 비용이 결정 모델의 등장 배경이다 ([Part 1/02](../01-foundations/02-system1-vs-system2.md) "문제와 맥락").

1. **토큰 낭비**: 답 하나(예: `approve`)를 얻기 위해 설명·형식 토큰을 수십~수백 개 생성한다. 라우팅처럼 요청마다 반드시 거치는 지점에서는 이 비용이 누적된다.
2. **흔들림**: 온도 0이어도 프롬프트 미세 변화에 결과가 바뀐다. 판정은 재현성이 중요하다.
3. **비보정 확신도**: LLM이 "확률 80%"라고 써도 그 숫자는 보정(calibrated)되어 있지 않다. 임계값 기반 HITL 분기([Part 3/12](../03-agent-workflow-rag/12-guardrails-hitl.md))가 의미를 가지려면 확률이 보정되어야 한다.

결정 모델은 이 셋을 **인터페이스 수준에서** 해결하겠다고 한다: 텍스트 생성 없음(1), 타입드 질문·스키마 보장(2), 보정 확률 반환(3). 세 번째가 가장 큰 약속이자 가장 검증이 안 된 부분이다.

### 표 해설: 같은 인터페이스, 다른 내부

두 접근은 "생성 없는 판정 API"라는 **인터페이스**는 같지만 **구조**가 다르다. 이 차이는 위키 전체에서 한 번은 명시해야 하는 사항이다 (연구 노트 서술 규칙).

- **Jev = 결정 전용 모델.** 벤더 설명에 따르면 자기회귀 디코딩을 하지 않고 단일 패스로 여러 질문에 병렬로 답한다. 70~500ms 지연과 "200배 빠르다"는 주장은 이 구조에서 나온다. 보정 확률은 RLCD라는 별도 학습 절차로 만든다고 한다 `[벤더]`. 구조가 다르므로 **생성 모델의 일반 지식·추론 능력을 그대로 가정할 수 없다** — 영어 중심 학습이라는 한계가 특히 그렇다.
- **Decisions API = 생성 모델의 출력 제약.** gpt-6-luna라는 범용 모델 위에 출력 형식을 제약한 엔드포인트다 `[2차]`. 모델의 범용 지식과 이미지 입력을 그대로 쓸 수 있는 대신, 지연·비용은 생성 모델의 그것에 묶이며 벤더가 지연을 보고하지 않았다. "별도 결정 전용 모델이 아니다"는 점은 성능 기대치를 세울 때 중요하다.

따라서 같은 범주로 묶어 부르되, `[실측]`은 **따로** 한다. Jev에서 얻은 보정 곡선이 Decisions API에도 성립한다고 가정하면 안 된다.

### 어디에 끼우나

[Part 1/02](../01-foundations/02-system1-vs-system2.md)의 조합 패턴 네 가지(Gate → Generate, Generate → Judge, Parallel Vote, Confidence-Routed HITL) 모두에서 결정 모델은 "판정" 자리를 맡는다. 단, **행동으로 이어지는 판정은 결정 모델이 마지막 관문이 아니다** — 규칙이 최종 허가하는 게이트 패턴([Part 1/04](../01-foundations/04-neuro-symbolic-ai.md))과 결합한다.

## 우리 프로젝트에서의 채택 기준

"관찰"에서 "시험"으로: 한국어 평가셋을 만들고 PoC를 시작하는 시점. "시험"에서 "채택"으로 올리려면 아래가 **전부** `[실측]`되어야 한다. 비교군은 반드시 (a) 현재 쓰는 프롬프트 LLM 구조화 출력, (b) 소형 파인튜닝 분류기 둘 다 둔다.

1. **한국어 평가셋 `[실측]`**: 실제 운영 질의 분포를 반영한 한국어·한영 혼합 라벨셋(판정 지점별 최소 수백 건)에서 정확도가 비교군 (a)(b) 이상. 영어 번역본이 아니라 **원문 한국어**로 평가한다.
2. **보정 곡선 `[실측]`**: 반환된 확률을 구간별로 묶어 실제 정답률과 비교(reliability diagram, ECE 류 지표). 보정이 확인된 구간에서만 HITL 임계값을 설정한다. 보정이 안 되어 있으면 "확률"을 순위 점수로만 쓰고 임계값은 실측으로 다시 잡는다.
3. **지연·비용 `[실측]`**: 우리 입력 길이·질문 수·동시성에서 p50/p95 지연과 요청당 비용. 벤더 수치(70~500ms, 200배/400배)와의 괴리를 기록한다.
4. **폴백 설계 완료**: 결정 모델 장애·타임아웃·확신 낮음 각각에 대해 규칙 또는 분류기 폴백이 있고, 폴백 경로가 테스트되어 있다.
5. **게이트 결합**: 행동으로 이어지는 판정 지점마다 코드 규칙(권한·한도)이 최종 허가하는 구조가 들어가 있다.
6. **Jev와 Decisions API를 따로 측정**: 한쪽 결과를 다른 쪽에 전용하지 않는다.
7. **인터페이스 추상화**: 판정 호출이 단일 어댑터 뒤에 있어 벤더 교체·분류기 교체가 설정 변경으로 가능하다.

PoC 결과는 [Part 7 시나리오](../07-appendix-scenarios/00-overview.md) 페이지에 `[실측]`으로 기록하고, 이 페이지의 "벤더 주장 vs 검증된 사실" 표에 "우리의 판단" 열을 갱신한다. 절차는 [00-overview](00-overview.md) "트렌드를 채택으로 올리는 절차"를 따른다.
