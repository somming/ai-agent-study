# 시나리오 B: 커머스 상담 + Generative UI

> **범위**: 상품 온톨로지 → 에이전트 → 동적 UI까지 구성 예시
> **시각화**: [`assets/html/scenario-commerce-genui.html`](../assets/html/scenario-commerce-genui.html)
> **성격**: [Part 7 개요](00-overview.md)의 비교표대로 **Interaction 중심**, 자율성 중간(툴 호출 에이전트), UI는 Controlled → 일부 Declarative. 세 시나리오 중 유일하게 "사용자가 결과를 조작하는" 시스템이며, 상품 온톨로지 → 컴포넌트 매핑이 설계의 중심이다.

## 1. 상황 설정

가상 조직이다. 아래 규모 수치는 모두 **설계 가정**이며, "이 정도 규모·갱신 속도면 어떤 선택이 달라지는가"를 보여 주기 위한 값이다.

| 항목 | 내용 |
|---|---|
| 업무 도메인 | 가전·디지털 기기를 파는 자사 온라인몰(단일 테넌트). 상품 탐색·비교·옵션 선택·장바구니·주문 조회를 돕는 상담 어시스턴트. **결제는 어시스턴트 밖**(기존 결제 페이지·외부 결제 대행) |
| 사용자 | 비로그인 방문자(탐색·비교)와 로그인 고객(장바구니·주문 조회). 월 활성 사용자 수십만, 피크 시 동시 상담 수백 세션(설계 가정). 사용자는 **답을 읽고 → 비교표를 보고 → 옵션을 고르고 → 장바구니에 담는다**. 웹 + 모바일 웹, 디자인 시스템이 엄격하다 |
| 데이터 | **정형**: 상품 마스터 수십만 SKU(카테고리·브랜드·속성·호환성·대체 상품), 가격·재고(분 단위 갱신, 하루 수만 건 변경 이벤트), 주문·배송 상태(고객 본인 것만). **반정형**: 리뷰 수백만 건(하루 수천 건 신규), FAQ·배송·교환 정책 문서 수백 건. **멀티모달**: 상품 이미지. **언어**: 한국어 중심, 모델명·스펙은 영문 혼재. **권한**: 주문·장바구니는 본인 세션에 한정, 리뷰 작성자 PII 포함 |
| 핵심 요구 | **정확도**: 재고·가격·호환성이 틀리면 금전 민원 — 사실 정보는 레코드 그대로, 추천은 정책·재고 규칙을 통과한 것만. **근거**: 상품 레코드·리뷰 문장 citation 권장(규제상 필수는 아님). **지연**: 대화형(수 초), 비교표까지 포함. **규제**: 전자상거래 표시 의무·개인정보(법무 검토 사항으로 두고, 설계는 "가격·재고·배송 정보는 시스템 레코드 외 생성 금지"로 고정) |
| 제약 | **팀**: 프론트(React) 팀과 백엔드(Python) 팀이 분리, 디자인 시스템 팀 보유, 데이터 엔지니어 2명. RDF 경험 없음, 상품 DB 스키마는 잘 정리돼 있음. **예산**: 리뷰 전수 LLM 처리는 건수 비례라 상한 필요. **기존 시스템**: 상품 DB(CDC 가능), 검색엔진(상품 검색에 이미 사용), 장바구니·주문 API, 외부 결제 대행. 단일 벤더 LLM 종속 허용 |

## 2. 요구사항 → 결정 변수 추출

[종합 결정 트리](../00-overview/02-decision-guide.md)의 입력 변수 V1~V15에 값을 채우고, 질문 Q1~Q15를 돌린 경로를 적는다.

| # | 변수 | 이 시나리오의 값 | 움직이는 선택 |
|---|---|---|---|
| V1 | 데이터 유형 | **정형 중심**(상품·가격·재고·주문) + 반정형(리뷰·FAQ) + 이미지 | 레코드 근거 단위, 규칙 추출 그래프, 변환기 패턴 |
| V2 | 규모·갱신 빈도 | SKU 수십만, 리뷰 수백만 / 가격·재고 **분 단위** / 트래픽 대량 | CDC, 결정 모델의 비용 이점이 의미 있음 |
| V3 | 지연 요구 | 응답 대화형(<5s), 신선도 **분** | CDC + 변경 큐, 리랭커는 리뷰 경로에만 |
| V4 | 정확도·근거 요구 | 사실(가격·재고)은 레코드 그대로, citation 권장 | 레코드 citation, 규칙 게이트 |
| V5 | 규제·감사 | 전자상거래 표시 의무(법무), 리뷰 PII, 주문은 본인 한정 | bitemporal 가격, PII 마스킹, 본인 확인 |
| V6 | 멀티홉·동일성·설명 | **있음** — 호환성("이 TV에 맞는 사운드바"), 대체 상품, "왜 추천" 설명. 정형 관계라 규칙 추출 가능 | 상품 온톨로지 + 규칙 추출 그래프 |
| V7 | 과업 예측 가능성 | 몇 가지 분기(탐색·비교·옵션·장바구니·주문 조회·정책 문의) | 라우팅 + 오케스트레이터-워커 |
| V8 | 실패 비용 | **금전**(잘못된 장바구니·가격 안내) — 결제는 밖이라 비가역 아님 | 정책 게이트, 동기 승인, 멱등 키 |
| V9 | 행동 유무 | 쓰기 포함 툴 10~20개(검색·비교·장바구니 담기·옵션 변경·주문 조회·환불 접수) | 등급별 멱등·게이트, 2단계 라우팅은 불필요 |
| V10 | 사용자 행위 | **선택·비교 + 장바구니 승인** | 3-Layer 전체, Controlled 기본 |
| V11 | 플랫폼 | 웹 + 모바일 웹(네이티브는 2차) | AG-UI, 반응형, A2UI 보류 |
| V12 | 조직 경계 | 프론트·백 분리, 외부 결제 대행(에이전트 밖) | AG-UI, 네이티브 툴(소비자 하나) |
| V13 | 팀 역량 | 디자인 시스템 팀, Python 백엔드, React 프론트, RDF 없음 | DS 패키지 내장 레지스트리, CopilotKit/AG-UI SDK, 경량 온톨로지 |
| V14 | 예산·반출·종속 | 리뷰 LLM 처리 상한, 단일 벤더 허용 | 리뷰는 샘플·요약 수준, 벤더 SDK 후보 |
| V15 | 언어 | 한국어 + 영문 모델명 | 형태소 BM25 + 상품 코드 정확 매칭, 결정 모델 한국어 골든셋 |

**질문 트리 경로**: Q1 읽기만 → **아니오**(3-Layer, Controlled부터) · Q2 행동 → **예**(결정 레이어·검증기·가드레일 생략 불가, 등급별 멱등) · Q3 정형 중심 → **예**(레코드 근거 단위, 템플릿 직렬화, 규칙 추출 그래프, 변환기) · Q4 분 단위 SLO → **예**(CDC + 변경 큐) · Q5 citation 필수 → **부분**(가격·재고는 bitemporal, 리뷰는 존재 검증만) · Q6 멀티홉·설명 → **예, 단 정형 관계**(경량 상품 온톨로지, 규칙 추출 그래프, GraphRAG 계열은 불필요) · Q7 PII·권한 → **예** · Q8 예측 가능 → **예, 몇 가지 분기**(라우팅 + 오케스트레이터-워커, Tool-use) · Q9 당사자 둘 이상 → **아니오**(툴은 단일 백엔드; 프론트 분리는 Q14에서) · Q10 결정 모델 한국어 `[실측]` → **아직 아니오**(LLM 툴 호출/소형 분류기로 시작, `decide()` 뒤에 결정 모델 섀도 → 골든셋 통과 후 교체) · Q11 쓰기 툴 → **예**(Schema + 규칙 게이트, 정책 엔진) · Q12 멀티세션 → **예(로그인 고객)**, 선호 메모리는 항목 제한 + no-memory 대비 `[실측]` · Q13 비가역·고액 → **아니오**(결제가 밖), 단 장바구니·환불 접수는 승인 카드 · Q14 프론트·백 분리 → **예**(AG-UI) · Q15 벤더 종속 → **예**(벤더 SDK 또는 LangGraph PoC).

## 3. 단계별 설계 결정

선택은 세 결정 매트릭스의 시나리오 B 행과 일치시켰다. "선택 이유"는 해당 페이지의 선택 가이드 조건을 인용한다.

### 3.1 데이터 파이프라인 (Part 2)

|---|---|---|---|---|

| 지식그래프 | **규칙 추출 중심 그래프**: 상품–카테고리–브랜드–호환–대체–옵션. 소스는 마스터 DB 필드. LLM 추출은 리뷰 속 속성 언급(소음·발열 등)에만, 근거 문장 필수 + SHACL 등가 제약 | 전면 LLM 추출; 그래프 미도입 | 2/05 선택 가이드: "정형 데이터(마스터)가 섞여 있다면 → 하이브리드 추출, 정형은 규칙. | 동기화 | **CDC 이벤트 기반 + 단일 변경 큐**, 재고 소진·가격 변경 톰스톤 즉시, 같은 이벤트가 인덱스와 그래프를 모두 트리거. 리뷰는 증분 배치 | 폴링 배치 | 2/07 선택 가이드: "소스가 운영 DB이고 SLO가 분 단위라면 → CDC + 단일 변경 큐. 삭제까지 이벤트로 오는 유일한 방식". 2/05 한계 "벡터만 갱신하고 그래프 방치" 회피 | [2/07](../02-data-pipeline/07-freshness-and-sync.md) |

### 3.5 트렌드 세 축 적용

| 축 | 이 시나리오에서의 자리 | 채택 수준 | 채택을 올리기 위한 조건 |

## 4. 전체 아키텍처

시각화: [`assets/html/scenario-commerce-genui.html`](../assets/html/scenario-commerce-genui.html) — 선택한 노드만 진하게, 뺀 노드(멀티 에이전트 오케스트레이션, MCP, 결제 툴, A2UI·MCP Apps 등)는 흐리게. 번호는 아래 흐름과 같다.

사용자 질의 1건("20만 원 이하 노이즈캔슬링 헤드폰 3개 비교해 줘. 내 폰이랑 호환되는 걸로")이 끝까지 흐르는 경로:

1. **[Interaction]** 사용자가 모바일 웹 상담 위젯에 입력. AG-UI 어댑터가 `RunStarted` + 사용자 메시지 이벤트를 백엔드로 전송. 로그인 고객이면 세션 본인 ID, 항목 제한 선호 메모리(보유 기기·선호 브랜드)가 상태에 로드된다.
2. **[Reasoning]** 입력 가드레일(규칙) → 질의 이해: 한국어 정규화 → `decide("intent")` = `compare`(운영은 소형 LLM/분류기, 결정 모델은 섀도 로그) → 슬롯 추출(카테고리=헤드폰, 가격 상한, 속성=노이즈캔슬링, 호환 대상=보유 폰).
3. **[Reasoning → Knowledge]** 비교 워커(Plan-and-Execute): ① 온톨로지 필터(Category ⊑ 헤드폰, Offer.price ≤ 상한, 재고 > 0, 유효 시점 = 현재)를 **변환기**가 읽기 전용 쿼리로 변환·실행 → 후보 레코드 ② 호환성 그래프 1홉(`compatibleWith` 보유 폰) → ③ 후보별 리뷰 문장 hybrid 검색 + cross-encoder. Knowledge가 **근거 단위(계약 ①)** 반환: `evidence_type: record`(SKU·가격·재고·유효 시점·옵션), `sentence`(리뷰 문장·작성자 마스킹), `path`(호환 경로).
4. **[Reasoning]** 뉴로심볼릭 **규칙 게이트**: 재고·유효 가격·판매 정책·호환 경로 존재·후보 수 ≥ 2를 검사. 통과한 후보만 생성 단계로. 한 후보가 재고 소진이면 대체 관계(`substituteOf`) 1홉으로 보충.
5. **[Reasoning]** 생성: 구조화 출력 — 비교 축(가격·무게·배터리·노이즈캔슬링 등급·호환) 선택과 추천 사유 문장(리뷰 `evidence_id` 인용). **가격·재고 값은 생성하지 않고 레코드 필드를 바인딩**. citation 존재 규칙 검증.
6. **[Reasoning]** `decide("ui_intent")`: 규칙(모바일 폭 → 열 ≤ 3, 항목 3) → 온톨로지(다중 Product + 속성 축 → 후보 `CompareTable` / `ProductCardList`) → LLM(섀도: 결정 모델) → `CompareTable`(Declarative). 승인 필요 여부 판정은 "비교"라 해당 없음.
7. **[Reasoning → Interaction]** **렌더 가능한 응답(계약 ②)**: `text`(요약), `citations[]`, `ui_intent = {component: CompareTable, tree: …, bindings: SKU 레코드}`, 확신도, `requires_approval: false`. AG-UI 이벤트(텍스트 델타, 커스텀 이벤트에 트리, 상태 스냅샷)로 스트리밍.
8. **[Interaction]** 서버 재검증 통과한 트리를 **트리·조합·바인딩 검증기**가 검사 → React 렌더러가 디자인 시스템 토큰으로 비교표 렌더(접근성 런타임 검증, 실패 시 요약 카드 폴백). 각 행에 `OptionSelector`(색상), `AddToCartButton`(Controlled).
9. **[Interaction → Reasoning]** 사용자가 2번 상품의 색상을 고르고 "담기"를 누름 → **사용자 이벤트(계약 ③)**: `option_selected`(SKU·옵션) → 상태 패치(순서 번호), 이어서 `action_requested`(add_to_cart, SKU·옵션·수량, `as_shown_hash`).
10. **[Reasoning]** 정책 엔진: 등급 "쓰기-가역" → 규칙 게이트 재실행(재고·가격 **재확인**: 1~8단계 사이에 가격이 바뀌었는지) ∧ `decide("requires_approval")`(수량·금액 이상치 아님 → 자동 허용 범위지만 매트릭스 B 기본대로 **동기 승인 카드**는 표시) → **승인 카드** 렌더(금액·수량·가역성 "장바구니에서 삭제 가능").
11. **[Interaction → Reasoning → Action]** 사용자 승인 이벤트(계약 ③, `as_shown_hash` 일치 확인) → 장바구니 툴 실행(멱등 키 = 세션·SKU·옵션·hash) → optimistic "전송됨" → 실행 결과 상태 스냅샷 → `CartSummary` 카드. "결제하기"는 **기존 결제 페이지로 핸드오프**(에이전트 밖, 링크만).
12. **[Cross-cutting]** 전 과정의 스팬(intent·UI 판정과 섀도 결정 모델 판정, 게이트 결과·규칙 ID, 레코드 `evidence_id`, UI 렌더·이벤트 스팬, 멱등 키)이 같은 trace_id로 기록. 승인 이벤트는 감사 레코드로 불변 저장.

## 7. 예상되는 한계와 2차 과제

**이 설계가 해결하지 않는 것**

- **결제·주문 생성·환불 처리**. 에이전트 밖에 둔 것이 설계 결정이다. 결제 대행이 본인 인증·규제 준수를 맡고, 에이전트는 장바구니까지만. 2차에 결제를 넣더라도 3/12 "비동기 HITL + 체크포인트 + 만료=거부"와 4/06 승인 카드가 선행 조건이다.
- **VLM 캡션의 "근거 있는 환각"**(색상·재질 오기). 등급 C·검증 근거 불허·"생성됨" 표시로 완화할 뿐 막지 못한다([2/08](../02-data-pipeline/08-grounding-data-design.md) 한계).
- **리뷰 LLM 처리 비용**이 건수에 비례한다. 샘플링·요약 수준으로 상한을 두므로 롱테일 상품의 리뷰 속성은 비어 있을 수 있다.
- **결정 모델의 UI 선택 적용 사례 부족·한국어 미검증**. `[실측]` 전까지 LLM 병행이 필수이고, 비용 이점은 가정이다([4/99](../04-dynamic-ui/99-decision-matrix.md) 한계).
- **Declarative 비교표의 접근성**은 런타임 검증기에 의존한다. 검증기가 못 잡는 트리 품질 문제(헤딩 순서·포커스 흐름)는 폴백·사람 샘플링으로만 발견된다.
- **인젝션**: 리뷰 본문이 에이전트 입력이 되는 경로가 있다. 등급 상향·규칙 게이트가 피해를 제한하지만 탐지는 뚫릴 수 있다([5/01](../05-cross-cutting/01-security-prompt-injection.md)).

**규모 10배(SKU 수백만, 입점 셀러 다수, 네이티브 앱)가 되면 바뀌는 것**

- 멀티테넌트(입점 셀러): 테넌트 인덱스 분리, 그래프는 엣지 단위 `tenant_id`(공통 브랜드 노드가 경계를 흐림 — [2/99](../02-data-pipeline/99-decision-matrix.md) B 한계), 게이트웨이 단일 강제가 생존 조건.
- 전용 벡터DB + 양자화 + 2단계 재순위(2/04 조건 B), 레지스트리 수십 → 백 개면 결정 모델 enum 계층화가 사실상 필요.
- 네이티브 앱: Declarative 내용층을 A2UI로 교체 검토, 단 v0.9 `[벤더]`·렌더러 품질 `[실측]` 선행, 그 전엔 자체 Controlled 네이티브 렌더러([4/07](../04-dynamic-ui/07-frontend-integration.md)).
- 판정 건수가 커져 결정 모델의 비용 이점이 커지는 반면, 외부 API로 상태(장바구니·선호)가 나가는 경로의 PII 최소화·데이터 처리 계약이 쟁점이 된다(3/11 한계).

**트렌드 축을 채택으로 올리기 위해 필요한 `[실측]`**

| 축 | 필요한 실측 | 판단 기준 |
|---|---|---|
| 온톨로지 | 온톨로지 후보 축소 유무에 따른 UI 선택 정확도·폴백률, 추출 위반율, 매핑 테이블 행 수 변화 | 후보 축소가 정확도를 올리고 매핑 행 수를 줄임 |
| 뉴로심볼릭 | 게이트 차단률·오탐률, 변환기 쿼리 오류율, 트리 검증 실패율과 그중 사람 검수에서 "정당한 차단" 비율 | 오탐이 사용자 이탈을 만들지 않는 수준 |
| 결정 모델 | 세 판정 지점의 한국어 골든셋 정확도·ECE·지연·비용 (LLM/분류기와 동일 셋), 베타 상태·가격 변동 모니터 | 지점별로 LLM 동등 이상 + 보정 확인 시 교체. 행동 판정은 제외 |

## 9. 운영 계획 — 이 시나리오를 운영 상태로 유지하기

용어는 [Part 1/07](../01-foundations/07-operations-vocabulary.md), 단계별 상세는 각 페이지의 "운영 설계" 섹션, 종합은 [Part 5/06](../05-cross-cutting/06-operational-design-matrix.md). 이 시나리오의 운영 무게중심은 **두 종류의 동기화**다 — 가격·재고가 소스와 화면 사이에서 어긋나지 않는 것(틀리면 금전 민원·표시 의무 위반), 그리고 UI가 어떤 장애에서도 **텍스트로 안전하게 저하**되되 승인 카드만은 저하되지 않는 것. 프론트·백엔드·디자인 시스템·데이터 네 팀이 관여하므로 롤백 단위와 소유자를 명확히 하는 것이 A보다 중요하다. 수치는 모두 **예시**이며 11주차 파일럿 실측 뒤 재설정한다.

### 9.1 E2E SLO와 레이어별 SLI (예시값)

| 지표 (사용자 관점) | 목표 (예시) | 측정 위치 — 받치는 레이어·단계 SLI | 위반 시 런북 (한 줄) |
|---|---|---|---|
| **첫 컴포넌트 지연 / 비교표 완성 지연** | 첫 컴포넌트 p95 < 3초, 비교표 포함 전체 p95 < 5초 | Interaction: 4/04 첫 토큰 ~ 첫 컴포넌트 p95, 4/08 트리 검증 소요 · Reasoning: 3/03 리뷰 리랭커 p95, 3/06 비교 워커 스텝 수 · Knowledge: 2/04 상품 검색 p95 | 리뷰 리랭커 비활성 → 비교표를 요약 카드로 저하 → 후보 수 축소. 비교 워커 스텝 상한(3) 초과율 급등이면 워커 프롬프트 롤백 |

### 9.2 장애 시나리오 3개 — 무엇이 죽으면 사용자에게 어떻게 보이고 누가 뭘 하나

세 장애는 각각 Knowledge(동기화)·Reasoning/Interaction(판정·매핑)·Interaction/Action(승인·실행) 레이어에서 가장 아픈 것이다. 공통 원칙: **읽기는 저하, 쓰기는 차단**. 가격이 불확실하면 "확인 중"을 보여주고, 멱등성이 불확실하면 담지 않는다.

| 장애 | 증상 (사용자에게) | 자동 대응 | 사람 개입 | 복구 후 |
|---|---|---|---|---|
| **① 재고·가격 CDC 동기화 지연** (변경 큐 적체·브로커 다운 — 프로모션 시작 시각에 가격 변경 수만 건 몰림) | 어시스턴트가 **구 가격·품절 상품**을 추천·비교표에 표시. 담기 시점 재확인 게이트가 막아 "가격이 변경되었습니다" 거부가 급증 | 2/07: 커넥터 커서 보존(유실 없음), 우선 레인이 재고 소진·가격 변경 톰스톤을 먼저 처리. CDC 지연이 예시 15분 초과 시 **가격 표시 저하**: 비교표·카드의 가격 셀에 "확인 중" 배지 + 유효 시점이 지연 범위 밖인 Offer는 추천 후보에서 제외(3/10 게이트 조건 엄격화). 시맨틱 캐시는 가격 유효 시점 키 덕분에 자동 무효 | 지연이 가장 짧은 SLO(5분)의 3배 초과 → 데이터 온콜. 프로모션 중이면 상품 운영(MD)에 "어시스턴트 가격 표시 저하 중" 통보. 표시 의무 관련 민원 가능성은 법무에 사전 공유 | 대조 배치로 누락분 보충, 저하 구간에 표시된 가격·실제 가격 불일치 건을 감사 레코드(`price_snapshot`)로 추출해 CS에 전달. 큐 파티셔닝·프로모션 사전 워밍 여부 결정 |
| **② 결정 모델·매핑 폴백 폭증** (결정 모델 API 다운·레이트 리밋, 또는 모델 버전 변경 후 오선택 급증) | 비교 질문에 비교표 대신 **텍스트 답변**, 카드 대신 목록 텍스트. 과업은 가능하지만 완료율·턴 수 악화 | 4/05: 서킷 브레이커 → **규칙 기본값**(의도별 1순위 컴포넌트: `compare` → `ProductCardList` 요약 카드) → 없으면 텍스트, 저하 플래그. 3/11: `decide("intent")`도 규칙 → 캐시 → 보수적 경로(명확화 선택지). 레이트 리밋이면 저위험 지점(UI 선택)부터 규칙으로 전환, **`requires_approval` 판정은 애초에 규칙 전용**이라 영향 없음. 오선택 급증이면 θ 상향 + 오선택 의도 행 규칙 고정 | 폴백율 5분간 20% 초과 → 백엔드 온콜. 모델 버전 변경이 원인이면 이전 구현체(LLM 툴 호출)로 전환하고 결정 모델은 섀도 강등 | 한국어 골든셋 재실행으로 보정 재측정, θ 재설정. 폴백 구간의 완료율을 층화 A/B 데이터에서 **제외**(오염). 질문 정의·매핑 테이블 롤백 여부 결정 |

**위험 등급과의 연결**: ①은 표시 자체가 등급 1이지만 틀린 가격 표시는 법적 영향(표시 의무)이라 **등급 3 수준의 탐지·교정**(불일치 추출·CS 전달)을 둔다. ②는 등급 1 행동의 저하라 사용자 마찰만 늘고 안전 문제는 없다 — 단 4/05 "행동 의도가 확률 행으로 흘러감"은 1건이라도 설계 결함으로 다룬다. ③은 등급 1~2 행동(가역 장바구니)이지만 이중 실행은 금전 민원이므로 **차단이 저하보다 우선**이다.

### 9.3 변화 시나리오 — 1년 안에 일어날 변화와 흡수 경계

이 시나리오에서 가장 자주 바뀌는 것은 **지식(가격·재고·리뷰, 분 단위) > 도메인 모델(카테고리·속성) > 규칙(판매·결제 정책) > 카탈로그 > 모델**이다. 상품 온톨로지가 그래프·게이트 어휘·UI 매핑·레지스트리 `bindings` 네 곳의 공통 어휘이므로, **온톨로지 변경의 전파 범위가 가장 넓다**는 점이 변화 설계의 핵심이다.

| 예상 변화 (구체적 사건) | 유형 | 어디서 흡수 (안정 계약 / 가변 구현) | 재배포 여부 | 다시 돌릴 평가 |

| **입점 셀러 도입** (멀티테넌트 전환) | 규모 · 조직 | 처음부터 둔 테넌트 분리 가능 인덱스 구조 활성화, 그래프 엣지 `tenant_id`, 정책 엔진 기본 정책 + 테넌트 오버라이드, 게이트웨이 단일 강제 | **데이터 마이그레이션 + 게이트웨이 설정** | 테넌트 교차 누출 카나리 0건, 셀러별 정책 규칙 테스트, 공통 브랜드 노드 경계 점검 |
| **AG-UI 스펙 개정 / CopilotKit 메이저 업** | 프로토콜·SDK | 어댑터 계층 교체, 버전 고정 + 계획된 업그레이드 창. 이벤트 **스키마**(계약 ③)는 전송 무관 | **어댑터만** | E2E 이벤트 흐름 테스트(옵션 선택 → 담기 승인 → 실행), 재개 성공률, 승인 카드 흐름 |

여덟 변화 중 백엔드 코드 재배포가 필요한 것은 없고, 프론트 재배포는 둘(앱·디자인 시스템)뿐이다. 가장 무거운 변경은 **온톨로지 클래스 개명·병합**인데, 이는 추출 스키마·SHACL·게이트 어휘·매핑 테이블·레지스트리 `bindings`·결정 모델 enum 여섯 곳에 번지므로 2인 승인 + 호환 검증기 + 매핑 골든셋 전수 재실행을 요구한다(9.4 승인 매트릭스).

### 9.4 거버넌스 — RACI, 위험 등급표, 승인 매트릭스, 감사 필드

**RACI** — 네 팀이 관여하므로 "같은 PR에서 바뀌는 것"끼리 A를 맞춘다. 카탈로그는 디자인 시스템 팀, 온톨로지는 상품 운영, 규칙은 제품 책임자, 승인 매트릭스는 사업 책임자.

| 대상 | R (실행) | A (책임) | C (자문) | I (통보) |
|---|---|---|---|---|
| 프롬프트·결정 질문 정의·θ | 백엔드(AI 엔지니어) | 제품 책임자 | 상품 운영(MD), CS | 프론트 |
| 상품 온톨로지·매핑 테이블(컴포넌트 열·enum 열) | 데이터 엔지니어 | **상품 운영 책임자**(도메인 소유자) | 디자인 시스템, 백엔드 | 전체 |
| 컴포넌트 카탈로그·레지스트리 스키마 | 디자인 시스템 팀 | 디자인 책임자 | 접근성, 프론트 | 백엔드 |
| 정책 엔진 규칙(재고·가격 유효·판매 정책·호환·한도) | 백엔드 | 제품 책임자 | **법무**(표시 의무), CS | 데이터 |
| 툴 권한·멱등(장바구니·옵션·주문 조회·환불 접수) | 백엔드 | 장바구니·주문 서비스 소유자 | 보안 | CS |
| 승인 매트릭스(환불 비동기·한도) | CS 운영 책임자 | 사업 책임자 | 법무 | 전체 |
| CDC·변경 큐·인덱스·그래프 | 데이터 엔지니어 | 상품 DB 팀(데이터 소유자) | 백엔드 | 프론트 |
| 모델 버전·결정 모델 승격·프레임워크 | 백엔드 | 아키텍트 | 보안·법무(선호 메모리·PII 외부 전송) | 전체 |
| 감사 레코드·리뷰 PII 마스킹·보존 | 백엔드 | 개인정보 보호 책임자 | 법무 | 전체 |

**위험 등급표** — 결제가 에이전트 밖이므로 등급 5 행동은 없다. 외부 텍스트(리뷰)를 읽은 세션은 한 등급 올린다.

| 등급 | 이 시나리오의 행동 | 필수 통제 |
|---|---|---|
| 1 | 탐색·비교·정책 문의 표시, 선택지 제시, 선호 메모리 저장(본인·항목 제한), 주문 조회(본인 ID 사전 필터) | 출력 가드레일 + 로그 |
| 1~2 | 장바구니 담기·옵션 변경(본인·가역·멱등 키) — 매트릭스 B 기본대로 **동기 승인 카드는 본인 확인용** | 규칙 게이트(재고·가격 재확인) + 승인 카드 + 감사 |
| 2 | 가격·재고·배송 값 표시(틀리면 법적 영향 — 표시 자체는 가역이지만 생성 금지 규칙으로 통제), 프롬프트·θ·매핑 테이블 배포, 금액·수량 이상치 담기 | 규칙 게이트 + 골든셋 게이트 + 감사 |
| 3 | 환불 접수(금전·외부 전송, 접수 취소 가능), 온톨로지 버전 상승·카탈로그 스키마 버전 상승(전파 여섯 곳), 테넌트 정책 변경 | 승인(1~2인) + 폴백 + 호환 검증기 |
| 3→4 | 리뷰 본문을 읽은 세션의 환불 접수·외부 전송(등급 상향 규칙) | 승인자 상향 + 전송 툴 등급 상향 |
| 5 | 결제·주문 생성·환불 처리 — **에이전트 밖**(기존 결제 페이지 핸드오프, 툴 없음) | 자동 실행 금지 |

**승인 매트릭스** — 3/12 형식. 승인자는 역할로 적고 사람 매핑은 조직 디렉터리에서 조회한다.

| 행동 유형 | 영향 범위 | 요청자 역할 | 승인자 (역할) | 승인 수 | 시한 → 에스컬레이션 | 만료 시 | 등급 |
|---|---|---|---|---|---|---|---|
| 탐색·비교·정책 문의·주문 조회 | 본인 | 모두 / 로그인 고객 | 없음 (출력 가드레일 + 본인 ID 규칙 + 로그) | 0 | — | — | 1 |
| 장바구니 담기·옵션 변경 (정상 범위) | 본인 | 로그인 고객 | **요청자 본인 확인** (동기 승인 카드, `as_shown_hash`) | 1 | 5분 → 없음 | 담지 않음 | 1~2 |
| 장바구니 담기 (금액·수량 이상치 — 규칙 한도 또는 `decide("requires_approval")` p ≥ θ) | 본인·금전 | 로그인 고객 | 본인 확인 + 추가 확인 질문(수량·총액 재표시) | 1 | 5분 → 없음 | 담지 않음 | 2 |
| 환불 접수 ≤ 한도(예시 30만 원) | 금전·외부 | 로그인 고객 | 본인 확인(동기) → **CS 담당(비동기)** | 1 + 1 | 4시간 → CS 리드 → 24시간 만료 | 거부 + 수동 창구 안내 | 3 |
| 환불 접수 > 한도, 또는 세션 중 리뷰 본문 읽음 | 금전·외부 | 로그인 고객 | CS 리드(비동기) | 1 | 4시간 → CS 매니저 → 24시간 만료 | 거부 + 수동 창구 안내 | 3→4 |
| 정책 규칙·θ·매핑 테이블·프롬프트 배포 | 전 고객 | 백엔드 | 제품 책임자 + 규칙 테스트·매핑 골든셋 통과 | 1 | 1영업일 → 없음 | 배포 안 함 | 2 |
| 온톨로지 클래스 개명·병합 / 카탈로그 스키마 버전 상승 | 전 고객·전 팀 | 데이터 / 디자인 시스템 | **상품 운영 책임자 + 디자인 책임자** + 호환 검증기 통과 + 시행일 | 2 | 3영업일 → 아키텍트 | 배포 안 함 | 3 |
| 결제·주문 생성 | — | — | **에이전트 금지** — 결제 페이지 핸드오프 링크만 | — | — | — | 5 |

**감사 필드** — 3/12 감사 레코드 스키마를 기준으로, 이 시나리오 고유의 **가격 스냅샷**과 **UI 선택 정보**를 더한다. 승인 1건(장바구니·환불)마다 1레코드, 관측 로그와 저장소·보존 분리, 샘플링 없음.

| 블록 | 필드 | 왜 필요한가 |
|---|---|---|
| 상관 키 | `record_id`, `tenant_id`(단일이지만 처음부터), `run_id`, `checkpoint_id`, `trace_id` | 프론트 `ui_event` 스팬과 같은 trace로 연결 |
| 요청자 | `session_id`, `customer_id`(가명 키), `logged_in`, `channel: web\|mobile_web`, `requested_at` | 본인 확인 근거 |
| 행동 | `action: {type: add_to_cart\|change_option\|refund_request, tool, tool_version, args_hash, args_redacted(SKU·옵션·수량·금액), effect_grade, risk_level, reversible, session_flags: [external_data_read]}` | 리뷰를 읽은 세션의 등급 상향 근거 |
| **가격 스냅샷** | `price_snapshot: {offer_id, price, currency, valid_from, recorded_at, stock_at_display, stock_at_execute}` | **"표시된 가격과 실행 시점 가격이 같았는가"** — 민원 대응의 핵심 |
| 규칙 | `rules_applied[]: {rule_id, rule_version, result, matched_condition}` — 재고·가격 유효·판매 정책·연령·배송 지역·호환 경로·금액·수량 한도 | 어떤 규칙이 막았나·통과시켰나 |
| 판정 | `decisions: {intent, ui_intent, requires_approval}` 각각 `{source, choice, p, θ, question_version, fallback}` | 폴백 구간의 판정을 정상과 구분 |
| **UI** | `ui: {component, catalog_version, mapping_table_version, mapping_source: rule\|ontology\|model, tree_hash?(Declarative), fallback_reason?}` | 승인자가 **어떤 화면**을 봤는지 |
| 게이트·승인 | `gate_output`, `approval: {approval_id, matrix_row_id, matrix_version, approver: {role: self\|cs_agent\|cs_lead, user_id}, decision, as_shown_hash, card_shown: {price, qty, total, reversible_display, evidence_refs[]}, escalations[], expired}` | "승인자가 틀린 정보를 보고 승인했는가" |
| 실행 | `execution: {executed, executed_at, idempotency_key, args_hash_verified, result_code, result_summary_ref}` | 이중 실행·거짓 완료 추적 |
| 버전 | `versions: {policy_set, approval_matrix, ontology, catalog, mapping_table, prompt, decision_question, llm, framework}` | 시점 재현 키(릴리스 번들과 일치) |

보존 기간은 전자상거래 거래 기록 요건에 따라 **법무가 정한다**(이 위키에서 수치를 정하지 않는다). 리뷰 작성자 PII는 수집 시 마스킹되어 레코드에 들어오지 않고, 고객 ID는 가명 키로만 둔다. 추천 사유의 "왜"는 온톨로지 경로(`path` evidence)로 재구성하며 LLM 설명 텍스트는 보조 참조다(5/04).

### 9.5 관측 설계 — 한 요청을 끝까지 따라가는 트레이스

4절의 질의 흐름 ①~⑫를 스팬 트리로 옮긴다. 규약은 [Part 1/07 관측성 설계 요소](../01-foundations/07-operations-vocabulary.md)와 [Part 5/03](../05-cross-cutting/03-observability-tracing.md), 심각도는 1/07의 P1/P2/P3. 이 시나리오는 세 시나리오 중 유일하게 **프론트엔드가 1급 관측 원천**이다 — 과업 완료율·수정률·텍스트 폴백률은 `ui.render`·`ui.event` 스팬 없이는 계산할 수 없고, "사용자가 본 가격 = 실행 시점 가격"은 트레이스가 증명해야 한다. 그래서 AG-UI 어댑터가 `trace_id`를 이벤트 스트림에 실어 보내고 프론트가 모든 이벤트 요청 헤더(W3C Trace Context)에 되돌려 보내며, 레코드 근거 단위의 **`price_snapshot_version`**(`offer_id`·`valid_from`·`recorded_at`의 해시)이 ③ 검색 → ⑧ 렌더 → ⑩ 재확인 → 감사 `price_snapshot`까지 같은 값으로 따라간다. 모든 스팬에 버전 키 5종 + `agent.mapping_table_version`·`agent.ontology_version`·`agent.policy_set_version`, `tenant_id`, `channel`(web / mobile_web)이 붙는다.

| 구간 (레이어 → 단계) | 스팬 이름 | 반드시 남길 속성 | 이 시나리오 전용 지표 | 알림 → 런북 |
|---|---|---|---|---|
| ① Interaction · 세션·질의 수신 | `turn` (루트) → `invoke_agent {commerce_assistant}`, 프론트 `ui.stream {session}`(AG-UI 연결 단위) | `session_id`, `customer_id`(가명 키), `logged_in`, 뷰포트 폭, AG-UI 이벤트 스키마 버전, 선호 메모리 로드 여부·항목 수, 이벤트 순서 번호 시작값 | 동시 스트림 수, 재접속률, 메모리 적중률 | 재접속률 급증 → 스트림 게이트웨이 백프레셔·스냅샷 재동기화 확인 P2 |
| ② Reasoning · intent·슬롯 | `routing.decide {intent}` → 자식 `routing.shadow {decision_model}`, `generation.extract {slots}` | `agent.decision`(7개 중 하나), `agent.confidence`, θ, `agent.decision_source`, 질문 정의 버전, 슬롯 스키마 통과 여부, `agent.shadow_agreement` | intent 분포·ECE, **명확화 트리거율**(p < θ), 슬롯 스키마 실패율, 섀도 불일치율 | 명확화율 급증 또는 섀도 불일치 급등 → θ·질문 정의 점검, 벤더 변경 확인 P3 |
| ③ Reasoning → Knowledge · 비교 워커 | `invoke_agent {compare_worker}` → `tool.invoke {product_query}`(변환기), `retrieval.graph {compatibleWith}`, `retrieval.search {reviews}` → `retrieval.rerank` | 스텝 수(상한 3)·재계획, 변환기 쿼리 해시·결과 수, 그래프 홉 수·`path_ids[]`, `agent.evidence_ids[]` — `record`(SKU + **`price_snapshot_version`**, `recorded_at`), `sentence`(작성자 마스킹 여부), `path`; `agent.index_version`; **후보 신선도** = 검색 시각 − 레코드 `recorded_at` | 스텝 상한 초과율(9.1 ①), 상품 검색 p95(2/04), 리뷰 리랭커 p95, **후보 레코드 CDC 지연 분포**(9.1 ④), 경로 불일치(벡터 답 ≠ 그래프 답) 건수 | 후보 신선도 p95 > 15분 → 9.2 ① 런북(가격 "확인 중" 저하) P2 / 스텝 초과율 급등 → 워커 프롬프트 롤백 P2 |
| ④ Reasoning · 규칙 게이트 | `gate.evaluate {recommend}` | `rules_applied[]`(재고·유효 가격·판매 정책·호환 경로·후보 수 ≥ 2 — rule_id·version·결과), `agent.rules_version`, 차단 사유 코드, `substituteOf` 보충 발생 | 게이트 차단률(사유별), 품절 → 대체 보충률 | "유효 가격" 차단 급증 = CDC 지연의 **선행 신호** → 9.2 ① 런북 P2 |
| ⑤ Reasoning · 생성·바인딩 검증 | `generation.generate` → `generation.verify {binding}` | 1/01 모델 호출 속성 + 비교 축 선택, 인용 `evidence_ids[]`, **`agent.generated_value_violation`**(가격·재고·배송 값이 레코드 바인딩이 아닌 생성 토큰에서 나옴), citation 존재 결과 | **생성 금지 규칙 위반 건수(0)**(9.1 ④), citation 존재율, 스키마 실패율 | 위반 ≥ 1 → 9.1 ④ 런북(프롬프트 즉시 롤백 + 샘플 전수 리뷰) **P1** |
| ⑥ Reasoning · UI 판정 | `routing.decide {ui_intent}` | `agent.mapping_stage`(rule / ontology / model — 어느 단계에서 결정됐나), 후보 컴포넌트 집합, `agent.decision`(CompareTable), `agent.confidence`, θ, `agent.decision_source`, 섀도 일치, `agent.fallback_reason`, 매핑 캐시 적중, **행동 의도의 비규칙 단계 진입 여부** | UI 선택 정확도(골든셋 일일 재실행, 9.1 ②), 매핑 소스 분포, **텍스트 폴백률(원인별)**(9.1 ⑥), 행동 의도가 확률 단계로 흘러간 건수(0) | 폴백률 5분간 20% → 9.2 ② 런북(규칙 기본값·θ 상향) P2 / 행동 의도 비규칙 1건 → 설계 결함 **P1** |
| ⑦⑧ Reasoning → Interaction · 스트리밍·렌더 | `ui.stream` 이벤트 카운터(텍스트 델타·커스텀 트리·스냅샷·패치, 순서 번호) + 프론트 `ui.render {CompareTable}` | 컴포넌트 인스턴스 ID, `agent.catalog_version`, 프론트 export 버전, 트리 해시, 트리 검증 결과(스키마 / 조합 / 바인딩), 접근성 런타임 검증 결과, 렌더 지연, 요약 카드 폴백 여부, **표시된 각 가격 셀의 `price_snapshot_version`**, 디자인 토큰 enum 위반 | 첫 컴포넌트 p95·비교표 완성 p95(9.1 ①), 트리 검증 실패율·접근성 실패율·렌더 실패율(9.1 ⑥), **카탈로그 ↔ export 버전 불일치 건수** | 특정 컴포넌트 렌더 실패 집중 → 9.1 ⑥ 런북(카탈로그 버전 대조·재로드 안내) P2 / 트리 검증 실패 집중 → 비교표 의도 요약 카드 고정 P2 |
| ⑨ Interaction → Reasoning · 사용자 이벤트 | `ui.event {option_selected \| action_requested}` (헤더로 `trace_id` 되돌림) | 대상 인스턴스 ID, SKU·옵션(값은 해시·범주), `as_shown_hash`, `client_state_seq`, 패치 순서 번호, 서버 재검증 결과 ①~⑤ | **수정률·무시율**(9.1 ②), 순서 위반율, `as_shown_hash` 불일치 거부율, 렌더 → 첫 이벤트 시간 | hash 불일치 거부 급증 = 표시 후 가격 변동 **선행 신호** → 9.2 ① 확인 P2 / 순서 위반 급증 → 스냅샷 재동기화 강제 P2 |
| ⑩ Reasoning · 정책·재확인·승인 | `gate.evaluate {add_to_cart}` → `routing.decide {requires_approval}`, `approval.request` → `approval.resolve` | 재확인 결과 — **표시 시점 vs 실행 시점 `price_snapshot_version` 일치 여부**·가격 변경 감지, `agent.decision_source=rule`(강제), `approval_id`, 매트릭스 행·버전, 승인 카드 표시 성공, 카드 내용 해시, 대기 시간, 결과(approve / reject / expired) | **표시 ↔ 담기 시점 가격 불일치율**(9.1 ④ < 0.5%), 승인 카드 표시 성공률(100%), 승인 대기 p95·만료율, `requires_approval`이 규칙 외 소스로 판정된 건수(0) | 승인 카드 미표시 1건 → 상태 머신 `AWAITING_APPROVAL` 확인 **P1** / 불일치율 > 0.5% → 9.2 ① 런북 P2 |
| ⑪ Action · 장바구니 실행 | `tool.invoke {add_to_cart}` | `agent.idempotency_key`, 멱등 중복 히트(허용) vs 실제 이중 실행(불허), 결과 코드, optimistic "전송됨" 롤백 발생·이유 코드, 재검증기·멱등 저장소 상태(ok / unavailable → fail-closed), `agent.tool_version` | **승인 없는 실행·이중 실행 건수(0)**(9.1 ⑤), fail-closed 거부율(9.2 ③), 쓰기 툴 p95, optimistic 롤백률 | 이중 실행·승인 없는 실행 ≥ 1 → 9.1 ⑤ 런북(쓰기 킬 스위치) **P1** / fail-closed 거부율 급증 → 9.2 ③ 런북(쓰기 전면 중단 공지) **P1** |

**이 시나리오의 차별점 — 프론트 렌더·이벤트·가격 시점을 한 트레이스로.** `price_snapshot_version`이 ③(후보 레코드) → ⑧(가격 셀 표시) → ⑩(담기 직전 재확인) → 9.4 감사 `price_snapshot`에서 같은 값인지 조인하면 "사용자가 본 가격 그대로 담겼는가"를 민원 전에 대시보드에서 본다. ⑧ 렌더 스팬의 컴포넌트 인스턴스 ID를 ⑨ 이벤트가 들고 돌아오므로 과업 완료율(장바구니 담기 또는 명시적 종료)·수정률·무시율이 제품 분석 도구와의 조인 없이 트레이스 안에서 계산된다 — 5/03 레이어 간 정합성 검토의 "Part 3는 벤더 SDK, Part 4는 제품 분석으로 따로 기록"을 피하는 구조다. 섀도 결정 모델 판정(②⑥)은 관측에만, 폴백 구간 턴은 `agent.outcome=fallback`으로 표시해 층화 A/B 데이터에서 제외한다(9.2 ②).

**9.1 SLO → 측정 스팬·지표.**
- ① 첫 컴포넌트·비교표 지연 → `turn` + ③⑦⑧ 분해
- ② UI 선택 정확도·수정률 → ⑥ `routing.decide {ui_intent}` + ⑨ `ui.event`
- ③ 과업 완료율 → ⑧ 인스턴스 ID ↔ ⑨⑪ 이벤트 조인(의도별)
- ④ 재고·가격 불일치율·생성 위반 0 → ③ 후보 신선도 + ⑩ 재확인 + ⑤ `generated_value_violation`
- ⑤ 승인 없는 실행·이중 실행 0 → ⑩ `approval.resolve` ↔ ⑪ `tool.invoke` 순서·멱등 키
- ⑥ 텍스트 폴백률(원인별) → ⑥ `fallback_reason` + ⑧ 트리·접근성·렌더 실패
- ⑦ 가용성 → 전 구간 `agent.degradation[]` 비율

**9.2 장애 → 탐지 신호.**
- ① CDC 지연 → ③ 후보 신선도·④ 유효 가격 차단·⑨ hash 불일치 세 신호
- ② 결정 모델 폴백 폭증 → ②⑥ `fallback_reason`·서킷 이벤트
- ③ 멱등 저장소 다운 → ⑪ fail-closed 거부율·optimistic 롤백률

**대시보드 3장.**
- ① 사용자 관점 E2E: 과업 완료율(의도 유형별 분해)·평균 턴 수, 첫 컴포넌트·비교표 p95, 텍스트 폴백률(원인별 스택), 저하 플래그 비율("확인 중" 가격 셀 비율), 승인 카드 표시 성공률·대기 p95·만료율, **승인 없는 실행·이중 실행·생성 위반 카운터(상시 0)**.
- ② 레이어별 SLI: Knowledge — CDC 반영 지연·변경 큐 깊이·후보 신선도 분포·경로 불일치; Reasoning — intent ECE·명확화율, 게이트 차단(사유별), UI 매핑 소스 분포(rule / ontology / model)와 행동 의도 규칙 전용 확인, `requires_approval` 소스(규칙 100%); Interaction — 트리 검증·접근성·렌더 실패율, 카탈로그 ↔ export 일치, 순서 위반율, `as_shown_hash` 불일치율; Action — 멱등 중복 vs 이중 실행, fail-closed 거부율, optimistic 롤백률.
- ③ 비용·판정 분포: 판정 지점 4곳(intent · ui_intent · next_action · requires_approval)별 비용·소스 분포·확신도 히스토그램, 섀도 결정 모델 × 운영 일치 매트릭스, 리뷰 LLM 처리 비용(건수 상한 대비 소진율), 시맨틱 캐시 적중률(가격 유효 시점이 키라 프로모션 중 급락이 정상), 모델 티어별 비용.

**감사 추적 저장소로 분리되는 필드와 보존.** 9.4 감사 필드 표(승인 1건 = 1레코드)의 `price_snapshot`·`card_shown`·`ui`·`approval`·`execution`·`rules_applied`·`decisions`·`versions`를 ③⑥⑧⑩⑪ 스팬에서 `trace_id`·`approval_id` 기준으로 추출해 별도 저장소에 append-only로 쓴다. 보존 기간은 전자상거래 거래 기록 요건에 따라 **법무가 정한다**(9.4와 동일 — 이 절에서 수치를 정하지 않는다). 관측 트레이스에만 남는 것: 렌더 지연·이벤트 카운터·순서 번호·트리 해시·토큰·캐시·섀도 판정·A/B 층 표지 — 메타데이터 보존 예시 30일, 승인·폴백·불일치·위반 건은 90일. 본문 저장소(opt-in: 질의·생성 텍스트·인용된 리뷰 문장)는 예시 14일, 리뷰 작성자 PII는 수집 시 마스킹된 상태로만 들어오고 고객 ID는 가명 키뿐이다. 장바구니·주문 값(수량·금액)은 관측 스팬에 범주·해시로만, 원값은 감사 레코드에만.

**샘플링 정책.** 메타데이터와 **모든 `ui.render`·`ui.event` 스팬은 전수**(완료율·수정률의 분모). 본문은 opt-in으로 예시 3% 샘플. 테일 샘플링으로 턴 단위 전수 보존하는 것: 승인 카드가 뜬 턴(승인·거절·만료 포함 — 민원 재구성 단위), 생성 금지 위반, 게이트 차단, hash·순서 불일치 거부, 트리·접근성 검증 실패, 텍스트 폴백, fail-closed 거부, 저확신(p < θ) 판정, 이중 실행 의심(멱등 중복 히트). 샘플링 결정은 `turn` 종료 시 한 번 — 백엔드 스팬은 있는데 같은 턴의 프론트 렌더 스팬이 샘플링돼 없는 상태를 만들지 않는다. 프로모션 기간에는 본문 샘플률을 낮추되 ③ 후보 신선도와 ⑩ 재확인 결과는 어떤 경우에도 전수다.

### 9.6 운영 준비도 리뷰(ORR) 통과 조건

전 카테고리 확대(12주차) 전에 아래가 모두 체크되어야 한다.

- [ ] **[Knowledge]** CDC 반영 지연 p95 ≤ 5분이 실측되었고, 지연 초과 시 가격 "확인 중" 저하와 유효 시점 조건 엄격화가 자동으로 켜진다
- [ ] **[Knowledge]** 같은 변경 이벤트가 인덱스와 그래프를 모두 트리거하며, 경로 불일치(벡터 답 ≠ 그래프 답) 모니터가 있다
- [ ] **[Knowledge]** 온톨로지 변경의 전파 범위 표(추출·SHACL·게이트 어휘·매핑·`bindings`·enum)가 있고, 클래스 개명은 2인 승인 + 호환 검증기를 거친다
- [ ] **[Reasoning]** 가격·재고·배송 값은 레코드 바인딩만 허용하고 생성 금지 규칙이 CI와 운영 양쪽에서 0건을 보고한다
- [ ] **[Reasoning]** 담기 직전 재확인 게이트(재고·가격 유효 시점)가 승인과 별도로 실행되며, 승인 카드 표시 후 가격이 바뀌면 `as_shown_hash` 불일치로 거부된다
- [ ] **[Reasoning]** `requires_approval`과 행동 의도(장바구니·환불)의 판정 수단이 **규칙 전용**임이 매핑 결과 감사로 확인된다
- [ ] **[Reasoning]** 멱등 키 없는 쓰기 툴이 없고, 쓰기 모의 섀도에서 이중 실행 0건·승인 없는 실행 0건이 확인되었다
- [ ] **[Interaction]** 결정 모델·매핑 테이블·온톨로지 조회 장애 각각에서 규칙 기본값 → 텍스트 폴백이 30초 내 전환되고 저하 플래그가 기록된다
- [ ] **[Interaction]** 승인 카드는 텍스트 폴백이 **금지**되어 있고, 미표시 시 상태 머신이 `AWAITING_APPROVAL`에 머물며 실행하지 않는다
- [ ] **[Interaction]** 멱등 키 저장소·재검증기 다운 시 승인 이벤트가 거부(fail-closed)되고, optimistic "전송됨"이 이유 코드와 함께 롤백된다
- [ ] **[Interaction]** Declarative 비교표의 트리·조합·바인딩 검증기와 접근성 런타임 검증이 있고, 실패 시 요약 카드로 저하된다
- [ ] **[Interaction]** 레지스트리 ↔ 프론트 export 호환 검증기가 CI에 있고, 카탈로그 + 프론트가 한 롤백 단위로 정의되어 있다
- [ ] **[횡단]** 감사 레코드에 `price_snapshot`·`card_shown`·`catalog_version`·규칙 버전이 있고, 민원 1건을 레코드만으로 재구성하는 리허설을 마쳤다
- [ ] **[횡단]** 7개 E2E SLO 대시보드와 알림·런북이 있고, 승인 카드는 A/B 대상에서 제외되어 있다
- [ ] **[횡단]** RACI 모든 행에 A가 있고, 기술 부채가 기록되어 있다 — "결제는 에이전트 밖", "A2UI 보류·네이티브는 요약 카드", "리뷰 속성은 샘플링 수준", "결정 모델은 섀도"
- [ ] **[횡단]** 한 턴의 트레이스에서 `price_snapshot_version`이 `retrieval(record evidence) → ui.render(표시 가격 셀) → gate.evaluate(담기 직전 재확인) → 감사 price_snapshot`까지 같은 값으로 이어지고, 불일치 쿼리가 대시보드에 있다
- [ ] **[횡단]** 프론트 `ui.render`·`ui.event` 스팬이 백엔드 스팬과 같은 trace_id·같은 백엔드에 전수 기록되어 과업 완료율·수정률이 외부 조인 없이 계산되며, 승인 카드 미표시·행동 의도의 비규칙 매핑·이중 실행·생성 금지 위반이 각각 P1 알림으로 연결되어 있다
