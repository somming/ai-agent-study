# 시나리오 B: 커머스 상담 + Generative UI

> **범위**: 상품 온톨로지 → 에이전트 → 동적 UI까지 구성 예시
> **시각화**: [`assets/html/scenario-commerce-genui.html`](../assets/html/scenario-commerce-genui.html)
> **성격**: [Part 7 개요](00-overview.md)의 비교표대로 **Interaction 중심**, 자율성 중간(툴 호출 에이전트), UI는 Controlled → 일부 Declarative. 세 시나리오 중 유일하게 "사용자가 결과를 조작하는" 시스템이며, 상품 온톨로지 → 컴포넌트 매핑이 설계의 중심이다.

## 1. 상황 설정

가상 조직이다. 아래 규모 수치는 모두 **설계 가정**이며, "이 정도 규모·갱신 속도면 어떤 선택이 달라지는가"를 보여 주기 위한 값이다.

| 항목 | 내용 |
|---|---|
| 업무 도메인 | 가전·디지털 기기를 파는 자사 온라인몰(단일 테넌트). 상품 탐색·비교·옵션 선택·장바구니·주문 조회를 돕는 상담 어시스턴트. **결제는 어시스턴트 밖**(기존 결제 페이지·외부 결제 대행) |
| 사용자 | 비로그인 방문자(탐색·비교)와 로그인 고객(장바구니·주문 조회). 월 활성 사용자 수십만, 피크 시 동시 상담 수백 세션(설계 가정). 사용자는 **답을 읽고 → 비교표를 보고 → 옵션을 고르고 → 장바구니에 담는다**. 웹 + 모바일 웹, 디자인 시스템이 엄격하다 |
| 데이터 | **정형**: 상품 마스터 수십만 SKU(카테고리·브랜드·속성·호환성·대체 상품), 가격·재고(분 단위 갱신, 하루 수만 건 변경 이벤트), 주문·배송 상태(고객 본인 것만). **반정형**: 리뷰 수백만 건(하루 수천 건 신규), FAQ·배송·교환 정책 문서 수백 건. **멀티모달**: 상품 이미지. **언어**: 한국어 중심, 모델명·스펙은 영문 혼재. **권한**: 주문·장바구니는 본인 세션에 한정, 리뷰 작성자 PII 포함 |
| 핵심 요구 | **정확도**: 재고·가격·호환성이 틀리면 금전 민원 — 사실 정보는 레코드 그대로, 추천은 정책·재고 규칙을 통과한 것만. **근거**: 상품 레코드·리뷰 문장 citation 권장(규제상 필수는 아님). **지연**: 대화형(수 초), 비교표까지 포함. **규제**: 전자상거래 표시 의무·개인정보(법무 검토 사항으로 두고, 설계는 "가격·재고·배송 정보는 시스템 레코드 외 생성 금지"로 고정) |
| 제약 | **팀**: 프론트(React) 팀과 백엔드(Python) 팀이 분리, 디자인 시스템 팀 보유, 데이터 엔지니어 2명. RDF 경험 없음, 상품 DB 스키마는 잘 정리돼 있음. **예산**: 리뷰 전수 LLM 처리는 건수 비례라 상한 필요. **기존 시스템**: 상품 DB(CDC 가능), 검색엔진(상품 검색에 이미 사용), 장바구니·주문 API, 외부 결제 대행. 단일 벤더 LLM 종속 허용 |

## 2. 요구사항 → 결정 변수 추출

[종합 결정 트리](../00-overview/02-decision-guide.md)의 입력 변수 V1~V15에 값을 채우고, 질문 Q1~Q15를 돌린 경로를 적는다.

| # | 변수 | 이 시나리오의 값 | 움직이는 선택 |
|---|---|---|---|
| V1 | 데이터 유형 | **정형 중심**(상품·가격·재고·주문) + 반정형(리뷰·FAQ) + 이미지 | 레코드 근거 단위, 규칙 추출 그래프, 변환기 패턴 |
| V2 | 규모·갱신 빈도 | SKU 수십만, 리뷰 수백만 / 가격·재고 **분 단위** / 트래픽 대량 | CDC, 결정 모델의 비용 이점이 의미 있음 |
| V3 | 지연 요구 | 응답 대화형(<5s), 신선도 **분** | CDC + 변경 큐, 리랭커는 리뷰 경로에만 |
| V4 | 정확도·근거 요구 | 사실(가격·재고)은 레코드 그대로, citation 권장 | 레코드 citation, 규칙 게이트 |
| V5 | 규제·감사 | 전자상거래 표시 의무(법무), 리뷰 PII, 주문은 본인 한정 | bitemporal 가격, PII 마스킹, 본인 확인 |
| V6 | 멀티홉·동일성·설명 | **있음** — 호환성("이 TV에 맞는 사운드바"), 대체 상품, "왜 추천" 설명. 정형 관계라 규칙 추출 가능 | 상품 온톨로지 + 규칙 추출 그래프 |
| V7 | 과업 예측 가능성 | 몇 가지 분기(탐색·비교·옵션·장바구니·주문 조회·정책 문의) | 라우팅 + 오케스트레이터-워커 |
| V8 | 실패 비용 | **금전**(잘못된 장바구니·가격 안내) — 결제는 밖이라 비가역 아님 | 정책 게이트, 동기 승인, 멱등 키 |
| V9 | 행동 유무 | 쓰기 포함 툴 10~20개(검색·비교·장바구니 담기·옵션 변경·주문 조회·환불 접수) | 등급별 멱등·게이트, 2단계 라우팅은 불필요 |
| V10 | 사용자 행위 | **선택·비교 + 장바구니 승인** | 3-Layer 전체, Controlled 기본 |
| V11 | 플랫폼 | 웹 + 모바일 웹(네이티브는 2차) | AG-UI, 반응형, A2UI 보류 |
| V12 | 조직 경계 | 프론트·백 분리, 외부 결제 대행(에이전트 밖) | AG-UI, 네이티브 툴(소비자 하나) |
| V13 | 팀 역량 | 디자인 시스템 팀, Python 백엔드, React 프론트, RDF 없음 | DS 패키지 내장 레지스트리, CopilotKit/AG-UI SDK, 경량 온톨로지 |
| V14 | 예산·반출·종속 | 리뷰 LLM 처리 상한, 단일 벤더 허용 | 리뷰는 샘플·요약 수준, 벤더 SDK 후보 |
| V15 | 언어 | 한국어 + 영문 모델명 | 형태소 BM25 + 상품 코드 정확 매칭, 결정 모델 한국어 골든셋 |

**질문 트리 경로**: Q1 읽기만 → **아니오**(3-Layer, Controlled부터) · Q2 행동 → **예**(결정 레이어·검증기·가드레일 생략 불가, 등급별 멱등) · Q3 정형 중심 → **예**(레코드 근거 단위, 템플릿 직렬화, 규칙 추출 그래프, 변환기) · Q4 분 단위 SLO → **예**(CDC + 변경 큐) · Q5 citation 필수 → **부분**(가격·재고는 bitemporal, 리뷰는 존재 검증만) · Q6 멀티홉·설명 → **예, 단 정형 관계**(경량 상품 온톨로지, 규칙 추출 그래프, GraphRAG 계열은 불필요) · Q7 PII·권한 → **예** · Q8 예측 가능 → **예, 몇 가지 분기**(라우팅 + 오케스트레이터-워커, Tool-use) · Q9 당사자 둘 이상 → **아니오**(툴은 단일 백엔드; 프론트 분리는 Q14에서) · Q10 결정 모델 한국어 `[실측]` → **아직 아니오**(LLM 툴 호출/소형 분류기로 시작, `decide()` 뒤에 결정 모델 섀도 → 골든셋 통과 후 교체) · Q11 쓰기 툴 → **예**(Schema + 규칙 게이트, 정책 엔진) · Q12 멀티세션 → **예(로그인 고객)**, 선호 메모리는 항목 제한 + no-memory 대비 `[실측]` · Q13 비가역·고액 → **아니오**(결제가 밖), 단 장바구니·환불 접수는 승인 카드 · Q14 프론트·백 분리 → **예**(AG-UI) · Q15 벤더 종속 → **예**(벤더 SDK 또는 LangGraph PoC).

## 3. 단계별 설계 결정

선택은 세 결정 매트릭스의 시나리오 B 행과 일치시켰다. "선택 이유"는 해당 페이지의 선택 가이드 조건을 인용한다.

### 3.1 데이터 파이프라인 (Part 2)

|---|---|---|---|---|

| 지식그래프 | **규칙 추출 중심 그래프**: 상품–카테고리–브랜드–호환–대체–옵션. 소스는 마스터 DB 필드. LLM 추출은 리뷰 속 속성 언급(소음·발열 등)에만, 근거 문장 필수 + SHACL 등가 제약 | 전면 LLM 추출; 그래프 미도입 | 2/05 선택 가이드: "정형 데이터(마스터)가 섞여 있다면 → 하이브리드 추출, 정형은 규칙. | 동기화 | **CDC 이벤트 기반 + 단일 변경 큐**, 재고 소진·가격 변경 톰스톤 즉시, 같은 이벤트가 인덱스와 그래프를 모두 트리거. 리뷰는 증분 배치 | 폴링 배치 | 2/07 선택 가이드: "소스가 운영 DB이고 SLO가 분 단위라면 → CDC + 단일 변경 큐. 삭제까지 이벤트로 오는 유일한 방식". 2/05 한계 "벡터만 갱신하고 그래프 방치" 회피 | [2/07](../02-data-pipeline/07-freshness-and-sync.md) |

### 3.5 트렌드 세 축 적용

| 축 | 이 시나리오에서의 자리 | 채택 수준 | 채택을 올리기 위한 조건 |

## 4. 전체 아키텍처

시각화: [`assets/html/scenario-commerce-genui.html`](../assets/html/scenario-commerce-genui.html) — 선택한 노드만 진하게, 뺀 노드(멀티 에이전트 오케스트레이션, MCP, 결제 툴, A2UI·MCP Apps 등)는 흐리게. 번호는 아래 흐름과 같다.

사용자 질의 1건("20만 원 이하 노이즈캔슬링 헤드폰 3개 비교해 줘. 내 폰이랑 호환되는 걸로")이 끝까지 흐르는 경로:

1. **[Interaction]** 사용자가 모바일 웹 상담 위젯에 입력. AG-UI 어댑터가 `RunStarted` + 사용자 메시지 이벤트를 백엔드로 전송. 로그인 고객이면 세션 본인 ID, 항목 제한 선호 메모리(보유 기기·선호 브랜드)가 상태에 로드된다.
2. **[Reasoning]** 입력 가드레일(규칙) → 질의 이해: 한국어 정규화 → `decide("intent")` = `compare`(운영은 소형 LLM/분류기, 결정 모델은 섀도 로그) → 슬롯 추출(카테고리=헤드폰, 가격 상한, 속성=노이즈캔슬링, 호환 대상=보유 폰).
3. **[Reasoning → Knowledge]** 비교 워커(Plan-and-Execute): ① 온톨로지 필터(Category ⊑ 헤드폰, Offer.price ≤ 상한, 재고 > 0, 유효 시점 = 현재)를 **변환기**가 읽기 전용 쿼리로 변환·실행 → 후보 레코드 ② 호환성 그래프 1홉(`compatibleWith` 보유 폰) → ③ 후보별 리뷰 문장 hybrid 검색 + cross-encoder. Knowledge가 **근거 단위(계약 ①)** 반환: `evidence_type: record`(SKU·가격·재고·유효 시점·옵션), `sentence`(리뷰 문장·작성자 마스킹), `path`(호환 경로).
4. **[Reasoning]** 뉴로심볼릭 **규칙 게이트**: 재고·유효 가격·판매 정책·호환 경로 존재·후보 수 ≥ 2를 검사. 통과한 후보만 생성 단계로. 한 후보가 재고 소진이면 대체 관계(`substituteOf`) 1홉으로 보충.
5. **[Reasoning]** 생성: 구조화 출력 — 비교 축(가격·무게·배터리·노이즈캔슬링 등급·호환) 선택과 추천 사유 문장(리뷰 `evidence_id` 인용). **가격·재고 값은 생성하지 않고 레코드 필드를 바인딩**. citation 존재 규칙 검증.
6. **[Reasoning]** `decide("ui_intent")`: 규칙(모바일 폭 → 열 ≤ 3, 항목 3) → 온톨로지(다중 Product + 속성 축 → 후보 `CompareTable` / `ProductCardList`) → LLM(섀도: 결정 모델) → `CompareTable`(Declarative). 승인 필요 여부 판정은 "비교"라 해당 없음.
7. **[Reasoning → Interaction]** **렌더 가능한 응답(계약 ②)**: `text`(요약), `citations[]`, `ui_intent = {component: CompareTable, tree: …, bindings: SKU 레코드}`, 확신도, `requires_approval: false`. AG-UI 이벤트(텍스트 델타, 커스텀 이벤트에 트리, 상태 스냅샷)로 스트리밍.
8. **[Interaction]** 서버 재검증 통과한 트리를 **트리·조합·바인딩 검증기**가 검사 → React 렌더러가 디자인 시스템 토큰으로 비교표 렌더(접근성 런타임 검증, 실패 시 요약 카드 폴백). 각 행에 `OptionSelector`(색상), `AddToCartButton`(Controlled).
9. **[Interaction → Reasoning]** 사용자가 2번 상품의 색상을 고르고 "담기"를 누름 → **사용자 이벤트(계약 ③)**: `option_selected`(SKU·옵션) → 상태 패치(순서 번호), 이어서 `action_requested`(add_to_cart, SKU·옵션·수량, `as_shown_hash`).
10. **[Reasoning]** 정책 엔진: 등급 "쓰기-가역" → 규칙 게이트 재실행(재고·가격 **재확인**: 1~8단계 사이에 가격이 바뀌었는지) ∧ `decide("requires_approval")`(수량·금액 이상치 아님 → 자동 허용 범위지만 매트릭스 B 기본대로 **동기 승인 카드**는 표시) → **승인 카드** 렌더(금액·수량·가역성 "장바구니에서 삭제 가능").
11. **[Interaction → Reasoning → Action]** 사용자 승인 이벤트(계약 ③, `as_shown_hash` 일치 확인) → 장바구니 툴 실행(멱등 키 = 세션·SKU·옵션·hash) → optimistic "전송됨" → 실행 결과 상태 스냅샷 → `CartSummary` 카드. "결제하기"는 **기존 결제 페이지로 핸드오프**(에이전트 밖, 링크만).
12. **[Cross-cutting]** 전 과정의 스팬(intent·UI 판정과 섀도 결정 모델 판정, 게이트 결과·규칙 ID, 레코드 `evidence_id`, UI 렌더·이벤트 스팬, 멱등 키)이 같은 trace_id로 기록. 승인 이벤트는 감사 레코드로 불변 저장.

## 7. 예상되는 한계와 2차 과제

**이 설계가 해결하지 않는 것**

- **결제·주문 생성·환불 처리**. 에이전트 밖에 둔 것이 설계 결정이다. 결제 대행이 본인 인증·규제 준수를 맡고, 에이전트는 장바구니까지만. 2차에 결제를 넣더라도 3/12 "비동기 HITL + 체크포인트 + 만료=거부"와 4/06 승인 카드가 선행 조건이다.
- **VLM 캡션의 "근거 있는 환각"**(색상·재질 오기). 등급 C·검증 근거 불허·"생성됨" 표시로 완화할 뿐 막지 못한다([2/08](../02-data-pipeline/08-grounding-data-design.md) 한계).
- **리뷰 LLM 처리 비용**이 건수에 비례한다. 샘플링·요약 수준으로 상한을 두므로 롱테일 상품의 리뷰 속성은 비어 있을 수 있다.
- **결정 모델의 UI 선택 적용 사례 부족·한국어 미검증**. `[실측]` 전까지 LLM 병행이 필수이고, 비용 이점은 가정이다([4/99](../04-dynamic-ui/99-decision-matrix.md) 한계).
- **Declarative 비교표의 접근성**은 런타임 검증기에 의존한다. 검증기가 못 잡는 트리 품질 문제(헤딩 순서·포커스 흐름)는 폴백·사람 샘플링으로만 발견된다.
- **인젝션**: 리뷰 본문이 에이전트 입력이 되는 경로가 있다. 등급 상향·규칙 게이트가 피해를 제한하지만 탐지는 뚫릴 수 있다([5/01](../05-cross-cutting/01-security-prompt-injection.md)).

**규모 10배(SKU 수백만, 입점 셀러 다수, 네이티브 앱)가 되면 바뀌는 것**

- 멀티테넌트(입점 셀러): 테넌트 인덱스 분리, 그래프는 엣지 단위 `tenant_id`(공통 브랜드 노드가 경계를 흐림 — [2/99](../02-data-pipeline/99-decision-matrix.md) B 한계), 게이트웨이 단일 강제가 생존 조건.
- 전용 벡터DB + 양자화 + 2단계 재순위(2/04 조건 B), 레지스트리 수십 → 백 개면 결정 모델 enum 계층화가 사실상 필요.
- 네이티브 앱: Declarative 내용층을 A2UI로 교체 검토, 단 v0.9 `[벤더]`·렌더러 품질 `[실측]` 선행, 그 전엔 자체 Controlled 네이티브 렌더러([4/07](../04-dynamic-ui/07-frontend-integration.md)).
- 판정 건수가 커져 결정 모델의 비용 이점이 커지는 반면, 외부 API로 상태(장바구니·선호)가 나가는 경로의 PII 최소화·데이터 처리 계약이 쟁점이 된다(3/11 한계).

**트렌드 축을 채택으로 올리기 위해 필요한 `[실측]`**

| 축 | 필요한 실측 | 판단 기준 |
|---|---|---|
| 온톨로지 | 온톨로지 후보 축소 유무에 따른 UI 선택 정확도·폴백률, 추출 위반율, 매핑 테이블 행 수 변화 | 후보 축소가 정확도를 올리고 매핑 행 수를 줄임 |
| 뉴로심볼릭 | 게이트 차단률·오탐률, 변환기 쿼리 오류율, 트리 검증 실패율과 그중 사람 검수에서 "정당한 차단" 비율 | 오탐이 사용자 이탈을 만들지 않는 수준 |
| 결정 모델 | 세 판정 지점의 한국어 골든셋 정확도·ECE·지연·비용 (LLM/분류기와 동일 셋), 베타 상태·가격 변동 모니터 | 지점별로 LLM 동등 이상 + 보정 확인 시 교체. 행동 판정은 제외 |

## 8. 다른 시나리오와의 차이점

| 단계 | B (이 시나리오) | A 문서 QA | C 운영 인시던트 | 왜 B는 다르게 선택했나 |
|---|---|---|---|---|
| 근거 단위 | **레코드** + 리뷰 문장 + 호환 경로 | 청크 + 문장 | 로그 레코드·메트릭 구간·런북 단계 + 트리플 경로 | 데이터가 정형이라 값 대조와 표 렌더가 필요하고, 레코드가 곧 UI 바인딩이다 |
| 온톨로지 | 상품 온톨로지가 UI 매핑·게이트·그래프의 공통 어휘 | 택소노미만 | 서비스 의존성 온톨로지(영향 분석용) | Interaction이 중심이라 온톨로지의 주 소비자가 UI 매핑이다 |
| 동기화 | CDC 이벤트(분 단위) | 증분 배치 | 실시간 스트림 | 가격·재고가 틀리면 금전 민원이라 신선도가 핵심 |
| 자율성 | 라우팅 + 오케스트레이터-워커, Tool-use(스텝 상한 3) | 라우팅 워크플로우 | Supervisor 멀티 에이전트 | 경로는 열거 가능하지만 경로 안의 툴 조합이 질의마다 다르다 |
| 결정 모델 | intent·UI 선택·승인 필요 — 섀도 → 지점별 교체 | 라우팅·분류, 섀도 | 심각도·승인 게이팅, 핵심 | 트래픽이 커 비용 이점이 의미 있지만 틀려도 사용자가 다른 UI를 고를 수 있어 보수적 θ로 시험 가능 |
| 뉴로심볼릭 | 변환기 + 규칙 게이트(재고·가격·정책·호환) | 정합성 검증 | 런북 규칙 ∧ LLM, 변경 명령 게이트 | 행동이 있으므로 "행동 앞 게이트"가 필요하고, 정형 데이터라 변환기가 환각을 구조적으로 막는다 |
| HITL | 동기 승인 카드(장바구니), 환불 접수는 비동기 | 없음 | 비동기 승인 + 에스컬레이션 + 만료=거부 | 결제가 밖이라 비가역 행동이 없고, 승인은 "본인 확인" 성격 |
| UI | Controlled → 비교표만 Declarative, AG-UI, 수십 개 컴포넌트, 층화 A/B | Controlled citation 렌더 4개, 내장 스트리밍 | Controlled 고정, 승인 카드·diff, A/B 금지 | 사용자가 선택·비교하므로 UI 자유도가 가치가 있고, 열 구성이 매번 달라 Declarative가 정당화된다 |
| 메모리 | 항목 제한 선호 메모리(`[실측]` 후) | no-memory | 에피소드 메모리 보수적 | 반복 방문 고객의 보유 기기·선호가 추천 품질을 바꾼다 |
