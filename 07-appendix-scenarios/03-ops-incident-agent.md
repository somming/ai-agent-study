# 시나리오 C: 운영 인시던트 대응 에이전트

> **범위**: 로그/메트릭 파이프라인 → 결정 모델 게이팅 → 승인 UI 구성 예시
> **시각화**: [`assets/html/scenario-ops-incident.html`](../assets/html/scenario-ops-incident.html)
> **성격**: [Part 7 개요](00-overview.md)의 비교표대로 **Reasoning/Action 중심**, 자율성 높음(멀티 에이전트, 툴 실행), UI는 HITL 승인 중심. 세 시나리오 중 유일하게 "틀리면 서비스가 내려가는" 시스템이며, **진단(열린 탐색)과 조치(고정 절차)의 분리**, **Rule ∧ Model 게이트**, **감사 추적**이 설계의 중심이다.

## 1. 상황 설정

가상 조직이다. 아래 규모 수치는 모두 **설계 가정**이며, "이 정도 규모·실시간성이면 어떤 선택이 달라지는가"를 보여 주기 위한 값이다.

| 항목 | 내용 |
|---|---|
| 업무 도메인 | 구독형 B2B 소프트웨어를 운영하는 조직. 마이크로서비스 수백 개, prod/stg 환경 분리. 알림이 뜨면 **원인 진단 → 영향 범위 분석 → 조치 제안 → 승인 후 실행**까지를 돕는 에이전트. 조회는 자동, **변경은 반드시 승인** |
| 사용자 | SRE 팀(교대 온콜)과 서비스 소유 팀 수십 개의 담당자. 동시 사용자는 적지만(인시던트당 수 명) **야간·교대 중 사용**이 많고, 승인자는 인시던트마다 바뀐다. 사용자는 **진단 결과를 읽고 → 영향 범위를 확인하고 → 조치를 승인·거절·에스컬레이션**한다. 운영 콘솔과 모니터링 포털에 임베딩 |
| 데이터 | **스트림**: 로그·메트릭(기존 로그 인프라에 하루 수 TB 적재), 알림 하루 수백 건(그중 실제 인시던트는 소수). **반정형**: 인시던트 티켓 누적 수만 건(한국어 서술 + 영어 로그 발췌), 런북 수백 건(절차 단계 포함, 개정 잦음), 아키텍처 문서·도표. **정형**: CMDB(서비스·컴포넌트·의존 관계 수천 개·담당 팀·환경). **채팅**: 인시던트 채널 대화. **언어**: 한국어 티켓·런북 + 영어 로그·에러 코드 |
| 핵심 요구 | **정확도**: 진단은 틀릴 수 있지만(사람이 검토) **조치 실행 오류는 허용 0** — 잘못된 재시작·롤백·스케일 변경은 되돌릴 수 없는 장애로 이어진다. **근거**: 모든 진단 주장에 로그 레코드·메트릭 구간·런북 단계 citation 필수. **지연**: 진단은 수십 초~수 분 허용, 승인 후 조치는 빠르게. **규제·감사**: 변경 관리 정책(변경 창·승인자 분리), 모든 승인·실행의 감사 추적, 로그 속 고객 식별자 PII |
| 제약 | **팀**: 플랫폼 팀이 에이전트를 만들지만 **툴(재시작·롤백·스케일·설정 변경 등 20개 초과)은 여러 서비스 팀이 소유**. Python·Go 혼재, 모니터링 포털은 React. 데이터 엔지니어링·검색엔진 운영 경험 있음, RDF 없음. **예산**: 원시 로그 전수 임베딩은 불가(비용). **기존 시스템**: 로그 인프라(검색엔진 보유), 메트릭 저장소, CMDB, 티켓 시스템, 배포·오케스트레이션 API. 벤더 중립 요구(모델 교체 가능해야 함) |

## 2. 요구사항 → 결정 변수 추출

[종합 결정 트리](../00-overview/02-decision-guide.md)의 입력 변수 V1~V15에 값을 채우고, 질문 Q1~Q15를 돌린 경로를 적는다.

| # | 변수 | 이 시나리오의 값 | 움직이는 선택 |
|---|---|---|---|
| V1 | 데이터 유형 | 반정형(로그·티켓·런북) + 스트림 + 정형(CMDB) + 도표 | 엔트리 단위 청킹, 규칙 추출 그래프, 변환기(로그 쿼리) |
| V2 | 규모·갱신 빈도 | 로그 하루 수 TB(원시), 티켓 수만, 런북 수백 / **실시간** | 원시 로그는 BM25(기존 인프라), 요약·티켓만 임베딩 |
| V3 | 지연 요구 | 진단 수십 초~분 허용, 조치는 빠르게, 신선도 **분 이하** | 진단은 루프 허용(상한), 조치는 고정 워크플로우, 이벤트 기반 |
| V4 | 정확도·근거 요구 | **citation 필수**(로그·메트릭·런북) | 하이브리드 근거 단위 + 경로, 후검증 |
| V5 | 규제·감사 | 변경 관리 정책, **감사 추적 필수**, PII(고객 식별자) | 감사 레코드, 승인자 분리, PII 마스킹, A/B 금지 |
| V6 | 멀티홉·동일성·설명 | **있음** — "이 서비스 → 의존 → 그 컴포넌트 → 과거 인시던트", 영향 범위 설명 | 서비스 의존성 그래프 적극 도입, 트리플 경로 근거 |
| V7 | 과업 예측 가능성 | **진단은 열린 탐색**, 조치는 고정 절차(런북) | 자율 에이전트(상한) + 조치 워크플로우 |
| V8 | 실패 비용 | **되돌릴 수 없음**(운영 변경) | 세 갈래 θ, 비동기 HITL, Rule ∧ Model |
| V9 | 행동 유무 | 쓰기 툴 **20개 초과**, 여러 팀 소유, 외부 전송(알림·티켓) | 자체 MCP 서버, 2단계 라우팅, 멱등 키 |
| V10 | 사용자 행위 | **승인**(행동으로 이어짐) | 승인 카드·diff·에스컬레이션 UI |
| V11 | 플랫폼 | 운영 콘솔 + 모니터링 포털 임베딩(웹) | AG-UI, 위젯 |
| V12 | 조직 경계 | 여러 팀(툴 소유), 백엔드 언어 다수, 타 조직 에이전트는 2차 | MCP, Supervisor, A2A는 보류 |
| V13 | 팀 역량 | Python·Go, 검색엔진 운영, CMDB 보유, RDF 없음 | 기존 검색엔진 hybrid, CMDB 상향식 경량 온톨로지, LangGraph 또는 ADK |
| V14 | 예산·반출·종속 | 원시 로그 임베딩 불가, **벤더 중립 요구**, 로그 본문 외부 전송 최소화 | LangGraph, 결정 모델은 `decide()` 뒤 + 규칙 폴백 |
| V15 | 언어 | 한국어 티켓·런북 + 영어 로그 | 형태소 BM25 + 에러 코드 정확 매칭, 결정 모델 한국어 티켓 `[실측]` |

**질문 트리 경로**: Q1 읽기만 → **아니오**(3-Layer) · Q2 행동 → **예**(결정 레이어·검증기·가드레일 생략 불가) · Q3 정형 중심 → **부분**(CMDB는 규칙 추출, 로그·티켓은 엔트리 청크, 로그 질의는 변환기) · Q4 분 단위 SLO → **예**(이벤트 기반) · Q5 citation·감사 → **예**(런북 버전, 근거 문장, 감사 로그, 후검증) · Q6 멀티홉·설명 `[실측]` → **예**(과거 인시던트 분석에서 의존 경로 질의 확인된 것으로 설계 가정; 경량 온톨로지 + 규칙 그래프 + 경로 근거) · Q7 권한·PII → **예**(환경·팀 필터, 고객 식별자 마스킹) · Q8 예측 가능 → **아니오(진단) / 예(조치)** — 자율 에이전트(상한) + Plan-and-Execute + Reflection + 내구 실행, 조치는 워크플로우 고정 · Q9 당사자 둘 이상 → **예**(자체 MCP 서버, Supervisor + 공유 상태, 2단계 툴 라우팅) · Q10 결정 모델 한국어 `[실측]` → **아직 아니오**(규칙 + 소형 LLM/분류기, `decide()`·트레이스·평가셋 먼저, 결정 모델 섀도; 승인 필요 판정은 통과 전까지 "모두 승인") · Q11 쓰기 툴 → **예**(Schema + 규칙 게이트 + 정책 엔진 + 행동 직전 규칙 최종 허가) · Q12 멀티세션 → **예, 보수적**(과거 인시던트는 RAG·KG로, 에피소드 메모리는 no-memory 대비 후) · Q13 비가역·고액 → **예**(Controlled 고정, 승인 카드, 타임아웃 = 실행 안 함 + 에스컬레이션, 매핑 규칙만, A/B 금지) · Q14 프론트·백 분리·백엔드 다수 → **예**(AG-UI) · Q15 벤더 종속 → **아니오**(LangGraph; Go 팀 비중이 크면 ADK PoC).

## 3. 단계별 설계 결정

선택은 세 결정 매트릭스의 시나리오 C 행과 일치시켰다. "선택 이유"는 해당 페이지의 선택 가이드 조건을 인용한다.

### 3.1 데이터 파이프라인 (Part 2)

| 단계 | 선택 | 고려한 대안 | 선택 이유 | 근거 페이지 |
|---|---|---|---|---|
| 수집·파싱 | 티켓·알림은 API/웹훅(이벤트), 런북은 위키 커넥터, CMDB는 API 스냅샷 + 변경 이벤트, 아키텍처 도표는 VLM 캡션("생성됨", 등급 C). 원시 로그·메트릭은 **복사하지 않고 기존 저장소를 툴로 조회** | 로그 전수 수집·재적재 | 2/01 선택 가이드: "소스가 운영 DB이고 신선도가 분 단위라면 → CDC"의 정신을 이벤트 소스에 적용. 로그는 이미 검색 가능한 인프라에 있어 복제가 비용만 늘린다 | [2/01](../02-data-pipeline/01-source-ingestion.md) |
| 청킹 | 로그·티켓은 **엔트리 단위**(줄 번호·타임스탬프 보존), 런북은 구조 기반 + **절차 단계 보존**(단계를 자르지 않음) + parent-child, 채팅은 스레드 단위 | 토큰 고정 분할 | 2/02 선택 가이드: "평문·로그·트랜스크립트라면 → 재귀 분할 + parent-child. 자연 경계만 존중", "문서에 제목 계층이 있다면 → 구조 기반". 런북 단계가 조치의 근거 단위이므로 단계 경계가 곧 청크 경계 | [2/02](../02-data-pipeline/02-chunking-strategies.md) |
| 메타데이터·출처 | 다섯 축 + 서비스·컴포넌트·환경(prod/stg)·팀 택소노미, **런북 버전·`superseded_by` 필수**, 인시던트는 시간 구간·심각도·해결 상태, PROV로 "LLM 추출 원인 관계" 표시 | 평면 메타데이터 | 2/03 선택 가이드: "권한이 있거나 운영 서비스라면 → 구조화 스키마 + 별도 저장소 + 불변 버전", "생성물이 섞인다면 → PROV 어휘". 낡은 런북 단계를 실행하면 사고다 | [2/03](../02-data-pipeline/03-metadata-provenance.md) |
| 임베딩·인덱싱 | **BM25 비중 높은 hybrid**, 기존 로그 검색엔진 재사용. 에러 코드·호스트명·서비스명 정확 매칭, 한국어 형태소 분석. **원시 로그는 BM25만**, 티켓·알림 요약·런북만 dense 임베딩 | 전용 벡터DB + 로그 전수 임베딩 | 2/04 선택 가이드: "질의가 코드·ID·고유명사 중심이라면 → BM25 비중을 높인 hybrid", "이미 검색엔진을 운영 중이라면 → 그 엔진의 벡터 기능으로 hybrid". 2/99 C 한계: "로그 양이 커 전수 임베딩은 비용↑" | [2/04](../02-data-pipeline/04-embedding-indexing.md) |
| 지식그래프 | **경량 그래프 적극 도입**: 서비스–의존–컴포넌트–담당 팀–런북–과거 인시던트. ## 4. 전체 아키텍처

시각화: [`assets/html/scenario-ops-incident.html`](../assets/html/scenario-ops-incident.html) — 선택한 노드만 진하게, 뺀 노드(Declarative UI, A2UI·MCP Apps, 장기 메모리, GraphRAG 글로벌 요약, A/B 등)는 흐리게. 번호는 아래 흐름과 같다.

알림 1건("결제 API 5xx 비율 급증")과 온콜 담당자의 요청("원인이랑 조치안 줘")이 끝까지 흐르는 경로:

1. **[Knowledge → Reasoning]** 알림 웹훅이 단일 변경 큐로 들어온다. 수집 단계에서 고객 식별자 PII 마스킹, 환경·서비스 택소노미 태그 부착. 알림은 "외부 텍스트" 등급.
2. **[Reasoning]** `decide("severity")`·`decide("duplicate")` — 규칙(에러 코드·임계값·환경) → 소형 분류기, 결정 모델은 섀도. P2 판정, 기존 인시던트와 비중복 → 새 인시던트 상태 생성(체크포인트). 온콜 담당자에게 알림 카드.
3. **[Interaction → Reasoning]** 온콜 담당자가 모니터링 포털 위젯에서 "원인이랑 조치안 줘"를 입력 → AG-UI 이벤트 → Supervisor 상태 머신 입력. 담당자의 팀·권한·환경 범위가 요청 컨텍스트에 붙는다.
4. **[Reasoning]** Supervisor가 계획을 세우고 **진단 에이전트**에 위임(위임 판정은 규칙). 진단 에이전트는 Plan-and-Execute 루프(스텝 상한 8, 시간 상한): 가설 수립 → **변환기**가 자연어를 로그·메트릭 쿼리로 변환 → MCP 조회 툴(읽기 등급, 자동 실행) → 결과는 저장소 + 참조 ID(툴 출력 외부화) → 가설 검증 → 재계획. 동시에 런북·과거 인시던트를 hybrid(BM25↑)로 검색.
5. **[Knowledge → Reasoning]** Knowledge가 **근거 단위(계약 ①)**를 반환: `log_record`(에러 로그 줄·시각), `metric_window`(5xx 비율 구간·임계값·쿼리), `runbook_step`(결제 API 런북 v7 단계 3·4), `incident`(유사 과거 티켓 2건·해결 요약), 모두 환경·팀 사전 필터를 통과한 것.
6. **[Reasoning]** **영향 분석 에이전트**가 의존성 그래프를 멀티홉 탐색: 결제 API → `dependsOn` 인증 서비스(최근 배포 이벤트 발견) → `affects` 주문·구독 서비스 2개 → 과거 인시던트 연결. 결과는 `path` 근거 단위 + 원문(티켓·CMDB 레코드)으로 환원.
7. **[Reasoning]** **조치 제안 에이전트**가 런북 단계와 매칭된 조치 후보를 구조화 출력으로 생성: "인증 서비스 직전 배포 롤백"(비가역 등급) / "결제 API 재시작"(가역 등급). 각 조치에 근거 `evidence_id`, 영향 범위, 가역성. Supervisor가 종합 → 종합 전 **근거 부합 검증기**(규칙: citation 존재·수치 일치, NLI/결정 모델: 가설 ↔ 로그 함의) → Reflection 1회(평가자는 규칙 + 다른 모델).
8. **[Reasoning]** **Rule ∧ Model 게이트**: 규칙 — 변경 창 안인가, prod 보호 정책, 요청자 권한, 영향 서비스 수 ≤ 상한, 제안 조치가 현행 런북 v7 단계와 일치, 멱등 키 발급 가능 — 모두 참. `decide("requires_approval")` — 롤백은 비가역 등급이라 규칙상 **무조건 승인**, 재시작은 p 판정이지만 `[실측]` 전 θ 보수화로 **승인**. 섀도 결정 모델 판정 로그.
9. **[Reasoning → Interaction]** **렌더 가능한 응답(계약 ②)**: `text`(진단 요약·abstain 아님), `citations[]`, `ui_intent`(규칙 매핑: `ApprovalCard` × 2 + `ImpactGraph` + `EvidencePanel` + `DiffView`(롤백 대상 배포 diff)), 확신도(진단·승인 판정 각각), `requires_approval: true`, 시한·에스컬레이션 대상. 실행은 **체크포인트에서 정지**(내구 실행).
10. **[Interaction]** 운영 콘솔이 승인 카드를 렌더: 실행될 명령·대상·환경, 영향 범위 그래프(의존 서비스 3개), 근거(로그 줄·메트릭 구간·런북 단계·과거 인시던트), 가역성("롤백은 재배포로만 복구"), 확신도, 변경 창, 시한(15분 → 미응답 시 상위 온콜로 에스컬레이션, **만료 = 실행 안 함**). 기본 포커스는 "거절/상세 보기", `assertive` 라이브 영역.
11. **[Interaction → Reasoning]** 담당자가 "결제 API 재시작"은 승인, "롤백"은 인증 서비스 팀에 에스컬레이션 → **사용자 이벤트(계약 ③)**: `approve`(대상 조치 ID, `as_shown_hash`, `client_state_seq`, 승인자·시각) + `escalate`(대상 팀·사유). 서버가 hash·seq·승인자 권한·대리 권한을 재검증.
12. **[Action]** 조치 워크플로우(고정 그래프): 실행 직전 **규칙 최종 허가**(변경 창·권한 재확인) → MCP 변경 툴 "재시작"(멱등 키) → optimistic "전송됨" → 실행 결과 → `ProgressTimeline` 패치 → Reflection: 메트릭 쿼리로 5xx 비율 회복 확인(미회복 시 "원인 미확정" abstain + 사람 전담 전환). 에스컬레이션된 롤백은 인증 팀 승인 대기(체크포인트).
13. **[Cross-cutting]** 전 과정이 같은 trace_id로 에이전트별 스팬에 기록(MCP 경계 헤더 전파). **감사 레코드**: 근거 ID + 판정·규칙 ID·확신도(섀도 포함) + 승인 이벤트·hash·승인자 + 실행 결과를 불변 저장. 인시던트 종결 시 티켓·해결 요약이 Knowledge로 환류(이력, 톰스톤 아님).

## 7. 예상되는 한계와 2차 과제

**이 설계가 해결하지 않는 것**

- **승인 피로**. 인시던트 중 연속 승인이 반사적이 되면 HITL이 형식화된다. θ 완화(자동 범위 확대)는 보정 `[실측]` 뒤에만 가능하므로 초기에는 승인 수가 많다. 완화는 배치·세션 사전 승인, 카드 내용 압축, 승인 소요 시간 모니터([3/12](../03-agent-workflow-rag/12-guardrails-hitl.md), [4/06](../04-dynamic-ui/06-hitl-ui-patterns.md) 한계).
- **멀티 에이전트의 책임 귀속**. 진단이 틀렸는지 영향 분석이 틀렸는지 통합 점수로는 모른다 → 에이전트 단위 평가가 필수지만 비용이 곱이다([3/07](../03-agent-workflow-rag/07-multi-agent-orchestration.md) 한계).
- **결정 모델 장애 시 "모두 승인" 폴백으로 지연 증가**. 보수적이지만 야간 인시던트에서 승인자가 없으면 에스컬레이션 체인이 길어진다([3/99](../03-agent-workflow-rag/99-decision-matrix.md) C 한계).
- **CMDB가 낡으면 그래프도 낡는다**. 영향 범위가 틀리면 승인 카드가 틀린 것을 보여 준다. 대조 배치와 불일치율 모니터로 완화할 뿐([2/99](../02-data-pipeline/99-decision-matrix.md) C 한계).
- **LLM 원인 관계 추출의 환각**. 과거 인시던트 서술에서 뽑은 `causedBy`는 등급 B 이하·검증 근거 불허로 두므로 진단의 "참고"에 그친다.
- **타 조직 에이전트 연동(A2A)**·**MCP Tasks(장기 실행)**는 2차. A2A 1.0 전용 발표 미확인 `[2차]`, MCP 2026-07-28 개정 세부는 공식 changelog 재확인 권장.
- **자율 탐색의 비용 상한**이 진단 품질을 제한한다. 상한에 걸리면 abstain으로 사람 전담 전환.

**규모 10배(서비스 수천, 알림 하루 수천, 팀 수백)가 되면 바뀌는 것**

- Supervisor → Hierarchical(서비스 도메인별 Supervisor), 툴 100개 초과 → 툴 검색·계층 에이전트(3/09 조건).
- 판정 건수가 커져 결정 모델의 비용·지연 이점이 실질적이 되고, 승인 피로 해소를 위해 θ 완화 압력이 커진다 → 보정 `[실측]`과 사후 되돌림률이 더 중요해진다.
- 로그 인프라 쿼리 비용·동시성 상한, 변환기 쿼리 캐시(시간 구간 포함 키) 필요.
- 팀 간 툴 소유가 조직 경계를 넘으면 MCP 서버별 인증·권한·감사·레이트 리밋 설계가 생존 조건(3/09 한계 "프로토콜이 보안·멀티테넌시를 정의하지 않음").

**트렌드 축을 채택으로 올리기 위해 필요한 `[실측]`**

| 축 | 필요한 실측 | 판단 기준 |
|---|---|---|
| 결정 모델 | 5개 판정 지점의 한국어 혼합 평가셋 정확도·ECE·세 갈래 비율·지연·비용(Jev / Decisions API / 분류기 동일 셋), 승인 판정의 사후 되돌림률 | 지점별로 분류기 동등 이상 + 보정 확인. **승인 필요 판정은 사람 판정 대비 되돌림률이 낮을 때만** θ 완화 |
| 뉴로심볼릭 | 게이트 차단률·오탐률, 승인 후 규칙 차단 건수(규칙과 사람의 불일치), 변환기 쿼리 오류율 | 오탐이 MTTR을 늘리지 않는 수준, 금지 단계 위반 0건 유지 |
| 온톨로지 | 영향 범위 예측 정밀도·재현율, CMDB 불일치율, 경로 근거의 사용자 확인율 | 영향 분석이 사람 판단보다 넓고 정확한 범위를 제시 |

## 9. 운영 계획 — 이 시나리오를 운영 상태로 유지하기

용어는 [Part 1/07](../01-foundations/07-operations-vocabulary.md), 단계별 상세는 각 페이지의 "운영 설계" 섹션, 종합은 [Part 5/06](../05-cross-cutting/06-operational-design-matrix.md). 이 시나리오는 **통제를 공급하는 시스템 자체가 장애를 겪을 때** 어떻게 동작하는가가 운영의 전부다. 원칙은 3/12와 같다 — 가드레일·승인·결정 모델의 장애는 "통제 없음"이 아니라 **"보수적 통제"**(모두 승인, 만료 = 실행 안 함, 멱등 불확실 = 실행 안 함)로 떨어져야 한다. 그 대가는 승인 적체와 MTTR 증가이며, 이를 감수하는 것이 설계 결정이다. 승인자는 교대 온콜이라 **역할 기반**으로만 적는다. 수치는 모두 **예시**이며 12주차 파일럿 뒤 재설정한다.

### 9.1 E2E SLO와 레이어별 SLI (예시값)

| 지표 (사용자 관점) | 목표 (예시) | 측정 위치 — 받치는 레이어·단계 SLI | 위반 시 런북 (한 줄) |
|---|---|---|---|
| **심각도 판정 정확도** (과소 판정은 별도) | 정확도 ≥ 90%, **과소 판정(실제 P1을 P3 이하로) ≤ 2%** | Reasoning: 2/09·3/02 `decide("severity")` 정확도·ECE(과거 티켓 라벨), 폴백율 · Knowledge: 알림 택소노미 태그 누락률 | 과소 판정 1건 → 해당 에러 코드·서비스의 규칙 임계값 **보수화(상향)**, 분류기 직전 버전 롤백. 결정 모델 섀도 불일치율 급등이면 벤더 변경 확인 |
| **승인 응답 시간 / 만료율** | 1차 승인자 p95 ≤ 15분(인시던트 중), 만료율 ≤ 5%, 에스컬레이션 비율 ≤ 20% | Reasoning: 3/12 승인 대기 p95, 큐 길이, 역할별 활성 승인자 수 · Interaction: 4/06 승인 카드 표시 성공률 **100%**, 타임아웃 미처리 0건 | 만료율 급등 → 역할별 활성 승인자 수 0인 역할 확인 → 디렉터리 매핑 당일 수정. 카드 미표시 1건 → 즉시(안전 결함) |
| **승인 없는 변경 / 이중 실행 / 승인 후 규칙 차단** | 승인 없는 변경 **0건**, 이중 실행 **0건**, 승인 후 규칙 차단은 측정(규칙과 사람의 불일치 신호) | Reasoning: 3/10 Rule ∧ Model 게이트 로그, 3/09 멱등 키 충돌(허용) vs 실제 중복(불허), 실행 직전 재허가 결과 · Interaction: 4/04 `as_shown_hash`·`client_state_seq` 불일치 거부 | 승인 없는 변경·이중 실행 1건 → **변경 툴 전체 킬 스위치**(조회·진단은 유지) + break-glass급 사후 감사. 승인 후 규칙 차단 급증 → 승인 카드 내용(변경 창·영향 범위 표시) 리뷰 |
| **사후 되돌림률** (실행 후 되돌린 조치) | < 2%, 사람 단독 판정 베이스라인 이하 | Interaction: 4/06 되돌림률 · Reasoning: 3/11 `requires_approval` ECE·세 갈래 비율, 3/06 Reflection 회복 확인 실패율 | 상승 → θ를 보수적 방향으로만 이동(자동 범위 축소), 조치 제안 에이전트의 런북 일치 규칙 점검. θ 완화는 이 지표가 베이스라인 이하일 때만 |
| **MTTR 기여** — 진단 보고서 도달 시간, 원인 적중률 | 알림 → 진단 보고서 p95 ≤ 5분, 원인 적중률 ≥ 70%(사후 RCA 대비), 상한(스텝 8·시간) 초과율 ≤ 10% | Reasoning: 3/06 스텝 수·시간 상한 초과율, 3/03 런북 단계 recall, 3/07 핸드오프 라우팅 정확도 · Knowledge: 2/05 영향 범위 정밀도·재현율, 변환기 쿼리 오류율, 로그 인프라 쿼리 p95 | 상한 초과율 급등 → 변환기 쿼리 오류·로그 인프라 지연 확인 → 진단 에이전트는 "원인 미확정" abstain으로 사람 전담 전환(저하). 적중률 하락 → 프롬프트·모델 버전 역추적 |
| **런북 구판 인용 / 근거 부합** | 구판 `runbook_step` 인용 **0건**, 근거 부합 검증 통과율 ≥ 95% | Knowledge: 2/03·2/07 `superseded_by` 반영 지연, CMDB 대조 불일치율 · Reasoning: 3/04 citation 존재·수치 일치 규칙, NLI/결정 모델 근거 부합 | 구판 인용 1건 → 런북 커넥터 동기화 점검 + 해당 런북 검색 차단. 불일치율 상승 → 주 1회 대조를 즉시 실행 |
| **감사 레코드 재구성 가능률** | **100%** — 실행된 변경 전 건을 레코드만으로 "누가 무엇을 보고 승인했나" 재구성 | 횡단: 5/04 필수 필드 존재 검사(CI), MCP 경계 trace 전파 끊김률 | 필수 필드 누락 → **배포 차단**. 전파 끊김 → 헤더 전파 규약 점검, 끊긴 구간의 변경 실행 금지 |

오류 예산을 소진하면 프롬프트·θ·툴 등록 변경을 동결한다. 단 **보수적 방향의 변경**(θ 상향, 규칙 추가, 툴 비활성)은 동결 대상이 아니다.

### 9.2 장애 시나리오 3개 — 무엇이 죽으면 사용자에게 어떻게 보이고 누가 뭘 하나

세 장애는 통제 체인(판정 → 승인 → 실행)의 세 고리 각각이 끊어지는 경우다. 공통 원칙: **의심스러우면 실행하지 않는다**. 야간 교대 중 발생이 전제이므로 모든 자동 대응은 사람이 깨어나기 전에 안전 상태에 도달해야 한다.

| 장애 | 증상 (사용자에게) | 자동 대응 | 사람 개입 | 복구 후 |
|---|---|---|---|---|
| **① 결정 모델 다운·타임아웃** (심각도·승인 필요 판정 불가) | 모든 알림이 **보수적 심각도**(규칙 상향)로 뜨고, 가역 등급 조치까지 **전부 승인 카드**로 감 → 승인 요청 수 급증, 온콜 피로 | 3/11 `decide()` 폴백 순서: 규칙 기본 경로 → 동일 입력 캐시 → **보수적 경로**(심각도는 규칙 임계값, `requires_approval`은 "승인 필요", 근거 부합은 "표시 보류 + 사람 검토"). 서킷 브레이커 개방, 트레이스·감사 레코드에 `fallback=true`. 섀도였다면 운영 영향 없음 — 운영 승격 후라면 이전 구현체(분류기)로 자동 전환 | 폴백율 5분간 20% 초과 → 플랫폼 온콜. 승인 적체가 2차 효과로 오면 아래 ②의 절차. **θ를 완화해 승인 수를 줄이지 않는다** | 보정 재측정(폴백 구간 판정은 평가셋에서 제외), 벤더 변경 내역 확인 후 복귀. 폴백 구간의 승인 건은 사후 샘플링 100% |
| **② 승인자 부재·승인 적체** (야간, 역할에 활성 승인자 0명, 또는 P1 중 승인 요청 수십 건) | 승인 카드가 **시한 내 처리되지 않고 에스컬레이션** → 상위 온콜 → 최종 만료 = **실행 안 함**. 사용자(온콜)는 "조치가 승인 대기 중"만 본다 | 3/12: 에스컬레이션 체인(1차 승인자 → 상위 온콜 → 서비스 소유 리드, 대리 권한 검증) → 체인 끝이면 **만료 = 거부** + 운영 알림. 자동 승인으로 넘어가는 경로는 **없다**. 큐 길이 상한(예시 승인자당 20건) 초과 시 백프레셔 — 신규 승인 필요 조치는 "지연 안내", 조회·진단은 계속. 체크포인트에서 실행 정지 상태 유지(내구 실행) | 역할에 활성 승인자 0 → 운영 책임자가 당일 배정. P1이고 승인 경로 전체가 작동 불능이면 **break-glass**(9.4): 당직 아키텍트 단독, 사유 필수, 시간 제한 | 만료된 조치 제안은 재실행하지 않고 **재제안**(상황이 바뀌었을 수 있음). 매트릭스 정합성(역할 ↔ 사람) 주간 점검을 당겨 실행. 반복되면 야간 NOC 역할 신설 또는 가역 등급 세션 사전 승인 검토 |
| **③ 툴 실행 중 부분 실패** (재시작 대상 3개 인스턴스 중 1개 타임아웃, 롤백이 중간에 끊김) | `ProgressTimeline`에 "부분 완료", Reflection 회복 확인 실패 → **"원인 미확정 · 사람 전담"** abstain. optimistic "전송됨"이 "부분 실패"로 교체 | 3/09: 멱등 키로 재시도 안전한 단계만 **상태 조회 후** 재시도(상한 예시 2회), 타임아웃 계층(툴 < 노드 < 실행). 가역 등급(스케일·재시작)의 **보상은 자동**(원복 명령, 같은 멱등 키 체계, 감사 레코드에 `compensation`). 비가역 등급(롤백·설정)의 보상은 **자동 실행 금지** — 보상 후보를 제안만 하고 사람 전담으로 전환. 조치 워크플로우는 체크포인트에서 정지 | 즉시 서비스 소유 팀 온콜 + 요청 온콜. 부분 실패 상태(어느 인스턴스가 어떤 상태인지)를 `EvidencePanel`에 조회 결과로 제시. 비가역 보상은 사람이 자기 콘솔에서 실행 | 부분 실패 원인(툴 타임아웃 설정·멱등 미지원 레거시 API)을 툴 인벤토리에 기록, 해당 툴 등급·타임아웃 재조정. 멱등 키 미지원 툴은 **운영 배포 불가**로 되돌림(ORR 항목) |

**위험 등급과의 연결**: ①은 등급 3~4 행동(prod 변경)의 **판정 수단** 장애라 폴백이 "승인 필요"로 가는 것이 미탐 방지의 마지막 선이고, 그 비용(승인 적체)이 ②로 이어진다. ②에서 "만료 = 승인"이나 θ 완화로 적체를 풀면 등급 4 행동이 통제 없이 실행되므로 금지한다. ③은 등급 3(가역)과 4(비가역)에서 보상 정책이 다르다 — 가역은 자동 보상, 비가역은 제안만. 세 장애 모두 **조회·진단 경로는 살아 있어야** 한다(저하지 중단이 아님).

### 9.4 거버넌스 — RACI, 위험 등급표, 승인 매트릭스, 감사 필드

**RACI** — 플랫폼 팀이 에이전트를 만들지만 **툴·런북·CMDB는 서비스 팀과 CMDB 소유자가 A**다. 변경 관리 책임자와 운영 총괄이 게이트·승인의 A를 맡아 "만든 사람이 통제를 정하지 않게" 한다.

| 대상 | R (실행) | A (책임) | C (자문) | I (통보) |
|---|---|---|---|---|
| 진단·영향·조치 프롬프트, 결정 질문 정의, θ | 플랫폼 AI 엔지니어 | 플랫폼 팀 리드 | SRE 리드 | 서비스 팀 |
| 결정 모델·LLM 버전, 프레임워크(LangGraph/ADK) | 플랫폼 | 아키텍트 | 보안(로그 본문 외부 전송) | 전체 |
| 게이트 규칙(변경 창·prod 보호·승인자 분리·영향 상한·런북 일치) | 플랫폼 SRE | **변경 관리 책임자** | 보안, 서비스 소유자 | 온콜 전체 |
| 승인 매트릭스·에스컬레이션 체인·break-glass 역할 | SRE 운영 책임자 | **운영 총괄** | 보안, 법무 | 전체 |
| 툴(MCP 서버 툴 정의·등급·멱등·권한) | 각 서비스 팀 | **서비스 소유자** | 플랫폼, 보안 | SRE |
| 런북 내용·버전·`superseded_by` | 각 서비스 팀 | 서비스 소유자 | SRE | 플랫폼 |
| 서비스 토폴로지 온톨로지·의존성 그래프 | 데이터 엔지니어 | **CMDB 소유자** | 플랫폼, 서비스 팀 | 전체 |
| 레지스트리 10여 개·승인 카드·diff·접근성 | 포털 프론트 | 운영 콘솔 디자인 책임자 | 접근성, SRE | 플랫폼 |
| 감사 저장소·보존·PII 마스킹·헤더 전파 | 플랫폼 | **보안 책임자** | 법무, 내부 감사 | 전체 |

**위험 등급표** — 1/07 축(가역성 × 영향 범위)에 놓는다. 영향 범위는 B2B 고객 서비스이므로 prod 변경은 모두 "조직 외부"다.

| 등급 | 이 시나리오의 행동 | 필수 통제 |
|---|---|---|
| 1 | 진단 보고서·영향 그래프·타임라인 표시, abstain 안내 | 출력 가드레일(PII·근거 없음) + 로그 |
| 2 | 로그·메트릭·CMDB·런북 **조회**(변환기, 읽기 전용, prod 포함 — 고객 식별자 포함 데이터), 티켓 코멘트·채널 알림(내부 전송), stg 변경(재시작·스케일·롤백) | 권한 사전 필터 + PII 마스킹 + 규칙 게이트 + 감사 |
| 2→3 | 알림 본문·로그(외부 텍스트)를 읽은 세션의 외부 전송(고객 공지 채널·외부 티켓) | 등급 상향 규칙 + 승인 1인 |
| 3 | **prod 변경-가역**: 재시작·스케일·캐시 퍼지(가역 × 고객 영향) | Rule ∧ Model + 승인 1인(승인자 ≠ 요청자) + 자동 보상(원복) + 실행 직전 재허가 |
| 4 | **prod 변경-비가역·부분 가역**: 배포 롤백·설정 변경·피처 플래그 / 게이트 규칙·매트릭스·θ 변경 / 툴 등록·등급 변경 | 승인 2인(승인자 분리) + 쓰기 모의 섀도 기간 + 실행 직전 재허가 + 보상은 제안만 |
| 5 | 데이터 삭제·DB 스키마·IAM·결제 설정 변경 | **에이전트 자동 실행 금지** — 해당 툴을 MCP 서버에 등록하지 않음. 제안 + 런북 링크만 |

**승인 매트릭스** — 3/12 형식. 요청자는 대부분 "에이전트(온콜 대리)"이므로 요청자 역할은 **세션의 온콜 담당자**로 본다. 등급 3 이상 빈 행 없음을 CI에서 확인한다.

| 행동 유형 | 영향 범위 | 요청자 역할 | 승인자 (역할) | 승인 수 | 시한 → 에스컬레이션 | 만료 시 | 등급 |
|---|---|---|---|---|---|---|---|
| 조회(로그·메트릭·CMDB·런북·과거 인시던트) | 요청자 팀·환경 범위 | 온콜·서비스 팀 | 없음 (권한 사전 필터 + PII 마스킹 + 감사) | 0 | — | — | 2 |
| 티켓 갱신·내부 채널 알림 | 내부 여러 사용자 | 에이전트(자동) | 없음 (규칙 게이트 + 감사). 외부 텍스트 읽은 세션은 온콜 1인 | 0 / 1 | 10분 → 없음 | 전송 안 함 | 2→3 |
| stg 변경(재시작·스케일·롤백) | 내부 | 서비스 팀 | 요청자 본인(동기) | 1 | 15분 → 없음 | 실행 안 함 | 2 |
| prod 변경-가역, **변경 창 내** | 고객 영향·가역 | 온콜 SRE | 서비스 소유 팀 온콜 1인 (**요청자 ≠ 승인자**) | 1 | 15분 → 상위 온콜 → 30분 만료 | 실행 안 함 + 재제안 | 3 |
| prod 변경-가역, **변경 창 밖** | 고객 영향·가역 | 온콜 SRE | 서비스 소유 온콜 + 변경 관리자 당직 | 2 | 15분 → 각 상위 → 30분 만료 | 실행 안 함 | 3→4 |
| prod 변경-비가역(롤백·설정·플래그) | 고객 영향·부분 가역 | 온콜 SRE | **서비스 소유 팀 리드 + 변경 관리자 당직** (승인자 분리, 요청자 제외) | 2 | 15분 → 각 상위 → 45분 만료 | 실행 안 함 + 사람 전담 전환 | 4 |
| 영향 서비스 수 > 상한(예시 5) 또는 P1 — 변경 유형 무관 | 광범위 | — | 인시던트 커맨더 + 서비스 소유 리드 (Parallel Vote 결과 카드에 첨부) | 2 | 10분 → 운영 총괄 → 30분 만료 | 실행 안 함 | 4 |
| 데이터 삭제·스키마·IAM·결제 설정 | 비가역·외부 | — | **에이전트 금지** — 제안 + 런북 링크, 실행은 사람이 자기 콘솔에서 | — | — | — | 5 |
| **break-glass** (승인 경로 장애 또는 P1 중 승인자 전원 부재) | — | 당직 아키텍트(사전 지정 1인) | **단독** — 사유 입력 필수, 예시 2시간 후 자동 복원, 사용 즉시 보안 책임자·운영 총괄 알림, **72시간 내 2인 사후 감사**(정당성·영향·재발 방지). 등급 5 행동은 break-glass로도 불가 | 1 (사후 2) | — | 자동 복원 | 예외 |
| 게이트 규칙·매트릭스·θ 변경 / 툴 등록·등급 변경 | 전 사용자 | 플랫폼 / 서비스 팀 | 변경 관리 책임자 + 운영 총괄 / 서비스 소유자 + 플랫폼 + 규칙·툴 계약 테스트 + 시행일 | 2 | 1영업일 → 없음 | 배포 안 함 | 4 |

break-glass는 **쓰이지 않는 것이 정상**이다. 분기당 사용 건수와 사후 감사 결과를 운영 총괄 리뷰에 보고하고, 반복 사용은 정상 경로(에스컬레이션 체인·야간 승인자 배치)의 설계 결함으로 본다(3/12 예외 처리 절차).

**감사 필드** — 3/12 감사 레코드 스키마를 **거의 전부** 쓰고, 멀티 에이전트·영향 범위·보상 정보를 더한다. 실행된 변경 1건 = 1레코드, append-only·해시 체인, 보존은 변경 관리 정책 기간, 로그 본문은 참조 ID만(PII 마스킹 후).

| 블록 | 필드 | 왜 필요한가 |
|---|---|---|
| 상관 키 | `record_id`, `incident_id`, `run_id`, `checkpoint_id`, `trace_id`, `agent_span_ids[]`(Supervisor·진단·영향·조치) | MCP 경계를 넘은 에이전트별 스팬과 연결, 책임 귀속 |
| 요청자·승인자 | `requester: {user_id, role, team, env_scope, channel}`, `approval.approvers[]: {role, user_id, at, decision}`, `separation_verified: bool` | 승인자 분리(요청자 ≠ 승인자, 2인이 서로 다른 역할) 증명 |
| 판정 | `severity: {choice, p, source, question_version, fallback}`, `requires_approval: {choice, p, θ_auto, θ_review, source, fallback}`, `rule_and_model: {rule_result, model_result, combined}` | 결정 모델 폴백 구간의 판정과 Rule ∧ Model 양쪽 결과 |
| 근거·영향 | `evidence_refs[]` 타입별 — `log_record{ref_id, ts}`, `metric_window{query_hash, range}`, `runbook_step{runbook_id, version, step_no}`, `incident{ticket_id}`, `path{path_id}`; `impact: {predicted_services[], path_ids[], count, cmdb_snapshot_version}` | "어느 런북 버전 어느 단계였나", "영향 범위를 무엇으로 계산했나" |
| 규칙·변경 창 | `rules_applied[]: {rule_id, rule_version, result, matched_condition}` — 변경 창·prod 보호·승인자 분리·권한·영향 상한·런북 일치·멱등 가능; `change_window: {in_window, window_id}` | 어떤 규칙이 통과시켰나 |
| 행동·승인 카드 | `action: {tool, tool_version, tool_def_hash, args_hash, args_redacted, effect_grade, risk_level, reversible, env, session_flags}`, `approval: {approval_id, matrix_row_id, matrix_version, as_shown_hash, client_state_seq, card_shown: {command, target, env, impact_graph_hash, evidence_refs[], reversible_display, p_display, window_display, expires_at}, escalations[], expired}` | **승인자가 실제로 본 명령·영향 범위·근거**를 복원 |
| 실행·보상 | `pre_exec_rule_recheck: {result, at}`, `execution: {executed, executed_at, idempotency_key, args_hash_verified, result_code, partial_failure?: {succeeded[], failed[]}}`, `compensation?: {proposed_action, auto_executed: bool, actor, at}`, `reflection: {recovery_metric, result}` | 실행 직전 재허가, 부분 실패와 보상이 자동이었는지 사람이었는지 |
| 예외 | `exception?: {type: review\|break_glass, exception_id, actor, reason, auto_restore_at, post_audit_ref}` | break-glass 사후 감사 연결 |
| 버전 | `versions: {policy_set, rule_set, approval_matrix, runbook_index, ontology, cmdb_snapshot, tool_catalog, decision_question, prompts: {supervisor, diagnose, impact, remediate}, llm, framework}` | 시점 재현 키 — 에이전트별 프롬프트 버전까지 |

관측 트레이스에는 지연·토큰·스텝 수를, 감사 레코드에는 위 블록만 둔다. 섀도 결정 모델 판정은 관측에만 남기되, **폴백 여부(`fallback`)는 감사에 반드시** 남긴다.

### 9.5 운영 준비도 리뷰(ORR) 통과 조건

prod 가역 등급 연결(11주차) 전에 아래가 모두 체크되어야 하며, 비가역 등급 연결은 파일럿(12주차) 결과까지 본 뒤 별도 ORR을 거친다.

- [ ] **[Knowledge]** CMDB 변경 이벤트가 의존성 그래프에 증분 반영되고, 주 1회 대조 불일치율과 영향 범위 정밀도·재현율이 대시보드에 있다
- [ ] **[Knowledge]** 런북 개정이 구판 보존(`superseded_by`)으로 반영되며, 구판 `runbook_step` 인용 0건 검사가 CI와 운영에 있다
- [ ] **[Knowledge]** 환경(prod/stg)·팀 사전 필터 누출 0건, 로그 속 고객 식별자 PII 마스킹이 수집·조회 결과 양쪽에서 확인된다
- [ ] **[Knowledge]** 권한 서비스 다운 시 조회 툴이 fail-closed이고, 원시 로그는 복제 없이 기존 저장소 쿼리로만 접근된다
- [ ] **[Reasoning]** 결정 모델 다운 시 `decide()` 폴백이 "보수적 경로"(심각도 상향·모두 승인·표시 보류)로 가고, 감사 레코드에 `fallback=true`가 남는다
- [ ] **[Reasoning]** 변경 명령은 Rule ∧ Model 양쪽 참일 때만 승인 카드로 가며, 승인 후 **실행 직전 규칙 재허가**가 별도로 실행된다
- [ ] **[Reasoning]** 등급 5 툴(데이터 삭제·스키마·IAM·결제 설정)이 MCP 서버에 등록되어 있지 않고, 툴 인벤토리 전 건에 등급·멱등 키·소유 팀이 있다
- [ ] **[Reasoning]** 멱등 키 없는 쓰기 툴이 없고, 쓰기 모의 섀도에서 이중 실행 0건·승인 없는 변경 0건(트래젝토리 금지 단계)이 N=5 반복으로 확인되었다
- [ ] **[Reasoning]** 체크포인트 저장소 장애 시 새 전이를 중단하고 쓰기 툴 실행은 자동 재개하지 않으며, 부분 실패 시 가역 보상만 자동·비가역 보상은 제안만임이 테스트되었다
- [ ] **[Interaction]** 승인 카드 표시 성공률 100%가 보장되고(미표시 시 텍스트 폴백 금지, `AWAITING_APPROVAL` 유지), 기본 포커스가 비승인 요소다
- [ ] **[Interaction]** 타임아웃 만료 = 실행 안 함, 에스컬레이션 체인 끝 = 거부, 자동 승인 경로 부재가 상태 머신 테스트로 확인되었다
- [ ] **[Interaction]** `as_shown_hash`·`client_state_seq` 불일치 시 거부 + 카드 재제시가 동작하고, 멱등 키 저장소 장애 시 승인 이벤트가 거부된다
- [ ] **[횡단]** 승인 매트릭스에 개인 이름이 없고 역할 ↔ 사람이 디렉터리 조회이며, 등급 3 이상 빈 행 없음과 역할별 활성 승인자 ≥ 1이 주간 배치로 점검된다
- [ ] **[횡단]** break-glass 경로가 있고 사용 시 사유 필수·자동 복원·즉시 알림·72시간 사후 감사 레코드가 자동 생성되며, 등급 5에는 적용되지 않는다
- [ ] **[횡단]** 실행된 변경 1건을 감사 레코드만으로 "누가 무엇을 어떤 근거·영향 범위를 보고 승인했고 규칙 버전은 무엇이었나"까지 재구성하는 리허설을 마쳤고, 7개 E2E SLO 알림마다 런북이 있으며, 승인 UI는 A/B 대상에서 제외되어 있다
