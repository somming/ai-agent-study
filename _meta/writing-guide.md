# 작성 가이드

이 위키의 모든 페이지가 따르는 규칙. 새 페이지를 쓰기 전에 반드시 읽는다.

## 1. 이 위키가 답해야 하는 질문

이 위키는 **프로젝트 수행 가이드**다. 모든 기술 페이지는 독자가 다음 네 질문에 답할 수 있게 써야 한다.

| 질문 | 페이지가 반드시 담아야 하는 것 |
|---|---|
| **무엇을** | 이 단계가 책임지는 산출물과 그 품질 기준 |
| **언제** | 이 단계가 필요한 조건, 생략해도 되는 조건, 나중으로 미뤄도 되는 조건 |
| **어떻게** | 표준 진행 절차와 산출물 템플릿, 흔한 실수 |
| **왜** | 생략하거나 잘못 선택했을 때 실제로 생기는 문제 |

기술을 소개만 하고 끝나는 페이지는 미완성이다. **"이 상황이면 A, 저 상황이면 B, 둘 다 아니면 C"** 가 표로 나와야 완성이다.

## 2. 페이지 템플릿

- 기술 페이지: [`_templates/page.md`](../_templates/page.md)
- 결정 매트릭스: [`_templates/decision-matrix.md`](../_templates/decision-matrix.md)
- 트렌드 심화: [`_templates/trend.md`](../_templates/trend.md)
- 시나리오(부록): [`_templates/scenario.md`](../_templates/scenario.md)

섹션 순서는 바꾸지 않는다. 해당 없는 섹션은 삭제하지 말고 "해당 없음 — 이유"를 한 줄 적는다.

## 3. 프론트매터

```yaml
---
title: "페이지 제목"
part: 02-data-pipeline            # 디렉터리명과 동일
stage: indexing                   # ingestion | indexing | knowledge | retrieval | reasoning | action | interaction | all
tags: [chunking, rag]             # 소문자 영문, 하이픈
maturity: 채택                    # 채택 | 시험 | 관찰 | 보류 | 미정  (트렌드 레이더와 동일 어휘)
status: stub                      # stub | draft | review | done
updated: 2026-10-11
---
```

`stage` 는 레퍼런스 아키텍처의 파이프라인 단계와 1:1로 맞춘다. HTML 시각화에서 단계를 클릭하면 같은 `stage` 태그를 가진 페이지로 이동한다.

## 4. 기술 비교표 작성 규칙

모든 기술 페이지에 들어가는 비교표의 열은 고정이다.

| 열 | 작성 기준 |
|---|---|
| 기술 / 접근 | 고유명사 또는 패턴명. 벤더 제품은 제품명 그대로 |
| 적합한 상황 | 데이터 특성·규모·지연 요구·팀 역량 등 **판단 가능한 조건**으로 서술 |
| 부적합한 상황 | 반드시 채운다. 비어 있으면 비교표가 아니다 |
| 비용·복잡도 | 하 / 중 / 상 + 한 줄 근거 (토큰 비용, 인프라, 학습 곡선) |
| 성숙도 | 표준 / 안정 / 신생 / 실험 |
| 검증 수준 | 아래 5절 표기 |

## 5. 검증 수준 표기 (필수)

모든 수치·성능 주장·참고 문헌에 다음 중 하나를 붙인다.

| 표기 | 의미 | 예 |
|---|---|---|
| `[검증]` | 독립 벤치마크, 피어리뷰 논문, 표준 문서 | arXiv 논문의 벤치마크 수치, W3C 스펙 |
| `[벤더]` | 벤더 자체 주장. 수치는 재검증 전까지 인용만 | "200배 빠르다" 류의 출시 자료 |
| `[2차]` | 블로그, 해설 기사, 커뮤니티 글 | 프레임워크 비교 블로그 |
| `[실측]` | 우리가 직접 측정 | 사내 PoC 결과 |

원칙: **`[벤더]`와 `[2차]`만으로 기술을 "채택"으로 분류하지 않는다.** 채택은 `[검증]` 또는 `[실측]`이 있어야 한다.

## 6. 트렌드 서술 규칙

- 기간: **최근 1년 (2025-10 ~ 2026-10)** 에 각광받은 것만 트렌드로 분류. 그 이전 것은 기반 지식으로 서술
- 트렌드는 두 곳에 쓴다. `06-trends/` 심화 페이지는 "무엇인가", 각 단계 페이지의 "최신 트렌드 적용" 섹션은 "이 단계에서 어떻게 쓰는가"
- 필수 주제: **온톨로지, 뉴로심볼릭, 결정 모델(TypeSafe AI Jev, OpenAI Decisions API)**. 관련 있는 모든 단계 페이지에서 적용 여부를 명시한다 (적용 안 되면 "해당 없음 — 이유")
- 날짜·버전·수치는 출처와 검증 수준을 반드시 붙인다. 소스가 충돌하면 충돌 사실을 적는다

## 7. HTML 시각화 규칙

- 위치: `assets/html/`. 파일명은 kebab-case
- 외부 CDN 없이 단일 파일로 동작 (오프라인 열람 가능)
- 레이어 색상 고정: Knowledge `#2E7D6B`, Reasoning `#3A5FA8`, Interaction `#B5651D`, Cross-cutting `#6B6B6B`
- 노드 클릭 시 해당 md 페이지로 이동 (상대 경로), 호버 시 한 줄 설명
- 라이트/다크 모두 가독. `prefers-color-scheme` 대응
- md 페이지에서는 상단 "시각화" 인용 블록으로 링크

## 8. 문체

- 본문 한국어, 기술 용어는 처음 등장 시 영문 병기
- 단정할 수 있으면 단정한다. 불확실하면 검증 수준으로 표시하고 넘어간다
- 한 문단 하나의 주장. 비교는 표로

## 9. 상태 전이

`stub` → `draft`(본문 작성) → `review`(비교표·한계·트렌드 섹션 완성) → `done`(검증 수준 표기 완료, 관련 페이지 링크 완료)

`_meta/CHANGELOG.md`에 상태 변화를 기록한다.
